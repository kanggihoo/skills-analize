# 공격 클래스

#### 공격 클래스 — Phase 1을 기반으로 선택하고 분할

애플리케이션 유형에 관련된 공격 클래스를 선택하라. 모든 클래스가 모든 코드베이스에 적용되는 것은 아니다. 아래 목록은 출발점이며, Phase 1에서 도출한 애플리케이션 고유 클래스를 추가하고 큰 코드베이스는 서브시스템별로 분할하라. 작업은 취약점을 찾고, 검증하고, 수정하고, 우선순위를 정하는 것으로 구성하라. 검증은 소스 검토와 제한된 로컬 픽스처로 한정하라. 페이로드 체인을 개발하거나, 라이브 서비스의 가용성을 테스트하거나, 공유 환경에서 조치를 취하지 마라.

`confirmed`는 소스 증거와 제한된 검증이 전체 경계와 의미 있는 결과를 입증할 때만 사용하라. 특정 배포, 제공자, 플랫폼, 신원, 또는 런타임 사실을 확인할 수 없을 때는 `needs_validation`을 사용하라. 누락된 사실과, 이를 해소하는 안전한 소유자 관찰 또는 로컬 검사를 명시하라.

> **네이티브 / 바이너리 / 커널 대상** (C/C++/Rust-unsafe, 커널 모듈, 파서와 디코더, FFI, 동시성 런타임, 바이너리 로더, JIT, 펌웨어): [MEMORY-SAFETY-AND-BINARY-KO.md](MEMORY-SAFETY-AND-BINARY-KO.md)의 메모리 안전성, 정수/ABI, 동시성, 바이너리 로더, 특권 인터페이스 클래스를 사용하라.
>
> **AI / LLM / 에이전트 대상** (챗봇, RAG, 영속 메모리, 도구 호출 에이전트, MCP 서버/클라이언트, 프롬프트 조립, 또는 모델이 제어하는 동작): [AI-AND-LLM-KO.md](AI-AND-LLM-KO.md)의 컨텍스트, 메모리 오염, 동작 바인딩, 도구 스키마, MCP 신원, 출력 클래스를 사용하라.
>
> **HTTP, 웹, 신원 대상** (일반 웹 앱, API, 리버스 프록시, CDN, 게이트웨이, 커스텀 HTTP 파서, 세션, CSRF, JWT, OAuth/OIDC, SAML, MFA, 패스키, 계정 복구/연결, API 키, 또는 mTLS): [WEB-PROTOCOL-AND-AUTH-KO.md](WEB-PROTOCOL-AND-AUTH-KO.md)를 사용하라.
>
> **클라이언트 측 및 브라우저 대상** (SPA, 브라우저 확장, 임베디드 웹뷰, 서비스 워커, 브라우저 스토리지, 윈도우 간 메시징, CORS, WebSocket, 또는 DOM 렌더링): [CLIENT-SIDE-KO.md](CLIENT-SIDE-KO.md)를 사용하라.

**인젝션(Injection)** (subagent_type: `general`)
신뢰할 수 없는 입력을 진입점에서 위험한 싱크(sink)까지 추적하라. "위험한 싱크"가 무엇인지는 애플리케이션에 따라 다르다.
- 웹 앱: SQL 쿼리, HTML 출력, 셸 명령, 템플릿 엔진, 파일 경로, HTTP 리디렉션, 역직렬화
- 라이브러리: 호출자가 제공한 데이터를 검증 없이 처리하는 모든 함수 — 버퍼 연산, 파서, 포맷 문자열
- CLI 도구: 셸 명령 구성, 파일 경로 처리, 환경 변수 보간
- 서비스: 쿼리 구성, 메시지 직렬화, 로그 인젝션, LDAP/XPATH 쿼리
- 클라이언트 측(브라우저/JS): DOM XSS, 프로토타입 오염, `postMessage`/오리진 신뢰, 그 밖의 브라우저 측 클래스 — 선택된 경우 [CLIENT-SIDE-KO.md](CLIENT-SIDE-KO.md) 컴패니언 블록이 다룬다

뻔한 직접 경로에서 멈추지 마라. 간접 인젝션을 찾아라. 데이터가 안전하게 저장된 뒤 다른 코드에 의해 조회되어 위험한 컨텍스트에서 사용되는 경우이다. 값만이 아니라 필드 이름, 키, 헤더, 메타데이터를 통한 인젝션을 찾아라. 보조 시스템(로그, 캐시, 검색 인덱스, 분석)으로의 인젝션을 찾아라.

**접근 통제(Access control)** (subagent_type: `general`)
호출자가 자신의 권한 밖의 일을 할 수 없는지 검증하라. 권한 검사가 존재하는지 확인하는 데 그치지 말고, *올바른* 자원에 대해 *올바른* 메커니즘으로 *올바른* 권한을 검사하는지 검증하라.
- 동일한 상태 변경에 이르면서 다른(더 약한) 권한을 검사하는 경로가 있는가?
- 요청 본문의 필드가 권한 시스템이 제한하려던 것을 덮어쓸 수 있는가?
- 인증으로만 게이트하고 인가를 잊은 엔드포인트가 있는가?
- 동일한 자원에 일관성 없는 검사를 가진 접근 경로가 여러 개 있는가?
- 대량/배치/내보내기/가져오기 연산은 항목별 권한을 강제하는가?

복잡한 접근 모델에서는 인증 우회와 인가 로직으로 나누어 별도 에이전트로 분할하라.

**자원 및 파일 처리** (subagent_type: `general`)
- 경로 탐색(의도한 디렉터리 밖의 읽기/쓰기) — 심볼릭 링크, 인코딩된 시퀀스, null 바이트를 통한 것을 포함
- SSRF(애플리케이션이 공격자가 제어하는 URL을 가져오게 하는 것) — 리디렉션, DNS 리바인딩, URL 파서 차이를 통한 것을 포함
- 안전하지 않은 역직렬화, 아카이브 추출(zip slip), 임시 파일 처리
- 메모리 안전성(해당하는 경우): 버퍼 오버플로, use-after-free, 정수 오버플로
- 파일 연산의 경쟁 조건(검사와 사용 사이의 TOCTOU)

**암호화 및 비밀** (subagent_type: `general`)
- 보안상 중요한 값(토큰, 키, nonce)에 대한 취약한 난수
- 하드코딩된 비밀, 로그, 오류 메시지, URL, 또는 클라이언트에 보이는 응답에 있는 비밀
- 깨진 키 유도, 누락된 HMAC 검증, nonce 재사용
- 비밀 비교에 대한 타이밍 부채널
- 암호 프리미티브의 오용(ECB 모드, 인증되지 않은 암호화, 정적 IV 등)
- 암호 연산이 실패하면 어떻게 되는가? 오류 경로가 암호화 없음으로 폴백하는가?

**비즈니스 로직** (subagent_type: `general`)
로직 오류는 수작업으로 찾아라. 표준 스캐너는 이를 찾지 못하며, 영향이 큰 발견 사항(finding)을 낳는다. 각 주요 워크플로에 대해 다음을 점검하라.
- **상태 머신 위반**: 단계를 건너뛸 수 있는가? 뒤로 갈 수 있는가? 유효하지 않은 상태에 도달할 수 있는가? 완료된 흐름을 재생(replay)하면 어떻게 되는가? 부분 실패는 어떤가 — 3단계 중 2단계가 실패하면 1단계가 롤백되는가?
- **비즈니스 영향이 있는 경쟁 조건**: 유효하지 않은 상태를 만드는 동시 연산(이중 지출, 이중 승인, 갱신 손실). 검사 후 실행(check-then-act)을 비원자적으로 수행하는 연산에 집중하라.
- **수치/수량 조작**: 음수 값, 0 값, 오버플로, 정밀도 손실, 문자열과 숫자 간 타입 강제 변환.
- **접근 경계 위반**: "권한 검사가 존재하는가"가 아니라 "그것이 비즈니스 규칙에 맞는 검사인가"를 묻는다. 한 연산에 대한 입력이 동일한 효과를 내는 다른 연산에 강제된 제한을 우회할 수 있는가?
- **암묵적 신뢰 가정**: 저장소, 구성, 다른 컴포넌트, 플러그인에서 온 데이터가 "들어올 때 검증했다"는 이유로 안전하다고 가정되는 경우. 다른 코드 경로가 그것을 썼다면 어떻게 되는가?
- **시간 기반 로직**: 만료 검사, 스케줄링, 속도 제한 윈도우, 시계 오차(clock skew). 정확한 경계 시점에 어떻게 되는가? 컴포넌트 간 시간대 차이는 어떤가?
- **기본값 및 폴백 동작**: 구성이 없을 때의 보안 상태는 어떤가? 기능 플래그가 꺼져 있을 때는? 의존성을 사용할 수 없을 때는? 시스템이 마이그레이션 중일 때는?

**기능 악용 및 데이터 유출** (subagent_type: `general`)
합법적인 기능이 의도하지 않은 목적으로 사용되는 경우. 코드뿐 아니라 설계의 버그를 찾아라.
- **유출 수단으로서의 내보내기/백업**: 낮은 권한의 사용자가 자신의 접근 수준 이상의 데이터를 포함하는 내보내기, 스냅샷, 백업을 트리거할 수 있는가? 다른 사용자의 데이터를 내보낼 수 있는가? 내보내기에 삭제된/초안/비공개 콘텐츠가 포함되는가? 정리되었어야 할 리비전 이력은?
- **인젝션 수단으로서의 가져오기/복원**: 가져오기가 기존 데이터를 덮어쓸 수 있는가? 일반 검증을 우회하는 레코드를 만들 수 있는가? 사용자에게 쓰기 권한이 없는 컬렉션에 콘텐츠를 주입할 수 있는가? UI와 동일한 권한 모델을 따르는가?
- **오라클로서의 검색/필터/정렬**: 검색 쿼리가 사용자가 직접 접근할 수 없는 콘텐츠의 존재 여부를 드러낼 수 있는가? 필터 매개변수로 사용자가 알아서는 안 되는 상태, 역할, 필드를 탐색할 수 있는가? 숨겨진 필드로 정렬하면 결과 순서를 통해 그 값이 드러나는가?
- **부수 효과를 통한 열거**: 오류 메시지가 "존재하지 않음"과 "접근 불가" 사이에서 다른가? 응답 시간이 다른가? 응답 크기는? HTTP 상태 코드는? 비밀번호 재설정, 초대, 가입 흐름으로 사용자를 열거할 수 있는가?
- **미리보기/초안/스테이징 유출**: 미리보기 토큰의 범위가 한 항목으로 한정되는가, 아니면 더 넓은 접근을 여는가? 초안 콘텐츠가 검색, RSS 피드, 사이트맵, API 목록 엔드포인트를 통해 발견될 수 있는가? 캐시 헤더 때문에 CDN이 비공개 콘텐츠를 공개적으로 제공할 수 있는가?
- **SSRF로서의 알림/웹훅**: 사용자가 서버가 가져가는 알림 URL, 웹훅 URL, 콜백 URL을 설정할 수 있는가? 내부 네트워크에 대해 검증되는가? 리디렉션 이후는 어떤가?

**연쇄 취약점 및 신뢰 경계** (subagent_type: `general`)
개별적으로는 허용되거나 억제된 동작이라도, 다른 컴포넌트나 수명 주기 단계가 더 강한 보장에 의존하면 취약점이 될 수 있다.
- **다단계 경계 실패**: 낮은 권한 주체가 읽고, 쓰고, 호출하고, 보유할 수 있는 것을 매핑한 뒤, 구체적인 출력만을 이후의 신뢰 결정에 연결하라. 각 선행 조건을 확인하고 하위 영향을 가정하지 마라.
- **컴포넌트 간 신뢰 공백**: 컴포넌트 A가 입력을 검증하여 컴포넌트 B에 전달한다. A가 만드는 정확한 보장을 B가 가정하는 것과 비교하라. 절단(truncation), 타입 강제 변환, 정규화, 테넌트 범위, 플러그인/확장 접근을 포함한다.
- **2차 사용(second-order use)**: 저장될 때는 안전했던 데이터가 이후 컨텍스트에서 위험해질 수 있다. 필드 이름이 JSON 경로가 되고, 슬러그가 파일 경로가 되고, 이스케이프된 텍스트가 원시 렌더링에 들어가고, 저장된 문자열이 URL, 정규식, 템플릿, 정책 표현식이 되는 경우이다.
- **범위 및 권능 증가**: 토큰, API 키, 플러그인, OAuth, MCP, AI 권능이 위임, 갱신, 캐싱, 역할 변경, 합성 이후 더 넓어진다. 결과 주체가 가져서는 안 되는 구체적인 연산을 명시하라.
- **타이밍과 순서**: 설정, 마이그레이션, 소프트 삭제, 폐기/캐시 만료, 검사/사용, 검증/소비 윈도우를 검토하라. 보고하기 전에 오래된(stale) 상태가 수용되는지 확인하라.
- **롤백 및 복구**: 삭제 취소, 복원, 리비전 롤백, 취소는 현재의 소유권, 검증, 인가를 적용해야 한다. 어떤 유효하지 않은 상태가 복원되는지 확인하라.

**와일드카드(Wildcard)** (subagent_type: `general`)
너에게는 카테고리가 주어지지 않는다. 이미 할당된 표준 클래스 밖의 취약점을 찾아라.

지루해 보이거나 보안과 무관해 보이는 코드를 읽어라. 불완전하거나, 실험적이거나, 호환성 또는 폴백 기능을 따라가되, 다른 모든 클래스와 동일한 구체적 경계 및 검증 요건을 유지하라.

다음 출발점을 사용하되 여기에 국한하지 마라.
- 코드베이스에서 가장 이상한 코드는 무엇인가? 왜 존재하는가? 악용되면 어떻게 되는가?
- 미완성이거나, 실험적이거나, 덧붙인 느낌의 기능이 있는가? 그런 기능은 검토를 가장 적게 받았기 때문에 보안이 가장 약하다.
- 프런트엔드가 결코 하지 않을 방식으로 API를 사용하면 어떻게 되는가? UI는 사용자를 제약하지만 API는 그렇지 않다. 가능하지만 클라이언트가 한 번도 하지 않는 API 호출은 무엇인가?
- 숨겨졌거나 문서화되지 않은 엔드포인트, 매개변수, 헤더, 기능이 있는가? 문서에 없는 것을 찾기 위해 라우트 등록, 미들웨어, 구성을 살펴라.
- 함께 동작하도록 설계되지 않은 기능을 섞으면 어떻게 되는가? 현지화 + 미리보기 + 캐싱. 가져오기 + 플러그인 + 웹훅. OAuth + 가장(impersonation) + API 키.
- git 이력에 흥미로운 것이 있는가? 되돌려진 보안 수정, 주석 처리된 인증 검사, 커밋되었다가 제거된(이력에는 여전히 남은) 비밀.
- 유효한 계정의 어떤 동작이 다른 사용자, 공유 무결성, 가용성, 또는 운영자가 부담하는 비용에 영향을 주는가? 그 동작 주변의 억제, 쿼터, 인가, 복구를 검증하라.
- 어떤 연산이 되돌릴 수 없거나 상위 확인을 요구하는가? 인가와 승인을 최종 주체, 동작, 자원에 바인딩하라.
- 코드가 환경에 대해 어떤 가정을 하는가? 데이터베이스가 로컬이라는 것, 시계가 정확하다는 것, DNS가 신뢰할 만하다는 것, 파일 시스템이 대소문자를 구분한다는 것?
- 테스트 파일을 보라 — 무엇을 테스트하고 **있지 않은가**? 개발자가 생각한 엣지 케이스(테스트가 있음)와 생각하지 못한 것(테스트가 없음)을 비교하라.

불변식이 결론 날 때까지 할당된 범위 안의 이상 징후를 추적하라. 이상해 보이는 것이 있으면 안전한지 말할 수 있을 때까지 읽어라. 함수에 안전한 이유를 설명하는 주석이 있으면 그 설명을 검증하라. 변수 이름이 `temp`, `hack`, `legacy`이면 면밀히 읽어라.

**뻔한 것들(Obvious things)** (subagent_type: `general`)
다른 에이전트는 미묘한 버그를 찾는다. 이 에이전트는 모두가 다른 누군가가 이미 확인했으리라 가정하기 때문에 놓치기 쉬운 기본적인 노출을 점검한다.
- 소스에 하드코딩된 비밀번호, API 키, 토큰, 비밀이 있는가? (`password`, `secret`, `apikey`, `token`, `Bearer`, `-----BEGIN`, 흔한 기본 비밀번호를 grep)
- 보안을 언급하는 TODO/FIXME/HACK/XXX 주석이 있는가? (`TODO: add auth`, `FIXME: validate input`, `HACK: skip permission check`)
- 디버그 모드 / 개발 모드가 제대로 게이트되어 있는가? 환경 변수, 쿼리 매개변수, 헤더로 프로덕션에서 활성화할 수 있는가?
- 프로덕션에서 동작하는 테스트/예제/시드 자격 증명이 있는가?
- 보호되지 않은 `/debug`, `/admin`, `/test`, `/status`, `/health`, `/metrics`, `/env`, `/.env`, `/config` 엔드포인트가 있는가?
- 저장소에 `.env`, `.env.local`, `credentials.json`, `*.pem`, `*.key` 파일이 체크인되어 있는가?
- `.gitignore`가 실제로 비밀, 업로드, 로컬 구성을 포함하는가?
- 의존성이 고정(pin)되어 있는가? 의존성 트리에 알려진 CVE가 있는가? (락파일을 확인)
- 동적 입력을 받는 `eval()`, `exec()`, `child_process`, `Function()`, `vm.runInContext`, `import()`가 있는가?
- CORS 헤더가 `*`로 설정되었거나 지나치게 허용적인가? `Access-Control-Allow-Credentials`가 와일드카드 오리진과 결합되어 있는가?
- 쿠키에 `HttpOnly`, `Secure`, `SameSite` 속성이 빠져 있는가?
- 오픈 리디렉션이 있는가? (`redirect`, `return`, `next`, `url`, `goto`, `continue`라는 이름의 매개변수가 검증 없이 리디렉션에 전달됨)
- TLS가 강제되는가? HTTP 전용 엔드포인트가 있는가?
- 프로덕션의 오류 응답이 스택 트레이스, 내부 경로, SQL 오류를 반환하는가?

이 에이전트는 창의적일 필요가 없다. 철저하고 문자 그대로여야 한다. 모든 항목을 확인하라. 각 결과를 보고하라.

**중요**: 이 에이전트가 보고하는 모든 발견 사항에 대해, 표면적 겉모습만이 아니라 전체 코드 경로를 검증해야 한다. 쿠키에 `HttpOnly`가 없다면 그 쿠키가 보안상 민감한 데이터를 담고 있는지, 그리고 설계상 JS가 그것을 읽어야 하는지 확인하라. 오류 메시지에 필드 이름이 들어 있다면 그 필드가 실제로 민감한 데이터로 채워지는지 확인하라. 플래그는 발견 사항이 아니다 — 보고하기 전에 영향을 추적하라.
