# 정찰

### 1단계: 소스를 매핑하고 커버리지를 계획한다

parent는 `run-metadata.json`을 초기화하고 `SKILL.md`의 엄격한 정찰 전 예산 게이트를 적용한 뒤, 헌팅 전에 에이전트 scratch 루트와 공유 원장을 만든다. 게이트가 실패하면 메타데이터에 incomplete 상태를 기록하고 정찰 에이전트를 실행하지 않는다. 정찰은 대상과 로컬에서 사용 가능한 빌드/구성 상태만 읽는다. 배포된 엔드포인트, 외부 ID 제공자, 레지스트리, 브로커, 클라우드 API, 기타 공유 서비스에 접속하지 않는다.

여러 `research` 에이전트를 병렬로 실행하라. 이들은 구조화된 사실을 parent에게 반환하며 파일을 쓰지 않는다.

**에이전트 1a: 제품, 스택, 로컬 운영**

```text
<target>의 대상을 읽어라. 네트워크 접근을 사용하지 마라. 다음을 반환하라:
1. 제품 유형, 사용자, 운영자, 신뢰에 민감한 일반적 동작.
2. 언어, 프레임워크, 빌드 시스템, 런타임, 로컬에서 보이는 배포 모델.
3. 저장소 상대 진입점과 subsystem 경계.
4. 로컬 의존성으로 오프라인에서 실행할 수 있는 정확한 빌드 및 테스트 명령, 예상되는 쓰기 위치, 그것이 처리하는 대상이 제어하는 입력. 정찰 중에는 실행하지 마라.
5. 로컬 문서와 의존성에서 보이는 비교 가능한 소프트웨어 또는 프로토콜. 소스에 근거한 유용한 비교가 없다면 그렇게 말하라.
6. 제한된 실행을 제약하는 누락된 로컬 툴체인 또는 런타임 사실.
저장소 상대 file:line 참조가 있는 소스 사실만 반환하라.
```

**에이전트 1b: 주체, 권한, 통제**

```text
ID, 인가, 격리, 권한을 확립하는 모든 소스를 읽어라. 다음을 매핑하라:
1. 각 낮은 신뢰 주체와 설계상 그것이 가진 동작.
2. 각 진입 표면의 인증 또는 피어 ID.
3. 리소스별 인가와 테넌트/소유자 범위.
4. 프로세스, 브라우저, 워크로드, CI, 플러그인, 모델/도구, 장치, 로컬 IPC의 권한.
5. 권한 변경, 확인, 철회, 복구, 폴백 경로.
6. 어떤 통제가 소스에서 보이고 어떤 통제가 관찰되지 않은 배포 사실에 의존하는지.
저장소 상대 file:line 참조와 함께 신뢰 경계와 통제 위치를 반환하라. 라이브 도달 가능성을 추론하지 마라.
```

**에이전트 1c: 진입 표면, 사본, 싱크**

```text
외부 또는 낮은 신뢰 입력이 들어오는 소스에서 보이는 모든 위치를 목록화하라:
- HTTP/브라우저, RPC/메시지/프로토콜, 파일/아카이브/문서, CLI/env/config, 플러그인/의존성/CI, 클라우드 이벤트/IAM 셀렉터, 모델 컨텍스트/도구 인자, 모바일/딥링크/웹뷰, 로컬 IPC.
각 표면에 대해 주요 변환, 저장되거나 파생된 사본, 보안 관련 싱크를 따라가라. 소스에서 보이는 제한과 동일한 효과로 이어지는 병렬 경로를 기록하라.
저장소 상대 경로와 줄 번호를 반환하라. 완전하게 하되 입력을 실행하거나 보내지 마라.
```

**에이전트 1d: 로컬 실행과 배포 가시성**

```text
테스트, 빌드 정의, 매니페스트, 패키징, 유지되는 환경 오버레이를 읽어라. 다음을 반환하라:
1. 필수 OS 강제 샌드박스 안에서 더미 데이터로 신뢰 경계를 검증할 수 있는 작은 오프라인 테스트 또는 기존 픽스처.
2. 외부 또는 공유 의존성 없이 격리된 루프백 네트워크 네임스페이스를 사용할 수 있는 프로세스.
3. 의존성을 가져오거나, 산출물을 게시하거나, 유료/제공자 API에 접속하거나, 공유 상태에 영향을 주는 명령. 이 실행에서는 금지로 표시하라.
4. 소스가 확립할 수 없어서 결정적일 경우 needs_validation이 필요한 배포된 통제와 부착물.
5. 저장소가 결정론적으로 선택하는 경우에만, 각 배포 모드의 최종 활성 소스 경로.
6. 로컬 플랫폼이 허용 목록의 빈 환경, 외부 네트워크 없음, 읽기 전용 대상/툴체인 마운트, scratch에만 쓰기, 명시적인 CPU, 메모리, 프로세스, 파일 크기, 디스크, 실제 경과 시간 제한을 강제할 수 있는지 여부. 통제가 누락되면 대상이 제어하는 실행이 차단된다.
7. 신뢰할 수 있는 parent 측 코드가 경로 격리된 no-follow 디스크립터 순회, non-blocking 일반 파일 검사, 모든 대상 부모의 no-follow 순회, 배타적 일반 파일 대상 생성, 명시적인 파일별 및 누적 크기 한도로 사전 선언된 scratch 파일을 승격할 수 있는지 여부. 승격 통제가 누락되면 scratch 파일을 증거로 사용할 수 없다.
```

이 네 에이전트가 매핑하지 못하는 실질적으로 다른 배포 모드나 subsystem에 대해서는 집중 정찰 에이전트를 추가하라. 조용히 생략하지 마라. `SKILL.md`의 예산 게이트가 집중 에이전트를 막으면 그것을 위해 아무것도 실행하지 말고, 매핑되지 않은 영역을 이유 `budget_cannot_reserve_critics_and_validation`과 함께 `deferred` 원장 단위로 시드하고, 그 공백을 보고서에 공개하라.

## 이전 실행 입력

작업을 선택하기 전에 parent는 동일 저장소에 대해 사용 가능한 모든 이전 `coverage-ledger.json`과 `findings.json`을 읽는다.

- 모든 이전 기록과 단위의 소스 위치, 통제, 조건, 소스 유래 정체성(identity)을 현재 소스와 비교한다.
- 변경되지 않은 이전 `confirmed` 기록은 관련 소스, 조건, 적격 증거가 여전히 적용될 때만 동일 지문으로 현재 후보 집합에 가져온다. `prior_status: "prior_confirmed_same_source"`인 현재 `planned` 단위에 연결하고 그 근본 원인만 헌터 제외 목록에 넣는다. 가져온 기록을 다시 검증하는 3단계 검증자가 그 단위의 할당 소유자가 되며, 그 소스 재확인이 단위의 첫 검사가 되어 단위를 가져온 지문과 함께 `candidate`로 옮긴다.
- 관련 소스나 조건이 하나라도 변경되면 현재의 planned `prior_confirmed_changed_source` 재검증 단위를 만든다. 그 근본 원인을 헌팅에서 제외하거나 이전 판정이 여전히 적용된다고 가정하지 마라.
- 이전 `needs_validation`, `deferred`, `blocked`, `out_of_scope`, 소스가 변경된 모든 단위에 대해 현재 작업 단위를 만든다. 이 상태들은 우선순위 입력이지 중복 제거나 억제 키가 결코 아니다.
- 여전히 막힌 이전 `needs_validation` 기록은 현재 소스가 그 추적을 뒷받침한 후에만 동일 지문으로 가져온다. `prior_status: "prior_needs_validation"`인 현재 `planned` 단위에 연결하며, 기록은 해결되지 않은 차단 요인을 유지한다. 가져온 기록을 다시 확인하는 3단계 검증자가 그 단위의 할당 소유자가 되며, 그 재확인이 단위의 첫 검사가 되어 단위를 가져온 지문과 함께 `candidate`로 옮긴다. 그 기록을 최종 검증에 포함한다.
- 이전 rejected 기록은 현재 증거가 실패한 추적이나 누락된 조건을 바꾸지 않는 한 오래된 주장으로 취급한다. 변경되지 않은 기각은 정확히 그 주장만 억제하며 커버리지 단위의 검토는 억제하지 않는다.
- 누락되었거나 호환되지 않는 원장은 빈 커버리지로 취급하지 말고 기록하라.

`run-metadata.json`에 사용한 경로와 소스 참조를 명시하라. `architecture.md`에는 커버리지에 미치는 결과만 요약하라.

## 아키텍처 요약과 동반 파일 선택

parent는 약 1,000단어를 상한으로 하여 `<output-dir>/architecture.md`를 종합한다. 다음을 포함하라.

1. 제품, 주체, 일반 권한, 보호되는 리소스.
2. 에이전트 1a에서 얻은 비교 가능한 소프트웨어 기준선(소스에 근거한 것이 있을 때): 비교 대상이 받아들이는 보안 트레이드오프. 이는 노력과 심각도를 보정하는 데 사용하며 입증된 발견 사항을 기각하는 데 **절대** 사용하지 않는다. 비교 대상이 실제로 문제가 된 결함 패턴을 공유한다면 그것은 발견 사항을 강화한다. 의미 있는 비교 대상이 없으면 이 줄은 생략한다.
3. 기술 스택, 소스에서 보이는 배포 경로, 오프라인 빌드/테스트 제한.
4. 진입 표면과 중요한 소스-싱크 또는 수명 주기 경로.
5. 신뢰 경계와 각 경계에서 소스로 보이는 가장 강한 통제.
6. 저장소 상대 시작 경로.
7. 이전 커버리지 공백, 소스가 변경되었거나 차단된 재검증 대상, 동일 소스 확정 제외 항목.
8. [ATTACK-CLASSES-KO.md](ATTACK-CLASSES-KO.md)에서 도출한 짧은 동반 파일 선택 요약: 선택된 파일과 그것을 필요로 하는 소스에서 보이는 경계.

할당 수준의 일반 블록, 선택된 동반 블록, 이유가 있는 제외 블록은 `architecture.md`가 아니라 각 원장 단위에 유지하라. 이는 큰 실행에서도 아키텍처 상한을 유효하게 하고 정확한 헌터 프롬프트 매핑을 기계로 검사할 수 있게 한다.

언어나 의존성 이름이 나온다는 이유만으로 동반 파일을 선택하지 마라. 정찰이 그 파일의 `When to use this file` 절이 설명하는 신뢰에 민감한 경계를 발견했기 때문에 선택하라. 다른 에이전트가 관련 클래스를 검토할 것이라는 이유로 보이는 경계를 제외하지 마라.

## 결정론적 커버리지 원장

parent는 `<output-dir>/coverage-ledger.json`을 최상위 JSON 배열로 작성한다. 실행 프로필이 정하는 세분도에서 진입 표면, 신뢰 경계, subsystem, 해당하는 일반 또는 동반 공격 클래스의 모든 실질적 조합마다 단위를 하나씩 도출한다(`quick`은 범위 내 전체 subsystem 하나의 정체성을 사용하고, `deep`은 수명 주기 모드를 추가한다). 범위 지정 실행에서는 범위 내 표면을 할당용으로 시드하고, 발견된 제외 표면은 이후의 전체 실행이 이를 현재 작업으로 바꿀 수 있도록 `out_of_scope` 단위로 유지한다.

각 차원은 사람이 읽는 레이블과 `canonical_refs`의 안정적인 소스 유래 값을 가진다. 표시 레이블이 바뀌더라도 실행 간에 동일한 소스 객체에는 동일한 정규 참조를 사용하라. 적합한 참조에는 저장소 상대 진입 경로와 내보낸 범위, 소스에 정의된 라우트 또는 메시지 정체성, 경계를 정의하는 소스 통제, 저장소 패키지 경로, 정확한 공격 클래스 블록 참조가 있다. 블록 참조는 `FILE.md#`에 그 파일에서 굵게 또는 제목으로 쓰인 정확한 클래스 이름을 붙인 것이다. 렌더링된 HTML 앵커가 아니라 파일 텍스트와 대조되는 안정적인 식별자이다. 동반 절 블록에는 괄호 한정어 앞의 제목 텍스트를 사용한다(예: `Core discipline`). 표시 레이블을 소문자로 바꾸거나 슬러그화하여 참조를 도출하지 마라.

손실이 있는 슬러그 없이 `coverage_id`를 도출하라.

1. 모든 참조가 유효한 스칼라 값을 가진 유니코드 NFC이고, 보이는 내용이 있으며, 제어, 서식, 줄/단락 구분자, 기본 무시 가능(default-ignorable) 코드 포인트가 없고, 앞뒤 공백이 없도록 요구한다.
2. UTF-8 바이트를 RFC 3986 퍼센트 인코딩으로 인코딩한다. `A-Z a-z 0-9 - . _ ~`만 이스케이프하지 않고 나머지 모든 바이트에는 대문자 `%HH`를 사용한다.
3. 인코딩된 `surface`, `boundary`, `subsystem`, `attack_class` 참조를 `::`로 잇고, `lifecycle`이 있으면 인코딩하여 덧붙인다.

quick 프로필의 성긴 subsystem 차원에는 고정된 정규 값 `profile/quick/all-in-scope-subsystems`를 사용하라. 웨이브 번호, 에이전트, 판정, 심각도, 줄 번호를 참조나 ID에 포함하지 마라. 각 할당 전에 단위를 `coverage_id`의 사전순으로 정렬하라. 중복 ID는 모두 실패 처리한다. 중복 ID가 서로 다른 의미 필드를 가지면 정규 정체성 충돌로 취급하라. 절대 병합하거나 조용히 덮어쓰지 마라. 검증기는 하나의 의미 튜플이 서로 다른 정규 참조로 표현되는 경우도 거부한다.

각 단위는 다음을 기록한다.

```json
{
  "coverage_id": "...",
  "canonical_refs": {
    "surface": "src/router.ts#POST /users/:id",
    "boundary": "src/authz.ts#requireOwner",
    "subsystem": "packages/api",
    "attack_class": "ATTACK-CLASSES.md#Access control"
  },
  "surface": "...",
  "boundary": "...",
  "subsystem": "...",
  "attack_class": "...",
  "starting_paths": ["repo/relative/path"],
  "ordinary_attack_class_block": "ATTACK-CLASSES.md#Access control",
  "selected_companion_blocks": ["FILE.md#section"],
  "excluded_blocks": [{"block": "FILE.md#section", "reason": "..."}],
  "prior_status": "new|prior_confirmed_same_source|prior_confirmed_changed_source|prior_needs_validation|prior_deferred|prior_blocked|prior_out_of_scope|prior_covered_same_source|prior_covered_changed_source|prior_rejected_claim_changed|none",
  "attempts": [],
  "wave": 1,
  "status": "planned",
  "agent_id": null,
  "reviewed_paths": [],
  "local_checks": [],
  "result_fingerprints": [],
  "unresolved": []
}
```

`lifecycle`이 실질적일 때는 `canonical_refs.lifecycle`과 사람이 읽는 `lifecycle` 필드를 모두 추가하라. `ordinary_attack_class_block`은 일반 블록이 적용되지 않을 때만 null이다. 선택된 동반 목록에는 해당하는 각 클래스와 그 동반 파일의 `Core discipline`, `Universal moves`, `Validation rules`가 포함된다. `excluded_blocks`는 고려했지만 선택하지 않은 모든 블록과 그것을 제외시키는 소스 사실을 기록한다.

parent는 부기 필드를 추가할 수 있지만 위의 의미 필드는 안정적으로 유지한다. `prior_status`에서 `new`는 호환되는 이전 원장이 있을 때 이번 실행에서 처음 본 표면을 나타내고, `none`은 호환되는 이전 원장이 없을 때 시드된 단위를 나타낸다. 이전 `deferred`, `blocked`, `out_of_scope`, 소스가 변경된 단위는 현재 범위 내라면 현재 `planned` 작업으로 초기화된다. 이전의 동일 소스 커버 단위는 현재 원장에 계속 보인다. 변경된 소스, 중요한 수명 주기 경로, 정확한 충돌을 먼저 할당한 뒤, 커버리지 비평자를 사용해 다른 패스가 필요한지 판단하라.

`attempts`는 커버리지 비평자가 다시 연 증거 보유 할당을 위한 추가 전용(append-only) 아카이브이다. 재할당 전에 이전 단위의 정확한 `wave`, `status`, `agent_id`, `reviewed_paths`, `local_checks`, `result_fingerprints`, `unresolved`와 비평자의 소스 기반 `reassignment_reason`을 덧붙여라. `blocked`, `covered`, `candidate` 상태만 아카이브할 수 있다. 아카이브된 시도는 라이브 단위와 동일한 상태 및 증거 불변식을 유지하고, 현재 웨이브보다 낮은 엄격히 증가하는 웨이브를 사용하며, 그것을 만든 소유자와 산출물을 유지한다. 다음 할당은 `wave`를 증가시키고, 새 소유자를 사용하며, 빈 라이브 증거로 시작한다. 프로필이나 예산이 다른 할당을 막으면 `wave`를 증가시키고 null 소유자, 빈 증거, 중단 이유와 함께 라이브 `deferred` 상태를 사용하라. 아카이브된 소유자의 검사나 산출물을 라이브 상태로 절대 복사하지 마라. 이후의 라이브 종료 상태는 새 시도의 증거만 담으며 아카이브는 변경되지 않는다.

이 상태 표를 정확히 강제하라.

| 상태 | 단위 `agent_id` | `reviewed_paths` / `local_checks` | `result_fingerprints` | `unresolved` |
|---|---|---|---|---|
| `planned` | null | 비어 있음 | 비어 있음 | 비어 있음 |
| `not_applicable`, `out_of_scope`, `deferred` | null | 비어 있음 | 비어 있음 | 비어 있지 않은 이유 |
| `in_progress` | 정규 소유자 | 비어 있음 | 비어 있음 | 비어 있음 |
| `blocked` | 정규 소유자 | 둘 다 비어 있지 않음(소유한 부분 증거) | 비어 있음 | 비어 있지 않은 차단 요인 |
| `covered` | 정규 소유자 | 둘 다 비어 있지 않음 | 비어 있음 | 비어 있음 |
| `candidate` | 정규 소유자 | 둘 다 비어 있지 않음 | 비어 있지 않음 | 선택 사항 |

정규 에이전트 ID는 `^[a-z0-9][a-z0-9_-]{0,63}$`와 일치하며 Windows 장치 이름이 아니다. 소문자는 필수이므로 하나의 원장에 대소문자 접기 별칭이 존재할 수 없다. 단위 `agent_id`는 할당 소유자를 기록한다. 모든 검사는 자신의 `agent_id`와 비어 있지 않은 `reviewed_paths`를 기록하며, 단위 수준 `reviewed_paths`는 정확히 그 합집합이다. 소스 전용 검사는 `artifact: null`을 사용한다. 로컬 검사는 정확히 `agents/<check.agent_id>/artifacts/` 아래에서 신뢰할 수 있는 parent 측 코드만이 승격한 일반 파일을 요구한다. 이로써 헌터 검사와 검증자 검사가 한 단위에 공존할 수 있다. scratch 경로, 출력 루트 파일, 심볼릭 링크, 특수 파일, 다른 검사 소유자의 산출물은 증거가 아니다.

원장이 곧 커버리지 주장이다. 아키텍처 요약, 에이전트 수, 일반적인 "auth reviewed" 문장은 커버리지 증거가 아니다. 2단계는 헌터의 구조화된 결과에 있는 경로와 검사로만 단위를 닫는다.

시드 후, parent가 갱신할 때마다, 6단계 전에 `node <skill-dir>/validate-coverage-ledger.cjs <output-dir>/coverage-ledger.json`을 실행하라. 검증기는 5 MiB, 중첩 64단계, 단위 10,000개, 중첩 컬렉션 항목 1,000개, 순회한 값 500,000개를 초과하는 입력을 거부하며 보고되는 검증 오류를 100개로 제한한다. 실제로 5 MiB 바이트 한도는 현실적인 단위 약 2,000~5,000개를 수용하므로 10,000개 단위 상한보다 먼저 걸린다. 작업을 할당하거나 커버리지 주장을 하기 전에 모든 오류를 수정하라.
