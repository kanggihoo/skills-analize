# 보안 감사

실제 신뢰 경계(trust boundary)를 위반하는 취약점을 찾고, 소유자(owner)에게 소스 근거, 안전한 재현(safe reproduction), 우선순위(priority), 가장 작은 효과적 수정(fix)을 제공한다. 이 워크플로는 방어 목적이며 소스 우선이다. 영향받는 주체(principal), 리소스, 보안 결과가 구체적이지 않은 후보(candidate)는 확정된 발견 사항(finding)이 아니다.

## 운영 모드

이 스킬은 기본적으로 가이드이다. 이 스킬을 로드한다고 해서 전체 감사 워크플로나 파일 생성이 승인되는 것은 아니다.

- **가이드 모드(Guidance mode)**: 보안 질문, 집중 검토, 방법론, 선별(triage), 특정 발견 사항 조사에는 이 스킬의 관련 부분만 사용한다. 여섯 단계(phase) 전체를 자동으로 실행하거나, 출력 디렉터리를 만들거나, 감사 산출물을 작성하지 않는다. 유용하면 집중 에이전트를 실행할 수 있으며, 이들은 결과를 현재 작업에 반환한다.
- **전체 감사 모드(Full audit mode)**: 사용자가 코드베이스를 감사하거나 모의 침투 테스트하라고 명시적으로 요청하거나, 전체/포괄적/엔드투엔드 보안 검토를 요청하거나, 보고서 산출물을 요청한 경우 전체 워크플로를 사용한다. 여섯 단계를 모두 실행하고 아래에 정의된 파일을 작성한다.

요청이 두 모드 중 어느 쪽인지 불분명하면, 파일을 만들거나 전체 워크플로를 시작하기 전에 집중된 질문을 하나 한다.

## 플랫폼 용어

이 스킬은 에이전트 중립적이다.

- **Parent**는 실행을 조율하고 공유 상태를 소유하는 에이전트이다.
- **Task tool**은 플랫폼의 위임 또는 서브에이전트(sub-agent) 메커니즘이다.
- **`research` 에이전트**는 집중적인 소스 탐색과 사실 검증을 위한 위임 에이전트이다.
- **`general` 에이전트**는 폭넓은 조사와 제한된 로컬 실행을 위한 위임 에이전트이다.
- 제목의 **`subagent_type:`**은 이 두 위임 에이전트 역할 중 해당 작업을 실행하는 역할을 지정한다.

역할, 쓰기 격리, 프롬프트, 독립성 경계를 유지하면서 동등한 플랫폼 기능을 사용하라.

## 범용 실행 안전

이 규칙은 두 운영 모드 모두에 적용된다. 소스 검사는 읽기 전용이다. 대상이 제어하는 빌드, 테스트, 프로세스, 브라우저, 에뮬레이터, 퍼저, 픽스처 처리는 다음 통제를 모두 제공하는 OS 강제 샌드박스 안에서만 실행하라.

- 외부 네트워크 없음. 검사에 로컬 클라이언트/서버 트래픽이 필요할 때만 격리된 루프백 네임스페이스를 사용한다.
- 명시적 허용 목록에서 안전한 값으로 채운 빈 환경. `HOME`, 임시 디렉터리, 캐시는 scratch 로컬로 둔다.
- 읽기 전용 대상과 툴체인. 대상이 제어하는 프로세스는 할당된 `scratch/` 디렉터리 안에만 쓸 수 있다.
- CPU, 메모리, 프로세스, 파일 크기, 디스크, 실제 경과 시간(wall-clock)에 대한 명시적 하한 제한.

대상이 제어하는 프로세스 밖에 있는 에이전트는, 빌드가 소스 옆에 써야 할 때 할당된 `scratch/` 디렉터리에 일회용 소스 사본을 만들 수 있다. 가이드 모드에서는 대상이 제어하는 파일을 보존하지 마라. 전체 감사 모드에서는 신뢰할 수 있는 parent 측 코드만이 쓰기 격리(Write isolation) 아래의 절차에 따라 비밀이 아닌 최소한의 결과를 보존되는 `artifacts/`로 승격할 수 있다. 보존되는 출력 디렉터리(에이전트 자신에게 할당된 `scratch/` 제외), 다른 에이전트의 디렉터리, 호스트 홈 디렉터리, 자격 증명, 소켓, 공유 서비스를 대상 코드에 **절대** 노출하지 마라. 의존성을 설치하거나 빌드가 의존성을 가져오게 하지 마라. 이미 로컬에서 사용 가능한 도구와 의존성만 사용하라. 모든 통제를 강제할 수 없다면 대상 코드를 실행하지 말고, 누락된 샌드박스 기능을 needs-validation 차단 요인으로 보고하고 안전한 검증 계획을 제시하라.

더미 주체, 픽스처, 시크릿을 사용하라. 배포된 엔드포인트, 외부 서비스, 공유 인프라, 프로덕션 ID, 다른 사용자의 데이터, 라이브 컨트롤 플레인을 탐침(probe)하지 마라. 라이브 또는 공유 프로세스에 대해 가용성을 테스트하지 말고, 산출물을 게시하거나 릴리스를 변경하거나 유료 API 할당량을 소비하지 말며, 결함을 입증하는 데 필요한 최소한의 로컬 효과를 넘어 진행하지 마라. 결정적인 사실이 소스나 샌드박스된 픽스처 밖에 있다면 검증이 필요하다고 보고하라.

## 전체 감사 설정

전체 감사 모드에서는 정찰(reconnaissance) 전에 다음 값을 확정하라.

- **스킬 디렉터리(Skill directory)**: 이 `SKILL.md`가 들어 있는 절대 디렉터리.
- **대상(Target)**: 검토 대상 저장소 루트의 절대 경로.
- **저장소 이름(Repo name)**: 디렉터리 또는 로컬 Git 원격에서 얻은 안정적인 저장소 식별자.
- **출력 디렉터리(Output directory)**: 대상 밖에 있는 새로운 쓰기 가능 디렉터리. 기본값은 `~/security-audit-skill/<repo-name>/run-<N>`이며 `<N>`은 사용되지 않은 다음 정수이다. 사용자가 명시적으로 선택하고 parent가 버전 관리가 디렉터리 전체를 무시하는지 확인한 경우에만 대상 내부 디렉터리를 사용한다. 그렇지 않으면 중단하고 외부 경로를 요청하라.
- **소스 참조(Source ref)**: 검토한 커밋과 워크트리가 dirty한지 여부. 검토되지 않은 생성 파일이나 수정된 파일을 다른 리비전으로 취급하지 마라.

### 쓰기 격리

parent가 공유 실행 파일을 생성하며 유일한 작성자이다.

- `run-metadata.json`
- `architecture.md`
- `coverage-ledger.json`
- `findings.json`
- `REPORT.md`
- `FINDINGS-DETAIL.md`
- `NEEDS-VALIDATION.md`

각 헌터(hunter) 또는 검증자(verifier)는 `<output-dir>/agents/<agent-id>/` 아래에 별도의 `scratch/`와 `artifacts/` 디렉터리를 가진 고유한 루트를 받는다. 정규(canonical) 에이전트 ID는 `^[a-z0-9][a-z0-9_-]{0,63}$`와 일치해야 하며, `con`, `prn`, `aux`, `nul`, `com1`부터 `com9`, `lpt1`부터 `lpt9` 같은 Windows 장치 이름과 같아서는 안 된다. 소문자 ID는 대소문자 접기(case-fold) 충돌을 방지한다. 에이전트와 대상이 제어하는 모든 프로세스는 `scratch/`에만 쓸 수 있다. 보존되는 `artifacts/`는 parent 소유이며 샌드박스에 노출되지 않고, 신뢰할 수 있는 parent 측 승격 코드만 쓸 수 있다. 에이전트는 공유 파일, 대상 소스, 보존된 산출물, 다른 에이전트의 디렉터리를 변경할 수 없다. `/tmp`나 호스트 홈 디렉터리를 쓰기 가능한 대체 경로로 사용하지 마라.

실행 전에 parent는 에이전트의 `scratch/`와 `artifacts/` 루트에 대한 신뢰할 수 있는 상속 불가(non-inheritable) 디렉터리 디스크립터를 열어 유지하고, 예상되는 scratch 상대 산출물 파일의 허용 목록과 파일별 및 누적 바이트 한도를 명시적으로 기록한다. 이 디스크립터를 에이전트나 샌드박스에 **절대** 전달하지 마라. 샌드박스와 모든 하위 프로세스가 종료된 후, 신뢰할 수 있는 parent 측 코드가 허용 목록의 각 파일을 개별적으로 승격한다.

1. 선언된 상대 경로를 검증한다. 절대 경로, 빈 경로, `.`, `..`, 심볼릭 링크 구성 요소는 거부한다.
2. 보존된 scratch 루트 디스크립터에서 시작해 no-follow 디렉터리 상대 연산으로 각 부모 구성 요소를 순회한다. 경로로 다시 열지 않는다.
3. 리프(leaf)를 no-follow 및 non-blocking으로 연다.
4. `fstat`으로 일반 파일이고 링크 수가 정확히 하나이며 기록된 파일별 및 누적 바이트 한도 이내인지 확인한다.
5. 해당 디스크립터에서 읽는 동안 그 한도를 다시 강제한다.
6. 검증된 크기만큼 정확히 복사하고 `fstat`을 반복하여, 식별자, 유형, 링크 수, 크기가 바뀌었으면 거부한다.
7. 대상(destination)에 대해서는 보존된 artifacts 루트 디스크립터에서 시작해 no-follow 디렉터리 상대 연산으로 모든 부모 구성 요소를 순회한다. 기존 구성 요소는 각각 실제 디렉터리여야 하며, 없는 디렉터리는 배타적으로 생성한 뒤 no-follow로 다시 열어 검증한다.
8. 링크를 따라가지 않고 리프를 배타적으로 생성하고, 열린 대상이 링크 수가 정확히 하나인 일반 파일인지 확인한 뒤, 어느 경로도 다시 열지 않고 검증된 소스 디스크립터에서 복사한다.
9. 비 POSIX 시스템에서는 동등한 경쟁 조건 안전(race-safe) API를 사용한다.
10. scratch를 재귀적으로 복사하거나 glob하지 말고, 아카이브를 artifacts로 추출하지 말며, 심볼릭 링크, FIFO, 소켓, 장치, 디렉터리, 하드 링크된 파일, 변경 중인 파일, 한도를 초과하는 파일을 열거나 승격하지 마라.
11. 어느 검사든 사용할 수 없거나, 강제할 수 없거나, 실패하면 scratch 항목을 폐기한다. 그것이 결정적 증거라면 정확한 승격 차단 요인과 함께 `needs_validation`을 유지한다.

[HUNTING-KO.md](HUNTING-KO.md)와 [VALIDATION-AND-REPORTING-KO.md](VALIDATION-AND-REPORTING-KO.md)는 헌터 및 검증자 프롬프트용으로 이 절차를 하나의 동일한 펜스 블록으로 담고 있으며, 이 목록과 같은 순서로 같은 규칙을 기술한다.

재현된 검사에는 명령, 정확한 테스트 입력, 샌드박스 한도, 그리고 재현에 필요한 허용 목록의 환경 변수 이름과 안전한 비밀 아닌 값만 기록하라. 주변(ambient) 환경, 상속된 변수, 자격 증명 값, 인증 상태, 관련 없는 호스트 경로를 캡처하거나 복사하지 마라. 실행 후에 환경을 삭제(redact)하려 하지 말고 빈 환경에서 시작하라.

위임 전에 parent는 최소한 `run_id`, `repo`, `target`, `source_ref`, `profile`, `scope_paths`, `budget`(미설정 시 null), `execution_policy: "sandboxed-source-and-local-only"`, 선택된 동반(companion) 파일, 이전 실행 경로, 공유 파일 소유자, `run_status: "in_progress"`를 담은 `run-metadata.json`을 작성한다. 이 사실이 바뀔 때만 메타데이터를 갱신하라. 후보 상태는 커버리지 원장(coverage ledger)과 `findings.json`에 속한다.

## 전체 감사 계획

이 절의 커버리지, 이전 실행, 프로필, 예산 요구 사항은 전체 감사 모드에서만 적용된다.

### 커버리지와 이전 실행

한 번의 패스로 완전해지는 경우는 없다. 헌팅(hunting) 전에 결정론적 커버리지 계획을 세우고 모든 에이전트 결과 후에 갱신하라. [RECONNAISSANCE-KO.md](RECONNAISSANCE-KO.md)는 안정적인 커버리지 단위를 정의하고 [HUNTING-KO.md](HUNTING-KO.md)는 커버리지 비평자(critic) 웨이브를 정의한다. 원장은 parent만 갱신한다.

이전 실행이 있으면 현재 실행을 계획하기 전에 호환되는 모든 `coverage-ledger.json`과 `findings.json`을 읽어라.

1. 관련된 현재 소스를 각 이전 기록 및 단위와 비교한다. 이전 소스 참조만으로는 경로가 변경되지 않았다는 증거가 되지 않는다.
2. 이전 `confirmed` 기록은 관련 소스와 조건이 변경되지 않았고 증거가 여전히 현재 계약을 충족할 때만 현재 후보 집합으로 가져온다. 이를 `planned`로 시드된 현재 원장 단위에 연결하고, 지문(fingerprint)을 보존하며, 가져온 그 근본 원인(root cause)만 헌터에서 제외하고, 가져온 기록을 현재의 최종 검증 경로에 보낸다. 이를 다시 확인하는 3단계 검증자가 그 단위의 할당 소유자가 되며 단위를 `candidate`로 옮긴다.
3. 이전 `confirmed` 기록의 관련 소스가 변경되었다면 현재의 planned 재검증 단위를 만든다. 그 기록을 헌터 제외 목록에 넣지 마라. 현재 독립 검증이 현재 경로와 결과를 입증한 경우에만 confirmed로 유지된다.
4. 이전 `needs_validation`, `deferred`, `blocked`, `out_of_scope`와 소스가 변경된 모든 단위를 현재 작업으로 만든다. 여전히 외부 요인에 막힌 `needs_validation` 기록은 현재 소스 추적을 확인하고, 검증자의 재확인이 소유자와 증거를 제공하는 현재 `planned` 단위에 지문으로 연결한 후에만 가져올 수 있다. 그 기록은 해결되지 않은 차단 요인을 유지한다. 이러한 이전 상태는 현재 단위를 결코 억제하지 않는다.
5. 이전의 동일 소스 커버 단위는 우선순위에 참고가 될 수 있지만 현재 원장에 계속 보여야 한다. 이전 `rejected` 기록은 변경되지 않은 실패한 주장만 억제하며 그 단위의 커버리지는 억제하지 않는다. 증거가 바뀌면 현재 작업이 생긴다.
6. 이전 프로필과 범위를 읽는다. 이전 `quick` 또는 범위 지정 원장은 기록된 증거와 공백만 기여하며 "나머지는 괜찮다"는 암시를 주지 않는다.

이전 원장이 없으면 최종 커버리지 진술에 그렇게 명시하라. 한 번의 실행이 대상을 다 소진했다고 암시하지 마라.

### 실행 프로필과 범위

전체 감사 설정 중에 사용자의 요청에서 프로필을 고르거나 대상의 크기와 중요도에 따라 하나를 제안하라. 이를 `run-metadata.json`(`profile`, `scope_paths`)에 기록하고 보고서에 명시하라. 기본값은 `standard`이다.

- **`quick`** — 작은 대상, 재실행, 빠른 첫 확인을 위한 제한된 패스. 원장 단위를 surface × boundary × attack class로 성기게 하고(subsystem은 고정된 정규 식별자 `profile/quick/all-in-scope-subsystems`를 사용), 헌터 웨이브를 정확히 한 번 실행한 후 최종 커버리지 비평자 패스를 정확히 한 번 실행하며, 후보 검증과 최종 기록 검증 모두에 후보당 새 검증자 하나를 사용한다. 후속 헌터 웨이브를 실행하지 마라. 비평자가 인정한 발견과 재할당은 `deferred`로 기록하라.
- **`standard`** — 기술된 그대로의 워크플로.
- **`deep`** — 중요도가 높거나 큰 대상용. 원장 단위를 subsystem과 수명 주기(lifecycle) 모드별로 나누고, 비평자 웨이브를 깨끗한 패스가 나올 때까지 실행하며, 후보 검증과 최종 기록 검증을 별도의 새 에이전트로 유지하고, `prior_covered_same_source` 단위에는 독립적인 두 번째 패스를 준다.

**범위 지정 실행(scoped run)**은 일부를 감사한다. 명명된 경로, 하나의 subsystem, 하나의 동반 도메인, 또는 두 소스 참조 사이의 diff이다. 범위 내 표면에 대해서만 원장 단위를 시드하고 나머지는 모두 `out_of_scope`로 기록하라. 절대 `covered`로 기록하지 마라. 범위 지정 실행이나 `quick` 실행은 부분 커버리지임을 스스로 밝혀야 한다.

프로필은 폭과 중복성을 바꿀 뿐 증거 기준은 절대 바꾸지 않는다. 후보 게이트, 소스/로컬 실행 경계, `needs_validation` 규율, 스키마 검증, `confirmed` 기록의 독립 검증을 축소하지 마라.

#### 비용 예산

원장은 지출을 셀 수 있게 한다. 한 단위는 대략 헌터 할당 하나이고, 살아남은 후보 하나는 프로필에 따라 검증자 할당 하나 또는 둘이다. 사용자가 예산을 설정하거나 — 큰 대상에 대해 parent가 제안하는 경우 — 모든 단계에 걸친 에이전트 호출 최대 횟수로 `run-metadata.json`에 `budget`을 기록하라.

정찰 에이전트를 실행하기 전에 엄격한 예산 게이트를 적용하라. 네 개의 기본 정찰 호출, `quick`에는 마지막 웨이브 후 비평자 하나, `standard`/`deep`에는 웨이브 후 비평자 하나와 별개의 최종 클린 비평자 하나, 그리고 최소 한 번의 검증자 호출을 예약한다. 추가 집중 정찰은 호출마다 이 게이트를 반복한 후에만 추가한다. 요청된 예산이 이 최소치를 감당할 수 없으면 에이전트를 하나도 실행하지 말고 더 큰 예산, 더 좁은 범위, 또는 다른 프로필을 요청하라. 요청이 그대로이면 `run_status: "incomplete"`와 `incomplete_reason: "budget_cannot_fund_reconnaissance_and_reserves"`를 설정하고 감사 패스가 실행되지 않았다고 보고하라.

다음 순서로 지출하라.

1. 정찰, 모든 웨이브 후 비평자, 별도의 최종 클린 비평자를 에이전트 호출로 센다.
2. **헌팅 전에 비평자와 검증을 예약한다.** `quick`에는 마지막 웨이브 후 비평자 하나를 예약한다. 모든 `standard` 또는 `deep` 헌터 웨이브 전에 직후 웨이브 후 비평자 하나와 별개의 최종 클린 비평자 하나를 예약한다. 또한 프로필에서 검증자 비용을 예약한다(예상 후보당 약 1~2개 에이전트, 불확실하면 비평자 예약 후 잔액의 30%를 예약). 어느 예약분에도 헌터를 배정하지 마라.
3. 헌팅 허용분을 소진할 때까지 우선순위 순으로 헌터를 단위에 배정한다. 예약된 웨이브 후 비평자는 그 웨이브 직후에 사용하고, 최종 클린 및 검증 예약분은 그대로 유지한다.
4. 이후 웨이브 전에 그 웨이브의 새 웨이브 후 비평자를 다시 예약한다. 남은 예산이 필요한 비평자 호출과 검증 예약분을 감당할 수 없으면 그 웨이브에서 헌터를 실행하지 않고, 계획된 단위를 이유 `budget_cannot_reserve_critics_and_validation`과 함께 `deferred`로 표시하며, 유지된 최종 클린 비평자를 사용해 그로 인한 공백을 기록한다.

웨이브 1 전에, 시드된 단위, 암시되는 헌터 수, 필수 비평자 호출, 검증 예약분, 남은 예산이 계획을 감당하는지 여부로 정찰 전 추정치를 갱신하라. 명백히 감당할 수 없다면 증거를 조용히 줄이지 말고 그렇게 말한 뒤 더 좁은 범위나 더 성긴 프로필을 제안하라. 이후 사실 때문에 필수 최종 비평자 예약분이 소진되면 헌터를 실행하지 않고, 계획된 모든 작업을 deferred로 표시하며, 실행을 이유 `critic_budget_exhausted`와 함께 incomplete로 설정하고, 완전한 커버리지 주장을 하지 마라.

엄격한 총 에이전트 예산도 예상 밖으로 큰 후보 집합이나 또 다른 독립 검증자가 필요한 5단계의 중대한 대체(replacement)로 초과될 수 있다. 남은 예산으로 모든 후보를 검증할 수 없으면 헌팅을 중단하고, 예산이 허용하는 동안 지문 순으로 후보를 검증하며, `run_status: "incomplete"`와 `incomplete_reason: "validation_budget_exhausted"`를 설정하라. 검증되지 않은 각 지문은 해결되지 않은 그 이유와 함께 `candidate` 원장 단위에 연결해 둔다. 검증되지 않은 후보를 `findings.json`에 넣거나, `needs_validation`으로 이름만 바꾸거나, 실행이 완료되었다고 보고하지 마라. 6단계는 첫 절에서 후보 검증이 불완전하다고 밝히고 영향받는 지문과 단위를 나열하는 경우에만 부분 보고서를 만들 수 있다. 사용자가 설정한 엄격한 예산을 조용히 초과하지 마라.

## 핵심 원칙

### 경계와 결과를 요구한다

모든 후보에 대해 낮은 신뢰의 주체, 받아들여진 입력 또는 행동, 의도된 통제, 넘어선 경계, 영향받는 주체 또는 리소스, 구체적이고 관찰되었거나 소유자가 관찰할 수 있는 결과를 명시하라. 누락된 모범 사례, 추측한 배포 동작, 일반적인 파서 크래시, 자기 영향(self-impact)을 보안 발견 사항으로 격상하지 마라.

### 제한된 로컬 증거를 사용한다

정적 분석은 소스 경로를 확립한다. 샌드박스된 로컬 테스트는 모든 실행 통제가 가능할 때 동작을 해소한다. 최소 함수 하니스, 기존 단위 테스트, 작은 파서 픽스처, 더미 테넌트 통합 테스트, 로컬에서 렌더링한 구성, 제한된 격리 루프백 클라이언트가 그 예이다. 잘못된 반환 값, 인가되지 않은 더미 레코드, 새니타이저 발견, 정책 차이, 또는 다른 최소한의 효과에서 멈춰라. 로컬 검사를 최소한의 경계 결과를 넘어 확장하거나 지속성(persistence), 사후 장애(post-fault), 은닉 자료를 만들지 마라.

### 소스 가시성을 존중한다

배포 통제, 프록시 동작, 제공자 설정, 브라우저 헤더, ID 정책, 브로커 ACL, 패키징, 토폴로지는 실제 통제이다. 이것이 필요한데 저장소에 없다면 존재도 부재도 가정하지 마라. 정확한 누락 사실과 안전한 소유자 관찰 또는 로컬 계획과 함께 `needs_validation`을 사용하라.

### 우선순위와 확실성을 구분한다

`confirmed` 기록만 심각도(severity)를 받는다. 가능성(likelihood)과 영향(impact)은 입증된 조건과 결과를 반영해야 하며, 전체 심각도는 입증된 영향을 초과할 수 없다. `needs_validation`은 특정한 소스 기반 경계 가설이 막혀 있다는 뜻이지 신뢰도 낮은 confirmed 취약점이 아니며 심각도가 없다.

다음 기준점으로 전체 심각도를 보정하라.

- **critical** — 인증되지 않은 행위자가 코드 실행, 전체 데이터 저장소 접근, 또는 임의 계정 탈취를 얻는다.
- **high** — 행위자가 실제 결과를 가져오는 명시적 보안 통제를 완전히 무력화한다. 인증 우회, 테넌트 간 읽기 또는 쓰기, 다른 사용자에게 영향을 주는 저장형 스크립트 실행, 인증된 코드 실행, 공유 서비스의 인증되지 않은 원격 중지가 이에 해당한다.
- **medium** — 영향 반경(blast radius)이 제한적이거나, 드문 선행 조건이 필요하거나, 결과가 좁은 리소스 집합에 국한되는 실제 경계 위반.
- **low** — 비밀이 아닌 내부 정보의 노출, 또는 최소한의 이득을 위해 지속적인 노력이 필요한 효과.
- **informational** — 확인되었지만 영향이 미미한 관찰로, 주로 더 큰 발견 사항 안의 선행 조건으로서 유용하다.

high/medium 판별 기준은 다음과 같다. 입증된 결과가 실제 결과를 가져오는 행위에 대한 명시적 통제를 완전히 무력화하는가, 아니면 약화할 뿐인가? 구체적인 피해를 진술할 수 없다면 심각도는 느낌보다 낮다.

### 가장 작은 효과적 소스 수정을 권고한다

각 confirmed 발견 사항에 대해 코드가 강제해야 하는 불변식(invariant)과, 마지막 신뢰 결정 지점에서 그것을 강제하는 가장 좁은 소스 변경을 식별하라. 일반적인 하드닝 조언보다 구체적인 저장소 상대 변경과 회귀 테스트를 선호하라. 감사는 수정을 기술할 뿐 대상 소스를 수정하지 않는다.

## 전체 감사 워크플로

전체 감사 모드에서는 여섯 단계를 순서대로 모두 따르라.

1. **정찰(Reconnaissance)** — [RECONNAISSANCE-KO.md](RECONNAISSANCE-KO.md)로 소스, 신뢰 경계, 로컬 빌드 경로, 동반 파일 선택, 이전 증거, 초기 결정론적 커버리지 원장을 매핑한다.
2. **커버리지 주도 헌팅 웨이브(Coverage-led hunting waves)** — [HUNTING-KO.md](HUNTING-KO.md), [ATTACK-CLASSES-KO.md](ATTACK-CLASSES-KO.md), 선택된 도메인 동반 파일로 원장에서 격리된 헌터를 할당하고 구조화된 후보 결과를 수집한다.
3. **후보 검증(Candidate validation)** — [VALIDATION-AND-REPORTING-KO.md](VALIDATION-AND-REPORTING-KO.md)에 정의된 대로 지문을 통합하고 모든 후보를 새 소스 검증자에게 준다.
4. **구조화된 출력(Structured output)** — 최종 `confirmed`, `needs_validation`, `rejected` 기록을 모두 `findings.json`에 쓰고, `report-schema.json`과 `validate-findings.cjs`로 검증하며, `validate-coverage-ledger.cjs`로 커버리지 주장을 검증한다.
5. **독립 기록 검증(Independent record verification)** — 새 에이전트로 최종 소스 주장을 검증하고 수정이나 상태 변경을 조정한다.
6. **대상 중립 보고서(Target-neutral report)** — 최종 기록에서 `REPORT.md`, `FINDINGS-DETAIL.md`, `NEEDS-VALIDATION.md`를 도출하며 라이브 탐침 지침은 포함하지 않는다.

정확히 두 가지 종료 상태 중 하나에 도달하기 전에는 실행을 끝내지 마라. (a) 6단계 산출물이 모두 작성되고 두 검증기가 모두 통과한다. (b) `run_status: "incomplete"`가 정확한 이유와 함께 기록되고 그 공백이 보고서에 공개된다. 단계 중간에 절대 멈추지 마라.

## 안티패턴

1. 체크리스트 이탈을 취약점으로 제시하는 것.
2. 도달 가능한 경계 위반이 없는 심층 방어(defense-in-depth) 조언.
3. 제한된 로컬 증거로 충분하지 않은 라이브 또는 공유 환경 테스트.
4. 소스에 없는 제공자, 프록시, 브라우저, ID, 배포 동작을 추측하는 것.
5. 의도된 동일 주체의 권한이나 자기 영향을 경계를 넘는 결과로 취급하는 것.
6. 관찰된 효과보다 강한 파서 또는 런타임 효과를 보고하는 것.
7. 중복 제거나 검증이 불가능한 산문뿐인 헌터 결과를 내보내는 것.
8. 가져온 동일 소스의 이전 confirmed 기록을 다시 보고하거나 헌팅을 고정시키는 예시로 사용하는 것.
9. `needs_validation` 기록에 심각도를 부여하는 것.
10. 독립 검증 전에 보고서를 작성하거나 산문과 JSON이 불일치하게 두는 것.
