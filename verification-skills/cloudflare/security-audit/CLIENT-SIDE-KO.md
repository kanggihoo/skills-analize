# 클라이언트 측 및 브라우저 헌팅

#### 이 파일을 사용하는 경우

의미 있는 신뢰 결정이나 신뢰할 수 없는 렌더링이 브라우저에서 일어날 때 이 파일을 참조하라. 대상에는 싱글 페이지 앱, 브라우저 확장, 임베디드 WebView, 서비스 워커, 오프라인 애플리케이션, 그리고 공격자가 영향을 줄 수 있는 콘텐츠를 DOM에 렌더링하거나 교차 윈도우 메시지를 수신하거나 브라우저 저장소를 사용하는 코드가 포함된다. 이러한 경로에는 URL 프래그먼트, `window.name`, `postMessage`, 이전에 캐시된 콘텐츠처럼 서버가 결코 보지 못하는 소스가 포함된다.

`ATTACK-CLASSES.md`와 함께 사용하라. 이 파일은 브라우저 소스와 싱크, 출처 경계, 브라우저 지속성, 교차 사이트 상태 오라클을 다룬다. WebView 브리지의 네이티브 측에는 `DESKTOP-MOBILE-AND-LOCAL-IPC.md`를, 서버 측 CSRF, 세션, 인증 콜백에는 `WEB-PROTOCOL-AND-AUTH.md`를 사용하라.

## 핵심 규율 (이 도메인의 모든 에이전트 프롬프트에 포함하라)

```
- 클라이언트 측 후보에는 제어 가능한 소스와 실행 또는 노출을 일으키는 싱크가 필요하다. 둘 다 명시하고 공격자가 영향을 준 데이터가 싱크에 도달함을 보여라.
- 영향은 피해자의 세션, 다른 출처 또는 공유 지속성에 도달해야 한다. 자기 주입과 공격자 자신의 데이터 노출은 발견 사항이 아니다.
- 프레임워크 이스케이프, 브라우저 동일 출처 정책, CSP, COOP/CORP, 서비스 워커 스코프, 최신 noopener 기본값은 실제 통제이다. 영향을 부여하기 전에 이를 검증하라.
- 브라우저 저장소와 캐시는 출처별로 공유되며 로그인 상태보다 오래 남을 수 있다. 누가 쓰고, 누가 읽고, 어떤 계정, 테넌트 또는 워커 수명 주기가 각 레코드를 지우는지 식별하라.
- 완전한 소스 증거와 제한된 로컬 브라우저 테스트가 있을 때만 `confirmed`를 사용하라. 렌더러, 확장 권한, 배포된 헤더 또는 브라우저 정책 동작이 필요하지만 사용할 수 없으면 `needs_validation`을 사용하라.
```

## DOM 및 객체 상태 공격 클래스 (subagent_type: `general`)

**DOM 기반 XSS(DOM-based XSS)**
`location` 필드, `document.referrer`, `window.name`, 메시지 데이터, 저장소, 브라우저가 제어하는 문서 상태가 `innerHTML`, `outerHTML`, `document.write`, 문자열을 평가하는 API, 실행 가능한 URL, jQuery HTML API 또는 프레임워크 이스케이프 해치로 흘러가는 경로를 추적하라. 프레임워크가 이스케이프한 보간은 발견 사항이 아니다.

**DOM 클로버링(DOM clobbering)**
공격자가 주입한 `id` 또는 `name` 속성이 이후 코드가 신뢰하는 전역 변수, 폼 속성, 구성 객체 또는 초기화 플래그를 가린다. 속성을 보존하는 마크업 경로와 클로버링된 값의 보안 관련 사용을 모두 요구하라.

**프로토타입 오염과 가젯 체인(Prototype pollution and gadget chain)**
공격자가 제어하는 키가 깊은 병합이나 경로 할당 같은 재귀적 쓰기에 도달하여 프로토타입 상태를 수정한다. 그런 다음 도달 가능한 가젯이 오염된 속성을 소비하여 인가, 실행, 내비게이션 또는 렌더링을 변경한다. `JSON.parse`, 얕은 복사 또는 가젯 없는 오염만으로는 충분하지 않다.

## 교차 출처 메시징 및 네트워크 공격 클래스 (subagent_type: `general`)

**`postMessage` 출처 및 소스 신뢰(`postMessage` origin and source trust)**
핸들러가 정확한 출처 허용 목록 없이, 그리고 여러 프레임이 출처를 공유하는 경우 기대되는 `event.source` 없이 `event.data`로 민감한 동작을 수행한다. 송신 측에서는 `*`로 전송된 민감한 데이터가 의도하지 않은 임베더에 도달한다. 약한 부분 문자열, 접두사, 접미사 또는 고정되지 않은 정규식 출처 매칭은 출처 검사가 아니다.

**교차 사이트 WebSocket 요청 사용(Cross-site WebSocket request use)**
WebSocket 업그레이드가 `Origin` 검사나 채널별 토큰 없이 신뢰할 수 없는 출처의 앰비언트 쿠키를 수락하여 피해자의 세션이 데이터를 읽거나 변경할 수 있게 한다. 업그레이드 동작과 보안 관련 메시지 핸들러를 모두 확인하라.

**자격 증명 포함 CORS 신뢰(Credentialed CORS trust)**
서버가 자격 증명을 허용하면서 `Origin`을 반사하거나 약하게 매칭하고 민감한 응답을 반환한다. 자격 증명과 함께 쓰인 단순 와일드카드는 브라우저가 거부한다. 실제로 반사/허용되는 출처 경로와 교차 출처 데이터 또는 변경만 보고하라.

## 서비스 워커 및 브라우저 저장소 공격 클래스 (subagent_type: `general`)

**서비스 워커 등록 및 스코프 탈취(Service-worker registration and scope takeover)**
공격자가 영향을 줄 수 있는 콘텐츠가 등록된 워커 스크립트가 되거나, 지나치게 넓은 `Service-Worker-Allowed` 스코프를 받는 경로를 제어하거나, 무결성 통제 없이 업데이트 임포트를 변경할 수 있다. 최종 스크립트 URL, 응답 MIME 타입, 출처, 스코프, 그리고 임포트되는 모든 스크립트를 누가 제어하는지 검증하라. 의도된 스코프를 가진 일반적인 동일 출처 워커는 결함이 아니다.

**서비스 워커 캐시 및 신원 혼동(Service-worker cache and identity confusion)**
워커가 정책에 계정, 테넌트, 인가 상태 또는 요청 모드를 포함하지 않고 개인화된 응답을 캐시한 뒤 계정 전환이나 로그아웃 이후에 이를 제공한다. fetch 이벤트 라우팅, 캐시 이름과 키, 내비게이션 폴백, 캐시 정리, 그리고 오류/오프라인 경로가 다른 사용자의 이전 응답을 반환하는지 검토하라.

**브라우저 저장소 노출과 오래된 인가(Browser-storage disclosure and stale authorization)**
토큰, 비공개 응답, 임시 저장 데이터 또는 인가 결정이 `localStorage`, `sessionStorage`, IndexedDB, Cache Storage, 확장 저장소 또는 클라이언트 상태에 남아 다른 계정이나 신뢰도가 낮은 동일 출처 컴포넌트가 읽을 수 있게 된다. 토큰 저장만으로는 발견 사항이 아니다. 권한이 더 낮은 현실적인 읽기 주체가 있거나, 폐기/로그아웃 이후에도 계속 사용되어야 한다.

**교차 컨텍스트 저장소 및 브로드캐스트 혼동(Cross-context storage and broadcast confusion)**
`storage` 이벤트, `BroadcastChannel`, 공유 워커 또는 출처 전체 캐시가 현재 세션에 바인딩하지 않은 채 탭 간에 신원이나 명령을 전달한다. 계정 전환, 비공개/공개 윈도우, 테넌트 변경, 그리고 더 새로운 인증 상태를 덮어쓸 수 있는 오래된 탭을 확인하라.

## 교차 사이트 정보 유출 클래스 (subagent_type: `general`)

**XS-Leaks 및 교차 출처 상태 오라클(XS-Leaks and cross-origin state oracles)**
브라우저가 피해자 자격 증명을 첨부하는 동안 공격자 페이지가 리소스 로드/오류 이벤트, 프레임 또는 윈도우 상태, 리디렉션 동작, 타이밍, 캐시 상태 또는 응답 크기를 통해 보호된 교차 출처 상태를 구별할 수 있다. 비공개 객체, 역할 또는 계정의 존재 여부처럼 시크릿을 담은 구체적인 술어 하나를 요구하라. 일반적인 타이밍 변동이나 공개 리소스의 가용성은 발견 사항이 아니다.

**윈도우 및 오프너 상태 노출(Window and opener state disclosure)**
교차 출처 윈도우의 허용된 메타데이터나 내비게이션 결과가 보호된 상태를 드러내거나, 유지된 오프너/명명된 윈도우 관계로 인해 공격자가 제어하는 페이지가 권한 있는 내비게이션에 영향을 줄 수 있다. COOP, 프레임 보호, `noopener`, 정확한 출처, 그리고 관찰 가능한 상태가 기밀인지 확인하라.

## UI 리드레스 및 내비게이션 공격 클래스 (subagent_type: `general`)

**클릭재킹(Clickjacking)**
프레임에 삽입된 상태 변경 동작에 효과적인 `frame-ancestors`, `X-Frame-Options` 또는 이에 상응하는 UI 격리가 없다. 민감한 동작을 요구하고 프레임된 상태에서 완료될 수 있음을 확인하라. 읽기 전용 콘텐츠의 헤더 누락은 하드닝 참고 사항이다.

**클라이언트 측 내비게이션 혼동(Client-side navigation confusion)**
클라이언트 소스가 스킴 및 대상 정책 없이 리디렉션이나 내비게이션을 제어하며, 실행 가능한 `javascript:` 또는 `data:` 대상을 포함한다. 리버스 탭내빙은 코드가 명시적으로 `window.opener`를 유지하거나, 격리 없이 `window.open`을 사용하거나, 암묵적 `noopener`가 없는 브라우저를 지원하는 경우에만 적용된다.

## 범용 기법 (위 모든 항목에 적용)

- DOM, 내비게이션, 워커, 메시지, 저장소 싱크에서 시작하여 브라우저 전용 소스와 서버 제어 소스로 거슬러 추적하라. 해당 경로를 막아야 하는 브라우저 정책을 기록하라.
- 로컬 테스트 출처와 더미 계정으로 계정 전환, 로그아웃, 워커 업데이트, 오프라인 폴백, 오래된 탭 상태를 테스트하라. 프로덕션 사용자, 출처 또는 공유 서비스를 사용하지 마라.
- XS-Leaks의 경우 소스와 로컬 브라우저 동작으로 증명된 술어만 나열하라. 그런 다음 오라클을 제거할 응답 헤더나 렌더링 선택을 식별하라.

## 검증 규칙 (여기서 어떤 발견 사항이든 보고하기 전에 적용)

1. 소스, 싱크, 브라우저 정책, 영향받는 출처/세션, 관찰 가능한 변경 또는 노출을 인용하라.
2. 프로토타입 오염의 경우 재귀적 쓰기와 보안 관련 가젯을 증명하라. DOM 클로버링의 경우 마크업이 살아남고 가려진 값이 사용됨을 증명하라.
3. 서비스 워커와 저장소의 경우 수명 주기 도달 가능성을 증명하라. 공격자가 제어하는 쓰기나 캐시 항목이 다른 계정, 테넌트 또는 이후의 인가 상태에 도달해야 한다.
4. 메시징, CORS, WebSocket, XS-Leaks의 경우 정확한 출처/소스 검증과 노출된 보호 상태 또는 동작을 보여라. CSP, COOP/CORP, 쿠키, SameSite 정책이 이미 이를 차단하지 않는지 확인하라.
5. 완전한 클라이언트 경로와 제한된 로컬 증거가 있는 경우에만 `confirmed` 발견 사항을 반환하라. 소유자가 확인해야 할 정확한 배포 헤더, 확장 권한, 브라우저 버전 또는 렌더러 동작과 함께 `needs_validation`을 반환하라.
