# HTTP 프로토콜 및 인증 헌팅

#### 이 파일을 사용하는 경우

대상이 파싱, 캐싱, 브라우저 인증, 또는 신원 경계에서 HTTP를 사용할 때 이 파일을 참조하라. 웹 애플리케이션, API, 리버스 프록시, CDN, 게이트웨이, 커스텀 HTTP 서버, 그리고 세션, JWT, OAuth/OIDC, SAML, 비밀번호 복구, MFA, 패스키, API 키, mTLS를 구현하는 서비스가 해당한다. 이 파일은 `ATTACK-CLASSES.md`와 함께 사용하라. 접근 통제 검토는 주체가 어떤 연산을 수행해도 되는지를 묻고, 이 파일은 HTTP 또는 신원 계층이 그 연산이 어떤 주체, 요청, 보증 수준, 토큰에 속하는지를 혼동할 수 있는지를 묻는다.

Phase 1에서 클래스를 선택하라. 큰 대상은 요청 프레이밍과 캐시 정책, 브라우저 인증, 연합 신원, 강한 인증과 복구, 서비스 자격 증명, 세션 수명 주기로 분할하라. 관찰할 수 없는 관리형 프록시 뒤의 단일 서버는 소스로 확인 가능한 스머글링 공격 표면이 거의 없다. 프록시나 커스텀 파서에는 훨씬 많다.

## 핵심 원칙 (이 도메인의 모든 에이전트 프롬프트에 포함)

```
- 프레이밍과 캐시 발견 사항에는 동일한 요청, 응답, 또는 키에 대한 두 가지 해석이 필요하다. 두 컴포넌트와 각 측의 정확한 정규화된 값을 명시하라.
- 모든 자격 증명에 대해 서명 또는 비밀 검증과, 그 역할에 필요한 모든 바인딩(issuer, audience, origin, RP, client, session, principal, resource, assurance, expiry, 일회성 상태)을 찾아라.
- Host, Forwarded, X-Forwarded-*, Origin, Referer, 리디렉션 대상, 콜백 state, 요청에서 파생된 URL은 신뢰 결정이다. 각각을 영향받는 신원이나 응답까지 추적하라.
- 헤더, 쿠키 속성, MFA 프롬프트, 속도 제한의 누락만으로는 발견 사항이 아니다. 유효하지 않은 요청의 수용, 주체 간 영향, 보증 수준 하향, 또는 자격 증명 노출이 필요하다.
- `confirmed`는 완전한 소스 증거와 제한된 로컬 요청/토큰 테스트로만 분류하라. 프록시, IdP, 브라우저, 인증서, 비밀, 또는 배포 구성이 필요하지만 보이지 않을 때는 `needs_validation`을 사용하라.
```

## HTTP 프레이밍 및 캐시 공격 클래스 (subagent_type: `general`)

**요청 프레이밍과 비동기화(desynchronization)**
프런트엔드와 백엔드가 요청 길이나 헤더 정규화에 대해 의견이 다르다. 여러 `Content-Length` 값, `Transfer-Encoding`, HTTP/2 또는 HTTP/3 다운그레이드, 헤더 이름 정규화, 금지된 연결 헤더, CR/LF 변환을 검토하라. 한 컴포넌트가 어떤 바이트를 한 요청에 할당하고, 상대 컴포넌트가 어떤 바이트를 다음 요청에 할당하는지 확인하라.

**키에 포함되지 않은 입력을 통한 웹 캐시 포이즈닝**
요청 값이 캐시된 콘텐츠나 보안과 관련된 헤더를 변경하지만 캐시 키에는 없다. 캐시 키 구성을 포워딩된 호스트/스킴, 선택된 쿠키, 쿼리 정규화, 언어/디바이스 헤더, 인가 상태를 포함한 모든 응답 변형과 비교하라.

**캐시 기만(cache deception) 및 비공개 응답 캐싱**
캐시 라우팅이 비공개 동적 경로를 공개 정적 자산으로 취급하거나, 신원과 인가 입력이 정책에서 빠진 응답을 캐시한다. 에지 캐시 가능성을 애플리케이션 라우트 파싱, 접미사/경로 매개변수 정규화, 응답 캐시 지시자와 비교하라.

**Host 및 포워딩 헤더 신뢰**
신뢰할 수 없는 호스트/프록시 메타데이터가 절대 URL, 테넌트 라우팅, 콜백, 재설정 링크, 캐시 키, 또는 인가가 사용하는 클라이언트 주소를 결정한다. 누가 헤더를 제공할 수 있는지, 그리고 신뢰할 수 있는 인그레스가 클라이언트가 제공한 사본을 제거하는지 확인하라.

**응답 헤더 인젝션**
신뢰할 수 없는 데이터가 안전하지 않은 제어 문자나 정규화와 함께 `Location`, `Set-Cookie`, CSP, 또는 다른 응답 헤더에 도달한다. 보고하기 전에 프레임워크의 거부 여부를 검증하고, 보안과 관련된 응답 변화를 요구하라.

## 브라우저 세션 공격 클래스 (subagent_type: `general`)

**일반 CSRF**
브라우저가 유효한 CSRF 방지 토큰, same-site 요청 바인딩, 또는 엄격한 Origin/Referer 검증 없이 교차 사이트 요청을 수용하는 상태 변경 엔드포인트에 ambient 자격 증명을 보낸다. 폼, JSON 유사, multipart, 메서드 오버라이드, 레거시 라우트를 포함해 쿠키 인증을 사용하는 모든 변경 동작을 목록화하라. SameSite는 실제로 사용되는 쿠키와 브라우저 컨텍스트에서만 유효하다. 로그인 CSRF와 교차 사이트 하위 리소스 요청은 요건이 다를 수 있다.

**세션 고정(fixation)과 무효화**
세션 식별자가 로그인, 계정 전환, MFA 완료, 가장(impersonation), 또는 그 밖의 권한 변경 시 교체되지 않거나, 로그아웃, 비밀번호 변경, 폐기, 계정 비활성화 이후에도 유효하게 남는다. 서버 세션, 리프레시 토큰, 서명된 쿠키, 웹소켓 상태, 캐시 사본, 폴백 엔드포인트를 확인하라.

**쿠키 범위와 전송**
민감한 쿠키가 지나치게 넓은 `Domain` 또는 `Path`를 가지거나, 안전하지 않은 전송 경로를 건널 수 있거나, 다른 컴포넌트가 다르게 선택하는 형제 쿠키와 충돌한다. 플래그가 단순히 누락된 경우는 현실적인 낮은 신뢰의 오리진, 네트워크 위치, 또는 브라우저 경로가 자격 증명을 얻거나 대체할 수 있지 않는 한 하드닝 메모로 남는다.

## 연합 신원 공격 클래스 (subagent_type: `general`)

먼저 역할을 확정하라. 리디렉션 허용 목록과 코드 발급 같은 인가 서버 통제는 신뢰 당사자(relying-party) 클라이언트에 속하지 않는다. 검증 및 바인딩 결함은 아티팩트를 소비하는 컴포넌트에 속한다.

**JWT 검증과 클레임 바인딩**
서명 검증, 서버에 고정된 알고리즘과 키 소스를 확인한 다음 `exp`, `nbf`, `aud`, `iss`를 확인하라. `kid`, `jku`, `x5u`를 신뢰할 수 없는 키 선택자로, 그리고 중복/헤더 정규화와 검증 없는 디코드 경로를 검토하라. 다른 서비스를 위한 유효한 토큰은 신뢰할 수 있는 발급자가 서명했더라도 여기서는 유효하지 않다.

**OAuth/OIDC 요청 및 콜백 바인딩**
대상이 인가 서버인 경우 정확한 `redirect_uri` 소유권, 세션에 바인딩된 `state`, 해당되는 경우 PKCE와 인가 코드 바인딩, ID 토큰의 issuer/audience/signature/nonce, 다중 제공자 흐름에서 선택된 IdP 바인딩을 검증하라. 최초 콜백, 재시도, 모바일/딥 링크, 계정 연결 경로를 비교하라.

**SAML 서명 객체 및 어서션 바인딩**
서명이 검증되는 요소가 신원으로 사용되는 요소와 같은지 확인하라. 서명되지 않은/폴백 경로, 안전한 XML 파서 구성, 정규화(canonicalization) 차이, 유효 기간, audience/recipient, 요청 상관관계, 재생(replay) 상태 같은 신선도/바인딩 필드를 검토하라.

## MFA, 패스키, 계정 전환 공격 클래스 (subagent_type: `general`)

**MFA 등록과 보증 수준 하향**
등록, 교체, 비활성화, 복구 코드 생성, 신뢰 디바이스 생성, 폴백 로그인에는 의도된 사전 보증 수준이 필요하다. 유효한 첫 번째 요소가 정책이 요구하는 새로운 인증 없이 두 번째 요소를 등록하거나 교체할 수 없는지, 그리고 비활성화되었거나 오래된 요소가 더 이상 세션을 인가하지 못하는지 확인하라.

**스텝업 바인딩과 우회**
성공한 챌린지가 잘못된 세션, 계정, 테넌트, 동작, 또는 API 요청을 상향시키거나, 대체 경로가 보증 수준 검사를 생략한다. 챌린지를 주체, 현재 세션, 보증 대상, (필요한 경우) 연산 또는 자원, 만료, 일회성 완료에 바인딩하라. UI, API, 배치, 복구, 재개된 흐름 경로를 비교하라.

**WebAuthn 및 패스키 검증**
등록 시 챌린지, RP ID, 기대 오리진, 자격 증명, user/userHandle, 알고리즘, 정책이 요구하는 사용자 검증을 시작한 세션에 바인딩하라. 인증 시 챌린지, RP/오리진, 자격 증명 소속, 서명, 의도된 사용자 존재/검증을 검증하라. 계정 발견 및 연결 흐름에서 userHandle 또는 자격 증명-계정 혼동을 확인하라. 서명 카운터 처리는 제품이 카운터 후퇴를 복제 신호로 취급할 때만 의미가 있다.

**계정 연결과 신원 충돌**
기존 계정에 IdP, 패스키, 이메일, 전화번호, 디바이스, 외부 계정을 추가하려면 현재 인증된 세션, 새 신원에 대한 검증된 소유권, 정책이 요구하는 스텝업, 연결을 시작한 계정에 바인딩된 콜백 state가 필요하다. 연결 해제/재연결과 초대 수락 경로에서 검증된 식별자 또는 테넌트 충돌을 검토하라.

**비밀번호 재설정과 더 넓은 복구**
복구 토큰, 지원/관리자 복구, 백업 코드, 디바이스 마이그레이션, 이메일 또는 전화번호 변경은 흔히 가장 약한 인증 경로가 된다. 토큰 무작위성, 사용자/동작 바인딩, 만료, 일회성 상태, 속도/회계 통제, 전달 URL 신뢰, 이전 토큰과 세션의 무효화를 검증하라. 공개된 계정 존재 여부만 드러내는 응답 차이는 자동으로 보안 발견 사항이 되지 않는다.

## API 키 및 mTLS 공격 클래스 (subagent_type: `general`)

**API 키 범위와 자원 바인딩**
키가 서버 측 레코드가 부여한 것보다 더 넓은 테넌트, 자원, 동작, 또는 환경에 대해 인증하거나, 요청 매개변수가 그 바인딩을 덮어쓴다. 키 조회, 접두사/전체 비밀 검증, 공개용 키와 비밀 키 간 타입 혼동, 범위 검사, 로테이션, 폐기 캐시, 대량 엔드포인트를 검토하라.

**API 키 노출과 안전하지 않은 전송**
키가 클라이언트 번들, URL, 리디렉션, 로그, 오류 경로, 빌드 아티팩트, 또는 낮은 신뢰의 주체가 접근할 수 있는 응답에 나타난다. 키라고 불리지만 공개 식별자인 것은 비밀이 아니다. 키 유형과 노출로 얻는 권한을 확인하라.

**mTLS 피어와 애플리케이션 신원 혼동**
프로세스가 어떤 네트워크 피어가 보낸 클라이언트 인증서 신원 헤더든 신뢰하거나, 체인은 검증하지만 공격자가 영향을 줄 수 있는 subject 텍스트를 계정에 잘못 매핑하거나, 잘못된 신뢰 도메인, 확장 용도(extended usage), audience, 또는 유효성 정책의 인증서를 수용한다. 신뢰할 수 있는 프록시가 mTLS를 종료하는 경우, 해당 프록시만 연결할 수 있는지, 들어오는 신원 헤더를 제거하는지, 백엔드가 정제된 신원을 요청에 바인딩하는지만 검증하라.

**인증서 수명 주기 폴백**
만료되었거나, 폐기되었거나, 없거나, 갱신에 실패한 인증서가 bearer 전용 또는 익명 동작으로의 조용한 폴백을 일으키거나, 수명이 긴 풀링된 연결이 폐기 후에도 인가를 유지한다. 배포 폐기 데이터가 없으면 결과는 `needs_validation`이며, 저장소 내의 fail-open 분기는 소스로 확인 가능하다.

## 공통 기법 (위 전체에 적용)

- 모든 자격 증명과 챌린지에 대해 발급 → 저장 → 전송 → 소비 → 갱신 → 폐기를 따라가라. 정상, 오류, 재시도, 마이그레이션, 레거시, 계정 전환 경로를 비교하라.
- 동일한 신원으로 가는 모든 문과 동일한 민감 연산으로 가는 모든 경로를 열거하라. 유효한 정책은 가장 세련된 UI가 아니라 가장 약한 병렬 경로이다.
- 파서, 프록시, 라우터, 캐시, 애플리케이션 정규화를 나란히 diff하라. 로컬 검증에서는 라이브 배포에 트래픽을 보내는 대신 동일한 제한된 요청 픽스처를 각 컴포넌트에 입력하라.
- 복구와 연결에서는 계정의 이전/이후 그래프를 그려라. 각 간선은 현재 주체, 새 신원의 증명, 필요한 보증 수준, 콜백/세션 바인딩, 폐기 효과를 명시해야 한다.

## 검증 규칙 (여기서 어떤 발견 사항이든 보고하기 전에 적용)

1. 소스 가시성 게이트를 적용하라. 프록시 체인, 에지 캐시 키, IdP 정책, 인증서 신뢰, 브라우저 쿠키 동작, 비밀, 배포된 인증 모드는 저장소 밖에 있을 수 있다. 없는 인프라의 동작을 단정하지 말고 정밀한 `needs_validation` 후보를 기록하라.
2. 프레이밍과 캐시 발견 사항에는 두 컴포넌트와 갈라지는 파싱/키를 명시하라. 제한된 로컬 픽스처로 요청 간, 사용자 간, 또는 비공개 응답 영향을 확인하라.
3. 토큰, MFA, 패스키, 계정 연결, 복구, API 키, mTLS 발견 사항에는 검증 라인과, 누락된 주체/세션/자원/오리진/audience/동작/보증 수준 바인딩을 인용하라. 서버가 유효하지 않은 전환이나 자격 증명을 수용함을 입증하라.
4. CSRF에는 ambient 자격 증명, 상태 변경 라우트, 수용되는 교차 사이트 요청 형태, 브라우저 쿠키 정책, 누락된 유효 검사를 명시하라. 읽기 전용 동작과 ambient가 아닌 bearer 토큰을 요구하는 라우트는 해당하지 않는다.
5. 프레임워크와 라이브러리의 기본값을 검증하라. 버전이나 구성을 알 수 없으면 `needs_validation`을 사용하라. 검증되지 않은 critical 주장을 더 낮은 심각도의 confirmed 발견 사항으로 바꾸지 마라.
6. 완전한 소스 추적과 관찰 가능한 무단 신원, 상태, 또는 노출이 있을 때만 `confirmed`를 반환하라. `needs_validation`에는 누락된 사실과 이를 해소하는 안전한 로컬 또는 소유자 관찰 검사를 명시하라.
