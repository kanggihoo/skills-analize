# Constraint-Driven Development

## 개요

이 팩의 다른 스킬들은 좋은 상태가 어떤 모습인지 설명한다. `code-review-and-quality`는 다섯 가지 축을 제공한다. `test-driven-development`는 사이클을 제공한다. `security-and-hardening`은 위협 목록을 제공한다. 이 모두는 에이전트가 읽고 따를 수도 있고 따르지 않을 수도 있는 산문으로 존재하며, 어느 것도 세션이 끝나면 남지 않는다.

이 스킬은 다른 것을 만들어 낸다. **이 프로젝트의** 기준을 수치와 함께 문서로 기록한 것으로, 대화가 끝난 뒤에도 남고 기계적으로 검사할 수 있다.

이유가 중요하다. 직접 코드를 작성할 때는 그 코드를 읽으면 좋은 코드인지 알 수 있었다. 에이전트는 오후 한나절에 당신이 한 주 동안 읽을 분량보다 더 많이 작성하므로, 판단은 당신의 머릿속에서 루프 주변에서 실행되는 검사로 옮겨 간다. 그 검사는 존재해야 하고, 당신이 실제로 고른 수치를 가져야 하며, 에이전트가 자신의 출력을 스스로 고칠 수 있을 만큼 작업과 가까운 곳에서 작동해야 한다.

스펙 주도 개발은 무엇을 만들지 말한다. 테스트 주도 개발은 그것이 동작함을 증명한다. 제약 조건 주도 개발은 풀 리퀘스트에서 누군가 논쟁을 벌이기 전에 "배포하기에 충분히 좋다"가 무엇을 뜻하는지 정의한다.

## 사용 시점

다음의 경우 이 스킬을 적용한다.

- 프로젝트나 중요한 기능을 시작하는데 품질 기준이 문서로 정해져 있지 않을 때
- 사용자가 "set up constraints", "add quality gates", "define our standards", "stop the agent shipping junk"를 요청할 때 (제약 조건 설정, 품질 게이트 추가, 표준 정의, 에이전트가 쓰레기를 배포하지 못하게 막기)
- 에이전트가 아무도 한 줄씩 읽지 않는 분량을 만들어 내고 있을 때
- CI에 검사가 있지만 어떤 것이 머지를 막고 어떤 것이 장식인지 아무도 말하지 못할 때
- 커버리지, 성능, 접근성 수치를 한 번에 정하지 않고 PR마다 논쟁할 때
- `/build auto`나 다른 자율 루프를 실행하려는데, 그것과 main 사이를 가로막는 것이 에이전트가 직접 작성한 테스트 스위트뿐일 때

**사용하지 말아야 할 때:**

- 프로젝트에 이미 `CONSTRAINTS.md`가 있고 사용자가 그것을 바꾸지 않을 때 — 대신 그 파일을 읽고 따른다
- 일회용 스크립트, 스파이크, 버려질 프로토타입
- 사용자가 지금 당장 코드 리뷰(`code-review-and-quality`)를 원하거나 CI 파이프라인(`ci-cd-and-automation`) 구축을 원할 때
- 기대 수명이 2주인 제품-시장 적합성(product-market fit) 이전의 코드 — 아래의 하한선(floor)은 여전히 가치가 있지만, 나머지는 그렇지 않다

## 로딩 제약

인터뷰에는 실제 사용자가 필요하다. **비대화형 컨텍스트(CI, `/loop`, 자율 실행)에서는 인터뷰를 실행하지 마라.** 제약 조건이 없는데 그런 컨텍스트에 있다면, 아래의 하한선(Floor)을 적용하고, 적용했음을 기록하고, 나머지는 사람이 처리하도록 표시하라.

## 프로세스

### Step 1: 묻기 전에 먼저 탐지하라

읽을 수 있는 것을 절대 묻지 마라. 첫 질문을 하기 전에 다음을 수집하라.

| 대상 | 확인할 위치 |
|------|---------------|
| 언어와 스택 | `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml` |
| 테스트 러너 | 개발 의존성, `test` 스크립트, 기존 테스트 파일 |
| 기존 린터 | `eslint.config.*`, `biome.json`, `.ruff.toml` |
| 현재 커버리지 | `coverage/` 출력, 또는 스위트를 한 번 실행 |
| CI | `.github/workflows/`, `.gitlab-ci.yml` |
| 에이전트 하네스 | `.claude/`, `.codex/`, `AGENTS.md` |

발견한 내용을 두 줄로 보고한 뒤, 남은 것만 질문하라.

### Step 2: 네 가지 질문, 각각 기본값 포함

`interview-me`의 한 번에 한 질문씩 하는 원칙을 따르되, 한 가지를 바꾼다. 여기서는 모든 질문에 기본값이 있으므로, "모르겠다"도 동작하는 설정을 만들어 내는 완전한 답이다.

```
Q1: 하한선 외에 다음 중 무엇을 강제하고 싶은가?
    (a) 새 코드의 테스트 커버리지
    (b) 보안 스캔
    (c) 성능 예산
    (d) 접근성
    (e) 아키텍처 경계
GUESS: (a)와 (b) — 이미 테스트 러너가 있고 사용자 입력을 처리하고 있다.
DEFAULT if unsure: (a)와 (b).
각 선택의 비용을 말하라: (c)와 (d)는 실행 중인 URL이 필요하고, (e)는 규칙 파일을 작성해야 한다.
```

```
Q2: 에이전트가 작업 중간에 검사가 실패하면, 차단해야 하는가 경고해야 하는가?
GUESS: 차단. 에이전트를 무인으로 돌리고 있고, 아무도 읽지 않는 경고는 그냥 경고일 뿐이다.
DEFAULT if unsure: 하한선은 차단하고, 그 외 모든 것은 처음 2주 동안 경고한다.
```

```
Q3: 염두에 둔 목표 수치가 있는가, 아니면 내가 현재 위치를 측정하고 그 선을 유지해야 하는가?
GUESS: 측정. 대부분의 팀에는 수치가 없고, 지어낸 수치는 무시된다.
DEFAULT if unsure: 측정하고 유지한다. 아래 "Ratchets"를 참고하라.
```

```
Q4: 에이전트가 작업을 되돌려 주기 전에 허용할 수 있는 가장 느린 검사는 얼마인가?
GUESS: 약 90초. 그보다 길면 실행하지 않게 된다.
DEFAULT if unsure: 작업 종료 시 90초, CI에서는 무제한.
```

네 개에서 멈춰라. 열두 개짜리 질문지는 아무도 이해하지 못하는 설정과 시작한 것을 후회하는 사용자를 낳는다.

### Step 3: CONSTRAINTS.md를 작성하라

저장소 루트에 파일 하나를 둔다. 어떤 하네스의 어떤 에이전트든 읽을 수 있고, 변경 사항이 마땅히 있어야 할 리뷰에 나타난다.

```markdown
# Constraints

Last reviewed: 2026-08-08 by @addy

## Floor (항상 강제, 별도 설정 불필요)

- 새로운 억제 주석 금지: `@ts-ignore`, `eslint-disable`, `# noqa`, `# type: ignore`
- 구현되지 않은 스텁 금지: `throw new Error("Not implemented")`, 빈 `catch {}`
- 커밋 메시지에 사유 없이 테스트를 건너뛰거나 삭제하는 것 금지
- 소스에 시크릿 금지
- 변경을 통과시키려고 이 파일을 약화시키지 않는다

## Enforced with numbers

| Dimension | Rule | Checked by | Runs at |
|-----------|------|-----------|---------|
| Types | 타입 오류 0건 | `tsc --noEmit` | 모든 편집 |
| Lint | 우리 설정 기준 오류 0건 | `biome check` | 모든 편집 |
| Secrets | 소스에 시크릿 없음 | `gitleaks detect --redact` | 모든 편집 |
| Coverage | 변경된 라인 ≥ 80% 커버 | `vitest run --coverage` + git diff | 작업 종료, CI |
| Security: code | high 발견 사항 없음 | `semgrep scan --config p/default` | CI |
| Security: deps | high 이상 없음 | `osv-scanner scan source -r .` | CI |
| Accessibility | critical 또는 serious 0건 | `axe $PREVIEW_URL --tags wcag2a,wcag2aa,wcag21aa` | 프리뷰 배포 |
| Performance | LCP ≤ 2500ms, CLS ≤ 0.1 | `lighthouse $PREVIEW_URL --output=json` | 프리뷰 배포 |

모든 행은 판정을 내리는 명령을 명시한다. 수치는 있는데 이 열에 명령이
없는 차원은 제약 조건이 아니라 바람일 뿐이다.

## Measured, not yet enforced

| Metric | Today | Direction |
|--------|-------|-----------|
| Project coverage | 62.4% | 떨어지면 안 됨 |
| Bundle size (main) | 184 kB | 커지면 안 됨 |

## Exceptions

| ID | Rule | Path | Reason | Owner | Expires |
|----|------|------|--------|-------|---------|
| W1 | `no-explicit-any` | `src/legacy/**` | 재작성은 ENG-441에서 추적 | @addy | 2026-11-01 |
```

그런 다음 `AGENTS.md`와 `CLAUDE.md`에 한 줄을 추가한다: `Read CONSTRAINTS.md before writing code. Do not weaken it to make a change pass.`

### Step 4: 각 차원에 필요한 것을 설치하라

차원을 고른다는 것은 무언가를 설치한다는 뜻이다. 수치만 쥐여 주고 메커니즘은 없는 채로 사용자를 두지 마라. 사실상의 표준(de facto) 도구가 있는데 직접 검사기를 만들어 내지도 마라. 아래 도구들이 나열된 이유는 이들의 규칙 형식과 임계값이 생태계의 나머지 전부가 목표로 삼는 대상이어서, 팀의 기존 설정이 계속 동작하기 때문이다.

| 차원 | 도구 | 설치 | 실행 | 게이트 기준 |
|-----------|------|---------|-----|---------|
| Types (TS) | tsc | 이미 있음 | `tsc --noEmit` | 모든 오류 |
| Types (Python) | mypy | `pip install mypy` | `mypy .` | 모든 오류 |
| Lint | 기존 설정 | 이미 있음 | `eslint .` / `biome check` / `ruff check` | 모든 오류 |
| Coverage (JS) | 테스트 러너 | 이미 있음 | `vitest run --coverage` (또는 `jest --coverage`) | 변경된 라인의 커버리지 |
| Coverage (Python) | pytest-cov | `pip install pytest-cov` | `pytest --cov --cov-report=lcov` | 동일 |
| Security: code | Semgrep | `pipx install semgrep` | `semgrep scan --config p/default --config p/owasp-top-ten` | high 발견 사항 하나라도 |
| Security: secrets | gitleaks | `brew install gitleaks` | `gitleaks detect --redact --no-banner` | 발견 사항 하나라도 |
| Security: dependencies | osv-scanner | `brew install osv-scanner` | `osv-scanner scan source -r .` | high 이상 |
| Performance: page | Lighthouse | `npm i -D lighthouse` | `lighthouse $URL --output=json --quiet` | LCP, CLS, 성능 점수 |
| Performance: bundle | size-limit | `npm i -D size-limit` | `size-limit --json` | 항목별 바이트 예산 |
| Accessibility | axe-core | `npm i -D @axe-core/cli` | `axe $URL --tags wcag2a,wcag2aa,wcag21aa` | critical 또는 serious 0건 |
| Architecture | dependency-cruiser | `npm i -D dependency-cruiser` | `depcruise --validate src` | 모든 위반 |
| Assertion quality | Stryker | `npm i -D @stryker-mutator/core` | `stryker run --mutate <changed files>` | 뮤테이션 점수 |

건너뛰면 곤란해지는 다섯 가지:

1. **gitleaks의 `--redact`는 선택 사항이 아니다.** 이것이 없으면 매치된 시크릿이 에이전트의 트랜스크립트에 남게 되고, 유출된 키가 로그, 요약, 커밋 메시지에 들어가는 경로가 바로 이것이다. 규칙과 위치를 보고하고, 값은 절대 보고하지 마라.
2. **Lighthouse와 axe에는 URL이 필요하다.** 실행 중인 앱에 대해서만 동작하므로, 프리뷰 배포나 먼저 띄워 둔 로컬 서버를 대상으로 하는 런타임 단계에 속한다. 접근할 URL이 없는 프로젝트(CLI, 라이브러리, 데스크톱 앱)라면, 실행할 수 없는 검사를 지어내지 말고 그렇다고 말한 뒤 해당 차원을 제외하라.
3. **비싼 검사는 diff로 범위를 좁혀라.** 저장소 전체에 `stryker run --mutate`를 돌리면 몇 시간이 걸려 결국 꺼지지만, 변경이 건드린 파일에 돌리면 1분이 안 걸린다. 경로 목록을 받는 Semgrep도 마찬가지다.
4. **커버리지를 위해 테스트를 두 번 실행할 필요는 없다.** 스위트가 이미 쓰는 lcov를 읽어 `git diff`와 교집합을 구하라. 수치 하나를 얻으려고 스위트를 두 번 돌리는 것은 사람들이 이 방식을 싫어하게 만드는 가장 빠른 길이다.
5. **Semgrep의 레지스트리 규칙은 무료로 실행할 수 있지만, 재배포하기 전에 라이선스를 확인하라.** 법무팀에 중요하다면 `opengrep`이 같은 규칙 형식과 JSON 출력을 가진 드롭인 포크다.

에이전트 없이도 재현할 수 있도록 각각을 프로젝트 자체의 스크립트에 추가하라.

```json
{
  "scripts": {
    "check:fast": "tsc --noEmit && eslint . && gitleaks detect --redact --no-banner",
    "check:task": "npm run check:fast && vitest run --coverage",
    "check:full": "npm run check:task && semgrep scan --config p/default && osv-scanner scan source -r ."
  }
}
```

이 매핑이 도구보다 더 중요하다. `check:fast`는 편집 후에 실행되고, `check:task`는 에이전트가 작업이 끝났다고 생각할 때, `check:full`은 CI에서 실행된다.

이제 명령이 두 곳, 즉 `CONSTRAINTS.md`의 `Checked by` 열과 이 스크립트들에 존재한다. `CONSTRAINTS.md`가 정본(canonical source)이다. 각 명령 옆에 이유를 함께 담고 있고 리뷰에 나타난다. 스크립트는 그것을 그대로 반영해야 하는 편의용 래퍼일 뿐 두 번째 진실의 원천이 아니며, 둘이 어긋나면 파일이 이긴다.

### Step 5: 라이프사이클에 연결하라

가장 큰 실수는 모든 것을 모든 곳에서 실행하는 것이다. 에이전트를 멈춰 세우는 검사는 꺼지고, 사람들이 꺼 버린 게이트는 게이트가 없는 것보다 나쁘다. 기준이 여전히 존재하는 것처럼 보이기 때문이다.

| 단계 | 명령 | 실행되는 것 | 예산 |
|-------|---------|-----------|--------|
| BUILD | `/build` | 타입, 린트, 시크릿, 하한선 | 5초 미만, 변경된 파일만 |
| VERIFY | `/test` | 관련 테스트, 변경된 라인의 커버리지 | 90초 미만 |
| REVIEW | `/review` | 모든 것, 그리고 아래의 가드 | 수 분 |
| SHIP | `/ship` | 방향성 검사, 회귀 없음 | CI |

이를 견딜 만하게 유지해 주는 두 가지 규칙:

1. **diff로 범위를 좁혀라.** 저장소 전체가 아니라 이 변경이 건드린 라인을 검사하라. 변경된 라인의 커버리지는 에이전트가 움직일 수 있는 수치이고, 프로젝트 커버리지는 물려받은 수치다.
2. **비용이 배치를 결정한다.** 몇 초를 넘는 것은 모두 편집 루프 밖으로 옮긴다. 저장소 전체의 뮤테이션 테스트는 몇 시간이 걸리지만, 변경이 건드린 파일에서는 1분이 안 걸린다. 사람들이 실행하는 검사와 실행하지 않는 검사의 차이가 바로 이것이다.

### Step 6: 기준 자체를 지켜라

에이전트가 코드와 검사를 모두 작성한다면 검사는 아무것도 증명하지 못한다고 누군가 지적할 것이다. 절반은 맞고, 그에 대비해 설계할 가치가 있다.

에이전트는 영리한 허점을 만들지 않는다. 빨간 검사에 부딪히면 green으로 가는 가장 싼 길을 택한다. 리뷰 시점에 diff에서 다음 다섯 가지 움직임을 살펴라.

1. **임계값이 움직였다.** 예산이 낮아졌거나, 심각도가 내려갔거나, 검사가 빠른 단계에서 제거되었다. `CONSTRAINTS.md`를 브랜치 분기 시점의 상태와 비교하라.
2. **테스트가 쉬워졌다.** `.skip`이 추가되었거나, 테스트 파일이 삭제되었거나, 남아 있는 테스트에서 assertion이 빠졌다.
3. **검사기가 침묵당했다.** 새로운 `@ts-ignore` 또는 `eslint-disable`. 네 가지 억제 주석은 의존하고 있는 검사를 꺼 버리므로 특별히 주의할 가치가 있다. `istanbul ignore`는 코드를 테스트하는 대신 커버리지에서 제외하고, `Stryker disable`은 살아남은 뮤턴트를 숨기며, `nosemgrep`과 `gitleaks:allow`는 보안 발견 사항에 대해 같은 일을 한다.
4. **작업이 미완성이다.** 예외를 던지는 스텁, 실패를 침묵으로 바꾸는 빈 `catch`, 구현이 있어야 할 자리에 서 있는 `TODO`.
5. **예외가 나타났다.** 아무도 논의하지 않은 Exceptions 표의 새 행.

이 중 어느 것도 `git diff` 이상의 도구가 필요하지 않다. 기준을 조이는 것은 조용해야 하고, 느슨하게 하는 것은 시끄러워야 한다.

번호가 매겨진 차원들과 달리 하한선에는 사실상 표준인 전용 도구가 없으므로, 이를 강제하라는 요청을 받은 에이전트는 검사기를 처음부터 작성하는 경향이 있고, 두 에이전트는 서로 다른 검사기를 작성한다. 이 다섯 가지 검사의 참조 구현이 이 스킬과 함께 [references/floor-guard-KO.md](references/floor-guard-KO.md)로 제공된다(diff 범위, 종료 코드 `0`/`1`/`2`, 에코시스템별로 조정 가능한 패턴). 다시 만들지 말고 이것을 조정해 사용하라. 모든 차원이 사실상 표준 도구를 명시하는 것과 같은 이유로, 즉 실행과 스택이 달라도 메커니즘이 같도록 하기 위해서다.

**모든 검사가 똑같이 순환적인 것은 아니다.** 한 가지 질문으로 순위를 매겨라. 에이전트가 동작하지 않는 코드를 작성해서 이것을 통과시킬 수 있는가?

- **외부(External)** — axe-core는 WCAG를 담고 있고, `osv-scanner`는 취약점 데이터베이스를 읽으며, Lighthouse는 실제 브라우저를 측정한다. 에이전트는 이들과 논쟁할 수 없다.
- **프로젝트(Project)** — 당신의 린트 규칙, 당신의 레이어 경계. 사람이 파일을 소유한다.
- **스위트(Suite)** — 당신의 테스트. 가장 유용하지만, 진정으로 순환적인 유일한 것이다.

전적으로 세 번째 종류로만 이루어진 기준은 외부의 의견이 들어 있는 기준보다 가치가 낮다. 외부 제약 조건이 최소 하나는 있는지 확인하라.

### Step 7: 래칫(Ratchets), 수치가 없을 때

62%인 코드베이스에 80% 커버리지를 설정하면 영원히 빨간 빌드가 되고, 그다음에는 빨간 빌드를 무시하는 법을 배운 팀이 된다.

대안은 어떤 결정도 요구하지 않는다. 현재 위치를 기록하고, 그보다 나빠지는 것을 거부하라. 오늘의 수치와 방향을 "Measured, not yet enforced" 표에 넣어라. 모든 검사는 이상적인 목표가 아니라 기록된 값과 비교한다. 수치가 개선되면 갱신하고, 떨어지면 그것이 발견 사항이다.

이는 학습(training)에 대한 정당한 반론에도 답한다. 모델은 몇 초 만에 평가할 수 있는 테스트 통과에 대해 보상받는다. 아키텍처의 부패는 수개월에 걸쳐 드러나며 가중치에는 결코 도달하지 않는다. 래칫(ratchet)은 빠져 있던 페널티를 빌드가 볼 수 있는 곳에 문서로 적어 둔 것이다.

## 합리적 기본값(Sane Defaults)

사용자에게 의견이 없을 때 이것들을 사용하라. 대부분의 코드베이스가 첫날부터 충족할 수 있도록 고른 값이다.

| 제약 조건 | 기본값 | 이 수치인 이유 |
|------------|---------|-----------------|
| 변경된 라인의 커버리지 | ≥ 80% | 테스트를 강제할 만큼 높고, 설정 한 줄은 허용할 만큼 낮다 |
| 프로젝트 커버리지 | 오늘의 값, 떨어지면 안 됨 | 채택하는 데 논쟁이 필요 없다 |
| 뮤테이션 점수 (사용하는 경우) | 시작은 ≥ 60% | 뮤테이션을 한 번도 해본 적 없는 스위트의 전형적인 값. 80%는 성숙한 수준이다 |
| 의존성 취약점 | high 이상 없음 | 그 아래는 대부분 노이즈다 |
| LCP | ≤ 2500 ms | Core Web Vitals "good" 임계값 |
| CLS | ≤ 0.1 | 동일 |
| 접근성 | critical 또는 serious axe 위반 0건 | moderate와 minor는 흔히 논쟁의 여지가 있다 |
| 예외 수명 | 90일 | 수정을 계획하기에 충분히 길고, 기억하기에 충분히 짧다 |
| 래칫 허용 오차 | 0.5% | 관련 없는 파일이 수치를 움직일 때의 드리프트를 흡수한다 |

수치와 이유를 함께 명시하라. 근거가 없는 임계값은 그것에 걸린 다음 사람이 삭제해 버린다.

## 단계적 강화 경로(Escalation Path)

제약 조건은 세 가지 수준의 강제력으로 작동한다. 첫 번째에서 시작하라.

1. **문서만(Written only).** `CONSTRAINTS.md`가 존재하고 에이전트가 읽는다. 비용이 들지 않고, 성실한 실수를 잡아내지만, 에이전트가 준수하는 데 의존한다.
2. **스크립트(Scripted).** 빠른 검사를 실행하는 `npm run check`(또는 `make check`)를 에이전트의 post-edit 훅과 CI에 연결한다. 결정적이고, 새로운 의존성이 없다.
3. **도구 기반(Tool-backed).** diff 범위 지정, 예산, 래칫, 가드 검사를 처리하는 전용 러너. 설정이 셸 스크립트의 범위를 넘어설 때 사용한다. [references/floor-guard-KO.md](references/floor-guard-KO.md)의 floor-guard 참조 구현이 이 중 가드 검사 부분의 출발점이다.

대부분의 프로젝트는 2에서 멈춰야 한다. 검사를 실행하는 셸을 약 30줄 넘게 유지보수하게 되면 3으로 옮겨라.

**첫 실행은 하한선만으로도 된다.** floor guard는 diff만 대상으로 하고 설치가 필요 없으므로, 첫 커밋이 보호받기 전에 모든 검사기를 세워 둘 필요 없이 첫날부터 하한선을 강제하고, 도구를 설치할 때마다 번호가 매겨진 차원을 추가할 수 있다. 머신 전체에 설치되는 보안 도구(gitleaks, osv-scanner)는 노트북을 깨끗하게 유지하고 싶다면 CI 전용으로 실행할 수도 있다. 각 차원이 어디서 실행되는지는 `Runs at` 열에 선언하라.

## 흔한 합리화

| 변명 | 현실 |
|--------|---------|
| "코드가 안정되면 제약 조건을 추가하겠다" | 코드는 움직이는 동안 허용된 것을 중심으로 안정된다 |
| "테스트가 곧 제약 조건이다" | 직접 쓴 테스트는 자기 자신과 동의한다는 것을 증명할 뿐이다. 새 코드의 커버리지, 의존성 위험, 번들 증가에 대해서는 아무것도 말해 주지 않는다 |
| "80% 커버리지는 달성할 수 없다" | 그렇다면 80%로 설정하지 마라. 오늘의 수치를 설정하고 그것을 유지하라 |
| "이러면 에이전트가 느려질 것이다" | 느린 검사를 빠른 루프에 넣었을 때만 그렇다. 그것은 배치 오류이지, 제약 조건에 반대할 근거가 아니다 |
| "우리의 표준이 무엇인지는 내가 기억할 것이다" | 에이전트는 기억하지 못하고, 코드의 대부분을 쓰는 것도 에이전트다 |
| "제약 조건이 배포를 막을 것이다" | 소유자와 날짜가 있는 예외가 당신을 풀어 준다. 제약 조건을 삭제하면 모두를 영원히 풀어 준다 |

## 위험 신호(Red Flags)

다음을 발견하면 멈추고 다시 생각하라.

- 인터뷰가 네 개 질문을 넘겼거나, 사용자가 설명할 수 없는 설정이 만들어졌다
- 코드베이스가 오늘 실패하는 예산이 설정되었는데 그것을 달성할 계획이 없다
- 수치는 있지만 뒷받침하는 도구가 없는 차원이 CONSTRAINTS.md에 기재되었다
- 사실상 표준 검사기가 있는데 직접 만들어서 팀의 기존 설정이 무시된다
- 모든 제약 조건을 프로젝트 자체의 테스트 스위트가 검사하며 외부의 의견이 없다
- 실패하던 기능과 같은 커밋에서 `CONSTRAINTS.md`가 변경되었다
- 예외에 소유자가 없거나, 만료일이 1년 넘게 남아 있다
- 에이전트가 코드를 고치는 대신 임계값을 완화하자고 제안했다
- 느린 검사가 편집 루프에 들어가서 누군가 `--no-verify`를 쓰기 시작했다
- 작성된 이후 아무도 `CONSTRAINTS.md`를 열어 본 적이 없다

## 검증

이 스킬이 올바르게 적용되었다면 다음이 충족된다.

- [ ] `CONSTRAINTS.md`가 존재하며, 그 안의 모든 수치에 명시된 이유가 있다
- [ ] 하한선이 강제되고 있으며 현재 코드베이스에서 변경 없이 통과한다
- [ ] 사용자가 고른 모든 차원에 설치된 도구와 오늘 실행되는 명령이 있다
- [ ] 각 제약 조건이 어디서 실행되는지 명시하고, 빠른 단계는 몇 초 안에 머문다
- [ ] 최소 하나의 제약 조건이 외부적이다 (이 프로젝트 자체의 테스트가 판단하지 않는다)
- [ ] 측정만 하는 지표는 오늘의 값과 방향을 기록한다
- [ ] 예외에 소유자와 만료일이 있다
- [ ] `AGENTS.md` 또는 `CLAUDE.md`가 이 파일을 가리킨다
- [ ] 현재 브랜치에서 시험 실행했을 때 사용자가 동의하지 않는 실패가 나오지 않는다
