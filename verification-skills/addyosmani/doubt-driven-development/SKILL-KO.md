# Doubt-Driven Development

## 개요

확신에 찬 답이 올바른 답은 아니다. 긴 세션은 컨텍스트를 쌓고, 그 컨텍스트는 아무도 알아채지 못하는 사이에 가정을 "사실"로 바꿔 놓는다. Doubt-driven development는 어떤 중요한 출력이든 확정되기 전에, 승인이 아니라 **반증**하도록 편향된 새로운 컨텍스트의 리뷰어를 구체화해 내는 규율이다.

이것은 `/review`가 아니다. `/review`는 완성된 산출물에 대한 판정이다. 이것은 진행 중에 취하는 자세로, 방향 수정이 아직 저렴한 동안 중요한 결정을 반대 심문한다.

## 사용 시점

다음 중 최소 하나라도 참이면 결정은 **중요한(non-trivial)** 것이다.

- 분기 로직을 도입하거나 수정한다
- 모듈 또는 서비스 경계를 넘나든다
- 타입 시스템이나 컴파일러가 검증할 수 없는 속성(스레드 안전성, 멱등성, 순서, 불변식)을 주장한다
- 정확성이 미래의 독자가 볼 수 없는 컨텍스트에 달려 있다
- 영향 반경(blast radius)이 되돌릴 수 없다 (프로덕션 배포, 데이터 마이그레이션, 공개 API 변경)

다음의 경우 이 스킬을 적용한다.

- 불확실한 상태에서 아키텍처 결정을 내리려는 때
- 중요한 코드를 커밋하려는 때
- 자명하지 않은 사실("이것은 안전하다", "이것은 확장된다", "이것은 스펙과 일치한다")을 주장하려는 때
- 완전히 이해하지 못하는 코드에서 작업할 때

**사용하지 말아야 할 때:**

- 기계적인 작업(이름 변경, 포매팅, 파일 이동)
- 명확하고 모호하지 않은 사용자 지시를 따를 때
- 기존 코드를 읽거나 요약할 때
- 정확성이 자명한 한 줄짜리 변경
- 순수한 도구 작업(테스트 실행, 파일 목록 조회)
- 사용자가 검증보다 속도를 명시적으로 요청했을 때

모든 키 입력을 의심하면 아무것도 배포하지 못한다. 이 스킬은 위에서 정의한 중요한 결정에만 적용된다.

## 로딩 제약

이 스킬은 **메인 세션 오케스트레이터**를 위해 설계되었으며, 여기서는 Step 3(DOUBT, 아래에 상술)이 새로운 컨텍스트의 리뷰어를 생성할 수 있다.

- **이 스킬을 페르소나의 `skills:` 프론트매터에 추가하지 마라.** Step 3을 따르는 페르소나는 또 다른 페르소나를 생성하게 되며, 이는 `../../references/orchestration-patterns.md`가 명시적으로 금지하는 오케스트레이션 안티패턴이다 ("personas do not invoke other personas").
- **서브에이전트 컨텍스트 내부에서 이 스킬을 적용하고 있다면**(Claude Code는 중첩된 서브에이전트 생성을 막는다): 선호되는 경로는 doubt-driven을 중첩해서 실행할 수 없음을 사용자에게 알리고 메인 세션이 처리하게 하는 것이다. 최후의 수단으로만, 성능이 저하된 자기 질문(self-questioning) 대체 방안이 있다. ARTIFACT + CONTRACT를 이전 추론과 분명한 정신적 구분선을 둔 새로운 자기 프롬프트로 다시 쓰고, Step 1–5를 거쳐 나아가라. 이것은 **새로운 컨텍스트 리뷰가 아니므로**(자신의 컨텍스트를 그대로 가지고 있다), 결과를 저하된 것으로 표시하고, 사용자와 연락이 닿는다면 항상 에스컬레이션을 선호하라.

## 프로세스

이 스킬을 적용할 때 이 체크리스트를 복사하라.

```
Doubt cycle:
- [ ] Step 1: CLAIM — 주장과 why-it-matters를 작성했다
- [ ] Step 2: EXTRACT — 추론을 제거하고 artifact와 contract를 분리했다
- [ ] Step 3: DOUBT — 적대적 프롬프트로 새로운 컨텍스트의 리뷰어를 호출했다
- [ ] Step 4: RECONCILE — 모든 발견 사항을 artifact 텍스트에 대조하여 분류했다
- [ ] Step 5: STOP — 중단 조건을 충족했다 (사소한 발견 사항, 3 사이클, 또는 사용자 오버라이드)
```

### Step 1: CLAIM — 무엇이 서 있는지 드러내라

결정을 두세 줄로 명명하라.

```
CLAIM: "새로운 캐싱 계층은 스펙에 기술된 읽기 위주
        워크로드에서 스레드 안전하다."
WHY THIS MATTERS: 여기서 경쟁 상태가 생기면 사용자 데이터가 손상되며
                  QA에서 탐지하기 어렵다.
```

주장을 이렇게 간결하게 쓸 수 없다면, 그것은 결정이 아니라 느낌(vibe)이다. 면밀히 따지기 전에 먼저 드러내라.

### Step 2: EXTRACT — 리뷰 가능한 가장 작은 단위

새로운 컨텍스트의 리뷰어에게 필요한 것은 과정이 아니라 **artifact**와 **contract**다.

- 코드: diff 또는 함수 — 파일 전체가 아니다
- 결정: 제안을 3–5문장으로, 그리고 그것이 충족해야 하는 제약 조건
- 주장(Assertion): 주장과 그것을 뒷받침한다고 여겨지는 증거(Step 1의 CLAIM 블록과는 별개로 유지하며, CLAIM 블록은 면밀히 검토받는 오케스트레이터의 가설이다)

당신의 추론을 제거하라. 결론을 넘기면 당신의 결론에 대한 확인만 돌아온다. 단위는 리뷰어가 한 번 읽고 머릿속에 담을 수 있을 만큼 작아야 한다 — 500줄짜리 PR이라면 먼저 분해하라.

### Step 3: DOUBT — 새로운 컨텍스트의 리뷰어를 호출하라

리뷰어의 프롬프트는 **반드시 적대적이어야 한다.** 프레이밍이 답을 결정한다.

```
적대적 리뷰. 이 artifact의 무엇이 잘못되었는지 찾아라.
작성자가 과신하고 있다고 가정하라. 다음을 찾아라:
- 명시되지 않은 가정
- 처리되지 않은 엣지 케이스
- 숨겨진 결합 또는 공유 상태
- contract가 위반될 수 있는 방식
- 이것이 깨뜨릴 수 있는 기존 컨벤션
- 예상치 못한 입력에서의 실패 모드

검증하지 마라. 요약하지 마라. 문제를 찾거나, 철저히 검토한 뒤에도
찾을 수 없다고 명시적으로 밝혀라.

ARTIFACT: <artifact를 붙여넣기>
CONTRACT: <contract를 붙여넣기>
```

**ARTIFACT + CONTRACT만 전달하라. CLAIM은 절대 전달하지 마라.** 리뷰어에게 당신의 결론을 건네면 동의하는 쪽으로 편향된다. 리뷰어는 artifact가 contract를 충족하는지 독립적으로 판단해야 한다.

Claude Code에서 `agents/`의 역할 기반 리뷰어는 설계상 격리된 컨텍스트로 시작하므로 여기서 사용할 수 있다 — 명단과 도메인별 대응은 `agents/`를 참고하라.

**위의 적대적 프롬프트는 페르소나의 기본 응답 형식보다 우선한다.** `code-reviewer` 같은 페르소나는 강점과 약점을 모두 담은 균형 잡힌 판정을 내놓도록 작성되어 있지만, doubt-driven에는 문제만 나열한 출력이 필요하다. 적대적 프롬프트를 호출에 그대로(verbatim) 붙여넣어 페르소나의 기본값을 덮어쓰게 하라. 페르소나의 응답 형식을 깔끔하게 덮어쓸 수 없다면, 적대적 프롬프트를 사용한 일반 서브에이전트로 대체하라.

#### 교차 모델 에스컬레이션(Cross-model escalation)

단일 모델 리뷰어는 원래 작성자와 사각지대를 공유한다 — 더 차갑고 아키텍처가 다른 모델이 그것을 잡아낸다. Doubt-driven은 이미 중요한 결정에 한해 옵트인이므로, 그 범위 안에서 교차 모델(cross-model)을 제안하는 것은 선택적인 마찰이 아니라 이 스킬의 가치의 일부다.

**대화형 세션: 항상 제안하라. 조용히 건너뛰지 마라.**

**Step 1: 사용자에게 물어라**

위 Step 3의 단일 모델 리뷰가 끝난 뒤, RECONCILE 전에 멈추고 물어라.

> *"단일 모델 리뷰가 완료되었습니다. 교차 모델 세컨드 오피니언을 받으시겠습니까? 옵션: Gemini CLI, Codex CLI, 수동 외부 리뷰(다른 곳에 직접 붙여넣기), 또는 건너뛰기."*

이 질문은 모든 대화형 doubt 사이클에서 필수이며, 위험도가 낮아 보이는 artifact라도 마찬가지다. 비용을 감수할 가치가 있는지는 에이전트가 아니라 사용자가 결정한다. 에이전트의 역할은 선택지를 드러내는 것이다.

**Step 2: 사용자가 CLI를 고르면 — 확인한 다음 호출하라**

1. 도구가 PATH에 있는지 확인한다(`which gemini`, `which codex`).
2. 전체 프롬프트를 넘기기 전에 동작하는지 테스트한다(`gemini --version` 또는 이에 준하는 명령). 오래되었거나 망가진 바이너리는 `which`는 통과해도 실제 입력에서는 실패할 수 있다.
3. 필요한 플래그, 인증, 환경 변수(예: API 키)를 포함해 정확한 호출 방식을 사용자와 확인한다. 구현은 제각각이므로 절대 가정하지 마라.
4. ARTIFACT + CONTRACT + 적대적 프롬프트**만** 전달한다. 세션 컨텍스트도, CLAIM도 전달하지 않는다.
5. 셸 이스케이프에 주의하라. artifact에 따옴표, `$(...)`, 백틱이 들어 있다면 인라인 `-p "…"`보다 stdin(`echo … | gemini`)이나 heredoc을 선호하라. 확실하지 않으면 실행하기 전에 사용자에게 호출 방식을 확인해 달라고 요청하라.
6. 출력을 Step 4(RECONCILE)로 가져간다.

**artifact를 셸 따옴표로 감싼 인자에 절대 끼워 넣지 마라.** 코드, 마크다운, 리뷰 프롬프트에는 백틱, `$(...)`, 따옴표 문자가 흔히 들어 있어서 프롬프트가 잘리거나 내장된 셸이 실행된다. 전체 프롬프트를 파일에 쓰고 stdin으로 파이프하라.

예시 형태(설치된 도구에 맞춰 플래그를 확인하라 — 구현과 버전마다 문법이 다르다):

```bash
# Write the adversarial prompt + ARTIFACT + CONTRACT to a temp file first.
# Then pipe via stdin so shell metacharacters in the artifact stay inert.

# Codex (read-only sandbox keeps the CLI from writing to your workspace):
codex exec --sandbox read-only -C <repo-path> - < /tmp/doubt-prompt.md

# Gemini ('--approval-mode plan' is read-only; '-p ""' triggers non-interactive
# mode and the prompt is read from stdin):
gemini --approval-mode plan -p "" < /tmp/doubt-prompt.md
```

읽기 전용 샌드박스가 핵심이다. doubt artifact 자체가 지시(의도적이든 우발적이든 프롬프트 인젝션)를 담고 있을 수 있고, 교차 모델 CLI가 그렇지 않았다면 그것을 당신의 워크스페이스에 대해 실행할 수 있기 때문이다.

**Step 3: CLI를 사용할 수 없거나 실패하면**

실패를 명시적으로 알려라. 수동 실행, 다른 도구 시도, 또는 건너뛰기를 제안하라. 조용히 단일 모델로 대체하지 마라 — 사용자는 교차 모델이 수행되지 않았음을 알아야 한다.

**Step 4: 사용자가 건너뛰면**

출력에 건너뛰었음을 명시하고(*"단일 모델 발견 사항만으로 진행합니다"*) RECONCILE로 계속하라. 건너뛰는 것은 괜찮지만, 조용히 건너뛰는 것은 안 된다.

**비대화형 컨텍스트**(CI, `/loop`, autonomous-loop, 예약 실행):

- 교차 모델은 **건너뛰며**, 건너뛰었음을 출력에 **알려야 한다**: *"Cross-model skipped: non-interactive context."*
- **명시적인 사용자 승인 없이는 외부 CLI를 절대 호출하지 마라** — 이것은 핵심적인 안전 속성이다.

교차 모델은 비용, 지연 시간, 도구의 취약성을 더한다. 에이전트는 매 사이클마다 선택지를 드러내고, 이 artifact가 그럴 만한 가치가 있는지는 사용자가 결정한다.

### Step 4: RECONCILE — 발견 사항을 되돌려 반영하라

리뷰어의 출력은 판정이 아니라 데이터다. **여전히 당신이 오케스트레이터다.** 분류하기 전에 각 발견 사항에 대해 artifact 텍스트를 다시 읽어라 — 리뷰어를 무조건 승인하는 것은 무시하는 것과 같은 실패 모드다.

각 발견 사항을 다음 **우선순위 순서**로 분류하라(처음 일치하는 분류가 이긴다).

1. **Contract 오독(Contract misread)** — 당신이 제공한 CONTRACT가 불명확하거나 불완전했기 때문에 리뷰어가 특정 사항을 지적했다. contract를 먼저 고치고, 다음 사이클에서 다시 분류하라.
2. **유효 + 조치 가능(Valid + actionable)** — artifact의 변경이 필요한 실제 문제. 변경하고 다시 루프를 돈다.
3. **유효한 트레이드오프(Valid trade-off)** — 문제는 실제이지만 고치는 비용이 감수하는 비용을 넘는다. 사용자가 볼 수 있도록 트레이드오프를 명시적으로 문서화하라.
4. **노이즈(Noise)** — 리뷰어가 갖지 못한 컨텍스트에서는 사실 올바른 것을 리뷰어가 지적했다. 기록하고 넘어가되, 그 컨텍스트를 contract에 추가했다면 잘못된 지적을 막을 수 있었는지 자문하라.

새로운 리뷰어는 컨텍스트가 없기 때문에 틀릴 수 있다. "새롭다"는 이유만으로 따르지 마라.

### Step 5: STOP — 재귀가 아니라 제한된 루프

다음의 경우 멈춰라.

- 다음 반복이 사소하거나 이미 고려된 발견 사항만 반환하는 경우, **또는**
- 3 사이클이 완료된 경우(혼자서 네 번째를 갈지 말고 사용자에게 에스컬레이션하라), **또는**
- 사용자가 명시적으로 "ship it"이라고 말한 경우

3 사이클 후에도 리뷰어가 여전히 실질적인 문제를 드러낸다면, artifact가 준비되지 않았을 수 있다. 이를 사용자에게 알려라 — 해결되지 않은 세 사이클은 artifact에 대한 정보이지 계속 루프를 돌 이유가 아니다.

artifact가 커서 3 사이클이 "명백히 부족하다"면, artifact가 너무 큰 것이다 — Step 2로 돌아가 분해하라. 제한을 풀지 마라.

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "나는 확신한다, doubt 단계는 건너뛰자" | 새로운 문제에서 확신은 정확성과 상관관계가 낮다. 확신이 드는 순간이야말로 사각지대가 숨어 있는 때다. |
| "리뷰어를 생성하는 것은 비싸다" | 프로덕션에서 잘못된 커밋을 디버깅하는 것이 더 비싸다. 검사는 한계가 있지만 버그는 그렇지 않다. |
| "리뷰어는 그냥 트집만 잡을 것이다" | 범위를 정하지 않았을 때만 그렇다. 프롬프트를 "contract 하에서 이것을 실패하게 만들 문제"로 제한하라. |
| "마지막에 `/review`로 doubt를 하겠다" | `/review`는 최종 게이트다. Doubt-driven은 방향 수정이 저렴한 초기에 잘못된 방향을 잡아낸다. PR 시점에는 너무 늦다. |
| "모든 단계를 의심하면 절대 배포하지 못한다" | 이 스킬은 모든 키 입력이 아니라 중요한 결정에 적용된다. "When NOT to Use"를 다시 읽어라. |
| "두 의견이 한 의견보다 항상 낫다" | 두 번째가 컨텍스트가 적고 노이즈를 만들어 낸다면 그렇지 않다. 따르지 말고 조정(reconcile)하라. |
| "리뷰어가 반대했으니 내가 틀렸다" | 리뷰어에게는 당신의 컨텍스트가 없다 — 반대는 판정이 아니라 정보다. artifact를 다시 읽고, 분류하고, 그다음에 결정하라. |
| "교차 모델이 항상 더 낫다" | 교차 모델은 단일 모델이 스스로와 공유하는 사각지대를 잡아내지만, 비용과 도구의 취약성을 더한다. 매 대화형 doubt 사이클마다 제안하라 — artifact가 그럴 만한지는 사용자가 결정한다. 에이전트의 역할은 선택지를 드러내는 것이지, 그것을 가로막는 것이 아니다. |
| "사용자가 한 번 승인했으니 계속 CLI를 호출해도 된다" | 각 호출은 별개의 승인이다. 호출마다 artifact, 프롬프트, 플래그가 바뀌므로 — 매번 실행 전에 정확한 명령을 사용자와 다시 확인하라. |

## 위험 신호(Red Flags)

- 한 줄짜리 이름 변경이나 포매팅 변경을 위해 새로운 컨텍스트의 리뷰어를 생성하는 것
- artifact 텍스트를 다시 읽지 않고 리뷰어의 출력을 권위 있는 것으로 취급하는 것
- 사용자에게 에스컬레이션하지 않고 3 사이클을 초과해 루프를 도는 것
- 리뷰어에게 "find issues" 대신 "is this good?"라고 프롬프트하는 것
- 위험이 큰 결정에서 시간 압박 때문에 doubt를 건너뛰는 것
- 변경되지 않은 artifact에 대해 새로운 컨텍스트를 다시 생성하는 것(같은 발견 사항을 얻게 된다. 시간을 끌고 있는 것이다)
- **Doubt theater (확인 가능한 신호)**: 리뷰어가 실질적인 발견 사항을 낸 2 사이클 이상에 걸쳐, 조치 가능(actionable)으로 분류된 발견 사항이 하나도 없다. 당신은 의심이 아니라 승인을 하고 있다. 멈추고 에스컬레이션하라.
- 커밋한 후에야 의심하는 것 — 그것은 doubt-driven development가 아니라 `/review`다
- 도구가 존재하고, 설정되어 있고, 그 정확한 문법을 받아들이는지 사용자와 확인하지 않은 채 외부 CLI 호출을 하드코딩하는 것
- **대화형 doubt 사이클에서 교차 모델을 조용히 건너뛰는 것.** 추천하지 않더라도 제안은 눈에 보여야 한다. 건너뛰는 것은 괜찮지만, 조용히 건너뛰는 것은 안 된다.
- 외부 CLI가 오류를 내거나 없을 때 조용히 대체하는 것 — 실패를 알리고 사용자가 방향을 바꾸게 하라
- 리뷰어의 입력에서 contract를 제거하는 것
- 리뷰어에게 CLAIM을 전달하는 것(동의하는 쪽으로 편향시킨다)

## 다른 스킬과의 상호작용

- **`code-review-and-quality` / `/review`**: 상호 보완적. `/review`는 사후 PR 판정이고, doubt-driven은 진행 중 결정별이다. 둘 다 사용하라.
- **`source-driven-development`**: SDD는 프레임워크에 대한 *사실*을 공식 문서와 대조해 검증한다. Doubt-driven은 artifact에 대한 *당신의 추론*을 검증한다. SDD는 API가 존재하는지 확인하고, doubt-driven은 contract 하에서 그것을 올바르게 사용했는지 확인한다.
- **`test-driven-development`**: TDD의 RED 단계는 구체화된 doubt다 — 실패하는 테스트는 반증 시도다. TDD가 적용될 때, 그 실패하는 테스트가 행동에 대한 주장의 doubt 단계 *그 자체*다.
- **`debugging-and-error-recovery`**: 리뷰어가 실제 실패 모드를 드러내면 디버깅 스킬로 넘어가 위치를 특정하고 고쳐라.
- **저장소 오케스트레이션 규칙** (`../../references/orchestration-patterns.md`): 이 스킬은 메인 세션에서 오케스트레이션한다. 페르소나가 다른 페르소나를 호출하는 것은 안티패턴 B다 — 위의 Loading Constraints를 참고하라.

## 검증

doubt-driven development를 적용한 후:

- [ ] 모든 중요한 결정(위의 정의에 따른)이 확정되기 전에 CLAIM으로 명시적으로 명명되었다
- [ ] 중요한 artifact마다 새로운 컨텍스트 리뷰가 최소 한 번 있었다 (TDD의 RED 단계가 만든 실패하는 테스트는, Interaction with Other Skills에 따라 행동에 대한 주장에 대해 이를 충족한다)
- [ ] 리뷰어가 ARTIFACT + CONTRACT를 받았다 — CLAIM도, 당신의 추론도 아니다
- [ ] 리뷰어의 프롬프트가 적대적("find issues")이었고, 검증하는("is it good") 것이 아니었다
- [ ] 발견 사항이 artifact 텍스트에 대조하여 분류되었고(무조건 승인하지 않았고), 우선순위는 contract 오독 / 조치 가능 / 트레이드오프 / 노이즈였다
- [ ] 중단 조건이 충족되었다 (사소한 발견 사항, 3 사이클, 또는 사용자 오버라이드)
- [ ] 대화형 모드에서 교차 모델이 사용자에게 **명시적으로 제안**되었고(artifact의 위험도와 무관하게) 그 응답이 출력에 기록되었다
- [ ] 비대화형 모드에서 교차 모델을 건너뛰었고 건너뛰었음을 알렸다
- [ ] 모든 외부 CLI 호출에 앞서 PATH 확인, 동작하는 바이너리 테스트, 사용자와의 문법 확인, 실행에 대한 명시적 승인이 있었다
