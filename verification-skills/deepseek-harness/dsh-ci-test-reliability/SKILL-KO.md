# 신뢰할 수 있는 DSH CI 테스트

한가한 워크스테이션에서 혼자 실행할 때만이 아니라, 저장소의 실제 CI 토폴로지에서도 올바르게 유지되는 테스트를 만들어라. 이 스킬은 격리와 신뢰성에 관한 결정을 소유하며, 저장소의 테스트 계층 정책을 대체하거나 push를 위한 모든 명령을 선택하지는 않는다.

## 소유 규칙 읽기

- 단위, 커버리지, 기대 출력, 스냅샷, 브라우저, 실제 API 증거를 선택할 때는 [테스트 정책](../../../docs/testing.md)을 사용한다.
- 라이프사이클, 서브프로세스, 취소, 정리 동작에는 [방어 패턴](../../../docs/defensive-patterns.md)을 사용한다.
- worker 또는 job 토폴로지가 테스트에 영향을 줄 때는 활성 Vitest 구성과 GitHub 워크플로를 읽는다.
- 기록된 세션 시나리오에는 [스냅샷 지침](../../../snapshots/AGENTS.md)도 따른다.
- 테스트 설계가 견고해진 후 나가는 검증을 선택할 때는 [dsh-pre-push-checks](../dsh-pre-push-checks/SKILL-KO.md)를 사용한다.

## 실행 토폴로지 모델링하기

활성 구성이 달리 증명하지 않는 한, 다음 레이어들이 겹칠 수 있다고 가정하라.

1. 하나의 Vitest 파일 안의 테스트들.
2. 별도의 Vitest 파일 또는 worker 프로세스.
3. 한 job 안의 독립된 Vitest 또는 저장소 게이트 프로세스.
4. 러너가 하나의 호스트를 공유하는 서로 다른 Actions job.

프로세스 격리는 호스트 포트, 예측 가능한 파일시스템 경로, 외부 서비스, 데이터베이스, 소켓, 상속된 자식 프로세스를 격리하지 않는다. 획득하는 모든 리소스마다 소유자, 원자적 할당 메커니즘, 관찰 가능한 준비 신호, 등록된 정리, 정지 상태 완료 신호를 식별하라.

한 픽스처에 격리가 없다는 이유만으로 스위트 전체를 직렬화하지 마라. 먼저 배타적 범위를 좁히거나 리소스 할당을 바꿔라. 순차 Vitest 블록은 다른 파일, 프로세스, job, 러너로부터 호스트 리소스를 보호할 수 없다.

## 리소스를 원자적으로 할당하기

가용성을 확인한 뒤 나중에 점유하는 대신 리소스 소유자의 할당자를 사용하라.

- 네트워크 픽스처는 `listen(0)`으로 loopback에 바인드하고, 서버가 listening 중이라고 보고한 뒤에만 할당된 주소를 읽는다. 빈 포트를 스캔한 뒤 나중에 바인드하지 마라.
- 테스트별 비공개 임시 루트는 `mkdtemp`로 만든다. 예측 가능한 공유 경로를 획득하지 마라.
- 공유 데이터베이스, 소켓, 세션, 출력 위치에는 테스트별 고유 네임스페이스를 부여한다.
- 경로가 이미 존재하면 안 되는 곳에서는 배타적 생성을 사용한다.
- 안정적인 기록된 식별자를 일시적인 전송 주소와 분리해 둔다. 라이브 리소스가 기록된 값을 쓰도록 강제하는 대신 픽스처 안에서 변환하라.

파서 입력이나 기대값으로만 쓰이는 리터럴 경로와 URL은 획득된 리소스가 아니다. 고정된 것처럼 보인다는 이유만으로 다시 쓰지 마라.

## 프로세스 전역 상태 격리하기

`process.env`, `cwd`, 가짜 타이머, 로캘과 시간대, 모듈 목, 레지스트리, 콘솔 훅, `globalThis`, 전역 `fetch` 가로채기를 배타적 가변 리소스로 취급하라.

주입된 의존성이나 인스턴스 로컬 어댑터를 선호하라. 변경이 필요할 때는:

- 원래 값이 없었는지 있었는지 기록한다.
- 정확히 그 상태를 복원한다.
- 복원을 즉시 등록한다.
- 가장 작은 변경 범위를 `try/finally`로 감싼다.
- 로컬 `finally` 이전에 실패할 가능성이 있으면 `afterEach` 폴백을 유지한다.
- 픽스처가 소유한 가장 좁고 정확한 요청 또는 호출만 가로챈다.

## 플랫폼이 소유한 의미론 존중하기

CI는 같은 스위트를 Windows와 POSIX 호스트에서 실행하며, 운영체제가 소유한 값은 테스트가 쓴 그대로 돌아오지 않을 수 있다.

- 값을 다시 쓰는 것은 write-back 실패를 assertion이 허용할 때만 안전하다. 핑거프린트가 어떻게든 무효화됨을 증명하려고 파일의 `mtime`을 복원하는 것은 어디서나 성립한다. 레코드가 유효하게 유지됨을 증명하려고 복원하는 것은 무손실 왕복을 가정하는데, NTFS의 100나노초 틱은 소수 밀리초에 대해 이를 보장하지 않는다. assertion이 복원에 의존할 때는 기억해 둔 값이 아니라 새로 읽은 값에서 기대값을 가져와라.
- Windows는 환경 변수 이름을 대소문자 구분 없이 매칭하므로, `http_proxy`와 `HTTP_PROXY`를 별개 키로 시드하는 픽스처는 그곳에서 하나의 항목만 갖게 된다.
- Windows는 파일 핸들을 비동기로 해제하므로, POSIX 호스트에서는 즉시 끝나는 rename이나 삭제도 관찰된 경합에 맞춘 크기의 제한된 재시도가 필요하다.
- Windows에는 POSIX 권한이나 시그널 의미론이 없다. 그에 의존하는 케이스는 모든 곳에서 assertion을 약화하는 대신, 이유를 명시한 명시적 플랫폼 skip을 사용한다.

모든 플랫폼에서 성립하는 관찰을 선호하라. 케이스가 정말로 그럴 수 없을 때는 해당 플랫폼에서 명시적으로 제외하라.

## 레인에 맞춰 타임아웃 예산 잡기

`describe` 또는 케이스 타임아웃은 러너의 `--testTimeout`에 양보하지 않고 그것을 덮어쓰므로, 레인의 예산보다 낮은 값은 CI가 이미 부여한 것을 낮춘다. 그리고 기본값이 더 작은 호스트에서는 같은 리터럴이 확장처럼 읽힌다. 프로세스 생성에 묶인 스위트는 레인 예산을 따른다. 더 빡빡한 값에는 더 빡빡한 이유를 함께 적는다.

훅 예산은 테스트 예산과 함께 올려라. 설정과 정리도 같은 경합을 겪으므로, 케이스 예산만 올리면 경합으로 인한 실패가 `afterEach`로 옮겨간다.

타임아웃 자체가 대상일 때는 바깥 대기를 테스트 중인 타임아웃보다 훨씬 크게 유지하라. 20 ms 데드라인이 발동함을 증명하는 케이스가 하네스 자체의 대기와 경쟁해서는 안 되며, 그러지 않으면 부하가 어느 데드라인이 먼저 보고되는지를 결정한다.

## 상태에 동기화하기

고정된 sleep은 설정이 완료되었거나 정리가 안정되었다는 증거가 아니다.

- 명시적인 준비 이벤트, 핸드셰이크, 상태 전이, 소유한 promise, 또는 외부에서 관찰 가능한 조건을 기다린다.
- 지연된 promise나 배리어를 사용해 경쟁을 결정적인 지점에 두고 관련 작업이 겹침을 증명한다.
- 타임아웃은 대기를 제한하는 용도로만 사용하고, assertion을 올바르게 만드는 조건으로는 절대 사용하지 않는다.
- 그 순서가 테스트 대상 제품 동작이 아닌 한, 스케줄러에 의존하는 순서를 assertion하지 않는다.
- 시간 자체가 대상일 때는 시계를 주입하거나 가짜로 만들고, 실제 타이머는 항상 복원한다.

## 정지 상태까지 정리하기

획득 직후 정리를 등록해 assertion 실패 시에도 리소스가 해제되게 하라. 정리는 새 콜백이나 요청을 중단하고, 리스너를 분리하고, 전역 훅을 복원하고, 소유한 작업을 종료하며, 자식 종료, 서버 close, worker 종료 또는 그에 상응하는 완료 신호를 await한다.

소유한 완료 신호를 await하지 않고 `abort()`, `close()`, `kill()`을 호출하는 것은 불완전한 정리다. 늦은 완료가 가능할 때는, 정리가 그것이 다른 테스트를 변경하지 못하게 막음을 증명하라.

## 의도한 회귀 증명하기

- 가능하면 일반적인 회귀가 수정 전에 실패하는 것을 관찰한다.
- 새로운 정적 또는 코퍼스 가드의 경우, 거부해야 할 케이스를 임시로 넣고 의도한 실패를 관찰한다.
- 경쟁의 경우 배리어로 겹침을 증명한다. 반복 실행만으로는 경쟁 테스트가 아니다.
- 포트, 소켓, 공유 경로, 서브프로세스 또는 기타 호스트 리소스의 경우, 프로세스 간 격리가 수정의 일부라면 독립된 테스트 프로세스를 동시에 실행한다.
- 픽스처가 자체 데드라인으로 spawn할 때는, 종료 상태를 assertion하기 전에 어떤 시그널이나 타임아웃도 자식을 끝내지 않았음을 assertion하라. 그러면 kill된 자식이 상태 불일치가 아니라 타임아웃으로 보고된다.
- 컴포넌트의 자체 보고를 신뢰하지 말고 외부 상태, 이벤트, 파일, 로그, 종료, 정리를 검증한다.

스트레스 실행은 결정적 회귀를 보완할 뿐 대체하지 않는다.

## 플레이키 은폐 수정 거부하기

결정적인 로컬 테스트에 대한 근본 원인 수정으로 다음을 제시하지 마라.

- 기다리는 상태를 식별하지 않고 타임아웃을 늘리는 것;
- 재시도를 추가하는 것;
- 모든 파일을 직렬로 만드는 것;
- 오류나 처리되지 않은 rejection을 삼키는 것;
- assertion을 약화하는 것;
- 불안정한 동작을 정규화로 없애는 것;
- 정리나 assertion 전에 sleep을 추가하는 것.

재시도는 실제 API 정책 아래의 문서화된 일시적 외부 프로바이더 테스트에서는 여전히 유효하다. 그 예외를 외부 경계에 한정하라.

예산을 복원하는 것은 은폐가 아니다. 스위트를 이미 가지고 있던 레인 예산으로 되돌리거나, 러너에서 실제로 측정된 경합에 맞춰 제한된 재시도의 크기를 정하는 것은 기다리는 작업을 명명하고 레인이 부여한 것을 되돌려 놓는다. 어느 쪽도 검토되지 않은 대기 주변에 여유를 만들어내지 않는다.

## 기존 플레이키 진단하기

기존의 확률적 CI 실패에는 [CI 플레이키 진단 워크플로](references/ci-flake-diagnosis-KO.md)를 읽어라. 진단만 요청한 경우는 계속 읽기 전용이다. 사용자가 수정도 요청하지 않는 한 원인과 증거를 보고하라.

## 검증하고 보고하기

영향받는 동작에 대해 가장 작고 집중된 회귀를 실행하라. 변경이 그 위험을 소유할 때만 토폴로지별 증거를 추가하라.

- 전역 변경에는 복원 증거가 필요하다;
- 라이프사이클 또는 서브프로세스 작업에는 정지 상태 정리 증거가 필요하다;
- 포트, 소켓, 공유 경로에는 동시 독립 프로세스 증거가 필요하다;
- 새 가드에는 음성 대조군(negative control)이 필요하다.

push 전에는 [dsh-pre-push-checks](../dsh-pre-push-checks/SKILL-KO.md)를 사용하라. 정확한 명령과 관찰된 결과를 보고하라. 재시도, skip된 테스트, 보류 중인 CI를 통과한 것으로 설명하지 마라.
