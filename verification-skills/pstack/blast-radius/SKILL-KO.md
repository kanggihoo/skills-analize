# Blast radius

변경이 배포되기 전에 다른 곳에서 무엇을 깨뜨리는지 찾아라. "blast radius of X", "what could this break", 또는 아직 신뢰하지 못하는 작은 diff를 리뷰할 때 사용한다.

`how`, `why`의 짝이다. `how`는 코드가 무엇을 하는지 알려 준다. `why`는 코드가 왜 그런 모양인지 알려 준다. 영향 반경(blast radius)은 그것이 다른 곳에서 무엇을 깨뜨리는지 알려 준다.

호출자를 나열하는 것은 일이 아니다. 에이전트는 그것을 1초 만에 grep할 수 있다. 일은 grep이 보여 주지 않는 깨짐을 찾는 것이다.

## 자신의 작성 내용을 믿지 마라

그럴듯하게 들리는 영향 반경 작성물은 가치가 없다. 사실이든 아니든 설득력 있게 읽히기 때문이다. 그러니 작성물을 돌려주지 마라. 전체가 의존하는 한두 가지 사실을 찾아 코드를 실행해 증명하라.

### 얼마나 확신하는가

변경의 안전성이 의존하는 각 사실마다, 비용이 적게 드는 선에서 이 목록의 가능한 한 아래 단계까지 끌어올리고, 어디서 멈췄는지 밝힌다.

1. 당신이 그렇다고 말했다. 그것만으로는 가치가 없다.
2. 당신이 해당 줄을 가리켰다. 실제 `file:line` 또는 라이브러리 자체의 소스.
3. 나쁜 경우가 일어날 수 없음을 보였다. 실패 경로를 단계별로 따라가 봤고 그곳에 이르지 않는다.
4. 실행해 봤다. 실제 코드를 호출하고, 당신이 틀렸다면 큰 소리로 실패하는 스크립트나 테스트.
5. 실행 중인 앱에서 재현했다.

4단계는 보통 앱이 배포하는 것과 같은 라이브러리를 import해서 걱정되는 바로 그 함수를 호출하는 작은 스크립트 하나로 충분하다.

## 단계

1. 변경을 읽는다. diff, 그것이 추가, 변경, 삭제하는 심볼, 그리고 diff가 명시하지 않는 부분을 포함해 이제 무엇이 다르게 동작하는지. `why`의 2단계를 사용해 PR과 커밋을 가져온다.
2. 변경이 안전한 이유가 되는 단 하나의 사실을 찾는다. 위험해 보이는 대부분의 변경은 "이 호출은 이미 죽은 캐시 항목만 버리고 다른 일은 하지 않는다" 같은 단 하나의 사실 때문에 안전하다. 그 사실을 찾아라. 그것이 성립하면 위험한 경우 대부분이 한꺼번에 해소된다. 시간은 "어쩌면"의 긴 목록이 아니라 여기에 써라.
3. grep이 멈추는 곳을 살핀다. 호출하는 라이브러리의 소스를 읽고, 고정된 버전과 로컬 패치를 확인한다. 언제 실행되는지 파악한다. 마이크로태스크, 언마운트와 teardown, Solid 대 React. 심볼 검색이 놓치는 것을 따라간다. API가 반환하는 JSON, DB 컬럼, 와이어 포맷, 같은 바이트를 읽는 다른 언어, 기능 플래그, 세 단계 아래 다운스트림의 코드.
4. 각 위험에 대해 솔직해진다. 실제로 일어날 가능성과 일어났을 때의 실제 비용을 적는다. 확인된 위험은 유지한다. 확인해서 해소된 것은 따로 나열한다. `why`와 같은 규칙이다. 실제 `file:line`을 인용하고, 아무것도 찾지 못한 검색도 여전히 답이며, 호출자나 API를 절대 지어내지 마라.
5. 그 단 하나의 사실을 증명한다. 실제 코드를 실행하는 스크립트나 테스트를 작성하고, 실행하고, 무슨 일이 일어났는지 붙여 넣는다.
6. 크거나 광범위한 변경이라면 `arena`로 실행한다. 여러 모델에 같은 질문을 하고 답을 병합한다. 모델마다 잡아내는 실제 버그가 다르다.

## 돌려줄 것

- **무엇을 하는가.** 명백하지 않은 부분을 포함해 무엇이 바뀌었는지.
- **안전한 이유가 되는 단 하나의 사실.** 그것을 서술하고, 몇 단계까지 끌어올렸는지 밝히고, 증명을 보인다. 증명하지 못했다면 unproven이라고 적는다.
- **위험.** 각각 어떻게 깨지는지, `file:line`, 가능성과 심각도, 확인 방법을 적는다. 중요한 것들은 증명을 붙여 넣는다.
- **해소됨.** 무엇을 확인했고 왜 괜찮은지.
- **머지하기 전에.** 당신이 작성한 스크립트를 포함해, 실제 버그를 잡아내는 가장 저렴한 테스트나 재현 방법.

`unslop`을 거쳐 작성하고, 실제 코드를 인용하며, 공개된 곳에 나가기 전에 비공개 내용은 모두 제거한다.

**Reply:** 위의 작성물. 단 하나의 안전성 사실은 증명되었거나 unproven으로 표시되어야 한다.
