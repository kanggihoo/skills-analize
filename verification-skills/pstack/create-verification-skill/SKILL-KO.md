# Create a verification 스킬

진지한 프로젝트라면 모두 실제 앱을 구동하고 동작을 증명하는 스크립트화된 방법이 필요하다. 앱을 실행하고, 사용자가 하듯이 기능을 사용해 보고, 증거를 캡처하는 것이다. 이 스킬은 그것을 저장소에 맞춘 프로젝트 로컬 스킬(`.cursor/skills/verify-<app>/`)로 생성한다. 생성기의 출력은 사람이 아니라 다음 에이전트를 위해 쓴다. 앱을 본 적 없는 에이전트가 작업 도중에 아무 맥락 없이 읽게 된다.

## 1. 사용자가 아니라 저장소를 인터뷰하라

이 질문들은 코드베이스에서 답을 찾고, 관찰할 수 없는 것만 사용자에게 물어라.

- **Surface(표면):** 사용자가 실제로 무엇을 만지는가? 웹 UI, CLI/TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리? 저장소에는 여러 개가 있을 수 있다. 주된 것 하나를 고르고 나머지는 기록해 둔다.
- **Run(실행):** 앱은 로컬에서 어떻게 시작되는가? 저장소 자체의 문서화된 dev 명령(package scripts, Makefile, README 퀵스타트)을 선호한다. 포트, 환경 변수, 시드 데이터, 인증을 기록한다.
- **Drive(구동):** 에이전트가 프로그램적으로 앱과 어떻게 상호작용할 수 있는가? 기존 하네스를 먼저 본다. Playwright/Cypress 스펙, expect 스크립트, PTY 헬퍼, curl로 호출 가능한 엔드포인트, 디버그 포트. 그런 다음에야 범용 레시피를 고른다. 웹과 Electron에는 browser/CDP, CLI/TUI에는 tmux/PTY 하네스, 서비스에는 순수 HTTP.
- **Observe(관찰):** 어떤 증거를 캡처할 수 있는가? 스크린샷, 터미널 트랜스크립트, 응답 본문, 로그, 종료 코드, DB 상태.
- **Isolate(격리):** 두 인스턴스를 나란히 실행할 수 있는가(포트, 데이터 디렉터리, 프로필)? 그렇지 않다면 생성되는 스킬에 그렇게 명시하라. 공유 인스턴스를 이중으로 구동하기를 거부하는 편이 사용자의 세션을 망가뜨리는 것보다 낫다.

체크아웃이 있는 그대로 빌드되거나 시작되지 않는다면, 생성하기 전에 먼저 그것을 고치거나(또는 정확히 보고하라). 망가진 기반 위에서 작성한 스킬은 틀린 단계를 가르친다. 관련 없는 누락된 자산이 시작을 막는 경우(API가 절대 서빙하지 않는 정적 디렉터리, 샘플 설정)에는 생성되는 스킬이 그것을 만들 수 있으나, 검증용 비계(scaffolding)임을 분명히 표시하고 정리 단계에서 제거한다.

## 2. 스킬 생성

`.cursor/skills/verify-<app>/SKILL.md`를 YAML frontmatter(`name: verify-<app>`과, 앱, 표면, 언제 이를 찾아야 하는지를 명시하는 `description`. frontmatter가 없으면 스킬은 등록되지 않는다)와 다음 섹션들로 작성한다. 각 섹션은 인터뷰에서 실제로 알아낸 내용에 근거해야 한다(플레이스홀더를 남기지 마라).

- **Launch:** 검증을 위해 앱을 시작하는 정확한 명령과, 준비되었음을 아는 방법(로그 줄, 응답하는 포트, 프롬프트). 종료(teardown)를 포함한다. 수명이 짧은 CLI나 TUI에는 유지할 서버가 없다. 그 경우 launch는 바이너리를 한 번 빌드하는 것(또는 의존성을 설치하는 것)을 뜻하고, 이후 각 구동은 자체 격리된 PTY 또는 tmux 세션에서 시작한다.
- **Doctor:** "이 인스턴스는 구동할 가치가 있는가?"에 답하는 읽기 전용 검사 하나. 프로세스가 떠 있는지, 올바른 버전/빌드인지, 포트를 우리가 소유하는지, 인증이 유효한지. 에이전트는 무언가 이상해 보일 때마다 이것을 가장 먼저 실행한다.
- **Drive:** 예시가 아니라 이 저장소의 실제 셀렉터/명령을 담은 하네스 레시피. 좌표와 탭 순서보다 안정적인 핸들(ARIA 레이블, data 속성, 프롬프트 문자열, 라우트 경로)을 선호한다.
- **Evidence:** 증명을 위해 무엇을 캡처하고 어디에 두는지. 증명 기준을 명시한다. 내부 setter나 테스트 전용 엔드포인트가 아니라 실제 사용자 경로를 사용한다. 최종 화면만이 아니라 동작과 그 결과 상태를 캡처한다. 눈에 보이는 것과 함께 부수 효과(기록된 파일, 삽입된 행, 전송된 메시지)를 검증한다. 목(mock)은 프로덕션 경계가 이미 외부 시스템을 격리하는 곳에서만 쓴다. 안전한 경로가 dry-run이나 테스트 모드일 때는 이름을 믿는 대신 관찰(파일, 네트워크, git ref)로 그것이 실제로 무엇을 건너뛰는지 검증한다. 어떤 dry-run은 여전히 네트워크를 건드리거나 브라우저를 연다.
- **Cleanup:** 실행이 만든 인스턴스를 정리하는 방법. 프로세스 이름으로 kill하지 마라. 당신이 시작한 것을 kill하라. 정리는 인스턴스와 임시 상태를 제거하지, 증거를 제거하지 않는다. 증명 산출물은 스킬이 명시한 위치에서 종료 후에도 남는다.
- **Helpers:** 스킬이 함께 제공하는 모든 스크립트는 실행 가능하며 그 호출 방법이 스킬 본문에 나와 있다. 읽는 쪽이 역설계해야 하는 헬퍼는 헬퍼가 아니다.

## 3. 기능 맵(feature map) 시드 만들기

`.cursor/skills/verify-<app>/features/README.md`와, 식별할 수 있는 사용자 대면 기능마다 파일 하나씩을 만든다(처음에는 라우트, 명령, 메뉴, 문서에서 상위 3-5개를 목표로 한다). [`references/feature-map-example/`](references/feature-map-example/)의 형태를 따르며, README 인덱스와 기능마다 파일 하나로 구성한다. 각 파일은 사용자 관점에서 다음에 답한다. 기능이 무엇인지, 어떻게 도달하는지, 하네스로 어떻게 구동하는지, 어떤 관찰 가능한 최종 상태가 그것이 동작함을 증명하는지. 네 개의 H2는 `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, `Gotchas`이다. 이 맵은 저장소가 유지하는 검증의 원천이다. 맵이 다른 진입점들을 나열하는데 편리한 진입점 하나만 구동한 증명은 불완전하다.

## 4. 생성된 스킬을 넘기기 전에 증명하라

그 스킬 자신의 지침을 처음부터 끝까지 한 번 실행한다. launch, doctor, 매핑된 기능 하나 구동(하나면 충분하다. 맵은 이후 실행이 나머지를 다루도록 존재한다), 증거 캡처, 정리. 정리 후, 증거가 명시된 위치에 여전히 존재하는지 확인한다. 증명을 지워 버리는 정리는 이 단계에서 실패한 것이다. 실패한 것을 고치고, 실패한 반복마다 생성된 정리도 실행해 망가진 시도가 프로세스와 포트를 남기지 않게 한다. 한 번도 실행되지 않은 생성된 스킬은 초안이지 산출물이 아니다.

## 5. 유지보수 루프 제안

앱이 변경되는 동안 맵을 정직하게 유지하기 위해 사용자에게 `/maintain-verification-skill`을 안내한다. 사용자가 묻는 경우에만 주기를 제안한다.
