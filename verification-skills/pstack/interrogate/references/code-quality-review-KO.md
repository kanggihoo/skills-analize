# 코드 품질 리뷰(Code Quality Review)

각 리뷰어는 루브릭에 더해 이 코드 품질 관점(lens)을 적용한다. 이는 구현 품질, 유지보수성, 추상화 품질, 코드베이스 건강에 초점을 맞춘 엄격한 기준이다.

무엇보다 코드 구조에 대해 야심차게 접근하라. 국소적인 정리만 찾아내는 데 그치지 마라. "code judo" 수, 즉 동작은 보존하면서 구현을 극적으로 더 단순하고, 더 작고, 더 직접적이고, 더 우아하게 만드는 재구성을 적극적으로 찾아라.

## 핵심 프롬프트(Core Prompt)

다음을 기준선으로 시작한다.

> 현재 브랜치의 변경 사항에 대해 심층적인 코드 품질 감사를 수행하라.
> 동작에 영향을 주지 않으면서 코드 품질을 의미 있게 개선할 수 있도록 변경 사항의 구조화/구현 방식을 다시 생각하라.
> 추상화와 모듈성을 개선하고, 스파게티 코드를 줄이며, 간결성과 가독성을 높이도록 작업하라.
> 야심차게 임하라. 코드베이스 일부를 재구성하는 것을 포함해 구현을 개선할 분명한 길이 있다면 그렇게 하라.
> 극도로 철저하고 엄밀하게 하라. 두 번 재고 한 번 잘라라.

## 평가 차원(Dimensions)

각 차원은 한 번씩만 서술한다. 관련 있는 것을 적용한다.

0. **구조적 단순화에 야심차게 임하라.** "이것은 조금 더 깔끔해질 수 있다"에서 멈추지 마라. 분기, 헬퍼, 모드, 조건문, 계층 전체를 사라지게 만드는 재해석을 찾아라. "code judo" 수가 가능한 경우가 많다고 가정하라. 그것은 기존 아키텍처를 더 효과적으로 활용하여 변경을 극적으로 단순하게 만든다. 복잡성을 재배치하는 대신 삭제할 수 있다면 강하게 밀어붙여라.

1. **PR이 매우 강력한 이유 없이 파일을 1k줄 미만에서 1k줄 초과로 만들지 못하게 하라.** 이를 강한 악취(smell)로 취급한다. 헬퍼, 하위 컴포넌트, 모듈로 추출하는 쪽을 선호한다. diff가 그 임계값을 넘으면 코드를 먼저 분해해야 하는지 물어라. 결과 파일이 명확하게 정리되어 있는 설득력 있는 구조적 이유가 있을 때만 면제한다.

2. **기존 코드에서 스파게티가 자라나는 것을 허용하지 마라.** 관련 없는 흐름에 끼워 넣은 새로운 임기응변식 조건문, 흩어진 특수 케이스, 일회성 분기를 의심하라. "엉뚱한 곳에 있는 이상한 if문"을 스타일 사소한 트집이 아니라 설계 문제로 취급한다. 기존 경로를 얽히게 하는 대신 로직을 전용 헬퍼, 상태 머신, 모듈로 옮기는 쪽을 선호한다.

3. **동작하는 코드를 그냥 받아들이기보다 설계를 정리하는 쪽으로 기울어라.** 동작은 그대로이면서 구조가 의미 있게 더 깔끔해질 수 있다면, 더 깔끔한 버전을 밀어붙여라. 같은 복잡성을 여기저기 퍼뜨리는 리팩터링보다 움직이는 부품을 제거하는 단순화를 선호한다.

4. **해키하거나 마법 같은 코드보다 직접적이고 평범하며 유지보수하기 쉬운 코드를 선호하라.** 취약하거나, 임기응변식이거나, "마법" 같은 동작을 문제로 취급한다. 단순한 데이터 형태 가정을 숨기는 범용 메커니즘을 회의적으로 보라. 명확성은 사지 못하고 간접 참조만 더하는 얇은 추상화, 항등 래퍼(identity wrapper), 단순 전달(pass-through) 헬퍼를 지적하라.

5. **유지보수성에 영향을 줄 때는 타입과 경계의 깔끔함을 밀어붙여라.** 더 명확한 타입 경계가 있을 수 있는데도 불필요한 optional, `unknown`, `any`, 캐스트 투성이 코드가 있다면 의문을 제기한다. 느슨한 형태의 임기응변 객체보다 명시적인 타입 모델을 선호한다. 분기가 불분명한 불변식(invariant)을 덮으려고 조용한 폴백에 기대고 있다면, 경계를 명시적으로 만들어야 하는지 물어라.

6. **로직은 표준(canonical) 계층에 두고 기존 헬퍼를 재사용하라.** 공유 경로로 새어 나간 기능 로직이나 API를 통해 새어 나온 구현 세부 사항을 지적하라. 맞춤형 일회성 코드보다 기존의 표준 유틸리티를 선호한다. 드리프트를 정상화하는 대신 코드를 올바른 패키지, 서비스, 모듈로 옮겨라.

7. **더 깔끔한 구조가 분명할 때 불필요한 순차적 오케스트레이션과 비원자적(non-atomic) 업데이트를 설계 악취로 취급하라.** 독립적인 작업이 이유 없이 직렬화되어 있다면 병렬로 실행해야 하는지 물어라. 관련된 업데이트가 상태를 반쯤만 적용된 채로 둘 수 있다면 더 원자적인 구조를 밀어붙여라. 마이크로 최적화에 과도하게 치중하지 말되, 코드를 더 취약하게 만드는 피할 수 있는 오케스트레이션 복잡성은 지적하라.

## 출력 기대 사항(Output Expectations)

구조적인 코드 품질 퇴행과 놓친 단순화를 가장 먼저, 그다음 스파게티와 분기 복잡성, 그다음 경계, 타입, 파일 크기 문제, 그다음 더 작은 모듈성과 가독성 문제 순으로 우선순위를 둔다.

## 승인 기준(Approval Bar)

동작이 올바른 것처럼 보인다는 이유만으로 승인하지 마라. 작성자가 정당화하지 못하는 한, 다음을 차단 사유로 간주한다. code-judo 수로 삭제할 수 있는 우발적 복잡성을 PR이 많이 유지하고 있다. 파일을 1000줄 미만에서 1000줄 초과로 밀어 올린다. 기존 흐름을 얽히게 하는 임기응변식 분기를 추가한다. 기능 검사를 공유 코드 곳곳에 흩뿌린다. 불필요한 추상화, 래퍼, 캐스트 투성이의 계약을 추가하거나, 기존 헬퍼를 중복하거나, 분명한 표준 위치가 있는데 로직을 잘못된 계층에 둔다. 이런 조건에 해당하지 않으면 명시적이고 실행 가능한 피드백을 남기고 더 깔끔한 분해를 밀어붙여라.

## 리뷰 어조(Review Tone)

직접적이고, 진지하고, 품질에 대해 요구 수준을 엄격하게 하라. 무례하지는 마라. 그러나 중대한 유지보수성 문제를 가벼운 제안으로 누그러뜨리지 마라. 코드가 코드베이스를 더 지저분하게 만들고 있다면 그렇다고 말하라. 구현이 명백하고 극적인 단순화를 놓쳤다면 그것도 말하라. 진짜 문제가 구조적일 때 "이름을 바꾸는 게 좋겠다" 정도로 만족하지 마라.
