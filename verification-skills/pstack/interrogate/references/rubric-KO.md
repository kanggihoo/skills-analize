# 리뷰 루브릭(Review Rubric)

관련 있는 관점(lens)을 통해 리뷰한다. 모든 관점이 모든 변경에 적용되는 것은 아니다. 판단력을 사용하라.

## 정확성(Correctness)

코드가 실제로 의도가 말하는 바를 수행하는가?

- 엣지 케이스: 빈 입력, nil/undefined, 경계값, 동시 접근
- 에러 처리: 에러가 잡히는가, 전파되는가, 조용히 삼켜지는가?
- off-by-one, 타입 강제 변환, 정수 오버플로, 문자열 인코딩
- 상태 관리: 경쟁 상태(race condition), 오래된 클로저(stale closure), 댕글링 참조
- 정상 경로(happy path)가 동작하는가? 실패 경로(sad path)는 동작하는가?
- 멱등성: 이 작업이 두 번 실행되거나 이전 실행이 중간에 죽었다면 어떻게 되는가? 답이 "남겨진 상태에 따라 다르다"라면 조정(reconciliation) 단계가 빠져 있는 것이다.
- 동시성: 여러 행위자가 같은 가변 상태(파일, 브랜치, 공유 데이터)를 건드릴 수 있다면, 접근이 구조적으로(락, 순차적 단계, 독점 소유) 직렬화되는가, 아니면 유지되지 않을 관례로 직렬화되는가?

잠재적 버그를 발견하면 실행 경로를 추적하라. "이것이 nil일 수 있다"라고만 지적하지 마라. 그것을 nil로 만드는 호출 체인을 보여라.

## 근본 원인 대 증상(Root Causes vs. Symptoms)

코드가 실제 문제를 고치고 있는가, 아니면 증상을 덮고 있는가?

이에 답하려면 흔히 변경된 파일 너머를 봐야 한다. 주변 코드(호출자, 피호출자, 타입 정의, 형제 모듈)를 읽고 변경이 속한 아키텍처를 이해하라. 사용 가능한 도구(Read, Grep, Glob)를 사용해 탐색하라. 호출 체인을 따라가라. 타입을 읽어라. 변경이 올바른 계층을 다루는지 판단하기 전에 그 코드가 왜 존재하는지 이해하라.

- 더 깊은 불변식 위반을 가리는 가드 절
- 깨진 계약을 숨기는 재시도 로직
- 모델링 오류를 잠재우는 타입 캐스트
- 우회책(workaround)을 보면 물어라. 왜 우회책이 필요한가? 올바른 수정은 어떤 모습인가?
- 모듈 B의 계약에서 고쳐야 할 것을 모듈 A에서 고친 수정
- 구조가 더 나았을 곳의 지침: 수정이 "X를 하지 마라"라는 주석이거나 누군가 기억해야 하는 관례라면, 그것이 대신 잘못된 일을 불가능하게 만드는 타입 제약, lint 규칙, 런타임 검사가 될 수 있는지 물어라

## 구조적 무결성(Structural Integrity)

코드가 속한 시스템에 잘 들어맞는가?

- 경계 규율: 검증이 시스템 경계에 있는가, 비즈니스 로직 곳곳에 흩어져 있는가? 데이터가 시스템에 들어오는 곳에서 한 번 검증하고, 내부에서는 그것을 신뢰하라.
- 추상화 수준: 코드가 고수준 오케스트레이션과 저수준 세부 사항을 섞고 있는가?
- 결합도: 이 변경이 향후 변경을 더 어렵게 만들 의존성을 도입하는가?
- 데이터 모델 적합성: 데이터 구조가 실제 접근 패턴과 맞는가? 올바른 구조는 다운스트림 코드를 자명하게 만든다. 잘못된 구조는 매 순간 당신과 싸운다.
- 덧붙임 대 통합: 변경이 기존 설계에 덧붙여졌는가, 아니면 설계가 처음부터 그것을 고려한 것처럼 읽히는가? 새 요구 사항을 처음부터 알았다면 코드가 이런 모습이었겠는가?
- 레거시 이중 경로: 변경이 옛 API를 살려 둔 채 새 API를 도입하는가? 외부 소비자가 없다면 호출자를 마이그레이션하고 같은 묶음(wave)에서 옛 경로를 삭제하라. 영구화될 호환성 계층을 남기지 마라.

추상화가 부족하다는 이유로 단순한 코드에 불이익을 주지 마라. 시기상조의 추상화는 중복보다 나쁘다.

## 검증(Verification)

코드를 읽는 것만으로 이 코드가 동작한다고 알 수 있는가?

- 테스트가 있는가? 동작을 테스트하는가, 구현 세부 사항을 테스트하는가?
- 회귀를 잡아낼 assertion/불변식이 있는가?
- 버그 수정이라면: 그 버그에 대한 테스트가 있는가?
- 통합 경계를 건드린다면: 전체 경로가 테스트되는가?
- 대리 지표가 아니라 실제 대상을 확인하라. 코드가 실제 값을 읽는 대신 파일 mtime이나 캐시된 상태로 생존 여부(liveness)를 확인한다면, 그것은 검증의 빈틈이다.
- 위임되었거나 비동기인 작업이라면: 코드가 실제 출력 산출물을 검증하는가, 아니면 자기 보고와 요약을 신뢰하는가?

## 복잡성 예산(Complexity Budget)

복잡성이 코드가 달성하는 바로 정당화되는가?

- 정확성이나 명확성을 잃지 않고도 더 단순할 수 있는 코드
- 호출 지점이 하나뿐인 추상화
- 아직 존재하지 않는 케이스를 위한 설정이나 매개변수화
- 죽은 코드, 쓰이지 않는 import, 흔적만 남은 매개변수
- 과잉 설계: 현재 호출자가 없는 "만약을 위한" 코드 경로
- 더 이상 필요 없는 과도기적 안정성을 위해 살려 둔 낡은 호환성 경로. 마이그레이션이 끝났다면 비계(scaffolding)를 삭제하라
- 사용자 경험이 그 복잡성을 정당화하는가? 모든 기능, 컨트롤, 옵션은 자기 자리를 얻어야 한다. 반쯤 완성된 기능은 없는 것보다 나쁘다.

더 단순한 것이 틀린 것이 아니라면 단순한 것이 낫다. 세 줄의 중복이 시기상조의 추상화보다 낫다.

## 보안(Security)

보안 관련 발견 사항마다 코드를 통한 입력 경로를 추적해 보여라.

- 위험한 싱크(SQL, shell, eval, innerHTML)로 살균 없이 흘러가는 사용자 입력
- 새 엔드포인트의 인증/인가 공백
- 코드, 로그, 에러 메시지에 들어 있는 시크릿
- 보안상 중요한 경로의 TOCTOU(time-of-check-time-of-use)
