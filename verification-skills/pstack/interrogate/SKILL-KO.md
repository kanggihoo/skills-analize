# Interrogate

설정된 모델마다 리뷰어를 하나씩 생성해 코드 변경을 적대적으로 리뷰한다. 각 모델은 같은 프롬프트와 루브릭(rubric)을 받는다. 적대적 신호는 지정된 페르소나가 아니라 모델의 다양성에서 나온다.

산출물은 종합된 판정(verdict)이다. 변경을 자동으로 적용하지 마라.

## Step 1, 범위 결정

맥락에서 무엇을 리뷰할지 파악한다.

- 사용자가 특정 파일이나 diff를 지목하면 그것을 사용한다
- 기능 브랜치에 있다면 `git diff main...HEAD`(또는 적절한 기준 브랜치)를 실행해 전체 변경 집합을 얻는다
- 사용자의 메시지가 최근 작업을 가리키면 관련 파일을 수집한다

diff(또는 파일 내용)와 리뷰어가 코드를 이해하는 데 필요한 주변 맥락 파일을 함께 묶는다.

## Step 2, 의도 서술

리뷰어를 생성하기 전에 의도를 명시적으로 서술한다. 다음에서 도출한다.

- 사용자의 메시지
- 커밋 메시지
- PR 설명(있다면)
- 코드 자체

명확한 한 단락으로 쓴다. 의도가 확실하지 않다면 진행하기 전에 사용자에게 물어라.

## Step 3, 리뷰어 생성

Task 도구를 사용해 모든 리뷰어를 하나의 메시지에서 실행한다. `~/.cursor/rules/pstack-models.mdc`의 `interrogate reviewers` 줄을 사용하고, 항목마다 리뷰어 하나씩 두며, 아래의 Reviewer A/B/C 레이블은 설정된 항목 수에 맞춰 늘리거나 줄인다. 규칙 파일이나 그 줄이 없으면 표의 기본값을 사용한다.

| 서브에이전트 | 기본 모델 |
|----------|---------------|
| Reviewer A | `claude-opus-5-5-max` |
| Reviewer B | `gpt-5.6-sol-max` |
| Reviewer C | `grok-4.7-xhigh-fast` |

각 리뷰어마다:
- `subagent_type`: `generalPurpose`
- `model`: 설정된 `interrogate reviewers` 항목, 설정된 줄이 없으면 표의 기본값. `auto` 또는 `inherit-parent` 항목이면 `model`을 생략해 해당 리뷰어가 부모 모델에서 실행되게 한다.
- `readonly`: `true`

Task 도구가 설정된 항목을 거부하면 그 리뷰어는 해당 계열(family)의 표 기본값으로 실행하고 그 사실을 밝힌다. 계열은 접두사로 구분한다. `claude-*`, `gpt-*`, `grok-*`. 일치하는 계열이 없으면 Reviewer A의 기본값을 사용한다. 표의 기본값이 거부되면 Task 도구의 에러 메시지에서 유효한 slug를 확인하고, 같은 계열에서 가장 가까운 동등 모델(가장 높은 추론 등급 우선)을 골라 그것으로 생성하며, 기본값 표를 갱신하는 별도의 PR을 연다. slug 문제 때문에 리뷰를 막지 마라. 별칭(alias) 항목을 거부된 slug로 취급하거나 그것에 두 폴백 중 어느 쪽이든 적용하지 마라.

`references/reviewer-prompt.md`를 읽고 템플릿을 다음으로 채운다.
1. 서술한 의도
2. diff 또는 파일 내용
3. `references/rubric.md`의 리뷰 루브릭
4. `references/code-quality-review.md`의 코드 품질 관점(lens)

채워진 같은 템플릿이 모든 리뷰어에게 전달되므로, 모든 모델이 코드 품질 관점을 적용한다.

## Step 4, 종합

결과가 돌아오는 대로 통합된 그림을 만든다.

1. 리뷰어들의 **모든 발견 사항(finding)을 파싱한다**
2. **합의를 식별한다**. 2개 이상의 모델이 독립적으로 제기한 발견 사항이 가장 강한 신호다.
3. **단독 모델의 발견 사항을 식별한다**. 여전히 읽을 가치는 있지만 그에 맞게 가중치를 둔다.
4. **중복을 제거한다**. 모델마다 같은 문제를 다르게 서술할 수 있다. 이를 병합하고 어느 모델들이 제기했는지 기록한다.
5. **불일치를 기록한다**. 한 모델이 지적한 것을 다른 모델이 명시적으로 반대로 말한다면, 판정에 유용한 맥락이다.

## Step 5, 리드 판단

당신은 중립적인 취합자가 아니라 실용적인 시니어 엔지니어인 리드 리뷰어다.

전체 프레임워크는 `references/lead-judgment.md`를 읽는다.

모든 발견 사항을 다음 구분으로 분류한다.

- **Act on**(조치 필요). 실제 목표에 비추어 정확성, 보안, 유지보수성에 영향을 주는 실제 문제. 실제 PR을 막을 만한 것들.
- **Consider**(고려). 정당한 지적이지만 지금 이를 처리하는 비용보다 이득이 큰지 확신할 수 없는 것. 사용자가 주목할 가치가 있다.
- **Noted**(참고). 기술적으로는 타당하지만 조치할 수는 없는 것. 맥락에 따라 달라지거나, 시기상조의 최적화이거나, 현재 단계에서는 영향이 작은 것.
- **Dismissed**(기각). 틀렸거나, 사소한 트집이거나, 맥락이 빠진 것. 이유를 간단히 설명한다.

각 발견 사항마다 다음을 포함한다.
- 어느 모델(들)이 제기했는지
- 분류(act on / consider / noted / dismissed)
- 분류에 대한 한 줄 근거

## 출력 형식(Output Format)

판정을 다음 구조로 제시한다.

### Intent
> [Step 2에서 서술한 의도 단락]

### Reviewers
- Reviewer [label]: [model name], [N findings] (리뷰어당 글머리 기호 하나)

### Act On
[처리해야 할 발견 사항. 각각에 대해: 설명, 제기한 모델, 중요한 이유.]

### Consider
[생각해 볼 가치가 있는 발견 사항. 각각에 대해: 설명, 제기한 모델, 관련된 트레이드오프.]

### Noted
[타당하지만 우선순위가 낮은 것. 간단한 목록.]

### Dismissed
[기각한 발견 사항과 간단한 근거.]

### Agreement Map
[모델들이 어디에서 합의했고 어디에서 갈렸으며, 합의/불일치의 패턴이 무엇을 알려 주는가?]
