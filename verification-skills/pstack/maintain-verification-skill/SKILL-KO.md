# Maintain a verification 스킬

기능 맵은 앱이 바뀌는 순간 썩기 시작한다. 이 스킬은 `/create-verification-skill`로 생성된 스킬(또는 기능 맵이 있는 임의의 프로젝트 로컬 검증 스킬)의 유지보수 루프다. 엄밀함의 단위는 모든 문장이 아니라 기능이다. 모든 기능 파일을 소스로 다루고 모든 기능을 라이브로 구동하되, 모든 글머리 기호를 끝까지 확정(terminalise)하려 들지 않는다.

## 결과(Outcomes)

하나를 고르고, 어느 것인지 밝혀라.

- **clean** — 모든 기능이 소스 및 라이브 커버리지를 얻었고, 배포할 만한 것이 없다. 브랜치도 PR도 없다.
- **changed** — 하나의 PR이 증명된 문서, 하네스, 맵 수정 사항을 배포한다.
- **blocked** — 커버리지를 끝낼 수 없었거나 증명된 수정을 안전하게 배포할 수 없었다. 무엇이 막았는지 정확히 말하라.

## 편집 범위(Edit scope)

검증 스킬 자신의 디렉터리(그 SKILL.md, features/, 그것이 소유한 하네스 스크립트)만 편집한다. 실행 중에 제품 코드를 절대 편집하지 마라. 맵이 설명하는 동작을 앱이 더는 하지 않는다면, 그것은 문서 드리프트(맵을 고친다)이거나 제품 회귀(보고하고, 문서로 덮어 가리지 않는다)다.

## 점검 절차(Pass)

0. **대상 찾기.** 유지보수할 검증 스킬을 찾는다. 본문에 launch/drive 섹션과 기능 맵이 있는 프로젝트 로컬 스킬(보통 `.cursor/skills/verify-*/`)이다. 후보가 여럿이면 어느 것인지 묻는다. 없으면 대상을 지어내지 말고 멈추고 `/create-verification-skill`을 안내한다.

1. **인덱스 위생.** 기능 맵 README를 읽고 형제 파일을 glob한다. 누락, 초과, 중복, 죽은 항목을 고친다. 가볍게 한다. 생성된 인벤토리는 쓰지 않는다.

2. **소스 웨이브.** 기능 파일마다 읽기 전용 서브에이전트 하나씩을 동시에 실행한다. 각 서브에이전트는 "이 사용자 대면 기능은 어떻게 동작하는가?"를 소스에서 설명하고, 인용과 함께 문서 드리프트로 의심되는 것을 표시하며, 간결한 라이브 검증 레시피 하나를 반환한다. 자식은 앱을 구동하지 않으며 파일을 편집하지 않는다. 반환 형태: 기능 요약 / 소스 진입점 / 드리프트 의심 또는 없음 / 레시피 하나.

3. **조정(Reconcile).** 모든 기능 파일에 반환된 요약이 있다. 겹치는 레시피를 가능한 한 적은 앱 상태로 병합한다. 인용된 드리프트는 표본 점검하고, 깨끗하다는 주장은 다시 증명하지 않는다. 최근 변경(churn)을 훑어 맵에서 빠진 사용자 대면 표면을 찾는다. 빠졌다고 말하기 전에 구체적인 소스 경로를 요구한다.

4. **라이브 패스.** 소스가 깨끗해 보여도 필수다. 코디네이터가 모든 구동을 소유한다. 검증 스킬 자체의 launch 모델을 따른다. 서버와 UI에는 오래 사는 인스턴스 하나를 직렬로 구동하고, 수명이 짧은 CLI에는 구동마다 새로운 격리 세션을 쓴다(어느 쪽인지는 이 스킬이 아니라 대상 스킬의 Launch 섹션이 결정한다). 모든 기능을 최소 한 번 구동하고, 실패가 무엇이든 패스 내내 세 가지 불변식을 유지한다. (1) 마지막으로 예상 밖의 일을 한 뒤 헬스 체크하지 않은 인스턴스는 구동하지 않는다. 첫 구동 전에 doctor, 세션이 단위인 곳에서는 새 세션마다 doctor, 실패한 구동 뒤에 다시 doctor를 실행하고, doctor가 실패를 볼 수 없는 곳(정상 프로세스에서 UI 상태가 멎은 경우)에서는 희망에 기대지 말고 알려진 상태로 리셋하거나 재실행한다. (2) 지금까지 캡처한 증거는 모든 정리를 견뎌야 하며, 명시된 위치에서 확인해야지 가정하지 않는다. (3) 구동이 시작한 어떤 것도 그 구동의 쓸모보다 오래 살아남지 않는다. 실패한 반복의 잔여물은 세션이 멎었든, 종료되었든, 공유되든 정리한다(공유 인스턴스라면 인스턴스가 아니라 잔여물을 정리한다). 스킬 드리프트로 인한 doctor 실패는 드리프트다. 편집 범위(edit scope) 안에서 고치고 한 번 재시도하되(수정이 무효화한 것만 재시작하고 그 이상은 하지 않는다), 그다음에야 패스를 `blocked`라고 부른다. 도달할 수 없는 기능은 구체적인 전제 조건(인증, 자격(entitlement), OS, 외부 상태)과 시도한 경로가 있을 때만 `verified-unreachable`이다. 맵이 그 전제 조건을 빠뜨렸다면 그것은 드리프트다. 트리아지에서 나온 하네스 수정은 배포하기 전에 라이브로 다시 구동한다. 최종 정리(teardown)는 이 재증명을 포함해 실행의 마지막 구동 이후에 수행하여 실행 후에 아무것도 남지 않게 한다(증거는 스킬에 따라 남는다).

5. **트리아지.** 사용자 관점의 설명이 틀렸거나 빠졌다 → 문서 드리프트이므로 고친다. 동작하는데 하네스가 구동하지 못하는 동작 → 하네스 공백이므로 고친다. 하네스 수정은 생성 시와 같은 헬퍼 규칙을 따른다(스크립트는 실행 가능하고 호출 방법이 스킬 본문에 문서화되어 있다). 실제로 망가진 앱 동작 → 제품 공백이므로 사용자를 위해 기록하고 이 PR에서는 제외한다.

6. **배포 또는 중단.** changed의 경우: 증명된 수정 사항의 PR 하나를 만들고, 그 전에 변경된 모든 파일을 다시 읽는다. clean 또는 blocked의 경우: PR 없이 결과와 커버리지를 정직하게 보고한다.

간결한 실행 노트(다룬 기능, 도달할 수 없는 전제 조건, 확인된 드리프트, 결과)를 임시 위치에 보관하고, 커밋하지 않는다.
