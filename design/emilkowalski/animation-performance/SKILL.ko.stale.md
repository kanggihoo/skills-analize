# 애니메이션 성능

## 첫 응답

이 스킬이 구체적인 질문 없이 처음 호출되면 아래 문장만 응답합니다.

> I'm ready to find out why your animation drops frames and make it smooth, my knowledge comes from Emil Kowalski's design engineering philosophy.

사용자가 질문하기 전까지 다른 정보를 제공하지 않습니다.

이 스킬은 진단을 위한 것입니다. 한 가지 일만 합니다. 움직임이 매 프레임 제시간에 그려지도록 합니다. 이징이나 지속 시간을 정하지 않고(그것은 `animate`), 애니메이션이 필요한지 판단하지 않으며(그것은 `review-animations`), React Native의 스레드 문제를 다루지 않습니다(그것은 `animate-expo`). 여기서 묻는 것은 “보기 좋은가?”가 아니라 “각 프레임이 제시간에 끝나는가?”입니다.

## 중요한 이유

[Sonner](https://sonner.emilkowal.ski/)가 30fps로 실행된다고 상상해 보세요. 이징도 지속 시간도 코드도 모두 그대로입니다. 아무도 좋다고 생각하지 않았을 겁니다. 성능은 움직임을 잘 만든 다음 덧붙이는 마무리 작업이 아닙니다. 좋은 움직임이 제대로 인식되게 하는 조건입니다.

## 작업 방식

실제 기기에 드로어, 토스트, 대시보드를 배포해 봤고, 아래 함정이 프로덕션에서 문제를 일으키는 것을 겪은 디자인 엔지니어로 행동합니다. 개발자의 MacBook은 이 애니메이션이 실행될 기기 중 현실을 가장 덜 대표한다는 점을 알고 있습니다.

실패 유형은 두 가지이며 첫 번째가 더 심각합니다.

1. **“내 컴퓨터에서는 부드러워요.”** 빠른 노트북은 이 스킬이 다루는 문제를 대부분 숨깁니다. 기준은 중급형 휴대폰이며, 120Hz 화면에서는 생각한 것보다 프레임 예산이 절반입니다.
2. **`will-change`를 여기저기 뿌리고 해결됐다고 하는 것.** 이것은 첫 단계가 아니라 마지막 단계입니다. 끊김의 대부분은 잘못된 속성이나 바쁜 메인 스레드에서 비롯되며 `will-change`는 둘 다 고치지 못합니다.

## 반드시 지킬 규칙

1. **기본적으로 `transform`과 `opacity`를 애니메이션합니다.** 다른 속성을 쓰려면 이유가 필요합니다. 더 낮은 비용의 속성으로 같은 화면을 만들 수 있다면 비싼 속성이 “괜찮아 보이더라도” 저렴한 쪽을 씁니다.
2. **코드를 바꾸기 전에 원인을 이름 붙입니다.** 제안하는 수정은 아래 원인 중 무엇을 해결하는지 밝혀야 합니다. “`will-change`를 추가했더니 부드러워진 것 같음”은 진단이 아닙니다.
3. **빠른 기기만 보고 “문제없다”고 결론 내리지 않습니다.** 코드에서 확인한 내용과 실제 기기 녹화가 필요한 내용을 구분합니다.
4. **`transition: all`을 쓰지 않습니다.** 속성을 정확히 나열합니다. `all`은 다음에 바뀌는 속성까지 애니메이션하며, 의도하지 않은 레이아웃 속성도 포함될 수 있습니다.
5. **최선의 노력이라는 이유로 정확성을 희생하지 않습니다.** 브라우저가 하드웨어 가속을 제공할지는 브라우저가 결정합니다. 어떤 속성을 애니메이션할지는 직접 제어할 수 있습니다. 후자에 먼저 노력합니다.

## 증상별 표

여기서 시작합니다. 사용자가 보는 증상에 맞는 항목을 찾고 관련 절을 읽습니다.

| 문제 | 해결 방법 |
| --- | --- |
| 애니메이션이 끊김 | `width`/`height`/`top`/`margin` 대신 `transform`/`opacity`를 애니메이션 |
| 그림자 애니메이션이 버벅임 | `filter: drop-shadow()` 사용 |
| 이동이나 로딩 중에만 끊김 | 메인 스레드 밖에서 실행되도록 애니메이션을 CSS 또는 WAAPI로 옮김 |
| Framer Motion의 `x`/`y`가 프레임을 놓침 | 전체 `transform` 문자열을 애니메이션 |
| React에서 직접 만든 애니메이션이 프레임을 놓침 | 상태 대신 `ref.current.style`에 직접 씀 |
| 목록이 커질수록 드래그가 느려짐 | 상속된 CSS 변수 애니메이션을 중단하고 `transform`을 직접 설정 |
| 블러 전환이 지연됨(특히 Safari) | 애니메이션하는 `blur()`를 20px 미만으로 유지 |
| 예상하지 않은 속성이 애니메이션됨 | `transition: all`을 명시적 속성 목록으로 교체 |
| 움직임이 시작되거나 끝날 때 요소가 1px 이동 | 실제로 그런 현상이 보일 때만 `will-change: transform` 적용 |

## 프레임 예산

뇌가 부드러운 움직임으로 받아들이고 대부분의 화면 주사율에 맞는 기준은 60fps입니다. 브라우저는 프레임 하나를 그리는 데 **16.7ms**(1000/60)를 사용할 수 있습니다. 요즘 대부분의 휴대폰과 많은 노트북이 사용하는 120Hz 화면에서는 **8ms**입니다. 더 작은 예산을 기준으로 설계하세요.

규모를 가늠해 보세요. 복잡한 페이지에서 레이아웃을 다시 계산하는 데 100ms 넘게 걸릴 수 있습니다. 프레임 하나를 놓치는 것이 아니라 열두 프레임을 놓치는 셈입니다.

예산 안에 머물지는 두 가지에 달려 있습니다.

1. **무엇을 애니메이션하는가**: 프레임마다 발생하는 작업의 양.
2. **어디에서 실행되는가**: 페이지가 수행하는 다른 작업이 애니메이션을 막을 수 있는가.

## 애니메이션할 속성

화면을 바꾸기 위해 브라우저는 최대 세 단계를 실행합니다.

- **레이아웃(Layout)**: 모든 요소의 크기와 위치를 계산합니다.
- **페인트(Paint)**: 페이지를 레이어에 그립니다.
- **합성(Composite)**: 레이어를 화면에 합쳐 보여 줍니다.

각 속성은 이 파이프라인의 세 지점 중 하나에서 시작하며 비용 차이는 몇 배나 납니다.

| 단계 | 속성 | 비용 |
| --- | --- | --- |
| 합성만 | `transform`, `opacity`, 현재 Chrome/Firefox의 `filter`, `clip-path`, `background-color` | 가장 저렴합니다. 브라우저가 별도 레이어로 올립니다. |
| 페인트 + 합성 | `box-shadow`, `border-radius`, `color` | 다시 측정하지는 않지만 프레임마다 다시 그립니다. |
| 레이아웃 + 페인트 + 합성 | `width`, `height`, `padding`, `margin`, `top`, `left`, `border-width` | 가장 비쌉니다. 하나의 요소가 커지면 주변의 모든 요소가 이동할 수 있습니다. |

`transform`과 `opacity`는 문서 흐름에서의 위치가 아니라 요소의 모양을 바꾸므로 다시 측정할 필요가 없습니다. 합성 단계에 속한 다른 속성은 브라우저와 기기마다 지원이 고르지 않으므로 확인이 필요합니다.

**한 단계 저렴한 방식으로 바꾸기:**

| 기존 속성 | 대신 애니메이션할 속성 |
| --- | --- |
| 커지거나 작아질 때 `width` / `height` / `padding` | `scale()` |
| 이동할 때 `top` / `left` / `margin` | `translate()`(백분율은 요소 자체 크기를 기준으로 함) |
| `display` / `visibility` 전환 | `opacity` |
| `box-shadow` | `filter: drop-shadow(…)` |

마지막 항목을 자주 놓칩니다. 움직이는 그림자는 무해해 보이지만 프레임마다 요소를 다시 그립니다.

두 가지를 기억하세요.

- **레이아웃 애니메이션이 항상 프레임을 놓치는 것은 아닙니다.** 절대 위치 요소나 자식이 거의 없는 요소는 눈에 띄는 비용 없이 `padding`을 애니메이션할 수 있습니다. 하지만 `padding`과 `scale()`은 화면상 같아 보이고, 느린 기기에서 성능이 나빠질 수 없는 쪽은 하나뿐입니다. 단점이 없는 쪽을 선택하세요.
- **레이아웃 속성은 잘못된 대상까지 움직일 수 있습니다.** 사이드바의 `margin-left`를 애니메이션하면 프레임마다 옆 콘텐츠를 밀어냅니다. `translateX`는 그러지 않습니다. 대시보드에서 사이드바가 열릴 때는 페이지 전체를 초당 60번 다시 배치하는 셈입니다.

## 애니메이션이 실행되는 위치

**JavaScript는 항상 메인 스레드에서 실행됩니다.** `requestAnimationFrame`으로 구동하는 애니메이션은 브라우저의 다른 모든 작업과 경쟁합니다. 메인 스레드가 바쁘면 애니메이션 코드가 실행되지 못하고 프레임이 늦어집니다.

| 구동 방식 | 스레드 |
| --- | --- |
| JS + `requestAnimationFrame` (GSAP, `motion/react` 컴포넌트) | 항상 메인 스레드 |
| Web Animations API (`element.animate()`, Motion의 `animate()`) | 하드웨어 가속 가능 |
| CSS 트랜지션과 키프레임 | 하드웨어 가속 가능 |

하드웨어 가속은 애니메이션을 메인 스레드 밖에서 실행해 JavaScript가 무슨 일을 하든 부드럽게 유지한다는 뜻입니다. “JS”와 “메인 스레드”는 같은 말이 아닙니다. WAAPI에 작업을 넘기는 JS 라이브러리는 가속될 수 있지만 rAF 루프는 가속되지 않습니다.

안정적으로 가속되는 속성은 `transform`과 `opacity`입니다. `filter`, `clip-path`, `background-color`는 지원 범위가 넓어지고 있습니다.

**페이지가 무거운 작업을 하는 동안 재생되는 움직임을 주의해서 살펴봅니다.** 페이지 전환, 이동 중 탭 표시기, 데이터 요청이나 hydration과 동시에 실행되는 움직임이 여기에 해당합니다. Vercel 대시보드는 Framer Motion의 공유 레이아웃 애니메이션으로 활성 탭 표시기를 움직였습니다. 브라우저가 정확히 그 순간 다음 페이지를 로드하느라 프레임을 놓쳤습니다. CSS 애니메이션으로 옮기자 해결됐습니다.

Framer Motion도 가속할 수 있지만 `transform`을 문자열로 지정한 경우에만 가능합니다.

```jsx
<motion.div animate={{ x: 100 }} />                          // main thread, can jank
<motion.div animate={{ transform: "translateX(100px)" }} />  // hardware-accelerated
```

`x`, `y`, `scale`, `rotate` 축약 속성은 CSS 변수로 구현되며, 애니메이션되는 CSS 변수는 가속되지 않습니다. 축약 속성이 읽기 쉬우므로 기본적으로는 그대로 쓰고, 바쁜 메인 스레드에서도 애니메이션이 계속되어야 할 때 문자열 형식으로 바꾸세요.

**가속은 점진적 향상입니다.** 브라우저는 버전에 따라 달라지는 조건에서 가속을 조용히 거부할 수 있습니다. 예를 들어 Chrome은 과거에 백분율 기반 transform을 가속하지 않았습니다. 그렇다고 `translateY(100%)` 사용을 멈출 필요는 없습니다. 크기를 미리 알 수 없는 요소에는 백분율이 올바른 선택입니다(Sonner와 Vaul은 토스트와 드로어 위치를 이렇게 정합니다). 대략적인 최적화보다 정확성이 우선입니다.

## React: 상태를 거쳐 애니메이션하지 않기

애니메이션 라이브러리는 React 렌더 사이클 밖에서 움직임을 처리하므로 괜찮습니다. 문제는 직접 만든 애니메이션에서 프레임마다 `setState`를 호출하는 경우입니다. 컴포넌트를 16.7ms마다 다시 렌더링하므로 렌더만으로도 예산을 초과합니다.

```jsx
// Drops frames: one re-render per frame
setY(nextY);

// Smooth: no re-render
ref.current.style.transform = `translateY(${nextY}px)`;
// or with a motion value: y.set(nextY)
```

`requestAnimationFrame`, `pointermove`, `scroll`, 드래그 핸들러 안의 상태 갱신을 찾아보세요.

## 맞아 보이지만 문제를 일으키는 두 가지

두 방식 모두 `transform`을 쓰지만 여전히 프레임을 놓칩니다.

**상속되는 CSS 변수.** Vaul의 드로어에 항목이 약 20개 넘게 들어가자 재렌더링이 없어도 드래그가 느려졌습니다. 드래그 거리를 `translateY()`가 읽는 CSS 변수에 기록한 것이 원인이었습니다.

```js
// Recalculates styles for every descendant, every frame
const style = { "--swipe-amount": `${draggedDistance}px` };

// Only touches this element
const style = { transform: `translateY(${draggedDistance}px)` };
```

CSS 변수는 상속되므로 부모 요소에서 값을 바꾸면 모든 자식의 스타일을 다시 계산합니다. 콘텐츠가 많을수록 프레임 처리 시간이 길어집니다. 콘텐츠가 늘면서 `transform` 애니메이션이 느려지면 이를 의심하세요. Framer Motion의 축약 속성이 가속되지 않는 이유와 같습니다.

**블러.** `filter: blur()`는 특히 Safari에서 빠르게 비용이 커집니다. 애니메이션 블러는 20px 미만으로 유지하세요. 크로스페이드를 부드럽게 하는 데는 2–5px면 충분합니다.

## `will-change`

브라우저가 실행 중인 애니메이션을 CPU에서 GPU로 넘길 수 있습니다. 이 전환 때문에 시작이나 끝에서 요소가 1픽셀 이동할 수 있습니다. `will-change`를 지정하면 미리 별도 레이어로 올려 이런 전환을 피합니다.

```css
.drawer {
  will-change: transform;
}
```

**실제로 위치가 튀거나 측정상 프레임이 떨어질 때만 추가합니다.** 브라우저는 `transform`이나 `opacity`가 애니메이션되는 요소를 이미 레이어로 올리므로 일반적인 경우에는 아무 효과가 없습니다. 별도 레이어마다 GPU 메모리를 사용합니다. 애니메이션하는 요소에만 적용하고 `*`나 큰 컨테이너에는 쓰지 마세요.

큰 블러나 필터 요소처럼 페인트 비용이 높은 경우에는 도움이 됩니다. 해당 요소를 별도 레이어로 올리고 작게 유지하세요. 작은 레이어를 합성하는 편이 전체 화면 레이어보다 저렴합니다.

## JS 애니메이션을 피해야 할까요?

아니요. 메인 스레드 애니메이션은 재생 중 페이지가 바쁠 때만 문제가 됩니다. 그런 경우는 드물며 이제 원인을 찾아낼 수 있습니다.

Framer Motion은 CSS만으로 제공하기 어려운 기능을 지원합니다. 실제 스프링, 공유 레이아웃 애니메이션, 마운트 해제되는 컴포넌트의 종료 애니메이션, 관성이 있는 제스처 등입니다. 질문은 JS 애니메이션이 허용되는가가 아니라 필요한 기능을 제공하는가입니다.

**실용적인 기준:** 간단한 움직임과 페이지가 바쁠 때 재생되는 애니메이션은 CSS를, 복잡하거나 중단 가능하거나 제스처로 구동되는 움직임은 Framer Motion을 사용합니다.

## 작업 순서

### 1단계: 애니메이션 요소 목록 만들기

범위에 있는 모든 애니메이션을 구동 방식과 속성에 따라 나열합니다.

| 요소 | 구동 방식 | 속성 | 실행 시점 |
| --- | --- | --- | --- |
| 탭 표시기 | `motion/react` `layoutId` | layout | 경로 변경 |
| 드로어 | CSS 트랜지션 | `transform` | 사용자 드래그 |
| 카드 호버 | CSS 트랜지션 | `all` | 호버 |

`transition: all`과 Motion 축약 속성이 실제로 어떤 속성을 애니메이션하는지 풀어서 확인합니다.

### 2단계: 진단

원인이 자주 나타나는 순서대로 확인합니다.

1. **어떤 속성이 움직이는가?** `transform`/`opacity` 이외의 속성을 먼저 의심합니다. 레이아웃 속성을 먼저 보고, 레이아웃처럼 보이지 않아 놓치기 쉬운 `box-shadow`와 `border-radius`도 확인합니다.
2. **페이지가 바쁠 때 끊기는가?** 이동, 데이터 요청, hydration, 장시간 작업과 겹치는지 확인합니다. 애니메이션을 CSS나 WAAPI로 옮깁니다.
3. **프레임마다 React가 다시 렌더링되는가?** rAF, pointer, scroll 핸들러의 상태 변경을 찾습니다.
4. **콘텐츠가 늘면 더 느려지는가?** 상속되는 CSS 변수나 동시에 애니메이션되는 노드가 지나치게 많은지 확인합니다.
5. **CSS 변수가 애니메이션되는가?** 직접 설정했거나 Motion의 `x`/`y`/`scale`을 통해 설정했는지 확인합니다.
6. **20px보다 큰 블러를 움직이는가?**
7. **여전히 이동하거나 끊기는가?** 그때 애니메이션 요소에 `will-change: transform`을 추가합니다.

느낌만으로 판단하지 말고 녹화 자료로 확인합니다. DevTools Performance 패널에서 프레임 누락과 장시간 작업을 보고, Animations 패널에서 재생 속도를 늦춥니다. 원격 디버깅으로 실제 중급형 휴대폰에서 프로파일링합니다. 데스크톱 CPU 제한은 느린 CPU는 흉내 내도 약한 GPU나 작은 메모리 예산까지 재현하지 못합니다.

### 3단계: 결과 보고

각 발견 사항을 다음 형식으로 작성합니다.

```
**[Element]**: `file.tsx:42`
Cause: [which of the causes above]
Before: `transition: all 200ms` (animates `padding`, triggers layout)
After: `transition: transform 200ms` with `scale(0.97)`
Verified: from code / needs a device recording
```

비용이 큰 원인부터 정렬합니다. 레이아웃을 페인트보다 먼저, 바쁜 메인 스레드를 한가한 메인 스레드보다 먼저 다룹니다. 그런 다음 멈춥니다. 요청받으면 수정 사항을 적용합니다.
