# 애니메이션 감사 플레이북

감사할 여덟 가지 범주와 각 범주에서 확인할 항목, 발견 사항과 계획에 인용할 정확한 목표값을 정리했습니다. Emil Kowalski의 디자인 엔지니어링 철학([emilkowal.ski](https://emilkowal.ski/))에서 추렸습니다. 여기에 나온 값을 어림잡지 말고 그대로 복사합니다.

## 1. 목적과 사용 빈도

모든 애니메이션에는 “왜 움직이는가?”에 답이 있어야 합니다. 공간적 일관성, 상태 표시, 피드백, 설명, 갑작스러운 변화 방지 등이 목적입니다. 자주 보는 요소에 “멋져 보이기”는 목적이 아닙니다.

| 빈도 | 결정 |
| --- | --- |
| 하루 100회 이상(키보드 단축키, 커맨드 팔레트 토글) | 애니메이션하지 않음. 절대로. |
| 하루 수십 회(호버 효과, 목록 탐색) | 제거하거나 크게 줄임 |
| 가끔(모달, 드로어, 토스트) | 표준 애니메이션 |
| 드물게 / 처음 한 번(온보딩, 피드백, 축하) | 즐거움을 더할 수 있음 |

확인할 것: 키보드로 시작하는 동작의 애니메이션, 열기 / 닫기 전환이 있는 커맨드 팔레트(Raycast에는 없음 — 그게 맞음), 목록 항목이나 호버 상태에 적용되어 계속 눈에 띄는 장식 움직임. 가장 효과적인 수정은 **애니메이션 제거**인 경우가 많습니다.

## 2. 이징과 지속 시간

이징 선택 순서:

- 진입 또는 퇴장 → **`ease-out`**(빠르게 시작해 반응이 빠르게 느껴짐)
- 화면에서 이동 / 모핑 → **`ease-in-out`**
- 호버 / 색상 변화 → **`ease`**
- 일정한 움직임(마퀴, 진행 표시) → **`linear`**
- 기본값 → **`ease-out`**

**UI에서 `ease-in`을 사용하면 반드시 발견 사항으로 기록합니다.** 시작이 느려 사용자가 지켜보는 바로 그 순간을 지연시킵니다. 기본 CSS 이징은 의도적인 움직임을 만들기에 너무 약합니다. 계획에서는 저장소 관례에 맞춰 강한 사용자 지정 곡선을 토큰으로 추가하도록 합니다.

```css
--ease-out: cubic-bezier(0.23, 1, 0.32, 1);        /* strong ease-out for UI */
--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1);    /* strong ease-in-out for on-screen movement */
--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1);     /* iOS-like drawer curve */
```


지속 시간 예산 — **UI 애니메이션은 300ms 미만으로 유지합니다.**

| 요소 | 지속 시간 |
| --- | --- |
| 버튼 누름 피드백 | 100–160ms |
| 툴팁, 작은 팝오버 | 125–200ms |
| 드롭다운, 선택 상자 | 150–250ms |
| 모달, 드로어 | 200–500ms |
| 마케팅 / 설명용 | 더 길어도 됨 |

확인할 것: 어디서든 사용하는 `ease-in`, 진입에 기본 `ease` / `linear`를 사용한 경우, UI 요소에 300ms가 넘는 지속 시간, 도구 모음의 모든 툴팁에 지연 + 애니메이션을 반복하는 경우(첫 툴팁 이후에는 즉시 열려야 함).

## 3. 물리감과 시작점

- **`scale(0)`은 절대 사용하지 않습니다.** 현실에서 아무것도 없는 곳에서 요소가 나타나지는 않습니다. 목표값은 `scale(0.9–0.97)` + `opacity: 0`입니다.
- **팝오버 / 드롭다운 / 툴팁은 중앙이 아니라 트리거에서 확대합니다.**
  ```css
  .popover { transform-origin: var(--transform-origin); } /* Base UI */
  ```
  **모달은 예외**입니다. 중앙에 표시되므로 `transform-origin: center`가 맞습니다. 모달에 이 값을 쓴 경우는 보고하지 않습니다.
- **누름 피드백:** `:active`에 `transform: scale(0.97)`을 적용하고 `transition: transform 160ms ease-out`을 사용합니다. 미묘한 수준(0.95–0.98)으로 유지합니다.

확인할 것: `scale(0)`, 시작 transform 없이 opacity만 바뀌는 진입, 트리거에 고정된 요소에 `transform-origin: center` 또는 원점 미지정, 누름 피드백이 없는 누를 수 있는 요소.

## 4. 중단 가능성

CSS **트랜지션**은 애니메이션 도중 현재 상태에서 새 목표로 바뀌지만 **키프레임**은 처음부터 다시 시작합니다. 빠르게 재호출되거나 움직임 도중 되돌릴 수 있는 요소(쌓이는 토스트, 토글, 드래그, 펼치기 / 접기)에는 트랜지션이나 스프링을 사용해야 합니다.

- JS 없이 진입: `@starting-style`(레거시 대안: `useEffect`에서 설정하는 `data-mounted` 속성)
- 제스처로 움직이는 요소는 스프링을 사용합니다. 중단돼도 속도를 이어받습니다.
- Apple 스타일 스프링 설정(권장): `{ type: "spring", duration: 0.5, bounce: 0.2 }`. 바운스는 약하게(0.1–0.3) 유지하고, 눈에 띄는 바운스는 드래그로 닫기나 장난스러운 순간에만 사용합니다.
- **시간 비대칭:** 의도적인 구간(누르기, 길게 누르기, 파괴적 동작 확인)은 느리게, 시스템의 반응은 빠르게 처리합니다. 누름과 해제의 속도가 같다면 발견 사항입니다.

확인할 것: 토스트 / 토글 / 빠르게 다시 실행되는 UI에 `@keyframes` 사용, 제스처 핸들러에서 고정 시간 키프레임 사용, 거리만 기준으로 닫는 드래그(거리 임계값만 쓰지 말고 `Math.abs(distance)/elapsedMs > ~0.11` 속도 기준도 적용), 증가하는 마찰 대신 경계에서 딱 멈추는 드래그.

## 5. 성능

- **`transform`과 `opacity`만 애니메이션합니다.** `width`/`height`/`margin`/`padding`/`top`/`left`는 레이아웃 + 페인트 + 합성을 유발합니다.
- **`transition: all`**은 GPU를 쓰지 않는 의도치 않은 속성까지 애니메이션하므로 항상 발견 사항입니다.
- **Framer Motion의 `x`/`y`/`scale` 축약 속성은 하드웨어 가속되지 않습니다.** 메인 스레드에서 실행돼 부하가 걸리면 프레임을 놓칩니다. 목표는 전체 transform 문자열입니다: `animate={{ transform: "translateX(100px)" }}`.
- **부모 CSS 변수로 자식의 transform을 제어하지 않습니다.** 모든 자식 스타일을 다시 계산하게 됩니다. 요소에 `transform`을 직접 설정합니다.
- 부하가 있을 때 CSS와 WAAPI는 rAF 기반 JS보다 안정적입니다. 미리 정해진 움직임에는 CSS를, 동적이고 제스처로 제어되는 움직임에는 JS / 스프링을 사용합니다.
- 전환 중 `filter: blur()`는 20px 미만으로 유지합니다. 강한 블러는 특히 Safari에서 비용이 큽니다.

확인할 것: `transition: all`, 애니메이션되는 레이아웃 속성, 바쁜 페이지에서 Framer Motion 축약 속성, `setProperty('--x', …)`로 자식 transform 제어, CSS로 할 수 있는 동작을 rAF 루프로 구현한 경우.

## 6. 접근성

```css
@media (prefers-reduced-motion: reduce) {
  .element { animation: fade 0.2s ease; } /* keep opacity/color, drop movement */
}
@media (hover: hover) and (pointer: fine) {
  .element:hover { transform: scale(1.05); } /* touch fires false hovers on tap */
}
```


움직임 줄이기는 애니메이션을 **없애는 게 아니라 수와 강도를 줄이는 것**입니다. 이해를 돕는 트랜지션은 유지하고 위치 변화는 제거합니다. JS에서는 `useReducedMotion()`을 사용해 transform 값을 분기합니다.

확인할 것: `prefers-reduced-motion` 처리가 없는 움직임, 게이팅되지 않은 `:hover` 움직임, 모든 피드백을 없애는 움직임 줄이기 구현.

## 7. 응집력과 토큰

- 움직임은 제품의 성격과 맞아야 합니다. 장난스러운 제품은 더 튀어도 되지만 대시보드는 또렷해야 합니다. 컴포넌트 사이에 성격이 맞지 않으면 발견 사항입니다.
- 곡선과 지속 시간은 공유 토큰으로 관리합니다. 거의 같은 cubic-bezier를 다섯 군데 직접 입력했다면 통합 대상입니다.
- 그룹 진입에서 **30–80ms 시차**가 필요한데 모든 항목이 동시에 나타나는지 확인합니다. 시차는 장식이므로 상호작용을 막으면 안 됩니다.
- 겹친 두 상태가 보이는 거친 크로스페이드는 전환 중 `filter: blur(2px)`를 은은하게 적용해 가릴 수 있습니다.

확인할 것: 서로 거의 같은 이징 / 지속 시간의 중복, 또렷한 앱에서 한 컴포넌트만 튀는 움직임, 시차가 없는 목록 / 그리드 진입, 겹친 상태가 눈에 보이는 크로스페이드.

## 8. 놓친 기회

추가 기회 범주입니다. 움직임이 없어도 되는 곳이 아니라 있어야 하는 곳을 찾습니다.

- 갑작스러운 변화가 있는 상태 전환(콘텐츠 교체, 레이아웃 점프) — 짧은 트랜지션으로 변화가 덜 거칠게 느껴질 수 있습니다.
- 공간적으로 연결된 UI(트리거에서 나타나는 패널)에 어디서 왔는지 설명하는 움직임이 없음.
- 처음 실행, 성공, 축하처럼 드물지만 감정이 중요한 순간에 허용된 즐거움의 예산을 전혀 사용하지 않음.
- `translate` 백분율(`translateY(100%)` = 요소 자체 높이)과 `clip-path: inset()` 진입은 이를 위한 도구이며 픽셀을 하드코딩할 필요가 없습니다.

실제로 확인한 UX 연결 지점에 근거해 몇 가지만 보고합니다. 희망 목록을 만들지 않습니다.
