# Apple 디자인

## 첫 응답

이 스킬이 구체적인 질문 없이 처음 호출되면 다음 문장만 응답합니다.

> I'm ready to help you build fluid, Apple-style interfaces on the web, my knowledge comes from Apple's WWDC design talks, translated for the web.

사용자가 질문하기 전까지 다른 정보를 제공하지 않습니다.

Apple이 인터페이스를 어떻게 설계해 컴퓨터를 조작하는 느낌을 줄이고, 사람의 연장처럼 느끼게 하는지 다룹니다. 이 지식은 Apple의 WWDC 디자인 강연, 특히 *Designing Fluid Interfaces*(WWDC 2018)를 바탕으로 하며 웹 플랫폼(CSS, Pointer Events, `requestAnimationFrame`, Motion/Framer Motion 같은 스프링 라이브러리)에 맞게 정리했습니다.

핵심 원칙은 다음과 같습니다. **움직임이 현재 화면에 표시된 값에서 시작하고, 사용자의 속도를 이어받으며, 관성을 앞으로 투영하고, 언제든 잡아 반대 방향으로 움직일 수 있을 때 인터페이스는 살아 있는 것처럼 느껴집니다.** 스프링은 본질적으로 중단할 수 있고 속도를 반영하므로 이 모든 동작을 자연스럽게 구현하는 도구입니다.

## 핵심 생각

> “인터페이스를 우리가 생각하고 움직이는 방식에 맞추면 마법 같은 일이 일어납니다. 인터페이스는 컴퓨터처럼 느껴지지 않고 우리와 자연스럽게 이어지는 연장처럼 느껴집니다.”

인터페이스가 물리 세계처럼 동작하면 유연하게 느껴집니다. 즉각 반응하고, 연속적으로 움직이며, 관성을 이어받고, 경계에서 저항하고, 움직이는 도중에도 방향을 바꿀 수 있어야 합니다. 아래 원칙은 모두 이 상태에 가까워지기 위한 방법입니다.

Apple은 디자인이 사람의 네 가지 필요를 충족해야 한다고 설명합니다. **안전과 예측 가능성, 이해, 성취, 즐거움**입니다. 여기의 각 규칙은 그중 하나를 돕습니다.

## 1. 반응 — 지연 없애기

지연이 느껴지는 순간 직접 조작하는 느낌은 “절벽처럼 떨어집니다.” 반응성은 다른 모든 경험이 쌓이는 기반입니다.

- **손을 떼었을 때가 아니라 포인터를 누르는 순간 반응합니다.** 버튼을 누르는 바로 그 순간 강조 표시를 보여 줍니다. `click`이나 터치 해제가 끝날 때까지 피드백을 미루면 반응이 없는 듯 느껴집니다.
- **모든 지연을 꼼꼼히 확인합니다.** 디바운스, 인위적인 타이머, 트랜지션 대기, 약 300ms의 탭 지연을 점검합니다. 입력 경로에 있는 작업 중 꼭 필요하지 않은 것은 회귀 원인입니다.
- **피드백은 끝에만 나타나는 것이 아니라 상호작용 *도중 내내* 이어져야 합니다.** 드래그, 슬라이더, 드로어는 제스처가 끝날 때까지 기다리지 말고 포인터와 1:1로 UI를 갱신해야 합니다.

```css
/* Feedback lives on the press, and it's instant */
.button:active {
  transform: scale(0.97);
  transition: transform 100ms ease-out;
}
```

## 2. 직접 조작 — 1:1로 따라가기

> “터치와 콘텐츠는 함께 움직여야 합니다.”

사용자가 무언가를 끌면 요소는 손가락에 붙어 움직여야 하며, *잡은 지점의 오프셋*도 유지해야 합니다. 잡는 순간 요소의 중앙으로 맞추면 착각이 바로 깨집니다.

- Pointer Events와 `setPointerCapture`를 사용해 포인터가 요소 경계를 벗어나도 추적을 계속합니다.
- 현재 좌표만 저장하지 말고 짧은 **속도/위치 기록**(최근 `pointermove` 몇 회)을 유지합니다. 손을 놓을 때 속도가 필요합니다.

```js
el.addEventListener('pointerdown', (e) => {
  el.setPointerCapture(e.pointerId);
  const grabOffset = e.clientY - el.getBoundingClientRect().top; // respect where they grabbed
  // ...track position + timestamp history for velocity
});
```

## 3. 중단 가능성 — 가장 중요한 원칙

> “생각과 제스처는 동시에 일어납니다.”

모든 애니메이션은 언제든 중단하고 방향을 바꿀 수 있어야 합니다. 사용자는 움직이는 요소를 도중에 잡아 애니메이션이 끝날 때까지 기다리지 않고 반대로 움직일 수 있어야 합니다. 닫히는 모달을 다시 잡으면, 먼저 닫힌 다음 다시 열리는 게 아니라 손가락을 따라가야 합니다.

- **전환 중에 입력을 막지 않습니다.**
- **항상 목표값이 아닌 표현값(presentation), 즉 현재 화면에 표시된 값에서 애니메이션을 시작합니다.** 중단할 때 요소가 화면에서 실제로 보여 주는 transform을 읽고, 그 위치에서 다음 애니메이션을 시작합니다. 논리적 목표값에서 시작하면 눈에 띄게 튑니다.
- **제스처로 제어하는 움직임에는 CSS 트랜지션과 `@keyframes`를 피합니다.** 움직임 중간에 자연스럽게 잡아 반대로 돌리기 어렵습니다. 스프링은 기본적으로 현재 값에서 시작하므로 중단 상황에 적합합니다.
- **제스처 방향이 바뀔 때 속도를 끊지 말고 이어 붙입니다.** 반전 시 기존 애니메이션을 새 애니메이션으로 바꾸면 속도가 불연속적으로 바뀌어 “벽에 부딪힌” 듯 느껴집니다. 목표를 바꿀 때 속도를 유지하는 스프링 라이브러리를 쓰면 이런 문제를 피할 수 있습니다. (iOS의 *additive animations*가 기본적으로 하는 일입니다. 웹에서는 현재 속도에서 목표를 다시 설정하는 스프링 라이브러리를 고릅니다.)
- **2D 움직임은 X축과 Y축의 독립된 스프링으로 나눕니다.** X축과 Y축의 속도가 다른데 하나의 2D 거리값에 스프링을 적용하면 동기화가 어긋납니다.

## 4. 애니메이션보다 동작 — 스프링 사용

> “애니메이션을 인터페이스가 미리 정해 놓은 동작이 아니라, 사람과 사물 사이의 대화라고 생각하세요.”

미리 정해진 고정 지속 시간의 애니메이션은 새로운 입력에 반응할 수 없습니다. 스프링은 가능합니다. 입력이 새로 들어오면 목표값만 바뀌고 움직임은 계속 이어집니다. 사용자가 만질 수 있는 동작에는 스프링을 우선 고려합니다.

Apple은 물리학의 세 요소(mass/stiffness/damping)를 디자이너가 쓰기 쉬운 두 매개변수로 바꾸었습니다. 다음 기준으로 생각하세요.

- **감쇠비(damping ratio)** — 오버슈트 정도를 제어합니다. `1.0`은 임계 감쇠로 튀지 않고 부드럽게 안착합니다. `< 1.0`은 목표를 넘어 진동합니다. 값이 낮을수록 더 많이 튑니다.
- **반응 속도(response)** — 초 단위로 목표값에 도달하는 속도를 정합니다. 낮을수록 빠릿합니다. **이 값은 “지속 시간”이 아닙니다.** 스프링에는 고정된 지속 시간이 없습니다. 설정값에 따라 안착 시간이 정해집니다.

**기본값:**

- 대부분의 UI는 **감쇠 `1.0`**(임계 감쇠)에서 시작합니다. 자연스럽고 산만하지 않습니다.
- 바운스(**감쇠 약 `0.8`**)는 **제스처에 관성이 실린 경우**(플릭, 던지기, 드래그 후 놓기)에만 추가합니다. 페이드인한 메뉴가 목표를 넘어 튀면 어색하지만, 손가락으로 튕긴 카드는 자연스럽습니다.

**Apple에서 사용하는 구체적인 값:**

| 상호작용 | 감쇠 | 반응 속도 |
| --- | --- | --- |
| 이동 / 위치 변경(예: PiP) | `1.0` | `0.4` |
| 회전 | `0.8` | `0.4` |
| 드로어 / 시트 | `0.8` | `0.3` |

**웹에서의 대응(Motion / Framer Motion):** `bounce` + `duration` 스프링 API는 Apple의 감쇠와 반응 속도에 가깝게 대응됩니다. 기본적으로 모든 곳에 `damping: 1.0`을 사용하고, 관성이 동반된 물리적 상호작용에만 바운스를 남겨 두는 방식이 안전합니다.

```js
import { animate } from 'motion';

// Critically damped default (no overshoot)
animate(el, { y: 0 }, { type: 'spring', bounce: 0, duration: 0.4 });

// Momentum interaction — a little bounce, only because a flick preceded it
animate(el, { y: target }, { type: 'spring', bounce: 0.2, duration: 0.4 });
```

## 5. 속도 전달 — 드래그와 애니메이션 사이의 연결

제스처가 끝나면 애니메이션은 **손가락의 정확한 속도에서 이어져야** 합니다. 그래야 드래그가 애니메이션으로 바뀌는 순간에 경계가 보이지 않습니다. 이 세부 사항이 “유연함”과 “그럭저럭 괜찮음”을 가장 크게 가릅니다.

포인터를 놓는 순간의 속도를 스프링의 초기 속도로 전달합니다. 일부 스프링 API는 **상대 속도**를 요구합니다. 이 경우 남은 목표 거리로 나눠 정규화합니다.

```
relativeVelocity = gestureVelocity / (targetValue − currentValue)
```

예를 들어 요소가 `y=50`에 있고 목표가 `y=150`이라 남은 거리가 100px이며 손가락이 50px/s로 움직였다면, 초기 스프링 속도는 `50 / 100 = 0.5`입니다. Framer Motion / Motion은 `velocity` 옵션에 px/s 단위의 절대 속도를 받으므로 보통 원래 값을 그대로 전달하면 됩니다.

## 6. 관성 투영 — 제스처가 *향하는 곳*으로 애니메이션

> “작은 입력으로 큰 결과를 만드세요.”

손을 놓은 지점에서 가장 가까운 경계로 바로 붙이지 마세요. 스크롤 감속처럼 속도를 이용해 **멈출 위치를 투영**한 다음, 그 투영 지점에 가장 가까운 목표로 붙입니다. 그래야 플릭으로 요소를 던진 느낌이 납니다.

Apple의 정확한 투영 함수(*Designing Fluid Interfaces* 샘플 코드):

```js
// decelerationRate ≈ 0.998 for normal scroll feel; 0.99 for snappier
function project(initialVelocity /* px/s */, decelerationRate = 0.998) {
  return (initialVelocity / 1000) * decelerationRate / (1 - decelerationRate);
}

const projectedEndpoint = currentPosition + project(releaseVelocity);
const target = nearestSnapPoint(projectedEndpoint);   // choose target from the projection
animateSpringTo(target, { velocity: releaseVelocity }); // then hand off velocity (§5)
```

참고: 물리학 교과서의 `v²/(2·decel)` 공식은 Apple이 사용하는 방식이 아닙니다. 위의 지수 감쇠식을 사용하세요. Vaul이나 Embla 같은 좋은 바텀 시트와 캐러셀에서 표준적으로 사용하는 동작입니다.

## 7. 공간적 일관성 — 대칭 경로와 고정된 시작점

> “무언가가 한 방향으로 사라지면, 그곳에서 다시 나타날 것이라고 기대합니다.”

- **들어오고 나가는 경로를 같게 합니다.** 오른쪽에서 들어온 패널은 오른쪽으로 나가야 합니다. 오른쪽에서 들어와 아래로 나가면 단절되고 혼란스럽습니다.
- **상호작용을 시작한 위치에 연결합니다.** 메뉴, 팝오버, 시트는 이를 연 요소에서 시작해야 합니다. `transform-origin`을 트리거에 맞춰 버튼과 콘텐츠 사이의 공간적 관계를 분명히 합니다. (팝오버를 중앙이 아니라 트리거에서 확대하는 원칙과 같습니다.)
- **되돌릴 수 있는 전환에는 반대 방향의 이징을 짝지어** 나갈 때의 경로와 돌아올 때의 경로를 맞춥니다(양방향에 역 cubic-bezier 제어점을 사용).

## 8. 제스처가 향하는 방향을 미리 보여 주기

사람은 움직임의 궤적을 보고 최종 상태를 예측합니다. 중간 움직임은 요소가 어디로 갈지 암시해야 합니다. Control Center 모듈이 “손가락 방향을 향해 바깥쪽으로 커지는” 것이 한 예입니다. 중간 프레임은 결과를 가리켜야 하며, 목적지까지 무작정 보간하는 데 그치면 안 됩니다.

## 9. 고무줄 효과 — 부드러운 경계

경계에 닿으면 갑자기 멈추지 말고 점점 강해지는 저항을 줍니다. 딱 멈추는 동작은 “얼어붙음”으로 읽히지만, 연속적인 저항은 “반응하지만 더 갈 수는 없음”으로 느껴집니다. 사용자가 경계를 더 넘어 끌수록 감쇠를 높입니다.

```js
// The further past the bound, the less the element follows — real things slow before they stop
function rubberband(overshoot, dimension, constant = 0.55) {
  return (overshoot * dimension * constant) / (dimension + constant * Math.abs(overshoot));
}
```

## 10. 제스처 설계 세부 사항(“느낌” 점검표)

- **탭:** 터치가 *시작되는 순간* 즉시 강조하고, 손을 *뗄 때* 동작을 확정합니다. 대상 주위에 약 10px의 히스테리시스 / 터치 여유 공간을 주고, 드래그해서 벗어났다가 돌아오면 취소할 수 있게 합니다.
- **드래그 / 스와이프:** 방향을 확정하기 전에 작은 이동 임계값(히스테리시스, 약 10px)을 요구하고, 이후에는 1:1로 추적합니다.
- **첫 움직임부터 가능한 제스처를 모두 병렬로 감지한 다음**, 사용자의 의도가 명확해지면 나머지를 확실히 취소합니다. 최종 상태만 알려 주는(`swipeleft` 유형) 인식기는 피합니다. 피드백에 필요한 연속 추적 정보가 사라집니다.
- **제스처 판별에 필요한 지연을 최소화합니다.** 더블 탭 감지는 단일 탭 반응을 불가피하게 늦춥니다. 더블 탭이 실제로 있는 곳에서만 그 비용을 감수합니다.

## 11. 프레임 단위의 부드러움

부드러움은 프레임 속도만이 아니라 *각 프레임에 무엇이 담기는지*에 달려 있습니다.

- 스트로빙을 막으려면 프레임마다의 위치 변화가 지각 임계값 아래로 유지되게 합니다.
- 매우 빠른 움직임에는 선명한 선을 딱 그어 놓기보다 은은한 **모션 블러 / 늘어짐**을 더하면 속도감이 더 잘 전달됩니다.
- `requestAnimationFrame`은 웹의 디스플레이 동기화 시계입니다(Apple은 `CADisplayLink` 사용). 합성에 유리한 `transform`과 `opacity`만 애니메이션하고 움직임이 곧 시작될 요소에는 `will-change`로 힌트를 줍니다.

## 12. 소재와 깊이 — 반투명함으로 위계 표현

Apple은 반투명 소재를 초점은 빼앗지 않으면서 구조를 더하는 떠 있는 기능 레이어로 사용합니다. 웹에서는 `backdrop-filter`로 비슷하게 표현할 수 있습니다.

- **탐색 막대 / 도구 모음 / 시트를 반투명 레이어로 구성합니다**(`backdrop-filter: blur()` + 반투명 배경). 콘텐츠는 아래로 스크롤되게 하고, 일정한 영역을 차지하는 불투명 막대는 피합니다.
- **소재의 무게감으로 위계를 전달합니다.** 어둡고 무거운 소재는 사이드바처럼 구조적인 영역을 나누고, 가벼운 소재는 버튼처럼 상호작용 요소에 시선을 모읍니다. **밝은 반투명 표면을 서로 겹치지 않습니다.** 글자가 읽기 어려워집니다.
- **큰 표면은 더 두껍게 보이게 합니다.** 작은 칩보다 블러를 강하게 하고 그림자를 깊게 줍니다. 배경에 따라 그림자도 조정합니다. 복잡하거나 텍스트가 많은 콘텐츠 위에서는 분리를 위해 더 강하게, 단순한 배경 위에서는 더 약하게 합니다.
- **초점을 위해 어둡게 하고, 흐름을 위해 분리합니다.** 모달 작업에서는 표면에 어두운 스크림을 더해 배경을 뒤로 물립니다. 병렬로 열어 두는 비차단 패널에는 스크림 없이 반투명 표면과 오프셋을 사용해 흐름을 유지합니다. 시트가 겹치면 부모 레이어마다 점진적으로 어둡게 하고 뒤로 물립니다.
- **배경이 바뀌어도 읽히도록 텍스트 대비를 조정합니다.** 흐리거나 반투명한 표면에는 단순한 회색 텍스트를 쓰지 않습니다. 대비를 높이고 글자 굵기를 약간 키우며 자간을 조금 넓힙니다. 색상은 반투명 전경이 아니라 불투명 레이어에 둡니다.
- **딱딱한 구분선 대신 스크롤 가장자리 효과를 사용합니다.** 고정 헤더 아래에 1px 선을 긋는 대신 콘텐츠와 떠 있는 UI가 만나는 지점에만 작은 블러 / 그라데이션 마스크를 둡니다.
- **그냥 페이드하지 말고 소재가 나타나게 합니다.** 유리 / 블러 표면이 들어오고 나갈 때 블러 반경과 스케일을 함께 애니메이션하면 단순히 투명해지는 것이 아니라 실제 소재가 나타나는 느낌을 줍니다.

```css
.toolbar {
  background: rgba(255, 255, 255, 0.6);
  backdrop-filter: blur(20px) saturate(180%);
  border-top: 1px solid rgba(255, 255, 255, 0.4); /* bright top edge = light catching the material */
}
```

## 13. 다중 감각 피드백 — 움직임 + 소리 + 햅틱

감각을 결합하는 세 가지 규칙(*Designing Audio-Haptic Experiences*에서 발췌):

1. **인과성(Causality)** — 무엇이 피드백을 일으켰는지 명확해야 합니다. 실제 원인이 발생한 순간(토글이 바뀌거나 요소가 제자리에 안착할 때)에 실행하고, 물리적 동작에 어울리는 특성을 선택합니다.
2. **조화(Harmony)** — 시각 효과, 소리, 햅틱이 **같은 프레임**에 실행되어야 합니다. 시간 차가 나면 착각이 깨집니다. CSS 트랜지션이 오디오 / 햅틱(Vibration API)보다 늦지 않게 합니다.
3. **유용성(Utility)** — 필요한 곳에만 피드백을 추가합니다. 햅틱과 소리는 성공, 오류, 확정, 안착 같은 중요한 순간에 남겨 둡니다. 피드백이 과하면 사용자는 모든 피드백을 무시하게 됩니다.

## 14. 움직임 줄이기와 접근성

움직임 줄이기는 *피드백을 모두 없애는 것*이 아니라 전정계를 자극하지 않는 더 부드러운 대안을 제공하는 것입니다. 세 가지 독립된 설정에 반응하도록 컴포넌트에 미리 반영합니다.

- **`prefers-reduced-motion: reduce`** — 슬라이드 / 스프링 / 패럴랙스를 짧은 opacity **크로스페이드나 정적 전환**으로 바꿉니다. 탄성이나 오버슈트는 제거합니다. 이해에 도움이 되는 opacity / 색상 변화는 유지합니다.
- **`prefers-reduced-transparency: reduce`** — 반투명 표면을 더 불투명하게 만듭니다. 배경 opacity를 높이고 블러를 제거합니다.
- **`prefers-contrast: more`** — 거의 불투명한 배경과 분명하고 대비가 뚜렷한 테두리를 사용합니다.

추가로 화면 전체를 덮는 움직이는 배경, 느린 반복 진동(약 0.2Hz / 5초에 한 주기), 갑작스러운 밝기 변화(밝은 테마와 어두운 테마 전환을 부드럽게 처리)를 피합니다. 큰 요소가 이동할 때는 반투명하게 만들고 큰 위치 변경 중에는 표면을 페이드아웃했다가 안착한 뒤 다시 나타나게 합니다.

```css
@media (prefers-reduced-motion: reduce) {
  .sheet { transition: opacity 200ms ease; transform: none !important; }
}
@media (prefers-reduced-transparency: reduce) {
  .toolbar { background: white; backdrop-filter: none; }
}
```

## 15. 타이포그래피 — 광학 크기, 자간, 행간

Apple은 글자 크기에 따라 글꼴의 형태도 달라지도록 설계합니다. 웹에서도 같은 세심함이 필요합니다. (*The Details of UI Typography*, WWDC 2020 참고.)

- **자간(letter-spacing)은 글자 크기에 맞춰 정합니다. 한 값을 모든 크기에 쓰지 않습니다.** 큰 디스플레이 글자는 크기가 커질수록 글자 사이가 더 벌어져 보이므로 *음수* 자간이 필요합니다. 작은 글자는 가독성을 위해 약간 *양수* 자간이 좋습니다. 고정된 `letter-spacing`은 어느 한쪽에서는 틀립니다. 제목은 좁히고 본문은 `0`에 가깝게 둡니다.
- **행간(line-height)은 크기가 커질수록 줄입니다.** 큰 제목은 촘촘하게, 본문은 여유 있게 배치합니다. 위아래로 길게 뻗는 글자가 많은 문자 체계는 행간을 늘리고, 정보가 빽빽한 UI는 줄입니다.
- **크기만으로가 아니라 굵기 + 크기 + 행간을 한 세트로 위계를 만듭니다.** 공간을 더 차지하지 않으면서 존재감을 더하려면 굵기를 사용합니다.
- **사용자의 텍스트 크기 설정(Dynamic Type)을 존중합니다.** 고정 px이 아니라 `rem`/`em`으로 여백과 레이아웃을 텍스트 크기에 맞춰 조정해 큰 글꼴에서도 레이아웃이 깨지지 않게 합니다.
- **사용자 지정 글꼴보다 플랫폼 시스템 글꼴을 먼저 고려합니다.** 광학 크기, 자간 표, 가독성 조정이 이미 제공됩니다. 바꿔야 할 이유가 있을 때만 다른 글꼴을 사용합니다.

```css
:root { font: 100%/1.5 system-ui, sans-serif; } /* body: system font, comfortable leading */

.display {
  font-size: clamp(2rem, 5vw, 4rem);
  line-height: 1.05;        /* tight leading for large text */
  letter-spacing: -0.02em;  /* negative tracking as it grows */
  font-optical-sizing: auto;
}
```

## 16. 디자인 기반 — 여덟 가지 원칙

위의 움직임과 구현 원칙은 Apple의 여덟 가지 디자인 원칙(*Principles of Great Design*, WWDC 2026)을 따릅니다. 판단을 설명할 때 이 원칙의 이름을 사용하세요.

1. **목적(Purpose).** 의도를 갖고 만들고, 무엇을 만들지 않을지도 정합니다. 모든 기능은 사용자의 시간, 주의, 신뢰를 요구합니다. 효과가 있을 때만 그 자원을 사용합니다.
2. **주도권(Agency).** 사용자가 통제권을 갖도록 선택지를 제공하고 한 가지 경로를 강요하지 않습니다. 실수는 쉽게 되돌릴 수 있게 합니다. 정말 파괴적이고 되돌릴 수 없는 동작에만 확인 대화상자를 씁니다(절제해서 사용합니다. 남용하면 사용자는 확인을 무심코 누르게 됩니다).
3. **책임(Responsibility).** 사용자에게 이익이 되는 방향으로 동작합니다. 개인정보는 필요한 것만, 적절한 순간에, 투명하게 요청합니다. 안전을 위해 특히 AI의 오용이나 피해 가능성을 예상합니다(알레르기를 고려하는 레시피 앱은 해로운 재료를 제안하면 안 됩니다). 미리보기, 확인, 고지를 추가하고 위험이 가치를 넘어서는 기능은 제거합니다.
4. **익숙함(Familiarity).** 사용자가 이미 아는 것 위에 설계합니다. 너무 문자 그대로도 추상적이지도 않은 비유를 씁니다(휴지통은 삭제를 의미). 비유에 맞는 물리적 동작을 따릅니다. 같은 모양의 요소는 같은 위치에서 같은 방식으로 동작해야 사용자가 다음 결과를 예측할 수 있습니다(macOS의 닫기 버튼은 항상 왼쪽 위). 더 나은 이유를 입증할 수 있을 때만 익숙한 패턴을 깨고, 가정하지 말고 검증합니다.
5. **유연성(Flexibility).** 다양한 상황, 기기, 능력에 맞게 설계합니다. 플랫폼에 맞추고(iPhone은 빠른 터치, 데스크톱은 정밀한 포인터로 깊이 있는 작업), 맥락에 맞게 조정합니다. 나이, 언어, 숙련도, 접근성을 포괄합니다. 하나의 레이아웃이 모두에게 맞지 않으면 사용자가 조정할 수 있게 합니다(컨트롤 재배치, 사용하지 않는 기능 숨기기).
6. **단순성 — 미니멀리즘이 아님(Simplicity — not minimalism).** 불필요한 것을 덜어 핵심 목적을 돋보이게 합니다. 모든 것을 한곳에 숨기는 것은 미니멀해 보일 뿐 단순하지 않습니다. 평이한 언어와 적은 단계로 간결하게 쓰고, 순서·여백·대비로 위계를 만들어 중요한 정보가 즉시 보이게 합니다. 모든 요소는 자리를 차지할 이유가 있어야 합니다. 남은 시간을 표시하는 동영상 스크러버처럼 맥락을 추가하는 것이 오히려 단순하게 만들 때도 있습니다. 흔한 경로를 먼저 보여 주고 고급 설정은 한 단계 깊이 둡니다.
7. **완성도(Craft).** 세부 사항에 대한 타협 없는 관심이 신뢰를 만듭니다. 아름다운 타이포그래피, 밝은 테마와 어두운 테마에 맞는 색상, 분명한 아이콘, 즉각적이고 자연스러운 피드백을 주는 반응성 애니메이션을 구현합니다. 값은 임의가 아닙니다. 모든 간격, 타이밍, 정렬을 설명할 수 있어야 합니다. 스크롤 끊김, 어긋난 아이콘, 회전할 때 깨지는 레이아웃은 부주의로 보입니다. 완성도에는 반복 개선과 지속성이 필요합니다. 기능과 하드웨어가 바뀌면 디자인도 계속 발전시킵니다.
8. **즐거움(Delight).** 나머지 일곱 가지를 제대로 구현한 결과이지, 위에 색종이 효과를 얹는 일이 아닙니다. 사용자가 느끼기를 바라는 감정(차분함, 자신감, 설렘)을 정하고 모든 결정에 반영합니다.

이를 뒷받침하는 실무 규칙:

- **피드백은 네 종류입니다.** 상태, 완료, 경고, 오류. 중요한 동작은 확인하고, 진행 중인 상태를 보여 주고, 문제가 생기기 전에 경고하며, 제출 시점이 아니라 입력 옆에서 즉시 검증합니다.
- **길 찾기.** 모든 화면은 다음 질문에 답해야 합니다. 지금 어디에 있는가? 어디로 갈 수 있는가? 그곳에는 무엇이 있는가? 어떻게 나갈 수 있는가? 사용자를 가두지 않습니다.
- **그룹화와 대응 관계.** 가까이 있는 요소는 관련 있다고 느껴집니다. 컨트롤은 영향을 주는 대상 가까이에 두고, 컨트롤 배치는 바뀌는 대상의 구조를 반영합니다. 컨트롤을 설명하는 레이블이 필요하다면 대응 관계가 약한 것입니다.
- **안전하고 모호한 이름보다 직접적이고 구체적인 레이블을 씁니다.** 탐색 항목에는 “홈” 같은 포괄적인 이름 대신 “진행 상황”, “라이브러리”처럼 내용을 구체적으로 나타내는 이름을 붙입니다. 구체성이 예측 가능성을 만듭니다.

## 17. 프로세스

- **상호작용 가능한 프로토타입을 만듭니다. 정적인 디자인 백만 장보다 인터랙티브 데모 하나가 더 낫습니다.** 만들고 직접 조작하면서 인터페이스를 발견할 수 있습니다. 작동하는 프로토타입은 최종 구현이 평범한 수준에 머무르지 않도록 구체적인 기준도 제공합니다.
- **상호작용과 시각 디자인을 함께 설계합니다.** “어디서 하나가 끝나고 다른 하나가 시작되는지 알 수 없어야 합니다.” 움직임은 화면을 다 그린 뒤 추가하는 레이어가 아닙니다.
- **실제 상황에서 실제 사용자에게 테스트하고, 새로운 관점으로 움직임을 검토합니다.** 느린 재생이나 프레임 단위 검토로 정상 속도에서는 놓치는 문제를 찾습니다.

## 빠른 참조

| 필요 | 기법 | 구체적인 값 |
| --- | --- | --- |
| 기본 UI 스프링 | 임계 감쇠, 오버슈트 없음 | `damping 1.0`, `response 0.3–0.4` |
| 관성 / 플릭 스프링 | 감쇠 부족, 가벼운 바운스 | `damping ~0.8`, `response 0.3–0.4` |
| 제스처에서 스프링으로 속도 전달 | 놓는 순간의 속도를 전달 | 정규화할 때 `gestureVelocity / (target − current)` |
| 플릭이 도착할 지점 | 관성을 투영 | `current + (v/1000)·d/(1−d)`, `d ≈ 0.998` |
