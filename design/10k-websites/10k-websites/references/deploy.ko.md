# 배포: 승인된 사이트에서 검증된 출시까지 Hostinger로 배포

출시할 때 읽는다. 사용자의 주소와 배포 승인은 턴이 바뀌어도 유지한다. 이미 승인된 출시는 다시 디자인 검토, 업그레이드 제안, 필수 새 채팅 없이 계속한다.

## 계정, 비용, 연결

OpenArt 생성, GPT 사용, 호스팅은 각각 별도다. GPT와 미디어 선택은 [production.md](production.md)를 따른다. Full throttle이라고 해서 과도하게 큰 호스팅 플랜이 자동으로 필요한 것은 아니다. 구매를 추천하기 전에 현재의 Hostinger 플랜 기능, 가격, 갱신 조건, 도메인/메일함 자격, 사이트 한도를 확인한다. 단순한 사이트에는 정적 파일 제공이 필요하다. 실제 인박스에는 PHP와 비공개 쓰기 가능 저장소도 필요하다. 맞는 기존 플랜이 있으면 그것을 쓴다. SKILL.md에 명시된 크리에이터 링크 공개 범위를 넘어서, 고정된 무료 메일함 개수나 검증되지 않은 할인을 약속하지 않는다.

Hostinger가 이미 응답하면 설정을 건너뛴다. 그렇지 않으면 앱이 노출하는 현재의 커넥터/플러그인 설치 및 인증 경로를 쓴다. 지원되는 설정 단계는 직접 실행한다. 사용자는 로그인하고 접근을 승인한다. 실제 설치 상태에서 필요한 경우에만 재시작을 요청한다. 읽기 호출이 계정 데이터를 반환하는지 확인한다. 액세스 토큰을 절대 출력하지 않고, 관련 없는 앱 설정을 편집하지 않는다. 사용자가 실제로 호스팅이 필요할 때만 SKILL.md의 가입 링크와 공개 문구를 사용한다.

## 좁게 탐색하고, 실제 스키마를 따른다

현재 커넥터는 수백 개의 직접 도구 대신 `search`, `execute`, `multi_execute`만 노출할 수 있다. 필요한 작업만 찾고, 반환된 입력 스키마를 확인한다. 예전 작업 이름은 힌트일 뿐 권위 있는 API가 아니다. 전체 목록을 출력하지 않는다.

일반적인 작업 목적과 최근 이름(사용 전에 확인한다):

| 목적 | 최근 작업 |
|---|---|
| 사이트와 기존 플랜 목록 | `hosting_websites_list`, search가 반환하는 호스팅 주문 목록 |
| 사용 가능한 도메인 확인 | search가 반환하는 도메인 포트폴리오 목록 |
| 무료 주소 생성 | `hosting_domains_generate-free-subdomain` |
| 선택한 플랜에 생성 | domain과 order_id를 넣은 `hosting_websites_create` |
| 웹사이트 설정 대기 | 도메인에 대한 `hosting_websites_list-setups` |
| 미리 빌드된 파일 업로드 | domain과 archivePath를 넣은 `hosting_deploy-static-website` |

변경 전에 계정/플랜과 정확한 대상을 확인한다. 대기열 등록 또는 수락 응답은 완료가 아니다. 업로드 전에 제한된 대기와 백오프로 설정 상태를 추적한다. 시간이 걸린다고 생성/배포 요청을 반복하지 않는다. 진행 메시지는 짧게 유지한다. 기존의 관련 없는 사이트를 덮어쓰지 않고, 사용 가능한 도메인이 이 브랜드의 것이라고 추측하지 않는다.

## 주소와 배포 패키지

사용자가 이미 고른 도메인/무료 주소를 쓴다. 그렇지 않으면 계정을 확인한 뒤 간단한 선택지를 제시한다. 무료 `*.hostingersite.com` 주소는 자격이 되는 호스팅에서 미리보기와 출시에 유효하다. 하지만 구매한 도메인이나 메일함을 뜻하지는 않는다. 실제 자격을 확인한다. 구매는 사용자가 직접 한다.

실제 주소가 생기면 canonical, OG, 구조화된 데이터, 백엔드 사이트 URL을 패치한다. 정적 PHP 미리보기를 시작하지 않고 검색용 파일을 생성한다.

```sh
node .10k/tools/report.mjs site review --seo https://their-address --seo-only
```

패치에는 파일 도구나 명시적인 UTF-8 스크립트를 쓴다. 재배포 전에 변경된 CSS/JS의 URL 버전을 올려, 캐시 때문에 업데이트가 가려지지 않게 한다.

`site/`의 내용물을 아카이브한다. `index.html`이 최상위에 있고, 필요한 모든 자산이 그 옆에 있어야 한다. 현재의 배포 도구가 요구하는 아카이브 이름/스키마를 따른다(예: `site_YYYYMMDD_HHMMSS.zip`). 숨김 `.htaccess` 파일을 포함해 아카이브를 검사한다. 실제 인박스가 있다면 `api/`, 보호된 설정, `admin/`, `data/.htaccess`, `forms.js`를 포함한다. 저장된 문의, 로그, 이 백엔드와 무관한 자격 증명, 소스 마스터, `.10k/`, node_modules, 검토 파일, 아카이브 자체는 절대 패키징하지 않는다. 재배포할 때 기존 백엔드 시크릿/설정을 보존해서 비공개 저장소와 비밀번호가 계속 작동하게 한다. 자격 증명은 버전 관리 밖에 둔다.

이 정적 사이트와 PHP 파일에는 커넥터의 미리 빌드된/정적 배포 작업을 쓰고, 스키마가 지원할 때만 쓴다. Node 빌드는 필요 없다. 정확한 대상, 아카이브 해시, 배포 응답, 이후 검증된 버전을 기록한다. 업로드 성공을 곧 라이브 사이트로 취급하지 말고, 완료될 때까지 기다린다.

## 배포 응답과 별개로 독립적으로 검증한다

- 홈페이지가 HTTPS로 로드되고, 기대한 내용/버전이 보인다.
- 의도한 데스크톱 및 세로 방향 미디어가 정상적으로 반환된다. 휴대폰은 큰 파일 두 개를 모두 받지 않고 의도한 변형을 요청한다.
- 실제 브라우저에서 앞으로/뒤로 스크럽, 읽을 수 있는 자막, 내비게이션, 커스텀 상호작용, 동작 감소(reduced motion), 미디어 대체 화면이 콘솔이나 리소스 오류 없이 작동한다.
- 실제 인박스가 있다면, health가 쓰기 가능한 비공개 저장소를 보고하고, config/data URL이 소스나 데이터를 노출하지 않으며, 인증되지 않은 관리자 화면이 설정/로그인 화면인지 확인한다. Health는 이메일 전달을 입증하지 않는다.
- [launch.md](launch.md)의 라이브 휴대폰 및 데스크톱 보고서를 실행한다. 별도로 라이브 `robots.txt`, 응답의 noindex 헤더, 페이지의 robots 태그를 확인한다. Hostinger는 임시 주소에서 업로드된 robots 설정을 덮어쓸 수 있다. Lighthouse SEO 100점은 Google 색인 가능성을 입증하지 않는다. 실제 제약을 그대로 설명하되, 사용자가 고른 미리보기 주소를 실패한 출시로 취급하지 않는다.

새 주소는 DNS/HTTPS 설정에 시간이 걸릴 수 있다. 원인을 확인하고 백오프로 기다린다. 브라우저의 인증서 보호를 우회하지 않는다. 불확실성은 솔직하게 보고한다.

## 측정, 제시, 인계

실제 HTML과 자산, 각 영상의 크기와 도착 시간을 측정한다. HTML 가져오기만으로는 전체 페이지 무게나 실제 사용자 속도를 알 수 없다. 사이트에는 인박스를 위한 PHP가 포함될 수 있으므로, 서버 코드가 없다고 주장하지 않는다. 히어로 엔진이 영상을 Blob으로 가져올 수도 있다. 구현을 검증하기 전에는 이를 네트워크 스트리밍이라고 설명하지 않는다. Lighthouse 랩 점수와 로컬 요청 시간은 이번 실행의 증거일 뿐, 모든 연결에 대한 보장이 아니다.

검증된 공개 HTTPS URL을 직접 열고, 이를 라이브 사이트로 표시한다. 로컬 미리보기와 보고서 링크는 구분해서 표시한다. 실제 브라우저가 사용자의 수락 워크플로에 포함되어 있으면, 가능한 경우 그 브라우저에서 이 주소를 검증한다. 로컬 HTML 파일이나 내장 미리보기가 배포를 대신한다고 가정하지 않는다. 휴대폰 보고서는 따로 연다. 사용자에게 실제 휴대폰에서 확인해 달라고 요청한다. 일반 스크롤, 빠른 플릭, 역방향 스크롤, 영상의 시작과 끝 장면, CTA를 확인하게 한다. 실제 기기 확인은 에뮬레이션과 별도로 기록한다.

실제 인박스의 경우 [backend.md](backend.md)의 소유자 활성화와 전달 단계를 따로 마친다. 라이브 사이트를 넘기면서, 남은 소유자 전용 작업을 분명히 밝힌다. 이후 승인된 업데이트는 같은 대상을 쓰고, 승인된 자산과 백엔드 상태를 보존하고, 버전을 올리고, 재배포한 뒤, 바뀐 라이브 내용을 검증한다.
