# 이미지 사용

이미지는 생성된 페이지가 가장 뻔하게 포기하는 부분입니다: 회색 상자, 네모 안 아이콘, 가짜 대시보드, 추상 덩어리. 이 문서는 어떤 이미지가 필요한지, 실제 이미지를 어디서 찾을지, 어떻게 자르고 배치할지, 이미지가 없을 때 무엇을 할지 정합니다.

## 1. 연구 측정값

- 조사한 사이트 중 60%는 첫 화면의 절반 이상을 미디어 하나가 차지하고, 절반가량은 거의 전체를 채웁니다. 상위 점수 사이트는 각각 68%, 56%였고 하위 사이트는 48%, 39%였습니다.
- Hero 중 미디어가 전혀 없는 곳은 15%뿐이며, 이런 경우는 의도적인 타이포그래피 표현입니다.
- 사이트의 73%에서 미디어 모서리는 각졌습니다. 둥근 경우에는 보통 약 12px 반경을 모든 이미지에 동일하게 적용합니다.
- 상위 점수 페이지에는 훨씬 더 많은 이미지가 있습니다 (중앙값 37장, 하위 페이지 5장). 강한 사이트는 보여주고 약한 사이트는 설명만 합니다.
- 패널이 분류한 미디어 유형: 혼합 32%, 사진 14%, 생성형 / WebGL 장면 13%, 실제 제품 인터페이스 12%, 3D 렌더 11%, 일러스트 9%, 영상 6%, 타이포그래피만 사용 3%.
- 패널 점수가 6.8 미만인 54개 사이트 중 13개에서 가독성 (복잡한 이미지에 묻힌 텍스트 또는 대비 부족)이 약점으로 지적됐습니다.
- 2026년 10월 Awwwards Sites of the Day 91개 연구 (12절)에서 페이지당 이미지 중앙값은 7장 (상위 8장, 최하 2장)이며 사이트의 42%에 영상이 있었습니다 (상위 절반, 최하 16곳 중 1곳).
- 이미지는 화면을 통째로 차지하기도 합니다: 스크롤 화면의 42%는 이미지가 없고 19%는 화면의 90% 이상을 이미지가 차지합니다.
- 이미지 94%의 모서리는 각졌고 일반적인 사이트에서는 비율 두 가지가 전체 이미지의 4분의 3을 차지합니다.

## 2. 사용할 수 있는 이미지 결정

우선순위:

1. **프로젝트 자체 이미지.** 제품 사진, 장소, 사람, 작업물. 실제와 평범한 사진이 다른 무언가의 아름다운 사진보다 낫습니다. 어떤 것이 있는지 묻고 저장소를 살펴봅니다.
2. **현재 세션에서 이미지 도구로 만들 수 있는 이미지.** 사진가의 촬영 의뢰서처럼 주제, 각도, 빛, 배경, crop 비율, “텍스트 없음”을 포함해 프롬프트를 씁니다. 먼저 hero 이미지를 만들고 나머지도 그 빛과 일치시킵니다.
3. **공개 컬렉션에서 찾은 주제 세계의 실제 이미지** (3절). 아카이브, 박물관, 사진가가 크레딧 표기를 조건으로 누구나 쓸 수 있는 수백만 장의 이미지를 공개했습니다. 고객의 도시와 거리 옛 엽서, 동네 지도, 재료, 거래의 판화, 관련 박물관 유물 등이 있습니다. 정직하게 사용할 이미지가 있다면 같은 것을 그린 그림보다 낫습니다: 실제이며 페이지 예산의 그림보다 세밀하고 역사를 담고 있습니다. 정직한 이미지란 고객의 제품, 객실, 음식, 사람, 팀의 것이라고 오해할 수 없는 이미지를 말합니다.
4. **정직한 이미지가 없는 대상은 주제 자체를 코드로 그립니다** (8절). 제품에 고유한 물체를 평면 도형으로, 장소의 타일과 창문, 거리 지도, 도구가 만드는 문서, 소프트웨어 인터페이스 등을 그립니다. 테스트에서 주제를 세심하게 그린 페이지는 관련 없는 사진을 빌린 페이지보다 항상 좋았고, 이미지를 전혀 보여주지 않은 페이지보다도 좋았습니다.
5. **방향표에서 추첨된 사진.** 장소, 빛, 질감, 날씨를 담은 실제 사진을 씁니다. 정직하게 일반 이미지가 맞는 경우에만 사용합니다 (바닷가 집에 열린 바다, 고요한 휴양지에 안개). 특정 제품, 음식, 객실, 사람, 화면을 대신할 수 없습니다. 식당 페이지에 안개 낀 고속도로를 쓰면 즉시 스톡 이미지처럼 읽히고 심사위원도 알아봅니다.
6. **타이포그래피와 색상만 사용** (의도된 디자인일 때, 9절).

draw.mjs에 실제 상황을 --have로 전달합니다. 제품 사진도 이미지 도구도 없으면 product-photo를 넘기지 않습니다. 그래야 해당 물체를 보여줘야 하는 방향을 피합니다. 공개 컬렉션에서 찾은 사진은 프로젝트 자체 이미지가 아니므로 photography로 지정하지 않습니다.

## 3. 공개 컬렉션의 실제 이미지

scripts/assets.mjs는 키 없이 공개 소스 네 곳을 검색하고 각 결과의 직접 이미지 URL, 출처 페이지, 크기, 제작자, 라이선스, 크레딧 문구를 출력합니다.

- **Openverse**: Flickr, Wikimedia Commons, 박물관, 도서관을 한데 모은 인덱스.
- **Wikimedia Commons**: 아카이브 사진, 옛 지도, 판화와 책 스캔, 현재 모습의 장소.
- **Art Institute of Chicago** 및 **Metropolitan Museum of Art**: 퍼블릭 도메인 회화, 판화, 드로잉, 사진, 직물, 사물의 대형 스캔.

```bash
node <skill>/scripts/assets.mjs "ghent postcard"
node <skill>/scripts/assets.mjs "fig" --source museums --orientation portrait
node <skill>/scripts/assets.mjs "basalt texture" --min-width 2400 --source openverse,commons
node <skill>/scripts/assets.mjs --get commons:36649959,met:707892     # 다운로드 후 크레딧 기록
node <skill>/scripts/assets.mjs --credits                             # footer 문구와 보고서 목록 출력
```

기본 설정은 상업 이용이 가능한 라이선스만 (CC0, 퍼블릭 도메인, CC BY, CC BY-SA) 유지하고 폭 1000px 이상의 이미지로 제한하며 출력하는 각 이미지가 실제로 열리는지 확인합니다. --license pd는 크레딧이 필요 없는 이미지만 남기고 --orientation, --min-width, --limit은 결과를 좁히며 --source는 검색 출처를 고르고 --json은 원시 결과를 출력합니다. 각 결과에는 --get에서 사용하는 ref (예: commons:36649959)가 포함됩니다.

**무엇을 검색할지.** 카테고리가 아니라 SKILL.md 1단계의 주제 목록에서 시작합니다. “빵집”은 다른 빵집 이미지를 찾습니다. 주제의 세계를 구체적으로 검색합니다.

- **장소**: 도시, 거리, 항구, 계곡의 옛 엽서와 사진 (“ghent postcard”, “rotterdam harbour 1920”), 현재 모습 (“gent korenmarkt”).
- **지도**: 거리 도면, 만의 해도, 계곡 지질도 (“ghent old map”, “nautical chart lisbon”).
- **재료**: 표면으로 읽힐 만큼 가까운 이미지. 부두의 돌, 참나무 결, 유약, 타일 (“azulejo tiles”, “basalt cobblestones”, “oak grain”).
- **업계의 역사**: 옛 도구, 판화와 무역 카탈로그의 공예, 특허 도면 (“bread oven engraving”, “potter's wheel”, “bicycle patent drawing”).
- **같은 종류의 박물관 유물**: --source museums 사용. 예: 커피 세트를 만드는 스튜디오에는 1810년경 커피 세트, 서핑 학교에는 파도 목판화, 무화과 농원에는 무화과를 그린 도자기 접시.
- **과학 이미지**: 식물·동물 도판 (“botanical engraving fig”), 별자리 지도, 현미경 사진, 해안 위성 사진, 지질 단면.

장소의 원래 이름으로 검색합니다 (blue tile 대신 azulejo, market square 대신 Korenmarkt). 매체 (postcard, engraving, old map, lithograph, aerial photograph)나 연도를 더하고 아이디어마다 검색어 두세 개를 시도합니다. 박물관 소스는 단어 한두 개 (“fig”, “harbour”, “teapot”)로 검색할 때 가장 잘 맞습니다.

**좋은 결과의 조건.**

- 이 주제 세계에 속하며 가장 가까운 경쟁자 페이지에는 어울리지 않음.
- 필요한 crop에서도 읽힘. 결정 전에 직접 봅니다: --get으로 다운로드한 뒤 파일을 엽니다. 제목만으로는 이미지가 아닙니다.
- 충분한 해상도: 블리드 전체 이미지라면 표시 크기의 두 배 너비 (스크립트는 사용 가능한 최대 크기를 출력). Flickr 사진이 1024px이면 페이지 절반 너비 정도까지만 사용합니다.
- 페이지의 다른 이미지와 하나의 계열을 이룸: 전부 판화, 한 시대의 사진, 같은 빛에서 찍은 표면 접사 등. 1900년 엽서, 현대 스톡 사진, 식물 도판을 나란히 두면 스크랩북처럼 보입니다.
- 워터마크, 이미지에 박힌 글자나 로고, crop할 수 없는 프레임 / 스캐너 가장자리가 없고 고객 직원이나 고객으로 오해할 수 있는 살아 있는 인물이 없음.

**창의적으로 사용합니다.** 발견한 이미지는 장식이 아니라 재료입니다.

- **아카이브 사진 하나를 hero로 블리드**: 100년 전 거리 사진 뒤에 오늘 그 자리에 있는 가게 이름을 두고 캡션에 연도를 씁니다.
- **박물관 판화를 확대해 선이 질감이 되게 함**: 타이트하게 crop하고 페이지의 유일한 모티프로 여러 크기에서 다시 씁니다 (hero에는 무화과 도판 전체, 메뉴 옆에는 잎 하나).
- **판화나 지도를 흰 종이에 놓고 페이지 색면 위에 mix-blend-mode: multiply 적용**해 잉크가 바탕에 찍힌 듯 보이게 합니다 (6절).
- **실제 거리 지도를 연락처 섹션으로 사용**: 문 위치, 북쪽, 축척을 원본에서 가져옵니다.
- **재료 접사로 화면 전체 채우기**: 영업시간 뒤에 부두의 돌 표면을 둡니다.
- **옛 엽서나 도판을 갤러리로 구성**: 크기와 처리를 통일합니다.

처리는 6절의 방식 안에서 선택합니다: 원본 그대로, 전체 이미지 세트를 흑백 처리, 또는 색면 위에 multiply.

**정직하게 사용합니다.**

- **발견한 사진은 고객의 사진이 아닙니다.** 고객의 도시, 재료, 역사, 제작 유형을 보여줄 수 있지만 고객의 제품, 객실, 음식, 사람, 팀, 고객을 대신할 수 없습니다. 고객의 것이라고 생각할 수 있다면 (빵집 카운터, 파스타 접시, 미소 짓는 바리스타, 객실) 사용하지 않습니다.
- **캡션이 도움이 되면 출처에 따라 작성합니다**: 무엇이며 언제인지 아카이브 설명대로 적습니다 (“Gand, unloading a steamer, 1905”). 고객과 연결하는 캡션은 쓰지 않습니다.
- **모든 이미지의 출처와 크레딧을 기록합니다.** --get은 각 이미지의 출처, 제작자, 라이선스, 페이지를 assets/credits.json에 기록합니다. CC BY와 CC BY-SA는 제목, 제작자, 출처 링크, 라이선스 링크가 포함된 크레딧이 필요합니다. --credits는 footer에 붙일 HTML 한 줄을 출력합니다 (10절). 퍼블릭 도메인 이미지는 크레딧 의무가 없어도 표기합니다.
- **라이선스를 존중합니다.** CC BY-SA: 색상 변경이나 다른 이미지와 조합한 변경본은 동일한 라이선스로 공유해야 합니다. 비상업 (NC)과 변경 금지 (ND) 라이선스는 고객 사이트에 쓸 수 없으므로 사용자가 요청하지 않으면 스크립트가 제외합니다. note를 읽습니다. 일부 이미지에는 초상권이나 상표가 포함될 수 있고, 미국에서만 퍼블릭 도메인이거나 라이선스 대신 아카이브 고지문만 있을 수 있습니다.
- **핫링크하지 말고 다운로드합니다.** 사용할 이미지는 프로젝트에 저장합니다. --get은 assets/에 폭 1920px로 저장합니다 (화면 절반에 표시할 때 --width 1280, 출처가 허용하면 아주 큰 hero에는 --width 3840). 페이지는 오프라인에서도 작동하고 아카이브가 파일을 옮겨도 깨지지 않으며 다른 서버에서 불러오지 않습니다. 기본 허용 라이선스는 모두 복사를 허용합니다.
- **보고서에 모두 기록합니다**: 파일, 제목, 제작자, 라이선스, 출처 페이지, 크레딧 위치. --credits가 목록도 출력합니다.

아이디어마다 정직한 검색어 두세 개를 시도했는데 맞는 것이 없으면 직접 그립니다 (8절). 주제를 위해 그린 그림은 그냥 가까운 이미지보다 낫습니다. 네트워크가 없어 검색 소스에 도달하지 못하면 직접 그리고 공개 컬렉션을 검색할 수 없었다고 보고합니다. 움직이는 이미지는 같은 스크립트에서 --video로 실제 영상을 검색합니다 (11절).

## 4. 추첨된 사진

- 방향표에는 주제와 빛을 통일한 한 세트의 사진 여덟 장이 포함됩니다. 세 장에서 여섯 장을 사용합니다.
- 각 줄은 차분한 여백이 있는 위치를 표시합니다. 여기에 텍스트를 두거나 이미지 위 텍스트를 피합니다.
- 같은 세트나 다른 세트에서 추가하려면 node scripts/draw.mjs --photos list, --photos <set>, 또는 설명 검색에 --photos "fog coast"를 사용합니다.
- URL 형식은 https://picsum.photos/id/<id>/<width>/<height>입니다. 선명하게 보이도록 실제 렌더 크기의 CSS 2배 픽셀을 요청하며 약 2400px 폭을 상한으로 둡니다. 흑백은 ?grayscale을 추가합니다.
- Unsplash 라이선스에 따라 Lorem Picsum이 제공하는 사진입니다. 사용한 id를 보고서에 기록합니다. 프로젝트 자체 이미지로 교체해야 하는 임시 자료입니다.

## 5. 자르기와 배치

- **소수의 화면비를 정하고 끝까지 유지합니다**: 인물은 4:5, 풍경은 16:10, 디테일은 1:1 등. 무작위 비율은 스톡 이미지 모음처럼 보입니다.
- **크게 사용합니다.** 사진을 전체 너비로 쓰거나 화면 절반 너비와 전체 높이로 쓰면 존재감이 있습니다. 작은 사진 여섯 장을 격자에 넣으면 존재감이 없습니다. 사진이 좋으면 공간을 주고, 좋지 않으면 제외합니다.
- **의도를 가지고 crop합니다.** object-fit: cover에 이미지별 object-position을 설정해 주제가 구도에 맞는 위치 (중앙에서 벗어난 지점, 삼분할선, 텍스트 반대편)에 오게 합니다.
- **이미지를 가장자리에 닿게 둡니다.** 블리드하거나 한쪽 가장자리 밖으로 뻗으면 디자인된 느낌입니다. 사방 여백이 같은 떠 있는 이미지는 기본값처럼 보입니다.
- **겹침은 의도적으로 절제해서 사용합니다**: 헤드라인 마지막 줄이 사진 위쪽을 살짝 넘거나 작은 이미지가 큰 이미지를 고정된 40–80px만큼 덮는 정도. 화면당 최대 한 번.
- 방향이나 주 모티프의 형태가 요구하지 않으면 모서리는 각지게 합니다. 둥글게 할 때는 모든 이미지에 반경 하나를 통일합니다.
- **프레임 금지**: 테두리, 그림자, 기기 mockup, 이미지 주위 브라우저 chrome을 두지 않습니다.
- **캡션**은 작고 흐린 잉크색으로 한 줄만, 이미지 모서리에 왼쪽 정렬해 둡니다. 대부분의 이미지에는 캡션이 필요 없습니다.
- 이미지별 페이지 위치와 크기, 휴대폰에서의 표현은 12절 참고.

## 6. 처리 방식

페이지 전체에 같은 처리 하나를 적용합니다.

- **원본 그대로.** 기본값입니다. 빛이 이미 잘 어울리는 이미지를 선택합니다.
- **흑백.** filter: grayscale(1) contrast(1.05) 또는 URL에 ?grayscale. 혼합된 세트를 즉시 통일하며 에디토리얼 / 타이포그래피 방향에 잘 맞습니다. 일부만 흑백으로 하지 말고 모든 이미지에 적용하거나 전혀 적용하지 않습니다.
- **색면 위 multiply.** 밝고 평평한 바탕에서 mix-blend-mode: multiply를 사용하면 흰 스튜디오 배경이 사라져 제품이 색면에 직접 놓인 것처럼 보입니다.
- **다크 페이지용 어둡게 처리.** filter: brightness(0.85) contrast(1.05)로 이미지 가장자리가 바탕에 이어지게 합니다.

허용되지 않는 처리: 사진 위 색상 워시, 듀오톤 오버레이, blur, 그레인 오버레이, 비네트, 그림자와 함께 기울인 “폴라로이드” 프레임.

사진 위에 텍스트를 놓을 때는 텍스트 영역에만 중립 scrim을 씁니다: 검정색 40–55%의 평면 블록 또는 아래쪽 1/3에 55% 검정에서 투명으로 이어지는 페이드. 색상 오버레이는 금지합니다.

## 7. 소프트웨어 화면 보여주기

- 축소 스크린샷이나 장식 mockup 대신 실제 크기의 HTML로 인터페이스 조각을 만들고 그럴듯한 콘텐츠를 넣습니다. 요점을 보여주는 부분 하나를 crop합니다: 컨트롤 하나, 행 하나, 패널 하나.
- 그럴듯한 콘텐츠란 실제 라벨, 합계가 맞는 수치, hover 또는 선택 상태 하나, 정확한 정렬을 의미합니다. 텍스트 대신 회색 막대를 놓는 것보다 이미지가 없는 편이 낫습니다.
- 조각을 페이지에 바로 놓거나 단색 무대 위에 놓습니다. 노트북 / 휴대폰 프레임을 씌우지 않습니다. 제품이 휴대폰 앱일 때만 단순한 둥근 직사각형 프레임을 허용합니다.
- 조각 내부에는 제품 자체의 인터페이스 관례를 적용합니다 (작은 반경, 1px 컨트롤 테두리, 열린 메뉴의 그림자 등). 조각 루트 요소에 data-ui 속성을 둡니다. 그러면 inspector와 linter는 내부를 건드리지 않고 페이지 주변에는 하우스 규칙을 적용합니다. data-ui는 crop한 조각에만 사용하며 제목이나 전체 섹션을 감싸면 실패입니다. linter가 페이지 스타일과 구분하도록 조각 CSS는 [data-ui] 선택자 아래에 씁니다 ([data-ui] .row { … }).
- 사용자가 실제 스크린샷을 제공하면 적어도 한 번은 크고 crop 없이 보여줍니다.

## 8. 주제 직접 그리기

실제 촬영할 수 없고 공개 컬렉션에도 정직하게 쓸 이미지가 없으면 직접 그립니다. 인라인 SVG와 CSS로 충분합니다. 직접 그린 그림과 발견한 사진은 한 페이지에 함께 둘 수 있습니다: 발견한 이미지는 고객 주변의 세계를, 직접 그린 그림은 고객 자체의 사물을 보여줍니다.

- **장식이 아니라 주제의 실제 사물을 그립니다**: 의자의 다리 세 개와 좌판 나뭇결, 빵집 문 위 법랑 표지판, 산장 창문 두 개와 난로 연통, 거리 지도, 도구가 만드는 송장, 축제 무대 등. 그림이 주제 세계에서 무엇을 묘사하는지 이름 붙일 수 없다면 장식입니다.
- **페이지 전체에 하나의 그래픽 언어를 사용합니다**: 평면 채움 도형, 외곽선 없음 또는 일정한 선 굵기, 모서리와 곡선 어휘 통일, 팔레트의 실제 색상 (바탕과 강조를 흐린 회색으로 바꾸지 않음). 서로 속한다고 느껴지는 그림 세트는 아이덴티티가 되고 스타일이 섞이면 클립아트처럼 보입니다.
- **색상은 재료입니다.** 마감이 제품인 경우 그 마감의 실제 색으로 그립니다. 바닷가 집은 바다의 파랑과 모래색을 사용하고 회색 placeholder 페이지를 만들지 않습니다.
- **세 단계의 디테일로 그립니다.** 심사위원은 단순한 그림을 매번 “기본적”이라고 평가했습니다. 각 그림에는 한눈에 읽히는 큰 형태, 사물의 특성을 설명하는 중간 형태 (손잡이, 창틀, 계단), 다시 볼 때 발견하는 작은 디테일 (제작자 표시, 집 번호, 깨진 타일, 경첩, 지붕 위 새)을 둡니다. 입체감은 그라데이션이 아니라 평면 명도 단계로 빛을 표현합니다 (각 덩어리의 밝은 면과 그늘 면). 화면을 실제 크기로 봤을 때 placeholder 아이콘처럼 보이는 그림은 미완성입니다.
- **크게 그리고 실제 기능을 맡깁니다**: hero의 주도 요소, 전체 폭 띠, 타일 세트, footer 표식으로 씁니다. 여기저기 흩어진 작은 낙서는 채움처럼 보입니다.
- 모티프처럼 **페이지 전체에 아이디어를 이어갑니다**: 같은 사물이 크기별로 돌아오고, 타일 격자가 영업시간이 되며, 지도가 예약 섹션으로 이어집니다.
- **정직성**: 고객이 실제 제품 사진으로 오해할 수 있다면 첫 그림 근처 작은 글자나 footer에서 사진이 준비될 때까지 그림을 사용한다고 명확히 알립니다. 보고서에 어떤 그림이 사진 자리를 대신하는지 나열합니다.
- **금지 예**: 그라데이션 음영 3D 덩어리, 등각 투영 클립아트, 노트북 앞 사람의 범용 선화, 추상적으로 떠 있는 도형, 사각형에 넣은 아이콘. 이런 것이 생성형 디자인 스타일입니다.

## 9. 타이포그래피와 색상만 사용

이것도 정당한 디자인이지 빈 부분을 감추기 위한 수단이 아닙니다. 조사한 사이트 중 7개만 이미지를 전혀 쓰지 않았지만 평균 패널 점수 7.5로 전체 평균 7.2와 비슷한 평가를 받았습니다.

- 타이포그래피가 이미지 역할을 하게 합니다: 10–14vw 문장 하나, 5vw 목록, 디스플레이 크기의 숫자.
- 색을 큰 면적으로 사용합니다: 전체 색면, 반전 섹션, 두 색면 분할.
- 방향에서 요구하면 주제 자체 형태를 평면 모티프로 씁니다 (원, 호, 홈 등). CSS로 만들고 viewport에서 crop합니다.
- 사각형 안 아이콘, 추상 그라데이션, 도트 격자, 물결 구분선, 떠 있는 도형, 이모지, 일반적인 선화, “나중에 이미지가 들어갈” 빈 박스를 추가하지 않습니다.

## 10. 마크업과 크레딧

--get으로 프로젝트에 다운로드한 발견 사진을 hero에 사용:

```html
<img src="assets/fig-engraving.jpg" width="1920" height="2807" fetchpriority="high" decoding="async"
     alt="검정, 분홍, 초록으로 채색한 무화과를 잘라 꽃과 씨앗을 보여주는 판화">
```

페이지 아래쪽에 배치할 추첨 사진:

```html
<img src="https://picsum.photos/id/626/2400/1500" width="2400" height="1500"
     alt="청록색 바다와 백악 절벽 아래에 선 빨강·흰색 등대" loading="lazy" decoding="async">
```

--credits가 출력한 크레딧을 footer에 넣습니다.

```html
<p class="credits">Pictures: <a href="https://commons.wikimedia.org/wiki/File:Fig_(Ficus_carica_L.);_57_segments_of_flowers_and_fruits_at_Wellcome_V0043000.jpg">“Fig (Ficus carica L.): 57 segments of flowers and fruits”</a>, <a href="https://creativecommons.org/publicdomain/mark/1.0/">public domain</a>, via Wikimedia Commons.</p>
```

- 이미지 로딩 중 레이아웃이 뛰지 않도록 width와 height (또는 CSS aspect-ratio)를 항상 지정합니다.
- hero를 제외한 모든 이미지에 loading="lazy"를 씁니다. hero에는 fetchpriority="high"를 설정합니다.
- alt는 평이한 말로 이미지 내용을 설명합니다. 장식용으로 반복되는 그림은 alt=""를 사용합니다. 스크립트 제안 alt는 아카이브 제목이므로 실제 그림이 보여주는 내용을 설명하도록 수정합니다.
- 이미지 컨테이너의 background-color를 바탕 / 표면색으로 지정해 이미지가 오기 전에도 레이아웃이 온전하게 보이게 합니다.
- 크레딧은 footer 디자인의 일부로 충분한 대비와 링크를 갖춰 둡니다. 본문 크기를 사용합니다. 본문이 많은 페이지만 한 단계 줄일 수 있습니다. 작은 크기의 긴 크레딧 줄은 페이지에서 가장 자주 쓰이는 글자 크기가 되어 inspector의 본문 크기 검사에 실패할 수 있습니다. 이미지 전체에 크레딧 하나를 사용하고 사진 위에 겹쳐 표시하지 않습니다. 페이지에서 아직 사용하는 이미지에만 크레딧을 씁니다.
- 깨진 이미지는 inspector에서 실패합니다. 스크린샷을 찍어 모든 이미지를 확인합니다.

## 11. 영상

주제 세계의 영상은 사진처럼 섹션을 전달할 수 있습니다: 거리 끝의 강, 돌아가는 로스터 드럼, 세우는 목재 골조. assets.mjs --video는 키 없이 실제 영상을 검색합니다: Wikimedia Commons (웹 크기 변환본이 제공되어 짧은 영상에 가장 적합), Internet Archive의 Prelinger Archives (1920–1970년대 산업, 교육, 도시, 가정 영화. 대부분 퍼블릭 도메인이지만 길이가 긴 편), NASA (궤도에서 본 지구, 발사, 항공기, 연구실). 누구나 올릴 수 있고 라이선스 주장을 확인하지 않는 Internet Archive의 나머지 영역은 제외합니다.

```bash
node <skill>/scripts/assets.mjs "coffee roasting" --video
node <skill>/scripts/assets.mjs "river" --video --source commons,nasa --orientation landscape
node <skill>/scripts/assets.mjs --get commons:49769620        # 클립, 포스터 프레임, 크레딧 다운로드
```

720p 이하 rendition을 사용합니다 (--res로 변경 가능). 짧은 클립을 앞에 보여주며 길이와 파일 크기를 출력하고 25MB 초과 또는 1분 초과를 표시합니다. --get은 --max-mb를 전달하지 않으면 25MB가 넘는 클립을 거부합니다. 소스의 정지 프레임을 poster로 저장합니다 (Commons와 NASA; 아카이브 자체 정지 프레임은 너무 작음). 10분짜리 아카이브 영상은 그대로 쓰기에는 너무 큽니다. ffmpeg가 설치되어 있으면 몇 초로 자르거나 더 짧은 클립을 선택합니다. 라이선스, 크레딧, 정직성 규칙은 이미지와 같습니다 (3절).

**클립 선택.**

- **짧게**: 눈에 띄는 점프 없이 반복 재생되는 5–20초. 물, 연기, 회전 드럼, 교통, 나뭇잎, 멀리서 본 군중 등. 선택 전에 끝까지 재생해 봅니다.
- **용량을 낮게**: 섹션용은 약 5MB 이하, hero용은 10MB 이하. 연구 소스는 1920×1080 (가장 흔함) 또는 1280×720이고 길이 중앙값은 10초였습니다. 텍스트 뒤에는 720p로 충분합니다. 블리드 hero는 휴대폰용 세로 720×1280 버전을 만들거나 피사체에 맞춰 object-position을 설정합니다.
- **깨끗한 클립**: 슬레이트, 타이틀 카드, 로고, 워터마크, 영상에 박힌 자막이 없음. NASA와 아카이브 영상은 슬레이트로 시작하는 경우가 많고 원본 poster가 슬레이트일 수도 있습니다. 직접 프레임을 뽑거나 발견 사진을 사용합니다. 고객 직원이나 고객으로 오해할 수 있는 인물은 없어야 합니다.
- **고객 자체 영상처럼 제시하지 않습니다**: 발견된 로스터리 영상이 이 로스터리의 영상은 아닙니다.
- **발견 영상은 페이지당 한 개, 최대 두 개.** 고객 주변의 세계를 보여주는 용도이며 세 번째부터는 테마처럼 보입니다. 프로젝트 자체 영상은 더 많이 쓸 수 있습니다. 연구에서 영상이 있는 사이트의 클립 중앙값은 세네 개였습니다. 어떤 경우에도 **화면마다 움직이는 이미지 하나만** 둡니다. 나란히 재생되는 루프 두 개는 잡음입니다.

**페이지 내 영상 사용.**

- assets.mjs가 출력한 형식처럼 포스터, 고정 크기, 음소거, 인라인 재생, 반복 루프로 표시합니다:
  <video autoplay muted loop playsinline preload="metadata" poster="assets/river-poster.jpg"
  width="854" height="480" aria-hidden="true"><source src="assets/river.webm" type="video/webm"></video>.
  장식용 루프는 소리나 컨트롤을 두지 않습니다. 장식이므로 aria-hidden을 지정합니다. 중요한 내용은 영상 옆 텍스트에 넣습니다.
- 포스터는 영상 재생 전, 느린 연결, 모션 감소 설정에서 먼저 보이므로 단독 이미지로도 완성되어야 합니다. 원본 정지 프레임이 슬레이트나 흐림 이미지라면 영상에서 프레임을 직접 뽑거나 발견 사진을 씁니다.
- 연구에서 영상 클립의 31%만 poster가 있었고 패널은 재생 전의 빈 상자와 회색 상자를 오류로 기록했습니다. 이 기준에서는 모든 영상에 poster가 필요합니다 (11절).
- 영상은 viewport 안에 있을 때만 재생하고 prefers-reduced-motion: reduce에서는 포스터만 표시합니다.

```html
<script>
  const calm = matchMedia('(prefers-reduced-motion: reduce)');
  const clips = [...document.querySelectorAll('video[autoplay]')];
  const inView = new Set();
  const sync = (v) => {
    if (calm.matches) return;
    if (inView.has(v)) v.play().catch(() => {}); else v.pause();
  };
  const settle = () => {
    for (const v of clips) {
      if (calm.matches) { v.removeAttribute('autoplay'); v.pause(); v.load(); }
      else if (inView.has(v)) v.play().catch(() => {});
    }
  };
  const watch = new IntersectionObserver((entries) => {
    for (const e of entries) {
      if (e.isIntersecting) inView.add(e.target); else inView.delete(e.target);
      sync(e.target);
    }
  }, { threshold: 0.2 });
  clips.forEach((v) => watch.observe(v));
  settle();
  calm.addEventListener('change', settle);
</script>
```

- 사진처럼 자르고 배치합니다 (5절과 6절): object-fit: cover, 비율 통일, 각진 모서리, 프레임 없음, 로딩 중에는 바탕색과 같은 background-color.
- 본문 텍스트 뒤에 두지 않습니다. 영상 위에는 헤드라인, 짧은 한 줄, 액션 하나까지만 허용합니다. 포스터에서만 대비를 보지 말고 루프 전체에서 텍스트가 놓인 위치의 대비를 확인합니다. 특정 초에는 어두운 영상도 다음에는 밝아질 수 있습니다. 어느 프레임에서든 대비가 4.5:1 미만 (24px 이상 텍스트는 3:1 미만)이면 6절 scrim을 적용하거나 텍스트를 영상 바깥으로 옮깁니다. 헤드라인이나 설명문 위에는 아무것도 겹치지 않습니다.
- 영상은 움직이는 요소입니다. 페이지에서 움직이는 요소 하나로 두거나 다른 요소가 움직이지 않는 섹션에 둡니다.
- 이미지와 함께 크레딧을 표시합니다. --credits는 영상 길이가 포함된 목록과 footer용 한 줄 ("Pictures and footage:")을 출력합니다.
- 영상 위치 (hero 배경, 인라인 루프, 커지는 프레임, 모서리 카드)와 연구 측정값은 12절에 있습니다. 중요한 내용은 hover에서만 재생하지 않습니다. 소리가 있는 긴 영상은 재생 버튼 뒤에 컨트롤이 있는 플레이어로 엽니다.

## 12. 이미지와 영상 배치

2026년 7월 10일부터 10월 17일까지 Awwwards Sites of the Day 100개에서 측정한 우수 페이지의 이미지 배치 방식입니다. 이 중 91개가 분석에 사용 가능했습니다. 패널은 모든 이미지 위치를 설명하고 Awwwards 방식으로 점수를 매겼으며 스크립트가 각 화면에서 이미지가 차지하는 면적을 측정했습니다. “상위”는 패널 점수 7.5 이상 (36개), “최하”는 7.3 미만 (16개)입니다. 점수 차이는 크지 않고 (6.7–7.9) 단일 점수에는 약 0.5점 노이즈가 있으므로 배치와 점수의 관계는 법칙이 아니라 경향으로 읽습니다.

### 각 화면에서 이미지가 차지하는 면적

- **양극단의 분포.** 사진, 영상, 사진 배경을 합산하고 캔버스는 제외했을 때 스크롤 화면의 이미지 비율 중앙값은 16%였지만 이 값 주변에 화면이 몰리지는 않습니다. 42%는 이미지가 없고 19%는 이미지가 90% 이상입니다. 20–60% 구간은 19%뿐입니다. 이미지는 화면을 주도하거나 화면에서 빠집니다.
- **약 3분의 1, 그리고 휴식.** 페이지에 이미지를 쓰는 67개 사이트에서 평균 화면 이미지 비율은 36% (가운데 절반 18–69%). 상위 사이트는 30%이며 화면의 28%에는 이미지가 없습니다. 이미지 화면 사이에 타이포그래피만 있는 화면이 휴식이 됩니다.
- **첫 화면.** 사이트의 41%는 첫 화면 절반 이상, 32%는 거의 전체를 이미지가 덮습니다. 29%는 사진이나 영상이 전체 첫 화면을 채우며 약 4분의 1은 영상이 핵심 hero 이미지입니다.
- **장면은 사진이 아닙니다.** 91개 중 66개는 화면의 30% 이상에 WebGL 캔버스를 둡니다. 캔버스를 포함하면 화면 중앙값은 완전히 덮인 상태입니다. 최저 점수 사이트에서는 캔버스만 있는 경우가 많았습니다: 분석 가능한 최하위 다섯 사이트 (6.7–7.0)는 화면 전체를 캔버스로 그렸고 페이지에 사진은 최대 두 장뿐이었습니다.
- **텍스트 면적은 작습니다.** 화면에서 텍스트 면적 중앙값은 8%입니다. 사진 옆에 빽빽하게 쌓는 대신 큰 글자를 드물게 배치합니다.
- **중앙을 벗어난 배치.** 크롤링된 사이트의 섹션별 측정에서 이미지는 왼쪽이나 오른쪽에 939번, 가운데에 273번, 전체 화면 또는 텍스트 뒤에 269번 놓였습니다.

**분할: 한쪽 절반 또는 3분의 2에 사진**

- *실패.* 세 섹션 연속으로 같은 분할을 사용하거나 사진이 절반 안에서 떠 있거나 텍스트 열이 약 30자보다 좁음.

**커지는 인셋 프레임**

- *사용 시점.* 페이지당 한 번, 페이지가 다루는 영상이나 사진을 보여주며 타이포그래피 화면에서 사진 화면으로 이동할 때.

- *휴대폰.* 좌우 16px 여백에서 전체 폭 세로 이미지로 커지게 하거나 확대를 생략합니다.

- *휴대폰.* 한 열에서 전체 폭과 약 70% 폭을 번갈아 배치하거나, 오프셋을 유지하는 120–180px 타일 두 열.

**가로 갤러리**

- *사용 시점.* 제품, 객실, 행사, 팀처럼 순서에 관계없이 둘러보는 세트.
- *기하.* 화면 너비의 25–35% 카드 (1440px에서 20px 간격으로 435×326 크기면 세 장이 보이고 네 번째가 가장자리에서 잘림), 고정 높이 띠 안에 폭이 다양한 사진 (연구에서 높이 576px), 또는 가운데 슬라이드가 너비의 약 73%이고 양옆 이웃이 각각 170–180px 보이는 slider. “더 있다”는 느낌이 들도록 항상 오른쪽 가장자리에서 잘리게 둡니다. marquee 사진은 천천히 움직이며 한 바퀴에 60–120초.
- *휴대폰.* 너비 75–80% (390px 화면에서 290–300px) 카드 하나와 다음 카드 일부를 표시하고 swipe 지원.
- *실패.* 화살표만 있고 drag / swipe가 없거나 읽어야 하는 콘텐츠를 marquee로 이동시키거나 페이지에서 가장 중요한 사진을 carousel 안에 넣음.

**고정 사진 위로 패널이 미끄러져 올라감**

- *사용 시점.* 장면 전환: 사진은 고정하고 다음 섹션이 위로 올라옵니다.
- *기하.* 사진을 100vh로 고정하고 다음 섹션의 바탕이 전체 폭으로 사진 위를 덮으며 올라옵니다. 상단 경계는 직선이거나 주제에서 가져온 모양 (연구에서는 건물 창문 아치). 여기서는 모서리 각진 단색 패널을 사용합니다. 둥근 종이 겹침이나 반투명 유리는 금지.
- *휴대폰.* 동일하게 적용.
- *실패.* 앞 카드가 얇은 조각으로 계속 남는 카드 덱을 다섯여섯 장 쌓거나 목적 없이 겹침.

**균등 격자**

- *사용 시점.* 아카이브 전용 (layout.md 5절): 제품 라인, 팀, 메뉴, 전체 작업 목록.
- *기하.* 한 행에 두세네 개의 같은 크기 칸, 8–16px 간격, 화면비 하나 (가장 흔한 4:5), 사진 아래 캡션.
- *휴대폰.* 제품은 한 행에 두 장, 작업물과 사람은 한 장씩.
- *실패.* “기능”을 설명하는 똑같은 카드 세 장. 연구에서 흔했던 사진 아래쪽의 어두운 그라데이션으로 라벨을 얹은 카드. 여기서는 라벨을 이미지 아래에 둡니다.

**Hover 미리보기 인덱스**

- *사용 시점.* 이름과 이미지가 모두 중요한 프로젝트 / 고객 목록 8개 이상.
- *기하.* 45–80px 간격의 행, 이름 글자 크기 30–60px. 사진 하나만 한 번에 표시하며 너비 약 3분의 1인 16:9 또는 세로 높이 300–450px. 고정 위치 (오른쪽 절반의 50% 선부터 또는 가운데)에 두고 0.3초 안에 교체합니다. 마우스가 필요 없는 버전은 가운데 고정한 사진 위로 이름이 스크롤되고 지나가는 이름에 맞춰 사진을 바꿉니다. 연구에서는 사진이 이름 위에 놓였지만 여기서는 큰 글자 위에 어떤 것도 겹치지 않습니다. 이름이 사진 앞을 지나가게 합니다.
- *휴대폰.* Hover가 없으므로 각 행에 약 100px 썸네일을 주거나 스크롤 버전을 씁니다.
- *실패.* 터치 화면에서는 사진이 안 보임. 행을 hairline으로 구분하는 수상 사이트 방식은 피합니다. 공간으로 행을 나누고 활성 행은 잉크색이나 바탕 변화로 표시합니다.

**색면 위 사진 하나 또는 문장 옆 작은 사진 하나**

- *사용 시점.* 페이지의 숨 고르기: 인물 또는 사물 사진 하나. 혹은 문장에 구체적인 표정을 더하는 작은 사진.
- *기하.* 색면 위 높이 3:4, viewport 높이 75%의 중앙 사진 하나. 또는 48–136px 크기 문장 옆 / 위 / 사이에 너비 7–26% (108–374px)의 작은 이미지를 배치하고 문장 한 줄과 정렬.
- *휴대폰.* 사진을 문장 위에 두고 너비는 60–100%로 설정.
- *실패.* 모든 사진의 기본 배치로 사용. 사방 여백이 같은 사진은 기본값처럼 보임 (5절).

**단어 사이의 작은 사진**

- *사용 시점.* 재료, 사람, 제품처럼 사물 자체에 관한 문장을 단독 화면으로 보여줄 때.
- *기하.* 문장 안에 칩 두세네 개를 배치합니다. 높이는 대문자 높이부터 글자 크기의 4분의 3까지, 너비는 높이의 1–1.5배 (60px 글자 줄 안의 50×46px 또는 150px 이름 두 단어 사이의 113×75px). 모두 한 번의 촬영에서 가져오고 모서리는 각지게 둡니다. 로딩 중 줄이 뛰지 않도록 너비와 높이를 지정합니다.
- *휴대폰.* 텍스트 높이에 맞춰 인라인으로 유지합니다.
- *실패.* 네 개 초과, 촬영 출처가 제각각인 칩, 단어에 없는 정보를 전달하는 이미지.

**디스플레이 글자 안 또는 뒤의 사진**

- *사용 시점.* 제품, 건물, 사람처럼 대상 자체가 주제일 때.
- *기하.* 150–200px 디스플레이 글자 안에 작은 사진 창을 넣어 다음 화면에서 열거나, 글자 사이와 주위로 대상이 보이도록 글자 뒤에 배치하거나, 글자를 가리지 않고 단어 가장자리에 닿게 합니다. 연구에서는 대상이 앞에 놓여 글자 한두 개를 가리키거나 글자 줄이 정사각 사진 뒤로 지나가는 경우가 많았습니다. 여기서는 큰 글자 5분의 1 이상 가리면 inspector가 실패시키므로 글자가 항상 앞에 옵니다.
- *휴대폰.* 유지하되 글자 크기는 약 15vw로 조정하고 단어를 계속 읽을 수 있는지 확인.
- *실패.* 글자 위의 오브젝트, 이미지 때문에 위치가 밀리거나 글리치된 글자.

**평면 색면의 오려낸 오브젝트**

- *사용 시점.* 제품과 사물에 적합. 표에서 평균 점수가 가장 높았고 상위 36개 중 7개에서 사용.
- *기하.* 색상에서 가져온 평면 바탕 위에 너비 35–60%의 오브젝트를 놓습니다. 아래쪽 가장자리에 기대거나 한쪽으로 삐져나오게 하고 텍스트는 뒤나 옆에 둡니다.
- *휴대폰.* 헤드라인 아래 너비 80–90%로 배치.
- *실패.* 바탕 없이 허공에 뜬 렌더, cut-out에 추가한 drop shadow (정지 사물에는 그림자 금지. 촬영본에 원래 있는 접촉 그림자만 허용).

**흩어진 콜라주**

- *사용 시점.* 아카이브, 잡동사니, 작은 물건이 많은 축제. 절제해 씁니다. 최하위 페이지와 상위 페이지에서 비슷한 비율로 나타났습니다.
- *기하.* 가운데 정렬한 제목 주위에 100–300px 이미지 여섯 장에서 열여섯 장을 몇 가지 크기로 배치하고 텍스트 위로는 겹치지 않습니다.
- *휴대폰.* 한 열의 겹치는 쌍으로 다시 쌓습니다.
- *실패.* 기울어진 인쇄물과 스티커에 어긋난 그림자. 연구에서 흔했지만 여기서는 처리 방식이 아닙니다 (6절). 이미지를 텍스트 위로 지나가게 함.

**모서리에 고정한 작은 카드**

- *사용 시점.* 릴이나 다음 항목을 계속 가리키는 요소.
- *기하.* 약 216×144에서 240×140, 모서리에서 30–43px 거리. 페이지당 하나.
- *휴대폰.* 제거하거나 콘텐츠 흐름 안으로 옮김.
- *실패.* 콘텐츠가 그 아래로 스크롤되거나 두 개 이상 사용.

### 영상

**연구 측정값.**

- 91개 사이트 중 38개 (42%)에 영상이 있었습니다: 상위 36개 중 18개, 중간 39개 중 19개, 최하 16개 중 한 곳. 영상이 있는 사이트의 클립 중앙값은 세네 개 (가운데 절반 1–8개).
- 약 4분의 1 사이트에서 영상이 첫 화면 절반 이상을 덮고 대부분 전체 화면 블리드였습니다.
- 영상은 짧았습니다: 길이 중앙값 10초, 가운데 절반 5–14초. 61%가 10초 이하, 88%가 20초 이하.
- 장식용 클립은 모두 음소거, 반복, 인라인이며 컨트롤이 없습니다. autoplay 속성을 쓴 영상은 44%이며 나머지는 스크립트에서 시작합니다. 대부분 화면 안에 들어올 때 재생합니다.
- 포스터가 있는 클립은 31%뿐이었습니다 (38개 중 13개). 나머지는 재생 전 빈 상자나 회색 상자를 보여 패널이 빈 첫 화면으로 기록했습니다. 이 기준에서는 포스터가 필수입니다 (11절).
- 소스 해상도는 1920×1080이 가장 흔하고 그다음 1280×720입니다. 휴대폰용 세로 클립은 450×800 또는 540×960, 세로 타일로 제공됩니다. 소스 너비 중앙값은 1,080px.
- 페이지 배치 비율: 16:9 41%, 정사각 19%, 세로 (4:5–9:16) 25%, 4:3 또는 3:2 12%. 모서리는 75%가 각졌고 나머지도 8px 이하 또는 20–32px. object-fit: cover는 84%, contain은 16% (타일의 제품, 레터박스 영화)에 사용.

**배치 위치.**

- **Hero 배경:** 전체 화면에 cover로 배치하며 가장자리가 드러나지 않도록 보통 1–25% 크게 둡니다. 느린 단일 숏이나 1–2초마다 컷되는 몽타주를 사용합니다.
- **사진처럼 인라인 배치:** 분할, 타일, 카드에 너비 약 3분의 1 (중앙값 33%, 가운데 절반 24–45%)으로 사용. 이 중 3분의 1은 너비 4분의 1 미만이고 전체 폭은 10개 중 하나보다 적습니다. 물, 피부, 빛, 회전 물체처럼 느리거나 거의 정지된 대상은 움직이는 사진처럼 보여 정지 이미지 사이에 잘 어울립니다.
- 위에서 설명한 **커지는 프레임**으로 릴 표현.
- 위에서 설명한 **고정 카드**: 모서리에 클립 하나.
- **Hover 재생**: 인덱스 / 목록에서 두세 사이트만 hover로 재생했습니다. hover만 해야 볼 수 있는 중요한 콘텐츠는 두지 않습니다. 휴대폰에는 hover가 없습니다.
- **전체 영상**: 약 열 개 사이트는 재생 버튼 뒤에 컨트롤이 있는 전체 영상을 제공합니다. 자동 재생하는 곳은 없었습니다.
- **사운드**: 사이트 여섯 곳이 토글 뒤에 사운드를 뒀으며 사운드가 있는 클립도 시작부터 재생하지 않습니다.

**영상 위 텍스트.**

- 첫 화면에서 전체 화면 사진 / 영상 뒤에 텍스트를 둔 약 30개 사이트 중 14개 정도는 영상을 텍스트가 놓인 부분만 어둡게 색보정한 뒤 텍스트를 바로 얹었습니다. 약 10개는 절반 밝기, 30–40% 어두운 레이어, 또는 아래 180–590px 어두운 페이드로 화면을 어둡게 했습니다. 약 6개는 텍스트를 사진 바깥이나 단색 카드에 배치했습니다.
- 연구에서 영상에 올린 텍스트는 47–136px 이름이나 헤드라인과 짧은 한 줄이며 아래쪽 왼쪽 또는 중앙에 놓였습니다. 11–14px 본문이 영상이나 복잡한 사진 위에 있을 때 상위 사이트에서도 오류로 지적됐습니다.
- 여기서는 영상 위에 디스플레이 텍스트, 짧은 한 줄, 액션을 최대 하나만 올리고 본문은 올리지 않습니다. 포스터뿐 아니라 루프 전체의 텍스트 위치 대비를 확인합니다. 프레임마다 대비가 4.5:1 미만 (24px 이상은 3:1 미만)이면 6절 scrim 또는 단색 띠를 사용합니다.

**휴대폰에서.** 영상은 전체 화면 세로 이미지로 다시 crop합니다 (별도 세로 원본 또는 피사체에 맞춘 object-position). 인셋 프레임은 전체 블리드가 됩니다. 연구의 한 사이트는 텍스트가 사진을 더 많이 덮는 휴대폰에서만 40% scrim을 추가했습니다.

### Crop과 처리

- **화면비.** 측정된 사진 / 영상 1,356개 중 4:5 21%, 16:9 19%, 1:1 16%, 16:10 10%, 3:2 7%, 2:3 5%, 4:3 5%, 5:4 4%, 3:4 3%, 2:1보다 넓은 비율 6%, 9:16 이상 세로 3%. 가로 52%, 세로 33%, 정사각 15%.
- **두 가지 비율이 대부분을 차지합니다.** 이미지가 네 장 이상인 사이트에서 가장 흔한 두 비율이 이미지의 76%를 차지합니다. 나머지 비율 (중앙값 다섯 가지)은 이유가 있는 예외입니다: 가로 이미지 사이의 세로 인물 사진 하나, 넓은 띠 하나 등.
- **사진 94%는 각진 모서리.** 페이지에 이미지가 있는 68개 사이트 중 62개는 이미지 80% 이상을 각지게 유지했습니다. 둥근 사이트는 3분의 2에서 5px 이하, 카드 인터페이스에서는 20–32px를 사용하며 사이트마다 하나의 값을 적용했습니다.
- **Cover.** object-fit: cover 78%, contain 10% (타일 위 제품, 레터박스 영화).
- **원본 그대로.** CSS 필터를 적용한 사이트는 아홉 곳뿐이며 대부분 hover 상태에서만 사용했습니다. 일부는 세트 전체를 흑백 사진으로 구성했고, 두 곳은 스캔한 종이를 배경에 multiply로 올렸습니다. 몇몇 사이트는 인터페이스를 흑백과 회색으로 두고 사진에만 색상을 맡겼습니다.
- **연구에서 흔했지만 여기서는 금지된 처리** (6절): 페이지 전체에 고정 그레인 레이어 (사이트 약 3분의 1), 듀오톤 / 틴트 사진, 사진 뒤를 흐리게 복사해 광륜을 만드는 방식, 그림자와 함께 기울인 인쇄물 / 스티커.
- **움직이는 거리만큼만 크게.** 22개 사이트가 스크롤에 따라 사진을 움직이며 1–25% 확대했습니다. 이동량만큼만 확대하고 화면당 사진 하나에만 적용합니다.
- **해상도.** 연구에서는 사진이 CSS 너비의 중앙값 1.9배로 제공됐지만 17%는 표시 크기보다 작았고 전체 폭 이미지의 너비 중앙값은 겨우 1,440px였습니다. 여기서는 CSS 너비의 두 배, 최대 약 2,400px를 사용합니다 (4절).

### 사진 위 텍스트

- 연구에서 텍스트가 사진 위에 자주 배치됐지만 검증은 부족했습니다: scrim 없는 사진 위 텍스트를 기록한 사례가 약 28건이고, 16개 사이트의 오류에는 사진 위에 묻힌 텍스트가 포함됐습니다. 사진 위 8–14px 라벨과 본문, 차이 혼합 모드나 바탕 없이 사진 위를 지나는 내비게이션 등이 있었습니다.
- 잘 된 사례는 디스플레이 크기 텍스트를 하늘, 어두운 벽, 그림자 쪽처럼 차분한 부분에 모서리 / 가장자리를 따라 배치했습니다. 다른 두 방식은 사진 위에 바탕색의 불투명 카드를 올려 제목을 담거나, 페이지와 이어지는 흰색 사진 영역 위에 텍스트를 두는 것입니다.
- 이 기준에서는 사진 위에 디스플레이 텍스트, 짧은 한 줄, 액션 하나까지만 둡니다. 본문, 캡션, 라벨은 사진 옆이나 아래에 놓습니다. 텍스트 위치의 대비 (4.5:1, 24px 이상은 3:1)를 측정합니다. 실패하면 더 차분한 영역으로 옮기거나 바탕색 단색 카드 또는 6절 scrim을 사용합니다. 사진 위를 지나는 고정 내비게이션은 단색 띠를 두거나 아래로 스크롤할 때 숨깁니다.

### 생성형 페이지 규칙

1. **페이지 화면의 약 3분의 1이 사진이어야 합니다.** 스크롤 화면 전체에서 사진이 차지하는 면적을 30–40%로 유지하고 화면 4개 중 적어도 하나에는 사진이 없어야 합니다 (상위 사이트: 30%, 이미지 없는 화면 28%).
2. **사진은 화면을 주도하거나 작게 남습니다.** 주도 사진은 화면의 최소 60%를 차지하고 장식용 이미지는 10% 미만입니다. 사진이 20–40%인 화면을 계속 이어가지 않습니다. 연구에서는 42%가 이미지 0%, 19%가 90% 이상이었습니다.
3. **페이지마다 배치 3–5개**를 사용하고 이웃한 섹션에 같은 배치를 반복하지 않습니다. 두 개 이하인 사이트 평균 7.31, 세 개 이상은 약 7.5.
4. **이미지 여섯 장에서 열두 장**, 네 장보다 적지 않게 사용합니다. 연구 중앙값 7장, 상위 4–27장, 최하 2장.
5. **사진의 75% 이상에 화면비 두 가지를 반복**합니다 (연구 76%). 세 번째 비율은 의도적인 예외에만 사용합니다. 기본은 인물 4:5, 풍경 16:9 또는 3:2.
6. **모든 이미지의 모서리를 각지게** 합니다 (연구 94%). 방향에서 둥근 모서리를 요구하면 모든 사진과 영상에 4px 하나로 통일합니다.
7. **분할 이미지 너비는 42–50% 또는 3분의 2**이며 섹션 전체 높이를 채우고 바깥쪽 가장자리가 viewport에 닿아야 합니다. 텍스트는 50% 경계에서 시작합니다. 휴대폰에서는 사진이 먼저 전체 폭으로 표시됩니다.
8. **전체 폭 띠는 화면 너비 100%, 높이 100–150vh**이며 세네 화면마다 한 번 사용합니다. parallax에는 최대 10% 확대하고 텍스트는 한쪽 모서리에서 최소 32px 안쪽에 한 곳만 둡니다. 휴대폰에서는 전체 화면 세로 이미지로 다시 crop합니다.
9. **페이지당 커지는 인셋 프레임 하나만** 둡니다. 너비 35–50%에서 전체 화면으로 720–2,700px 동안 확대하고 같은 화면에서 다른 요소를 움직이지 않습니다.
10. **가로 갤러리는 카드 세 개와 가장자리의 네 번째 일부**를 보여줍니다: 너비 25–35%, 간격 16–20px. 휴대폰에서는 너비 75–80% 카드 하나와 다음 카드 일부를 표시합니다.
11. **화면마다 움직이는 이미지는 하나만** 둡니다. 영상은 5–15초 (중앙값 10초), 음소거 / 반복 / 인라인, 포스터 포함, viewport 밖에서는 일시정지. hero 영상은 1920×1080 원본 기준 10MB 이하, 인라인 클립은 1280×720 이하 / 5MB 이하.
12. **사진 위에는 디스플레이 텍스트만.** 헤드라인, 짧은 한 줄, 액션 최대 하나를 두고 루프 전체에서 실제 텍스트 위치의 대비를 측정합니다. 16px 이상의 본문은 사진 위가 아니라 옆이나 아래에 둡니다.
