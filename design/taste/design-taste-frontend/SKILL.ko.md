# tasteskill v2

모델이 만든 페이지는 보통 학습한 모든 페이지의 평균처럼 보입니다. 가운데 놓인 3줄 헤드라인, 그 위의 작은 라벨, 아이콘 카드 행, 옅은 그라데이션, 가는 구분선 몇 개, 모노스페이스 캡션. 틀린 것은 없지만 스스로 결정한 것도 없습니다.

이 스킬은 네 가지 방법으로 기본값을 결정으로 바꿉니다.

1. **스크립트가 방향을 뽑고, 당신이 고릅니다.** 만들 스타일을 상상하라고 하면 모델은 매번 카테고리 기본값을 선택합니다. scripts/draw.mjs는 조사된 방향 20개 중 세 가지를 뽑습니다. 주제의 아이디어를 담는 방향을 고르면 스크립트가 실제 사이트 247개에서 추린 라이브러리에서 타이포그래피 체계, 팔레트, hero, 섹션 구성을 뽑습니다.
2. **아이디어는 주제에서 나옵니다.** 연구에서 최고 사이트와 잊히는 사이트를 가른 것은 스타일링이 아니라 대상 자체에서 나온 콘셉트였습니다.
3. **장식이 없는 하우스 스타일.** scripts/inspect.mjs로 실제 브라우저에서 측정해 규칙을 기대가 아닌 검증으로 만듭니다.
4. **만든 것을 직접 봅니다.** 세 가지 너비에서 스크린샷을 보고, 심사표로 평가하고, 수정한 뒤 다시 봅니다.

테스트에서 얻은 경고가 하나 있습니다. 장식을 걷어내는 것은 절반의 작업일 뿐입니다. 라벨, 구분선, 카드를 없애고 대신 아무것도 채우지 않은 페이지는 빈약해 보입니다. 심사자는 표시가 남은 풍부한 페이지를 빈 페이지보다 올바르게 선호합니다. 나머지 절반은 실질입니다: 더 큰 활자, 넓은 색면, 이 주제의 세계에서 가져온 실제 사진 (찾거나 그린 이미지), 내용을 온전히 담은 모든 섹션. 이 스킬은 그 결과를 만들도록 설계되었습니다. 절제를 핑계로 실질을 줄이지 마십시오.

아래 명령의 <skill>은 이 스킬 폴더를 뜻합니다. 프로젝트 루트에서 실행해 작업 파일이 .taste-skill/에 생성되게 합니다. 스크립트에는 Node 22 이상과 Chrome, Edge 또는 Chromium 설치가 필요하며 패키지를 설치하지 않습니다. assets.mjs에는 네트워크가 필요하지만 API 키는 사용하지 않습니다.

## 페이지 또는 앱 화면

먼저 두 작업 종류 중 하나를 정합니다.

- **페이지**는 읽고 스크롤합니다: 랜딩 페이지, 마케팅 / 제품 사이트, 포트폴리오, 이벤트, 레스토랑, 원페이지. 아래의 **실행 절차**를 따릅니다.
- **앱 화면**은 실제 작업에 사용합니다: 대시보드, 관리자 / 분석 화면, 설정, 결제, 작업할 받은 편지함 / 큐, 지갑, 필터가 있는 목록, 편집기, 빌더. 별도 실행 절차와 별도 draw (draw.mjs --app), 별도 하우스 규칙 (차분한 테두리, 작은 라벨, 반복 패널은 정상. 그라데이션, 광륜, 색조 칸의 아이콘, 무지개 그래프, 지어낸 허영 지표는 금지), inspect.mjs --app를 사용하는 **references/app-screens.md**를 따릅니다. 시작 전에 해당 파일 전체를 읽습니다. 아래 페이지 실행 절차는 적용되지 않습니다.

앱을 보여주는 제품 사이트는 페이지이며 사이트 안의 인터페이스 조각에는 내부 표현에 앱 화면 규칙을 적용합니다. 제품의 앱 스타일은 자체 폴더에서 한 번 뽑고 페이지의 팔레트와 글꼴은 유지합니다.

```bash
node <skill>/scripts/draw.mjs --app --kind <kind> --brief "<the product>" --keep palette,type --out .taste-skill/app
```

페이지가 보여주는 각 조각 (실시간 hero 화면, 기능의 crop, 그래프)을 실제 앱의 일부처럼 만듭니다: 패널, 표, 컨트롤에는 assets/app.css, 그래프에는 assets/charts.js, 합계가 맞는 실제 데이터, 페이지 청사진이 사진을 다루는 방식에 맞춘 crop과 크기를 적용합니다. 작동하는 제품처럼 보이는 조각은 소프트웨어 페이지에 가장 강한 이미지이며 회색 막대와 lorem 숫자는 가장 약합니다. 요청이 랜딩 페이지와 그 뒤의 대시보드처럼 둘 다라면 각자 실행 절차로 만들되 팔레트와 글꼴 하나를 공유합니다.

## 실행 절차

순서대로 진행합니다. 1–5단계는 몇 분이면 되며 페이지의 성패를 결정합니다.

### 1. brief와 프로젝트 확인

실제 정보를 파악합니다: 주제, 대상 고객, 페이지에서 꼭 일어나야 할 행동 하나, 스택, 기존 브랜드 (색상, 글꼴, 로고), 무엇보다 **실제로 쓸 수 있는 이미지가 무엇인지**. 프로젝트가 가진 사진이나 제품 사진, 보여줄 수 있는 실제 인터페이스, 실행할 이미지 생성 도구, 또는 아무것도 없는지 확인합니다. 없는 사진을 전제로 계획하지 않습니다. 자체 이미지가 전혀 없는 경우도 거의 없습니다. 주제의 도시, 거리, 재료, 역사는 공개 아카이브와 박물관에서 찾을 수 있으며 출처를 표기하면 무료로 쓸 수 있습니다 (6단계, scripts/assets.mjs).

요청이 모호하면 질문하지 말고 해석을 한 줄로 결정해 알립니다. 누락된 사실이 작업을 막을 때만 묻습니다 (예: 제품 이름이 없음).

그다음 메모에 **주제 고유 목록**을 작성합니다: 이 고객에게만 해당하고 경쟁자에게는 없는 요소 여덟 개에서 열두 개. 이름과 의미, 주소와 문 번호, 거리와 동네 및 그 장소의 모습 (타일, 간판, 페인트색, 지역 점포의 글꼴, 빛, 날씨), brief의 수치 (좌석, 객실, 바다까지 분, 가격, 연도), 운영 제약 (월 한 번만 생산, 겨울 휴무, 예약제), 재료와 색, 의식과 시간 (새벽 다섯 시 오븐 점화, 일곱 시 페리), 세계에 이미 존재하는 인쇄물 (시간표, 라벨, 티켓, 표지판)을 살펴봅니다. 이 목록에서 4단계의 아이디어를 찾습니다. 블라인드 테스트에서 각 brief의 승자는 이런 목록의 항목 (고객 이름과 뜻, 위치한 거리, 정체성을 만드는 제약 하나)을 바탕으로 만들었습니다. 패자는 좋은 구도에 카테고리 아이디어를 더한 페이지였습니다. 이 목록은 이미지 검색어도 제공합니다. 각 장소, 재료, 인쇄물이 6단계의 검색어가 됩니다.

### 2. 주장 작성

디자인 전에 페이지를 주장과 근거로 정리합니다. 섹션마다 한 줄씩 작성하며 references/copy.md `1 형식을 따릅니다. 주장이 섹션의 존재와 순서를 결정합니다. 주장이 없는 섹션은 삭제합니다. 이를 통해 hero, 로고, 기능 세 개, 후기, 가격, CTA로 이어지는 상투적 순서를 피합니다.

### 3. 방향 추첨

```bash
node <skill>/scripts/draw.mjs --sector <sector> --brief "<one line about the subject>" \
  --sections <roles in the order of your argument> [--tone <tone>] [--have <assets>] [--keep palette,type] \
  --options 3
```

방향 세 개와 각각의 짧은 요약이 나옵니다. 주제 고유 목록에 비춰봅니다: 어느 구도가 이 고객만 가진 것을 담을 수 있을까요? 가장 익숙한 것이 아니라 그 방향을 선택하고 이유를 메모에 한 줄로 씁니다. 테스트에서는 주제에 맞지 않는 무작위 방향 하나가 약한 페이지의 가장 흔한 원인이었습니다. 그다음 전체 방향표를 뽑습니다.

```bash
node <skill>/scripts/draw.mjs <same arguments, without --options> --direction <chosen id>
```

- **--sector**: node <skill>/scripts/draw.mjs --list sectors로 확인하고 가장 가까운 분야를 고릅니다.
- **--sections**: --list roles에 나오는 역할을 사용합니다 (features, showcase, how-it-works, testimonial, proof, stats, pricing, faq, cta, footer, intro, about, work, gallery, list, contact). hero는 자동 포함됩니다.
- **--tone** (선택): quiet, bold, warm, technical, playful, luxury, editorial 중에서 고릅니다. brief가 분명히 요구할 때만 전달합니다.
- **--have**: 실제 존재하는 에셋을 쉼표로 나열합니다: photography (장소, 사람, 작업에 관한 프로젝트 자체 사진), product-photo (특정 제품 사진 또는 제품 사진을 만들 이미지 도구), product-ui (실제 스크린샷), illustration, video. 해당 에셋이 없으면 옵션을 생략합니다. 방향표는 이를 필요로 하는 구도를 피하고 이미지 자리를 정직하게 채울 방법을 제안합니다 (소프트웨어는 HTML로 만든 자체 인터페이스를 보여주고, 사진 없는 제품은 가짜 제품 사진 대신 직접 그려 세계의 실제 사진 사이에 배치). 공개 컬렉션에서 찾은 사진은 프로젝트 자체 이미지가 아니므로 --have에 넣지 않습니다.
- **--keep palette,type**: 브랜드가 색상이나 글꼴을 이미 확정했을 때 사용합니다. 추첨은 구도만 고르고 브랜드 값을 역할에 맞춰 적용합니다.

명령은 **방향표**를 출력합니다. 이번 빌드의 아트 디렉션입니다.

- **채택합니다.** 평소 만들 구도와 혼합하지 않습니다. 낯설게 느껴진다면 좋습니다. 익숙한 레이아웃을 막는 것이 이 스킬의 목적입니다.
- 명시할 수 있는 이유가 있을 때만 슬롯 하나를 다시 뽑습니다 (--redraw hero | type | palette | photos | scenes | section:<role> | direction). 명시적 브랜드 제약에 어긋나거나 존재하지 않는 에셋이 필요하거나 섹션이 실제 콘텐츠를 담을 수 없을 때입니다 (다음 항목 참고). 더 편하다는 이유로 다시 뽑지 않습니다. 모든 재추첨을 보고서에 기록합니다.
- 뽑힌 섹션이 실제 콘텐츠를 담지 못할 때 (가격 세 개를 비교하도록 되어 있는데 가격은 하나뿐이거나 견적 다섯 개를 요구하지만 전혀 없음) 콘텐츠를 구도에 억지로 맞추지 않습니다. --alternatives <role>로 대안을 나열하고 실제 콘텐츠와 전제가 맞는 항목을 골라 --redraw section:<role>=<id>로 선택합니다.
- **팔레트를 주제와 대조합니다.** 뽑힌 팔레트는 색상뿐 아니라 비율 (바탕 하나, 잉크 하나, 강조색 하나, 넓은 색면)을 뜻합니다. 색이 주제의 실제 재료와 충돌하면 (피트 위스키에 캔디 파스텔, 산장에 네온) 팔레트를 한 번 다시 뽑습니다. 주제 자체에 식별력 있는 색 (재료, 거리의 페인트, 창밖 풍경)이 있다면 추첨 비율은 유지하고 색상은 주제에서 가져옵니다. 이유를 보고서에 씁니다.
- 필요할 때 node <skill>/scripts/draw.mjs --show로 방향표를 다시 출력합니다. 긴 세션에서는 섹션을 만들 때마다 다시 읽습니다.

### 4. 아이디어 찾기

방향은 구도 방식입니다. 아이디어는 이 주제에만 속하는 것입니다. 메모에 아래 문장을 채우고, 두 빈칸을 주제 자체에서 채우기 전에는 제작을 시작하지 않습니다.

> 이 페이지에서 **[주제에만 속하는 무언가]**는 **[방향이 요구하는 장치]**가 된다.

첫 빈칸을 찾을 곳:

- **주제의 산출물**: 무엇을 만들어내나요? 실제 결과물을 페이지의 재료로 사용합니다. (시를 인쇄하는 카메라는 출력물을 종이 띠로 보여줌.)
- **사물이나 형태**: 실제 물체의 단면과 실루엣은 어떤가요? 확대하거나 자르거나 프레임 또는 핵심 모티프로 씁니다.
- **이름**: 글자 안에 사진을 담거나 벽처럼 쌓거나 양쪽 모서리로 나눌 수 있나요?
- **장소**: 그곳에 가고 싶게 만드는 한 장면이 있나요?
- **의식**: 스크롤하면서 페이지가 직접 수행할 수 있는 순서가 있나요?
- **유물**: 그 세계에 이미 존재하는 인쇄물은 무엇인가요? 티켓, 메뉴, 라벨, 영수증, 초대장, 폴더, 설명서 등.
- **반대편**: 이 주제에 부족한 감정을 다른 어떤 카테고리가 가지고 있나요?

첫 빈칸은 카테고리가 아니라 주제 목록 (1단계)에서 찾습니다. **경쟁사 검사**: 가장 가까운 실제 경쟁자를 문장에 넣습니다 (두 거리 떨어진 빵집, 다른 참나무 가구 제작자, 같은 산의 다른 산장). 문장이 여전히 성립하면 아이디어는 카테고리 소유입니다. 빵 한 덩이는 모든 빵집에 해당하지만 이 가게 이름의 유래가 된 거리의 일곱 문은 이곳에만 속합니다. “깔끔하고 현대적”은 아이디어가 아닙니다. 연구 패널에서 최저 점수를 받은 사이트는 아이디어가 “표준 공식 외에는 없음”으로 기록된 경우였습니다.

**살아 있는 상호작용 하나.** 주제에서 나온 것으로 방문자가 직접 할 수 있거나 방문할 때마다 다르게 보이는 상호작용을 하나 만듭니다: 목재를 고르면 그 재질의 의자를 보기, 이름을 입력하면 주조소의 글자로 잘라 보기, 대출액을 정해 실제 월 상환액 읽기, 지금 산장의 난로가 켜져 있는지와 마지막 페리까지 남은 시간 확인, 크기를 선택해 방에 놓아 보기. 블라인드 테스트에서 모든 승리 페이지에는 하나가 있었고 심사위원은 이것을 첫 번째로 언급했습니다. 규칙: 주제의 실제 콘텐츠를 사용하고, 휴대폰에서 엄지로 조작 가능하며, 스크립트가 없어도 단순한 대체 경로가 있고, 읽기를 막지 않으며, 놀이터가 아니라 기능 하나여야 합니다. 9단계에서 모션으로 덧붙이는 것이 아니라 6단계에서 페이지 일부로 구현합니다.

**장면도 아이디어를 전달합니다.** 방향표의 스크롤 장면은 주제를 담을 장치입니다. 구현 전에 각 장면을 주제 목록의 무엇으로 채울지 정합니다: 비행 장면은 이 스튜디오만의 타이틀 카드를 통과하고, 경로는 이 배송이 실제로 거치는 도로가 되며, 전체 화면으로 열리는 사진은 투숙객이 아침에 눈을 뜰 방이 됩니다. 누구의 것이어도 되는 사진으로 채운 장면은 화면 보호기입니다.

### 5. 문구 작성

마크업을 쓰기 전에 references/copy.md에 따라 전체 페이지의 카피 덱 (일반 텍스트)을 만듭니다.

- **모든 헤드라인은 모든 너비에서 최대 두 줄**입니다. 문구를 확정하기 전에 copy.md §2에서 계산합니다. 자신감 있는 크기에서도 약 32자 이내가 안전합니다. 조사한 갤러리의 hero 헤드라인 중앙값은 5단어, 32자였습니다.
- 헤드라인 바로 아래 (32–48px 간격)에 헤드라인과 함께 표시하는 보조 문장 하나를 둡니다. 첫 화면 아래쪽에 고정하거나 애니메이션으로 숨기지 않습니다. 헤드라인이 이름이나 비유라면 이 문장에서 실제 대상이 무엇인지 명확히 설명합니다. 첫 화면에는 행동을 설명하는 이름의 기본 액션 하나를 실제 버튼으로 둡니다.
- **첫 화면은 방문자의 첫 질문에 큰 글자로 답해야 합니다.** 이벤트라면 무엇인지, 언제 어디인지 (날짜는 헤드라인이나 두 번째 크기에 표시하고 작은 글자에만 숨기지 않음). 제품이라면 무엇이며 가격이나 기능은 무엇인지. 사람이라면 누구이며 무엇을 하는지. 방문자가 찾으러 온 섹션 (출연자, 메뉴, 객실, 가격)은 각각 제목과 내비게이션 내 자리를 가져야 합니다.
- **콘텐츠를 온전히 작성합니다.** brief가 요구하는 모든 섹션에서 필요한 정보를 다 제공합니다: 전체 메뉴와 가격, 객실별 세부 사항, 발표자와 강연 전부, 포함 항목이 표시된 가격, 실제 질문마다 답변 하나. 내용이 빈약한 섹션은 깔끔하지만 알찬 다른 페이지보다 낮은 평가를 받는 가장 흔한 원인입니다.
- brief에 빈칸이 있으면 샘플 정보를 제공해 밀도 높은 디자인을 확인할 수 있게 합니다 (음식명, 객실명과 요금, 프로젝트 제목). 보고서에 고객 확인이 필요한 샘플을 모두 나열합니다. 근거는 절대 지어내지 않습니다: 고객, 인용, 후기, 언론, 로고, 사업 통계를 만들지 않습니다.

### 6. 페이지 제작

애니메이션을 껐을 때도 완성된 페이지여야 합니다. 움직임이 없으면 덜 완성돼 보이는 페이지는 이미 미완성입니다. 다음 순서로 작업합니다.

1. **토큰**: 방향표에서 색상과 글꼴 역할을 CSS 사용자 지정 속성으로 만듭니다. 이후의 모든 요소는 토큰만 참조합니다. <skill>/assets/base.css는 시작점으로 쓸 수 있는 중립 기반입니다 (reset, 토큰 이름, 유동 글자 크기 단계, 격자, focus / selection 스타일, 모션 도우미). 자체 시각 스타일은 없습니다.
2. **Hero**: 청사진에 정확히 따라 데스크톱과 휴대폰 너비로 구현합니다. 다른 요소를 만들기 전에 핵심 요소는 충분히 크게, 부차 요소는 충분히 작게 만듭니다.
3. **각 섹션**: 청사진에 따라 주제의 실제 콘텐츠를 넣습니다. 형태를 유지하되 주제만 바꿉니다. 이웃한 섹션의 레이아웃은 서로 달라야 합니다. **아이디어를 가격, FAQ, footer까지 모든 섹션에 적용합니다.** 연구에서 가장 흔한 실패는 좋은 사이트에도 나타났습니다. 첫 화면만 독특하고 뒤는 일반 블록으로 이어집니다.
4. **이미지**는 다음 우선순위로 사용합니다.
   1. 프로젝트 자체 자료.
   2. 이미지 도구가 있으면 생성 이미지.
   3. **공개 컬렉션에서 찾은 주제 세계의 실제 사진.** 정직하게 쓸 사진이 있으면 항상 우선 고려합니다. node <skill>/scripts/assets.mjs "<query>"로 검색합니다 (Openverse, Wikimedia Commons, Art Institute of Chicago, Met; 기본 설정은 상업적 이용 가능한 라이선스만). 카테고리가 아니라 주제 목록을 검색합니다: 옛 엽서 속 거리, 동네 옛 지도, 재료 접사, 관련 거래의 판화, 비슷한 유형의 박물관 유물, 식물 도판, 별자리 지도. 크고 의도적으로 사용합니다: 아카이브 사진 하나를 hero로, 판화를 확대해 페이지 모티프로, 실제 거리 지도를 연락처 섹션에 배치할 수 있습니다. 선택 전에 각 사진을 직접 확인합니다. --get <ref>는 assets/에 다운로드하며 출처와 라이선스를 기록하고 --credits는 footer용 크레딧 문구를 출력합니다. 공개 컬렉션 이미지는 고객을 둘러싼 세계를 보여주는 것이지 고객 자체의 제품, 객실, 음식, 사람, 팀이라고 소개하지 않습니다.
   4. 정직한 사진이 없는 것은 **주제에서 가져온 형태를 코드로 그립니다** (사물, 타일, 창문, 제품 인터페이스를 팔레트의 실제 색상으로 일관된 플랫 그래픽 언어로 그림).
   5. 방향표에서 뽑은 사진은 일반적인 이미지가 정직하게 맞는 곳에서만 사용합니다 (바닷가 집에 바다 사진). 주제 자체를 대신할 수 없습니다.
   6. 활자와 색상만 사용합니다.

   프로젝트 자체의 영상이나 실제 작업 / 제품 사진이 있으면 첫 화면에서 크게 (화면의 약 40% 이상) 보여줍니다. 사진의 출처나 아닌 것을 설명하는 문장을 페이지에 쓰지 않습니다 (“이 중 어떤 사진도 우리 바가 아닙니다” 등). 캡션에는 사진이 무엇인지 쓰고 출처 표기는 작게 footer에 둡니다. brief용으로 지어낸 작품을 보여주는 포트폴리오는 각 작품을 완성된 정지 이미지로 만듭니다 (자체 글꼴의 타이틀 카드, 엔드 프레임, 포스터). 디테일을 실제처럼 넣고 고객 제품을 픽토그램으로 표현하지 않습니다.

   **검사기가 확인하는 최소 기준**: 페이지에 실제 사진이 최소 네 장 있어야 하며 보통 여섯에서 열두 장을 사용합니다 (사진, 아카이브 이미지, 지도, 판화, 영상, 래스터 아트워크; 소프트웨어는 crop한 인터페이스 조각도 포함). SVG 그림은 최소 개수에 포함되지 않습니다. 사진이 없는 대상을 그리되 실제 사진도 포함합니다. 정직하게 쓸 영상이 있으면 움직이는 이미지 하나를 추가합니다: assets.mjs --video "<query>"로 검색하고 poster 프레임을 둔 음소거 루프로 사용합니다. 모델은 사진과 영상 찾기가 번거로워 건너뛰곤 하지만 없으면 페이지는 실패합니다.

   검색, 라이선스, 크레딧, 영상, 드로잉, crop과 처리는 references/imagery.md에 설명되어 있습니다.
5. **살아 있는 상호작용**: 4단계에서 설계한 항목을 주장을 입증하는 섹션 (대개 hero 또는 예약)에 넣습니다. 실제 콘텐츠를 쓰고 엄지 크기의 휴대폰 버전과 단순 대체 경로를 제공합니다.
6. **스크롤 장면**: 방향표에 포함된 경우 각 장면에 해당 섹션을 연결합니다. 페이지의 주요 순간, 작업 사이를 나는 카메라, 전체 화면으로 열리는 사진, 스크롤에 따라 휘는 단어를 구현합니다. <skill>/assets/scenes/의 공용 stage와 장면 파일을 복사하고 이 프로젝트의 사진과 문구로 채운 뒤 페이지 토큰이 시각 스타일을 적용하게 합니다. 장면은 구도입니다. 페이지 길이와 화면마다 보이는 내용을 결정하므로 지금 구현하고 모든 시각 검수에서 확인하며 끝에 덧붙이지 않습니다. 페이지에 장면을 배치하고 채우고 맞추고 휴대폰에서 확인하고 카탈로그를 보는 방법은 references/scenes.md의 설명을 따릅니다. assets/scenes/demo/<id>.html은 각 장면의 작동 예시입니다.
7. **밀도**: 데스크톱에서 각 화면을 포스터처럼 살펴봅니다. 주도 요소 하나와 그에 딸린 콘텐츠가 있어야 합니다. 대부분이 빈 바탕이라면 휴식이 아니라 미완성 섹션입니다. 페이지당 의도적인 휴식은 한 번까지만 허용하며 거의 비어 있는 화면이 두 개 이상이면 검사기가 실패시킵니다. 본문은 16px 이상 잉크색을 전부 사용하고 회색은 보조 메모에만 씁니다.
8. **프레임**: 모든 너비에서 페이지 바깥 여백 한 쌍을 동일하게 맞추고 각 섹션이 페이지가 마련한 너비를 모두 씁니다. 텍스트가 왼쪽 절반에 있으면 오른쪽 절반에는 이미지, 두 번째 열, 목록, 도형 중 하나가 있어야 하며 비우지 않습니다. 비대칭은 격자 안에서 만들고 프레임을 비대칭으로 만들지 않습니다. 한쪽에 빈 공간이 있으면 반대편에 이를 닫는 요소를 둡니다. 화면 높이의 절반을 넘는 빈 구간이 없어야 하며 데스크톱에서 섹션 간격은 120–240px입니다. 방문자가 찾는 모든 섹션은 내용을 이름 붙이는 제목으로 시작해야 하고 첫 화면에는 h1 제목이 있어야 합니다. 페이지가 잘못됐을 때 사람들이 먼저 지적하는 “명확한 제목 없음”, “무작위 빈 공간”, “모든 것이 한쪽으로 밀림”을 검사기가 측정합니다.
9. **상태와 의미 구조**: 실제 링크와 버튼, 보이는 focus, alt 텍스트, 고유한 구성을 가진 휴대폰 레이아웃을 구현합니다. 살아 있는 상호작용을 포함한 모든 컨트롤은 키보드만으로 읽기 순서대로 작동해야 하며 접근 가능한 이름이 있어야 합니다 (보이는 라벨 또는 아이콘만 있다면 aria-label).

결정의 상세 근거가 필요하면 references/type.md, references/colour.md, references/layout.md를 읽습니다. 아래 법칙은 요약입니다.

### 7. 게이트

```bash
node <skill>/scripts/lint.mjs <source files or folder>
node <skill>/scripts/inspect.mjs <url or path/to/index.html>
node <skill>/scripts/scenes.mjs <url or path/to/index.html>     # 페이지에 스크롤 장면이 있을 때
```

scenes.mjs는 모든 스크롤 장면을 유지 구간의 0, 10 … 100%에서 데스크톱, 휴대폰, reduced-motion 설정으로 촬영합니다. 장면이 있으면 inspect.mjs도 전체 스크롤 영상 (desktop-film-NN.jpg)을 기록합니다. 장면이 시작하지 않거나 데스크톱에서 정지하면 FAIL입니다.

lint.mjs는 소스에서 금지 패턴과 상투 문구를 찾습니다. inspect.mjs는 실제 브라우저에서 1440, 768, 390px로 페이지를 열어 측정합니다 (헤드라인 줄 수, 글자 크기, 실제 로드된 글꼴, 색상, 선, 그림자, 그라데이션, 대비, 넘침, 프레임: 좌우 여백 동일성, 한쪽에 몰린 섹션, 빈 구간, 제목, 제목 없는 섹션, 화면 가장자리와 맞닿은 텍스트). 스크린샷은 .taste-skill/inspect/에 저장합니다. 모든 FAIL을 수정합니다. WARN은 디자이너에게 한 문장으로 근거를 댈 수 없는 한 잘못된 결과로 간주합니다. FAIL이 없어질 때까지 다시 실행합니다. 측정 결과와 논쟁하거나 숨기지 않습니다. 검사기는 임시 로컬 서버로 파일을 제공합니다. 페이지를 파일 시스템에서 직접 열어야 한다면 끝내기 전에 index.html도 한 번 직접 엽니다.

방문자가 받는 결과물을 검사합니다. 빌드 단계가 있다면 개발 서버만 보지 말고 프로덕션 빌드를 마지막으로 검사합니다 (vite build && vite preview, next build && next start, 또는 빌드된 index.html). minifier와 bundler가 배포 결과를 바꿀 수 있습니다 (개발 서버에서는 보였던 backdrop-filter가 제거된 사례가 있음). 개발 서버 검사 중이면 검사기가 경고합니다.

### 8. 시각 확인

게이트 통과는 금지 항목이 측정되지 않았다는 뜻일 뿐 페이지가 훌륭하다는 뜻은 아닙니다. 검사기가 나열한 스크린샷을 모두 (모든 viewport) 이미지 뷰어나 Read 도구로 열어 references/critique.md에 따라 평가합니다: 14개 항목, Awwwards 가중치 점수, 상한 기준. 형식에 맞춰 비평을 기록하고 상위 세 문제를 수정한 뒤 검사기를 다시 실행하고 다시 확인합니다. 최대 세 라운드입니다.

코드가 아니라 이미지로 판단합니다. 스크린샷에 문제가 보이면 실제 문제입니다.

### 9. 움직임 추가

이제 모션 레이어를 만듭니다. 반드시 있어야 하며 단순 fade 하나로 끝나지 않습니다. 검사기는 페이지 로딩 중과 스크롤 중 실제로 움직이는 요소를 세며 8개 미만이면 실패합니다 (16개 미만은 경고). 방향표에 있는 스크롤 장면은 이미 6단계에서 만들어졌습니다. 그 밖의 모션은 네 부분으로 구성합니다.

1. **시그니처 동작**: 방향표에 지정된 동작 하나를 잘 만듭니다 (뽑힌 장면 하나가 이를 맡을 수 있음).
2. **모든 섹션 요소의 등장 동작**: 먼저 제목, 그다음 문구, 그다음 이미지가 60–90ms 간격을 두고 16–32px 위로 올라오며 opacity가 바뀝니다. 섹션 진입 시 한 번만 실행합니다. 블록 전체에 fade 하나만 적용하지 말고 스크립트가 실패해도 콘텐츠가 숨겨진 상태로 남지 않게 합니다.
3. **모든 컨트롤의 피드백**: 버튼, 링크, 카드, 살아 있는 상호작용에 눌림, hover, focus 상태를 둡니다.
4. **움직이는 이미지 하나**: 정직하게 쓸 영상 클립을 음소거 루프로 재생하거나 사진에 느린 확대 / 이동을 적용하거나 hero 이미지에 스크롤 연동 움직임을 둡니다.

transform과 opacity만 애니메이션합니다. 모든 동작에는 콘텐츠를 유지하고 이동 효과를 제거하는 prefers-reduced-motion 대체가 있어야 합니다. 페이지 전체 화면의 색을 장별로 바꾸거나 이야기를 고정하는 등 구성 전체를 바꾸는 움직임은 구도의 일부입니다. 6단계에서 구성해 모든 시각 검수에 포함합니다. references/motion.md에는 토큰과 검증된 레시피가 있습니다. 마지막으로 검사기를 한 번 더 실행하고 콘텐츠가 나타나지 않은 스크린샷이 있는지 확인합니다.
### 10. 보고

다음 조건을 모두 충족하기 전에는 보고하지 않습니다. 테스트에서 건너뛴 항목은 각각 나쁜 결과로 이어졌습니다.

- 마지막 페이지 버전에서 inspect.mjs가 1440, 768, 390px 모두 **FAIL 0개**를 표시.
- 마지막 변경 후 검사기가 나열한 스크린샷을 첫 화면뿐 아니라 모두 열어 확인.
- 스크롤 장면이 있다면 최종 페이지에서 scenes.mjs가 문제없이 실행되고 모든 결과 (데스크톱, 휴대폰, reduced-motion)를 읽음.
- 낯선 사람이 첫 화면을 5초 본 뒤 이 페이지가 무엇이며 무엇을 해야 하는지 설명할 수 있음.
- 모든 섹션에 제목이 있고 좌우 여백이 같으며 페이지에 빈 구간이 없음.
- 마지막 라운드의 비평을 references/critique.md §4 형식으로 기록.

사용자에게 간결히 보고합니다: 추첨된 방향 (이름과 seed)과 이유가 있는 재추첨; 아이디어 문장과 살아 있는 상호작용; 마지막 비평 라운드의 점수와 남은 부족점; 찾은 사진과 영상 클립 각각의 제목, 제작자, 라이선스, 출처 페이지 (assets.mjs --credits가 목록 출력), 페이지 내 크레딧 위치; 어떤 기본 제공 사진과 그림이 사진 대용인지 (교체할 수 있도록); 출시 전에 교체해야 할 샘플 콘텐츠. 실행하지 않은 검사는 실행했다고 말하지 않습니다.

## 하우스 규칙

방향에 관계없이 모든 빌드에 적용합니다. inspect.mjs가 측정합니다.

| 규칙 | 대안 |
| --- | --- |
| **헤드라인은 모든 너비에서 최대 두 줄.** 모든 h1–h6과 태그와 관계없이 첫 화면의 메인 문구. | 단어를 줄입니다. 그다음 문장 폭을 넓힙니다. 크기 조정은 마지막입니다. |
| **첫 화면에 명확한 제목**을 페이지의 h1 하나로 둡니다. 모든 섹션에도 제목을 둡니다. | 무엇인지 밝힙니다: 이름과 기능, 제품과 용도, 이벤트와 날짜·장소. |
| **바깥 여백을 양쪽으로 동일하게** 두고 한쪽 섹션 옆에 화면 절반을 비워 두지 않습니다. | 반대편에 빈 공간을 닫는 요소를 둡니다: 해당 섹션의 사진, 두 번째 열, 목록, 도형. |
| **화면 절반 높이를 넘는 빈 구간을 두지 않습니다.** | 일반 섹션 간격을 둡니다. 의도적인 휴식은 배치한 사진이나 색면으로 표현하고 페이지당 한 번만 사용. |
| **설명 문구는 문단으로.** 도입 문장이나 큰 인용문은 p 또는 blockquote로 표시하고 본문 크기로 유지합니다 (데스크톱 36px 이하, 휴대폰 24px 이하). 약 25단어, 세 줄 안팎으로 씁니다. | 그보다 크면 헤드라인이며 두 줄 규칙이 적용됩니다. 블라인드 테스트에서 42px 문장이 네 줄이면 네 줄짜리 헤드라인으로 읽혔습니다. |
| **Eyebrow 금지.** 제목 위 작은 라벨, 헤드라인 위 알약 배지, “New ·” 칩을 두지 않습니다. | 정보를 제목이나 첫 문장에 넣거나 삭제합니다. |
| **실제 코드 블록 밖에서 monospace 금지.** | 본문 글꼴을 씁니다. 숫자 정렬이 필요하면 tabular figure를 씁니다. |
| **인덱스 번호 금지.** 01 / 02 / 03, (001), “Step 2”를 두지 않습니다. | 위치, 크기, 단어로 순서를 보여줍니다. 순서가 중요하면 실제 ol을 사용합니다. |
| **가는 선 금지.** hairline divider, 1px 윤곽 박스, 격자선, 십자선, crop 표시를 쓰지 않습니다. | 여백, 배경 명도 변화, 크기 차이, 채운 도형을 사용합니다. |
| **그라데이션 금지.** 배경, 버튼, 텍스트 어디에도 사용하지 않습니다. | 평면 색이나 실제 사진을 씁니다. 사진 위 텍스트를 위한 중립 scrim만 예외입니다. |
| **정지 상태의 그림자 금지.** 광륜도 쓰지 않습니다. | 표면 사이의 명도 단계로 높이를 구분합니다. 그림자는 실제로 떠 있는 메뉴나 대화상자에만 사용합니다. |
| **Assistant 팔레트 금지.** 노란 크림 바탕 + 테라코타 / 녹슨 빨강, 보라, 인디고를 쓰지 않습니다. | 추첨된 팔레트를 따릅니다. |
| **작은 대문자 자간 라벨 금지.** | 읽기 쉬운 크기의 문장형 대소문자를 사용합니다. |
| **아이콘이 맨 위에 있는 기능 카드, 똑같은 카드 행 금지.** | 추첨된 섹션 청사진을 따릅니다. |
| **유리 효과 금지.** backdrop blur 패널이나 떠 있는 알약형 내비게이션을 쓰지 않습니다. | 단순한 바: 워드마크, 링크 몇 개, 동작 하나. |
| **이모지, 그라데이션 덩어리, 장식용 도형, 회색 막대만 있는 가짜 대시보드 금지.** | 실제 사진, 실제 인터페이스 조각, 또는 생략을 선택합니다. |
| **헤드라인 안에 강조 단어 하나만 다른 스타일로 넣지 않습니다** (이탤릭, 세리프, 색상, 밑줄). | 글꼴 한 종류, 색 하나로 쓰고 단어 자체가 강조를 전달하게 합니다. |
| **글꼴은 최대 두 종류, 대개 하나.** | 추첨된 타이포그래피 체계를 따릅니다. |

다음 세 곳은 고유 규칙을 사용하므로 검사기에서 예외입니다: 실제 코드인 pre / code (여기서 monospace가 적절함), 실제 표와 입력 필드 (선이 있을 수 있음), 루트에 data-ui 속성이 있는 실제 인터페이스 조각 (제품 자체 테두리와 메뉴; references/imagery.md §7 참고).

이 규칙이 생긴 이유를 솔직히 설명합니다. 일부는 연구에서 측정된 내용입니다: 사이트 247개 중 패널 점수 7.5 이상인 사이트의 아이콘 기능 카드는 1%, 6.5 미만 사이트는 28%였습니다. 알약 배지는 각각 14%와 34%, 그라데이션은 22%와 52%, 그림자는 24%와 48%, 작은 자간 대문자는 16%와 57%였습니다. 나머지는 소유자의 취향이며 현재 갤러리 유행에 역행합니다. monospace 라벨, 인덱스 번호, 헤어라인 격자는 오히려 약한 사이트보다 수상작에서 더 흔합니다. 그래서 생성기가 이를 모방하고 지금은 의상처럼 보이므로 예외 없이 금지합니다. references/tells.md에 날짜가 붙은 기록과 각 표현의 대체 방법이 있습니다.

장식을 제거하면 공간이 생깁니다. 다른 장식으로 채우지 않습니다. 규모로 채웁니다 (핵심 요소를 키움), 온전한 콘텐츠, 이 주제만을 위한 사진, 평면 색면을 사용합니다. 페이지당 한 번까지만 의도적으로 비워둡니다.

## 공예의 법칙

요약입니다. 숫자는 별도 표시가 없으면 연구에서 가져왔습니다.

**타이포그래피**
- 화면에서 역할을 하는 크기는 두세 가지입니다: 아주 큰 글자 하나, 작은 글자 하나, 중간 크기는 사용하지 않음. 조사한 사이트의 헤드라인 대 본문 크기 비율 중앙값은 4.3이며 상위 사이트는 훨씬 더 컸습니다 (최대 글자 크기: 상위 사이트 중앙값 8.4vw, 약한 사이트 5.0vw).
- 디스플레이 글꼴은 자간 -0.02~-0.05em, 행간 0.85–1.05. 본문은 16–20px, 행간 1.45–1.6, 한 줄 45–75자.
- 한 페이지에서 크기 단계는 최대 다섯 개. 글꼴 패밀리 하나가 일반적이며 (연구 사이트의 1/3) 두 개가 한계입니다.
- 기본 정렬은 왼쪽. 가운데 정렬은 페이지에서 한 번까지.

**공간**
- 한 격자와 좁은 바깥 여백 한 쌍 (16–32px)을 페이지 전체에서 사용합니다. 큰 요소는 가장자리까지 뻗습니다. 페이지 전체 텍스트 블록의 왼쪽 기준선은 두세 개만 둡니다.
- 비대칭은 격자 안에서만 허용하고 프레임은 대칭이어야 합니다. 바깥 여백 두 쪽은 같고 가운데에서 벗어난 제목은 격자 반대편의 요소로 균형을 맞춥니다.
- 섹션 사이 간격은 내부 요소 간격보다 분명히 커야 하며 데스크톱에서 120–240px입니다 (연구 중앙값 약 240px).
- 이웃한 섹션은 각각 다른 구성을 사용하고 카드 그리드를 만들지 않습니다.

**색상**
- 바탕 하나, 잉크 하나, 강조색 하나. 강조색은 액션과 다른 요소 한 곳 정도에만 사용합니다.
- 본문은 잉크색으로 표시합니다. 흐린 회색 글자로 페이지를 구성하면 미완성처럼 보입니다.
- 표면은 선이나 그림자가 아니라 약간의 색조 단계로 구분합니다.
- 섹션마다 전체 바탕색이 바뀔 수 있지만 다른 색으로 서서히 전환하지 않습니다.

**이미지**
- 작은 이미지 여섯 장보다 주도적인 이미지 한 장이 낫습니다. 상위 점수 사이트에서는 hero 미디어가 첫 화면의 절반 이상을 차지한 비율이 68%였습니다.
- crop 비율과 처리는 통일하며 방향에서 별도로 지시하지 않으면 모서리는 각지게 둡니다 (연구 사이트의 73%가 미디어에 둥근 모서리를 쓰지 않음).
- 이미지가 없다면 placeholder, 아이콘, 추상 도형을 쓰는 것보다 낫습니다. 주제의 실제 색과 정성을 담아 그린 그림이 둘보다 낫고, 출처를 밝힌 실제 세계의 사진이 가장 좋습니다.
- 찾은 사진은 프로젝트에 다운로드하고 페이지에 크레딧을 표기하며 보고서에 기록합니다. 고객 자체의 이미지인 것처럼 소개하지 않습니다.
- 헤드라인이나 설명문 위에 어떤 이미지도 겹치지 않습니다 (검사기에서 실패 처리).

**컴포넌트**
- 버튼: 단색 채움, 평면. 모서리는 각지거나 완전한 원형 중 한 방식을 선택합니다 (상위 사이트 중 52% 각진형, 23% 알약형. 9–16px의 “부드러운” 반경은 약한 사이트의 기본값). 상위 hero 대부분에는 버튼이 아예 없거나 하나만 있습니다.
- 내비게이션: 워드마크, 일반 링크 세 개에서 다섯 개, 액션 하나. 내비게이션 바 장식 없음.
- 컨트롤은 형태, 라벨, 위치로 사용 방법이 드러나야 합니다. 사용 방법 설명 문장이 있어야 작동할 것 같다면 그 문장을 추가하기보다 컨트롤을 다시 설계합니다. 입력 가능한 항목의 제한 안내는 다릅니다. 날짜 선택기나 일반 형식을 처리하는 parser를 써서 가능한 경우 제한을 먼저 제거합니다. 비밀번호 규칙, 파일 형식과 크기처럼 남는 제한은 필드 옆에 보이게 두고 aria-describedby로 연결합니다.
- Footer는 사이트맵이 아니라 디자인된 마무리입니다. 좋은 사이트 대부분은 footer에서 이름을 다시 전체 너비로 보여줍니다.

## 특별 사례

**기존 브랜드나 디자인 시스템이 있는 경우.** --keep palette,type을 전달하고 브랜드의 색상과 글꼴을 역할에 매핑한 뒤 방향표에서는 구도만 가져옵니다. 하우스 규칙은 계속 적용합니다. 브랜드가 금지된 장치 자체를 요구하면 (로고가 그라데이션에 놓임, 강조색이 보라색 등) 브랜드 에셋은 유지하고 보고서에 이유를 적은 다음 inspector에 --allow <rule>을 전달해 해당 규칙 하나만 허용합니다.

**기존 페이지 또는 앱 화면 리디자인, 스타일 변경, 검토.**

1. **수정 전 기록.** 프로젝트를 현재 상태로 실행하고 별도 폴더로 검사합니다 (앱 화면이면 inspect.mjs <url> --out .taste-skill/before --app). 소스도 lint합니다. 코드에서 프레임워크, 스타일 방식 (Tailwind v3 / v4, CSS modules, styled-components, 일반 CSS), 컴포넌트, 유지해야 할 것 (경로, 양식, 데이터, 동작, 브랜드 에셋)을 확인합니다.
2. **검토라면 여기서 멈춥니다.** 전 상태 스크린샷을 references/critique.md로 비평하고 검사기 측정값과 함께 발견 사항을 적습니다. 페이지를 가장 많이 개선할 변경 세 개를 지정합니다.
3. **스택, 콘텐츠, 정상 동작을 보존합니다.** 프레임워크나 스타일 라이브러리를 마이그레이션하지 않고 의존성 파일을 확인한 뒤에만 추가합니다. 스타일 변경은 레이아웃을 유지하고 추첨 방향에서 글꼴, 색상, 컴포넌트를 가져옵니다 (브랜드가 고정한 요소는 --keep). 리디자인은 전체 방향을 뽑고 기존 컴포넌트 안에서 청사진에 따라 섹션을 다시 구성합니다. 어느 방식이든 페이지의 실제 콘텐츠를 넣고 실행 절차 2단계부터 진행합니다.
4. **위험 대비 효과가 큰 순서로 작업:** 글꼴 (서체와 크기 체계), 색상 (바탕 하나, 잉크 하나, 강조색 하나), 프레임 (여백, 섹션 리듬, 첫 화면 제목, 모든 섹션 제목), 상태 (hover, focus, loading, empty, error), 마지막으로 일반 컴포넌트 (아이콘 카드, 알약 배지, 그라데이션 덩어리, 카드 그리드)를 추첨된 청사진으로 바꿉니다.
5. **개선을 입증합니다.** .taste-skill/after에 다시 검사하고 모든 너비에서 전후를 비교하며 기존에 작동하던 링크, 폼, 메뉴를 확인하고 측정값을 나란히 보고합니다.

**페이지가 아니라 컴포넌트나 단일 섹션.** 따를 방향이 있으면 draw를 건너뜁니다. 주변 디자인에 맞추고 하우스 규칙과 공예 법칙을 적용한 뒤 결과는 반드시 검사합니다.

**결제 시스템이나 폼 백엔드가 없는 경우.** brief에 실제 목적지가 있으면 기본 버튼이 그곳으로 이동합니다. 없으면 제목과 본문이 채워진 이메일을 엽니다 (방문자 선택을 미리 입력한 mailto). 상점이면 #checkout으로 연결하고 출시 전에 연결해야 한다고 보고서에 기록합니다. 가짜 결제 폼을 만들지 않습니다.

**Chrome 또는 Node 22가 없는 경우.** Node 18 이상에서 lint.mjs를 실행하고 사용 가능한 브라우저 도구로 스크린샷을 찍어 평가합니다. 보고서에 inspector를 실행할 수 없었다고 적습니다.

**네트워크가 없는 경우.** assets.mjs가 자료를 찾지 못하면 직접 이미지를 그리고 공개 컬렉션을 검색할 수 없었다고 보고합니다.
