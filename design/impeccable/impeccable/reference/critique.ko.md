### 목적

변하지 않는 대상 하나를 확정하고, 서로 독립된 평가 두 개를 수행한 뒤 디자인 비평을 종합하고 스냅샷을 저장한 다음 사용자에게 다음으로 개선할 부분을 묻습니다. 채팅 답변이 주요 산출물이고 스냅샷은 해당 실행의 보관본입니다.

### 반드시 지켜야 할 불변 조건

- Assessment A (디자인 검토)와 Assessment B (검출기 / 브라우저 근거)는 둘 다 필수입니다. 단, 네이티브 플랫폼은 예외입니다 (Assessment Orchestration 참고).
- 서브 에이전트 / Task 도구가 노출된 경우 Assessment A와 B는 반드시 별도의 격리된 서브 에이전트에서 실행해야 합니다. 이 문맥에서 인라인으로 실행하는 것은 “가능”하지만 **허용되지 않는 성능 저하 실행**입니다. 인라인 실행은 서브 에이전트 도구가 없거나 (확인을 묻는 하네스에서) 사용자가 거절한 경우에만 허용됩니다. 네이티브 플랫폼은 A만 실행합니다 (Assessment Orchestration 참고).
- 어떤 이유로든 성능 저하 실행을 했다면 보고서 첫 줄에 반드시 `⚠️ DEGRADED: single-context (<reason>)` 배너를 표시합니다. 성능 저하 실행을 알리지 않은 비평은 실패입니다.
- Assessment A는 검출기 결과가 상위 종합 문맥에 들어오기 전에 끝나야 합니다. 검출기 출력은 결정론적이지만 판단에 영향을 줄 수 있습니다.
- 검출기를 건너뛰면 비평 실행은 실패입니다. 단, 실제로 시도했지만 `impeccable detect`가 없거나 실행 중 중단된 경우, 또는 네이티브 플랫폼은 예외입니다 (Assessment Orchestration 참고).
- 확인 가능한 대상은 브라우저 검사 기능이 있을 때 반드시 브라우저로 확인합니다.
- 비평 시각화를 위해서만 시작한 로컬 서버는 백그라운드에서 실행하고 종료 방법을 기록해야 하며, 사용자가 유지해 달라고 하지 않는 한 최종 보고 전에 서버를 종료합니다.
- 스크립트 삽입에 성공해 페이지 안에서 검출기가 실행된 경우가 아니라면 사용자에게 보이는 오버레이가 있다고 주장하지 않습니다.
- 질문은 응답의 **맨 마지막**에 둡니다. 전체 보고서를 먼저 작성한 다음 질문하고 질문 뒤에는 아무 내용도 추가하지 않습니다. 구조화된 질문 뒤에 작성한 문장은 사용자가 답할 때까지 표시되지 않으므로 질문 뒤에 보고서를 쓰면 비평이 실행되지 않은 것처럼 보입니다.
- 대상 질문 또는 문자 그대로 `Questions skipped: <reason>` 줄로 끝나지 않은 실행은 미완료입니다. 보고서는 끝이 아닙니다.

### 설정

1. 대상을 구체적인 파일 경로나 URL로 확정합니다. 같은 표면을 가리키는 소스 경로와 개발 서버 URL이 모두 있다면 소스 경로를 우선합니다. 포트는 바뀌지만 경로는 바뀌지 않습니다.
   - “홈페이지” -> `site/pages/index.astro` 또는 `index.html`
   - “설정 모달” -> 기본 컴포넌트 파일
   - “이 페이지” -> 현재 URL 또는 소스 파일
2. 대상 slug를 정확하게 확인합니다.
   ```bash
   .agents/skills/impeccable/scripts/impeccable critique-storage slug "<resolved-path-or-url>"
   ```
   이후 명령에도 확정된 대상을 직접 전달할 수 있으며 같은 slug를 내부에서 계산합니다. slug를 직접 만들어 넣지 않습니다. 종료 코드가 0이 아니면 이번 실행의 저장과 추세 기록을 건너뛰되 비평은 계속합니다.
3. `.impeccable/critique/ignore.md`가 있으면 읽습니다. 이전 실행의 입력 중 비평이 사용하는 것은 이 파일뿐입니다. 일치하는 발견 사항은 조용히 제외합니다.

### 평가 오케스트레이션

**네이티브 플랫폼** (`ios` / `android` / `adaptive`): Assessment B는 적용되지 않습니다. `impeccable detect`와 브라우저 오버레이는 웹 마크업만 읽기 때문입니다. 현재 문맥에서 A만 실행하고 아래 두 서브 에이전트 게이트는 모두 건너뜁니다 (Codex 권한 질문 포함). B가 없으므로 A와 분리할 것이 없어 성능 저하 배너가 필요 없는 완전한 네이티브 절차입니다. 네이티브 소스에 `impeccable detect`를 실행하지 않습니다. 빈 결과를 문제가 없다는 뜻으로 오해할 수 있습니다.

Assessment A와 B는 서로 다른 서브 에이전트에 위임합니다. 서로의 출력을 보여주지 않습니다. 종합 전에는 발견 사항을 사용자에게 보여주지 않습니다.

서브 에이전트 게이트 (모든 하네스 공통):
- 아래의 하네스별 규칙이 우선 적용되지 않는 한, 서브 에이전트 / Task 도구가 노출되어 있으면 A와 B를 항상 격리된 병렬 서브 에이전트 둘로 실행합니다. 이것이 기본이며 필수입니다. 더 빠르다는 이유로 인라인 실행하지 않습니다.
- 데스크톱 앱 (Assessment B의 **Desktop apps** 참고)은 두 에이전트가 한 창을 동시에 제어하게 되므로 병렬 처리만 예외입니다. 창의 상태를 준비한 뒤 A를 실행하고, 완료되어 창을 원래대로 돌려놓을 때까지 기다린 다음 B를 실행합니다. 둘은 여전히 격리된 서브 에이전트이므로 성능 저하 경로가 아닙니다.
- “사용할 수 없음”은 한 가지 경우만 뜻합니다. 현재 세션에 서브 에이전트 / Task 도구가 노출되지 않았거나 (질문을 요청하는 하네스에서는) 사용자가 거절한 경우입니다. 불편하다는 뜻은 아닙니다.
- 서브 에이전트를 사용할 수 없는 경우에만 순차 실행으로 전환합니다. A를 끝내고 결과를 기록한 다음 B를 실행하고 종합한 뒤 성능 저하 배너를 표시합니다.
- 어느 방식이든 보고서 헤더에 사용한 방식을 선언합니다 (Report header provenance 참고). 서브 에이전트를 건너뛰고 배너를 표시하지 않는 것이 이 명령의 가장 흔한 실패 원인입니다.

Codex 서브 에이전트 게이트 (기본 규칙을 덮어씀 — Codex 권한 모델은 서브 에이전트 생성 전에 확인을 요청해야 함):
- 질문하는 것이 일반 절차이며 성능 저하가 아닙니다. 사용자가 승인해 생성하면 이중 에이전트 방식이며, 질문했다는 이유만으로 성능 저하 배너를 표시하지 않습니다.
- `spawn_agent`가 노출되고 사용자가 서브 에이전트 / 위임 / 병렬 작업을 명시적으로 허용한 경우 A와 B를 즉시 위임합니다 (데스크톱 앱에서는 기본 게이트대로 A 후 B를 실행).
- `spawn_agent`가 노출되었지만 사용자가 명시적으로 허용하지 않았다면 정확히 한 번만 묻습니다. “Impeccable critique는 기준점에 치우치지 않은 평가를 위해 서로 독립적인 서브 에이전트 두 개를 사용하도록 설계되어 있습니다. 이 비평에 서브 에이전트를 사용해도 될까요?” 그런 다음 답변을 기다립니다.
- 허용하면 A와 B를 실행합니다 (데스크톱 앱에서는 순차 실행). 거절하면 순차 실행하고 첫 줄을 `⚠️ DEGRADED: single-context (sub-agents declined by user)`로 시작합니다.
- `spawn_agent`가 노출되지 않았다면 묻지 말고 순차 실행한 뒤 `⚠️ DEGRADED: single-context (spawn_agent unavailable in this session)`로 시작합니다.
- 권한을 얻은 뒤 생성에 실패하면 순차 실행하고 `⚠️ DEGRADED: single-context (sub-agent spawn failed: <exact error>)`로 시작합니다.
자기완결적 프롬프트에 cwd, 대상, 라이브 URL, 참조 문서, 제품 맥락, 출력 규약을 포함하고 `fork_context: false`를 우선합니다. `fork_context: true`를 쓸 때는 `agent_type`, `model`, `reasoning_effort`를 생략합니다.

브라우저 자동화가 가능하면 각 평가는 각각 새 탭을 만듭니다. 대상 URL에 이미 열려 있어도 기존 탭은 재사용하지 않습니다. 데스크톱 앱만 예외입니다 (Assessment B의 **Desktop apps** 참고).

### Assessment A: 디자인 검토

관련 소스 파일을 읽고 브라우저 자동화가 가능하면 라이브 페이지를 시각적으로 검사합니다. 디자인 디렉터의 관점에서 평가합니다.

평가 항목:
- **디자인 고유성**: 구성, 상호작용, 시각 언어가 이 제품에 기반하는가, 아니면 어떤 제품에도 그대로 적용 가능한가? 검출기 출력을 보기 전에 판단합니다.
- **전체적인 디자인**: 위계, 정보 구조, 감정적 적합성, 발견 가능성, 구도, 타이포그래피, 색상, 접근성, 상태, 문구, 예외 사례.
- **인지 부하**: 아래 [Cognitive Load Assessment](#cognitive-load-assessment)를 참고합니다. 체크리스트 실패와 화면에 4개보다 많이 보이는 선택 지점을 보고합니다.
- **감정 여정**: peak-end rule, 감정적 저점, 중요한 순간에 안심할 수 있는지.
- **Nielsen 휴리스틱**: 아래 [Heuristics Scoring Guide](#heuristics-scoring-guide)를 참고합니다. 10가지 휴리스틱 모두 0–4점으로 평가하되, 모드 적용 규칙에 따라 점수를 강제할 수 없는 항목은 `n/a`로 표시합니다.

반환 내용: 디자인 고유성 판정, 휴리스틱 점수, 인지 부하, 감정 여정, 강점 2–3개, 우선순위 문제 3–5개, 페르소나별 위험 신호, 사소한 관찰, 도전적인 질문.

### Assessment B: 검출기 + 브라우저 근거

번들에 포함된 검출기를 실행하고 브라우저 시각화 근거를 확보합니다. 웹에서는 Assessment B가 필수이며 둘 다 끝날 때까지 A와 격리해야 합니다.

CLI 검사:
```bash
.agents/skills/impeccable/scripts/impeccable detect --json [target]
```

- 마크업 파일 / 디렉터리를 `[target]`으로 전달합니다. CSS 파일만 전달하지 않습니다.
- URL 대상은 CLI 검사를 건너뛰고 브라우저 시각화를 사용합니다.
- 검사 가능한 파일이 500개가 넘는 대규모 트리는 범위를 좁히거나 사용자에게 물어봅니다.
- 종료 코드 0 = 발견 사항 없음, 2 = 발견 사항 있음.
- 검출기 진입점이 없거나 로드에 실패하면 결정론적 검사가 불가능하다고 보고하고 브라우저 / 수동 검토를 계속합니다.

브라우저 시각화는 자동화가 가능한 경우 확인 가능한 대상에 필수입니다. 로컬 파일에는 localhost 개발 서버 / 정적 URL을 사용합니다. 사용 가능한 브라우저가 명시적으로 지원하지 않으면 `file://`을 피합니다. 오버레이 절차:

1. 새 탭을 만들고 이동합니다. 직접 Playwright / Puppeteer 스크립트를 만들기 전에 하네스의 기본 브라우저 / 캔버스 스크린샷 경로를 우선 사용합니다. 기본 브라우저 도구가 없을 때만 사용자 지정 스크립트로 대체합니다.
2. `document.title`을 설정하고 `<script>` 태그를 추가해 변경 가능한 스크립트 주입을 사전 확인합니다. 읽기 전용 evaluate API는 변경 가능 여부 확인으로 인정되지 않습니다.
3. 변경이 불가능하면 라이브 서버, 브라우저 표시, 스크립트 주입을 건너뛰고 대체 신호를 보고합니다.
4. 변경이 가능하면 `.agents/skills/impeccable/scripts/impeccable live-server --background`를 시작하고, 지원되는 경우 브라우저를 표시한 뒤 `[Human]`으로 라벨을 지정하고 페이지 맨 위로 스크롤합니다. `http://localhost:PORT/detect.js`를 주입하고 2–3초 기다린 다음 `impeccable` 콘솔 메시지를 읽고 `.agents/skills/impeccable/scripts/impeccable live-server stop --keep-inject`를 실행합니다. 오버레이는 브라우저를 통해 주입되므로 프로젝트 HTML에는 제거할 script 태그가 없습니다. 일반 `stop`은 프로젝트 진입 파일에 `live-inject --remove`를 실행하는데, 이는 읽기 전용 비평이 해서는 안 되는 수정입니다.
5. 여러 화면이 있는 대상은 대표 페이지 3–5개에 주입합니다.

**데스크톱 앱** (Electron, NW.js, CEF, WebView2): 열 URL이 없으므로 Assessment B는 실행 중인 앱에 연결합니다.

1. 로컬 DevTools 포트로 앱을 실행합니다: Electron / NW.js / CEF는 `--remote-debugging-port=9222`, WebView2는 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`를 사용합니다. 포트는 127.0.0.1에만 바인딩하고 이 기기 밖으로 공개하지 않습니다. 테스트 프로필과 테스트 데이터를 우선 사용합니다.
2. 검사할 상태 (경로, 열린 패널, 테마, 데이터)를 준비합니다. 검사는 현재 창 상태를 읽습니다. 창은 화면에 표시해 둡니다. 최소화하거나 숨기면 픽셀 대비를 읽지 못합니다.
3. `.agents/skills/impeccable/scripts/impeccable detect --cdp 9222 --target <part of the page URL or title> --json`을 실행합니다. URL 검사와 같은 JSON을 반환하고 페이지 상태를 그대로 둡니다. 페이지가 여러 개 열려 있으면 실패하면서 목록을 표시하므로 `--target`으로 하나를 지정해 다시 실행합니다.
4. 하네스의 CDP 도구로 스크린샷을 저장합니다 (같은 대상에서 `Page.captureScreenshot`). 라이브 서버 오버레이는 건너뜁니다. `[Human]` 탭이 없습니다.

앱 창은 하나이므로 두 평가 에이전트는 탭을 따로 열지 않고 순차적으로 작업합니다 (A 다음 B; 서브 에이전트 게이트 참고). 각 에이전트는 경로, 스크롤 위치, 테마, 패널을 원상 복구해야 합니다. macOS의 Tauri (WKWebView)와 Linux의 Tauri (WebKitGTK)는 CDP를 제공하지 않으므로 Assessment A와 소스 검사만 실행하고 Run Notes에 이를 명시합니다.

Codex Browser 참고: Browser skill을 사용합니다. `file://` URL로 Browser 시도를 낭비하지 않습니다. `[Human]` 오버레이 경로에서 변경 가능한 스크립트 주입을 확인한 뒤에만 `visibility.set(true)`를 호출하고 `get()`으로 검증합니다. 콘솔 결과는 `tab.dev.logs({ filter: "impeccable" })`로 확인합니다. Playwright의 `evaluate(...)`는 읽기 전용이므로 변경 작업에 의존하지 않습니다.

반환 내용: CLI 발견 사항 JSON / 개수, 해당 시 브라우저 콘솔 발견 사항, 거짓 양성, 건너뛰거나 실패한 브라우저 단계와 구체적인 이유.

Assessment B가 사용할 수 있는 CLI 발견 사항을 반환한 뒤에는 이를 재사용합니다. Assessment B가 실패했거나 결과가 잘렸거나 발견 건수, 규칙 이름, 파일 위치가 빠진 경우가 아니라면 상위 단계에서 `impeccable detect`를 다시 실행하지 않습니다.

Codex 오류 기록: 최종 Run Notes에는 대상 slug, ignore 목록, 평가 독립성, CLI 검출기, 브라우저 표시, 오버레이 주입, 라이브 서버 정리, 임시 파일 정리, 사용한 대체 신호를 모두 포함합니다. 보고서를 완성한 뒤 저장 과정 외의 저장소 상태 점검, 뒤늦은 API 조사, 무관한 검증을 실행하지 않습니다.

### 종합 비평 보고서 작성

두 평가를 하나의 보고서로 종합합니다. 단순히 붙여 넣지 않습니다. LLM 검토와 검출기가 일치한 부분, 검출기가 LLM이 놓친 문제를 발견한 부분, 검출 결과의 거짓 양성을 설명합니다.

채팅 답변이 사용자를 위한 주요 산출물입니다. 아래 전체 구조화 비평을 채팅에 작성하고 요약이나 링크로 대체하지 않습니다. 저장된 스냅샷은 실행 기록입니다.

Codex 최종 답변 참고: `$impeccable critique`는 보고서 산출물을 만듭니다. 따라서 최종 채팅 응답은 평소의 간결한 종료 메시지보다 충분히 길어야 합니다. 사용자가 요약을 명시적으로 요청하지 않는 한 제목을 “비평 요약”으로 붙이지 않습니다.

디자인 디렉터처럼 구성합니다.

#### 보고서 헤더 출처

성능 저하 실행을 숨길 수 없도록 보고서 첫 줄에 평가 방식이 반드시 표시되어야 합니다.
- 이중 에이전트: `Method: dual-agent (A: <agent-id> · B: <agent-id>)`
- 성능 저하: `⚠️ DEGRADED: single-context (<reason, e.g. no sub-agent tool exposed>)`
- 네이티브: `Method: design review only (detector not applicable, native platform)`

#### 디자인 상태 점수
> *아래 [Heuristics Scoring Guide](#heuristics-scoring-guide) 절을 참고합니다.*

Nielsen의 10가지 휴리스틱 점수를 표로 제시합니다.

| # | 휴리스틱 | 점수 | 핵심 문제 |
|---|---|---|---|
| 1 | 시스템 상태의 가시성 | ? | [구체적 발견 또는 문제가 없으면 "n/a"] |
| 2 | 시스템과 현실 세계의 부합 | ? | |
| 3 | 사용자 제어와 자유 | ? | |
| 4 | 일관성과 표준 | ? | |
| 5 | 오류 예방 | ? | |
| 6 | 기억보다 인식 | ? | |
| 7 | 유연성과 효율성 | ? | |
| 8 | 심미성과 미니멀 디자인 | ? | |
| 9 | 오류 인식, 진단, 복구 지원 | ? | |
| 10 | 도움말과 문서 | ? | |
| **총점** | | **??/해당 최대 점수** | **[등급 구간]** |

적용 가능한 최대 점수는 실제로 채점한 휴리스틱 수 × 4입니다. 모두 적용하면 **/40**, 두 개가 `n/a`이면 **/32**입니다. 부분 점수를 /40으로 표시하지 않습니다.

점수는 솔직하게 매깁니다. 4점은 정말 훌륭한 경우이며 단지 “쓸 만함”을 뜻하지 않습니다. 실제 인터페이스 대부분은 40점 중 20–32점입니다.

**모드 적용성**: Persuade와 Experience 표면 (랜딩 페이지, 캠페인, 포트폴리오, 작품 모음)에서는 휴리스틱 7 (유연성과 효율성)과 10 (도움말과 문서)을 `n/a`로 평가할 수 있습니다. 검토 대상에 실제로 적용할 수 없는 다른 항목도 `n/a`가 가능합니다. 점수 셀에 `n/a`와 한 줄 이유를 적고 해당 최대 점수로 재정규화합니다 (예: 두 항목이 n/a이면 **24/32**). 그래야 등급 구간이 비례를 유지합니다. 저장 스냅샷에는 적용 최대 점수와 n/a로 처리한 휴리스틱을 기록합니다.

#### 디자인 고유성 판정

**여기서 시작합니다.** 이 결과물이 이 제품만을 위해 설계된 느낌인가요, 아니면 어떤 제품에나 적용 가능한가요?

**LLM 평가**: 디자인 고유성에 대한 기준점 없는 평가를 합니다. 전체적인 응집도, 구조적 유사성, 제품 종류를 가리지 않고 적용되는 선택, 제품 고유의 성격을 살릴 기회를 놓쳤는지 다룹니다.

**결정론적 검사**: 자동 검출기가 찾은 내용을 건수와 파일 위치와 함께 요약합니다. LLM이 놓쳤지만 검출기가 잡은 문제를 표시하고 거짓 양성을 구분합니다. 네이티브 플랫폼에서는 `not applicable (native platform)`이라고 씁니다.

**시각 오버레이** (주입에 성공한 경우): 검출된 문제를 강조하는 오버레이가 브라우저의 **[Human]** 탭에 표시되고 있다고 사용자에게 알립니다. 콘솔 출력 결과를 요약합니다. 브라우저 시각화를 시도했지만 주입에 실패하면 사용자가 볼 수 있는 신뢰할 만한 오버레이가 없다고 말하고 대체 신호를 설명합니다.

#### 전체 인상
무엇이 잘 되고 무엇이 잘 안 되는지, 가장 큰 기회 하나를 간단히 표현합니다.

#### 잘된 점
잘된 점 2–3개를 짚습니다. 왜 효과적인지 구체적으로 설명합니다.

#### 우선순위 문제
영향이 가장 큰 디자인 문제 3–5개를 중요도 순으로 정리합니다.

각 문제에 **P0–P3 심각도**를 붙입니다 ([Issue Severity](#issue-severity-p0p3) 참고).
- **[P?] 무엇**: 문제를 명확하게 지정
- **중요한 이유**: 사용자 경험이나 목표를 어떻게 해치는지
- **수정 방법**: 구체적인 조치
- **권장 명령어**: 다음 목록에서 문제를 해결할 명령을 지정: $impeccable adapt, $impeccable animate, $impeccable audit, $impeccable bolder, $impeccable clarify, $impeccable colorize, $impeccable critique, $impeccable delight, $impeccable distill, $impeccable document, $impeccable harden, $impeccable layout, $impeccable onboard, $impeccable optimize, $impeccable overdrive, $impeccable polish, $impeccable quieter, $impeccable shape, $impeccable typeset

#### 페르소나 위험 신호
> *아래 [Persona-Based Design Testing](#persona-based-design-testing)을 참고합니다.*

이 인터페이스 유형에 가장 관련 있는 페르소나 2–3개를 자동으로 선택합니다 (참조 표 사용). `AGENTS.md`에 `impeccable init`이 생성한 `## Design Context` 절이 있으면 대상 고객 / 브랜드 정보에서 프로젝트별 페르소나 1–2개도 만듭니다.

선택한 각 페르소나가 주요 작업을 수행한다고 가정하고 구체적인 위험 신호를 적습니다.

#### 사소한 관찰
작지만 해결할 가치가 있는 문제를 간단히 기록합니다.

#### 생각해 볼 질문
더 나은 해법을 찾게 할 도전적인 질문:
- “주요 작업을 더 눈에 띄게 하면 어떨까요?”
- “이 정도로 복잡해야 하나요?”
- “자신감 있는 버전은 어떤 모습일까요?”

#### 실행 메모
간결하게 씁니다. 대상 slug, ignore 목록, 평가 독립성, CLI 검출기, 브라우저 표시, 오버레이 주입, 라이브 서버 정리, 임시 파일 정리를 포함합니다. 실패하거나 건너뛴 단계는 관찰된 구체적인 이유와 사용한 대체 신호를 적습니다. 최종 채팅 답변에는 저장 후 스냅샷 쓰기 상태와 추세 읽기 상태도 포함합니다.

Codex 실행 메모는 최종 채팅 답변에만 포함합니다. 저장 스냅샷 본문에는 넣지 않습니다. 스냅샷 저장, 추세 읽기, 임시 파일 정리는 저장 이후에 진행되므로 메모를 본문에 넣으면 “저장 후 처리 대기”처럼 오래된 상태를 저장할 수 있습니다.

**기억할 점**:
- 직접적으로 말합니다. 모호한 피드백은 시간을 낭비합니다.
- 구체적으로 말합니다. “몇몇 요소”가 아니라 “제출 버튼”이라고 지목합니다.
- 무엇이 잘못됐는지와 사용자에게 중요한 이유를 함께 설명합니다.
- 구체적인 해결책을 제안합니다. “검토해 볼 수 있습니다” 같은 표현은 빼십시오.
- 우선순위를 엄격히 정합니다. 전부 중요하다면 아무것도 중요하지 않습니다.
- 비판을 완곡하게 만들지 않습니다. 훌륭한 디자인을 출시하려면 개발자가 솔직한 피드백을 받아야 합니다.

### 보고서 전달

저장 작업 전에 전체 보고서를 채팅에 작성합니다. 이것이 산출물이며, 그 아래의 내용은 처리 기록입니다.

이 순서를 먼저 지킵니다. 가장 흔한 실패는 보고서를 처음부터 저장용 heredoc에 작성하고 사용자가 읽을 수 있는 보고서를 남기지 않는 것입니다. 파일로 작성하는 것은 전달이 아닙니다. 결과물이 `.impeccable/critique/`에만 있으면 사용자가 받은 것은 없습니다.

보고서 전달은 실행의 끝이 아닙니다. 그 뒤에도 추세 정보와 마무리가 남습니다.

### 스냅샷 저장

위 보고서를 확정한 뒤 `.impeccable/critique/`에 저장해 사용자가 다시 볼 수 있게 하고 `$impeccable polish`가 우선순위 문제를 이어받을 수 있도록 합니다.

Setup slug가 null (모호하거나 루트 수준 대상)이면 이 단계는 건너뜁니다.

1. 본문을 임시 파일에 씁니다. 전체 비평 보고서 (휴리스틱 표, 디자인 고유성 판정, 우선순위 문제, 페르소나 위험 신호, 사소한 관찰, 질문)를 사용하되, 뒤에 나오는 “Ask the User” / “Recommended Actions” 절 앞에서 끝냅니다.

   이는 이미 전달한 보고서를 후속 명령에서 읽도록 복사하는 단계입니다. 사용자에게 전달하는 절차가 아닙니다. heredoc에서 처음으로 보고서를 작성하고 있다는 걸 알게 되면 보고서 전달 단계를 빠뜨린 것입니다. 되돌아가 먼저 보고서를 보내야 합니다.

   Codex: 임시 본문 파일에서 Run Notes를 제외합니다. 저장, 추세 읽기, 임시 파일 정리는 저장 이후이므로 Run Notes는 최종 채팅 답변에만 둡니다.

2. `IMPECCABLE_CRITIQUE_META` (JSON)로 구조화된 메타데이터를 전달한 뒤 쓰기 명령을 실행합니다.
   ```bash
   IMPECCABLE_CRITIQUE_META='{"target":"<user phrasing>","total_score":<n>,"max_score":<n>,"na_heuristics":"<comma-separated numbers, or empty>","p0_count":<n>,"p1_count":<n>}' \
     .agents/skills/impeccable/scripts/impeccable critique-storage write "<resolved target>" <body-file>
   ```
   `max_score`는 휴리스틱 적용성을 반영한 최대 점수입니다 (모든 항목 적용 시 40). 따라서 이후 실행에서 재정규화된 점수와 전체 점수를 구분할 수 있습니다. 로컬 파일 대상이면 helper가 정확한 콘텐츠 지문도 기록해 `$impeccable polish`가 Git 상태나 타임스탬프에 기대지 않고 검토 당시 바이트와 이후 변경을 구별할 수 있습니다. helper는 저장한 절대 경로를 출력합니다. 해당 파일은 디스크에 남깁니다. 이 실행에서 저장 파일을 닫지 않습니다.

3. 쓰기 시도가 끝난 뒤 성공 여부와 관계없이 임시 본문 파일을 삭제합니다. 삭제에 실패하면 최종 출력에 `temp-file cleanup failed: <reason>`이라고 간략히 언급하되 비평을 중단하지 않습니다.

4. 맥락을 위해 추세를 읽습니다.
   ```bash
   .agents/skills/impeccable/scripts/impeccable critique-storage trend "<resolved target>" 5
   ```
   방금 저장한 항목을 포함해 최근 다섯 번의 frontmatter 항목을 JSON 배열로 반환합니다.

5. 사용자에게 보이는 출력에 보고서 뒤, 질문 앞에 한 줄을 추가합니다.

   > **`<slug>` 추세 (최근 5회): 24 → 28 → 32 → 29 → 32 (40점 만점)**
   > `.impeccable/critique/<filename>`에 저장했습니다.

   각 추세 항목의 `max_score`를 읽습니다. 모든 항목의 최대 점수가 같으면 위처럼 분모를 한 번만 씁니다. 다르면 점수마다 분모를 붙여 (`24/32 → 30/40`) 점수가 서로 다른 휴리스틱 집합을 채점했으므로 직접 비교할 수 없다고 설명합니다. 오래된 항목에서 `max_score`가 누락되면 40으로 간주합니다.

   slug에 대한 첫 실행이라면 점수 하나만 표시하고 “이 대상의 첫 실행이라 아직 비교할 추세가 없습니다.”라고 씁니다.

6. **실행을 마무리합니다.** 아래 Ask the User로 이동해 질문을 내거나, 허용 개수 조건을 충족하면 `Questions skipped: <reason>` 줄을 출력합니다. 이 단계를 마칠 때까지 실행은 완료가 아닙니다. 저장은 처리 기록일 뿐이며, 여기서 멈추면 사용자에게 보고서만 남고 다음 진행 방법이 없으며 `$impeccable polish`도 우선순위 정보를 이어받지 못합니다.

자동 저장 절차입니다. helper의 JSON 출력을 사용자에게 보여주지 않습니다. 사람이 읽을 수 있는 추세 한 줄과 저장 경로만 표시합니다. 여기서 오류가 나도 나머지 절차를 중단하지 말고 오류를 출력한 뒤 계속합니다.

### 사용자에게 질문하기

**발견 사항을 제시한 뒤**, 실제 발견을 바탕으로 구체적인 질문을 합니다. Codex의 구조화된 사용자 입력 / 질문 도구가 있으면 사용하고, 없으면 채팅에서 직접 질문한 뒤 답변을 기다립니다. 보고서를 담은 메시지 안에서 질문을 같이 하며 보고서를 먼저 쓰고 질문을 맨 마지막에 둡니다. 구조화된 질문 뒤의 문장은 응답 전까지 표시되지 않습니다.

질문은 다음 방향을 따르되 실제 발견에 맞춥니다.

1. **우선순위 방향**: 발견된 문제 중 지금 가장 먼저 다룰 범주를 묻습니다. 예: “시각적 위계, 색상, 정보 과밀 문제를 찾았습니다. 무엇부터 해결할까요?” 상위 문제 범주 2–3개를 선택지로 제시합니다.
2. **디자인 의도**: 분위기가 맞지 않으면 의도된 것인지 묻습니다. 예: “인터페이스가 차갑고 기업적으로 느껴집니다. 의도된 톤인가요, 아니면 더 따뜻하거나 대담하거나 장난스럽게 할까요?” 문제를 해결할 2–3개 분위기 방향을 선택지로 제시합니다.
3. **범위**: 어느 정도까지 진행할지 묻습니다. 예: “문제 N개를 찾았습니다. 전체를 수정할까요, 상위 3개에 집중할까요?” “상위 3개만”, “모든 문제”, “치명적인 문제만” 같은 범위 선택지를 제시합니다.
4. **제약** (선택, 관련 있을 때만 질문): 여러 부분에 영향이 있으면 변경하면 안 되는 영역이 있는지 묻습니다. 예: “그대로 유지해야 할 섹션이 있나요?” 그러면 이미 완료된 영역을 건드리지 않을 수 있습니다.

**질문 규칙**:
- 모든 질문은 보고서의 구체적인 발견을 언급해야 합니다. 일반적인 “대상 사용자는 누구인가요?”를 묻지 않습니다.
- 질문은 최대 2–4개로 제한합니다. 사용자 시간을 존중합니다.
- 열린 질문이 아니라 구체적인 선택지를 제공합니다.
- 우선순위 문제가 **3개 미만**인 경우에만 질문을 생략할 수 있습니다. 실제 개수를 셉니다. 느낌상 단순하다는 이유로 생략하지 않습니다. 3개 이상이면 질문이 필수입니다.

**최종 질문 게이트**: 사용자에게 보이는 응답에는 구체적인 질문이 있거나, 생략을 허용한 개수를 밝히는 문자 그대로의 줄 `Questions skipped: <reason>`이 반드시 포함되어야 합니다. 각 질문은 실제 비평 결과에 기반한 구체적 선택지 2–3개를 포함합니다. 열린 질문만 하고 끝내지 않으며 둘 다 없이 끝내지도 않습니다. 보고서 다음에 아무 질문도 하지 않고 생략 줄도 없으면 이 명령에서 가장 흔한 실패가 됩니다.

2. **`$command-name`**: 수정 내용 설명 (구체적인 맥락 포함)

**추천 규칙**:

- 우선순위 문제마다 적절한 명령을 지정합니다.

- 사용자가 범위를 제한했다면 그 범위의 항목만 포함합니다.

### 인지 부하 평가

인지 부하는 인터페이스를 사용할 때 필요한 전체 정신적 노력입니다. 과부하된 사용자는 실수하고, 좌절하고, 떠납니다. 이 참고 자료는 인지 과부하를 찾아 수정하는 데 도움이 됩니다.

---

#### 인지 부하의 세 가지 유형

##### 내재적 부하: 과업 자체
사용자가 하려는 일 자체에 내재한 복잡성입니다. 없앨 수는 없지만 구조화할 수 있습니다.

**관리 방법**:
- 복잡한 과업을 명확한 단계로 나누기
- 템플릿, 기본값, 예시로 발판 제공
- 점진적 공개: 지금 필요한 것을 보여주고 나머지는 숨기기
- 관련된 결정을 함께 묶기

##### 외재적 부하: 나쁜 디자인
잘못된 디자인 선택으로 생기는 정신적 노력입니다. **과감히 없앱니다.** 순수한 낭비입니다.

**흔한 원인**:
- 사용자가 머릿속 지도를 그려야 하는 혼란스러운 내비게이션
- 의미를 추측하게 만드는 불명확한 라벨
- 주의를 놓고 경쟁하는 시각적 잡음
- 일관되지 않은 패턴 때문에 학습이 불가능함
- 사용자 의도와 결과 사이의 불필요한 단계

##### 본질적 학습 부하: 배우는 노력
이해를 쌓는 데 쓰는 정신적 노력입니다. 이것은 *좋은* 인지 부하이며 숙련으로 이어집니다.

**지원 방법**:
- 복잡성을 점진적으로 드러내기
- 학습에 보상하는 일관된 패턴 사용
- 올바르게 이해했음을 확인하는 피드백 제공
- 장문의 텍스트 대신 행동을 통해 가르치는 온보딩

---

#### 인지 부하 체크리스트

다음 8개 항목으로 인터페이스를 평가합니다.

- [ ] **초점 하나**: 경쟁 요소에 방해받지 않고 핵심 과업을 완료할 수 있는가?
- [ ] **덩어리화**: 정보가 소화 가능한 묶음으로 제시되는가 (묶음당 ≤4개 항목)?
- [ ] **그룹화**: 관련 항목이 시각적으로 모여 있는가 (근접성, 테두리, 공통 배경)?
- [ ] **시각적 위계**: 화면에서 가장 중요한 것이 무엇인지 바로 알 수 있는가?
- [ ] **한 번에 하나**: 다음으로 넘어가기 전에 결정 하나에 집중할 수 있는가?
- [ ] **선택 최소화**: 각 결정 지점에서 보이는 선택지가 ≤4개로 단순화되었는가?
- [ ] **작업 기억**: 현재 화면에서 행동하려고 이전 화면 정보를 기억해야 하는가?
- [ ] **점진적 공개**: 사용자가 필요할 때만 복잡성이 드러나는가?

**점수 계산**: 실패한 항목 수를 셉니다. 실패 0–1개 = 인지 부하 낮음 (양호). 2–3개 = 보통 (가까운 시일 내 해결). 4개 이상 = 인지 부하 높음 (중대 문제).

---

#### 작업 기억 규칙

**사람의 작업 기억은 한 번에 최대 4개 항목**을 유지할 수 있습니다 (Cowan, 2001이 수정한 Miller의 법칙).

각 결정 지점에서 사용자가 동시에 고려해야 하는 구별된 선택지, 행동, 정보 수를 셉니다.
- **≤4개**: 작업 기억 한계 이내, 감당 가능
- **5–7개**: 한계에 가까움. 그룹화나 점진적 공개 고려
- **8개 이상**: 과부하. 사용자는 건너뛰거나 잘못 누르거나 포기할 수 있음

**실제 적용 예**:
- 작업 버튼: 기본 버튼 1개, 보조 1–2개, 나머지는 메뉴로 묶기
- 내비게이션 메뉴: 최상위 항목 ≤5개 (나머지는 명확한 범주 아래 그룹화)
- 긴 글: 읽기 경로 하나를 만들고 관련 링크를 흐름 중간에 흩뿌리지 말고 끝의 한 블록에 모으기
- 문서 사이드바: 그룹화하기 전에 한 레벨에서 같은 단계의 선택지를 ≤4개만 표시
- 포트폴리오 / 갤러리 인덱스: 화면마다 결정 하나 (어떤 작품을 열지). 필터, 정렬, 태그 컨트롤을 한꺼번에 두지 않기

---

#### 흔한 인지 부하 위반

##### 1. 선택지의 벽
**문제**: 위계 없이 선택지 10개 이상을 한꺼번에 보여줌.
**해결**: 범주로 묶고 추천 항목을 강조하며 점진적 공개 사용.

##### 2. 기억 다리
**문제**: 3단계를 완료하려고 사용자가 1단계 정보를 기억해야 함.
**해결**: 관련 맥락을 계속 보이게 하거나 필요한 위치에서 다시 보여줌.

##### 3. 숨겨진 내비게이션
**문제**: 사용자가 위치를 머릿속으로 파악해야 함.
**해결**: 현재 위치를 항상 표시합니다 (breadcrumb, 활성 상태, 진행 표시기).

##### 4. 전문 용어 장벽
**문제**: 기술 또는 도메인 용어를 해석하는 데 사용자의 노력이 필요함.
**해결**: 쉬운 말을 사용합니다. 도메인 용어가 불가피하면 같은 위치에서 뜻을 설명합니다.

##### 5. 시각적 잡음 바닥
**문제**: 모든 요소의 시각적 무게가 같아 눈에 띄는 것이 없음.
**해결**: 명확한 위계를 설정합니다. 기본 요소 하나, 보조 요소 2–3개, 나머지는 낮은 대비로 처리합니다.

##### 6. 일관되지 않은 패턴
**문제**: 비슷한 동작이 위치에 따라 다르게 작동함.
**해결**: 상호작용 패턴을 표준화합니다. 같은 종류의 동작은 같은 종류의 UI를 사용합니다.

##### 7. 멀티태스킹 요구
**문제**: 인터페이스가 여러 입력을 동시에 처리하도록 요구함 (읽기 + 결정 + 탐색).
**해결**: 단계를 순서대로 진행합니다. 한 번에 한 가지씩 하게 합니다.

##### 8. 맥락 전환
**문제**: 결정 하나를 내리려고 여러 화면 / 탭 / 모달을 오가며 정보를 모아야 함.
**해결**: 각 결정에 필요한 정보를 한 곳에 모읍니다. 왕복 이동을 줄입니다.

### 휴리스틱 점수 가이드

Nielsen의 사용성 휴리스틱 10개를 각각 0–4점으로 평가합니다. 솔직하게 채점합니다. 4점은 정말 훌륭한 경우이지 “그럭저럭 괜찮음”이 아닙니다.

#### Nielsen의 10가지 휴리스틱

##### 1. 시스템 상태의 가시성

적절한 시점에 맞는 피드백을 제공해 시스템이 무엇을 하는지 사용자에게 알립니다.

**확인할 항목**:
- 비동기 작업 중 로딩 표시
- 사용자 작업 (저장, 제출, 삭제)에 대한 확인
- 여러 단계 과정을 위한 진행 표시기
- 내비게이션상 현재 위치 (breadcrumb, 활성 상태)
- 양식 검증 피드백 (제출 시에만 표시하지 말고 입력 옆에 표시)

**점수**:
| 점수 | 기준 |
|---|---|
| 0 | 피드백이 없음. 사용자가 무슨 일이 일어났는지 추측해야 함 |
| 1 | 드물게 피드백 제공. 대부분의 동작에 보이는 반응이 없음 |
| 2 | 부분적임. 일부 상태는 전달되지만 주요 공백이 남음 |
| 3 | 양호함. 대부분 작업에 명확한 피드백이 있고 사소한 공백만 있음 |
| 4 | 탁월함. 모든 동작이 확인되고 진행 상황이 항상 보임 |

##### 2. 시스템과 현실 세계의 부합

사용자의 언어로 말합니다. 현실 세계의 관습을 따릅니다. 정보가 자연스럽고 논리적인 순서로 나타납니다.

**확인할 항목**:
- 익숙한 용어 사용 (설명 없는 전문 용어 없음)
- 사용자의 기대와 일치하는 논리적 정보 순서
- 알아보기 쉬운 아이콘과 비유
- 대상 사용자에게 적합한 도메인 표현
- 자연스러운 읽기 흐름 (왼쪽에서 오른쪽, 위에서 아래 우선)

**점수**:
| 점수 | 기준 |
|---|---|
| 0 | 기술 전문 용어뿐이며 사용자에게 생소함 |
| 1 | 대부분 혼란스러움. 사용하려면 도메인 지식이 필요함 |
| 2 | 혼합됨. 쉬운 표현도 있지만 전문 용어가 섞여 나옴 |
| 3 | 대체로 자연스러움. 가끔 용어에 맥락이 필요함 |
| 4 | 전반적으로 사용자의 언어로 자연스럽게 말함 |

##### 3. 사용자 제어와 자유

사용자는 긴 대화나 과정을 거치지 않고 원치 않는 상태에서 벗어날 수 있는 명확한 “비상구”가 필요합니다.

**확인할 항목**:
- 실행 취소 / 다시 실행
- 양식과 모달의 취소 버튼
- 안전한 상태로 돌아갈 명확한 내비게이션 (홈, 이전)
- 필터, 검색, 선택을 쉽게 초기화
- 길거나 여러 단계인 과정에서 빠져나오기

**점수**:
| 점수 | 기준 |
|---|---|
| 0 | 사용자가 갇힘. 새로 고치지 않고는 빠져나갈 수 없음 |
| 1 | 빠져나오기 어려움. 찾기 힘든 경로를 찾아야 탈출할 수 있음 |
| 2 | 일부 종료 방법이 있음. 주 흐름은 빠져나갈 수 있지만 예외 상황은 안 됨 |
| 3 | 제어가 양호함. 대부분의 동작을 취소하거나 되돌릴 수 있음 |
| 4 | 완전한 제어. 어디서든 실행 취소, 취소, 뒤로, 탈출 가능 |

##### 4. 일관성과 표준

서로 다른 단어, 상황, 동작이 같은 뜻인지 사용자가 고민하게 만들지 않습니다.

**확인할 항목**:
- 인터페이스 전반의 일관된 용어
- 같은 동작이 어디서든 같은 결과를 만듦
- 플랫폼 관례를 따름 (표준 UI 패턴)
- 시각적 일관성 (색상, 타이포그래피, 간격, 컴포넌트)
- 일관된 상호작용 패턴 (같은 제스처 = 같은 동작)

**점수**:
| 점수 | 기준 |
|---|---|
| 0 | 전반적으로 일관성이 없음. 서로 다른 제품을 이어 붙인 듯함 |
| 1 | 불일치가 많음. 비슷한 요소가 다르게 보이거나 동작함 |
| 2 | 부분적으로 일관됨. 주요 흐름은 맞지만 세부 사항이 다름 |
| 3 | 대체로 일관됨. 가끔 다르지만 혼란을 주지 않음 |
| 4 | 완전히 일관됨. 응집된 시스템과 예측 가능한 동작 |

##### 5. 오류 예방

좋은 오류 메시지보다 애초에 문제가 생기지 않도록 하는 디자인이 낫습니다.

**확인할 항목**:
- 삭제 / 덮어쓰기 같은 파괴적 동작 전 확인
- 잘못된 입력을 막는 제약 (날짜 선택기, 드롭다운)
- 오류를 줄이는 스마트 기본값
- 오해를 막는 명확한 라벨
- 자동 저장과 초안 복구

**점수**:
| 점수 | 기준 |
|---|---|
| 0 | 오류가 쉽게 발생하고 어떤 안전장치도 없음 |
| 1 | 보호 조치가 부족함. 일부 입력만 검증하고 대부분은 검증하지 않음 |
| 2 | 일부 예방. 흔한 오류는 잡지만 예외 상황은 놓침 |
| 3 | 예방 수준이 양호함. 대부분의 오류 경로를 미리 차단 |
| 4 | 탁월함. 적절한 제약으로 오류가 거의 불가능함 |

##### 6. 기억보다 인식

기억 부담을 줄입니다. 객체, 동작, 선택지를 화면에 보이게 하거나 쉽게 다시 찾을 수 있게 합니다.

**확인할 항목**:
- 숨겨진 메뉴에 묻히지 않는 선택지
- 필요한 순간의 맥락 도움말 (툴팁, 인라인 안내)
- 최근 항목과 기록
- 자동 완성 및 제안
- 아이콘에 붙은 라벨 (아이콘만 있는 내비게이션 지양)

**점수**:
| 점수 | 기준 |
|---|---|
| 0 | 기억 의존이 큼. 경로와 명령을 외워야 함 |
| 1 | 대부분 기억에 의존. 숨겨진 기능이 많고 보이는 단서는 적음 |
| 2 | 일부 보조 기능이 있음. 주요 동작은 보이지만 부차 기능은 숨겨짐 |
| 3 | 인식 지원이 양호함. 대부분 쉽게 찾을 수 있고 기억 요구는 적음 |
| 4 | 모든 것이 찾기 쉬움. 외울 필요가 전혀 없음 |

##### 7. 유연성과 효율성

초보자에게는 보이지 않는 가속 기능이 전문가의 상호작용을 빠르게 합니다.

**확인할 항목**:
- 자주 쓰는 동작의 키보드 단축키
- 사용자 지정 가능한 인터페이스 요소
- 최근 항목과 즐겨찾기
- 여러 항목을 한 번에 처리하는 동작
- 기본 사용을 복잡하게 만들지 않는 고급 사용자 기능

**점수**:
| 점수 | 기준 |
|---|---|
| 0 | 한 가지 고정 경로만 있음. 단축키나 대안 없음 |
| 1 | 유연성이 제한됨. 기본 경로의 대안이 거의 없음 |
| 2 | 일부 단축키가 있음. 기본 키보드 지원, 제한적인 일괄 작업 |
| 3 | 가속 기능이 양호함. 키보드 내비게이션, 일부 사용자 지정 가능 |
| 4 | 유연성이 높음. 여러 경로, 고급 기능, 사용자 지정 지원 |

##### 8. 심미성과 미니멀 디자인

인터페이스에는 불필요하거나 드물게 필요한 정보가 없어야 합니다. 모든 요소는 목적이 있어야 합니다.

**확인할 항목**:
- 각 단계에 필요한 정보만 표시
- 주의를 이끄는 명확한 시각 위계
- 목적에 맞게 색상과 강조 사용
- 주의를 빼앗는 장식적 잡음 없음
- 집중되고 정돈된 레이아웃

**점수**:
| 점수 | 기준 |
|---|---|
| 0 | 압도적임. 모든 요소가 똑같이 주의를 끌려고 함 |
| 1 | 복잡하고 잡음이 많아 중요한 내용을 찾기 어려움 |
| 2 | 일부 혼잡함. 주요 콘텐츠는 명확하지만 주변이 산만함 |
| 3 | 대체로 깔끔하고 초점이 분명하며 시각 잡음은 약간 있음 |
| 4 | 완벽하게 절제됨. 모든 요소가 화면을 차지할 이유가 있음 |

##### 9. 사용자가 오류를 인식하고 진단하고 복구하도록 지원

오류 메시지는 쉬운 언어를 사용하고 문제를 정확히 표시하며 해결 방법을 제안해야 합니다.

**확인할 항목**:
- 쉬운 오류 메시지 (사용자에게 오류 코드만 보여주지 않음)
- 구체적인 문제 지목 (“@가 빠졌습니다” — “잘못된 입력” 대신)
- 실행 가능한 복구 제안
- 문제 발생 위치 근처에 오류 표시
- 입력 양식을 지우지 않는 비차단 오류 처리

**점수**:
| 점수 | 기준 |
|---|---|
| 0 | 해독하기 어려운 오류. 코드나 전문 용어만 있거나 메시지가 전혀 없음 |
| 1 | 모호한 오류. 안내 없이 “문제가 발생했습니다”라고만 표시 |
| 2 | 명확하지만 도움이 되지 않음. 문제는 이름 붙이지만 해결 방법은 없음 |
| 3 | 해결 제안이 있음. 문제를 알려주고 다음 단계 제시 |
| 4 | 완벽한 복구 지원. 문제를 정확히 지목하고 해결을 안내하며 사용자의 작업을 보존 |

##### 10. 도움말과 문서

문서 없이도 시스템을 사용할 수 있더라도 도움말은 찾기 쉽고, 작업에 초점을 두며, 간결해야 합니다.

**확인할 항목**:
- 검색 가능한 도움말 또는 문서
- 맥락에 맞는 도움말 (툴팁, 인라인 안내, 안내 투어)
- 기능 목록이 아닌 작업 중심의 구성
- 간결하고 훑어보기 쉬운 내용
- 현재 맥락을 벗어나지 않고 도움말에 접근 가능

**점수**:
| 점수 | 기준 |
|---|---|
| 0 | 어디에도 도움말이 없음 |
| 1 | 도움말은 있지만 찾기 어렵거나 관련이 없음 |
| 2 | 기본 도움말. FAQ나 문서는 있지만 맥락에 맞지 않음 |
| 3 | 문서가 양호함. 검색 가능하고 대부분 작업 중심 |
| 4 | 맥락에 맞는 도움말이 뛰어남. 적절한 순간에 필요한 정보를 제공 |

#### 점수 요약

**총점 최대**: 40점 (휴리스틱 10개 × 최대 4점)

| 점수 범위 | 평가 | 의미 |
|---|---|---|
| 36–40 | 훌륭함 | 사소한 다듬기만 하면 출시 가능 |
| 28–35 | 양호 | 약한 부분을 개선할 것. 기반은 탄탄함 |
| 20–27 | 수용 가능 | 사용자가 만족하기 전에 상당한 개선이 필요함 |
| 12–19 | 미흡 | 주요 UX 개편 필요. 핵심 경험이 망가져 있음 |
| 0–11 | 치명적 | 재설계 필요. 현재 상태로는 사용할 수 없음 |

휴리스틱이 `n/a`로 채점되면 최대 점수는 40보다 낮습니다. 원점수 대신 백분율에 따라 등급을 정합니다 (90% 이상 훌륭함, 70% 이상 양호, 50% 이상 수용 가능, 30% 이상 미흡, 그 미만 치명적). 24/32는 75%이므로 양호입니다.

#### 문제 심각도 (P0–P3)

채점 중 발견한 각 문제에 우선순위 수준을 붙입니다.

| 우선순위 | 이름 | 설명 | 조치 |
|---|---|---|---|
| **P0** | 차단 | 과업을 완전히 완료할 수 없음 | 즉시 수정. 출시를 막는 문제 |
| **P1** | 중대 | 상당한 어려움이나 혼란을 일으킴 | 출시 전 수정 |
| **P2** | 경미 | 불편하지만 우회 방법이 있음 | 다음 개선 때 수정 |
| **P3** | 다듬기 | 수정하면 좋지만 실제 사용자 영향은 없음 | 시간 여유가 있으면 수정 |

**팁**: 두 단계 중 고민되면 “사용자가 이 문제로 지원팀에 문의할까?”라고 묻습니다. 그렇다면 최소 P1입니다.

### 페르소나 기반 디자인 테스트

서로 다른 사용자 유형 5명의 관점으로 인터페이스를 테스트합니다. 각 페르소나는 한 명의 “디자인 디렉터” 관점에서 놓칠 수 있는 고장 유형을 드러냅니다.

**사용 방법**: 비평하는 인터페이스와 가장 관련이 깊은 페르소나 2–3개를 선택합니다. 각 페르소나로 주요 사용자 동작을 수행해 봅니다. 일반적인 우려가 아니라 구체적인 위험 신호를 보고합니다.

#### 1. 성급한 고급 사용자: “Alex”

**프로필**: 비슷한 제품을 사용해 본 전문가. 효율을 원하고 과도한 안내를 싫어함. 단축 경로를 찾거나 떠날 것.

**행동**:
- 온보딩과 안내를 모두 건너뜀
- 즉시 키보드 단축키를 찾음
- 여러 항목 선택, 일괄 편집, 자동화를 시도
- 불필요해 보이는 필수 단계에 좌절
- 느리거나 훈계하는 느낌이 들면 포기

**테스트 질문**:
- Alex가 60초 안에 핵심 과업을 완료할 수 있는가?
- 자주 쓰는 동작의 키보드 단축키가 있는가?
- 온보딩을 완전히 건너뛸 수 있는가?
- 모달을 키보드로 닫을 수 있는가 (Esc)?
- 단축키나 일괄 작업 같은 고급 사용자 경로가 있는가?

**구체적으로 보고할 위험 신호**:
- 강제 튜토리얼 또는 건너뛸 수 없는 온보딩
- 핵심 동작의 키보드 내비게이션 없음
- 건너뛸 수 없는 느린 애니메이션
- 일괄 작업이 자연스러운 곳에서 한 번에 항목 하나만 처리
- 위험이 낮은 동작을 불필요하게 반복 확인

---

#### 2. 혼란스러운 첫 사용자: “Jordan”

**프로필**: 이런 유형의 제품을 사용해 본 적 없음. 매 단계에서 안내가 필요하며 스스로 알아내기보다 포기할 수 있음.

**행동**:
- 모든 안내를 꼼꼼히 읽음
- 익숙하지 않은 동작을 누르기 전에 망설임
- 도움이나 지원을 계속 찾음
- 전문 용어와 약어를 오해
- 모든 라벨을 가장 문자 그대로 해석

**테스트 질문**:
- 5초 안에 첫 행동을 명확히 알 수 있는가?
- 모든 아이콘에 텍스트 라벨이 있는가?
- 결정 지점에 맥락에 맞는 도움말이 있는가?
- 용어가 사전 지식을 가정하는가?
- 모든 단계에 명확한 “뒤로” 또는 “실행 취소”가 있는가?

**구체적으로 보고할 위험 신호**:
- 텍스트 라벨이 없는 아이콘 전용 내비게이션
- 설명이 없는 기술 용어
- 눈에 보이는 도움말 / 안내가 없음
- 동작을 완료한 뒤 다음에 무엇을 할지 모호함
- 동작이 성공했는지 확인이 없음

#### 3. 접근성에 의존하는 사용자: “Sam”

**프로필**: 스크린 리더 (VoiceOver / NVDA)와 키보드만 사용하는 내비게이션에 의존함. 저시력, 운동 장애, 인지 차이가 있을 수 있음.

**행동**:
- 탭 키로 인터페이스를 선형 탐색
- ARIA 라벨과 제목 구조에 의존
- 호버 상태나 시각적 신호만으로 전달되는 정보를 볼 수 없음
- 충분한 색상 대비 필요 (최소 4.5:1)
- 브라우저 확대를 최대 200%까지 사용할 수 있음

**테스트 질문**:
- 키보드만으로 주요 흐름을 모두 완료할 수 있는가?
- 모든 인터랙티브 요소에 포커스가 가고 포커스 표시가 보이는가?
- 이미지에 의미 있는 대체 텍스트가 있는가?
- 텍스트 대비가 WCAG AA (4.5:1)에 맞는가?
- 스크린 리더가 상태 변화 (로딩, 성공, 오류)를 알리는가?

**구체적으로 보고할 위험 신호**:
- 키보드 대안이 없는 클릭 전용 동작
- 포커스 표시가 없거나 보이지 않음
- 색상만으로 의미를 전달 (빨강 = 오류, 초록 = 성공)
- 라벨 없는 입력란이나 버튼
- 연장 옵션 없는 시간 제한 동작
- 스크린 리더 흐름을 깨뜨리는 사용자 지정 컴포넌트

#### 4. 의도적인 스트레스 테스터: “Riley”

**프로필**: 행복 경로를 벗어나 인터페이스를 꼼꼼히 시험함. 예외 사례를 테스트하고 예상 밖의 입력을 시도하며 경험의 빈틈을 찾음.

**행동**:
- 빈 상태, 긴 문자열, 특수 문자 등 예외 상황을 의도적으로 테스트
- 이모지, RTL 텍스트, 매우 긴 값 같은 예상 밖의 데이터로 양식 제출
- 뒤로 이동, 흐름 중 새로 고침, 여러 탭 열기로 워크플로를 깨뜨리려 함
- UI가 약속한 것과 실제 동작의 불일치를 찾음
- 문제를 체계적으로 기록

**테스트 질문**:
- 경계 상황 (항목 0개, 1000개, 매우 긴 텍스트)에서 어떻게 되는가?
- 오류 상태에서 자연스럽게 복구되는가, 아니면 UI가 망가진 상태로 남는가?
- 워크플로 중 새로 고침하면 어떻게 되는가? 상태가 보존되는가?
- 작동하는 것처럼 보이지만 잘못된 결과를 내는 기능이 있는가?
- 이모지, 특수 문자, Excel에서 붙여넣은 텍스트 같은 예상 밖의 입력을 어떻게 처리하는가?

**구체적으로 보고할 위험 신호**:
- 작동하는 것처럼 보이지만 조용히 실패하거나 잘못된 결과를 내는 기능
- 기술 세부 사항을 노출하거나 UI를 망가뜨리는 오류 처리
- 아무 도움도 되지 않는 빈 상태 (“결과 없음”만 표시하고 안내가 없음)
- 새로 고침이나 내비게이션 시 사용자 데이터가 사라지는 흐름
- 인터페이스의 서로 다른 곳에서 유사한 상호작용이 일관되지 않게 작동

#### 5. 주의가 분산된 모바일 사용자: “Casey”

**프로필**: 이동 중 한 손으로 휴대폰을 사용함. 자주 방해받고 연결이 느릴 수 있음.

**행동**:
- 엄지손가락만 사용하고 화면 아래쪽 동작을 선호
- 흐름 중 방해를 받고 나중에 다시 돌아옴
- 앱 사이를 자주 전환
- 주의 지속 시간이 짧고 인내심이 적음
- 입력을 최소화하고 탭과 선택을 선호

**테스트 질문**:
- 주요 동작이 엄지 영역 (화면 아래쪽 절반)에 있는가?
- 사용자가 떠났다가 돌아와도 상태가 보존되는가?
- 느린 연결 (3G)에서 작동하는가?
- 양식에서 자동 완성과 스마트 기본값을 쓸 수 있는가?
- 터치 영역이 최소 44×44pt인가?

**구체적으로 보고할 위험 신호**:
- 엄지로 닿기 어려운 화면 위쪽에 중요한 동작이 있음
- 상태 보존이 없어 탭 전환이나 방해 후 진행 상황을 잃음
- 선택으로 대체할 수 있는데 큰 텍스트 입력을 요구
- 매 페이지에서 무거운 에셋을 다시 로드 (lazy loading 없음)
- 탭 영역이 너무 작거나 서로 지나치게 가까움

#### 프로젝트별 페르소나

`AGENTS.md`에 `impeccable init`이 만든 `## Design Context` 절이 있으면 대상 고객과 브랜드 정보를 바탕으로 페르소나를 1–2개 더 만듭니다.

1. 대상 고객 설명을 읽습니다.
2. 미리 정의한 페르소나 5개에 포함되지 않은 주요 사용자 유형을 찾습니다.
3. 아래 템플릿으로 페르소나를 만듭니다.

```text
##### [역할]: "[이름]"

**프로필**: [Design Context에서 도출한 핵심 특성 2–3개]

**행동**: [설명된 대상 고객에 기반한 구체적 행동 3–4개]

**위험 신호**: [이 사용자 유형을 소외시킬 수 있는 요소 3–4개]
```

실제 Design Context 정보가 있을 때만 프로젝트별 페르소나를 만듭니다. 대상 고객 정보를 지어내지 않습니다. 맥락이 없으면 미리 정의한 페르소나 5개를 사용합니다.
