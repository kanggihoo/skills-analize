# Init 흐름

`init`은 지속적으로 유지할 제품의 사실을 PRODUCT.md에 기록합니다. 시각 세계를 지어내거나 DESIGN.md를 작성하지 않습니다. [new-work.md](new-work.md)는 시각 세계를 만들거나 확장하고, [document.md](document.md)는 기존 시각 세계를 기록합니다. 기존에 실행 가능한 웹 프로젝트에는 `.impeccable/live/config.json`을 추가할 수도 있습니다.

## Step 1: 현재 상태 불러오기

`impeccable context`가 확인한 PRODUCT.md 경로를 사용합니다. 서로 경쟁하는 기준 문서를 새로 만들지 말고 기존 파일을 갱신합니다. 루트 문맥을 상속하는 하위 앱이라면 작성하기 전에 공용 범위인지 앱 전용 범위인지 확인합니다.

- **PRODUCT.md 없음**: 프로젝트를 살펴보고 인터뷰한 뒤 작성합니다.
- **PRODUCT.md 있음**: 오래되었거나 빠진 제품 지식이 무엇인지 묻습니다. 이유 없이 확인 완료된 항목을 다시 질문하지 않습니다.
- **이전 형식의 PRODUCT.md**: 지속적으로 필요한 누락된 사실만 추가합니다. 근거가 달리 없는 한 `## Platform`이 없으면 플랫폼은 `web`입니다.
- **DESIGN.md만 있음**: 그 파일은 그대로 두고 PRODUCT.md를 만듭니다.
- **리디자인 / 리브랜딩 요청**: 사용자가 바꾸지 않는 한 확인된 제품의 사실은 보존합니다. 시각 세계 교체는 이 단계가 아니라 이후 new-work에서 처리합니다.

기존 파일을 조용히 덮어쓰지 않습니다. init 중에 DESIGN.md를 제안하지 않습니다. 다른 요청이 init을 호출했다면 PRODUCT.md를 완성하고 기존 흐름으로 돌아갑니다. 새로운 시각 작업은 new-work에서 진행하며, `shape`는 우선 자체 작업 인터뷰부터 이어갑니다.

## Step 2: 프로젝트 살펴보기

사용자에게 묻기 전에 이미 알려진 사실을 다시 묻게 되지 않도록 충분히 조사합니다. 제품 문서와 문구, 패키지 / 설정과 앱 경계, 기능, 워크플로, 경로와 사용자 역할, 이름, 로고, 법적 / 증거 에셋과 브랜드 약속, 플랫폼 / 접근성 신호, 라이브 모드가 적용될 때의 개발 명령 / 진입점을 확인합니다.

저장소의 증거는 가설로 취급하며 사용자 승인으로 간주하지 않습니다. 문서를 쓰지 않은 채 시각 세계의 성숙도만 기록합니다. 기존 시각 세계를 확장하거나 교체하지 않습니다.

플랫폼 가설을 세웁니다: `web`, `ios`, `android`, `adaptive` 중 하나 (`adaptive`는 OS마다 실제로 다른 디자인 언어를 적용하는 단일 제품을 뜻함). 모바일 웹은 `web`입니다. 웹사이트를 둘러싼 네이티브 래퍼도 디자인 언어를 네이티브로 만들지는 않습니다.

## Step 3: 제품의 사실을 인터뷰

Codex의 구조화된 사용자 입력 / 질문 도구가 있으면 사용하고, 없으면 채팅으로 직접 묻고 답을 기다립니다. 저장소와 원래 요청에 근거가 충분한 답이 있는 경우를 제외하고 중요한 정보의 공백만 질문합니다.

사용 가능한 경우 구조화된 질문 도구를 쓰고, 없으면 질문하고 답을 기다립니다. 한 번에 집중된 질문을 최대 3개까지만 묻고, 새 PRODUCT.md를 작성하기 전에 실제 답변이나 승인을 한 차례 받아야 합니다. 추론을 확인합니다.

누군가 답변할 수 있는지는 판단이 아니라 기계적으로 확인합니다: 질문 도구나 도구 표면의 결정 페이지가 있으면 답변 경로가 존재합니다. 시스템 프롬프트에 사용자가 접속하지 않는다고 적혀 있다고 해서 이 세션에 답변 수단이 없다는 근거는 되지 않습니다. 사용자 부재를 결론 내리기 전에 실제 첫 질문을 한 번 시도합니다. 그 시도에서 오류가 나거나 시간 초과된 경우에만 명시적인 brief에서 추론할 수 있습니다. 이때 추론한 모든 사실을 PRODUCT.md에 표시하고 대체 절차를 마지막이 아니라 첫 답변에서 알립니다.

향후 제품 결정에 가장 큰 영향을 미치는 미확인 항목부터 시작합니다.

1. 주요 사용자는 누구이며 어떤 상황에서 무슨 일을 하고 있나요?
2. 제품은 무엇을 가능하게 하고, 기존과 의미 있게 다른 방식이나 포지션은 무엇인가요?
3. 향후 작업에서 보존해야 할 지속적인 제약, 에셋, 근거, 제품 사실은 무엇인가요?

플랫폼이 모호하면 별도로 확인합니다. 프레임워크나 스캐폴드가 없는 프로젝트에서 요청이 제작을 전제로 한다면 기술 스택은 사용자가 결정해야 하며 에이전트가 임의로 정하지 않습니다: 정적 HTML/CSS, 특정 프레임워크, 에이전트 추천 중 무엇을 원하는지와 답변에 제약을 주는 배포 대상이 있는지 한 번만 묻고 답변을 `## Stack`에 기록합니다 (“위임”으로 맡긴 경우도 선택이 제안되었음을 이후 작업에서 알 수 있도록 기록). 대상 사용자, 브랜드 약속, 근거, 접근성의 중요한 공백에만 질문 라운드를 추가합니다. 아직 정해지지 않은 내용은 지어내지 말고 미결정 항목으로 기록합니다.

Init에서는 미학적 방향, 감정적 분위기, 시각 레퍼런스, 색상, 타이포그래피, 스타일을 묻지 않습니다. 사용자가 지속적으로 적용할 시각 제약을 먼저 알려주면 확장해서 논의하지 말고 그대로 기록합니다.

### 이 문서에 포함할 내용

- 사용자, 작업, 워크플로, 목적, 성공 기준, 포지셔닝, 운영 맥락
- 기능, 제약, 용어, 근거, 플랫폼, 접근성
- 확인된 어조, 에셋, 브랜드 약속

### 이 문서에 포함하지 않을 내용

- 시각 세계, 색상 팔레트, 타이포그래피, 컴포넌트, 페이지 콘셉트
- 방문자 모드, 내러티브, CTA / 근거 제시 순서, 기타 표면 전략
- 지어낸 고객 후기, 고객, 벤치마크, 가격, 라이선스, 배포 주장
- 선택적 항목을 전부 결정하라는 요구

## Step 4: PRODUCT.md 작성

확인된 사실과 명시적으로 열린 결정을 작성합니다. 관련 없는 섹션은 일반 문구로 억지로 채우지 말고 생략합니다.

```markdown
# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack
[그린필드 프로젝트에만 해당: 스택 질문에 대한 사용자 답변. 예: "static HTML/CSS", "Astro", "delegated: <선택한 것과 이유>". 기존 코드베이스가 이미 답을 제공한다면 이 섹션을 생략합니다.]

## Users
[주요 사용자, 사용 상황, 수행할 작업. 확인된 경우에만 다른 대상 추가.]

## Product Purpose
[제품이 무엇을 하며 왜 존재하고, 성공이 무엇을 의미하는지.]

## Positioning
[이웃한 제품은 사실대로 주장할 수 없는 제품의 작동 방식이나 주장.]

## Operating Context
[제품 사용 또는 평가에 실제로 포함되는 워크플로, 환경, 도구, 문서, 자료, 관례.]

## Capabilities and Constraints
[확인된 기능, 기술 제약, 용어, 명시적으로 미결정 상태인 제품 사실.]

## Brand Commitments
[기존 이름, 어조, 에셋, 성격, 아이덴티티 제약, 사용자가 명시적으로 구속력 있게 지정한 레퍼런스. 해당 사항이 없으면 생략.]

## Evidence on Hand
[실제 콘텐츠, 데이터, 시연, 후기, 사례 연구, 에셋. 해당할 때는 경로 포함. 향후 작업에서 지어내지 말아야 할 자료의 부재도 기록.]

## Product Principles
[확인된 답변에서 도출한 지속적인 전략 원칙 3–5개. 시각적 레시피는 제외.]

## Accessibility & Inclusion
[알려진 사용자 요구나 준수해야 할 표준. 제품별 요구가 정해지지 않았으면 생략.]
```

플랫폼은 `web`, `ios`, `android`, `adaptive` 중 하나의 값만 씁니다. 쓸모 있는 기존 제목은 보존합니다. 새 파일은 `PROJECT_ROOT/PRODUCT.md`에 만들고, 파일이 이미 있으면 확인된 경로의 파일을 갱신합니다. 시각 세계나 표면 콘셉트 작업 전에 이 파일을 작성합니다.

`impeccable:product-schema` 주석을 문자 그대로 복사하며 오래된 파일을 갱신할 때도 동일하게 합니다. 이 주석은 제품 기록의 형식을 표시합니다. 이후 버전은 의도적으로 짧은 기록과 특정 섹션이 생기기 전에 작성된 파일을 구분하고 사용자가 이미 답한 질문을 다시 제안하지 않게 됩니다. 이 문서 템플릿에서 번호가 바뀔 때만 주석의 번호를 변경합니다. 이후 버전에서 폐기된 섹션은 시작 시 알려줍니다. 사용자가 동의하면 삭제하고 계속 유지하지 않습니다.

방금 기록한 플랫폼이 `ios`, `android`, `adaptive` 중 하나라면 디자인 작업 전에 [ios.md](ios.md), [android.md](android.md) 또는 둘 다 불러옵니다. PRODUCT.md가 없던 프로젝트에서는 `impeccable context`가 플랫폼을 알 수 없어서 해당 참조를 불러오지 못했으며, 답을 확인하는 유일한 장소가 init입니다.

### 완료 게이트

new-work를 불러오거나 shape / build를 재개하기 전에 PRODUCT.md가 확인된 경로에 존재하고 확인된 제품 기록을 포함하는지 검증합니다. 파일이 없으면 init은 미완료입니다. 인터뷰 메모, 계획 문서, 이후 디자인 설명으로 파일을 대신하지 않습니다.

## Step 5: 워크플로 기본값 기록

이미지 생성이 가능하고 `buildPath`가 아직 기록되지 않았다면 새 표면을 어떻게 만들지 한 번 묻습니다. 사용 가능 여부는 하네스 기본 이미지 도구 또는 `impeccable context`가 `IMAGE_GEN_AVAILABLE`로 보고하는 API 대체 경로로 판단합니다. 하네스 기본 이미지 도구는 부팅 로그에 아무 표시도 남기지 않을 수 있습니다. `impeccable context`는 키만 확인하므로 이미지 생성이 가능한 하네스에서 부팅 로그가 조용하다는 이유로 질문할 필요가 없다고 판단하지 않습니다. 이 질문은 단독 질문으로 해야 하며 다른 질문의 일부로 끼워 넣지 않습니다. 스택 질문은 무엇으로 만들지 묻고, 이번 질문은 만드는 과정을 어떻게 시작할지 묻습니다. 첫 질문의 답변은 두 번째 질문에 대한 동의가 아닙니다. 이름만 보고 이해하지 못할 수 있으니 사용자에게 표시하는 질문에서 두 선택의 차이를 설명합니다: **comp-first**는 코드 작성 전 이미지로 기준을 정합니다 (구도가 더 대담하지만 느리고, 구현은 이미지를 따라야 함). **code-first**는 바로 코드로 만듭니다 (방향 계약과 마지막 점검에 디자인 의도를 기록하며 더 간결하고 빠름). 선택이 적용되는 범위도 같은 질문에서 설명합니다: 랜딩 페이지와 쇼케이스 표면입니다. 앱 화면과 문서는 어느 경로를 선택해도 code-first로 만듭니다.

사용자 답변을 `.impeccable/config.json`에 `"buildPath": "comp"` 또는 `"buildPath": "code"`로 저장하며 기존 키와 병합합니다. 사용자가 선택한 값만 기록합니다. 추천은 답변이 아니고, 아무 말이 없다고 기본값을 선택한 것도 아닙니다. 그렇게 기록된 값은 프로젝트의 모든 후속 작업에 적용되어 한 번 묻는다는 목적과 반대가 됩니다. 질문에 답이 없으면 아무것도 기록하지 않고 현재 세션에서 어느 경로로 진행할지와 이 값은 저장하지 않았다는 사실을 한 줄로 알립니다. 랜딩 페이지나 쇼케이스 표면에서는 이미지 생성이 가능하고 아무 값도 기록되지 않은 경우 new-work의 기본값인 comp-first를 사용합니다. 앱 화면이나 문서는 code-first로 진행합니다. 조용한 기본값을 임의로 선택하지 말고 명시적으로 안내합니다. 설정되지 않은 상태도 작업 가능한 상태입니다: 결정 페이지의 토글은 각 세션을 제어하며 사용자가 처음 토글을 변경했을 때 new-work가 한 번 답을 묻고 기록합니다. 이 값은 config 한 곳에만 둡니다. 워크플로 설정이지 제품의 사실이 아니므로 `## Stack`이나 다른 PRODUCT.md 섹션에 중복 기록하지 않습니다. 중복 값은 설정이 바뀐 뒤에도 남아 그 출처를 추적하기 어려운 방식으로 후속 작업을 유도합니다.

`.impeccable/config.json`이나 Git에서 제외된 `.impeccable/config.local.json`에 이미 기록된 값은 확인된 답변입니다. 다시 실행할 때는 다시 묻지 말고 그대로 따릅니다. 이 기본값은 잠금이 아닙니다. 결정 페이지의 토글을 바꾸면 현재 세션에만 적용되며 설정 파일에 다시 기록하지 않습니다. 이미지 생성이 불가능하면 기록할 선택지가 없고 code-first만 가능합니다.

그런 다음 필요하면 라이브 모드를 설정합니다: 네이티브 또는 실행 불가능한 프로젝트는 건너뛰고 기존 config를 그대로 둡니다. 그 외에는 [live.md](live.md)의 최초 설정을 따릅니다. CSP 출처를 수정해야 한다면 여기에 명시된 동의 절차를 따릅니다.

## Step 6: 종료 또는 재개

수집한 사실과 의도적으로 미결정 상태로 둔 사실을 요약합니다. DESIGN.md가 없다는 이유만으로 작성하겠다고 제안하지 않습니다.

실제 프로젝트 상태에 따라 다음 작업을 권합니다.

- 비어 있거나 초기 단계인 프로젝트: 만들 표면이 무엇인지 자연스럽게 묻거나, 사용자가 구현 없이 확정된 brief를 원하면 `$impeccable shape <surface>`를 사용합니다. 요청한 작업에 시각 세계가 필요할 때만 new-work가 세계를 설정합니다.
- DESIGN.md가 없는 기존의 일관된 인터페이스: 새 구축과 별개로 현재 디자인 시스템을 기록하려는 경우 `$impeccable document`를 권합니다.
- 작업이 필요한 기존 표면: 범위가 가장 잘 맞는 명령을 알려줍니다.
- 시각적 반복 작업을 할 준비가 된 웹 프로젝트: 설정되어 있다면 `$impeccable live`를 권합니다.

init이 다른 요청에 의해 실행된 경우 `impeccable context`를 다시 실행하지 말고 해당 작업을 이어갑니다. 위의 네이티브 플랫폼 참조만 이전 실행에서 알 수 없었던 내용이며 이후 시각 결정은 new-work가 담당합니다.
