> **추가로 필요한 맥락**: 대상 화면 크기, 기기, 플랫폼, 사용 상황.

기존 디자인을 다른 화면 크기, 기기, 플랫폼, 사용 사례에 맞게 조정합니다. 함정은 조정을 단순한 크기 변경으로 생각하는 것입니다. 새 사용 맥락에 맞게 경험을 다시 설계해야 합니다.

**웹 전용입니다**(모바일 웹 포함). 네이티브 플랫폼(`ios` / `android` / `adaptive`)은 [adapt.native.md](adapt.native.md)로 연결됩니다. 프로젝트가 네이티브라면 지금 해당 문서로 전환합니다.

## 조정 과제 살펴보기

무엇을, 왜 조정해야 하는지 파악합니다.

1. **출발 맥락 확인**:
   - 원래 어떤 용도로 설계했나요?(데스크톱 웹? 모바일 앱?)
   - 어떤 가정을 했나요?(큰 화면? 마우스 입력? 빠른 연결?)
   - 현재 맥락에서 무엇이 잘 작동하나요?

2. **대상 맥락 파악**:
   - **기기**: 휴대전화, 태블릿, 데스크톱, TV, 시계, 인쇄물?
   - **입력 방식**: 터치, 마우스, 키보드, 음성, 게임패드?
   - **화면 제약**: 크기, 해상도, 방향?
   - **연결 상태**: 빠른 Wi-Fi, 느린 3G, 오프라인?
   - **사용 상황**: 이동 중 vs 책상 앞, 빠르게 확인 vs 집중해 읽기?
   - **사용자 기대**: 해당 플랫폼에서 사용자가 기대하는 것은 무엇인가요?

3. **조정 과제 확인**:
   - 무엇이 들어가지 않나요?(콘텐츠, 탐색, 기능)
   - 무엇이 작동하지 않나요?(터치 기기의 hover 상태, 너무 작은 터치 영역)
   - 무엇이 부적절한가요?(모바일에서 데스크톱 패턴, 데스크톱에서 모바일 패턴)

조정은 픽셀 크기를 바꾸는 일이 아니라 새 맥락에 맞춰 경험을 다시 생각하는 일입니다.

## 조정 전략 계획

맥락에 맞는 전략을 만듭니다.

### 모바일 조정(데스크톱 → 모바일)

**레이아웃 전략**:
- 여러 열 대신 한 열
- 좌우 배치 대신 세로로 쌓기
- 고정 너비 대신 전체 너비 컴포넌트
- 상단 / 측면 탐색 대신 하단 탐색

**상호작용 전략**:
- hover에 의존하지 않는 최소 44x44px 터치 영역
- 적절한 경우 목록이나 캐러셀에 스와이프 제스처
- 드롭다운 대신 하단 시트
- 엄지손가락이 닿는 범위에 컨트롤 배치
- 더 넓은 탭 영역과 충분한 간격

**콘텐츠 전략**:
- 점진적 공개(한 번에 모든 내용을 보여 주지 않음)
- 기본 콘텐츠를 우선하고 보조 콘텐츠는 탭 / 아코디언으로 이동
- 문구를 짧고 간결하게 작성
- 글자는 더 크게(최소 16px)

**탐색 전략**:
- 햄버거 메뉴 또는 하단 탐색 사용
- 탐색 구조의 복잡성 줄이기
- 맥락을 유지하는 고정 헤더
- 탐색 흐름에 뒤로 가기 추가

### 태블릿 조정(하이브리드 접근)

**레이아웃 전략**:
- 한 열이나 세 열 대신 두 열 레이아웃
- 보조 콘텐츠를 위한 사이드 패널
- 마스터-디테일 화면(목록 + 상세)
- 화면 방향(세로 vs 가로)에 따라 레이아웃 조정

**상호작용 전략**:
- 터치와 포인터 모두 지원
- 터치 영역은 44x44px로 두되 휴대전화보다 정보 밀도를 높일 수 있음
- 측면 탐색 drawer
- 적합한 경우 여러 열의 양식

### 데스크톱 조정(모바일 → 데스크톱)

**레이아웃 전략**:
- 가로 공간을 활용한 여러 열 레이아웃
- 항상 보이는 측면 탐색
- 여러 정보 패널을 동시에 표시
- 최대 너비 제약이 있는 고정 너비 사용(4K까지 무작정 늘리지 않음)

**상호작용 전략**:
- 추가 정보에 hover 상태 사용
- 키보드 단축키
- 마우스 오른쪽 버튼의 컨텍스트 메뉴
- 도움이 되는 경우 드래그 앤 드롭
- Shift/Cmd를 활용한 여러 항목 선택

**콘텐츠 전략**:
- 점진적 공개를 줄이고 더 많은 정보를 먼저 표시
- 열이 많은 데이터 표
- 풍부한 시각화
- 더 자세한 설명

### 인쇄 조정(화면 → 인쇄물)

**레이아웃 전략**:
- 논리적인 지점에서 페이지 나누기
- 탐색, footer, 인터랙티브 요소 제거
- 흑백(또는 제한된 색상)으로 구성
- 제본할 수 있도록 적절한 여백 확보

**콘텐츠 전략**:
- 줄인 콘텐츠 확장(전체 URL과 숨겨진 섹션 표시)
- 페이지 번호, 머리글, 바닥글 추가
- 메타데이터(인쇄 날짜, 페이지 제목) 포함
- 차트를 인쇄에 적합한 버전으로 변환

### 이메일 조정(웹 → 이메일)

**레이아웃 전략**:
- 너비 제한(최대 600px)
- 한 열만 사용
- 인라인 CSS(외부 stylesheet 사용 불가)
- 이메일 클라이언트 호환성을 위한 표 기반 레이아웃

**상호작용 전략**:
- 크고 분명한 CTA(텍스트 링크보다 버튼)
- 안정적이지 않은 hover 상태 제거
- 복잡한 상호작용은 웹 앱의 딥 링크로 연결

## 조정 구현

체계적으로 변경합니다.

### 반응형 중단점

적절한 중단점을 선택합니다.
- 모바일: 320px~767px
- 태블릿: 768px~1023px
- 데스크톱: 1024px 이상
- 또는 디자인이 깨지는 지점을 기준으로 하는 콘텐츠 기반 중단점

### 레이아웃 조정 기법

- **CSS Grid/Flexbox**: 레이아웃을 자동으로 재배치
- **Container Queries**: viewport가 아니라 컨테이너에 따라 조정
- **`clamp()`**: 최솟값과 최댓값 사이에서 유동적으로 크기 변경
- **Media queries**: 맥락별로 다른 스타일 적용
- **Display 속성**: 맥락에 따라 요소를 표시하거나 숨김

### 터치 조정

- 터치 영역을 최소 44x44px로 확대
- 인터랙티브 요소 사이 간격 확대
- hover에 의존하는 상호작용 제거
- 터치 피드백(ripple, 강조) 추가
- 엄지 영역 고려(위쪽보다 아래쪽이 닿기 쉬움)

### 콘텐츠 조정

- `display: none`은 신중하게 사용(숨겨도 다운로드됨)
- 점진적 향상 적용(핵심 콘텐츠를 먼저 제공하고 큰 화면에서 기능 강화)
- 화면 밖 콘텐츠는 지연 로딩
- 반응형 이미지(`srcset`, `picture` 요소)

### 탐색 조정

- 복잡한 탐색을 모바일에서 햄버거 / drawer로 전환
- 모바일 앱에 하단 탐색 바 사용
- 데스크톱에서 측면 탐색을 계속 표시
- 작은 화면에서 맥락을 유지할 breadcrumb 사용

실제 기기에서 테스트합니다. DevTools 에뮬레이션은 유용한 첫 단계이지만 실제 터치, 성능, 브라우저 chrome을 놓칩니다.

**피할 것**:
- 모바일에서 핵심 기능 숨기기(중요하면 작동하게 만들기)
- 데스크톱 = 강력한 기기라고 가정하기(접근성 및 오래된 기기도 고려)
- 맥락마다 정보 구조를 다르게 만들어 혼란을 주기
- 플랫폼에 대한 사용자의 기대를 깨기(모바일 사용자는 모바일 패턴을 기대함)
- 모바일 / 태블릿의 가로 화면 방향을 잊기
- 일반적인 중단점을 무비판적으로 사용하기(콘텐츠 기준으로 정하기)
- 데스크톱에서 터치 입력을 무시하기(터치 지원 데스크톱 기기도 많음)

## 조정 결과 확인

맥락별로 충분히 시험합니다.

- **실제 기기**: 실제 휴대전화, 태블릿, 데스크톱에서 확인
- **화면 방향**: 세로와 가로
- **브라우저**: Safari, Chrome, Firefox, Edge
- **운영체제**: iOS, Android, Windows, macOS
- **입력 방식**: 터치, 마우스, 키보드
- **예외 상황**: 매우 작은 화면(320px), 매우 큰 화면(4K)
- **느린 연결**: 네트워크 속도를 제한해 확인

**사용자 지정 컨트롤**(슬라이더, 드래그 표면, 스크롤 가능한 컨트롤 띠): before/after 슬라이더는 위의 모든 너비 검사를 통과해도 iOS에서 드래그되지 않을 수 있습니다. 따라서 점검과 같은 한 번의 묶음에서 범위에 속한 각 컨트롤을 직접 실행합니다.

- **주요 제스처**: 탭해 의도한 반응을 확인한 뒤 대상 입력 방식으로 드래그합니다. 시작만 되는 것이 아니라 끝까지 드래그되어야 합니다.
- **컨트롤 위에서 스크롤**: 페이지 스크롤 방향으로 컨트롤을 지나 스와이프하면 컨트롤이 활성화되지 않고 페이지나 컨테이너가 스크롤되어야 합니다. 컨트롤 위에서 시작한 드래그는 페이지가 아니라 컨트롤을 움직여야 합니다. 어느 쪽의 실패도 오류를 내지 않으므로 둘 다 시도합니다.
- **증거**: 어떤 방식으로 증거를 만들었는지 밝힙니다. 에뮬레이트 viewport, 브라우저 도구로 합성한 터치 입력, 사용한 엔진(Chromium은 Safari가 아님), 실제 기기인지 구분합니다. 스크린샷과 크기 조정 viewport는 레이아웃을 검증할 뿐 제스처 동작을 검증하지 않습니다. 테스트하지 못한 점은 밝히고 다음으로 넘어갑니다. 접근할 수 없는 하드웨어는 차단 사유가 아니라 보고할 공백입니다.

각 맥락에 자연스럽게 어울리면 최종 점검을 위해 `$impeccable polish`로 넘깁니다.

## 참고 자료

아래 내용은 이전 `responsive-design.md`였으며, 이제 adapt 흐름에 상세 반응형 참고 자료로 포함되어 있습니다.

### 반응형 디자인

#### 모바일 우선: 올바르게 작성하기

모바일용 기본 스타일에서 시작해 `min-width` query로 복잡성을 더합니다. 데스크톱 우선(`max-width`)으로 작성하면 모바일이 불필요한 스타일을 먼저 불러옵니다.

#### 중단점: 콘텐츠 기준으로 정하기

기기 크기를 쫓지 말고 콘텐츠가 중단점을 알려주게 합니다. 좁은 화면에서 시작해 디자인이 깨질 때까지 늘리고 그 지점에 중단점을 추가합니다. 보통 세 개면 충분합니다(640, 768, 1024px). 중단점 없이 유동적인 값은 `clamp()`를 사용합니다.

#### 화면 크기만 보지 말고 입력 방식 감지하기

**화면 크기로 입력 방식을 알 수 없습니다.** 터치스크린이 있는 노트북도 있고 키보드가 있는 태블릿도 있습니다. pointer와 hover query를 사용합니다.

```css
/* 정밀한 포인터(마우스, 트랙패드) */
@media (pointer: fine) {
  .button { padding: 8px 16px; }
}

/* 거친 포인터(터치, 스타일러스) */
@media (pointer: coarse) {
  .button { padding: 12px 20px; }  /* 더 큰 터치 영역 */
}

/* 기기가 hover를 지원 */
@media (hover: hover) {
  .card:hover { transform: translateY(-2px); }
}

/* 기기가 hover를 지원하지 않음(터치) */
@media (hover: none) {
  .card { /* hover 상태 없이 active 사용 */ }
}
```

**중요**: 기능을 hover에 의존시키지 않습니다. 터치 사용자는 hover할 수 없습니다.

#### 안전 영역: 노치 처리

최신 휴대전화에는 노치, 둥근 모서리, 홈 표시기가 있습니다. `env()`를 사용합니다.

```css
body {
  padding-top: env(safe-area-inset-top);
  padding-bottom: env(safe-area-inset-bottom);
  padding-left: env(safe-area-inset-left);
  padding-right: env(safe-area-inset-right);
}

/* 대체값 포함 */
.footer {
  padding-bottom: max(1rem, env(safe-area-inset-bottom));
}
```

meta tag에서 **viewport-fit을 활성화합니다.**

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

#### 반응형 이미지: 올바르게 적용하기

##### 너비 descriptor와 `srcset` 사용

```html
<img
  src="hero-800.jpg"
  srcset="
    hero-400.jpg 400w,
    hero-800.jpg 800w,
    hero-1200.jpg 1200w
  "
  sizes="(max-width: 768px) 100vw, 50vw"
  alt="Hero image"
>
```

**동작 방식**:
- `srcset`은 실제 너비(`w` descriptor)가 다른 이미지 파일을 나열합니다.
- `sizes`는 이미지가 화면에 표시될 너비를 브라우저에 알려줍니다.
- 브라우저는 viewport 너비와 기기 픽셀 비율을 바탕으로 적절한 파일을 선택합니다.

##### 아트 디렉션에 `picture` 요소 사용

해상도만 다르게 하는 것이 아니라 crop이나 구성을 바꿔야 할 때 사용합니다.

```html
<picture>
  <source media="(min-width: 768px)" srcset="wide.jpg">
  <source media="(max-width: 767px)" srcset="tall.jpg">
  <img src="fallback.jpg" alt="...">
</picture>
```

#### 레이아웃 조정 패턴

**탐색**: 모바일에서는 hamburger + drawer, 태블릿에서는 간결한 가로형, 데스크톱에서는 레이블이 포함된 전체 탐색의 세 단계로 구성합니다. **표**: 모바일에서 `display: block`과 `data-label` 속성을 사용해 카드로 바꿉니다. **점진적 공개**: 모바일에서 접을 수 있는 콘텐츠에는 `<details>/<summary>`를 사용합니다.

#### 테스트: DevTools만 믿지 않기

DevTools 기기 에뮬레이션은 레이아웃 확인에 유용하지만 다음은 검증하지 못합니다.

- 실제 터치 상호작용
- 실제 CPU / 메모리 제약
- 네트워크 지연 패턴
- 글꼴 렌더링 차이
- 브라우저 chrome / 키보드 표시 방식

**최소 다음 기기에서 테스트합니다**: 실제 iPhone 한 대, 실제 Android 한 대, 해당되는 경우 태블릿 한 대. 저가 Android 휴대전화에서 시뮬레이터로는 보이지 않는 성능 문제가 드러납니다.
