응답은 다음으로 시작합니다.

```
──────────── ⚡ OVERDRIVE ─────────────
》》》 오버드라이브 모드 시작...
```

인터페이스를 관습적인 한계 너머로 밀어붙입니다. 시각 효과만을 뜻하지 않습니다. 브라우저의 모든 기능을 활용해 인터페이스의 어떤 부분이든 특별하게 느껴지도록 합니다. 예를 들어 백만 행을 처리하는 표, 트리거에서 형태가 변해 열리는 대화상자, 실시간 스트리밍 피드백과 함께 검증되는 양식, 영화처럼 느껴지는 페이지 전환 등이 있습니다.

“특별함”의 의미는 맥락에 따라 달라집니다. 창의적인 포트폴리오의 입자 효과는 인상적일 수 있지만 설정 페이지에 같은 효과를 쓰면 민망합니다. 반면 즉시 저장되는 낙관적 업데이트와 상태 전환 애니메이션이 있는 설정 페이지는 그 자체로 특별할 수 있습니다. 적절한 방향을 정하기 전에 프로젝트의 성격과 목표를 이해합니다.

### 구현 전에 제안

이 명령은 잘못 적용될 위험이 가장 큽니다. 구현부터 시작하지 않습니다. 다음을 반드시 수행합니다.

1. **서로 다른 방향 2~3개를 검토합니다.** 서로 다른 기법, 야심의 정도, 미적 접근을 고려하고 각 방향에서 결과가 어떻게 보이고 느껴질지 짧게 설명합니다.
2. **코드를 쓰기 전에 사용자가 고르게 합니다.** 사용할 수 있다면 Codex의 구조화된 사용자 입력 / 질문 도구로 묻고, 없으면 채팅에서 선택을 받은 다음 계속합니다. 각 방향의 설명과 장단점(브라우저 지원, 성능 비용, 복잡성)을 사용자가 읽고 비교할 수 있도록 선택지 안에 포함합니다. 구조화된 질문은 답변 전까지 해당 메시지 처리를 멈춥니다. 질문과 함께 쓴 방향 설명은 사용자가 선택하는 동안 보이지 않기 때문에 함께 보내지 않습니다.
3. 사용자가 확인한 방향만 진행합니다.

이 단계를 생략하면 폐기해야 할 민망한 결과물을 만들 위험이 있습니다.

### 브라우저에서 검증

야심 찬 효과는 첫 시도에 잘 작동하지 않는 경우가 많으므로 코드만 보지 말고 브라우저에서 검증합니다. 기술적으로 실행되더라도 끊기거나 easing이 이상하거나 잘못된 프레임에 놓일 수 있습니다. 타이밍, easing, 부드러움을 집중 확인하고, 한 차례 살펴본 뒤 수정 사항을 모아 고칩니다. 효과가 특별하게 느껴질 때까지 다듬습니다.

## 여기서 “특별함”의 의미 평가

적절한 기술 야심은 작업 대상에 따라 전적으로 달라집니다. 기법을 고르기 전에 묻습니다. **이 특정 인터페이스의 사용자가 무엇을 보고 “와, 좋다”고 할까요?**

### 시각 / 마케팅 화면

페이지, hero 섹션, 랜딩 페이지, 포트폴리오에서는 감각적인 반응이 “와”를 만드는 경우가 많습니다. 스크롤 연동 공개, shader 배경, 영화 같은 페이지 전환, 커서에 반응하는 생성형 아트 등이 있습니다.

### 기능 UI

표, 양식, 대화상자, 탐색에서는 “느낌”이 특별함을 만듭니다. View Transitions를 사용해 실행 버튼에서 형태가 변하며 나타나는 대화상자, 가상 스크롤링으로 60fps에 10만 행을 렌더링하는 데이터 표, 즉시 반응하는 스트리밍 검증 양식, 스프링 물리 효과가 있는 drag and drop 등이 있습니다.

### 성능이 중요한 UI

“와”가 눈에 보이지 않지만 체감됩니다. 5만 개 항목을 깜빡임 없이 필터링하는 검색, 메인 스레드를 막지 않는 복잡한 양식, 거의 실시간으로 이미지를 처리하는 편집기 등이 있습니다. 인터페이스가 전혀 망설이지 않고 반응합니다.

### 데이터가 많은 UI

차트와 대시보드에서는 유연함이 특별함을 만듭니다. 대규모 데이터셋을 Canvas/WebGL GPU 가속으로 그리기, 데이터 상태 간 애니메이션 전환, 자연스럽게 안정되는 force-directed 그래프 레이아웃 등이 있습니다.

**공통점**: 구현 기술이 사용자의 예상 범위를 넘어섭니다. 기법 자체가 목적이 아니라 경험에 도움이 되어야 합니다.

## 도구 상자

기술 이름이 아니라 달성하려는 목적별로 정리합니다.

### 전환을 영화처럼 만들기
- **View Transitions API**(같은 문서 내는 모든 브라우저, 문서 간은 Firefox 미지원): 상태 사이의 공통 요소 모핑. 목록 항목이 상세 페이지로 확장되거나 버튼이 대화상자로 변하는 경우입니다. 네이티브 FLIP 애니메이션에 가장 가까운 방식입니다.
- **`@starting-style`**(모든 브라우저): CSS만으로 `display: none`에서 표시 상태로 바꾸며 진입 keyframe을 적용합니다.
- **스프링 물리**: cubic-bezier 대신 질량, 장력, 감쇠로 자연스러운 움직임을 만듭니다. 라이브러리: motion(구 Framer Motion), GSAP 또는 직접 구현한 spring solver.

### 스크롤 위치에 애니메이션 연결
- **스크롤 구동 애니메이션**(`animation-timeline: scroll()`): JavaScript 없는 CSS 방식입니다. 시차, 진행 표시줄, 공개 시퀀스를 스크롤 위치에 연결합니다. (Chrome/Edge/Safari 지원, Firefox는 flag로만 지원. 반드시 정적 대체 동작 제공)

### CSS를 넘어 렌더링
- **WebGL**(모든 브라우저): shader 효과, 후처리, 입자 시스템. Three.js, OGL(경량), regl 등을 사용합니다. CSS로 표현하기 어려운 효과에 사용합니다.
- **WebGPU**(Chrome/Edge, Safari 26 이상, Windows/macOS의 Firefox 지원, Firefox Linux/Android는 flag로만 지원): WebGL보다 강력한 차세대 GPU 계산입니다. 항상 WebGL2 대체 경로를 둡니다.
- **Canvas 2D / OffscreenCanvas**: 사용자 지정 렌더링, 픽셀 조작, 또는 Web Workers + OffscreenCanvas를 통해 무거운 렌더링 작업 전체를 메인 스레드 밖으로 옮길 때 사용합니다.
- **SVG filter chain**: displacement map, turbulence, morphology를 활용한 유기적 왜곡 효과. CSS로 애니메이션할 수 있습니다.

### 데이터에 생동감 더하기
- **가상 스크롤링**: 수만 개 항목이 있는 표 / 목록에서 화면에 보이는 행만 렌더링합니다. 단순한 경우 라이브러리가 필요 없으며 복잡한 경우 TanStack Virtual을 사용합니다.
- **GPU 가속 차트**: SVG/DOM으로 처리하기에 너무 큰 데이터셋은 Canvas나 WebGL 시각화를 사용합니다. 라이브러리: deck.gl, regl 기반 사용자 지정 renderer.
- **애니메이션 데이터 전환**: 차트 상태를 교체하지 말고 모핑합니다. D3의 `transition()` 또는 DOM 기반 차트의 View Transitions를 사용합니다.

### 복잡한 속성 애니메이션
- **`@property`**(모든 브라우저): 타입이 있는 사용자 지정 CSS 속성을 등록해 보통 CSS가 보간할 수 없는 gradient, 색상, 복합 값을 애니메이션합니다.
- **Web Animations API**(모든 브라우저): CSS 성능을 활용하는 JavaScript 구동 애니메이션입니다. 조합, 취소, 역방향 실행이 가능합니다. 복잡한 연출의 기반입니다.

### 성능 한계 넘기
- **Web Worker**: 계산을 메인 스레드 밖으로 옮깁니다. 무거운 데이터 처리, 이미지 조작, 검색 인덱싱 등 끊김을 일으킬 작업에 사용합니다.
- **OffscreenCanvas**: Worker thread에서 렌더링합니다. 복잡한 화면이 백그라운드에서 그려지는 동안 메인 스레드를 비워 둡니다.
- **WASM**: 계산량이 많은 기능에 네이티브에 가까운 성능을 제공합니다. 이미지 처리, 물리 시뮬레이션, codec 등에 사용합니다.

### 기기와 상호작용
- **Web Audio API**: 공간 오디오, 오디오 반응 시각화, 소리 피드백. 시작하려면 사용자 제스처가 필요합니다.
- **기기 API**: 방향, 주변광, 위치 정보. 절제해 쓰고 항상 사용자 권한을 받습니다.

**주의**: 이 명령은 제품이 하는 일을 바꾸는 것이 아니라 인터페이스의 **느낌**을 개선하는 것입니다. 실시간 협업, 오프라인 지원, 새 백엔드 기능은 UI 개선이 아닌 제품 결정입니다. 기존 기능을 특별하게 느끼게 하는 데 집중합니다.

## 절제 있게 구현

### 점진적 향상은 필수

모든 기법은 graceful degradation을 제공해야 합니다. 향상 기능이 없어도 경험은 여전히 좋아야 합니다.

```css
@supports (animation-timeline: scroll()) {
  .hero { animation-timeline: scroll(); }
}
```

```javascript
if ('gpu' in navigator) { /* WebGPU */ }
else if (canvas.getContext('webgl2')) { /* WebGL2 fallback */ }
/* CSS-only fallback must still look good */
```

### 성능 규칙

- 60fps를 목표로 합니다. 50fps 아래로 떨어지면 단순화합니다.
- 무거운 리소스(WebGL context, WASM module)는 viewport에 가까워졌을 때만 지연 초기화합니다.
- 화면 밖 렌더링은 멈춥니다. 보이지 않는 작업은 정리합니다.
- 개발용 컴퓨터만이 아니라 실제 중급 기기에서 테스트합니다.

### 마지막 다듬기가 특별함을 만듭니다

“멋지다”와 “특별하다”의 차이는 마지막 20%의 다듬기에서 나옵니다. 스프링 애니메이션의 easing 곡선, stagger reveal의 미묘한 시간 offset, 전환을 물리적으로 느끼게 하는 보조 모션 등이 그 예입니다. 작동만 하는 첫 번째 버전을 출시하지 말고 당연한 선택처럼 느껴지는 버전을 출시합니다.

**절대 금지**:
- 중급 기기에서 끊기는 효과를 출시
- 기능적인 대체 경로 없이 최신 API 사용
- 사용자가 명시적으로 허용하지 않은 사운드 추가
- 기술 야심으로 기초 디자인이 약한 점을 가리기(먼저 다른 명령으로 수정)
- 경쟁하는 특별한 순간을 여러 개 겹쳐 놓기. 집중은 인상을 만들고 과잉은 잡음을 만듦
