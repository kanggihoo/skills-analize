> **추가로 필요한 맥락**: 대상 플랫폼 / 기기와 사용 상황.

기존 **네이티브** 디자인(`ios` / `android` / `adaptive`)을 다른 사용 맥락(기기 종류, 화면 방향, 플랫폼, 출발점)에 맞게 조정합니다. 함정은 조정을 단순한 크기 변경으로 취급하는 것입니다. 새 맥락에서 플랫폼 관례([ios.md](ios.md) / [android.md](android.md))를 지키면서 경험 자체를 다시 설계해야 합니다. 설정 단계에서 대상 플랫폼 참조를 불러오지 않았다면 계획하기 전에 읽습니다.

## 조정 과제 살펴보기

1. **출발 맥락**: 무엇을 위해 설계했고 어떤 가정을 했나요? (휴대전화 전용? 세로 방향 전용? 한 플랫폼의 관례? 웹사이트?)
2. **대상 맥락**: 어떤 기기 종류(휴대전화, 태블릿, 폴더블), 화면 방향, 플랫폼, 사용 자세(이동 중 한 손 사용 vs 멈춰서 양손 사용)를 대상으로 하나요?
3. **깨지는 부분**: 대상에서 탐색 방식이 맞지 않나요? 레이아웃이 재구성되지 않고 늘어나나요? 대상 플랫폼에 없는 제스처나 컨트롤을 사용하나요?

## 조정 전략

### 휴대전화 → 태블릿(iPad / 대형 화면)

- **늘리지 말고 재구성합니다.** 휴대전화 UI를 확대해 태블릿에 넣는 것은 실패한 설계입니다. 구조를 바꾸려면 iOS의 size class / Android의 window size class를 사용합니다.
- **탐색 방식도 변합니다.** iPad에서는 탭 바를 유지하거나 사이드바로 바꿀 수 있고, Android의 탐색 바는 너비가 확장되면 rail이나 drawer가 될 수 있습니다.
- **너비를 활용합니다.** 분할 화면 / 마스터-디테일(목록과 상세를 나란히), 여러 열의 그리드, 휴대전화에서 sheet를 썼던 자리에 팝오버를 사용합니다.
- **멀티태스킹은 예외가 아니라 화면 크기입니다.** iPad Split View와 Android 다중 창에서는 태블릿이 휴대전화 너비의 창을 받을 수 있습니다. size class 기반 레이아웃이면 별도 처리 없이 대응할 수 있습니다.

### 화면 방향과 폴더블

- 가로 방향에서는 나란한 패널이나 위치를 바꾼 컨트롤처럼 구조를 재구성합니다. 내용을 자르거나 레터박스를 두지 않습니다. 과업에 꼭 필요한 경우에만 화면 방향을 고정합니다.
- Android 폴더블은 window size class를 통해 자세와 힌지에 대응합니다. 접은 상태, 펼친 상태, 탁상 모드를 모두 확인합니다.

### 플랫폼 간 조정(iOS ↔ Android)

| iOS | Android |
|---|---|
| 탭 바 | 탐색 바 / rail / drawer |
| 가장자리에서 쓸어 뒤로 가기, 뒤로 가기 꺾쇠 | 예측형 Back 제스처 / 버튼 |
| 스위치, 분할 컨트롤, 시스템 선택기 | Material 스위치, 칩, Material 선택기 |
| 액션 시트 | 하단 시트 / Material 대화상자 |
| SF Symbols, SF Pro, Dynamic Type | Material Symbols, Roboto, sp 크기 조정 |
| 의미 기반 시스템 색상, 재질 | Material 색상 역할, tonal elevation |
| 시스템 push / sheet 전환 | Container transform, shared-axis, fade-through |

대상 플랫폼의 어휘로 탐색과 컨트롤을 다시 만듭니다. 브랜드의 표현 요소(팔레트 의도, 글꼴 포인트, 모션 성격)는 대상 플랫폼의 테마 시스템을 통해 이어갑니다.

### 웹 → 네이티브(웹사이트 또는 웹 앱 포팅)

단순히 재배치하지 말고 플랫폼 관례에 맞게 재구성합니다. 웹 탐색은 플랫폼의 탐색 방식으로, HTML 형태의 컨트롤은 플랫폼 컨트롤로, hover 기능은 터치 우선 동작으로, px 기반 글꼴은 Dynamic Type / sp로 바꿉니다. 그런 다음 대상 플랫폼의 전체 참조 지침을 적용합니다. 그곳의 품질 검사가 인수 기준입니다.

## 구현 및 확인

- 구조는 기기 모델 확인이 아니라 **size class / window size class**를 기반으로 구성합니다.
- 모든 새 구성에서 안전 영역과 윈도우 inset을 지킵니다(노치, 힌지, 상태 표시줄, 키보드).
- 다양한 상황은 시뮬레이터로 확인한 뒤 실제 기기에서 검증합니다. 출시 대상 플랫폼마다 휴대전화와 태블릿을 최소 한 대씩 사용하고, 두 화면 방향과 지원되는 경우 분할 화면도 확인합니다.

각 사용 맥락에 자연스럽게 어울리면 최종 점검을 위해 `$impeccable polish`로 넘깁니다.

**피할 것**:
- 휴대전화 레이아웃을 늘린 채 태블릿에 출시하기
- 한 플랫폼의 컨트롤이나 탐색을 다른 플랫폼에 그대로 옮기기
- 작은 기기에서 핵심 기능 숨기기(중요한 기능이면 작게 만들어서라도 작동하게 하기)
- 레이아웃 문제를 피하려고 화면 방향 고정하기
- 시뮬레이터만 믿기(기기 자세, 제스처, 성능은 실제 기기가 필요함)
