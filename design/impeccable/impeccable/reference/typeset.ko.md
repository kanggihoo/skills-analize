타이포그래피는 정보, 위계, 목소리를 전달합니다. 확립된 시각 세계 안에서 개선하고, 사용자가 요청하지 않았다면 정체성을 교체하지 않습니다.

---

## 방문자 모드

- **Persuade + Experience**: display 글꼴이 화면의 목소리를 이끌 수 있습니다. 구성이 이점을 얻는 경우 분명한 대비와 반응형 크기를 사용합니다.
- **Operate + Read**: 안정성, 훑어보기 쉬움, 행 길이를 우선합니다. 잘 조정된 단일 글꼴 계열과 고정 역할 크기 체계가 적합한 경우가 많습니다.
- **네이티브**: 플랫폼 글자 크기 조정과 접근성 동작을 포함해 [ios.md](ios.md) 또는 [android.md](android.md)를 따릅니다.

글꼴을 교체하면 새로운 정체성이 되는 경우 [new-work.md](new-work.md)를 따르고 DESIGN.md를 업데이트합니다. 그 외에는 확인된 글꼴 계열을 유지하고 사용법을 개선합니다.

## 서로 독립된 두 가지 평가

sub-agent 도구를 사용할 수 있고 허용된 경우 다음 두 검사를 독립적으로 실행합니다. 그렇지 않으면 직접 1번부터 실행합니다. 탐지기 결과가 디자인 평가의 판단 기준이 되지 않도록 합니다.

1. **타이포그래피 평가**: 대표 페이지와 스타일을 살펴봅니다. 아래 질문에 파일, selector, 계산된 값으로 답합니다.
   - **권위와 적합성**: 이미 정해진 글꼴, 굵기, 역할은 무엇인가요? 제품과 선택한 시각 세계에 맞나요, 아니면 확인하지 않은 기본값인가요? 모든 글꼴 계열이 필요한가요?
   - **위계**: 제목, 본문, 레이블, 메타데이터, 데이터 역할을 한눈에 구분할 수 있나요? 가까운 글자 크기나 굵기가 서로 다른 역할을 맡기에 너무 비슷한가요?
   - **크기 체계와 일관성**: 의도적으로 정한 역할 체계가 있나요, 아니면 임의 값 모음인가요? 반복되는 역할이 모든 화면과 상태에서 동일한가요?
   - **읽기**: 본문이 편안한 45~75자 행 길이를 유지하나요? 실제 글꼴, 너비, 언어, surface에 맞춰 행간, 단락 리듬, 대비, 자간을 조정했나요?
   - **부하 상황**: 긴 제목, 현지화로 늘어난 텍스트, 확대, 좁은 컨테이너, 굵기 누락, 글꼴 대체 상황은 어떤가요?
   - **전달 방식**: 실제 사용하는 에셋만 불러오나요? 대체 글꼴 메트릭, 로딩 전략, variable font 설정이 텍스트가 보이지 않거나 레이아웃이 크게 움직이는 문제를 막나요?
2. **기계 검사**: 다음 명령을 실행합니다.

```bash
.agents/skills/impeccable/scripts/impeccable detect --json --scope type [target files or dirs]
```

탐지기가 해석할 수 없는 동적 / 임의 글꼴 값도 확인합니다. 수정 전에 두 평가를 종합하고 각 평가에서만 발견한 사항을 기록합니다. 검사가 깨끗하더라도 좋은 타이포그래피가 입증된 것은 아니며 최소 기준일 뿐입니다.

## 시스템 정의

수정 전에 다음을 적습니다.

- 인터페이스에 필요한 역할
- 역할 간 의도한 대비
- 읽기 행 길이와 정보 밀도
- 기준으로 삼을 기존 글꼴과 굵기
- 성능, 현지화, 접근성 제약

분명한 위계를 만드는 데 필요한 최소한의 역할과 글꼴 계열만 사용합니다. 크기만으로 모든 역할을 구분하지 말고 크기, 굵기, 공간, 색조를 의도적으로 조합합니다. 역할 이름과 토큰 이름은 값을 설명하지 말고 목적을 설명해야 합니다.

## 적용

- 본문이 읽기 편하고 확대 가능하도록 합니다. 조밀한 역할, 플랫폼 관례, 사용자 설정으로 달리해야 하는 사유가 없다면 웹 본문의 일반적인 최소 크기는 `1rem` / `16px`입니다.
- 본문 행 길이는 45~75ch로 유지합니다. 행간은 행 길이에 반비례해 조정합니다. 행이 길면 대체로 행간을 더 넓힙니다.
- 어두운 surface의 밝은 글자는 인지의 세 축 모두에서 보정합니다. 행간을 약간 늘리고 자간을 소폭 추가하며 글꼴에 필요하다면 굵기를 한 단계 올립니다.
- 보편적인 비율 하나가 아니라 글꼴, 너비, 언어, 대비에 맞춰 행간을 조정합니다.
- 반복되는 역할은 화면과 상태 전반에서 일관되게 유지합니다.
- 콘텐츠가 이점을 얻는 경우 숫자, tabular, code, label 기능을 사용합니다.
- 실제 사용하는 글꼴 에셋과 굵기만 불러옵니다. 메트릭이 호환되는 대체 글꼴을 제공하고 텍스트 표시를 막지 않습니다.
- 유용하다면 마케팅용 display 글꼴은 남은 공간에 반응하게 합니다. 밀도가 높은 제품 UI와 읽기 화면은 공간적 예측 가능성을 유지합니다.
- 브라우저 확대, 사용자 글꼴 설정, Dynamic Type, 플랫폼 텍스트 크기 설정을 유지합니다.
- 단락 리듬은 단락 간격 또는 첫 줄 들여쓰기를 기본으로 사용합니다. 둘 다 함께 사용하면 경계를 이중으로 표시하는 경우가 많습니다.

이해를 해치도록 글자를 장식하거나 분명한 역할 없이 글꼴 계열을 두 번째로 추가하지 않습니다.

## 줄바꿈

Matthew Butterick의 *Practical Typography*를 바탕으로 풀어 썼습니다. 그의 수치와 이 문서의 수치가 다르면 이 문서의 값을 따릅니다.

- 제목과 가운데 정렬된 짧은 블록에는 `text-wrap: balance`, 본문에는 `text-wrap: pretty`를 설정합니다. 두 속성은 점진적 향상입니다. 브라우저가 무시해도 기본 줄바꿈이 유지됩니다.
- `pretty`는 줄 끝에 단어 하나만 홀로 남으면 옆줄로 내려 줍니다. 마지막 줄을 꽉 채우지는 않으며 마지막에 단어 두 개가 남는 것은 괜찮습니다.
- 둘 다 도움이 되지 않을 만큼 열이 좁으면 문구를 고치거나 열 너비를 늘립니다.
- 제목의 줄바꿈은 구절 사이에서만 직접 지정하고 그 제목이 표시되는 모든 화면 너비에서 확인합니다. 휴대전화에서 한 줄 한가운데에 걸리는 강제 줄바꿈은 기본 줄바꿈보다 나쁩니다.
- 불균형한 줄바꿈이 의미를 전달할 수는 있습니다. 강조하려고 한 단어만 남긴 제목, 포스터 문구, pull quote 등이 그렇습니다. 강제 줄바꿈이나 해당 요소에 설정한 wrap으로 의도적으로 구현하고 드물게 사용합니다. 그래서 detector의 `straggler`와 `unbalanced-heading` 발견 사항은 참고용입니다. 의도한 줄바꿈을 설명합니다.

## 검증

- 주요, 보조, 본문, 메타데이터 역할을 문구를 읽지 않고도 구분할 수 있습니다.
- 관련 너비와 언어에서 긴 텍스트를 편안하게 읽을 수 있습니다.
- 타이포그래피가 제품과 확립된 시각 세계에 어울립니다.
- 로딩 과정에서 레이아웃이 갑자기 이동하거나 글자가 보이지 않게 되지 않습니다.
- 확대, 텍스트 크기 변경, 초점, 대비, viewport 축소 상황에서 계속 사용할 수 있습니다.
- 마지막 기계 검사에서 설명되지 않은 발견 사항이 없습니다.

각 항목에 렌더링 또는 소스 근거로 답하고 검사를 다시 실행합니다. 확인 없이 단순히 “예”라고 답하지 않습니다.

위계가 안정되면 최종 점검을 위해 `$impeccable polish`로 넘깁니다.

## Live 모드 시그니처 매개변수

모든 변형은 대략적인 `scale` 매개변수를 선언하고 글자 크기 체계를 `var(--p-scale, 1)`에 맞춰 작성합니다.

```json
{"id":"scale","kind":"range","min":0.85,"max":1.3,"step":0.05,"default":1,"label":"Scale"}
```

실제 시스템 선택지를 나타내는 경우에만 글꼴 조합이나 굵기 매개변수를 하나까지 추가합니다. [live.md](live.md)의 매개변수 계약을 따릅니다.
