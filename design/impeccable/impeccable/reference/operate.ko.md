# Operate 모드 깊이 안내(및 Read 참고 사항)

디자인이 제품을 **지원**하는 화면을 대상으로 합니다. 앱 UI, 관리 대시보드, 설정 패널, 데이터 표, 도구, 인증 후 화면 등 사용자가 작업을 수행하는 모든 영역이 해당합니다. 기본 사항은 SKILL.md의 modes와 [craft-floor.md](craft-floor.md)에 있습니다. 이 파일은 Operate 화면을 위한 추가 지침입니다. Read 화면(문서, 안내서, 장문)은 SKILL.md의 Read 모드와 이 파일의 타이포그래피 및 일관성 규칙을 따릅니다. 이 경우 컴포넌트 밀도보다 문장의 길이와 탐색이 중요합니다.

## 제품 UI 품질 검사

익숙한 느낌은 이 화면에서 오히려 장점일 수 있습니다. 범주에 익숙한 사용자가 즉시 UI를 신뢰할 수 있나요, 아니면 미묘하게 관례에서 벗어난 컴포넌트마다 멈춰야 하나요?

제품 UI의 실패는 밋밋함이 아니라 목적 없는 낯섦입니다. 과하게 장식한 버튼, 서로 다른 양식 컨트롤, 쓸데없는 모션, 레이블에 사용한 디스플레이 글꼴, 표준 과업에 새로 만들어 낸 affordance가 그 예입니다. 목표는 신뢰할 수 있는 익숙함입니다. 도구는 과업에 녹아들어 눈에 띄지 않아야 합니다.

## 타이포그래피

- **하나의 글꼴 계열이 적절한 경우가 많습니다.** 제품 UI에 디스플레이 / 본문 페어링은 필요하지 않습니다. 잘 다듬은 산세리프 하나로 제목, 버튼, 레이블, 본문, 데이터를 표현할 수 있습니다.
- **유동 크기가 아닌 고정 rem 체계**를 사용합니다. clamp 기반 제목은 제품 UI에 적합하지 않습니다. 사용자가 일정한 DPI의 화면에서 보므로 sidebar 안에서 줄어드는 fluid h1은 더 나빠 보입니다.
- **크기 비율을 좁게 잡습니다.** 단계 사이 1.125~1.2가 일반적입니다. 브랜드 화면보다 다양한 글자 요소가 있으므로 과장된 대비는 잡음이 됩니다.
- 문장의 행 길이는 여전히 중요합니다(65~75ch). 데이터와 밀도 높은 UI는 더 촘촘할 수 있으며 표는 120ch 이상도 괜찮습니다.

## 색상

제품 UI의 기본은 절제입니다. 하나의 surface가 과감한 표현을 할 수는 있습니다(한 범주 색상으로 보고서를 표현하는 대시보드, 강한 색으로 채운 환영 화면이 있는 onboarding 등). 하지만 절제가 기본입니다.

- hover, focus, active, disabled, selected, loading, error, warning, success, info 등 상태 중심의 의미 색상 체계를 갖추고 표준화합니다.
- 포인트 색상은 주요 동작, 현재 선택, 상태 표시기에만 사용하며 장식에는 쓰지 않습니다.
- sidebar, toolbar, panel을 위한 두 번째 중성 레이어를 둡니다(콘텐츠 surface보다 약간 차갑거나 따뜻한 색조).

## 레이아웃

반응형 동작은 글꼴 크기가 유동적으로 바뀌는 방식이 아니라 구조적이어야 합니다(sidebar 접기, 반응형 표, 중단점에 따른 열 구성).

## 컴포넌트

모든 인터랙티브 컴포넌트는 기본, hover, focus, active, disabled, loading, error 상태를 갖습니다. 일부만 구현하고 출시하지 않습니다.

- loading 중에는 콘텐츠 가운데 spinner를 두지 말고 skeleton 상태를 사용합니다.
- 빈 상태는 “여기에 아무것도 없음” 대신 인터페이스 사용법을 알려야 합니다.
- 화면 전체에서 affordance를 일관되게 유지합니다. 버튼 모양, 양식 컨트롤 어휘, 아이콘 스타일을 맞춥니다.
- overlay는 부모 컨테이너 경계 밖에 표시되어야 합니다. `overflow: hidden` 또는 `overflow: auto`인 조상 안의 absolute dropdown은 잘립니다. `<dialog>`, popover API, `position: fixed`, portal을 사용합니다.

## 모션

- 대부분의 전환은 150~250ms로 설정합니다. 사용자가 작업 흐름 중이므로 연출을 기다리게 하지 않습니다.
- 모션은 장식이 아니라 상태를 전달합니다. 상태 변화, 피드백, 로딩, 공개가 목적이어야 하며 그 외의 이유로 쓰지 않습니다.
- 페이지 로드 연속 연출은 사용하지 않습니다. 제품이 로드되면 바로 작업할 수 있어야 합니다. 사용자는 로딩 장면을 보고 싶어 하지 않습니다.

## 제품 UI에서 피할 것

- 상태를 전달하지 않는 장식 모션
- 화면마다 다른 컴포넌트 어휘. 두 화면의 “저장” 버튼 모양이 다르면 하나는 잘못된 것입니다.
- UI 레이블, 버튼, 데이터에 디스플레이 글꼴 사용
- 개성을 위해 표준 affordance 재창작(사용자 지정 scrollbar, 낯선 양식 컨트롤, 표준에서 벗어난 modal)
- 비활성 상태에 진한 색상이나 완전 채도 포인트 적용
- 첫 선택으로 modal 사용. 보통 modal은 게으른 방법입니다. 먼저 인라인 / 점진적 대안을 충분히 고려합니다.

## 제품 UI에서 허용되는 것

브랜드 화면에서는 피해야 하는 요소도 제품 UI에서는 쓸 수 있습니다.

- 시스템 글꼴과 익숙한 기본 산세리프
- 표준 탐색 패턴: 상단 bar + 측면 탐색, breadcrumb, 탭, command palette
- 정보 밀도. 사용자가 필요로 한다면 행이 많은 표, 레이블이 많은 패널, 촘촘한 정보
- 놀라움보다 일관성. 화면마다 같은 시각 어휘를 쓰는 것은 장점이며, Delight는 화면 전체보다 특정 순간에 아껴 씁니다.
