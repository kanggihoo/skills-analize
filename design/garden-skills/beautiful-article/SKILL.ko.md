#아름다운기사

## 배경 원칙

AI가 생성하는 콘텐츠가 복잡할수록 출력 매체의 중요성도 커집니다. HTML의 가치는 정보 밀도, 시각적 명확성, 공유 용이성 및 대화형 기능(테이블, SVG, CSS, 코드 조각, 조정 가능한 컨트롤, 복사 및 내보내기 버튼)을 동시에 향상시키는 데 있습니다. 이를 통해 독자는 "읽기"뿐만 아니라 비교, 찾기, 조정, 검토 및 계속 사용할 수 있습니다. Beautiful Article의 목적은 원래 지루하고 선형적이며 소화하기 어려운 텍스트 자료를 더 아름다운 시각적 경험, 더 명확한 읽기 리듬을 갖고 검토 및 공유하기 더 쉬운 단일 파일 웹 기사로 변환하는 것입니다.


## 경계(먼저 이 스킬을 입력할지 여부를 결정)

- 최종 주요 제품은 웹 애플리케이션이 아닌 **단일 HTML 기사**입니다.
- 기사에는 `Raw` 무료 레이어(모든 HTML / CSS / JS / React: 상호 작용, 레이아웃, 애니메이션, 위젯,
  SVG/요청 시 캔버스 일러스트레이션), 읽기, 해석, 논쟁, 리듬 또는 미학을 제공해야 합니다.
- **생성되지 않음**: 백엔드, 양식, 드래그 앤 드롭 워크벤치, 전체 대시보드, 제품 프로토타입, 범용 웹 앱.
- 정보 밀도는 사용자에 의해 확인됩니다. **기본적으로 100% 정보를 유지**하고 긴 텍스트의 웹 기사를 생성합니다.

사용자가 기사가 아닌 애플리케이션을 원하는 경우 중지하고 명확하게 설명하고 이 기술을 입력하지 마세요.

   ▼
Phase 2  Editorial Planning 一份 plan.md（Brief / Outline / Theme / Assets 四段）
         └ 主 Agent 内联自查（无 SubAgent、无 review 文件）
   ▼
Phase 3  Plan Checkpoint   ★Checkpoint 1 必须停。逐项确认 5 件事：文章类型（含标配保留比例）/ 主题 / 版式 / 配图模式 / 封面
   ▼
Phase 4  First Spread      首屏 + 第一节 + 一个代表性视觉块（脚手架在此创建）
         └ First Spread Reviewer SubAgent（写 review/first-spread-review.md）
         └ ★Checkpoint 2 必须停。逐项确认 2 件事：验收结论 / 开发模式 A/B
   ▼

   ▼

## 엄격한 품질 검사 프로토콜(전체 스킬 전반)

**품질 검사 방법은 노드별로 다릅니다. 모든 품질 검사에 SubAgent를 열어야 하는 것은 아니며, 모든 품질 검사에 문서 작성이 필요한 것도 아닙니다. **
실수로 SubAgent를 열거나 실수로 파일을 쓰는 것이 주요 성능 문제입니다. 다음 표를 엄격하게 구현하십시오.

| 노드 | 품질검사방법 | 제품 | 왜 |
|---|---|---|---|
| **1단계 소스(기본값)** | 기본 에이전트에는 5개의 인라인 체크리스트가 있습니다 | 파일 없음 | 기본 에이전트는 어쨌든 source.md를 읽어야 합니다. |
| 1단계 소스(복잡하고 신뢰도가 낮은 소스만 해당) | 소스 검토자 SubAgent(`original.*` 대비) | `review/source-review.md` | 조용한 손실은 diff |
| **2단계 계획 / 1차 체크포인트** | **주 Agent 인라인 자체 점검(Sub Agent 열람 금지)** | **파일 없음** | 계획은 200-400줄의 텍스트 결정이며 컨텍스트가 뜨겁고 SubAgent 콜드 스타트가 더 느립니다 |
| **4단계 1차 확산 / 체크포인트 2전** | 첫 번째 스프레드 검토자 하위 에이전트 | `review/first-spread-review.md` | 첫 번째 화면이 톤을 설정하고, 독립적인 눈이 하나 더 있으면 더 안정적입니다 |
| **각 섹션별 5단계** | 섹션 검토자 하위 에이전트 | **반환 합격/불합격 + 메시지가 포함된 수리 지점(기록된 파일 없음)** | 하나의 기사에는 5-15개의 섹션과 N개의 리뷰 파일이 있을 수 있으며, 아무도 읽지 않습니다 |
| **6단계 최종 검토/3차 체크포인트** | 편집 + 시각적 + 기술 검토자 SubAgent | `review/final-review.md` | 파일 보관에 유용한 결과물의 일부 |

**철칙:**

1. **계획 체크포인트(2단계 → 체크포인트 1)에서는 품질검사를 위한 SubAgent 개설을 엄격히 금지합니다**. 메인 에이전트가 plan.md 작성을 마쳤습니다.
   그런 다음 **현장**에서 5개 목록을 확인하고(`references/review-checklist.md`의 자체 검토 계획 섹션 참조) 결론을 도출합니다.
   `plan/plan.md`를 변경한 후 **리뷰 파일을 작성하지 않음** 후 체크포인트 1에 진입합니다.
2. 첫 번째 Spread/Final은 SubAgent를 사용해야 합니다(이 두 노드의 SubAgent 값 > 오버헤드). 감지할 수 없는 경우에만
   SubAgent 환경은 기본 Agent가 담당하며 파일 시작 부분에 "SubAgent 환경이 없으며 기본 Agent가 처리합니다"라고 명시되어 있습니다.
3. 섹션 검토자는 SubAgent를 사용하지만 **반환 값은 메시지**입니다(합격/실패 + 복구 지점). 실패 항목이 주 Agent입니다.
   수령 후 바로 수리하세요. **SubAgent가 `review/section-NN-review.md` 파일을 쓰도록 허용하지 마세요**.
4. 품질 검사 결론 얻기 - **먼저 실패 항목을 클릭하여 출력 변경을 완료한 다음 "완료 + 자체 검사 결론 + 변경 사항"을 보고합니다**.
   고치지 않고 원래 결론대로 직접 신고하는 것 = 위반.
5. **결정 수집의 철칙 · 사용자에 대한 자동 선택 금지**: 각 체크포인트(1/2/3)에서 사용자 확인이 필요한 모든 결정은
   결정 항목 **독립적으로 나열되어야 하며 사용자 응답을 기다립니다**. 상담원이 **추천할 수 있습니다**("X를 추천하는 이유는..."). 하지만
   **"이미 X를 결정해 주셨는데, 옳지 않다면 말씀해주세요"라고 할 수는 없습니다.** - 이는 선택할 기회를 박탈하는 것과 같습니다.
   - **우선순위**: 환경에 `AskQuestion` 도구가 있는 경우 각 결정 항목은 독립적인 질문으로 처리됩니다(한 번의 호출로
     여러 질문 제출) 사용자는 선택 카드를 사용하여 하나씩 확인할 수 있습니다.
   - **그렇지 않은 경우**: 중지하고 메시지의 모든 질문 **번호**를 나열합니다(각 질문에는 자체 단락이 있으며 권장 사항 + 이유 +
     대안), "계속하기 전에 귀하의 항목별 응답을 기다리겠습니다"라고 명확하게 말하고 **후속 작업을 계속하지 않습니다**.
   - **안함**: 여러 결정을 하나로 묶습니다. "추천하는 항목을 모두 선택하세요. / 모두 괜찮나요?" 예/아니오 질문; 또한하지 않습니다
     "문장 추천" 후 바로 다음 단계로 넘어가는 것이 기본입니다.

각 노드의 체크리스트 및 SubAgent 프롬프트 템플릿은 `references/review-checklist.md`를 참조하세요.

## 1단계 —— 소스 → 마크다운

모든 입력을 `source/source.md`에 통합하고 불확실한 항목을 `source/extraction-notes.md`에 씁니다.
규칙 및 다양한 입력 처리에 대해서는 `references/source-to-markdown.md`를 참조하세요. 당신은 사용할 수 있습니다
PDF/DOCX/HTML 추출을 위한 MarkItDown 기본 경로 또는 경량 대체 스크립트입니다.

주문 후 **주 대리인은 인라인 자체 점검**(`references/source-to-markdown.md`에 대한 5개 체크리스트)을 수행하고 결론에 따라 수리합니다.
2단계를 다시 입력합니다. **`extraction-notes.md`가 낮은 신뢰도/복잡한 소스를 플래그하는 경우에만 독립형 소스 검토기로 업그레이드하세요**
SubAgent를 실행하고 `original.*`에 대해 차이점 확인(`review/source-review.md` 작성)을 수행합니다.

**언어 처리(추출 후 즉시)**: `source.md`의 언어를 결정합니다.- 사용자가 ** 지정하지 않았습니다 ** 대상 언어 또는 대상 언어 **가 소스와 일치합니다 ** → 번역이 없으며 이후 작성은 `source.md`를 기반으로 직접 작성됩니다.
  최종 기사 언어 = 소스 언어.
- 사용자가 대상 언어를 **지정**하고 **원본과 불일치** → **진짜 번역** `source/source.<lang>.md`를 먼저 생성합니다.

  테마와 스타일을 일관되게 유지하고 갈등을 해결하세요. 하위 에이전트 프롬프트 템플릿은 `references/section-build.md`를 참조하세요.

기타 원칙: 텍스트가 본문입니다. 모든 Raw는 `--ra-*` 테마 토큰을 사용하며 와일드 스타일은 금지됩니다. 긴 텍스트에 100% 정보가 유지됩니다.
구조가 주요 구조이며, 향상을 위해 Raw/이미지가 사용됩니다. 정보 밀도가 낮으면 시각적 블록의 비율이 늘어날 수 있지만 여전히 **기사 형식**이어야 합니다.

각 섹션이 완료된 후 **반드시** 엄격한 품질 검사 프로토콜을 따라야 합니다. **섹션 검토자 하위 에이전트**: 개요 완료 여부
업무 / 정보 보유율을 충족하는지 / 앞뒤로 연결되어 있는지 / 과도하게 구성요소화되어 있는지 / 텍스트가 충분한지 / Raw and
그림에 명확한 목적이 있는지 여부/이 섹션의 일련 번호는 일관성이 있습니다.

**SubAgent는 합격/실패 + 수리 포인트를 메시지로 반환합니다**(합격은 한 줄이 정상임을 의미하고, 실패는 수리 포인트가 나열됨을 의미함), ** 쓰지 않음
`review/section-NN-review.md` 파일**. 실패 항목을 받은 후 메인 에이전트는 해당 섹션 파일**을 직접 복구합니다.

##기본 전략

- 단일 HTML을 출력합니다. 품목 유형 `longform`; 정보 보존 100%.
- 언어: 사용자가 **지정하지 않으면**, **원본 언어를 따릅니다**. **원본을 명시하고 소스와 일치하지 않는** 경우 원본 번역이 먼저 생성됩니다.
  그런 다음 `source/source.<lang>.md`가 그에 따라 작성됩니다(번역을 제거하려면 1단계 참조).
- 주제: 기술/증거 우선 `tufte`, 서술/검토 우선 `press`(원본 자료에서 권장)
- 레이아웃: 너비는 기본적으로 `regular`로 설정되고 **TOC는 기본적으로 활성화됩니다**(테마와 분리됨, `references/layout.md` 참조, 둘 다 체크포인트에서 확인됨).
- 사진: **사진 모드는 체크포인트 1 필수** (`none` / `user-assets` / `placeholders` /
  `ai-generated`)는 외부 `Image` 사용 여부만 결정하며 **AI 이미지를 적극적으로 생성하지 않습니다**.
- 원시: **첨부된 그림과 직교하며 기본적으로 항상 존재합니다**, 다중 사용이 권장되지만 특정 단락을 제공하고 테마 토큰을 사용해야 합니다. `none`를 선택하세요.
  Raw에는 영향을 주지 않습니다.
- 자체 검사: **인라인 자체 검사 계획(하위 에이전트 없음, 파일 없음)**; **First Spread 및 Final은 SubAgent +를 사용하여 파일을 작성합니다**;
  **섹션이 SubAgent + 메시지와 함께 반환됩니다(파일을 쓰지 않음)**. 자세한 내용은 "하드 품질 검사 프로토콜" 섹션을 참조하세요.
- 의사결정 수집 : 체크포인트 1 / 2 / 3 **각자 독립적 확인 · 사용자에 대한 자동 선택 비활성화**. 권장되지만 건너뛸 수는 없습니다.
  `AskQuestion` 도구에 우선순위를 부여합니다(각각 독립적인 질문입니다). 도구가 없으면 중지하고 번호가 매겨진 질문을 나열하고 사용자 응답을 기다립니다.
- 복구: 최소 슬라이스, 복구된 경우에만 `review/repair-log.md`를 작성합니다.
- **콜로폰 · 분리 불가**: 비계에는 `article/Article.tsx` 끝에 콜로폰 원시 블록이 함께 제공됩니다.
  (`Made with [beautiful-article](github 仓库) · <主题> theme`, 낮은 대비 작은 글꼴, 테마 토큰 적응형).
  **모든 글은 그대로 남아 있어야 하며** 삭제하거나 영웅 옆으로 이동하거나 구석으로 떠다닐 수 없습니다. 테마 전환 시 동기식으로 콜로폰 업데이트
  테마 이름은 `main.tsx` + `<ThemeProvider theme="...">` 두 곳에 있습니다.
- **표지 · 기본적으로 켜져 있음 · 사진과 텍스트를 포함해야 함**: 스캐폴드는 기본적으로 `article/Cover.tsx`에서 생성됩니다** 화면 3:4 +
  PDF 독점홈페이지** 책 표지 스타일 제목 그림 셸 + 자리 표시자(`--no-cover` 닫힘). 표지는 TOC+히어로+텍스트 위에 있고,
  독립적으로 존재합니다. 4단계 첫 번째 확산 동안 주 에이전트는 `<CoverPlaceholder />`를 **topic +로 대체합니다.
  기사 주제** 맞춤형 그림 + 텍스트 구성. **강한 제약**: 쉘 비율/인쇄 페이지 매김은 이동할 수 없으며 시각적 요소가 있어야 합니다.
  + 텍스트, `--ra-*` 토큰만 사용, 원격 이미지 없음, 중복된 영웅 콘텐츠 없음. **시각적 기술은 완전히 개방되어 있습니다**:

  표지는 첫 번째 페이지에만 있고 TOC는 두 번째 페이지에서 시작됩니다.
- **PDF 내보내기 · 선택 사항**: 주요 결과물은 항상 `article/article.html`입니다. **해당 경우** 체크포인트 3 사용자가 선택됨
  `bash <skill>/scripts/html-to-pdf.sh`를 실행하여 생성하기 전에 "HTML + PDF를 동시에 내보내기"
  `article/article.pdf`; 선택하지 않으면 이동하지 않습니다. 사용자에게 기본값을 부여하지 마십시오. 자세한 내용은 `references/pdf-output.md`를 참조하세요.

## 성공 기준

- **가장 중요한 기사**입니다.
- 최종 기사의 언어가 사용자의 의도에 부합합니다.
  잔여 소스 언어 조각 없음).
- 이용자가 확인한 정보의 밀도를 존중합니다. 소스 자료의 주요 내용이 실수로 손실되지 않습니다.
- 주제와 기질이 통일되어 있다. 그림과 Raw는 모두 읽기용으로 사용됩니다.
- 페이지는 Markdown보다 읽을 가치가 더 높습니다. HTML을 직접 열고 공유할 수 있습니다.
- 40%의 정보는 요약된 요약이 아닌 편집된 기사처럼 읽혀집니다. 100% 정보는 세련된 장문의 글처럼 읽혀지며,
  원본 텍스트를 옮기는 대신.
