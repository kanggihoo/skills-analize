# 글 유형 · 설명문

메커니즘 / 시스템 / 개념 / 알고리즘 / 프로토콜을 설명합니다. 독자가 글을 읽고 나면 그것이 **어떻게 작동하는지, 왜 그렇게 되는지, 언제 쓰고 쓰지 말아야 하는지 이해**해야 합니다.

- **권장 정보 보존율:** 80%(주요 메커니즘과 핵심 세부는 남기고 반복 / 곁가지 / 역사적 배경을 제거합니다. “핵심 직관”과 “흔히 하는 실수”는 모두 보존합니다.)
- **전형적인 구조:** `Hero` → `Lead`(왜 이해해야 하는가 / 모르면 어떤 비용이 있는가) → `Section`: 문제 → 메커니즘 → 도식 → 예시 → 흔한 오해 → 사용 시점 / 금지 시점 → `Conclusion`.
- **컴포넌트 선택:** 메커니즘은 본문으로 설명합니다(**본문이 중심이며** 카드를 쌓듯 쪼개지 않습니다). “핵심 직관 / 한 문장 본질 / 흔한 실수”는 `Aside tone="principle"`로 강조합니다. 구체적인 예시는 `CodeBlock`, 방법 / 변형 비교는 `Table`, 부차적인 세부나 심화 유도는 `Detail` / `Tabs`, 원 논문 / 표준 문구는 `Quote`를 사용합니다.
- **Raw 사용 기준:** **설명을 돕는 시각 요소를 적극 활용합니다.** 메커니즘 흐름, 상태 변화, 데이터 흐름, 개념 간 관계를 Raw 자유 형식(HTML 레이아웃 / 간단한 상호작용 / 애니메이션 / 필요한 경우 SVG)으로 구현해 추상 개념을 보이고 비교합니다. 각 블록은 **구체적인 메커니즘 하나를 설명**해야 합니다. Raw는 보조 자료이며 중심이 아닙니다. Raw가 주요 정보를 맡고 본문이 그림 설명으로 변하면 `interactive-explainer`를 고려합니다.
- **이미지 성향:** 설명용 시각 자료를 우선합니다(Raw — 인터랙션 / 레이아웃 / 애니메이션 / SVG 모두 가능). 실제 UI / 시스템 스크린샷이 필요하면 `user-assets`를 쓰고 분위기용 이미지는 적게 사용합니다.
- **테마 성향:** `tufte`(기술 / 데이터), `shannon`(시스템 / 엔지니어링), `knuth`(학술), `freddie` / `bayer`(초보자용으로 활기 있게), `fuller`(시스템 설계 / 프로토콜).
- **자체 점검:**
  - 독자가 단순히 “이런 게 있구나”를 넘어 메커니즘을 **진짜 이해**하는가?
  - 도식은 이해에 도움이 되는가, 아니면 장식에 그치는가? 도식을 제거하면 이해가 어려워지는가?
  - 가장 흔히 걸리는 함정 2–3개를 다뤘는가?
  - “언제 사용 / 사용하지 말아야 하는가”가 명확한가? 이 지점이 explainer와 longform의 주요 차이입니다.
  - 긴 기술 글에서 20%를 줄여도 충분히 설명된다면 explainer를 우선합니다. 원문을 보관해야 한다면 `longform`을 사용합니다.

> **explainer를 사용하지 말아야 할 때:**
>
> - 독자가 **직접 조작해 배우도록** 하고 Raw가 주된 전달 수단이어야 함 → `interactive-explainer`.
> - 독자가 **따라 하며 무언가를 완성**해야 함 → `tutorial`.
> - 원본이 논문 / 보고서 수준의 완전한 논증임 → `longform` / `full-report`.
