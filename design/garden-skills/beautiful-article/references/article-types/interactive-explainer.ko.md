# 글 유형 · 인터랙티브 설명문

긴 기술 글 / 논문 / 시스템 설계 문서를 **인터랙티브 애니메이션을 중심으로 배우고 직접 써 볼 수 있는 학습 페이지로 재구성**합니다.
참고할 만한 방식: 3blue1brown의 시각화, 조정 가능한 매개변수를 사용하는 distill.pub의 머신러닝 설명, Bartosz Ciechanowski(ciechanow.ski)의 “직접 만져 보는 하드웨어 원리” 페이지.

> **explainer와의 핵심 차이:**
>
> - `explainer`: **본문이 중심**이고 Raw는 보조 삽화입니다. 독자가 읽고 “이해합니다.”
> - `interactive-explainer`: **Raw가 중심**이고 본문은 짧은 안내와 정의를 제공합니다. 독자가 **직접 조작한 뒤 “할 줄 알게 됩니다.”**

- **권장 정보 보존율:** 약 25%. (**주의:** 원문의 75%를 삭제하라는 뜻이 아닙니다. 결과물에서 원문 문장 / 문단을 그대로 가져오는 비율이 약 25%라는 뜻입니다.) 이 유형의 핵심은 **콘텐츠 재구성**입니다. 원문에서 핵심 지식의 정의, 공식, 데이터, 제약 조건, 흔한 실수만 **발췌**하고 나머지 75%는 해당 지식을 가르치도록 **새로 작성**합니다. 안내 문구, 직관 설명, 인터랙티브 시연, 직접 조작, 이해도 확인을 새로 만듭니다. 원문의 서사적 도입, 역사적 배경, 사례 전개, 확장 논의는 **모두 덜어 내고** 상호작용으로 대체합니다. 이를 “explainer에서 50%만 지우기”로 취급하지 마세요. 충분히 배우지도 못하고 이 유형의 의미도 사라집니다.
- **전형적인 구조:**
  - `Hero`(한 문장으로 이 페이지에서 배울 것 / 직접 해 볼 것 설명)
  - `Lead`(필요한 사전 지식 1–2문장, 끝난 뒤 할 수 있게 될 것)
  - 선택적 `Summary`(핵심 지식 N개를 로드맵으로 표시)
  - **Concept Section** 여러 개. 핵심 지식 하나마다 아래 세 부분을 구성합니다.
    1. **정의 / 직관:** 본문 1–3문단 + 핵심 직관 한 문장을 강조하는 `Aside tone="principle"`.
    2. **인터랙티브 시연(Raw 중심):** 애니메이션 / 슬라이더 / 드래그 / 상태 전환 / 매개변수 변화의 실시간 시각화.
    3. **직접 시도 / 이해 확인(Raw 상호작용):** 경계 조건 / 반례 / 적용 사례를 독자가 시험하게 합니다. “정답 보기”를 접어서 표시할 수 있습니다.
  - `Conclusion`(지식 연결 요약 + 언제 사용할지 / 사용하지 말아야 할지 + 추가 읽을거리).
- **컴포넌트 선택:**
  - 본문은 **짧게** 씁니다. 각 절의 본문을 합해 보통 200–400자를 넘기지 않습니다.
  - 정의, 핵심 직관, 흔한 실수는 `Aside tone="principle"`로 표시합니다.
  - 부차적인 세부, 정답, 유도 과정은 `Detail` / `Tabs`에 접습니다.
  - 원문 / 논문의 인용문은 `Quote`를 사용합니다.
  - `Table` / `CodeBlock`은 적게 사용합니다. 쓰는 경우 구체적인 인터랙티브 시연을 뒷받침해야 하며 전체 코드 덩어리를 그대로 넣지 않습니다.
  - **`Raw`가 중심입니다.**
- **Raw 사용 기준(핵심 · 필독):**
  - **각 Raw는 구체적인 지식 하나를 설명해야** 합니다. 장식용 과시는 허용하지 않습니다.
  - **직접 조작을 우선합니다.** 슬라이더 / 드래그 / 전환 / 입력 필드 / 단계 버튼으로 사용자가 **값을 바꾸고 결과를 실시간으로 확인**하게 합니다. 애니메이션을 가만히 보는 것보다 깊이 배울 수 있습니다.
  - **상태를 보이게 합니다.** 현재 매개변수, 값, 단계가 화면에 드러나야 하며 애니메이션 속에 숨기지 않습니다.
  - **초기화할 수 있게 합니다.** 각 인터랙션에 reset / 초기값 복원 기능을 제공해 반복해서 시험할 수 있게 합니다.
  - **스타일에는 토큰을 사용합니다.** 색상 / 글꼴 / 간격은 `--ra-*`를 쓰며 임의 CSS 값을 만들지 않습니다.
  - **오류 예시도 유용합니다.** 사용자가 “잘못되는” 위치까지 조작할 수 있게 하고 “여기서 왜 무너지는지” 한 줄로 설명합니다.
- **이미지 성향:** 상호작용이 사진보다 정보를 더 많이 전달하므로 `none`을 우선합니다. 이론 그림 / 스크린샷에는 `placeholders`를 소량 씁니다. 학습 리듬을 방해하는 분위기용 `ai-generated` 이미지는 피합니다.
- **테마 성향:** `tufte`(절제와 데이터 감각, ML / 알고리즘 시각화), `shannon`(어두운 엔지니어링 분위기, 시스템 / 하드웨어 시연), `knuth`(학술적 절제, 논문 재구성). `freddie` / `sottsass`처럼 활기찬 색상은 인터랙션을 학습이 아니라 게임처럼 보이게 하므로 피합니다.
- **자체 점검:**
  - 독자가 단순히 “들어 봤다 / 봤다”가 아니라 개념을 **정말 쓸 수 있게** 되었는가?
  - 각 인터랙션이 구체적인 지식 하나를 설명하는가? 배우는 내용 없이 과시하는 Raw가 있는가?
  - 상호작용이 없는 절이 정말 필요한가, 아니면 구현을 게을리한 결과인가? 이것이 이 유형이 본래 목적에서 벗어났는지 판단하는 핵심 질문입니다.
  - 모바일에서 조작할 수 있는가? 슬라이더 / 드래그 / 복잡한 SVG 다수는 모바일에서 쓸 수 없습니다. Plan 단계에서 “모바일 인터랙션을 포기할지”, “모바일용 대체 표시를 제공할지” 결정해야 합니다.
  - Raw를 모두 지웠을 때 본문이 지나치게 빈약해지는가? 그렇다면 Raw가 정보를 충분히 담지 못했다는 뜻입니다. Raw 안이나 바로 옆에 설명을 보충합니다.
  - 결과물에서 원문 문장 / 문단을 직접 가져온 비율이 실제로 **약 25%**인가? 40%를 넘으면 재구성이 아니라 explainer를 잘라낸 수준입니다. 10% 미만이면 핵심 지식을 제대로 설명하지 않은 것입니다.
  - **핵심 지식 선택에 근거가 있는가?** “왜 이 N개를 남겼는가?”에 한 문장으로 답할 수 있는가? 임의로 고르면 유형이 어긋나기 시작합니다.

> **interactive-explainer를 사용하지 말아야 할 때:**
>
> - 원본이 서사 / 의견 / 논평임 → essay.
> - 독자가 절차를 따라 실행해야 함 → tutorial(단계 사이에 선후 관계가 있고 지식점 병렬 나열이 아님).
> - 원본이 데이터 보고서임 → 상호작용보다 결론이 중요한 full-report.
> - 실제로 조작할 수 있는 Raw를 만들 계획이 없음 → `explainer`를 사용합니다. interactive인 척하지 않습니다.
