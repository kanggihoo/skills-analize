# 글 유형 · 리뷰

**엔지니어링 검토:** PR / 설계안 / 사고 분석 / 아키텍처 / API / 보안 감사. 출발점은 **구체적인 결과물**을 검토해 의견과 실행 항목을 만드는 것입니다.

- **권장 정보 보존율:** 60–80%(핵심 발견 + 근거 + 실행은 남기고 관련 없는 세부 / 배경 설명은 생략).
- **전형적인 구조:** `Hero`(검토 대상 + 범위 + 날짜 / 검토자) → `Summary`(**결론 / 검토 의견을 먼저 제시**) → `Section`: 배경과 목표 → 발견 사항(항목별) → 영향 평가 → 권고 → 실행 항목 → `Conclusion`(핵심 판단 + 통과 / 수정 필요 / 거부).
- **컴포넌트 선택:** **prose-first**를 유지합니다. 결론과 발견을 본문 + `Summary`로 먼저 명확히 씁니다. 아래 **분야별 컴포넌트**는 내용이 실제로 그 구조에 해당할 때만 선택적으로 씁니다. review라는 이유로 전부 넣지 않습니다.
  - 단계별 위험 그룹이 있을 때만 `RiskList`를 사용합니다.
  - 코드 변경을 줄 단위로 평가할 때만 `DiffReview`를 사용하고 코드는 항상 `CodeBlock`으로 표시합니다.
  - “X vs Y”의 선택 관계를 보여 줄 때만 `Decision` / `Tradeoff`를 사용합니다.
  - 사고 검토의 타임라인에는 `Incident`를 사용합니다.
  - 실행 / 승인 체크포인트를 구조화해야 할 때 `ActionList` / `Checkpoint`를 사용합니다.
- **Raw 사용 기준:** 영향 범위 도식, 의존 관계, 위험 히트맵, 호출 경로, 모니터링 추세 등은 Raw 자유 형식(HTML / CSS 매트릭스와 히트맵, 가벼운 상호작용, 필요한 경우 SVG)으로 표현합니다. **절제하고 근거를 우선하며 본문보다 눈에 띄지 않게 합니다.**
- **이미지 성향:** 실제 스크린샷 / diff / 모니터링 차트 / 대시보드 이미지에는 `user-assets`를 사용합니다(`tufte` 스타일).
- **테마 성향:** `tufte`(근거 중심 review), `shannon`(어두운 엔지니어링 / 사고 분석), `fuller`(시스템 설계 / RFC 검토), `vignelli`(중립적 사양 중심).
- **자체 점검:**
  - 검토 의견(통과 / 수정 필요 / 거부)을 글 시작에서 분명히 제시했는가?
  - 모든 발견에 코드 조각 / 스크린샷 / 데이터 / 로그 같은 **근거가 있는가?** 느낌만으로 판단하지 않았는가?
  - 권고와 실행 항목을 **수행할 수 있는가**(담당자 / 기한 / 검수 방법)?
  - 출발점이 **구체적인 결과물**을 검토하는 것인가? 독자의 의사 결정 지원이 목적이라면 `briefing`을 사용합니다.

> **review를 사용하지 말아야 할 때:**
>
> - **제품 / 책 / 논문 / 영화**를 리뷰함(의견 중심이며 “통과 / 거부”의 이분법적 판단이 없음) → `essay`.
> - 상사를 위해 “X를 할 것인가”를 판단하는 요약이 필요함 → `briefing`.
> - 완전한 사후 조사 보고서가 필요함 → `full-report`.
