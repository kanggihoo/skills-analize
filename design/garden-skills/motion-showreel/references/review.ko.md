# 검수와 검토

두 가지를 나눠서 한다.

| | 기술 검사 | 검토 |
|---|---|---|
| 무엇을 판단하나 | 파일이 맞는지: 디코딩 가능 여부, 크기, fps, 길이, 프레임 수, 오디오 트랙, 검은 프레임, 라우드니스, 피크, 루프 이음새 | 보기 좋은지, 잘 들리는지, brief의 목표를 달성했는지 |
| 누가 판단하나 | 프로그램(`inspect.mjs qa`, PASS / FAIL) | 사람. 에이전트는 먼저 이미지를 보고 관찰을 적으며, **최종 판단은 사용자가 한다** |
| 결과 | FAIL이 하나라도 있으면 전달할 수 없다 | 문제와 수정 내용을 기록하고, 알려진 문제는 사용자에게 사실대로 알린다 |

**스스로 매긴 점수는 검수를 대신할 수 없다.** 프레임 샘플은 구도만 검증하고, 연속 샘플은 움직임을 검증한다. 청취가 가능한 환경이라면 청감도 확인한다. 검토 기록에는 실제로 본 범위와 들은 범위를 적으며, 스크린샷, 파형, 자동 측정치를 완전한 시청으로 취급하지 않는다.

---

## 1. 기술 검사

```bash
node <skill>/scripts/inspect.mjs qa <slug>/out/final.mp4 --out <slug>/qa/final \
  --expect-size 1920x1080 --expect-fps 30 --expect-duration 16 \
  --audio required          # 有声片；无声片用 --audio none
  # 循环片再加 --loop（接缝那一步要和普通帧间的一步一样平滑）
```

| 검사 | FAIL 조건 |
|---|---|
| 파일 디코딩 | 비디오 스트림을 읽을 수 없거나 프레임 수가 0 |
| 크기 / fps / 길이 | `--expect-*` 값과 다름(길이는 ±1.5프레임 허용) |
| 프레임 수 | 길이 × fps와 2프레임을 넘게 차이 남 |
| 오디오 트랙 | `required`인데 트랙이 없거나, `none`인데 트랙이 있음 |
| 검은 프레임 | 검은 프레임 구간이 하나라도 나타남 |
| 라우드니스 / 트루 피크(오디오가 있을 때) | −14 ± 1.5 LUFS를 벗어나거나, 트루 피크가 −1 dBTP보다 큼 |
| 루프 이음새(`--loop`) | 마지막 프레임 → 첫 프레임의 SSIM이 그 양옆의 일반 프레임 간 단계(끝에서 두 번째 → 마지막, 첫 번째 → 두 번째)보다 0.03 이상 낮고, 0.97 미만임. 마지막 프레임은 원래 첫 프레임보다 한 프레임 앞서 있으므로, 빠르게 움직이는 루프의 처음과 끝은 완전히 같지 않다. 비교 대상은 「그 한 단계에서 튀었는가」이다 |

규격 항목을 전달하지 않은 경우(크기, fps, 길이, 오디오 트랙)는 `NOT CHECKED`로 나열되며, 결말에 「全部通过」(전부 통과)라고 쓰지 않는다. 이때는 검수로 인정하지 않으며, brief의 사양대로 다시 실행해야 한다. `sh build.sh`는 상단의 `FPS / SIZE / AUDIO / LOOP`와 `timeline.js`의 `DUR`을 사용해 모든 항목을 자동으로 채운다.

매개변수에 오타가 있으면(예: `--audio requried`, `--expect-size 1920*1080`) 조용히 넘어가지 않고 바로 오류로 종료한다.

또한 `render.mjs`는 프레임 수가 맞지 않거나, 페이지에서 오류가 나거나, 인코더가 종료되면 아무 출력도 남기지 않고 실패한다. `--determinism`은 반드시 통과해야 한다. `build.sh`는 출력 전에 이를 한 번 자동으로 실행한다(초안일 때만 `DETERMINISM=0`으로 건너뛸 수 있다).

## 2. 검토

이야기, 시연, 서사 영상은 내용이 화면 안에서 실제로 일어나는지 확인한다. 대상의 전후 상태가 분명한지, 샷들이 이어지는지, 그저 타이틀 카드와 정적 레이아웃을 바꿔 끼운 것은 아닌지 본다. 상태 변화와 이음새를 포함하는 연속 샘플을 골라 소리와 함께 재생하고, 핵심 지점은 드래그하거나 프레임 단위로 본다. 대상의 정체성, 공간 방향, 동작 속도를 확인하며, 넓은 배경 움직임으로 주체가 움직이지 않는 것을 가려서는 안 된다. 로고, 모션 타이포그래피, 의도적으로 정지한 스타일은 brief에 따라 판단하며, 지속적인 움직임을 강요하지 않는다.

나레이션이 있으면 먼저 `narration.mjs check`를 실행한다(사용법은 `narration.md` 참고). 그다음 사용자 원고가 완전한지, 음성에 글자가 빠지거나 반복되지 않는지, 화면이 문장의 강조점을 따르는지 문장별로 대조한다. 사람의 목소리가 나오는 동안 BGM과 효과음이 비켜 주는지 확인한다. 자동 라우드니스가 통과했다고 해서 음성이 선명하다는 뜻은 아니다. TTS 원고는 사용자가 제공한 것이므로, 오타를 발견하면 사용자에게 수정을 요청하며, 임의로 고쳐 다시 합성하지 않는다. 긴 영상은 `long-form.md`에 따라 챕터별로 자료를 제공하고 각 챕터의 이음새를 복기한다. 전편 개요는 챕터별 검토를 대신할 수 없다.

`qa`는 검토 자료도 함께 만든다. `-sheet.png`(24칸 프레임), `-phone.png`(피드 크기), 정지 구간, 컷 지점, 오디오 파형과 스펙트럼이다. `timeline.js`의 `HOLDS`에 선언된 정지 구간은 「intended hold」(의도된 정지)로 표시된다. 나머지는 빈 박자인지 판단해야 한다. 의도된 것이면 `HOLDS`에 추가하고, 아니라면 고친다. `DROPS`를 쓴 경우 오디오 부분에는 각 강박 앞의 숨 쉬는 움푹 들어감도 표시된다. 빠른 동작, 전환, 기억 지점은 `inspect.mjs strip --at <초>`로 연속 프레임을 확인한다.

판정(PASS / FAIL)은 아니지만 검토에 참고할 두 가지 단서가 있다. 스스로 결론을 내리면 된다.

- **샷별 모션**(`qa`와 `inspect.mjs motion`이 모두 출력하며, `timeline.js`에 `SHOTS`가 있으면 샷별로, 없으면 하드 컷 기준으로 나눈다): 각 샷에서 프레임 단계마다 얼마나 많은 화면이 바뀌는지(moving), 얼마나 많은 단계가 완전히 같은지(still), 갑작스러운 점프가 몇 번 있는지(jumps)를 보여 준다. 다음 세 가지 신호에 주목한다. 「nothing moves」(`HOLDS`에 없는데 오래 움직이지 않음), 「sudden jumps」(화면 전체의 노이즈가 몇 프레임마다 다시 생성되어 번쩍이는 것으로 읽히거나, 한 프레임이 깨짐), 「every other step is still」(스텝 애니메이션이거나, 카메라까지 스텝으로 움직임). 또한 별도로 **flash frames**를 나열한다. 어떤 프레임이 앞뒤 두 프레임과 모두 다르지만 앞뒤 두 프레임끼리는 같다면, 한 프레임 흰색 번쩍임, 빈 화면, 레이어 누락일 가능성이 크다. 의도된 단일 프레임 스트로브가 아니라면 고친다. 연속된 화면 전체의 큰 변화는 **rapid whole-frame changes**로 따로 나열된다. 빠른 몽타주는 의도된 것이다. 하지만 획, 노이즈, 질감이 몇 프레임마다 화면 전체에서 다시 생성되면 깜빡이는 것처럼 보인다.
- **텍스트 프레이밍**(`render.mjs --text-check`, `build.sh`가 기본으로 실행하며, 결과는 `qa/text.json`과 `qa/text-t<초>.png`에 저장됨): 글자가 화면 가장자리에서 잘림(CUT. 전시용 큰 글자의 번짐인 BLEED는 대부분 의도된 것), 서로 다른 두 글자 묶음이 겹침(OVERLAP), 세로 영상의 글자가 플랫폼 UI가 가리는 위아래 안전 영역에 들어감(SAFE), 휴대폰에서 읽기 어려울 만큼 작음(TINY). 0.3초 이상 지속될 때만 보고하며, 시점마다 박스를 표시한 이미지를 낸다. Canvas 2D와 DOM / SVG의 글자는 확인할 수 있지만, WebGL 텍스처와 이미지 속 글자는 볼 수 없으므로 그 프레임은 직접 봐야 한다.

텍스트 프레이밍 검사는 원래 페이지를 읽으며, 서브프레임 평균 후의 픽셀은 검증하지 않는다. 모션 블러를 쓰면서 문구나 샷이 하드 컷으로 바뀐다면, 내보낸 뒤 `inspect.mjs strip --at <전환 초>`로 완성본의 연속 프레임을 확인하고, 한 프레임만 보이는 겹쳐 찍힘이 있는지 살핀다. 문구 상태와 연속 모션 시간을 구분해야 하면 `stack.md`의 선택적 샘플링 컨텍스트를 연결할 수 있다. 의도된 크로스페이드는 유지한다.

각 항목은 관찰 내용을 적는다. **해당하지 않는 항목은 「不适用」(해당 없음)이라고 쓴다.**

| 항목 | 무엇을 보나 | 언제 해당하지 않나 |
|---|---|---|
| 오프닝 | 첫 1초에 사람의 시선을 잡는 것이 있는가 | — |
| 리듬과 밀도 | 변화 밀도가 용도와 스타일에 맞는가. 의도하지 않은 빈 박자가 있는가. 숨 쉴 틈이 있는가 | — |
| 모션 질감 | 스타일의 모션 규칙(스프링 / snap / 스텝 / 주기 운동)에 맞는가. 빠른 동작이 끊기지 않는가 | — |
| 내용 변화와 샷 이어짐 | 핵심 논점이 대상이나 관계의 변화로 드러나는가. 문장마다 페이지를 넘기지 않는가. 샷 간 주체, 방향, 속도가 의도치 않게 초기화되지 않는가. 연속 샘플을 실제로 봤는가 | 순수 레이아웃, 로고, 또는 정지가 디자인 의도인 경우 용도에 따라 판단 |
| 구도와 가독성 | 주체의 크기, 여백. 휴대폰 크기에서 글자가 읽히는가, 머무는 시간이 충분한가. `--text-check`가 표시한 모든 항목 | — |
| 내용과 수치의 기준 | 화면은 완벽한데 내용이 틀린 경우: 숫자, 단위, 이름이 사용자가 준 것과 일치하는가? 배수 표현은 맞는가(「9배 올랐다」와 「원래의 9배로 올랐다」는 다르다)? 차트의 숫자로 화면의 결론을 계산할 수 있는가? 막대가 0에서 시작하는가, 세로축을 자른 경우 그 사실을 적었는가? 예시 데이터에 「예시」라고 표시했는가? 펼침이나 장면 전환 뒤에 카운트가 0부터 다시 시작하지 않는가 | 사실, 데이터, 차트가 없는 영상 |
| 기억 지점 | 분명한 기억 지점이 있는가, 깔끔하게 구현되었는가 | 용도상 필요 없는 경우(예: 순수 루프 배경) |
| 스타일 일관성 | 선택한 스타일(또는 각색, 혼합, 직접 정의한 규칙)을 처음부터 끝까지 지켰는가. 금지 목록에 빠지지 않았는가. 혼합일 때 관통하는 선이 분명한가 | — |
| 클리셰에 빠졌나 | 스타일 파일의 「가장 흔한 버전」과 대조한다. 화면과 소리가 거의 그 버전을 따랐는가? brief에서 고른 신호가 실제로 화면에 나타났는가? 주제를 바꿔도 이 영상의 화면을 그대로 적용할 수 있는가? 적용된다면 주제에서 출발하지 않은 것이다 | 사용자가 클래식 버전을 명시적으로 원하는 경우 |
| 음과 화면의 관계 | 타격, 컷 지점, 효과음이 맞는가. 드롭 전의 여백이 있는가 | **무음 작품** |
| 완성도 | 깜빡임, 누락, 텍스트 겹침, 마무리 | — |

`qa/review_log.md`에 기록한다.

```markdown
## 第 N 轮
技术检查：全部 PASS（或列出 FAIL 项）
审片观察：
- 开场：…  - 节奏与密度：…  - 音画关系：不适用（无声）
最严重的 3 个问题：
1. [4.2–5.0s] 卡片形变是匀速的，和「极简界面」的弹簧规则不符 → 改用 springTo { freq: 2.4, damp: 0.75 }
2. …
重渲范围：2.0–9.0s
仍未解决（交付时告诉用户）：…
```

내보내기 전에 수정할 때는 워크스페이스를 새로 고쳐 관련 구간을 다시 보게 하고, 사용자가 확인한 뒤 MP4를 합성한다. 검토할 때마다 영상을 먼저 생성하지 않는다. 이미 내보낸 완성본에 문제가 발견되면, 먼저 고치고 워크스페이스에서 다시 확인한다. 오프라인 클립이 꼭 필요하면 사용자의 동의를 받아 필요한 범위만 다시 렌더링하고(`render.mjs --start --duration --out out/seg.mp4`), 현재 버전이 확정된 뒤에 전편을 다시 만들고 기술 검사를 다시 한다. 보통 두세 라운드가 걸리며, 목표는 문제를 해결하는 것이지 점수를 맞추는 것이 아니다. 같은 종류의 문제가 세 라운드 연속 해결되지 않고, 두 가지 수정 방법 모두 효과가 없다면, 그 구간을 더 붙잡고 있지 말고 brief로 돌아가 방법을 바꾼다(기술, 샷, 구조를 바꾸거나), 아니면 사용자에게 사실대로 알린다.

### 독립 검토(호스트가 하위 에이전트를 지원할 때)

제작한 사람이 세 번을 봐도 보이지 않는 문제를, 제작에 참여하지 않은 사람은 첫눈에 알아채는 경우가 많다. 동작이 몇 번 반복되는지, 두 요소가 겹쳐 이상한 무언가가 되었는지, 글자가 다른 단어로 읽히는지 같은 것이다. 호스트가 하위 에이전트를 띄울 수 있다면, 전달 전에 검토 전용 에이전트를 하나 보내서 검토 자료만 보게 한다.

- **넘겨줄 것**: `qa/` 안의 프레임 시트, 휴대폰 크기 이미지, 핵심 지점의 `strip` 연속 프레임, `--text-check`의 표시 이미지, 오디오 파형과 스펙트럼. 그리고 brief의 「관객이 기억할 한 문장」과 금지 목록. **넘기지 않을 것**: 코드, 제작 과정, 자신의 검토 기록. 그래야 그 에이전트가 당신의 생각을 따라가지 않는다.
- **돌려받을 것**: 심각도 순서로 정렬된 문제 목록. 각 항목에는 타임코드, 본 내용, 추측한 원인이 있어야 한다. 그리고 가장 확신이 없는 세 가지.
- **사용법**: 그 결과는 자신의 검토와 구분해서 `review_log.md`에 기록한다. 수정한 뒤 같은 에이전트가 한 번 더 보게 해서, 「예전 문제가 고쳐졌는지」와 「새로 발견된 문제」를 구분한다. 「기억 지점이 없다」, 「농담이 없다」처럼 무언가를 추가하라는 제안이라면, 그 항목은 사용자에게 판단을 넘긴다. 영상에 무언가를 더하려면 먼저 사용자에게 묻는다.
- 호스트에 하위 에이전트가 없으면 이 단계는 건너뛰며, 검토표는 그대로 직접 작성한다. 이 단계가 있든 없든, 사용자가 직접 영상을 보는 것을 대신할 수는 없다.

## 3. 자주 생기는 문제와 해결법

| 증상 | 원인 | 해결법 |
|---|---|---|
| 연속된 정지 카드, 슬라이드처럼 보임 | 나레이션 문장마다 페이지 하나를 만들고, 문구 교체, 페이드인, 장식 모션만 있음 | 의미 기반 분기를 다시 짜고, 대상의 상태 변화와 샷 간 이어짐을 명확히 한다. 먼저 연속 샘플을 보고, 그다음 모션 질감을 조정한다 |
| 빠른 움직임이 끊기고, 이음새에서 갑자기 멈춤 | 스텝이 카메라에 적용됨, 궤적이 문장마다 다시 시작됨, 속도가 연속되지 않음, 모션 샘플링이 부족함 | 스타일에 필요한 스텝은 남기되 카메라는 연속으로 유지한다. 동작 시간을 통일하고, 이음새의 속도를 맞추고, 필요하면 잔상이나 서브프레임을 추가한다 |
| 화면 전체가 번쩍임(motion이 sudden jumps 또는 rapid whole-frame changes를 보고함) | 획, 노이즈, 질감이 몇 프레임마다 화면 전체의 시드를 바꿈 | 획과 입자의 위치는 고정하고, 방향과 밝기 같은 매개변수가 t에 따라 연속적으로 변하게 한다. 손그림 떨림은 선화와 작은 영역에만 적용한다. 필름 그레인은 `--grain`에 맡긴다 |
| 한 프레임이 번쩍임(flash frames) | 한 프레임에 레이어가 빠졌거나, 빈 화면이 그려졌거나, 시간 창이 한 프레임 폭밖에 안 됨 | `inspect.mjs frames <video> <초>`로 그 프레임을 확인한다. 그 시점 앞뒤의 `seg()` 창과 레이어 순서를 점검한다 |
| 타격음이 화면보다 먼저 들림 | 전환이 강박에서 시작되는데 새 화면은 몇 프레임 뒤에 드러남. 카메라 충격을 새 레이어에만 줌 | `revealOn(hit, dur, reveal)`로 전환 시작점을 거꾸로 계산한다. 충격은 무대 전체에 준다(recipes.md 14절) |
| 시그니처 전환이 평범한 와이프로 보임 | 길이가 너무 짧아 ease-in/out의 양 끝에서는 변화가 보이지 않음 | 복잡한 전환에는 0.45~0.6초를 주고, `strip --at`으로 중간 부분이 읽히는지 확인한다 |
| 시대 / 매체가 바뀔 때 주인공의 자세가 튐 | 각 구간이 구간 내 시간으로 동작을 다시 재생함 | 관통하는 요소의 동작은 전체 시간을 기준으로 계산한다(mixed-media-era.md) |
| 글자가 흐림 | `will-change` 사용; 캔버스가 DPR에 맞게 설정되지 않음; 소재 해상도가 낮음 | `will-change`를 제거한다; `setupCanvas`를 쓴다; 2배 소재를 쓴다; `--dpr 2` |
| 새 글자와 옛 글자가 겹침 | 컨테이너 안의 내용에 별도의 진입과 퇴장이 없음 | 옛 내용은 먼저 흐려지며 사라지고, 새 내용은 나중에 들어온다 |
| 큰 글자가 깨진 글자나 겹친 글자처럼 보임 | 같은 색의 복잡한 내용(입체 측면, 파티클, 배열) 위에 글자가 올라감. 폰트나 코드의 문제가 아님 | 먼저 내용 레이어를 끄고 한 프레임을 렌더링해 글자 자체에 문제가 없는지 확인한다. 그다음 글자 주변에 금지 영역을 지정하고, 프레이밍 중심이나 주체의 윤곽으로 피하게 한다(stack.md 4절) |
| 처음 몇 프레임의 폰트가 틀림 | READY를 너무 일찍 설정함 | `await loadFonts()` 뒤에 READY를 설정한다 |
| 글자가 갑자기 사라짐 | 애니메이션 매개변수가 NaN을 냄(예: 빈 시간 창이나 무한한 시간 창) | `seg()`를 쓴다(NaN을 만들지 않음). 퇴장 시간에는 `Infinity` 대신 `null`을 쓴다 |
| WebGL 레이어가 완전히 검음 | 셰이더 컴파일 실패; `preserveDrawingBuffer`를 켜지 않음 | 컴파일 실패 시 예외를 던진다. 먼저 한 프레임을 렌더링해 확인한다 |
| 다시 렌더링한 구간이 맞지 않음 | 상태, 난수, 타이머 | `--determinism`으로 위치를 찾는다 |
| 「AI스럽게」 보임 | 어두운 배경 + 가운데 큰 글자 + 그라데이션 + 글로우 + 동시 페이드인 | 스타일 파일(`styles/<slug>.md`)의 규칙과 brief의 금지 목록으로 돌아간다 |
| 너무 시끄럽고 피곤함 | 층위가 없고, 숨 쉴 틈이 없음 | 미세한 변화를 줄이고, 드롭 전에 여백을 둔다 |
| 마무리가 갑자기 끊김 | 마무리 정지가 없음; 음악이 마디 중간에서 잘림 | 마무리 정지를 1.5초 이상 두거나, 끊김 없는 루프로 만든다. 길이는 마디 단위로 맞춘다 |
| 소리가 울리거나 답답함 | 저음이 너무 많음 | sound.md 9절을 본다 |

## 4. 전달 체크리스트

- [ ] 요구사항과 스타일 확인이 기록되었거나, 사용자가 명시적으로 면제했다. 필수 정보가 명확하고, 확정된 길이가 1200초를 넘지 않는다
- [ ] 기본적으로 워크스페이스를 열어 현재 버전의 미리보기와 내보내기 확인을 기록했다. 긴 영상은 챕터별로 미리봤거나, 사용자가 미리보기를 건너뛰라고 명시적으로 요청했다
- [ ] TTS는 사용자 원고를 쓴다. 나레이션이 있으면 실제 오디오, 문장 타임스탬프, 화면이 일치하며, 길이 불일치는 확인되었다
- [ ] BGM과 효과음의 출처가 각각 요구사항과 일치하며, 음성 구간에서 음악과 효과음이 비켜 준다. 계측 통과를 청감 통과로 취급하지 않는다
- [ ] 긴 영상은 챕터 목록, 부분 소스, 오디오를 재빌드할 수 있고, 각 챕터 검사와 이음새 복기가 기록되어 있다
- [ ] 서사나 설명 영상은 대표 연속 샘플을 봤다. 내용에 이해 가능한 상태 변화가 있고, 샷 이어짐이 자연스러우며, 글자 전환이나 장식 모션으로 설명을 대신하지 않았다

- [ ] `inspect.mjs qa` 기술 검사가 모두 PASS이고 NOT CHECKED가 없다(매개변수와 brief의 사양이 일치한다. `sh build.sh`를 쓰면 가장 간단하다)
- [ ] `--determinism`을 통과했다
- [ ] 사실, 숫자, 이름이 사용자가 제공한 것과 일치한다. 확실하지 않은 것은 따로 나열했다
- [ ] 글자는 휴대폰 크기에서 읽을 수 있으며, 넘치거나 겹치지 않는다(`qa/text.json`의 모든 항목을 확인했고, 의도된 출혈과 작은 주석은 검토 기록에 적었다)
- [ ] 샷별 모션과 flash frames를 모두 확인했다. `HOLDS`에 없는 빈 박자가 없고, 의도하지 않은 번쩍임이 없다
- [ ] 소재와 폰트의 사용 권한을 목록으로 정리했다
- [ ] `qa/review_log.md`에 검토 관찰, 수정 내용, 남은 문제를 기록했다
- [ ] `brief.md`, `build.sh`, 실제 내보낸 MP4(`out/editor-<task-id>.mp4` 또는 `out/final.mp4`), `out/poster.png`이 모두 프로젝트 디렉터리에 있다. 편집본은 해당 세션과 작업 기록을 함께 첨부했다
- [ ] 전달 설명에서 사용자에게 완성본을 직접 한 번 보라고 안내했다(소리가 있는 영상은 소리를 켜고 보라고 안내)
