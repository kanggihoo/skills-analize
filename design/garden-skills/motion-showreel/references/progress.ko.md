# 필요할 때 제작 진행 보여 주기

요구사항 문답에서 사용자가 「想看制作过程」(제작 과정을 보고 싶다), 「边做边看」(만들면서 보기), 「实时看进度」(실시간 진행 보기), 「每个阶段给我看看」(단계마다 보여 달라) 같은 말을 하는지 살핀다. 의도가 분명하면 바로 켜고, 같은 질문을 반복하지 않는다. 표현하지 않았다면 기본 최종 워크스페이스 미리보기를 유지하며, 필수 질문을 하나 더 늘리지 않는다. 요구사항 요약과 brief에는 사용자의 원래 말, 활성화 여부, 진행 페이지 링크를 기록한다. 사용자가 중간에 요청해도 켤 수 있으며, 이미 있는 결과물은 바로 발행할 수 있다.

이것은 같은 제작 흐름을 보여 주는 입구일 뿐이다. 원래의 요구사항 확인, 스타일 확인, 실제 나레이션 타임라인, 샷별 자체 점검, 최종 내보내기 확인, 완성본 검수는 그대로 진행한다. 진행 업데이트마다 사용자가 답할 필요는 없다. 진행을 보여 주려고 화질을 낮추거나, 샷을 단순화하거나, 원고를 고치거나, 추정한 나레이션을 쓰거나, 유료 TTS를 추가로 호출해서는 안 된다. 기존 결과물을 업데이트하면 된다.

## 안정적인 입구를 일찍 열기

사용자가 요청하면, 합의한 프로젝트 디렉터리에서 다음을 실행한다.

```sh
node <skill>/scripts/editor.mjs <project> --progress
```

출력된 로컬 주소를 능동적으로 연다. 진행 페이지와 편집 워크스페이스는 하나를 공유하며, 상단의 「制作进度」(제작 진행)를 누르면 단계 서랍이 열리고, 상단 바와 화면 컨트롤은 한 벌만 유지한다. 처음에는 빈 디렉터리여도 된다. 아직 `index.html`, 오디오, 제작 사양이 없어도 괜찮으며, 이때는 요구사항 단계와 설명을 보여 준다. 자리 표시용 샘플을 만들지 않고, 길이와 프레임레이트를 임의로 정하지 않는다. 요구사항을 확인한 뒤에는 같은 디렉터리를 정상적으로 scaffold한다. 서버는 계속 켜 두며, 이 링크를 프로젝트의 항상 같은 입구로 쓴다. 재생 가능한 버전이 준비되면 그 버전의 전체 워크스페이스가 자동으로 열리고, 브라우저 주소가 버전 주소로 바뀌므로 사용자가 링크를 다시 찾을 필요가 없다.

## 제작 중 업데이트

단계 ID는 다음과 같다. `brief` 요구사항과 스크립트, `style` 스타일과 화면, `narration` 나레이션 샘플, `scenes` 샷 제작, `audio` 음악과 효과음, `review` 최종 미리보기. 상태는 `pending`, `running`, `ready`, `failed`, `skipped`, `waiting`(사용자 피드백 대기) 중 하나이며, 나레이션이 없거나 무음인 등 필요 없는 단계는 명확히 `skipped`로 표시한다.

```sh
node <skill>/scripts/progress.mjs <project> --stage brief --status running --message "正在确认内容、画幅与声音方案"
node <skill>/scripts/progress.mjs <project> --stage scenes --status running --done 2 --total 8 --message "两个镜头已完成自查，继续制作第三个"
node <skill>/scripts/progress.mjs <project> --stage narration --status skipped --message "本片不需要口播"
```

새 카운트를 주지 않으면 기존 완료 수를 유지한다. 일부 샷만 발행한 경우에는 여전히 제작 중으로 간주되며, 단계 전체가 끝났을 때만 `--status ready`를 설정한다. 개수에는 실제로 완료된 수만 넣고, 타이머로 퍼센트를 지어내지 않는다. 단계 하위 작업이 끝날 때 카운트를 갱신하며, 코드를 한 줄 쓸 때마다 갱신하지 않는다. 새 단계를 시작할 때, 미리볼 수 있는 결과물이 생겼을 때, 사용자가 처리해야 할 문제가 생겼을 때 설명을 갱신한다. 진행 중에는 회전 아이콘이 표시되며, 상단 바에는 현재 단계와 완료 수가 남는다. 애니메이션은 작업이 아직 끝나지 않았음만 나타내며, 완료 비율을 흉내 내지 않는다. 확인을 기다릴 때는 `waiting`을 쓰고, 계산 중인 것처럼 보이도록 회전을 유지하지 않는다.

### 확인을 받으면 먼저 대기를 풀기

진행 페이지는 제작 측이 발행한 상태만 읽으며, 대화를 직접 읽을 수 없다. **사용자가 확인한 뒤 첫 번째 작업은 상태 동기화여야 한다.** 그다음에 자료를 조사하거나, 폰트를 내려받거나, 프로젝트를 세우거나, 샷을 만든다. 다음 결과물이 끝날 때까지 기다렸다가 갱신하지 않는다. 요구사항 확인 후에는 보통 스크립트가 아직 완성되지 않았으므로, 먼저 현재 단계의 제작 상태를 되돌리고, 확인을 스크립트 완료로 취급하지 않는다.

```sh
node <skill>/scripts/progress.mjs <project> --stage brief --confirm --message "需求已确认，正在整理脚本与分镜"
```

현재 단계의 결과물이 실제로 완료되었고 다음 단계로 넘어갈 때는, 두 가지 상태를 한 번에 기록할 수 있다.

```sh
node <skill>/scripts/progress.mjs <project> --stage style --confirm --next scenes --message "风格已确认，正在制作第一镜"
```

`--confirm`은 실제 사용자 피드백에 근거해서만 호출한다. 여러 번 실행해도 진행이 뒤로 가지 않는다. 이미 확인받은 단계에 다시 피드백을 요청할 때는 `--status waiting --reopen`을 써서 새 라운드를 명확히 연다. 예를 들어 수정한 스타일 이미지나 최종 미리보기가 여기에 해당한다. 이미 받은 확인을 예전의 대기 메시지로 덮어쓰면 안 된다. 앞선 단계의 완료 결과물을 뒤늦게 발행해도 현재 단계를 빼앗지 않는다. `--confirm`은 제작 상태만 동기화하며, MP4를 생성하지 않고, 이후의 확인과 검수를 면제하지도 않는다.

대기 중에 프로젝트 원본 파일이 바뀌었다는 것이 감지되면 페이지는 상태가 동기화되지 않았을 수 있다고 알린다. 제작 중이거나 대기가 3분을 넘었는데 업데이트가 없으면 미보고 안내도 뜬다. 이런 알림은 자동으로 승인하거나, 단계를 넘기거나, 파일을 발행하지 않는다. 알림이 뜨면 대화와 실제 작업을 대조하고, 실제 상태를 보고한다. 타임스탬프를 정기적으로 새로 고쳐서 누락을 가리지 않는다.

스타일 프레임과 음색 짧은 샘플은 기존 흐름의 산출물을 그대로 쓰며, 자체 점검 후 발행한다.

```sh
node <skill>/scripts/progress.mjs <project> --stage brief --preview brief.md --name "需求与分镜" --status ready
node <skill>/scripts/progress.mjs <project> --stage style --preview qa/directions.png --name "风格方向" --status waiting --message "三个风格方向，等待你选择"
node <skill>/scripts/progress.mjs <project> --stage narration --preview audio/voice-sample.wav --message "使用你提供的原稿生成的音色短样"
```

프로젝트 안의 이미지, 오디오, `.md/.txt/.json` 문서만 받는다. 독립된 결과물로 복사되므로, 원본을 나중에 수정해도 보고 있는 샘플은 깨지지 않는다. 요구사항, 스타일, 소리 등의 단계에는 해당 결과물 버튼이 남는다. 샷 제작 단계에서는 상태, 완료 수, 진행 막대만 보여 주며, 오른쪽 위에 모든 샷을 나열하지 않는다. 샷과 전체 버전은 화면 미리보기 툴바의 선택기에서 전환한다. 단계가 준비되었다고 해서 사용자가 승인한 것은 아니다. 요구사항/스크립트 단계는 실제 텍스트 진행을 보여 주고, 화면이나 오디오가 생긴 뒤에야 해당 결과물을 보여 준다.

## 샷 하나를 끝낼 때마다 하나씩 발행하기

이것은 사후에 진행을 채우는 것이 아니라 제작 방식이다. 첫 샷을 만들기 전에 총 개수를 정하고 `0/N running`으로 갱신한다. 첫 샷을 완성하고 자체 점검을 마치면 바로 발행해서, 사용자가 먼저 보고 나서 둘째 샷을 계속 만들게 한다. 긴 영상은 기존의 챕터/샷 모듈과 소재 캐시를 우선 재사용하고, 완성된 샷을 독립된 재생 가능 디렉터리로 묶는다. 그 디렉터리는 자체 `index.html`, `DUR`, 실제 의존성을 가지며, 렌더링은 같은 샷 구현을 쓴다. 저화질 프록시나 근사 애니메이션을 따로 만들지 않는다. 전편이 아직 없어도 첫 샷은 발행할 수 있으며, 아직 만들지 않은 다른 샷은 확인하지 않는다.

```sh
node <skill>/scripts/progress.mjs <project> --stage scenes --status running --done 0 --total 8 --message "正在做第一镜"
node <skill>/scripts/progress.mjs <project> --stage scenes --shot s01 --total 8 --name "镜头1：种子落下" --publish shots/s01 --size 1920x1080 --fps 30 --message "第一镜已自查并可播放，继续制作第二镜"
node <skill>/scripts/progress.mjs <project> --stage scenes --shot s02 --total 8 --name "镜头2：叶片展开" --publish shots/s02 --size 1920x1080 --fps 30
```

`--shot`은 scenes 단계에서만 쓰며, 안정적인 ID와 `--total`이 있어야 한다. 검사를 통과해야 결과물 목록에 추가되고 완료 수가 자동으로 갱신된다. 같은 ID로 수정하면 기존 결과물을 대체하며, 이중으로 세지 않는다. 실패하면 이전 결과물과 원래 개수를 유지한다. 독립 미리보기에는 해당 샷의 디렉터리를 복사하고 검사하기만 하면 된다. 전편을 먼저 만들 필요는 없고, MP4를 인코딩하지도 않는다. 사용자는 화면 영역의 샷 선택기에서 완료된 샷이나 전체 미리보기 중 아무거나 전환할 수 있다. 사용자가 이전 샷을 직접 돌아보고 있으면 자동 전환을 멈추며, 방금 본 버전으로 되돌리지 않는다. 최종 합성은 원래의 타임라인, 소리, 검수 흐름을 그대로 쓰며, 이 미리보기를 자동으로 이어 붙여 완성본으로 만들지 않는다.

단일 페이지로 된 예전 프로젝트도 단계 전체를 완성한 뒤 결과로 발행할 수 있다. 다만 이 방식을 위해 샷 전체가 끝날 때까지 기다려서 보여 주지 않는다. 같은 원칙을 긴 영상에도 적용한다. 전편이 끝날 때까지 기다리지 말고, 첫 샷이나 첫 챕터를 먼저 준다.

## 재생 가능한 단계 버전 발행하기

독립적으로 검사할 수 있는 샷이나 단계를 완성하면, **먼저 원래 흐름대로 자체 점검**을 하고 재생 가능한 프로젝트를 발행한다. 사양은 사용자가 이미 확인한 값을 쓴다.

```sh
node <skill>/scripts/progress.mjs <project> --stage scenes --publish . --size 1920x1080 --fps 30 --message "当前已完成的镜头；尚未加入最终配乐"
```

`--publish .`은 현재 프로젝트를 독립 버전으로 복사하고, 소재, 폰트, 오디오, 실행 의존성을 함께 가져간다. 복사본에서 원래의 결정성 검사를 돌린 뒤 발행한다. MP4는 인코딩하지 않는다. `<project>` 안에 있는 다른 완전한 프로젝트 디렉터리(`index.html`이 있어야 함)도 발행할 수 있다. 예를 들어 챕터나 독립된 동작 예고편이 여기에 해당한다. 아직 끝나지 않은 부분은 설명에 명확히 적고, starter를 완성된 샷처럼 내세우지 않는다. 믹스가 아직 없다면 소리 없이 예고편으로 보여 줄 수 있으며, 이것을 나레이션 정렬이 끝났다고 주장하지 않는다.

진행 페이지는 상태를 1초마다 읽는다. 새 버전이 발행 검사를 통과하면 완전한 워크스페이스에서 열리고, 원래 장면, 폰트, 실제 미리듣기를 로드한다. 발행이 실패하면 이전 버전을 유지한다. 작성 중인 코드는 사용자 페이지에 직접 핫 리로드되지 않는다. 사용자는 「自动切换阶段版本」(단계 버전 자동 전환)을 끌 수 있으며, 원하는 시점에 직접 전환한다. 단계 버전은 읽기 전용이며, 재생, 드래그, 프레임 단위 확인은 가능하지만 소리 편집과 내보내기는 열지 않는다.

오디오가 끝나면 같은 방식으로 `--stage audio`를 발행해서, 사용자가 화면과 현재 실제 믹스를 함께 확인할 수 있게 한다. 진행 페이지를 위해 따로 근사 음악을 만들거나, 자리 표시용 나레이션을 넣거나, 화면 복잡도를 낮추지 않는다. 복사와 검사에는 약간의 비용이 들기 때문에, 의미 있는 결과물 단위로 발행하며 키 입력마다 발행하지 않는다. 버전과 상태는 `.showreel-progress/`에 저장하며, 원래 제작 파일은 바꾸지 않는다. 의존성 규모가 크면 전체보다는 챕터 단위로 발행해 기존 챕터 캐시를 유지한다.

## 최종 미리보기와 내보내기

정상적인 화면과 오디오 자체 점검을 마친 뒤 최종 미리보기를 발행한다.

```sh
node <skill>/scripts/progress.mjs <project> --stage review --publish . --size 1920x1080 --fps 30 --final --status waiting --message "最终画面与混音已准备好，请预览后确认导出"
```

최종 버전을 발행할 때 brief에 `--subframes`, `--shutter`, `--dpr`, `--grain`, `--crf`, `--workers`가 있다면, 같은 옵션을 이 명령에 함께 붙인다. 원본 믹스를 명시해야 한다면 `--audio audio/final.wav`를 넘긴다. 진행 페이지를 일찍 열었다는 이유로, 아직 확인되지 않은 기본 내보내기 품질을 그대로 쓰면 안 된다.

`review --final`만 독립 소리 편집과 내보내기를 연다. 최종 버전으로 들어가면 버전 전환은 자동으로 닫히며, 사용자의 믹싱과 진행 중인 내보내기를 보호한다. 새 버전이 준비되면 미리보기 툴바에 「查看新版本」(새 버전 보기)이 나타나고, 사용자가 직접 전환한다. 현재 작업이 아직 끝나지 않았거나 편집이 저장되지 않았다면 전환을 미룬다. 사용자가 「导出视频」를 클릭하면 내보내기를 확인한 것이며, 원래 장면 렌더링, 소리, 기술 검수는 [`editor.md`](editor.md)를 따른다. 제작 진행을 본 것만으로는 최종 내보내기를 확인한 것이 아니다.

최종 버전은 `.showreel-progress/revisions/<버전>/project/`에서 실행된다. 편집 저장, 내보낸 파일, 검수 자료, receipt는 모두 그 버전 안에 있다. 전달할 때는 실제 출력 경로와 그 버전의 소스 및 편집 기록을 알려 주며, 루트의 예전 `out/final.mp4`를 가리키면 안 된다. 사용자가 대화에서 승인하면, 같은 최종 버전을 내보낸다. 소리 편집이 있다면 그 버전의 워크스페이스에서 내보내며 `.showreel-editor/session.json`을 유지한다. 소리를 편집하지 않았다면 같은 버전을 원래 빌드 흐름으로 내보낼 수 있다. 미리보기하지 않은 작업 파일을 승인된 버전으로 취급하면 안 된다.

긴 영상의 진행 페이지는 챕터별로 보여 주며, 챕터 이름과 전체에서의 위치를 명시한다. 현재 워크스페이스는 여전히 단일 페이지 타임라인이다. 챕터 하나를 `--final`로 전편인 척 내보내지 않는다. 각 챕터의 미리보기를 끝내고 전편 내보내기 확인을 받은 뒤, [`long-form.md`](long-form.md)에 따라 `build-long.mjs`로 전편을 합성하며, 챕터별 캐시와 교차 챕터 검수를 유지한다. 사용자가 특정 챕터만 따로 내보내기를 원하면, 그때 별도의 독립 납품으로 명시해서 처리한다.

미리보기는 원래의 결정성 검사, 음화 정렬 자체 점검, 완성본 기술 검수, 사람의 최종 검토를 대신하지 않는다. 실시간 재생은 프레임이 떨어질 수 있으며, 내보내기 중의 서브프레임 블렌딩, DPR 슈퍼샘플링, 후반 그레인은 [`editor.md`](editor.md)의 미리보기 제한을 따른다.
