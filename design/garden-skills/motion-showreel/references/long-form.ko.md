# 긴 영상: 챕터, 빌드, 검수

2분을 넘고 최대 20분에 이르는 영상에 적용한다. 긴 영상도 짧은 영상과 마찬가지로 기본적으로 먼저 편집 워크스페이스에서 미리보고, 사용자가 확인한 뒤에만 MP4를 렌더링한다. 짧은 영상은 단일 페이지를 쓰며, 긴 영상은 기존의 챕터 빌드, 캐시, 검수 방식을 유지한다.

## 콘텐츠를 먼저 기획하고, 그다음 챕터를 나눈다

요구사항 확인 단계에서 총 길이와 오차 허용 여부를 명확히 한다. 나레이션의 실제 길이가 목표와 맞지 않으면 먼저 확인한다. 1200초를 넘는 경우에도 자동으로 잘라내지 않는다. TTS는 반드시 사용자 원고를 사용한다. 나레이션이 없어도 박자 기반으로 제작할 수 있으며, 기존 스타일과 합성 엔진을 모두 그대로 쓸 수 있다.

brief에는 챕터의 목적, 길이, 이어짐, 전체를 관통하는 요소를 명확히 쓴다. 긴 영상은 여러 개의 중심점을 가질 수 있으며, 짧은 영상의 빠른 변화 밀도를 20분 내내 유지할 필요는 없다. 서체, 색, 도형의 의미는 일관되게 유지하고, 변화는 서사에 봉사해야 한다. 스타일 프레임은 기본 흐름을 따른다. 스타일이 정해졌다면 세 장을, 정해지지 않았다면 세 가지 방향을 제시한다. 확정 후에는 각 챕터의 대표 프레임을 추가로 자체 점검할 수 있다. 제작이 끝나면 워크스페이스에서 따로 미리보고, 현재 내용을 내보내도 되는지 확인한다.

내용의 경계에 따라 챕터를 나누며, 보통 빌드 단위 하나는 30~90초로 한다. 이것은 렌더링과 오디오 메모리를 관리하기 위한 권장치이지 서사의 규칙이 아니다. 챕터마다 독립된 프로젝트 디렉터리와 로컬 타임라인을 두고, `render(0)`에서 시작한다. 전체 영상 시간 = 앞 챕터들의 길이 합 + 챕터 내 시간이다. 공유하는 디자인 토큰, 소재, 빌드 의존성은 각 챕터의 `inputs`에 포함해서 외부 변화가 캐시에서 빠지지 않게 한다.

빌드 단위는 시각적 단락과 같지 않다. 챕터 안에서 `render(0)`이라고 해서 주체, 위치, 움직임을 초기화해서는 안 된다. 여러 조각이 같은 동작을 이어 갈 때는 공통 전체 시간이나 궤적, 또는 명시적인 연결 자세를 쓴다. 서사 단락 전환에서는 의도된 하드 컷을 허용하지만, 기술적인 분할 때문에 무작위 멈춤이나 공간 점프가 생겨서는 안 된다. 나레이션 문장마다 샷을 바꿀 필요는 없다.

## 재빌드 가능한 챕터 목록

프로젝트 루트에 `chapters.json`을 쓴다. 모든 경로는 이 파일 기준 상대 경로이다. 시간 단위는 초이며, 챕터는 배열 순서대로 이어 붙인다.

```json
{
  "version": 1,
  "duration": 180,
  "size": "1920x1080",
  "fps": 30,
  "chapters": [
    { "id": "intro", "project": "chapters/intro", "start": 0, "duration": 60, "audio": "chapters/intro/audio/final.wav" },
    { "id": "explain", "project": "chapters/explain", "start": 0, "duration": 60, "audio": "chapters/explain/audio/final.wav" },
    { "id": "end", "project": "chapters/end", "start": 0, "duration": 60, "audio": "chapters/end/audio/final.wav" }
  ],
  "render": { "workers": 3 }
}
```

`start`는 원본 페이지 안에서 챕터가 프레임을 가져오는 시작점이며, 최종 영상에서의 시작 시간이 아니다. 여러 챕터가 같은 페이지를 참조하면서 서로 다른 `start`를 쓸 수도 있지만, 공유 소스가 바뀌면 이 챕터들이 함께 무효화된다. 챕터 길이는 프레임 경계에 맞추고, 총합은 확정된 길이와 같아야 한다.

아래 명령은 사용자가 미리보기를 확인하고 전편을 합성하기로 한 뒤에만 실행한다. 이 명령으로 미리보기용 MP4를 먼저 만들지 않는다.

```bash
node <skill>/scripts/build-long.mjs <slug>/chapters.json
```

같은 명령을 다시 실행하면 검증을 통과한 챕터 캐시를 재사용한다. 어떤 챕터의 원본 파일이나 렌더링 사양을 바꾸면 그 챕터만 다시 빌드한다. `.showreel-cache/`는 유지하며, 정상적인 중단을 캐시를 비울 이유로 삼지 않는다. 내부 캐시는 기술 산출물이며, 소스 코드, brief, 원본 오디오를 대체하지 않는다.

- 챕터마다 독립된 오디오 트랙을 유지한다. `chapters[].audio`를 쓰고, 오디오가 없는 챕터는 같은 길이의 무음으로 채운다. 챕터 오디오 길이가 맞지 않으면 오류가 난다.
- 전체 믹스가 이미 있다면 최상위 `audio`에 전체 오디오를 지정하고, 어떤 `chapters[].audio`도 설정하지 않는다. 확정된 총 길이와 맞아야 한다.
- 전편이 무음이면 두 가지 오디오 필드를 모두 설정하지 않는다. 이때 기술 검사는 오디오 트랙이 없어야 통과한다. 짧은 영상에서 이에 대응하는 설정은 `AUDIO=none`이다. 무음 WAV를 라우드니스 검사를 통과해야 하는 유음 완성본처럼 취급하지 않는다.
- `--skip-qa`는 초안에만 쓰며, 전달용 빌드에는 사용할 수 없다. 최종본은 완전한 사양으로 검수를 통과해야 한다.

## 오디오도 챕터별로 만든다

내장 합성기와 Tone.js는 모두 전체 길이의 샘플 메모리를 할당한다. 20분 전편을 위해 Float32 버스를 여러 개 만들고 메모리를 늘려서 해결하려 해서는 안 된다.

챕터마다 자체 `timeline.js`, `score.mjs` 또는 `score.tone.js`를 두고, 기존의 음색, 이펙트, 비트 도구를 그대로 쓴다. 먼저 `audio.mjs build`로 해당 챕터의 음악과 효과음을 빌드하고, `narration.md`에 따라 해당 챕터의 나레이션과 믹싱해 챕터별 `audio/final.wav`를 얻는다. 마지막으로 챕터 빌더가 이를 스트리밍 방식으로 이어 붙인다.

사용자가 나레이션 전체를 하나의 긴 오디오로 제공했다면, 먼저 실제 문장 구간 타임스탬프를 얻고, 자연스러운 멈춤에서 챕터를 나눈다. 분할하면서 글자를 잃거나 속도를 바꿔서는 안 되며, 모든 챕터 구간은 확정된 전체 내용을 빠짐없이 덮어야 한다. 원본 녹음은 보존한다. 사용자 원고가 길면 TTS가 문장 단위 합성과 캐시를 자체적으로 제공하므로, 챕터에 맞는 조각을 골라 화면을 만든다. 전체 음성 트랙은 최상위에 두어 음성을 중복 인코딩하지 않도록 한다.

배경음악은 챕터 경계에서 미리 이어짐, 페이드아웃, 호흡을 설계한다. 챕터를 이어 붙인다는 이유로 음악을 아무 데서나 자르면 안 된다. 연속된 음악은 먼저 스트리밍 ffmpeg로 이어 붙여 처리할 수 있으며, 최종적으로 전체를 한 번에 마스터링한다. 원래 조용해야 할 챕터를 강제로 같은 라우드니스로 끌어올리지 않는다. 음성이 나오는 동안의 회피와 최종 믹싱은 `narration.md`를 본다.

## 챕터별 검수와 전편 검수

합성 전에 `editor.mjs`로 챕터를 하나씩 열어 본다(`editor.md` 참고). 챕터 순서와 각 워크스페이스 링크를 제공하고, 챕터 끝과 다음 챕터 시작을 대조한다. 여러 챕터가 같은 페이지를 공유할 때는 그 페이지의 워크스페이스에서 재생 헤드와 루프 구간으로 찾아본다. 첫 버전에서는 페이지를 가로지르는 연속 재생을 제공하지 않는다. 소리가 없는 챕터도 먼저 미리본다. 기본적으로 이 전편 내용을 사용자가 확인한 뒤에 빌드를 시작하며, 챕터마다 내보내기를 다시 확인받을 필요는 없다.

워크스페이스에서 소리를 편집했다면, 빌드 입력은 확인된 믹스를 써야 하며, 해당 출처, 길이, 해시 검사를 통과해야 한다. 현재 버전은 여러 챕터 세션을 `chapters.json`이나 `audio/mix.json`에 자동으로 다시 쓰지 않는다. 내보내기 프로젝트에서 이 입력과 검증 기록을 직접 동기화하고, 원본 파일을 보존한 뒤에 빌드해야 한다. 편집을 무시하거나 검증을 꺼서 이어 붙이면 안 된다.

빌드 전에 각 챕터에 대해 `render.mjs --determinism`을 실행한다. 각 챕터의 정지 프레임, 텍스트 프레이밍, 모션, 휴대폰 크기 검사를 수행하며, 자료는 `qa/<chapter-id>/`에 저장한다. 각 컷 지점 전후의 연속 프레임을 보고, 중복 프레임, 누락 프레임, 텍스트 점프, 오디오 이음새를 확인한다.

빌더는 전편에 대해 `inspect.mjs qa`를 실행해 크기, fps, 총 길이, 프레임 수, 최종 오디오 트랙을 검사한다. 전편의 프레임 샘플 디렉터리는 참고용일 뿐이며, 챕터별 검사를 대신할 수 없다. 나레이션이 있으면 `narration.mjs check`를 따로 실행하고, 원고, 소리, 화면을 문장별로 대조한다. 전편의 청감 검수는 여전히 사용자의 최종 판단에 맡긴다. 전달할 때는 챕터 목록, 캐시 재사용 방식, 재빌드 명령, 기술 결과, 알려진 문제를 함께 제공한다. 샘플 프레임만 보고 전편을 완전히 시청하거나 청취했다고 주장하지 않는다.
