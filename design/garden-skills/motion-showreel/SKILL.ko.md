# Motion Showreel

주제를 그래픽, 텍스트, 인터페이스 애니메이션 중심의 영상으로 만들고 MP4와 재빌드 가능한 소스를 전달한다. 짧은 영상의 모션 밀도와 창작 자유를 유지하며, 챕터 단위로 최대 20분 분량의 콘텐츠도 지원한다.

**원리**: 페이지가 결정적인 `render(t)`를 노출하고, 스크립트가 프레임마다 스크린샷을 찍은 뒤 ffmpeg로 MP4를 합성한다. 화면, 나레이션, 배경음악, 효과음은 `timeline.js`를 공유한다. 나레이션이 없으면 내용과 음악 비트에 맞춰 화면을 구성한다. 나레이션이 있으면 실제 음성 시간을 기준으로 삼고, 그에 맞춰 음악과 효과음을 배치한다.

**기본은 미리보기 후 내보내기**: 모든 유형은 먼저 편집 워크스페이스를 열어 사용자가 실제 화면과 소리를 확인하게 한다. 사용자가 「导出视频」(영상 내보내기) 버튼을 클릭하거나, 대화에서 미리보기가 통과되었고 내보내도 된다고 확인해야 MP4를 합성한다. 처음에 "영상을 만들어 달라"고 요청했다고 해서 미리보기가 통과된 것은 아니다. 사용자가 미리보기를 명시적으로 면제한 경우에만 바로 내보낼 수 있다. 정지 프레임, 자체 점검, 오디오 준비는 미리 진행할 수 있으며, 기본적으로 프록시 MP4나 샘플 전편을 만들지 않는다.

**제작 과정을 지켜보기(요청 시)**: 요구사항 문답에서 「边做边看」(만들면서 보기), 「实时进度」(실시간 진행), 「每个阶段看看」(단계마다 보여 달라) 같은 의향을 알아챈다. 사용자가 그렇게 말하면 바로 진행 페이지를 열고, 요구사항 설명부터 스타일 프레임, 음성 샘플, 镜头(샷)과 믹스까지 단계별로 보여 준다. `references/progress.md`에 따라 자체 점검을 마친 단계 결과물을 발행하며, 미완성 코드를 직접 로드하지 않는다. 사용자의 확인을 받으면 먼저 `progress.mjs <project> --stage <현재 단계> --confirm --message "已确认，正在……"`로 대기 상태를 풀고, 그 뒤에 조사, 다운로드, 제작을 진행한다. 결과물이 다 만들어질 때까지 기다렸다가 진행 상황을 뒤늦게 채우지 않는다. 요청이 없으면 기본값인 최종 워크스페이스 미리보기를 유지한다. 이 과정은 제작 기준, 확인 단계, 최종 영상 검수를 바꾸지 않는다.

**좋은 영상은 어디서 나오는가**: 변화의 밀도, 움직임의 질감, 기억에 남는 한 장면, 음과 화면의 관계, 이 네 가지가 보통 인상을 결정한다. 다만 구체적으로 어떻게, 얼마나 움직일지는 **스타일과 내용**이 정하며, 모든 영상에 다중 카메라, 스프링, 화면 가득한 효과음이 필요한 것은 아니다. 전역적으로는 몇 가지 바닥선만 지키고(「바닥선」 참고), 나머지는 모델에게 주는 출발점이지 천장이 아니다.

**영상감**: 설명, 제품 데모, 서사 영상은 대상의 행동과 관계가 내용에 따라 발전해야 하며, 카메라가 바뀌어도 공간이 이어져야 한다. 나레이션 문장마다 정적인 타이틀 카드를 만들고 페이드인, 줌, 배경 파티클로 포장해서는 안 된다. 분기를 짜기 전에 "관객이 무엇이 어떻게 변하는지 이해해야 하는가, 주체의 전후 상태는 무엇인가, 이전 샷과 어떻게 이어지는가"를 먼저 적고 나서 모션을 고른다. 로고, 모션 타이포그래피, 루프, 의도적으로 정지한 스타일은 자체 문법을 따르며, 계속 흔들리는지나 60fps인지로 좋고 나쁨을 판단하지 않는다. 구체적인 방법은 `references/craft.md`의 「연속 서사」를 참고한다.

| 사용자가 원하는 것 | 이 스킬을 쓰는가? |
|---|---|
| 제품 홍보 단편, 모션 포트폴리오, UI 모션, 키네틱 타이포그래피 / 비트 맞춤, 로고 연출, 타이틀, 루프 GIF | ✅ |
| 비디오 모델이 만든 그린스크린 인물 + 코드로 만든 장면, 큰 글자, 모션 | ✅ 인물은 사용자가 제공(`references/formats.md` H 유형) |
| 사용자가 나레이션 원고나 녹음을 제공하고 설명이 있는 MP4를 원함 | ✅ 나레이션 주도 모드. TTS는 반드시 사용자가 제공한 원고를 쓴다 |
| 클릭으로 진행하는 발표, 현장 연설, 인터랙티브 웹 데모, 기사에서 나레이션 원고 만들기 | `web-video-presentation` 사용 |
| 웹페이지, 랜딩 페이지, 인터랙티브 프로토타입, 정적 비주얼 시안 | ❌ `web-design-engineer` 사용 |
| 실사 인물 연기, 실제 촬영 질감, 기존 소재 편집, 비디오 모델로 바로 화면 생성 | ❌ |

**길이**: 최대 20분(1200초)이며, 사용자가 확정한 길이를 따른다. 단편은 여전히 5~60초가 적합하며, 긴 영상을 20분 내내 이어지는 고밀도 비트 맞춤으로 만들지 않는다. 2분을 넘으면 `references/long-form.md`를 읽고 챕터 단위로 기획, 제작, 검수한다. 사용자가 지정한 길이가 나레이션의 실제 길이나 콘텐츠 분량과 충돌하면, 멈추고 조정 방안을 확인한다. 임의로 잘라내거나, 나레이션을 빨리 하거나, 영상 길이를 바꾸지 않는다.

## Opus의 강점과 기본 함정

- **강점**: 파일 하나에서 Canvas, SVG/DOM, WebGL, Three.js를 섞을 수 있고, 한 구간마다 다른 매체로 바꿀 수도 있다. 모션은 수식으로 정확히 계산할 수 있다(닫힌 형태의 스프링, 비트 그리드, 서브프레임 모션 블러). 소리와 화면이 같은 타임시트를 읽는다. 오래 자율적으로 「정지 프레임 렌더 → 이미지 확인 → 수정」을 반복할 수 있다. 미적 판단력이 강해서 「全力以赴」(온 힘을 다해) 한마디로도 매우 인상적인 결과가 나올 수 있다.
- **기본 함정**: 제약이 없으면 화면은 어두운 배경, 가운데 큰 글자, 모든 요소가 함께 페이드인, 보라-파랑 그라데이션에 글로우, 움직이지 않는 카메라로 흘러간다. 음악은 A단조 4비트, 모든 강박의 impact + crash, 종소리로 마무리되는 쪽으로 흘러서 여러 편이 같은 노래처럼 들린다. 그래서 먼저 레퍼런스를 찾아야 하고(화면과 소리 모두), 스타일과 금지 목록을 명확히 적어야 한다. 다만 제약도 고정되어서는 안 된다. 이 스킬의 스타일 라이브러리와 기법 라이브러리는 출발점이며, 주제가 필요로 하면 언제든 각색하고, 섞고, 직접 만들 수 있다.
- **잘 못하는 것**: 사실적인 인물, 복잡한 손 / 천 / 털, 정밀한 실제 물리가 필요한 것, 사진 같은 제품(사용자가 모델이나 이미지를 제공한 경우는 제외). 이런 경우에는 스타일화하거나, 그린스크린 인물 + 코드 장면으로 역할을 나눈다.

## 워크플로

```
0 환경 점검(한 번만)
1 요구사항 확정 ──── 필수 항목 채우기, 요약 → 🛑 사용자 확인 대기
2 brief.md ──────── 레퍼런스 → 용도 + 스타일 → Reel Read → 분기 + 소리 계획
3 스타일 프레임 ──── 스타일이 정해짐: 3장 / 미정: 방향 3개 × 1장 → 🛑 사용자 확인 대기
4 제작 ──────────── 나레이션을 쓰면 실제 음성 타이밍 준비 → timeline → 샷별 제작 → 웹 자체 점검
5 음악과 믹싱 ────── BGM, SFX는 소스를 독립적으로 고름; 나레이션이 있으면 음성 우선
6 워크스페이스 미리보기 ─ 편집 워크스페이스를 열고 검토 및 수정 → 🛑 내보내기 승인 대기
7 내보내기와 검수 ── MP4 인코딩 → 기술 검사(반드시 전부 PASS) + 최종 검토
8 전달
```

공통 작업 폴더: 사용자의 현재 디렉터리에 `<slug>/`를 만들고 모든 파일을 그 안에 둔다. `brief.md`, `index.html`, `motion.js`, `timeline.js`, `score.mjs` 또는 `score.tone.js`(scaffold의 `--audio`로 선택), `build.sh`, `fonts/`, `assets/`, `audio/`, `qa/`, `out/`이다.

### 0단계: 환경

처음 사용할 때 `sh <skill>/scripts/setup.sh`를 실행한다. Playwright와 Chromium을 설치한 뒤 `check-env.mjs`를 실행한다. Node 18+와 ffmpeg가 필요하다. 없으면 설치 방법을 사용자에게 알려 주고, 사용자 대신 시스템 소프트웨어를 설치하지 않는다. 도구 자체의 테스트는 `cd <skill>/scripts && npm test`로 실행한다.

### 1단계: 요구사항 확정(멈추고 사용자를 기다린다)

빠진 항목을 한꺼번에 묻고, 이미 제공된 정보는 다시 묻지 않는다. 다음 정보는 반드시 명확해야 하며, 고정된 기본값으로 사용자의 결정을 대신하지 않는다.

| 필수 정보 | 명확히 해야 할 것 |
|---|---|
| 핵심 주제, 제작 내용 | 무엇을 보여 줄지, 반드시 들어가야 할 내용 |
| 길이 | 초 또는 분 단위의 정확한 값, 약간의 오차 허용 여부. 1200초를 넘을 수 없음 |
| 가로 또는 세로 | 선택에 따라 실제 크기를 정함. 사용자가 명시한 1:1 등 다른 화면비도 지원한다. 해상도와 프레임레이트는 제안할 수 있고, 확인 요약에 기록한다 |
| BGM 소스 | AI 자체 합성 / 사용자 제공. 사용자가 명시적으로 끌 수도 있음 |
| 효과음 소스 | AI 자체 합성 / 사용자 제공. BGM과 따로 선택하며, 끌 수도 있음 |
| 나레이션 방식 | 나레이션 없음 / AI TTS / 사용자 녹음 제공 |

**조건부 필수**: TTS를 고르면 사용자가 나레이션 스크립트를 제공해야 한다. 대신 써 주거나, 보충하거나, 고쳐서 임의로 합성하지 않는다. 또한 TTS 서비스와 필요한 API 설정을 명시한다(기존 설정은 재사용하고, 자격 증명은 환경 변수로 쓰며 brief에는 적지 않는다). Gemini, MiniMax, 사용자 정의 어댑터를 지원하며, 필요하면 `references/narration.md`를 읽는다. 사용자 녹음을 고르면 녹음 파일이나 접근 가능한 주소가 필요하다. 사용자 BGM/효과음을 고르면 해당 파일이 필요하다. 나레이션 언어, 음색 등은 원고나 설정에서 판단할 수 있으면 요약에 적고, 그렇지 않으면 함께 묻는다.

**선택 정보**: 참고 자료, 대상 독자와 발행 플랫폼, 주제 스타일. 대상과 플랫폼을 주지 않았다면 내용에서 추론하고 요약에 그 이유를 적는다. 스타일을 주지 않았다면 스타일 프레임 단계에서 세 가지 방향을 제시한다.

**제작 과정 선호**: 사용자의 기존 피드백에서 과정을 보고 싶어 하는지 판단한다. 분명히 말했다면 기록하고 바로 활성화하며, 같은 질문을 반복하거나 필수 문항을 늘리지 않는다. 활성화할 때는 `references/progress.md`를 읽고, `editor.mjs <slug> --progress`를 일찍 실행해 능동적으로 연다. 디렉터리에 아직 애니메이션이나 오디오가 없어도 괜찮다. 요구사항 요약에 단계마다 보여 준다는 점을 적고, 이후에도 원래의 요구사항과 스타일 확인을 그대로 기다린다.

**소재 처리**: 사용자가 구체적인 내용을 주고 AI 생성을 허락했다면 그에 따라 제작한다. 구체적인 내용이 부족하면 필요한 자료를 묻거나, 주제에 따라 온라인 조사를 하고 출처를 남긴다. 나레이션 원고가 있다면 원고에서 정보를 먼저 뽑아내고, 사용자에게 같은 내용을 다시 채우게 하지 않는다. AI는 일러스트, 장면, 추상 도형, 명확히 표시한 예시 내용을 만들 수 있다. 실제 제품 기능, 숫자, 브랜드 소재는 「바닥선」을 지켜야 하며, 가상의 자료로 실제 내용인 척해서는 안 된다. 브랜드 로고나 실제 제품 스크린샷의 요구사항은 `references/stack.md`를 참고한다.

- 사용자가 참고 영상을 줬다면: 먼저 `inspect.mjs sheet <ref> --cells 30`으로 전체를 보고, `inspect.mjs grid <ref> --strips`로 컷 지점과 그 컷이 놓인 비트 그리드(BPM 후보, 구간마다 몇 스텝인지, 각 전환의 연속 프레임)를 측정하고, `inspect.mjs heat <ref>`로 구간마다 어디가 얼마나 움직이는지 본다. 측정한 수치는 brief의 벤치마크 항목에 적는다. 구조와 기법만 배우고 소재는 가져오지 않는다.
- 사용자가 곡을 줬다면: 나레이션이 없으면 먼저 `audio.mjs beats <track> --out <slug>/audio/beats.json`을 실행한다. 나레이션이 있으면 음악의 비트는 설명의 리듬을 따른다.
- 화면에 나올 제품, 브랜드, 기술 용어 중 확실하지 않은 것은 먼저 확인한다.

확인된 주제, 길이, 화면비, BGM/효과음 각각의 소스, 나레이션 방식, 소재 상황을 요약하고, **사용자가 확인할 때까지 멈춘 뒤 brief를 쓴다**. 처음 요청에서 정보가 모두 갖춰졌더라도 먼저 요약을 보내 확인받는다. 사용자가 「全力以赴」, 「给我惊喜」(놀라게 해 달라), 「你看着办」(알아서 해 달라)라고 말하면 창작 선택만 위임된 것이며, 필수 정보를 생략하거나 확인 단계를 건너뛰는 허락이 아니다. 사용자가 특정 확인을 건너뛰라고 명시한 경우에만 계속할 수 있으며, 그 허락을 기록한다.

**자유 모드**: 창작 자율성은 유지하고 바닥선과 기술 파이프라인만 지킨다. 스타일, 구조, 기법은 스스로 판단할 수 있고, 스타일 라이브러리를 전혀 쓰지 않아도 된다. 그래도 brief를 쓰고, 세 가지 방향을 제시하며, 요구사항과 스타일 확인은 완료해야 한다. 제작 후에도 똑같이 먼저 워크스페이스에서 미리보기를 하고, 그다음 내보내기를 확인한다. 사용자가 명시적으로 면제한 확인만 예외다.

### 2단계: brief.md

**먼저 레퍼런스를 찾는다**: 작업을 시작하기 전에 이 영상(이 주제 + 이 용도)에 맞는 레퍼런스 작품을 1~2개 고른다. 영화 타이틀, 광고, 게임, 모션 작품, 디자인 유파 모두 가능하다. brief에 「배울 것」(구도, 리듬, 카메라 문법, 색 배치 논리, 음악 구조)과 「배우지 않을 것」(캐릭터, 특정 샷, 멜로디, 로고, 폰트 파일)을 적는다. 레퍼런스는 어떤 규칙보다도 완성도의 상한을 높인다.

**그다음 후보 구조 세 가지를 생각한다**: 예를 들어 하나의 여정, 전후 비교, 카운트다운, 하나가 다른 것으로 변하는 것, 컷 없이 이어지는 롱테이크 등이다. 각각 두세 줄로 적고, 하나를 고른 뒤 이유를 적는다. 처음 떠오른 아이디어는 대개 그 스타일의 클리셰다.

**용도와 스타일은 따로 고른다**:
- 용도(무엇을 찍고, 어떤 구조로 말할지)는 `references/formats.md`를 보고, 해당하는 절만 읽는다.
- 스타일(어떻게 보이고, 어떻게 움직이고, 어떤 소리인지)은 먼저 `references/styles/INDEX.md`를 보고, 선택한 1~2개의 스타일 파일**만** 읽는다. 스타일은 그대로 쓸 수도 있고, 각색(규칙 한두 개 교체)하거나, 혼합(주 하나 + 보조 하나, 또는 단락마다 매체를 전환)하거나, `styles/_template.md`로 직접 정의할 수도 있다. 스타일 규칙은 그대로 유지하고, 이야기, 샷, 구조는 사용자의 주제에서 가져오며, 다른 영상을 그대로 따라 하지 않는다. 각 스타일 파일에는 「식별 신호」와 「가장 흔한 버전」 두 절이 있다. 주제에 맞춰 신호를 2~3개 고르고(최소 하나는 클리셰가 아닌 것), brief에 클리셰 중 어떤 것을 뒤집었는지, 또는 왜 그대로 두었는지를 적는다. 사용자가 스타일을 골랐다면 한눈에 알아볼 수 있는 것이 목적이므로, 두세 개의 신호면 충분하다.
- 필요하면 `references/craft.md`(기법 라이브러리)를 추가로 본다.

`references/brief-template.md`에 따라 brief를 쓴다. 핵심은 다음과 같다.

```yaml
Reel Read:
  format: [用途，formats.md 里的类型]
  benchmark: [对标作品 · 学什么 · 不学什么]
  structure: [三个候选结构 → 选中哪个、为什么]
  style: [styles/ 里的风格（含改造点），或者混搭方案，或者自定义规则]
  signals: [挑了哪 2–3 个辨识信号、为什么；翻掉了俗套的哪几条]
  takeaway: [观众记住的一句话或一个画面]
  hook: [前 1 秒发生什么]
  signature: [记忆点：第几秒、什么手法]
  palette / type / motion / camera / texture: [按所选风格写出具体值]
  sound: [无声 / 合成（声音对标、律动、和声、配器、曲线，见 sound.md 第 2 节）/ 用户曲子（BPM、drop）]
  audio-sources: [BGM 与音效各自为 AI / 用户 / 关闭]
  narration: [无 / 用户原稿 TTS / 用户录音；有口播时句段时间轴路径、人声优先]
  forbidden: [这支片子的禁止清单]
```

이어서 분기표를 쓴다. 나레이션이 없으면 **박자 그리드 + 분기표**를 유지한다. 나레이션이 있으면 문장을 샷과 이벤트에 연결하고, `샷 / 문장 ID | 설명할 변화 | 대상의 시작과 끝 상태 | 이어받는 대상과 공간 | 핵심 이벤트와 실측 시간 근거 | 샷과 소리 | 전환 방식`을 적는다. 한 샷이 여러 문장을 덮을 수 있고, 한 문장에 여러 동작이 있을 수 있다. 나레이션 문장을 컷 지시로 취급하지 않으며, 원고 전체를 화면에 빠짐없이 옮기도록 요구하지도 않는다. 실제 구간은 음성 준비 후에 채우고, 글자 수로 추정한 시간을 최종 정렬의 근거로 삼지 않는다. 긴 영상은 챕터표, 챕터별 길이, 챕터 간 일관성 규칙을 따로 쓴다.

사용자가 「全力以赴」 한마디만 했더라도, 위의 구체적 제약으로 번역해야 한다. 그렇지 않으면 결과는 운에 맡긴 뽑기가 된다.

### 3단계: 스타일 프레임(두 번째로 멈추고 사용자를 기다린다)

프로젝트 생성: `sh <skill>/scripts/scaffold.sh <slug> [--audio synth|tone|layer|file|none]`(synth = 1단계 합성, 선택한 score만 복사하며, `file`은 준비된 최종 트랙을 사용). 스캐폴드의 엔진 기본값은 기술 초기화용일 뿐이며, 요구사항 확인을 대신하지 않는다. starter는 파이프라인이 돌아가는지 확인하기 위한 것이므로, 화면과 문구는 모두 바꿔야 한다.

**A. 사용자가 스타일을 이미 정한 경우**(또는 명확한 레퍼런스를 준 경우):
아래 명령의 초 단위 값은 예시일 뿐이다. 실제로는 이 영상의 시작, 기억 지점, 마무리의 유효 시간을 사용한다. 짧은 영상이든 긴 영상이든 14.5초를 그대로 베끼지 않는다.
1. 실제 코드로 hook 프레임, 기억 지점 프레임, 마무리 프레임을 만든다. 색, 폰트, 문구는 모두 최종본을 쓴다.
2. `render.mjs <slug> --still 0.6,7.2,14.5 --sheet`을 실행하고, 직접 먼저 확인한 뒤 명확한 문제를 고치고 나서 사용자에게 보여 준다. 움직임에 의존하는 방향이라면, 이 절이 요구하는 연속 클립을 워크스페이스에 보여 주며, MP4로 먼저 인코딩하지 않는다.
3. 요구사항 요약, 분기 개요, 스타일 프레임을 사용자에게 보내고 "방향이 맞습니까?"라고 묻는다.

**B. 사용자가 스타일을 정하지 않은 경우**(자유 모드 포함): `styles/INDEX.md`의 규칙에 따라 **서로 뚜렷이 다른 방향 3개**를 준다.
- A는 주제 / 브랜드에 맞추고, B는 다른 화면 언어(다른 그룹에서 가져온다), C는 대담하게(직접 정의하거나, 혼합하거나, 구조적으로 과감하게 한다. 최소 한 방향은 라이브러리에 없는 것이어야 한다).
- 방향마다 미니 Reel Read를 3~5줄로 쓰고(스타일, 레퍼런스, 기억 지점, 음악 방향), 실제 코드로 그 방향을 가장 잘 대표하는 **키프레임 한 장**을 렌더링한다. 세 방향의 페이지는 같은 프로젝트에 두고 `?dir=a|b|c`로 전환한다. B와 C는 이 키프레임 한 장을 위해서만 존재하면 되며, 재생 가능한 전편으로 만들 필요는 없다.
- `render.mjs <slug> --directions a,b,c --at 14.5,2,0`을 실행해 세 장을 한 번에 렌더링하고, 라벨이 붙은 `qa/directions.png`로 합친다. 이것을 사용자에게 보여 주고 "어느 것을 고를지, 아니면 어떻게 섞을지?"를 묻는다.

두 경우 모두 **사용자가 실제로 답할 때까지 기다린 뒤** 제작에 들어간다. TTS 프로젝트라면 사용자 원고의 구간 계획과 음색 짧은 샘플을 함께 첨부해(사용자가 준 텍스트만 사용), 소리 방향도 함께 확인한다. 별도의 필수 멈춤 지점을 추가하지는 않는다. 사용자가 미리 확인할 필요가 없다고 명시했다면 스스로 하나를 고르고 이유를 적은 뒤 자체 점검을 거쳐 계속한다. 전달할 때는 고르지 않은 방향도 함께 준다(B의 경우 `qa/directions.png`를 첨부하고, A의 경우 다른 두 가지 가능성을 각각 한 문장으로 적는다). 그래야 사용자가 나중에 돌아와서 바꿀 수 있다.

연속 동작에 의존하는 방향이라면, 정지 프레임 외에 워크스페이스에서 6~10초짜리 대표 모션 클립을 보여 준다(3초보다 짧은 영상이면 전편). 재생 헤드와 루프 재생으로 구간을 찾을 수 있게 하고, 상태 변화 한 번과 그 전후의 이어짐을 포함한다. 먼저 연속 프레임을 직접 보고 점프가 없는지 확인한다. 클립은 스타일 프레임과 함께 확인하며, 샘플 영상을 미리 내보내지 않는다. 나레이션이 아직 생성되지 않았다면, 이것이 동작 예고편이며 음성과 정확히 맞춰졌다고 주장할 수 없다고 명확히 표시한다. 스타일 확인과 최종 미리보기 확인은 각각 방향과 완성 내용을 따로 확인한다.

### 4단계: 제작

제작 전에 `references/stack.md`(페이지 계약, 결정성, 각 기술의 함정)를 먼저 읽는다. 바로 쓸 수 있는 코드가 필요하면 `references/recipes.md`를 본다.

**나레이션이 있으면 먼저 나레이션 타임라인을 고정한다**: `references/narration.md`에 따라 사용자 원고를 합성하거나 사용자 녹음을 가져와 실제 길이와 문장 구간 타임스탬프를 얻은 뒤 화면을 배치한다. 사용자 녹음은 사용 가능한 전사 도구나 사용자가 제공한 SRT/JSON으로 텍스트와 시간을 얻는다. 믿을 만한 타임스탬프가 없으면 문장 단위 정렬이 완료되었다고 주장할 수 없다. 길이가 맞지 않으면 먼저 확인하며, 조용히 채우거나, 자르거나, 속도를 바꾸지 않는다. 실제 구간을 분기표로 가져오고, 나레이션의 멈춤과 강조를 보존하며, 음악 마디에 억지로 맞추지 않는다. 2분을 넘으면 `references/long-form.md`에 따라 챕터로 나누어 제작하고 챕터 캐시를 유지한다.

문장 구간은 동기화 범위만 제공한다. 샷과 주체의 움직임은 문장을 넘어 이어질 수 있다. 핵심 변화에 단어 단위 동기화가 필요하면 실제 단어 시간이나 수동 앵커를 쓰고, `narration.js`로 조회해서 화면과 효과음이 같은 이벤트를 참조하게 한다. 문장 단위 시간만 있으면 문장 단위 동기화를 유지하며, 글자별 시점을 지어내지 않는다. 제작 중에는 기본적으로 `editor.mjs`로 소리를 함께 들으며 미리보고, 드래그와 프레임 단위 확인을 한다. `preview.mjs`는 가벼운 디버깅 도구로 남긴다. 미리보기는 같은 `render(t)`만 구동하며, 정식 렌더링에는 들어가지 않는다.

1. 모든 시점은 `timeline.js`에 쓴다. 페이지와 `score.mjs`는 모두 여기서 import한다. 샷표는 `SHOTS`에 쓰고(검수 시 샷별 모션을 보고), 의도된 정지는 `HOLDS`에 쓰며(예: 마무리 `[[b(36), DUR]]`), 숨을 쉬게 해야 할 강박은 `DROPS`에 쓴다. 검수 도구가 이 값들을 읽는다. 전환을 박자에 맞출 때는 `revealOn(박자점, 전환 길이, 드러나는 점)`으로 시작점을 거꾸로 계산해서, 새 화면이 드러나는 첫 프레임이 박자에 떨어지게 한다.
2. 샷은 하나씩 만든다. 사용자가 제작 과정을 보길 원하면, 샷마다 자체 점검을 통과한 뒤 독립적으로 재생 가능한 결과물을 발행하고(`progress.mjs --stage scenes --shot <id> --total <샷 총수> --publish <그 샷의 미리보기 디렉터리>`), 그다음 샷으로 넘어간다. 모든 샷을 다 쓴 뒤 한꺼번에 3/3으로 채우지 않으며, 전편 소재가 다 모일 때까지 첫 미리보기를 기다리지도 않는다. 샷마다 시작, 중간, 끝 정지 프레임 3장을 렌더링한다. 핵심 상태 변화와 샷 이음새는 별도의 짧은 연속 샘플로 보고, 주체가 까닭 없이 초기화되지 않는지, 동작 속도가 갑자기 바뀌지 않는지, 샷이 끊기지 않는지 확인한다. 정지 프레임이 좋아 보여도 모션 검사를 대신할 수 없으며, 빠른 동작은 `inspect.mjs strip`으로 연속 프레임을 본다.
3. 결정성 검사 `render.mjs <slug> --determinism`을 실행한다. 통과하지 못하면 먼저 고친다.
4. 웹 미리보기로 리듬과 연속 동작을 확인한다. 저해상도 프록시나 MP4 샘플을 기본으로 렌더링하지 않는다. 정지 프레임과 결정성 검사는 평소대로 진행한다. 오프라인 클립이 정말 필요하다면 이유를 설명하고, 사용자가 동의한 뒤 필요한 범위만 렌더링한다.
5. brief에 따라 `FPS`, `SIZE`, `AUDIO`, `LOOP`를 설정하고, 아래의 사운드 준비를 마친 뒤 6단계로 들어간다. 이 시점에는 `build.sh`, 영상 모드의 `render.mjs`, `build-long.mjs`를 실행하지 않는다.

**하드 룰**:
- 화면은 t에 의해서만 결정된다. `Math.random`, `Date.now`, rAF, 타이머, CSS 애니메이션을 쓰지 않으며, 프레임과 프레임 사이에 상태를 저장하지 않는다.
- 모든 폰트와 소재를 로드한 뒤에 `READY = true`를 설정한다. 폰트는 프로젝트에 셀프 호스팅한다.
- 레이아웃은 `stageSize()`가 돌려주는 너비와 높이에서 계산하며, 픽셀을 고정하지 않는다.

서브프레임 모션 블러를 쓰면서 문구가 하드 컷으로 바뀐다면, `references/stack.md`의 선택적 샘플링 컨텍스트를 써서 문구 상태와 연속 모션을 구분할 수 있다. 내보낸 뒤에는 전환 지점의 연속 프레임을 확인해, 서브프레임 평균으로 한 프레임만 텍스트가 겹쳐 보이는 현상이 없는지 본다.

제작 과정을 보여 주기로 했다면, 스타일 프레임과 음성 짧은 샘플은 자체 점검 후 이미지/오디오 결과물로 발행한다. 샷과 믹스가 재생 가능한 단계가 되면 `progress.mjs --publish`로 안정 사본을 발행한다. 작업을 시작하기 전에 `running`으로 갱신하고, 완료되면 결과물을 해당 단계에 붙인다. 요구사항/스크립트는 Markdown을 발행할 수 있고, 스타일 프레임은 이미지, 사운드는 오디오, 샷별 제작은 재생 가능한 버전을 발행한다. 사용자의 선택을 기다릴 때는 `waiting`을 쓰고, 미완성 부분은 명확히 적으며, 개수는 성공적으로 발행된 샷 수로 계산한다. 단계 미리보기는 확인 단계를 추가하지 않으며, MP4 합성을 트리거하지 않는다. 최종 짧은 영상은 `review --final`로 같은 진행 페이지에서 음량 조정과 내보내기가 가능한 워크스페이스로 넘어간다. 긴 영상은 챕터별로 계속 보여 주고, 전편을 확인한 뒤 원래 흐름에 따라 빌드한다.

### 5단계: BGM, 효과음, 믹싱

`references/sound.md`를 본다. BGM과 효과음은 각각 확정된 소스에 따라 제작하며, 사용자 음악 + AI 효과음 같은 조합을 허용한다. 아래 표는 AI 합성의 엔진 선택이며, 확정된 소재 소스를 엔진 기본값으로 덮어쓰지 않는다. 소리 방향(레퍼런스, 그루브, 화성, 편성, 곡선)은 brief에서 미리 정한다.

| 단계 | 무엇을 쓰나 | 적합한 용도 |
|---|---|---|
| 1단계 · 내장 합성 | `score.mjs`, Node에서 돌아가는 합성기(드럼, 핸드 퍼커션, 베이스, 패드, 플럭, 마림바 / 글로켄슈필 / 칼림바, 오르간, 보컬 패드, FM, 환경 노이즈, 효과음, 사이드체인, 리버브, lo-fi 처리). 의존성 없음 | 일렉트로닉, UI, 칩튠, 분위기, lo-fi, 핸드메이드와 장난감 느낌, 대부분의 모션 영상 |
| 2단계 · Tone.js | `score.tone.js`, 헤드리스 브라우저에서 Tone.js로 오프라인 렌더링. 샘플링 악기(`audio.mjs samples salamander`로 CC BY 피아노 다운로드), 컨볼루션 리버브, 더 풍부한 신스와 이펙트 | 실제 악기, 공간감, 시네마틱 느낌이 필요한 스타일 |
| 외부 곡 | 사용자가 제공한 음악(본인 것, 허락받은 것, AI 음악 서비스로 생성한 것) | 사용자가 이미 배경음악을 가지고 있을 때 |

- 빌드: `audio.mjs build <slug>/score.mjs` 또는 `score.tone.js`를 실행하면 −14 LUFS의 `audio/music.wav`가 나온다.
- 사용자 곡: 나레이션이 없으면 먼저 `audio.mjs beats`(librosa가 있으면 자동 사용)로 타임라인에 맞추고, score에서 `S.load()`로 효과음을 얹는다. 나레이션이 있으면 음악의 비트는 참고만 하고, 음악과 효과음을 음성에 맞춰 조정하며, 확정된 나레이션 타임라인은 옮기지 않는다.
- 무음: BGM, 효과음, 나레이션을 모두 끈 경우에만 건너뛴다. BGM만 껐다고 전편이 무음이 되는 것은 아니다.
- 나레이션이 있으면: 음악은 주선율, 밀집된 타격, 큰 다이내믹을 줄인다. 효과음은 정보 역할을 하는 동작만 남기고, 키워드와 문장 시작은 피한다. `narration.mjs mix`로 트랙을 따로 유지하면서, 음성이 나오는 동안 회피, 통일된 라우드니스, 피크 처리를 한다. 실제 문장 타임스탬프로 화면을 대조하되, 청감의 최종 판단은 사용자에게 맡긴다.

빌드할 때마다 최종 믹스에 `audio.mjs check`를 돌려 수치와 그래프를 확인한다. 호스트에서 청취가 가능하면 직접 들어 본다. 수치 통과를 "청감 확인 완료"로 적으면 안 된다. `timeline.js`에 `DROPS`가 있으면 이 도구는 강박 앞의 움푹 들어감과 상승을 측정하고, 숨 쉴 공간이 없으면 WARN을 낸다.

### 6단계: 워크스페이스 미리보기(기본 진입점, 내보내기는 사용자 확인 후)

모든 제작에서 `references/editor.md`를 읽는다. 제작 과정을 보여 주는 중인 짧은 영상은 같은 진행 페이지에서 `review --final`을 발행해 최종 워크스페이스로 쓴다. 이때 확정된 사양과 내보내기 품질 매개변수를 그대로 이어받으므로 별도의 진입점을 열지 않는다. 그 밖의 경우에는 `node <skill>/scripts/editor.mjs <slug> --size <이 영상의 크기> --fps <이 영상의 fps>`를 실행하고, 출력된 주소를 능동적으로 연다. 호스트가 브라우저를 열 수 없으면 접근 가능한 로컬 링크를 제공하고 사용자의 미리보기 피드백을 기다린다. 소리가 없거나, 나레이션이 없거나, 짧거나, 루프 영상도 이 단계를 거친다. 사용자가 다시 "워크스페이스를 열어 달라"고 말할 필요는 없다. 긴 영상은 `long-form.md`에 따라 챕터별로 워크스페이스를 열어 미리보고, 1차 버전은 여러 페이지에 걸친 전편 타임라인이 있는 척하지 않는다.

먼저 화면, 오디오 트랙, 길이, 오류를 직접 점검한 뒤, 사용자에게 재생, 드래그, 음량 조정을 맡긴다. 편집하지 않았다면 원래 믹스를 그대로 쓴다. 트랙을 조정하면 미리듣기를 갱신하고, 현재 믹스가 로드되었는지 확인한다. 사용자가 수정을 요청하면 고친 뒤 새로고침하고 다시 확인하게 한다. 이전 버전이 통과했다고 해서 수정본을 자동으로 내보내지 않는다. 사용자가 「导出视频」를 클릭하거나, 현재 미리보기가 통과되었고 내보내도 된다고 명확히 확인해야 다음 단계로 넘어간다. 두 가지 모두 내보내기 확인으로 치므로 같은 질문을 다시 하지 않는다.

미리보기 링크, 피드백, 내보내기를 확인한 버전, 음향 편집 기록은 `brief.md` / `qa/review_log.md`에 쓴다. 서비스나 브라우저를 쓸 수 없으면 원인을 설명하고 웹 미리보기 대안을 제공하되, 임의로 먼저 MP4를 생성하지 않는다. 서브프레임 블렌딩, DPR 슈퍼샘플링, ffmpeg 그레인은 내보내기 설정에 속한다. 미리보기가 모사하지 못하는 부분은 알려 주고, 완성본의 품질을 조용히 낮추지 않는다. 사용자가 미리보기 없이 바로 내보내라고 명시했다면 그 지시를 기록하고, 아래의 모든 기술 검수는 그대로 유지한다.

### 7단계: 내보내기와 검수

미리보기가 통과되면, 단일 페이지 영상은 워크스페이스에서 「导出视频」를 클릭하는 것을 우선한다. 기존 렌더러와 검수 도구가 편집판 MP4를 출력한다. 워크스페이스의 오디오 편집은 `build.sh`에 자동으로 반영되지 않으므로, 편집이 있다면 내보내기는 이미 들어 본 현재 세션에서 해야 하며 원래 믹스로 되돌아가면 안 된다. 워크스페이스에서 오디오를 편집하지 않았다면, 사용자가 확인한 뒤 `sh <slug>/build.sh`를 실행할 수도 있다. 이 명령은 음악을 빌드하고, 결정성을 확인하고, 렌더링하고, 텍스트 검토 자료를 만들고, 같은 사양으로 검수한다. 혼합 트랙은 `AUDIO=file AUDIO_FILE=audio/final.wav sh build.sh`로 쓰며, 기존 synth/tone/layer/none 방식도 계속 쓸 수 있다. 긴 영상은 확인 후 `build-long.mjs`로 챕터를 유지한 채 영구 빌드하며, 자세한 내용은 `references/long-form.md`를 참고한다.

`--subframes`, `--dpr`, `--grain`은 brief에 따라 넘긴다. 워크스페이스 출력과 수동 빌드는 같은 확정 사양을 쓴다. 이 값들은 시간을 늘리므로, 렌더링을 시작하기 전에 예상 시간을 보고한다. 루프 영상은 `--loop` 검수를 추가로 한다. 미리보기 확인은 내보낸 뒤의 기술 검사와 완성본 검토를 대신하지 않는다.

**기술 검사**: 프로그램이 판정한다. 하나라도 실패하면 전달할 수 없다.

```bash
node <skill>/scripts/inspect.mjs qa <slug>/out/final.mp4 --out <slug>/qa/final \
  --expect-size 1920x1080 --expect-fps 30 --expect-duration 16 --audio required   # 无声片用 --audio none；循环片加 --loop
```

이 명령은 파일 디코딩 가능 여부, 크기, fps, 길이, 프레임 수, 오디오 트랙, 검은 프레임, 라우드니스, 트루 피크, 그리고 필요하면 루프 이음새를 확인한다. 하나라도 FAIL이면 종료 코드는 1이며 반드시 고쳐야 한다. 전달하지 않은 사양 항목은 `NOT CHECKED`로 나열되며, 이때는 검수 통과로 치지 않는다. `build.sh`는 사양을 자동으로 넘긴다. 렌더 도구도 프레임 수가 맞지 않는 파일의 게시를 거부한다.

**검수**: 사람이 판단하기 위한 것이며, 프로그램이 판정하는 것이 아니다. 샘플 프레임 시트, 휴대폰 크기 샘플 프레임, 정지 구간(`HOLDS`에 선언된 것은 의도된 정지로 표시되고, 나머지는 빈 박자인지 판단해야 한다), 컷 지점, 샷별 모션과 플래시 프레임, 텍스트 프레이밍 표시 이미지(`qa/text-*.png`), 오디오 그래프를 살펴본다. `references/review.md`의 검수표에 따라 항목별로 관찰 내용과 가장 심각한 문제 3개를 적는다. 숫자와 차트가 있는 영상이라면 내용과 수치 기준이 맞는지도 확인한다. 수정한 뒤에는 문제가 있는 구간만 다시 렌더링하고, 그다음 전편을 출력한다. 과정은 `qa/review_log.md`에 기록한다.

나레이션이 있으면 추가로 `narration.mjs check`를 실행해 문장 시간 커버리지, 오디오 길이, 확정 사양을 대조한다. 원고를 문장별로 검토하여 원고, 소리, 화면이 일치하는지 확인한다. 자동 검사는 청감 검수를 대신하지 못한다. 긴 영상은 챕터별로 검수하고, 각 챕터의 이음새에서 화면, 소리, 타임라인이 맞는지 확인한다.

검수 결과는 사용자에게 참고용으로만 주며, **사용자가 직접 보는 것을 대신할 수 없다**. 해당되지 않는 항목은 「不适用」(해당 없음)으로 표시하며, 무음 작품의 음악-화면 동기처럼 맞지 않는 항목에 억지로 점수를 주지 않는다.

### 8단계: 전달

사용자에게 다음을 알린다.
- 실제 결과물 경로: 워크스페이스 내보내기는 `out/editor-<task-id>.mp4`, 원래 빌드는 `out/final.mp4`. 그리고 `out/poster.png`(poster: `render.mjs <slug> --poster <t>`).
- `brief.md`: 완전한 구조화 프롬프트, 요구사항과 스타일 확인, 최종 미리보기와 내보내기 확인 기록. 재사용 가능하며 API 자격 증명은 포함하지 않는다.
- 나레이션이 있으면 사용자 원고, 문장 타임라인, 각 트랙의 출처. 긴 영상은 챕터 manifest와 중단 지점에서 재빌드하는 명령.
- 기술 검사 결과(모두 PASS), 검수 기록에서 아직 해결하지 않은 문제, 렌더링 소요 시간.
- 워크스페이스를 다시 여는 방법, 현재 편집판을 재빌드하는 방법(editor.md 참고), 원래 빌드를 계속 `sh build.sh`로 할 수 있는지, 한 구간만 바꾸는 방법.
- 제3자 소재(폰트, 사용자 소재, 곡)의 출처와 라이선스. 사실에 관한 내용은 사용자가 한 번 더 확인하도록 알린다.

회고 결론과 검토 증거는 프로젝트의 `qa/review_log.md`에 저장하며, 이 제작 파일들과 함께 전달한다.

## 바닥선(모든 스타일이 지켜야 함)

1. **요구사항과 원고**: 필수 정보는 확정되어야 한다. 영상은 20분을 넘을 수 없다. TTS 원고는 반드시 사용자에게서 나와야 한다. 길이가 맞지 않으면 확인이 필요하며, 임의로 원고를 고치거나, 자르거나, 속도를 바꾸지 않는다.
2. **사실 정확성**: 제품 기능, 숫자, 이름은 사용자나 믿을 만한 출처에서만 가져오며, 확실하지 않은 것은 표시한다.
3. **글자 가독성**: 휴대폰 크기에서도 글자 크기가 읽히고, 다 읽을 수 있을 만큼 화면에 머문다(craft.md 7절 참고). 글자는 넘치거나, 겹치거나, 가려지지 않는다.
4. **소재의 사용 권한**: 로고, 스크린샷, 폰트, 곡 모두 사용할 수 있어야 하며, 전달할 때 목록으로 밝힌다.
5. **기술 정확성**: 결정적 렌더링, 기술 검사 전부 통과, 검은 프레임 없음, 끝이 갑자기 끊기지 않을 것(마무리 정지 또는 끊김 없는 루프).
6. **스타일 일관성**: 선택한 스타일 규칙을 처음부터 끝까지 지키며, brief의 금지 목록에 빠지지 않는다.

그 밖에, 샷이 얼마나 움직이는지, 스프링을 쓸지, 효과음 밀도, 리듬의 빠르기는 모두 스타일과 내용에 따라 정한다(references/styles/ 및 craft.md 참고).
