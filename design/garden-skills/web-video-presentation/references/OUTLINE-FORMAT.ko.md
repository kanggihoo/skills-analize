# `outline.md` 형식 명세

영상 챕터 계획을 담는 산출물입니다. **사용자가 직접 편집할 수 있으므로** JSON / YAML 대신 Markdown을 사용해 사람이 읽고 고치기 쉬운 형식으로 작성해야 합니다.

중요: 이 파일을 읽은 다음에는 웹 결과물의 실제 요구사항을 파악하기 위해 [`CHAPTER-CRAFT.md`](CHAPTER-CRAFT.md) 전체를 계속 읽은 뒤 outline 작성을 시작해야 합니다.

> ## ⚠️ outline은 개발 계획이지 시각 계획이 아닙니다
>
> outline은 **리듬 + 내용 + 정보 밀도**만 계획합니다.
>
> - 챕터 구분 / 챕터별 step 수 / 각 step의 예상 시간
> - 각 step의 화면 내용(hero / 문구 / 데이터 / 목록 항목)
> - `article`에서 가져온 숫자 / 인용 / 사례 / 레이블로 구성한 챕터 단위 **정보 풀**
>
> **outline의 step 수는 초기 예상치입니다.** 최종 step 수는 챕터를 구현할 때 `narrations.ts`를 기준으로 합니다. 이 파일은 step 수와 오디오 합성의 기준이기도 합니다([`CHAPTER-CRAFT.md`](CHAPTER-CRAFT.md)의 “코드 계층의 최소 제약”과 [`AUDIO.md`](AUDIO.md) 참고). 구현된 챕터의 step 수가 outline과 다르면 outline을 맞춰 고치면 됩니다. 숫자를 억지로 완전히 일치시킬 필요는 없습니다.

> **outline 작성 전 필독**(두 출처 원칙, [`CHAPTER-CRAFT.md` Part 0 원칙 10](CHAPTER-CRAFT.md#10-双源原则scriptmd-定节拍--articlemd-定画面密度)):
>
> - **`script.md`** — **박자**를 정합니다. `---`로 박자를 나누고, 박자마다 1~2 step과 예상 시간을 둡니다.
> - **`article.md`**(있는 경우) — **화면 정보 밀도**를 정합니다. 각 챕터의 첫 단락에서 **정보 풀**을 추출합니다.

---

## 추상 예시(형식 확인용)

````markdown
# Video Outline

> **주제**: `<theme-id>` (Checkpoint Plan에서 선택 완료) — <한 문장으로 설명하는 스타일>
> **전체 길이**: 약 <T>분 <S>초 (내레이션 ~<X>자 ÷ 초당 4자)
> **챕터 수**: <N>개 챕터 / <M>개 step

---

## 1. <chapter-id> — <챕터 제목>(<S> steps · ~<T>s)

**정보 풀**(chapter agent가 필요에 따라 보조 레이블 / 부제 / pull-quote / mono cue로 표시):
- <유형: 숫자 / 인용 / 출처 / 사례 / 의미 / 시간 / 비교 / ...>: <내용> — <출처 article §X / Lxx>
- ...

**개발 계획**:

- step 1 (~Ts) — <화면 내용>
- ...

내레이션 발췌:
> <script.md의 전체 원고 중 1~3문장 발췌>

---

## 2. <chapter-id> — ...
````

> **길이 표기**: outline에는 음성과 화면을 맞추기 위한 step별 내레이션 예상 길이 `(~Ts)`만 씁니다. 애니메이션 길이 / 시차 / keyframe 수치는 **절대 쓰지 않습니다.** 이 내용은 챕터 개발 단계에서 결정합니다([`CHAPTER-CRAFT.md`](CHAPTER-CRAFT.md) Part 3의 길이 참고 자료).

> **구체적인 예시 보기**:
> - 후크형 오프닝 구조 → [`EXAMPLES/hook-chapter/`](EXAMPLES/hook-chapter/)
> - 목록형 챕터 구조 → [`EXAMPLES/list-reveal/`](EXAMPLES/list-reveal/)
> - 기술 리뷰(실사용 / 비교 / 벤치마크) → [`EXAMPLES/case-tech-review/`](EXAMPLES/case-tech-review/)

## 필드 규칙

### 상단 metadata block

전체 규모를 빠르게 파악할 수 있도록 인용 블록(`>`) 형태로 씁니다.

| 필드 | 필수 | 설명 |
|---|---|---|
| **주제** | ✓ | Checkpoint Plan에서 먼저 선택해야 합니다. chapter agent는 주제의 색상 / 글꼴 토큰을 따릅니다. 애니메이션 / 리듬 / 시각적 표현은 챕터에서 자유롭게 정합니다. |
| **전체 길이** | ✓ | 내레이션 길이 예상치(중국어 기준 분당 약 250자) |
| **챕터 수** | ✓ | `N개 챕터 / M개 step` |

### 챕터 제목: `## N. <id> — <title>(<S> steps · ~<T>s)`

| 부분 | 규칙 |
|---|---|
| `N` | 1부터 시작하는 순서이며 `chapters.ts`의 등록 순서와 일치해야 합니다. |
| `<id>` | **소문자 + 하이픈**. React `key`, 폴더명(`src/chapters/0N-<id>/`), 오디오 하위 디렉터리(`public/audio/<id>/`)가 됩니다. |
| `<title>` | 사람이 읽는 중국어 제목입니다. React 코드에는 들어가지 않습니다. |
| `<S> steps` | 해당 챕터의 전체 step 수 |
| `~<T>s` | 해당 챕터에서 말하는 데 걸리는 총 예상 시간(중국어 기준 초당 약 4자) |

유효한 id: `coldopen`, `hook`, `why-good`, `why-good-text-render`.
유효하지 않은 id: `why_good`(하이픈 사용), `Hook`(소문자가 아님), `第一章`(라틴 문자가 아님).

### 챕터 첫 단락의 “정보 풀”(**두 출처 원칙을 적용하는 핵심**)

각 챕터마다 `article.md`에서 추출한 세부 정보 모음을 따로 적습니다. **chapter agent가 각 step 화면을 구현할 때 필요에 따라 가져다 쓸 수 있습니다.** 오른쪽 아래의 모노 보조 표기 / 작은 부제 / pull-quote / 데이터 오버레이로 표현할 수 있습니다.

#### 정보 풀 항목 형식

```
- <유형>: <구체적인 내용> — <출처 article §X / Lxx 또는 간단한 출처 설명>
```

> **article 없이 사용자가 script만 제공한 경우**: 정보 풀은 “화면 정보 밀도를 적극적으로 설계”하는 것으로 바뀝니다. 숫자 / 비교 / 메타데이터 등을 활용해 화면이 내레이션보다 더 많은 정보를 담도록 합니다. “article에서 가져온 항목” 대신 “화면 장식 요소 풀”을 작성할 수 있습니다.

### Step 목록: 각 step은 **한 줄**

```
- step N (~Ts) — <화면 내용>
```

| 규칙 | 이유 |
|---|---|
| `step N`은 1부터 시작 | agent 구현 시 `if (step === N - 1) ...` 형태를 씁니다(0부터 세므로 차이에 유의). |
| **`(~Ts)` 필수** | `script.md`에서 이 step에 대응하는 내레이션 단락의 글자 수를 4로 나눠 예상합니다(중국어 기준 초당 약 4자). 범위는 3~10초입니다. |
| **화면 내용** | 이 단계에서 무대에 무엇이 보이는지 한 문장으로 설명합니다: hero / 문구 / 데이터 / 장식 요소. **한 줄 이하**로 작성하고, 더 길면 step을 나눕니다. |
| **애니메이션은 쓰지 않음** | 구체적으로 고정하면 내용을 옮겨 적는 번역기처럼 되어 버립니다(문서 상단 안내 참조). |
| **지속 시간 수치 / 시차는 쓰지 않음** | 챕터 개발 단계에서 정합니다. |
| **구현 방법은 쓰지 않음** | filter / SVG / Canvas 선택은 chapter agent가 맡습니다. |

### 내레이션 발췌(각 챕터 끝, 선택 사항이지만 권장)

1~3문장으로 압축합니다. **전체 대본을 넣지 말고**, 계획 단계에서 “이 챕터가 무엇을 다루는지” 확인할 수 있게 합니다. 전체 원문은 `script.md`에 둡니다. `outline.md`의 각 챕터는 `script.md`에서 주제가 명확히 바뀌는 부분 사이의 단락에 해당합니다.

> 오디오 합성([`AUDIO.md`](AUDIO.md))은 전체 텍스트를 나누기 위해 `script.md`를 다시 확인합니다. outline의 발췌문은 사용하지 않습니다.

## 이름 규칙 빠른 참조

| 대상 | 규칙 | 예시 |
|---|---|---|
| 챕터 id | 소문자 + 하이픈 | `coldopen`, `why-good` |
| 챕터 폴더 | `0N-<id>` | `src/chapters/01-coldopen/` |
| 챕터 컴포넌트 | PascalCase | `Coldopen.tsx`, `WhyGood.tsx` |
| 챕터 CSS 클래스 접두어 | 챕터 약칭(챕터 사이 충돌 방지) | `.cd-` / `.wg-` / `.mg-` |
| 오디오 하위 디렉터리 | `<id>/` | `public/audio/coldopen/` |
| 오디오 파일 | `<step-N>.mp3`(1부터 시작) | `public/audio/coldopen/1.mp3` |

## 챕터 구분 경험칙

- **챕터마다 3~8 step**. 3개 미만이면 내용이 빈약하고, 8개를 넘으면 시청자가 챕터의 핵심을 잊기 쉽습니다.
- 전체 길이 ÷ 30초 ≈ 챕터 수(한 챕터는 대략 30~60초 안에 설명합니다.)
- **챕터 하나에 초점 주제 하나**. “왜 강한가 + 어떻게 쓰는가”는 한 챕터가 아니라 두 챕터입니다.
- **챕터 경계는 내레이션에서 화자가 어조나 주제를 바꾸는 지점**입니다. `script.md`를 읽다가 “흠, 다음 부분으로 넘어가자”고 무의식적으로 생각하는 곳이 챕터 경계입니다.
- `midnight-press` / 영화 같은 오프닝처럼 느린 장면과 긴 숏을 쓰는 테마는 챕터마다 2~3 step까지 줄일 수 있습니다. 기술 리뷰 / 비교표처럼 정보가 조밀하면 8~10 step까지 늘릴 수 있습니다.

## 자체 검토(outline 작성 후 **필수**, 건너뛰지 말 것)

> ⚠️ **필수 절차**: outline을 작성한 다음 자체 검토 → 수정 → 제출의 세 단계를 반드시 거쳐야 합니다. 검토 없이 곧바로 Checkpoint Plan으로 넘어가 사용자와 조율하지 마세요.
>
> **역량에 따라 다음 순서로 진행**:
>
> 1. **Agent Teams 우선**: 독립된 reviewer agent를 열고 `outline.md` + 이 절의 검토 목록 + `script.md` / `article.md` 경로를 전달합니다. reviewer가 항목마다 확인하고 실패한 항목과 근거를 보고하게 합니다.
> 2. **다음은 subAgent**: Teams는 쓸 수 없지만 subagent를 열 수 있으면 동일한 절차를 진행합니다.
> 3. **둘 다 쓸 수 없음**: 직접 항목별로 엄격하게 확인합니다.
>
> 검토 결과를 받은 뒤 실패 항목을 먼저 고치고 Checkpoint Plan으로 넘어갑니다.

- [ ] 모든 step이 **화면 내용을 설명하는 한 문장**이며 “애니메이션” 행이나 “기법” 행이 없음
- [ ] step에 구체적인 밀리초 / 초 수치가 없음(`(~Ts)` 내레이션 예상 시간은 예외)
- [ ] 각 챕터 첫 단락에 “정보 풀” 블록이 있고, `article`에서 추출한 항목이 최소 3개 있으며 **모든 항목에 출처 표기**가 있음(`— 출처 article §X / Lxx`). 표기가 없으면 chapter agent가 원문을 찾을 수 없습니다.
- [ ] 모든 step의 `(~Ts)`를 더한 값이 상단의 전체 길이와 대략 일치(오차 < 10%). 맞지 않으면 리듬 계획이 부정확한 것입니다.
- [ ] 챕터 구분이 경험칙(챕터마다 3~8 step / 초점 주제당 30~60초)에 맞음
- [ ] 마지막 “소재 목록”을 챕터별로 나누고 ✓ / ⚠️ 표시가 명확함
- [ ] 대본에는 제목이나 번호처럼 내레이션이 아닌 내용이 없어야 하며, 사람이 자연스럽게 읽는 내용만 포함함

마지막으로 확인합니다. **outline이 chapter agent가 바로 작업을 시작할 만큼 구체적이면서도, 설계 여지는 남겨 두고 있나요?** 그렇다면 적절합니다. 너무 비어 있어 애니메이션을 고를 수 없다면 보완해야 합니다.
