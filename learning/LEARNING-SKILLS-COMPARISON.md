# 학습·교육 스킬 비교 분석

`learning/` 아래 스킬 3개(dbs-learning, learning-medusa, teach)의 SKILL.md와 딸린 파일을 읽고, 각 스킬이 어떻게 동작하는지, 장단점과 부족한 점이 무엇인지 정리한 문서다.

- dbs-learning은 중국어 원문, 나머지는 영어 원문을 기준으로 분석했다.
- 실제로 실행해 보지는 않았다. 문서에 적힌 동작만 분석했다.

---

| 스킬 | 출처 | 파일 구성 | 산출물 | 상태 저장 | 호출 방식 |
|---|---|---|---|---|---|

| 축 | dbs-learning | learning-medusa | teach |
|---|---|---|---|
| 무엇을 가르치나 | 아무 주제 | Medusa 하나 (고정 커리큘럼) | 아무 주제 |

## 2. dbs-learning

### 2.1 동작 방식

하나의 주제를 연속된 글로 쪼개고, 사용자가 각 글 끝에 적은 피드백을 읽어 다음 글의 깊이와 각도를 정한다. 스킬은 이것을 "적응형 학습 경사"라고 부른다.

1. **주제 확인 (Phase 1)**: 주제가 없으면 묻는다.
2. **저장 위치 결정**: 사용자 지정 → 현재 디렉터리가 프로젝트(`.git`, `README.md`, `package.json` 등 존재)면 `学习课题/{주제}/` → `~`, `~/Desktop` 같은 범용 디렉터리면 `~/Documents/dbskill-learning/{주제}/`.
3. **지식 기반 확인 (Phase 1.5, 새 주제만)**
   - 프로젝트 안에서 주제 관련 자료를 가볍게 찾는다. `AGENTS.md`, `README.md` 같은 색인부터 읽고, 전체를 훑지 않는다.
   - `.env`, 키, 고객 자료 같은 민감 파일은 건너뛴다.
   - 찾은 자료를 증거 강도로 나눈다. 사용자가 직접 쓴 글은 강한 증거, AI 초안은 약한 증거, 제3자 자료는 증거 아님.
   - 3~5줄로 요약하고 "프로젝트 기반 / 처음부터 / 지정 자료" 중 고르게 한 뒤 **멈춘다**. 이때는 아무 파일도 만들지 않는다.
   - 관련 자료가 없으면 묻지 않고 바로 처음부터 시작한다.
4. **파일 생성**: `00-学习计划.md`(학습 목표, 지식 기반, 진도, 경로, 피드백 요약 표), `01.md`, `assets/`, `INDEX.md`.
5. **다음 글 (Phase 2~4)**
   - 학습계획과 가장 최근 글을 읽고, 글 끝 "学习反馈" 영역에서 **템플릿 문구를 걸러낸** 실제 피드백만 뽑는다.
   - 피드백 신호에 따라 다음 글을 조정한다.

| 피드백 신호 | 다음 글 |
|---|---|
| 이해 못 함, 질문 많음 | 추상도를 낮추고 예시를 늘린다 |
| 이해했지만 재미없음 | 각도를 바꿔 실제 문제와 연결한다 |
| 응용 질문 | 사례와 판단 방법을 늘린다 |
| 확실히 이해함 | 개념 밀도를 올린다 |
| 구체적 질문 | 질문부터 답한다 |
| 피드백 적음 | 난이도 유지, 작게 전진 |

6. **글 형식 고정**: 이 글이 풀 문제 → 본문 → 요약 3~5줄 → 다음 글 예고 → 피드백란(질문 4개).
7. **문체 규칙**: 항상 중국어. "A가 아니라 B다", "진짜 ~는 ~다" 같은 대조 문형을 금지한다. 독자의 오해를 전제하는 말투("당신은 ~라고 생각했겠지만")도 금지한다.
8. **경계**: 비즈니스 진단이나 단일 글 대필은 하지 않는다. 범위를 벗어나면 한 줄로 안내하고 `/dbs`를 추천한다.

### 2.2 장점

- **피드백 루프가 파일에 남는다.** 사용자가 글을 읽고 같은 파일에 피드백을 쓰면, 다음 세션이 그것을 읽는다. 세션이 끊겨도 맥락이 이어진다.
- **피드백 → 조정 규칙이 표로 명확하다.** 모델이 "어떻게 다음 글을 쓸지"를 즉흥적으로 정하지 않는다.
- **템플릿 문구를 피드백으로 오인하지 않게 막았다.** 실제로 자주 생기는 실수를 정확히 짚었다.
- **지식 기반 판단이 신중하다.** "파일에 개념이 나왔다 = 안다"로 보지 않고, 증거 강도를 나눈다. AI 초안과 제3자 자료를 사용자 지식으로 착각하지 않는다.
- **민감 파일 경계가 명시돼 있다.** 프로젝트를 뒤질 때 `.env`나 고객 자료를 읽지 않고, 요약에도 경로를 노출하지 않는다.
- **수용 테스트(验收用例)가 있다.** 상황 6개별로 "반드시 해야 할 것"이 적혀 있어 스킬이 제대로 도는지 확인하기 쉽다.

### 2.3 단점과 부족한 점

- **중국어 고정.** "永远使用中文" 규칙 때문에 한국어 사용자는 그대로 쓸 수 없다. 금지 문형 목록도 중국어 문형이라 번역하면 의미가 흐려진다.
- **수동적인 학습.** 글을 읽고 소감을 적는 구조라 인출 연습, 퀴즈, 실습이 없다. "이해했다"는 사용자의 자기 평가만 믿는다. 실제로 이해했는지 확인할 장치가 없다.
- **피드백을 파일에 직접 써야 한다.** 에디터로 md 파일을 열어 쓰는 수고가 들고, 안 쓰면 루프가 멈춘다. 대화로 받은 피드백을 파일에 옮겨 적는 절차도 없다.
- **간격 반복이 없다.** 앞에서 배운 개념을 다시 꺼내 보게 하는 장치가 없어 장기 기억 형성은 운에 맡긴다.
- **지식 출처 검증이 없다.** 본문을 모델 지식으로 쓴다. 인용이나 출처 요구가 없어서 틀린 내용이 그대로 강의가 될 수 있다.
- **학습 목표가 검증 가능하지 않다.** 학습계획에 "검사 가능한 능력으로 쓴다"고만 하고, 그 능력에 도달했는지 확인하는 단계가 없다. 언제 주제가 끝나는지 기준도 없다.
- **dbskill 생태계 의존.** 마지막 안내가 `/dbs` 설치를 전제로 한다. 단독으로 쓰면 이 부분은 쓸모가 없다.
- **디렉터리 이름이 중국어.** `学习课题/`, `00-学习计划.md` 같은 경로가 프로젝트 안에 생긴다.

## 3. learning-medusa

### 3.1 동작 방식

Claude가 "코딩 부트캠프 강사"가 되어, 사용자와 함께 Medusa에 **브랜드 기능**을 직접 만들면서 아키텍처를 가르친다. 커리큘럼이 처음부터 끝까지 정해져 있다.

1. **인사와 안내**: 레슨 3개, 총 2~3시간이라고 알린다.
2. **사전 점검**: Medusa 프로젝트가 있는지, 개발 환경이 준비됐는지, 시간을 낼 수 있는지 묻는다.
3. **레슨 3개 진행**

| 레슨 | 만드는 것 | 배우는 아키텍처 | 체크포인트 |
|---|---|---|---|
| 1. 커스텀 기능 | Brand Module → createBrandWorkflow → `POST /admin/brands` | Module → Workflow → API Route 계층, 보상(롤백) 함수 | module, workflow, api-route |
| 2. Medusa 확장 | 브랜드-상품 Module Link, `productsCreated` 훅, `GET /admin/brands` | 모듈 격리, 워크플로 훅, Query | module-links, workflow-hooks, querying |
| 3. 관리자 화면 | 상품 페이지 위젯, 브랜드 목록 UI Route | 위젯 vs UI Route, React Query, JS SDK | widget, ui-route |

4. **각 단계는 I Do → We Do → You Do**
   - I Do: 개념의 What / Why / How를 ASCII 다이어그램과 함께 설명한다.
   - We Do: 명령과 코드를 한 단계씩 같이 친다.
   - You Do: 개념 질문, 코드 리뷰, 빌드·cURL 테스트.
5. **체크포인트 검증 (5단계)**: 검증 질문 → 사용자 코드 공유받아 리뷰 → 같이 테스트 → 에러 진단 → 확인될 때까지 다음으로 넘어가지 않는다. 체크포인트 파일에는 `<details>`로 접힌 정답이 들어 있다.
6. **에러 처리**: 에러를 "가르칠 기회"로 본다. 절대 건너뛰지 않는다. `troubleshooting/common-errors.md`를 읽고, 진단 질문을 하고, 원인을 설명하고, 다시 테스트한다.
7. **범위 밖 질문**: MedusaDocs MCP의 `ask_medusa_question` 도구로 최신 문서를 찾아, 지금 만드는 기능에 맞춰 풀어 설명한다.
8. **세션 관리**: 레슨이 끝날 때마다 git 커밋을 권한다. 재개할 때는 코드를 보고 진도를 판단한다. 건너뛰기를 원하면 의존 관계를 설명하고 기존 코드를 보고 판단한다.

### 3.2 장점

- **실제로 돌아가는 결과물이 남는다.** 3시간 뒤에 브랜드 기능이 붙은 Medusa 프로젝트가 생긴다. 배운 것이 코드로 증명된다.
- **검증 게이트가 엄격하다.** "질문에 맞게 답함 + 코드 정상 + 테스트 통과 + 사용자 확인" 네 가지가 다 돼야 넘어간다. 이해 못 한 채로 진도만 나가는 일을 막는다.
- **참고 자료가 풍부하다.** 레슨 본문, 체크포인트, 아키텍처 심화, 문제 해결 문서가 약 8,500줄이다. 필요한 순간에만 읽도록(점진적 로딩) 나눠 놓았다.
- **에러를 교재로 쓴다.** 초보자가 가장 많이 막히는 지점을 피하지 않고 다룬다. 자주 나는 에러를 범주별로 미리 정리해 두었다.
- **Why를 꼭 가르친다.** 컴포넌트마다 What / Why / How를 설명하게 해서, 따라 치기만 하는 튜토리얼이 되지 않게 했다.
- **최신 정보 경로가 있다.** 동봉 문서가 낡아도 MCP로 최신 문서를 찾을 수 있다.

### 3.3 단점과 부족한 점

- **Medusa 전용.** 다른 주제에는 쓸 수 없다. 구조(체크포인트, I Do/We Do/You Do)만 가져올 수 있다.
- **진도가 저장되지 않는다.** 인사말에서 "어디까지 했는지 기억하겠다"고 약속하지만, 실제로는 진도 파일이 없다. 재개할 때 코드를 보고 추측한다. 어떤 체크포인트 질문을 통과했는지, 어떤 개념에서 막혔는지는 사라진다.
- **MCP 설치 안내가 없다.** MedusaDocs MCP를 쓰라고 하지만, 서버가 없을 때 어떻게 할지 적혀 있지 않다. 없으면 모델 지식으로 답할 가능성이 크다.
- **원칙끼리 충돌한다.** 프로토콜은 "먼저 설명(I Do)"인데, 교육 원칙 5번은 "먼저 만들고 나중에 이해한다"다. 어느 쪽을 따를지 모델이 매번 판단해야 한다.
- **버전 고정 위험.** 코드 예시가 특정 Medusa 버전 기준이다. Medusa가 바뀌면 레슨 코드가 깨지는데, 버전 확인 단계가 없다.
- **간격 반복이 형식적이다.** "레슨 3에서 모듈을 간단히 언급한다" 수준이다. 실제 인출 연습이라고 보기 어렵다.
- **말투가 과하다.** "Great question!", "Error messages are great teachers!" 같은 고정 문구가 예시로 박혀 있어, 그대로 따라 하면 반복적이고 가식적으로 들린다.
- **2~3시간 한 번에 하는 설계.** 레슨당 45~60분이라 중간에 끊기 쉬운데, 레슨 중간 지점에서 재개하는 방법이 없다.
- **정답이 체크포인트 파일에 같이 있다.** 모델이 질문하고 바로 정답을 읽기 쉬워서, 사용자가 답하기 전에 힌트를 흘릴 위험이 있다.

## 4. teach (mattpocock)

### 4.1 동작 방식

현재 디렉터리를 **학습 워크스페이스**로 보고, 여러 세션에 걸쳐 한 주제를 가르친다. 학습 상태를 파일 7종으로 관리한다. `/teach`로만 호출된다.

1. **워크스페이스 파일**

| 파일 | 역할 | 형식 문서 |
|---|---|---|
| `MISSION.md` | 왜 배우는지 (현실 목표, 성공 기준, 제약, 범위 밖) | MISSION-FORMAT.md |
| `RESOURCES.md` | 신뢰할 수 있는 자료 목록 (Knowledge / Wisdom) | RESOURCES-FORMAT.md |
| `learning-records/0001-*.md` | 실제로 배운 것 (ADR처럼 짧은 기록) | LEARNING-RECORD-FORMAT.md |
| `lessons/0001-*.html` | 레슨 1개 = HTML 1개 | (SKILL.md 본문) |
| `reference/*.html` | 치트시트, 용어집 등 압축 참고자료 | GLOSSARY-FORMAT.md (용어집) |
| `assets/*` | 레슨이 공유하는 스타일시트, 퀴즈 위젯 등 | (SKILL.md 본문) |
| `NOTES.md` | 사용자 선호 메모 | 없음 |

2. **흐름**
   - `MISSION.md`가 없거나 흐릿하면 **먼저 왜 배우는지 인터뷰한다**. 미션 없이 가르치지 않는다.
   - `RESOURCES.md`가 비어 있으면 **신뢰 자료부터 찾는다**. "모델 지식을 절대 믿지 말라"가 원칙이다.
   - `learning-records`를 읽어 **근접발달영역(ZPD)**, 즉 "딱 적당히 어려운" 다음 주제를 고른다.
   - `assets/`를 먼저 읽고 기존 컴포넌트로 레슨을 만든다. 새로 필요한 건 재사용 가능한 컴포넌트로 `assets/`에 추가한다.
   - 레슨 HTML을 만들고 가능하면 CLI로 연다.
3. **레슨 규칙**
   - 짧고 금방 끝나야 한다(작업 기억 한계). 대신 확실한 성취 하나를 준다.
   - Tufte 스타일로 아름답게. 다른 레슨과 참고자료에 링크한다.
   - 주장마다 외부 출처를 인용하고, 최고의 1차 자료 하나를 추천한다.
   - "모르는 건 에이전트에게 물어보라"는 안내를 넣는다.
4. **학습 이론**
   - **유창성 강도 vs 저장 강도**를 구분한다. 당장 떠오르는 것은 착각일 수 있고, 목표는 장기 기억이다.
   - 지식 습득에서 난이도는 적이고, 기술 습득에서 난이도는 도구다.
   - 인출 연습, 간격 두기, 교차 연습(기술 연습에만)을 쓴다.
   - 퀴즈는 선택지 길이를 똑같이 맞추고, 정답 위치를 섞는다. 형식으로 답을 흘리지 않는다.
5. **지혜(Wisdom)**: 실전 경험이 필요한 질문은 일단 답하되, 결국 평판 좋은 **커뮤니티**(포럼, 서브레딧, 오프라인 수업)로 보낸다. 사용자가 원치 않으면 존중한다.
6. **학습 기록 규칙**: "다뤘다"는 기록하지 않는다. 증거가 있을 때만 쓴다. 이해를 보여 줬을 때, 사전 지식을 밝혔을 때, 오해를 바로잡았을 때, 미션이 바뀌었을 때. 틀린 기록은 지우지 않고 `superseded`로 표시한다.

### 4.2 장점

- **학습 과학에 가장 충실하다.** 유창성 vs 저장 강도, 바람직한 어려움, 인출 연습, 간격 두기, 교차 연습, ZPD를 모두 명시한다. 세 스킬 중 이론적 기반이 가장 탄탄하다.
- **미션이 모든 결정의 기준이다.** "왜 배우는가"가 없으면 수업을 시작하지 않는다. 레슨이 추상적으로 흐르는 것을 막는다.
- **학습 기록 기준이 엄격하다.** "다룬 것 ≠ 배운 것"을 분명히 한다. 기록이 일지로 부풀지 않고, 다음 수업 결정에 쓰이는 정보만 남는다.
- **모델 지식을 믿지 않는다.** 외부 신뢰 자료를 먼저 찾고, 레슨에 인용을 단다. 환각을 강의로 만드는 위험이 가장 낮다.
- **남는 자료가 좋다.** 레슨은 다시 안 봐도 참고자료(치트시트, 용어집)는 다시 본다는 점을 짚어, 둘을 나눠 만든다. 인쇄하기 좋은 HTML이다.
- **컴포넌트 재사용.** 공유 스타일시트와 위젯이 쌓여서 레슨이 하나의 강좌처럼 보인다.
- **주제를 가리지 않는다.** 물리학, 요가, 프로그래밍 모두 예시로 든다. 지식형 주제와 기술형 주제를 구분해 다르게 다룬다.
- **용어집 규칙이 세밀하다.** 사용자가 이해한 용어만 올리고, 동의어 중 하나를 고르고, 정의 안에서도 용어집 용어를 쓴다.

### 4.3 단점과 부족한 점

- **퀴즈 결과가 에이전트에게 돌아오지 않는다.** 퀴즈와 피드백 루프는 브라우저 HTML 안에서 돈다. 사용자가 몇 문제를 틀렸는지 에이전트가 알 방법이 없다. 그래서 learning-records는 대화에서 얻은 증거에만 의존한다. 가장 큰 구멍이다.
- **간격 반복에 일정이 없다.** 간격 두기를 하라고 하지만, 언제 무엇을 복습할지 기록하는 필드(날짜, 다음 복습일)가 없다. 사용자가 다시 `/teach`를 부르지 않으면 복습도 없다.
- **초기 비용이 크다.** 첫 세션에 미션 인터뷰, 자료 조사, 스타일시트 제작, 레슨 HTML 제작까지 한다. 웹 검색과 HTML 생성 토큰이 많이 든다.
- **용어집 위치가 문서마다 다르다.** SKILL.md는 용어집을 `reference/*.html`의 하나로 설명하고, GLOSSARY-FORMAT.md는 `GLOSSARY.md`(마크다운)를 정의하고 LEARNING-RECORD-FORMAT.md도 `GLOSSARY.md`를 참조한다. SKILL.md의 워크스페이스 파일 목록에는 GLOSSARY.md가 없다.
- **`NOTES.md`만 형식이 없다.** 나머지는 형식 문서가 있는데 이것만 자유 형식이다.
- **"아름다운 HTML"의 기준이 모호하다.** "Think Tufte" 한 줄뿐이다. 디자인 품질은 모델 역량에 맡긴다.
- **한 워크스페이스 = 한 미션.** 주제마다 디렉터리를 따로 만들어야 한다. 여러 주제를 한곳에서 관리할 색인이 없다.
- **레슨 순서를 보여 주는 지도가 없다.** ZPD로 다음 레슨을 고르지만, 전체 경로(앞으로 무엇을 배울지)를 사용자에게 보여 주는 문서가 없다. dbs-learning의 학습계획 같은 것이 빠져 있다.

## 7. 정리

### 7.1 용도별 추천

| 상황 | 추천 |
|---|---|
| 새 분야를 몇 주에 걸쳐 깊게 배우고 싶다 | **teach** (mattpocock) |
| 특정 프레임워크를 손으로 만들며 배우고 싶다 | **learning-medusa** 방식 (Medusa라면 그대로) |
| 글 읽기 중심으로 주제를 천천히 따라가고 싶다 (중국어 가능) | **dbs-learning** |

### 7.2 스킬마다 가져올 만한 것

| 스킬 | 가져올 것 | 버릴 것 |
|---|---|---|
| dbs-learning | 피드백 신호 → 다음 글 조정 표, 템플릿 문구 걸러내기, 지식 기반 증거 강도 분류, 민감 파일 경계, 수용 테스트 형식, 학습계획(전체 경로) 문서 | 중국어 고정, 중국어 금지 문형, `/dbs` 의존, 수동적 글 읽기만 하는 구조 |
| learning-medusa | 체크포인트 5단계 게이트, I Do → We Do → You Do, What/Why/How 설명 틀, 에러를 교재로 쓰는 절차, 참고 파일 점진 로딩 | 진도 저장 없음, 과장된 고정 멘트, 원칙 충돌, 정답이 질문과 같은 파일에 있는 구조 |
| teach | 미션 우선, 유창성 vs 저장 강도, ZPD, "다룬 것 ≠ 배운 것" 학습 기록 기준, 신뢰 자료 + 인용, 레슨/참고자료 분리, 용어집 규칙 | 퀴즈 결과가 돌아오지 않는 구조, 용어집 위치 불일치 |

### 7.3 세 스킬 모두에 부족한 것

- **실제 간격 반복 일정.** 어느 스킬도 "언제 무엇을 복습할지" 날짜로 관리하지 않는다. 복습 예정일을 학습 기록에 넣으면 해결된다.
- **학습 결과 측정.** 퀴즈 점수나 정답률이 에이전트에게 다시 들어오는 경로가 없다. teach의 HTML 퀴즈 결과를 파일로 저장하거나, 대화에서 문제를 내는 방식이 필요하다.
- **한국어 지원.** 둘은 영어, 하나는 중국어 고정이다. 문체 규칙(금지 문형, 쉼표 규칙)도 원어 기준이라 한국어용으로 다시 써야 한다.
- **끝나는 기준.** "이 주제를 다 배웠다"를 판단하는 기준이 없다(learning-medusa는 3레슨 완료로 정해져 있어 예외). teach의 MISSION "Success looks like"를 체크리스트로 만들면 가까워진다.
