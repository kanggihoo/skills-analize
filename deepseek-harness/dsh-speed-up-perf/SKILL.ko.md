# DeepSeek Harness 속도 높이기

"더 빠르게 만들어 달라"는 넓은 요청을 재현 가능한 사용자 경로 측정과, 증거에 근거한 작은 수정으로 바꾼다. 이 스킬은 할당량이나 스크립트가 아니라 지침이다. 넓게 조사하고, 측정된 비용을 따라가며, 매력적이어도 실제 사용자가 돌리는 작업량을 개선하지 않는 변경은 거부한다.

## 범위와 현재 기준을 정한다

[AGENTS.md](../../../AGENTS.md), [architecture](../../../docs/architecture.md), [testing policy](../../../docs/testing.md), [defensive patterns](../../../docs/defensive-patterns/README.md)와 영향을 받는 패키지의 지침 및 Agent Note를 읽는다. process, clock, 브라우저 테스트, 비동기 정리에는 [CI test reliability](../dsh-ci-test-reliability/SKILL.md)를 쓴다.

사용자에게 보이는 최종 목표, 작업량 범위, 자원 제약, 허용되는 사소한 동작 차이, 중단 기준을 합의한다. 백엔드 측정과 브라우저 end-to-end 측정은 분리해서 유지한다. 빠른 history iterator나 Client fold는 빠른 transport, paint, 스크롤, 입력 응답을 증명하지 못한다. 로컬 오버헤드를 측정할 때는 모델과 네트워크 지연을 제외하고, 그 제외를 명시한다. 결과를 완전한 제품 지연 시간이라고 부르지 않는다.

실행 중인 checkout만 보지 말고 정확한 현재 base를 검사한다. 최종 병합된 diff, 소유 소스, 테스트, 해결된 리뷰 스레드를 읽는다. PR 본문은 버려진 구현을 설명할 수도 있다. 병합됨, 병합 없이 닫힘, 대체됨, 추정치, 새로 측정됨을 구분한다. [보관된 성능 워크플로 결정과 증거](../../notes/archived/process/2026-09-06-evidence-driven-performance-skill.md)는 과거의 단서일 뿐, 그 구현을 다시 들여올 권한이 아니다.

## 사용자 경로를 조사하고 후보를 순위 매긴다

독립된 영역은 넓이가 도움이 될 때 위임한다. 추측이 아니라 측정값과 실제 호출 지점을 요구한다. 유용한 영역은 다음과 같다.

- 콜드 profile 시작, 처음의 history 읽기, 현재 generation 재열기, 쓰기 가능한 재개.
- 턴이 많고 도구를 많이 쓰는 history, 큰 개별 메시지와 결과, 하위 Session 목록, Session 사이의 반복 이동.
- 초기 history transport와 fold, 처음 사용 가능한 브라우저 paint, 이전 페이지 로딩, 스크롤, 도구 펼치기, 비활성 뷰 활성화.
- 실시간 스트리밍과 재연결. 긴 활성 시도, 중간에 끼어든 도구 작업, 정산, 취소, teardown을 포함한다.

독립된 비용 요인을 달리한다. 바이트, 내구성 있는 이벤트, 압축된 레코드, 원시 delta, 턴, 도구, 자식, 보이는 DOM 노드는 서로 다른 양이다. 작은 동일 메시지가 많은 경우를 "현실적"이라고 부르기 전에, 그것이 어떤 사용자 작업을 자극하는지 확인한다. 꼬리 작업량(tail workload)과 전형적인 작업량을 모두 포함하되, 결정에 쓸모없는 조합 행렬은 만들지 않는다.

후보는 관찰된 사용자 지연 시간, CPU와 할당, 유지되는 메모리, 발생 빈도, 확신도로 순위를 매긴다. 각 후보마다 실제 소비자, 반복되는 작업, 예상 복잡도, 가장 작은 반증 가능한 개입, 유지되어야 하는 동작을 밝힌다. 의심스러운 루프, 쓰이지 않는 캐시, 큰 파일만으로는 병목의 증거가 되지 않는다.

## 현실적인 합성 벤치마크를 먼저 만든다

[benchmarks/AGENTS.md](../../../benchmarks/AGENTS.md)와 [performance-gate decision](../../notes/implemented/testing/2026-09-04-session-open-performance-gate.md)을 따른다. 경쟁하는 calibration이나 보고 인프라를 새로 만들지 말고, 기존의 필수 lane을 확장한다. 패키지 내부 진단은 그 소유자 옆에 둔다. 패키지를 가로지르는 필수 케이스는 측정하는 사용자 경로 아래 `benchmarks/`에 둔다.

사용자가 로컬 corpus 검사를 허가했다면, 집계된 작업량 특성만 추출한다. 프롬프트, 출력, 경로, 신원, ID, 자격 증명, 녹화, 알아볼 수 있는 조각을 fixture, 로그, 스크린샷, PR, 아티팩트에 복사하지 않는다. 고정 입력은 검토된 상수에서 생성한다. 어떤 벤치마크도 사용자의 home, 주변 저장소, 네트워크 서비스, 비공개 데이터에 의존하지 않는다.

구현 전에 측정 카드를 기록한다.

| 필드 | 필요한 결정 |
|---|---|
| 사용자 작업 | 정확한 행동과 외부에서 관찰 가능한 완료 조건 |
| 작업량 | 고정된 차원, 분포, 생성 seed/상수, 그리고 이것이 일반적인 사용과 꼬리 사용을 모두 자극하는 이유 |
| 진입 경로 | 제품 호출과 구성, 빌드된 아티팩트. 외부 경계는 mock 처리 |
| 시계 | 포함된 설정, 콜드/웜 상태, 타이밍 시작과 끝, 제외된 비용 |
| 메모리 | 도달 가능한 endpoint 객체, 기준선, GC 정책, 유지되는 것과 일시적인 것의 한계 |
| 판정 | 원시 샘플, 선택한 집계, 보정된 절대/비율/메모리 한계, negative control |
| 동작 | 소유 기능 테스트/스냅샷과 허용되는 사소한 차이 |

CPU worker는 plain Node에서 빌드된 JavaScript로 측정한다. source loader의 오버헤드와 모듈 해석은 실제 배포 경로가 아니다. 브라우저 케이스는 빌드된 제품 자산과 지원되는 `dsh` profile을 기존 테스트 harness를 통해 쓴다. 측정만을 위해 프로덕션 export를 추가하거나, 알고리즘을 "벤치마크 구현"으로 복사하지 않는다.

콜드 샘플과 프로세스 메모리 샘플에는 새 자식 프로세스와 비공개 임시 루트를 쓴다. 웜 샘플은 의도한 캐시를 명시적으로 유지한다. fixture 설정이 콜드 시나리오를 몰래 데우지 않게 한다. 양쪽에 같은 입력, 같은 검증, 같은 완료 조건, 같은 도달 가능한 출력을 준다. 파싱 후 버리기만 하는 기준선은 검증되고 유지되는 history와 비교할 수 없다.

모든 원시 샘플과 결과를 결정하는 집계를 보고한다. Node lane에는 기존의 공유 시간 calibration과 검토된 변동 여유를 쓴다. 바이트, 개수, 무차원 비율을 CPU 속도로 보정하지 않는다. 수동 브라우저 진단에는 임계값을 두지 않는다. 필수 브라우저 성능 케이스는 시간 예산을 채택하기 전에, 실제 CI 브라우저와 runner에서 명시적인 lane 결정과 반복 측정이 필요하다. Node 기계 배율만으로는 브라우저 calibration이 되지 않는다. 예산은 소스 상수이며 환경 변수로 override하지 않는다. 측정하는 작업은 다른 소유 CPU 집약 작업과 직렬화한다. 기준과 후보는 비슷한 조건에서 측정한다. 회귀를 숨기려고 예산을 넓히거나, 운 좋은 실행을 고르지 않는다.

end-to-end 지연 시간은 구성 요소의 단계별 시간과 독립적으로 측정한다. 의도된 객체가 여전히 도달 가능한 상태에서 유지 메모리를 추적한다. 일시적인 압박은 제한된 heap에서의 완료나 적절한 peak 측정으로 따로 본다. 유지량이 무제한인 채로 실행이 빨라졌다고 자동으로 이득이 되지 않는다.

브라우저 반응성을 보려면 실제 브라우저 입력을 쓰고, 그 결과로 생기는 UI 갱신을 관찰한다. 마지막 정지(stall)를 frame과 입력 측정에 포함한다. 예약된 timer와 실제 입력을 구별한다. 합성 producer에는 경계를 두어, catch-up 폭주가 다른 작업량을 만들어 내지 않게 한다. 첫 paint, 스크롤, 페이징, 실시간 갱신, 활성화되었지만 숨겨진 뷰가 다뤄졌는지 명시한다. Node fold, 가짜 DOM, 맞춤형 heartbeat 이벤트만으로는 브라우저 반응성을 입증할 수 없다.

## 회귀를 증명한 뒤 작업을 제거한다

제품 코드를 바꾸기 전에 최적화되지 않은 작업량을 먼저 실행한다. 명령, 리비전, 런타임과 플랫폼, fixture 차원, 원시 측정값, 판정을 저장한다. 실패하는 시나리오를 실제 병목을 여전히 자극할 만큼 줄인다. 그 뒤 패치하기 전에 반증 가능한 가설들의 순위를 매긴다. 프로파일, 할당 샘플, 작업 횟수, 단계별 시간으로 가설을 구별한다.

검토할 만한 흔한 패턴은 다음과 같다. 자동으로 처방되는 것이 아니다.

- 압축된 표현은 다운스트림 reader까지 압축된 채로 유지한다. 소비자가 확정된 내용이나 하나의 집계만 필요하다면 delta마다 객체를 만들지 않는다.
- 중복된 파싱, 복사, freeze, 검증은 실제 소유권과 신뢰 경계의 전환을 확인한 뒤에만 제거한다. 같은 프로세스 안의 타입이 있는 borrowing이 내구성 있거나 wire 파싱을 약화해도 된다는 허가는 아니다.
- 아티팩트 변환은 스트리밍으로 처리하고, 중간 상태를 제한한다. 모든 generation을 붙잡아 두지 않는다. 사용자 작업이 요구하는 경우 publication, 검증, 쓰기 준비 상태의 의무도 포함한다.
- 읽기 전용 준비 작업과 쓰기/publication 작업을 분리한다. 정확성에 필요한 endpoint를 넘어 기다리는 작업을 옮기지 않는다.
- 비활성 뷰와 접힌 상세 작업은 미룬다. 처음 활성화될 때의 비용과 유지되는 상태도 함께 측정한다. 미루는 것은 삭제가 아니며, 뷰포트 하이라이트는 완전한 가상화가 아니다.
- 식별자를 안정시키고 구독 범위를 좁혀서, 노드 하나가 바뀌었을 때 history 전체가 무효화되지 않게 한다. 업데이트 순서와 즉시 이벤트 동작을 보존한다.
- 반복적인 shift, scan, rebuild 대신 적절한 자료구조를 쓴다. 고립된 컨테이너 연산이 아니라 소비자 경로 전체를 측정한다.
- revision 키 기반의 재사용이나 singleflight는, 명시적인 무효화, 제한된 유지, 독립된 waiter 취소, disposal 소유권이 있을 때만 쓴다. 반복 벤치마크를 빠르게 보이게 하려고 확장된 표현을 캐시하지 않는다.

한 번에 인과 요인 하나만 바꾼다. 초점 시나리오와 그 상위 end-to-end를 모두 다시 실행한다. negative control을 요구한다. 강화된 assertion은 원래 구현이나, 목표 비용을 통제된 방식으로 다시 도입한 구현에서 실패해야 한다. 회귀를 놓칠 정도로 느슨한 임계값은 보호가 아니다. 검증된 noise floor 아래의 예산은 신뢰할 수 없다.

## 동작과 자원 소유권을 보존한다

성능 측정은 기능 증거를 보완할 뿐 대체하지 않는다. 출력, 순서, 페이징, stream 인덱스, 에러, 취소, 동시성, disposal에 해당하는 소유 테스트를 적용 범위에 맞게 실행하거나 추가한다. 모델에 보이는 것과 로그에 남는 것의 동등성, 릴리스된 generation의 불변성, 원자적 publication, 필수 검증, 쓰기 준비 상태를 보존한다. 숫자를 맞추려고 history를 조용히 자르거나, 도구 결과를 건너뛰거나, 생명주기 의미를 바꾸지 않는다.

의도한 사소한 가시적 차이는 명시하고, 소유 keyless 스냅샷으로 검증한다. 제품에 보이는 GUI 변경이라면 필요한 브라우저 증거나 GIF를 포함한다. 기능 기대치는 벤치마크 내부 구현과 무관하게 유지한다. 벤치마크 assertion은 실제 endpoint에 도달할 만큼의 증거만 가지면 된다. 두 번째 의미 테스트 모음이 되어서는 안 된다.

이득이 end-to-end에서 사라질 때, 전형적인 작업량이 눈에 띄게 악화될 때, 복잡도가 작은 이득보다 클 때, 취소, 유지, 내구성을 설명하고 테스트할 수 없을 때는 최적화를 거부한다. 거부한 가설은 범위를 넓혀 정당화하지 말고 짧게 기록한다.

## 경계가 있고 검토 가능한 결과를 낸다

지속되어야 할 근거, 대안, calibration, 제외, 남은 위험은 [Agent Note 규칙](../../notes/README.md)에 따라 기록한다. 관련 노트의 supersession을 확인하되, 성능 작업을 저장소 전체의 문장 정리 작업으로 바꾸지 않는다. 재사용할 절차는 이 스킬에 두고, 시나리오별 사실은 그 벤치마크나 패키지 소유자에게 둔다.

요청이 stacked PR이라면, 편집 전에 레이어를 정하고 공식 GitHub stack과 별도 worktree를 쓴다. 각 레이어는 단독으로 병합 가능해야 한다. 벤치마크 인프라는 측정 기준선을 보호할 수 있다. 최적화 레이어는 수정, 기능 커버리지, 더 엄격한 예산을 함께 가진다. 독립된 병목은 별도의 stack을 쓸 수 있다. 발견 사항은 상위로 옮기기 전에 소유 레이어에서 고친다.

[pre-push checks](../dsh-pre-push-checks/SKILL.md)를 적용하고, 실행한 증거만 보고한다. 로컬 타이밍이 러너 안정성을 증명한다고 가정하지 말고 CI를 확인한다. ready로 표시한 뒤에는 리뷰 발견 사항을 코드와 실행 가능한 증거에 비추어 평가한다. 이유나 수정으로 답하고, 처리한 스레드는 resolve한다. 봇이 보고했다는 이유만으로 보고를 기각하지 않는다.

각 결과는 다음 순서로 요약한다. 작업량 → 전후의 절대값과 비율 → endpoint와 메모리 의미 → 동작 증거 → negative control → 정확한 검사 → 제외 항목. 과거 작성자가 보고한 수치, 새로 한 로컬 측정, CI 증거를 구분한다. 합의된 시나리오와 수정 범위에서 멈추고, 관련 없는 기회를 쫓지 말고 짧은 순위 매긴 후속 목록만 남긴다.
