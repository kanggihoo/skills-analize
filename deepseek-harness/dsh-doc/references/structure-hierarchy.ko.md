# 페이지 구조와 계층

## 요약

각 페이지는 운영이나 구현의 깊은 내용을 보여 주기 전에, 처음 읽는 사람에게 짧은 진입점을 먼저 제공한다. 여러 패키지에 걸친 학습 자료와 엔지니어링 자료는 의도적으로 설계한 `docs/` 계층 아래에 두고, 패키지 계약(contract)은 코드 옆에 둔다. 작은 규칙 파일은 독립적으로 검색할 수 있는 요구사항 하나를 담당하지만, 임의로 잘게 쪼개는 것 자체가 목표는 아니다. 마지막 Dev Note는 위의 안정적인 설명과 활성 작업 맥락을 분리한다.

## 페이지 순서

형식 소유자가 허용하면, 사람이 읽는 작성형 페이지에는 이 순서를 사용한다. 생성된 산출물은 같은 진입 섹션을 생성할 수 있지만, Agent Notes와 postmortem은 저장소가 정의한 골격을 그대로 유지한다.

1. YAML 메타데이터.
2. H1 제목.
3. 이중 언어 페이지의 언어 전환 링크.
4. `## Summary`: 독자가 무엇을 할 수 있거나 관찰할 수 있는지, 왜 독자가 신경 써야 하는지, 핵심 운영 모델, 가장 중요한 경계를 설명하는 3~5문장. 영문 패키지 README의 Summary는 gate가 정한 100단어 제한 안에 머문다.
5. `## Table of Contents`: 페이지의 H2 섹션으로 가는 링크. 설명이 아니라 길 찾기 용도로 유지한다.
6. 안정적인 본문. 사용자 관점의 사용법에서 개발자 관점의 설계와 운영 세부 사항 순서로 배치한다.
7. 선택 사항인 `## Further Exploration`. 처음 보는 독자를 위해 인접 주제로 가는 링크를 둔다.
8. 마지막 `## Dev Note`. 권위가 없는 활성 작업 맥락을 둔다.

작은 기계 소유 파일, 생성된 조각, 실행되는 파서가 다른 헤더를 정의하는 형식에는 Summary/Table of Contents 래퍼를 억지로 씌우지 않는다. 잘못된 출력을 만드는 대신, 예외를 형식 소유자 문서에 명시한다. 패키지 README gate는 `Model Experience`와 `Known Limitations and Deferred Work`를 마지막 두 H2 섹션으로 요구한다. 따라서 `Further Exploration`은 그 앞에 두고, 마지막 `### Dev Note`는 limitations H2 안에 둔다.

## 섹션 진행

실질적인 내용이 있는 H2는 표, 코드, H3 하위 섹션보다 먼저 짧은 안내 문단으로 시작한다. 섹션의 주제와 판단에 필요한 핵심을 설명하고, 섹션의 전체 내용을 되풀이하지 않는다.

페이지 안에서는 독자가 필요로 하는 깊이 순서로 내용을 배치한다:

1. 기본 사용: 기능을 언제 선택하는지, 필수 입력, 가장 짧은 안전한 예시, 관찰 가능한 성공 조건, 가능성이 높은 복구 방법.
2. 고급 사용: 설정 선택지, 제한, 운영, 통합 동작.
3. 개발자 세부 사항: 유지 보수할 가치가 있는 소유권, 수명 주기, 데이터 모델, 실패, 성능, 보안, 확장 지점.

무거운 개발자 세부 사항과 마지막 Dev Note는 섹션 제목을 보이게 둔 채 `<details>` 블록 안에 접는다([style.md](style.md)에 방법이 있다).

접어 둔 개발자 세부 사항은 요구사항상 개념 수준이어야 한다. 전체 설계 개념, 주요 구성 요소의 아키텍처, 대략적인 데이터 흐름처럼 패키지가 어떻게 동작하는지 이해하기에 충분한 수준이어야 한다. 정확한 세부 내용은 source-map 표와 코드 링크로 대신한다. 접은 내용이 전체 목록이 되어서는 안 된다. 전체 API 목록, 열 목록, 이벤트 페이로드 열거, JSDoc 재진술은 넣지 않는다. Dev Note만 부분적인 아이디어, 메모, 아직 정하지 않은 방향을 담을 수 있다. 그 밖의 모든 내용(접은 부분 포함)은 정리된 현재 상태의 산문이어야 한다.

전체를 담은 생성 타입, 스키마, 카탈로그는 짧은 진입 문단과 안정적인 색인 뒤에 둔다. 하나를 찾기 위해 관련 없는 그룹을 훑어야 한다면, 기존 도메인 소유자를 기준으로 나눈다.

## 문서 계층

패키지 계약은 패키지 로컬 README에 작성하고 소스 옆에 둔다. 여러 패키지에 걸친 Markdown은 관련 없는 페이지를 `docs/`에 평평하게 두지 않고, 독자와 학습 의도를 기준으로 정리한다.

```text
docs/
  learn/
    overview/
    cordis/
    practices/
  user/
  developer/
    discussion/
  scratch/
  subsystems/
```

이 구조는 목표 지도로 취급하며, 기회가 될 때마다 대량으로 옮겨도 된다는 허가로 보지 않는다. 한 번에 하나의 일관된 주제만 옮기고, 들어오는 링크와 웹사이트 매핑을 한꺼번에 모두 고치며, 공개 경로나 alias는 유지한다. `subsystems/`는 페이지들이 논리적으로 동등하므로 평평하게 유지한다.

`docs/scratch/`에는 인수인계 후에도 남아야 하는, 추적되고 만료되는 논의를 둔다. 각 scratch 페이지는 소유자, 작성일, 만료일, 승격 대상을 명시한다. 로컬에서만 쓰는 일회성 메모는 계속 무시되고 커밋하지 않는다.

## 작은 규칙 파일

독립적으로 검색할 가치가 있는 규칙, 관행, 예시 묶음, 결정이 자체 소유자, 변경 주기, 들어오는 링크, 검증 절차를 가지면 작은 파일 하나를 준다. 관련 파일은 `docs/developer/code-quality/`처럼 설명적인 계층 아래에 묶는다. 밀접하게 연결된 규칙은 나누었을 때 한 가지 의무를 이해하려고 독자가 여러 파일을 열어야 한다면 함께 둔다.

색인 페이지는 폴더를 3~5문장으로 설명하고, 바로 아래 하위 항목을 목적별로 링크한다. 각 하위 항목의 규칙을 다시 적지 않는다.

## 더 알아보기

이 선택 섹션은 페이지를 다 읽고 인접 주제를 더 이해하고 싶은 처음 보는 독자를 위한 것이다. 직접 관련된 페이지 3~7개를 링크하고, 가장 가까운 선행 지식에서 더 깊은 탐구 순서로 정렬한다. 각 페이지가 무엇을 더해 주는지 짧은 구절로 밝힌다. 전체 사이트 색인으로 만들지 않는다.

## Dev Note 소유권

작성된 페이지는 Dev Note로 끝내되, 권위가 없다고 명시적으로 표시한다. 활성 가설, 호환성 우려, 거친 대안, 진행 상황 포인터, 미해결 질문은 여기에 둘 수 있다. 안정적인 동작, 필수 제한 사항, 승인된 근거는 원래의 소유자에 둔다.

Dev Note는 작업 진행 상황을 반영하거나 링크할 수 있지만, 두 번째 쓰기 가능한 대기열이 되어서는 안 된다. 작업이 끝나면 오래 유지될 결론은 승격하고, 재사용할 근거는 Agent Note로 옮기며, 사고 시간순 기록은 postmortem에 남기고, 해결된 잡담은 삭제한다. 이전 반복은 Git 이력이 보존한다.

## Dev Note

필수 마지막 섹션은 의도적으로 작성된 페이지에서 가장 다듬지 않은 부분이지만, 수명 주기 원칙은 여전히 지킨다. 내용이 없는 Dev Note에는 자리표시자 문장을 쌓지 말고 `None.`이라고 쓴다. 생성되었거나 파서가 소유한 형식은 명시된 예외를 통해 Dev Note를 생략할 수 있다.
