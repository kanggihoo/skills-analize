## 신규 독자 테스트

저장소 맥락이 없는 전문 엔지니어가 관련 페이지 3~5개를 읽은 뒤 다음 질문에 답할 수 있어야 한다. 제품이나 기능이 무엇을 하는가, 안전하게 실행하거나 사용하는 방법은 무엇인가, 상태는 어디에 있는가, 어떤 컴포넌트가 소유하는가, 어떻게 실패하는가, 어디를 고쳐야 하는가. 공개 흐름을 찾기 위해 독자가 소스를 직접 봐야 한다면, 빠진 설명을 복원한다. 독자가 무관한 내부 구현까지 이해해야 한다면, 그 세부를 더 깊은 곳으로 옮긴다.

## 근거 검토

각 중요한 진술을 가장 강한 소유자와 대조한다. 이름과 진입점은 패키지 메타데이터, API 계약은 공개 타입과 JSDoc, 동작은 런타임 코드, 실행된 실패 경로는 테스트, 전체 목록은 생성된 카탈로그, 근거는 활성 Agent Note로 확인한다. 이전 README, 논의, 보고서를 현재 코드와 테스트보다 강한 근거로 취급하지 않는다.

모든 운영상 주장(CLI 명령, 설정 스니펫, 기본값, 오류 메시지, 플랫폼 차이)의 근거는 읽는 것이 아니라 실행하는 것이다. 페이지가 동작을 말하기 전에, 현재 체크아웃에 대해 정확한 명령을 실행하거나 정확한 설정을 마운트한다. 관찰된 출력, 경고, 실패만 인용한다. 사용할 수 없는 키나 네트워크에 의존하는 주장은 동작을 단정하지 말고 검증 주체를 명시한다. 기존 페이지는 최신 `origin/master`와 비교하고, 오래된 진술은 코드에 맞춰 다시 검증한다.

설치 안내를 검토하기 전에 패키지 형태를 분류한다. `package.json`에 `dsh.bundle.patch`가 있으면 번들이다(`dsh plugin --profile <name> add <package>`로 설치하며, 이 명령이 레이어로 활성화하는 유일한 형태다). `apply` export나 기본 서비스 export가 있으면 플러그인이다(`cordis.yml` 행으로 마운트된다). 일반 모듈 API만 있으면 라이브러리다(설치 경로가 없는 의존성이다). 다른 형태를 위해 쓰인 설치 안내는 거부한다.

독자가 행동하거나, 추론하거나, 잘못 쓰지 않는 데 도움이 될 때만 진술을 남긴다. 배경, 이력, 테스트 설명, 중복 카탈로그, 무관한 패키지 세부는 각 소유자에게 옮긴다.

## 패키지 README 검토

하나의 보편적인 내부 제목 체계를 강제하지 않으면서, 다음 항목을 요구한다:

- 검색 가능한 YAML 메타데이터. 정확한 `description`과 기계적으로 도출된 `kind`(`package-group`, `package-reference`, `package-library`, `package-bundle` 중 하나)를 포함한다;
- 3~5문장으로 된 영문 Summary. `wc -w` 방식으로 100단어 이하이며, 주제가 사용자나 에이전트 독자를 위해 무엇을 하는지 말한다. 링크된 Table of Contents를 포함한다;
- 명시적 행위자, 안정적인 용어, 직접적인 동사, 분리된 지시와 조건, 바뀌지 않은 양태(modality)를 갖춘 통제된 영문;
- 패키지를 선택하거나 피해야 할 때;
- 가장 작은 안전한 설정이나 사용 경로(있는 경우). 번들이라면 검증된 `dsh plugin` 설치 경로를, 라이브러리라면 소비자 진입점을 쓴다. 그 형태가 받지 않는 프로필 설치 안내는 쓰지 않는다;
- 소비자와 관련된 관찰 가능한 동작, 실패, 내구성, 보안, 성능 제한;
- 공개 타입으로 저렴하게 복구할 수 없는 개발자용 소유권과 데이터·수명 주기 설계를 개념 수준(전체 설계, 아키텍처, 대략적인 데이터 흐름)으로 설명하고, 정확한 세부는 코드 링크로 연결한다;
- 패키지 정책이 요구하는 정식 Model Experience와 Known Limitations 섹션;
- 인접 문서가 실질적으로 도움이 되는 경우 처음 보는 독자를 위한 Further Exploration;
- 부분적인 아이디어, 메모, 미정 방향을 담는 유일한 곳인, 마지막 권위 없는 Dev Note.

JSDoc이나 생성된 카탈로그를 다시 적지 않는다. 소유자에게 링크하고, 현지에서 필요한 결정이나 관계만 설명한다. 패키지 Summary는 Cordis 역할, 등록, 내부 컴포넌트가 아니라 독자에게 보이는 기능을 설명한다. 독자가 설정, 명령, 공개 API에서 직접 사용하지 않는 한 소스 식별자를 넣지 않는다. 내부 구현(함수 주어, 이벤트 스트림, 데이터 흐름)을 서술하는 사용자 대상 섹션과, 개념을 설명하는 대신 API를 열거하는 접기 블록은 거부한다.

## 기준 예시

`session-persistence-jsonl` README 쌍([영문](../../../../packages/session/session-persistence-jsonl/README.md), [중문](../../../../packages/session/session-persistence-jsonl/README.zh.md))이 이 형식을 실제 운영 환경에서 보여 준다. YAML의 `kind`가 이 package-reference 기준을 선택하고, 4문장 Summary, 링크된 Table of Contents, 선택·설정·배치·내구성·읽기를 다루는 사용자 대상 섹션, 개발자용 설계와 저장 세부를 담은 GitHub 기본 `<details>` 접기, Further Exploration, 정식 Model Experience와 Known Limitations 섹션, 마지막 Dev Note를 갖췄다. 패키지 README와 교차 패키지 페이지의 모델로 이 구조, 근거 기준, 이중 언어 정렬을 사용하고, 모든 주장은 소유 소스와 근거로 뒷받침한다.

## 검증

반복 작업 중에는 가장 작은 범위의 집중 검사를 실행하고, 그다음 표준 문서 검사를 실행한다:

```sh
pnpm run test:docs
pnpm run verify-translation-pairing --write <pair>
pnpm run doc-sync
pnpm run lint
git diff --check
```

스킬을 변경했다면 저장소의 스킬 호출 메타데이터 검사를 실행하고, 줄 단위로 정렬된 영문/중문 쌍은 영문과 중문의 물리 줄 수를 비교한다. 최종 diff는 한 번은 사실 완전성을, 한 번은 간결성, 탐색성, 소유권을 위해 다시 읽는다.
