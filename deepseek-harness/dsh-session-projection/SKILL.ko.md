# 세션 Projection 규칙

## 요약

복구 가능한 세션 사실은 Projection에 보관하고, 그것을 소유한 서비스를 통해 노출한다. 지원되는 준비, 등록, 읽기, 정리 계약은 [API와 수명 주기](../../../packages/session/session-projection/README.md)를 읽는다.

1. 저장되거나 복원 가능한 세션 파생 상태는 host 전용 상태를 포함해 모두 Projection에 둔다. 적절하다면 기존 소유자를 재사용한다. 외부 리소스와 프로세스 범위 소유권은 저장 상태 밖에 둔다. 등록 핸들, Promise, 런타임 리소스가 아니라 사실만 저장한다.

2. projection 정의나 핸들을 운영용 읽기 API로 노출하지 않는다. ready 핸들은 비공개로 두고, 소비자는 소유 서비스의 도메인 메서드를 사용한다. 핸들은 프로세스 로컬 리더이며 activation 중에 다시 만들어진다. 서비스가 `sessionProjections`에 의존하면 이를 필수로 요구한다. 선택적 등록은 선택적 기여에만 쓴다. 누락된 필수 의존성을 다른 복구 경로로 가리지 않는다.

   여러 projected 상태가 필요한 런타임은 `handle.readerFor(session)`으로 만든 콜백들의 타입이 지정된 객체 하나를 받는다. 상태마다 생성자 파라미터나 기능별 리더를 추가하지 말고 속성을 추가한다. 각 콜백의 타입은 `() => S`다. 목적이 하나뿐인 협력 객체는 이를 직접 받는다. 이 host 상태 리더는 wire 스냅샷 및 살아 있는 Cordis Context와 별개다. 등록, 등록 해제, 캐시, I/O를 소유하지 않는다. 등록, Session 준비, 핸들의 수명은 각 소유자가 맡는다. 동기 API 호환성은 규칙 9가 정한다.

3. `init`과 `apply`를 통한 상태 복구는 동기적이고 결정적이다. I/O를 수행하거나 Cordis hook, 모델, 도구를 트리거하지 않는다. 그 효과는 런타임 hook이 소유한다. 리플레이가 이를 반복해서는 안 된다. 관계없는 이벤트에는 같은 상태 참조를 반환한다. 뷰는 동기적으로 유지하고, 보이는 값이 바뀌지 않으면 참조를 보존한다.

4. 스키마가 허용하는 JSON 상태만 저장한다. README의 state-version과 checkpoint-watermark 규칙을 따른다. 체크포인트를 복원하고 그 suffix를 리플레이한 결과는 전체 리플레이와 일치해야 한다. 상태 필드나 복구 의미가 바뀌면 버전을 올린다.

5. 고정 크기 또는 준선형 상태를 선호한다. 증가는 충분히 느려서 무시할 수 있을 때만 허용한다. 필요한 선형 상태는 현재 사용처가 있어야 하고, 메모리, 리플레이, 이벤트당 비용을 명시해야 한다. 이벤트 시퀀스 컬렉션을 포함해 히스토리 크기의 인덱스를 습관적으로 유지하지 않는다. 크기를 줄이려고 필요한 데이터를 버리거나 동작을 바꾸지 않는다. 완전한 구현으로 시작하고, 구체적인 필요가 생기면 최적화한다.

6. 캐시는 동작을 바꾸지 않고 버릴 수 있고 다시 만들 수 있어야 한다. 동기 소비자가 참조된 페이로드를 필요로 할 때 sequence 참조만으로는 부족하다. 규칙 5 안에서 필요한 현재 값을 저장하거나, 명시적인 비동기 경로로 페이로드를 준비한다. 캐시 미스 안에 전체 로그 읽기를 숨기지 않는다. `snapshotEvents`, `eventAt`, `ownEvents` 또는 이에 준하는 래퍼를 추가하지 않는다. 히스토리는 메모리에 남아 있을 필요가 없다. 비동기 래퍼가 동기 히스토리 읽기를 비동기로 바꾸지는 않는다. 기존 host 리플레이는 소유자와 제거 조건을 명시한 지원 호출자에 한해 남길 수 있다. 이것이 [Client 캐시 미스 전체 로그 읽기](../../../docs/defensive-patterns/conversation-and-session.md#cold-reads-are-the-last-resort)를 허용하지는 않는다. 대체된 복구 헬퍼는 제거한다. 캐시 재구성이 복구 규칙을 중복해서는 안 된다.

7. 동기 리더를 노출하거나 그 핸들을 쓰는 콜백을 설치하기 전에, 필수 등록을 기다린다. 보통 `[Service.init]`에서 한다. 등록이 거부되면 해당 activation을 실패시킨다. await 중에도 이벤트가 도착할 수 있다. 놓치는 이벤트를 막아야 할 때에만 리스너를 더 일찍 설치한다. 기다림을 지원하는 콜백에서만 await한다. 리스너를 기계적으로 옮기거나 대기를 추가하지 않는다. fiber 정리 소유권을 유지하고, 명시적 disposal을 await하며, 소유자가 disposed된 뒤에는 효과를 만들지 않는다.

8. 등록 준비 상태와 Session 복구를 분리한다. 비동기 Session 로딩 또는 준비 소유자는 Session을 동기 리더에 게시하기 전에 과거 복구를 완료한다. registry가 지원하는 수명 주기를 사용하고, 도메인 getter에 hydration이나 숨은 I/O를 추가하지 않는다. 복구는 상태를 준비하고, getter는 그 상태를 읽는다. 각 단위와 Session에 대한 registry의 오류 범위를 보존한다.

9. 읽기 경로를 바꾸기 전에 플러그인, CLI/GUI, 두 SDK를 포함해 모든 공식 소비자를 식별한다. 동기 호출자는 명시적으로 마이그레이션하기 전까지 유지한다. Promise로는 동기 API를 구현할 수 없다. 새 필수 서비스나 activation 단계에는 소비자 업데이트와 업그레이드 가이드가 필요하다. 호환성은 테스트 전용 구성이 아니라 실제로 지원되는 호출자에 맞춘다.

10. 영향을 받는 실제 진입점을 통해 값, 알림, 오류 범위와 타이밍, 복구를 검증한다. 기존 동작 단언은 유지한다. 소비자에게만 해당하는 오류를 즉시 실행되는 Projection 처리로 옮기지 않는다. 수명 주기를 바꾸면 await 중의 지연된 등록, 거부, 교체, disposal을 테스트한다. 부분 Session mock이나 microtask 횟수 대신 실제 Session/store 수명 주기와 명시적 barrier를 사용한다. 해제된 상태뿐 아니라 오류 로그도 확인한다. 복구 테스트는 사용 가능, 누락, 호환되지 않는 체크포인트와 suffix 리플레이를 다루되, 런타임 효과는 포함하지 않는다.
