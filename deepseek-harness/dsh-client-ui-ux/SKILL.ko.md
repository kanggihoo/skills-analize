# DeepSeek Harness 클라이언트 UI/UX

이 스킬은 지침이지 완전한 체크리스트가 아닙니다. lint, typecheck, i18n 게이트가 판단할 수 없는 판단 사안을 다룹니다. 피드백이 어디에 나타나는지, 무엇을 재사용하는지, 표면이 창 가장자리와 플랫폼마다 어떻게 동작하는지가 그것입니다. 문구 품질 자체는 [dsh-prose-standard](../dsh-prose-standard/SKILL.md)를 따르고, locale 소유권은 [locale 소유 문구 결정](../../notes/implemented/architecture/2026-08-23-locale-owned-client-ui-copy.md)을 따릅니다. 스타일링 소유권과 토큰 규칙은 [docs/web-styling.md](../../../docs/web-styling.md)와 [ui-primitives 컴포넌트 카탈로그](../../../packages/client/ui-primitives/README.md#component-catalog)에 있습니다. 이 스킬은 그 규칙 위에 판단을 더할 뿐, 같은 내용을 한 번 더 복사하지 않습니다.

## 아키텍처 선행 조건

컴포넌트 구조, 상태 흐름, effect 사용은 아키텍처 규칙을 따릅니다. 컴포넌트를 다시 설계하기 전에 이를 먼저 읽습니다.

- [packages/client/AGENTS.md](../../../packages/client/AGENTS.md): Slot과 props 규율, reactive 읽기, export, ctx, 레이어링 규칙.
- [Client component rules](../../../docs/defensive-patterns/client-components.md): 해당 요구 사항을 그것이 막는 결함과 함께 설명합니다.

## 시각 기반

- **색상, 반경, 간격에는 기존 토큰을 사용합니다.** 리터럴 값을 새로 도입하기 전에 대상 페이지와 가장 가까운 기존 형제 페이지(전체 페이지 표면은 보통 Plugins 페이지가 기준입니다)에서 이미 쓰는 토큰이나 값을 검색하고 그것을 채택합니다. 같은 원칙이 토스트, 메뉴, 메시지 안의 artifact 미리보기, 사이드바 탭 레이아웃, 색상, clearance 규칙, 페이지 패딩 같은 처리 전체에도 적용됩니다. 기존 컴포넌트나 규칙이 있다면 평행한 것을 새로 만들지 말고 그것을 재사용합니다.
- **모든 색상을 라이트 모드와 다크 모드 모두에서 확인합니다.** 잉크/배경 쌍은 출시 전에 두 테마 모두에서 읽을 수 있어야 합니다. 흐린 색조가 대표적인 반례입니다. 장식용 표면에는 어울리지만, 텍스트에 쓰면 한쪽 테마에서 가독성 기준 아래로 떨어지는 경우가 흔합니다. 두 테마를 모두 확인하지 않고는 흐린 색을 텍스트에 쓰지 않습니다.
- **추가하거나 바꾸는 기능 CSS에서 폰트 두께는 500이 상한입니다.** 강조에 600 이상을 쓰지 말고, 크기나 잉크 색으로 구분합니다. ui-theme이 소유한 markdown 타이포그래피 토큰만 예외입니다.
- **폰트 크기는 기존 역할이 맞으면 테마 타이포그래피 변수에서, 아니면 페이지의 기존 척도에서 고릅니다.** 나란히 놓인 콘텐츠는 같은 크기를 공유합니다. 한 요소만을 위해 크기를 새로 만들지 않으며, 한 페이지의 서로 다른 크기 수를 적게 유지합니다(13px가 확립된 행/상세 크기입니다). 페이지 자체에 선례가 없다면 가장 비슷한 기존 페이지나 요소의 크기와 간격 비율을 빌려 씁니다.
- **아이콘, 텍스트, 인접 요소는 비율이 맞고 정렬되어야 합니다.** 모든 요소는 의도된 축(베이스라인, 수직 중앙, 공유 가장자리) 위에서 형제 요소와 정렬되며, 아이콘 크기는 옆 텍스트와 비례를 유지합니다. 아무것에도 정렬되지 않거나 이웃보다 눈에 띄게 커 보이는 요소를 내보내지 않습니다.

## 재사용 우선

- **새로 만들기 전에 기존 컴포넌트, 컨테이너, 상호작용을 확장합니다.** 기존 표면에 맞는 새 기능(메뉴 항목 추가, 기존 프리미티브에 새 prop 추가)은 옆에 평행한 요소를 쌓는 것보다 낫습니다.
- **아이콘은 기존 아이콘 라이브러리에서 가져옵니다.** 의미상 가장 가까운 기존 아이콘을 고릅니다. 새 글리프는 들어가기 전에 디자이너 승인이 필요합니다. 이를 추가하는 PR을 검토할 때는 디자이너 검토를 요청하도록 제안합니다.
- **오른쪽 사이드바 콘텐츠는 기존 사이드바에 slot을 등록합니다.** 별도의 사이드바를 만들지 않습니다. 모든 사이드바 탭은 그 의미에 맞는 탭 아이콘을 선언합니다.
- **의미가 분명하지 않은 아이콘 전용 동작에는 Tooltip을 붙입니다.** 포인터를 올려 두거나 선택해야 보이는 정보성 콘텐츠에는 HoverCard를 씁니다. 즉석의 title 속성보다 이러한 공유 프리미티브를 우선합니다.

## 피드백 표면

실패 보고에는 [dsh-error-handling](../dsh-error-handling/SKILL.md#localized-actionable-visible-reports)을 적용합니다. 메시지의 수명이 그것을 만든 표면과 비교해 얼마나 지속되는지를 기준으로 표면을 고릅니다.

- **일시적인 작업 결과에는 앱 전역 Toast 프리미티브를 사용합니다.** 제자리 알림을 쓰지 않습니다. toast의 상태와 렌더링은 보고한 표면보다 오래 사는 호스트에 둡니다(RowActionToast가 그렇듯 `shell.overlay` 항목). 패널이 직접 렌더링한 toast는 그 패널과 함께 언마운트됩니다. 삭제는 요청한 패널이나 탭을 닫을 수 있으므로, 그 표면 바깥에 보관된 toast만 닫힌 뒤에도 살아남습니다. 성공과 실패를 보고하고, 아직 진행 중인 상태는 보고하지 않습니다.
- **실패한 작업은 데이터를 계속 보여 줍니다.** 실패한 삭제는 해당 행을 그대로 둡니다. 실패는 toast로 알립니다. 일시적인 작업의 오류를 보여 주려고 콘텐츠를 비우지 않습니다.
- **제자리 알림은 표면 자체와 묶인 상태에만 씁니다.** 예를 들면 Retry 동작이 있는 쿼리 실패, 필드를 소유한 폼의 필드 검증입니다. 콘텐츠가 채워진 패널은 유지되는 콘텐츠 옆에 작은 알림을 둡니다. 비어 있는 패널만 전체 오류 상태를 가운데에 둡니다.
- **오류 문구는 쉬운 말로, 짧게 씁니다.** 디버깅을 위해 오류 코드를 노출해야 하는 경우가 아니라면 내부 용어나 기술 명사를 쓰지 않습니다. 명확한 문장 하나를 선호합니다. 두 문장으로 설명할 수 있는 내용이 단락으로 늘어나면 안 됩니다. 중국어 알림이 두 문장 이하라면 끝의 句号（。）는 붙이지 않습니다. 알림은 기존 레이아웃을 깨면 안 됩니다. 공간을 미리 확보하거나 overlay로 띄우고, 인접 요소를 밀어내지 않습니다.

## 로딩 상태

- 목록은 자체 skeleton을 씁니다. 그 밖의 페이지 단위 로딩은 가운데에 맨 spinner를 둡니다. spinner를 페이지 모서리에 두지 않습니다.
- 페이지/컴포넌트마다 로딩 처리는 하나만 둡니다. 동시에 로딩되는 영역이 각자 다른 스타일로 깜빡이면 안 됩니다.
- 맥락상 필요한 경우가 아니라면 로딩 텍스트를 쓰지 않습니다(좁은 사이드바에는 거의 필요하지 않습니다).

## Overlay와 메뉴

모든 메뉴, popover, tooltip은 병합 전에 아래 세 가지를 모두 확인해야 합니다.

- **닫을 수 있음**: 바깥을 클릭하면(포커스를 받을 수 있는 곳에서는 Escape도) 닫힙니다.
- **뷰포트 안에 맞음**: 가장자리 여백을 두고 창 안에 머물도록 밀리거나 뒤집히며, 실제로 들어갈 수 있는 쪽으로만 뒤집힙니다. 어느 쪽도 맞지 않으면 계속 번갈아 뒤집히면 안 됩니다.
- **잘리지 않음**: `overflow` 조상과 containing block을 벗어나며(필요하면 body로 portal), 인접 요소에 가려지지 않습니다.

스크롤바는 컨테이너 안에 머뭅니다. 컴포넌트 전용 선택자 대신 공유 스크롤바 스타일을 사용하고, 바가 컨테이너를 넘치지도, 둥근 모서리나 가장자리에 잘리지도 않는지 확인합니다. 컨테이너 가장자리에 딱 붙이지 말고 작은 inset을 둡니다.

## 반응형 레이아웃

반응형 레이아웃, 모바일과 터치 감지, 텍스트 말줄임, 제목 줄바꿈, 아이콘 전용 컨트롤, 너비가 바뀔 때의 포커스에는 [dsh-responsive-ui](../dsh-responsive-ui/SKILL.md)를 사용합니다.

## 플랫폼 창 적응

- 새 헤더 요소나 전체 페이지는 macOS와 Windows 창 크롬을 고려해야 합니다. macOS에서 titlebar clearance는 `--dsh-frame-top-clearance`이며, Menu, Modal, overlay 프리미티브가 이를 상단 안전 여백으로 사용합니다. **페이지 하나를 고치려고 전역 변수를 바꾸지 마십시오.** 대신 페이지 자체 inset에 범위가 한정된 `[data-platform='darwin']` 오버라이드를 추가하고, 그 오버라이드를 페이지 스타일시트 스펙에서 검증합니다.
- 검토할 때는 의도한 총 오프셋(clearance + 페이지 inset)을 밝힙니다. 두 페이지가 "같은 상단 간격"에 맞추려 할 때, 한 항만 맞추는 것이 아니라 합계가 일치해야 하기 때문입니다.

## 간격 검토

- 바뀐 모든 영역에서 간격을 검토합니다. 의도된 간격 없이 이웃에 딱 붙어 있는 것이 없어야 하며, 인접한 아이콘과 요소는 해당 영역의 기존 간격을 유지합니다.
- 평행한 요소는 대칭을 선호합니다. 설명되지 않은 일회성 간격이나 오프셋은 보통 놓친 공유 값이 있다는 신호입니다.
- **복잡한 페이지와 컨테이너에서는 로컬 간격을 조정하기 전에 공유 가로·세로 정렬 축을 먼저 세웁니다.** hover, selected, expanded/collapsed 상태와, 인접 패널 및 다른 페이지 요소와의 전체 관계를 함께 고려합니다. 레이아웃의 유사성에 따라 아래 참조 중에서 고릅니다.
  - **사이드바:** 세로로 쌓인 행들에서 대응하는 텍스트 시작점과 선행 아이콘을 맞춥니다. hover와 selected 행 배경은 목록 위 버튼과 정렬해 시각적 균형을 유지합니다.
  - **Plugins 페이지:** 콘텐츠를 공유 가장자리를 따라 왼쪽 정렬합니다. 목록 행의 hover 배경은 그 가장자리를 넘어 확장할 수 있지만, 콘텐츠는 제자리에 머뭅니다.
  - **대화 및 오른쪽 사이드바 헤더:** 두 패널의 첫 헤더 행을 맞추고 높이를 일치시킵니다. 두 번째 행에도 같은 규칙을 적용하고, 대응하는 밑줄과 구분선은 공유 가로 베이스라인에 맞춥니다.

## 설계 검토 에스컬레이션

UI 변경이 광범위한 PR이나, UI 또는 상호작용에서 사용자가 분명히 인지할 수 있는 변경은 디자이너 또는 프로덕트 검토를 받아야 합니다. 승인자가 그 역할을 맡고 있지 않다면, 디자인/프로덕트 리뷰어(2026-09 기준 명단: yx zhang, yifffan, zhangziya, gaokaige) 중에서 요청하도록 제안합니다. 구성원이 바뀌면 이 목록을 여기서 갱신합니다.
