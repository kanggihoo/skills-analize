# DeepSeek Harness 오류 처리

실패, 실패의 담당자, 실패 이후에도 안전하게 남는 것을 정의한다.

## 타입이 있고 구조화된 실패

예상된 실패에는 선언된 타입, 안정적인 discriminant, 처리에 필요한 세부 정보가 필요하다. 패키지의 오류 관례를 재사용하고, 원인(cause)을 보존하며, 기계가 식별하는 값과 화면에 표시되는 문구를 분리한다. 메시지를 파싱해서 처리 방식을 고르지 않는다. `assertNever` 같은 예상치 못한 결함은 일반 `Error`로 둘 수 있다. 격리(containment)가 이를 성공으로 바꾸면 안 된다.

## 잡고, 복구하거나, 멈춘다

각 실패에 대해 처리 담당자와 보고 담당자, 격리 범위, 보장을 해당 API 문서에 정의한다. 유효한 invariant, 부분적으로 적용된 효과, 커밋된 효과, 알 수 없는 효과, 정리(cleanup) 책임을 포함한다. 백그라운드 작업에도 같은 의무가 있다.

예외 전파는 막아도 상태 변경은 막지 못한다. 영향받은 상태의 담당자만 안전한 계속 실행을 결정할 수 있다. 그렇지 않으면 의존 작업을 멈추고, 유효하지 않은 상태나 인스턴스를 버리거나, 상위로 에스컬레이션한다. 로그만 남기는 것은 복구가 아니다. 재시도에는 안전한 반복, 취소, 명확한 담당자가 필요하다. 끝이 있는 작업에는 예산(budget)이 필요하다. 계속 감시하는 작업에는 생명주기 담당자와 관찰 가능한 성능 저하(degradation)가 필요하다.

## 지역화되고, 실행 가능하며, 보이는 보고

모든 최종 보고에는 읽을 수 있는 요약, 영향받은 작업, 안전한 다음 행동이 있어야 한다. 받는 애플리케이션에 locale 메커니즘이 있으면 그것을 통해 지역화한다. 다른 진단 출력은 기존 출력 언어를 따른다. 민감한 내부 세부 정보는 사용자에게 보이는 문구에 넣지 않는다.

신뢰할 수 없는 상태나 결과를 알 수 없는 실패는 UI나 기본으로 켜져 있고 접근 가능한 로그를 통해 보여야 한다. 영향, 불확실성, 시스템의 처리 상태, 안전한 다음 단계를 알린다. 지속적으로 유효하지 않은 상태는 지속적으로 보여야 한다. 보장이 없으면 성공, 롤백, 안전한 재시도를 주장하지 않는다. 보고 실패에도 독립적인 대체 경로(fallback)가 필요하다.

예외가 잡혔는지만 확인하지 말고, 결과 상태와 화면에 보이는 결과를 검증한다.
