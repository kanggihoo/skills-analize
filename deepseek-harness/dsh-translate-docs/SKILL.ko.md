# DeepSeek Harness 문서 번역

## 호출 경계

사용자가 `dsh-translate-docs`를 이름으로 명시적으로 호출했을 때만 이 확장 워크플로를 실행합니다. 일반 문서 작업이나 다른 스킬에서는 이 스킬을 선택하거나 로드하지 않으며, 번역 필요를 추론해서 로드하지도 않습니다. 일상적인 번역은 [docs/AGENTS.md](../../../docs/AGENTS.md)에 있는 one-shot, one-pass 규칙을 따릅니다.

## 이 스킬의 성격

**이 스킬은 번역 메모리가 아니라 지침입니다.** `foo.md ↔ foo.zh.md` 쌍을 두 언어 모두에서 일관되고 자연스럽게 유지하기 위한 워크플로 지도입니다. 두 언어의 권한은 동등합니다. 변경은 어느 쪽에서든 작성할 수 있고, 그 쪽이 해당 업데이트의 원본이 됩니다. 번역자는 당신입니다. 아래 규칙은 반드시 지켜야 할 조건을 말하며, 개별 문장을 어떻게 표현할지는 당신의 판단에 맡깁니다. 다만 용어는 판단 대상이 아닙니다.

## 변경 유형별 분류: 이후 모든 절차를 결정합니다

- **Update** (쌍이 있고 한쪽이 수정됨): [업데이트 경로](#the-update-path-briefing-driven)를 따릅니다. 이 경로는 브리핑 중심이며 의도적으로 저렴하게 진행합니다. 가이드 코퍼스를 읽지 않고, git 이력을 파고들지 않으며, 대응하는 쪽은 최소한만 수정합니다. 업데이트를 적용하려고 문서 전체를 다시 번역하지 마십시오. 최소 업데이트는 변경되지 않은 부분의 검토된 표현을 보존하지만, 재번역은 그 검토 결과를 버리게 됩니다.
- **New pair** (대응 문서가 아직 없음): [문서 전체 경로](#the-whole-document-path-new-pairs)를 따릅니다.
- **Deleted or renamed doc** (삭제되거나 이름이 바뀐 문서): 대응 문서와 그 옆의 `.i18n.yaml`도 함께 삭제하거나 이름을 바꿉니다. 그렇지 않으면 게이트가 쌍이 불완전하다고 보고합니다.

`.agents/notes/archived/` 아래의 동결된 Agent Notes는 번역 작업 대상이 아닙니다. 완전한 세트(triplet)는 아카이브 검증기가 봉인하므로, 아카이브된 뒤에는 양쪽 어느 쪽도 업데이트, 재기록, 수리하지 않습니다.

## 업데이트 경로 (브리핑 중심)

브리핑 중심 경로는 가이드 코퍼스 수준의 품질을 훨씬 적은 비용으로 맞춥니다. 벤치마크 근거는 보관된 [briefed-updates Agent Note](../../notes/archived/process/2026-07-26-briefed-minimal-translation-updates.md)에 있습니다.

1. **브리핑 생성**: `pnpm run gen-translation-brief <쌍의 아무 파일>`을 실행합니다. 인자 없이 실행하면 동기화되지 않은 모든 쌍을 브리핑합니다. 브리핑은 변경 사항을 가능한 한 좁고 안전하게 정렬된 단위로 매핑합니다. 먼저 변경된 Markdown 단위(단락, 표의 행, 목록 항목, 제목)를 보고, 다음으로 제목 섹션 전체, 마지막으로 문서 전체 순서입니다. 브리핑에는 마지막으로 확인된 일관 상태 이후 작성된 쪽의 diff, 변경된 각 단위의 마지막 확인 원본, 현재 원본, 현재 대응 텍스트(줄 번호 포함), 변경과 관련된 용어 행, 첫 등장 위치 이동 메모, 바인딩 업데이트 규칙 요약이 들어 있습니다.
2. **기계적 diff만 있다면 `--apply`로 적용합니다.** 변경이 모두 두 쌍이 바이트 단위로 동일하게 공유하는 코드 펜스 안에 있으면, 브리핑이 그렇다고 표시합니다. 이때 `pnpm run gen-translation-brief --apply <쌍>`이 수정된 펜스를 대응 쪽에 끼워 넣고, 쓰기 전에 구조를 검증합니다. 서브에이전트도, 손 편집도 필요 없습니다.
3. **산문 diff라면 브리핑을 넘겨 서브에이전트에 위임합니다**(또는 브리핑을 생성하는 명령을 넘깁니다). 브리핑이 번역자가 작업하는 전체 자료입니다. 서브에이전트는 가이드 코퍼스를 다시 읽지 않으며(규칙 요약, 용어 행, 변경된 각 단위의 3자 대조 문맥이 인라인으로 제공됩니다), diff를 다시 계산하지도 않습니다. 브리핑이 특정 결정에 답할 수 없을 때만 문서 전체 경로의 진실 공급원으로 넘어갑니다. 예를 들어 주변 텍스트에 선례가 없는 목록 외 용어가 나오는 경우입니다. 문서 전체 브리핑(`BOTH sides changed`, 또는 단위와 섹션 모두 정렬되지 않는 경우)은 항상 [translation-rules.md](../../../docs/i18n/translation-rules.md)에 따라 손으로 조정해야 한다는 뜻입니다.
4. **diff를 덮는 가장 작은 편집.** diff가 건드리지 않은 부분의 검토된 표현은 그대로 보존합니다. 그다음 변경된 hunk를 원본과 절 단위로 대조합니다. 추가된 것도, 빠진 것도 없어야 하고, 용어는 인라인 행을 따르며, 코드 span은 그대로여야 합니다.
5. **범위를 한정해 기록하고 검증합니다**: `pnpm run verify-translation-pairing --write <쌍>`을 실행한 뒤 `pnpm run verify-translation-pairing <쌍>`을 실행합니다. `--write`는 확인한 쌍을 정확히 지정합니다. 인자 없이는 실행을 거부하므로, 대량 재기록은 항상 명시적인 `--all`로만 가능합니다. 저장소 전체 검사는 `doc-sync`/CI에서 여전히 실행되므로, 업데이트마다 실행하지 마십시오.

## 문서 전체 경로 (새 쌍)

번역을 처음부터 작성해야 할 때, 이를 조율하는 에이전트는 직접 번역하지 않고 번역 작업을 서브에이전트에 맡깁니다. 번역자는 먼저 아래 진실 공급원을 읽고, 긴 문서는 섹션별로 전체 파일을 다른 언어로 번역합니다. 구조는 마지막에 고치는 것이 아니라, 각 섹션을 번역하면서 원본에 맞춰 그때그때 고정합니다.

### 진실 공급원 (읽고, 다시 요약하지 않습니다)

- **[docs/i18n/README.md](../../../docs/i18n/README.md)**: 페어링 계약입니다. 세 파일 쌍(`foo.md`, `foo.zh.md`, `foo.i18n.yaml`), 일관성 기록의 섹션별 해시, 언어 전환 줄, 범위와 제외 대상을 정의합니다.
- **[docs/i18n/translation-rules.md](../../../docs/i18n/translation-rules.md)**: 번역 방법입니다. 충실성, 구조 보존, 용어 규율, 타이포그래피(MUST/SHOULD 수준)를 다룹니다.
- **[docs/i18n/terminology.md](../../../docs/i18n/terminology.md)**: 용어 표이며 양방향으로 구속력이 있습니다. 용어가 헷갈릴 때가 아니라 번역하기 전에 미리 읽습니다. 신경 쓰이지 않는 용어가 흔들리기 때문입니다.
- **[docs/i18n/translation-prompt.md](../../../docs/i18n/translation-prompt.md)**: 자동 파이프라인이 사용하는, 기계가 읽도록 보정된 템플릿입니다. 이 스킬을 쓰는 에이전트는 이를 렌더링하지 않습니다. 저장소 파일 중 자동 렌더러가 주입하는 것은 용어 표뿐이며, 에이전트가 작성하는 번역에는 이 스킬과 `translation-rules.md`가 여전히 구속력이 있습니다.
- **[dsh-prose-standard](../dsh-prose-standard/SKILL.md)**: 필수 산문 범위와 편집 판단입니다. 원본의 명제를 더하거나 빼지 않고 양쪽 모두에 적용합니다.

### 번역

- **Pass 1: 옮기지 말고 씁니다.** 의미 단위를 읽은 다음, 가장 가까운 [스타일 샘플](../../../docs/i18n/style-samples.md)의 어조로 네이티브 기술 작성자처럼 다시 씁니다. 필요한 프레임은 보존하되, 문장 단위로 1:1 대응시키지는 않습니다.
- **Pass 2: 원본과 절 단위로 대조합니다.** 충실성은 여기서 확인하며, 처음부터 써 넣는 것이 아닙니다. 아무것도 더하거나 빠뜨리지 않았는지, 모든 용어가 표를 따르는지, 각 코드 span이 그대로 살아 있는지 확인합니다. 고칠 때는 단어를 끼워 넣지 말고 문장을 자연스럽게 다시 씁니다.
- **완성된 대응 문서만 단독으로 읽습니다.** 원본과 비교한 뒤에는 원본을 옆에 두지 않고 번역된 파일만 읽습니다. 그때만 보이는 어색한 표현은 다시 씁니다.
- 파일에는 최종 텍스트만 씁니다. 초안이나 메모는 쓰지 않습니다.
- [terminology.md](../../../docs/i18n/terminology.md)의 모든 용어는 명시된 대로 정확히 표기합니다. 중국어 대상이면 중국어 열과 first-occurrence 열을 사용합니다. 표에 없는 용어는 인용 가능한 중국어 OSS/벤더 선례가 있어야 하며, 없으면 영어로 두고 「待定术语」로 표시합니다. 영어 대상이면 영어 열과 확립된 영어 기술 용어를 사용합니다. 모호한 원본 용어는 짧은 설명(gloss)과 함께 보존하고, 미정 목록에 올립니다. 인라인으로 표기를 새로 만들지 마십시오.
- 코드 블록은 쌍 사이에서 바이트 단위로 동일해야 하며, 주석도 포함됩니다. 저장소 상대 문서 링크는 의미상의 대상과 정확한 query/fragment 접미사를 유지합니다. 활성 이중 언어 코퍼스 안의 대상은 영어 쪽에서 `.md`, 중국어 쪽에서 `.zh.md`를 사용합니다. 범위 안의 대응 문서가 없으면 오류입니다. 코퍼스 밖의 대상은 작성된 경로를 유지합니다. 언어 전환 링크만 예외입니다.
- 페어링 게이트는 제목 깊이, 펜스 블록, 표의 행과 열 수, 목록 종류, 순서 목록의 시작 번호, 목록 항목 수, 링크 언어, 의미상 대상을 검사합니다. Pass 2에서는 목록과 표의 순서, 비표준 목록 번호, 인라인 코드, 강조, 의미, 용어, 어조를 직접 확인합니다.

## 작업 찾기

- `pnpm run verify-translation-pairing --list`는 범위 안의 모든 문서를 missing / out-of-sync / ok로 출력합니다. missing과 out-of-sync 행은 계약 위반이며, 일반 검사는 이를 거부합니다.
- 인자 없이 `pnpm run gen-translation-brief`를 실행하면 동기화되지 않은 모든 쌍의 브리핑을 출력합니다.
- 이중 언어 문서를 수정하는 PR에서는 diff 자체가 작업 목록입니다. 쌍의 변경된 모든 쪽에는 같은 PR 안에서 대응 문서 업데이트와 쌍의 재기록이 필요하며, 빠뜨리면 게이트가 실패합니다.

## 쌍 마무리

1. 언어 전환 링크: 중국어 파일의 H1 바로 뒤에 `[English](foo.md) | 中文`을, 영어 파일의 H1 바로 뒤에 `English | [中文](foo.zh.md)`를 넣습니다. 새 쌍이라면 둘 다 추가합니다. 다만 생성기가 소유한 영어 원본은 생성기 출력과 바이트 단위로 같아야 하므로 언어 전환 링크를 생략하고, 중국어 대응 문서는 여전히 영어 쪽으로 링크합니다.
2. 일관성 기록: `pnpm run verify-translation-pairing --write <쌍>`을 실행해 섹션별 해시를 다시 계산하고 `foo.i18n.yaml`에 기록합니다. PR의 yaml diff는 "이 두 문서가 같은 내용임을 확인했다"는 검토 가능한 진술입니다. 실제로 확인한 뒤에만 실행합니다.
3. 일반 문서에는 manifest 항목이 필요 없습니다. 범위 안의 모든 원본에는 쌍이 필요합니다. [scripts/translation-pairing.manifest.json](../../../scripts/translation-pairing.manifest.json)은 소유 정책이 생성, 지침, 이중 언어 구성 방식의 예외를 명시적으로 문서화한 경우에만 수정합니다.
4. PR 전 확인: 건드린 쌍은 범위 지정 검사를 통과해야 합니다. `pnpm run doc-sync`(저장소 전체 페어링 검사에 `verify-md-wrap`/`verify-md-links`를 더한 것)는 [dsh-pre-push-checks](../dsh-pre-push-checks/SKILL.md)에 따라 PR 단위로 한 번 실행하며, 각 번역 작업 안에서는 실행하지 않습니다.
5. PR을 검토 가능하게 유지합니다. 어떤 쌍이 새 쌍이고 어떤 쌍이 최소 업데이트인지 밝히고, 「待定术语」를 눈에 띄게 나열합니다.

## 번역 리뷰에 대응하는 방법

[코드 리뷰 보고 지침](../dsh-code-review/SKILL.md#reporting-findings)을 따릅니다. 각 코멘트는 장단점으로 판단합니다. 용어 관련 코멘트라면 용어 표가 계약이라는 점을 기억하고, 리뷰어의 표기 결정은 한 파일에만 적용하지 말고 [terminology.md](../../../docs/i18n/terminology.md)에 적용합니다.
