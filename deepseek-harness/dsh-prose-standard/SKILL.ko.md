# DeepSeek Harness 산문 표준

계약을 보존할 만큼만 쓰고, 그다음 추론 기록, 반복, 장식을 제거합니다. 계약이란 호출자, 피호출자, 구현자, 생산자, 소비자가 의존하는 의무, 불변식, 사전 조건, 사후 조건, 호환성 약속을 말합니다. 이 스킬은 편집 판단과 필수 산문 범위를 담당합니다. 배치, 분량 예산, 이중 언어 쌍, 문서 게이트는 [dsh-doc](../dsh-doc/SKILL.md)을, 추론 기록 누출을 찾아 고치는 일은 [dsh-trim-cot-leakage](../dsh-trim-cot-leakage/SKILL.md)를 사용합니다. 이 스킬은 지침이지 스크립트가 아닙니다.

`contract`, `boundary`, `shape`, `surface`, `seam`, `gate`, `vocabulary`는 금지어가 아니라 사용 전에 확인할 용어입니다. 먼저 정확한 규칙, API, 필드 집합, 타입, 검증, 시점, 컴포넌트 분할, 실패 상태가 그 사실을 더 잘 설명하는지 묻습니다. 호출자/피호출자 계약, 보안·프로세스 경계처럼 정확한 기술 대상을 가리키면 용어를 유지합니다.

주석은 코드로 표현할 수 없는, 자명하지 않은 계약이나 근거를 설명합니다. 코드가 이미 암시하는 내용을 되풀이하지 않습니다.

## 입력과 제외

명시적인 `scope`를 요구합니다. 없으면 필요한 입력을 보고하고 멈춥니다. 저장소 전체 범위를 추정하거나 인터뷰를 시작하지 않습니다.

`mode: automatic | interactive`를 받으며 기본값은 `automatic`입니다. 사용자가 질문이나 보정을 명시적으로 요청한 경우에만 interactive 모드에 들어갑니다.

`mode`는 질문을 제어하며, 쓰기 권한을 제어하지 않습니다. 검토와 감사 작업은 편집하지 않고 결과만 보고합니다. 쓰기, 수정, 축약을 명시적으로 요청받은 작업은 명확한 변경을 적용합니다.

항상 `vendor/`를 탐색, 검토, 편집에서 제외합니다. 요청 범위가 저장소 전체여도 마찬가지입니다. 그 안으로 가는 symlink를 따라가지 않습니다. 제외 조건은 포함 glob 뒤에 둬서, 나중의 포함 조건이 다시 들여보내지 못하게 합니다. 예를 들어 ripgrep 명령 끝에 `--glob '!vendor/**'`를 붙이고, Git 명령에는 명시적인 `:(exclude)vendor/**` pathspec을 줍니다. 요청 범위가 `vendor/`뿐이라면 검토할 파일이 남지 않았다고 보고합니다.

`.agents/notes/archived/`도 산문 검토와 편집에서 제외합니다. 보관된 Agent Notes는 동결된 스냅샷입니다. 과거의 인바운드 인용을 이해하려고 정확한 대상을 살펴볼 수는 있지만, 산문이나 아웃바운드 링크를 현대화하려고 건드리지 않습니다.

생성된 카탈로그, 스냅샷, 픽스처는 파생물로 취급합니다. 편집 전에 모든 소비자를 추적합니다. 원본 JSDoc이 생성된 모델 노출 카탈로그에도 들어갈 수 있기 때문입니다. 소유 원본이나 시나리오를 먼저 편집한 뒤 모든 파생물을 다시 생성합니다. 생성기가 소유자 산문에서 요약을 뽑아낸다면, 뽑힌 문장이 그 표면에서 완전하도록 만듭니다. 이중 언어 쌍에는 영구적인 소유자가 없습니다. 업데이트에서는 어느 언어든 작성된 쪽이 될 수 있습니다. [가벼운 일상 경로](../../../docs/AGENTS.md#writing-rules)를 따르고, 대응 쪽은 최소한으로 수정한 뒤 쌍을 다시 기록합니다.

## 완전한 명제를 보존합니다

편집하기 전에 단락의 모든 명제를 파악합니다. 관련된 각 항목을 보존합니다.

- 행위자와 행동
- 조건, 시점, 순서
- must, may, never 같은 양상(modality)
- 부정적 보장과 예외
- 소유권, 부작용, 실패 방식, 결과

형용사, 반복, 서술은 모든 사실 절이 살아남고 결과가 더 명확할 때만 제거합니다. 단어 수가 줄었다는 것만으로는 개선이 아닙니다.

사용 지점에는 완전한 로컬 계약을 둡니다. 호출자나 유지보수자에게 필요한 동작, 실패, 소유권, 결과를 그 자리에 적습니다. 아키텍처, 근거, 알고리즘, 이력, 확장 예시는 소유 문서로 적극적으로 링크합니다. 설명 하나에는 자리가 하나이며, 필수 계약 사실은 로컬에서 반복될 수 있습니다.

근거를 생략하면 오용이나 잘못된 단순화가 일어날 수 있다면, 자명하지 않은 근거를 유지합니다. 그렇지 않다면 결과를 진술하고 근거의 자리로 링크합니다.

## 산문 위치별 필수 범위

이것은 한 방향으로만 줄이는 과정이 아닙니다. 코드, 타입, 구조가 아래의 필수 계약을 전달하지 못하면 산문을 추가하거나 복원합니다. 그 사실이 이미 로컬에서 자명하다면 주석을 추가하지 않습니다.

- **공개 JSDoc:** 호출자에게 보이는 반환값의 구분, throw 또는 reject, 부작용, 소유권, 시점, 취소, 내구성을 문서화합니다.
- **내부 주석:** 지역적이지 않은 구조와 분명히 복잡한 지역 구조의 방향을 잡아 줍니다. 여기에는 불변식, race 순서, 소유권, 보안 경계, 놀라운 실패 동작이 포함됩니다. 제어 흐름 서술과 코드 재진술은 삭제합니다.
- **모듈 주석:** 모듈의 역할, 의존성, 책임, 자명하지 않은 아키텍처 선택을 밝힙니다. 아키텍처 선택은 소유 설명으로 링크합니다.
- **테스트:** 자명하지 않은 테스트 설계만 설명합니다. 즉 픽스처, 단언, 플랫폼 대응, 실제 진입 경로, 간접 관찰이 왜 필요한지를 다룹니다. 단계별 설명과 목록은 삭제합니다.
- **쿡북:** 사전 조건, 필수 작업, 실제 진입 경로, 관찰 가능한 검증, 간결한 경고를 포함합니다.
- **README:** 소비자 계약을 포함합니다. 설정, 의미, 실패, 제한 사항, 확장 지점, 모델에 보이는 효과가 여기에 해당합니다. 패키지가 소유한 안정적인 모델 노출 텍스트는 인용하고, 생성된 카탈로그와 패키지 간 소유자는 링크합니다. 지속되는 공백과 유지보수자의 함정은 남기되, 일상적인 정리 목록은 남기지 않습니다. [패키지 README 요구 사항](../../../docs/cookbook/adding-a-package.md#4-write-the-package-readme)을 따릅니다.
- **Agent Notes:** 고유한 근거, 메커니즘, 대안, 결과, 출시된 검증 증거, 명시된 검증 공백을 유지합니다. 구현된 Agent Notes는 출시된 현실을 현재 시제로 진술합니다. 계획 체크리스트는 제거하되, 결정을 고정하는 증거는 제거하지 않습니다.
- **사후 분석(Postmortems):** 사건 순서, 증거, 인과 사슬, 영향, 재발 방지를 유지합니다. 인과를 입증하지 않는 반복적인 설득이나 구현 세부 사항은 제거합니다.
- **스킬과 에이전트 지침:** 행동 가드레일과 "지침이지 스크립트/체크리스트가 아님" 같은 명시적 범위 제한을 진술합니다. 워크플로는 간결하게 유지하고 진실 공급원을 링크합니다.
- **예시와 설정 주석:** 접근 제한, 자명하지 않은 연결이나 로드 순서, 보안 입장, 재생 동작, 예외, 가능한 오용을 설명합니다. 설정에 이미 드러난 항목은 서술하지 않습니다.
- **프롬프트와 화면에 보이는 문자열:** 문구를 곧 동작으로 취급합니다. 클라이언트 UI 문구는 타입이 지정된 locale 사전에 두고, Cordis-free 프리미티브에는 명시적인 현지화 props로 전달합니다. 텍스트, 접근성 이름, 툴팁, 플레이스홀더, 형식 템플릿을 함께 검토한 뒤 `verify-client-ui-i18n`을 실행합니다. 플러그인의 `meta.title`과 `meta.description`을 포함한 영어 UI 문구는 sentence case를 사용합니다. 첫 단어, 고유명사, `Chrome DevTools`, `Git`, `MCP` 같은 제품명만 대문자로 씁니다(`Git Worktrees`가 아니라 `Git worktrees`). 중국어 문구는 중국어 관례를 따릅니다. 모델에 보이는 텍스트와 저장소가 요구하는 GUI 증거는 소유 실행 스냅샷을 갱신합니다. 승인된 범위에 소유 시나리오가 없으면 문구는 그대로 두고 보류 사실을 보고합니다. 산문만 고치는 편집에 조용히 포함시키지 않습니다.
- **진단 메시지:** 자명하지 않을 때 실패한 대상이나 경로, 위반된 규칙, 수정 방법을 명시합니다. 내부 실행 서술은 제거합니다.

검색 가능한 메커니즘 이름과 의미 있는 양상, 시간, 부정 강조는 보존합니다. 장식용 강조만 정규화합니다.

## 워크플로

1. 범위, 모드, 현재 브랜치 또는 PR 기준, 적용되는 `AGENTS.md` 파일을 확인합니다. 관련 없는 브랜치는 살펴보지 않습니다.
2. 단락을 판단하기 전에 [문서 표준](../../../docs/AGENTS.md)과 소유 코드 또는 문서를 읽습니다. 보정이 필요하거나 낯선 사례라면 [정제된 예시](references/examples.md)를 읽습니다.
3. 가장 큰 파일만 보지 말고 요청된 범위를 검사합니다. 검색과 단어 수로 후보를 찾은 다음, 의미 차원에서 단락을 판단합니다.
4. 각 후보를 keep, add, trim, restore, restructure, defer로 분류합니다. 작업이 편집을 승인한 경우에만 명확한 변경을 적용합니다. 삭제 목표를 채우려고 편집을 만들어 내지 않습니다.
5. 파생 산출물보다 소유자를 먼저 갱신합니다. 새 규칙을 알게 되면 유사한 단락을 다시 확인합니다.
6. 관련된 좁은 검사, 문서 게이트, `git diff --check`, 화면 문자열의 동작 테스트를 실행합니다. 최종 diff에 `vendor/` 경로가 없는지 확인합니다. 우연히 vendor가 매칭되었다면 깨끗한 제외 이력을 주장하지 말고 그대로 보고합니다.
7. 검사한 범위, 명확한 변경, 의도적으로 유지한 것, 보류한 사례, 실제로 실행한 검사를 보고합니다.

## 판단이 애매한 경우

사례가 애매한 것은 두 개 이상의 버전이 완전한 명제 규칙을 만족하면서 받아들여진 원칙끼리 맞바꿀 때뿐이며, 이 스킬이 그 트레이드오프를 이미 해결하지 못한 경우입니다. 명제를 보존하는 답이 하나뿐인 재작성은 애매하지 않습니다.

automatic 모드에서는 승인된 경우 명확한 편집을 적용하고, 실제로 애매한 사례는 질문하지 않고 보고합니다. 진행하려고 명제를 약화시키지 않습니다.

interactive 모드에서는 유사한 단락을 지배 원칙 아래 묶습니다. 실행 가능한 버전을 두세 개 제시하고 하나를 추천하며, 사실적 또는 구조적 차이를 밝힙니다. 열등한 대안을 들러리로 내놓지 않습니다. 사용자가 요청한 채널을 사용합니다. 인라인 코멘트로 PR을 보정하는 경우, 추천하는 임시 버전을 diff에 두고 대안은 그 정확한 줄에 첨부합니다.

사용자가 결정하면 원칙과 버전을 PR 이력이나 리뷰어 서술 없이 [예시](references/examples.md)로 정제하고, 배운 규칙을 범위 안의 모든 유사한 단락에 적용합니다.
