# 안정적인 DSH CI 테스트

테스트는 개발자 워크스테이션에서 단독으로 실행될 때만이 아니라, 저장소의 실제 CI 토폴로지에서도 올바르게 동작해야 한다. 이 스킬은 격리와 신뢰성에 관한 결정을 담당한다. 저장소의 테스트 계층 정책을 대체하지 않으며, 푸시에 쓸 명령을 모두 선택하지도 않는다.

## 소유 규칙 읽기

- unit, coverage, expected-output, snapshot, browser, real-API 증거를 고를 때는 [테스트 정책](../../../docs/testing.md)을 따른다.
- lifecycle, subprocess, cancellation, teardown 동작은 [방어 패턴](../../../docs/defensive-patterns/general.md)을 따른다.
- worker나 job 토폴로지가 테스트에 영향을 주면 활성 Vitest 설정과 GitHub workflow를 읽는다.
- 기록된 세션 시나리오는 [snapshot 지침](../../../snapshots/AGENTS.md)도 따른다.
- 테스트 설계가 타당해진 뒤에는 [dsh-pre-push-checks](../dsh-pre-push-checks/SKILL.md)로 아웃고잉 검증을 고른다.

## 실행 토폴로지 모델링

활성 설정이 분리를 증명하지 않는 한, 다음 계층들이 겹칠 수 있다고 가정한다.

1. 하나의 Vitest 파일 안의 테스트.
2. 별도의 Vitest 파일 또는 worker 프로세스.
3. 하나의 job 안에서 독립적으로 실행되는 Vitest 또는 저장소 게이트 프로세스.
4. 같은 호스트를 공유하는 서로 다른 Actions job의 runner.

프로세스 분리는 호스트 포트, 예측 가능한 파일 시스템 경로, 외부 서비스, 데이터베이스, 소켓, 상속된 자식 프로세스를 격리하지 않는다. 획득하는 모든 리소스에 대해 소유자, 원자적 할당 메커니즘, 관찰 가능한 준비 신호, 등록된 정리 작업, 정지 상태를 확인하는 완료 신호를 식별한다.

fixture 하나에 격리가 없다는 이유만으로 스위트 전체를 직렬화하지 않는다. 먼저 배타적 범위를 좁히거나 리소스 할당을 바꾼다. 순차 Vitest 블록은 같은 호스트의 다른 파일, 프로세스, job, runner로부터 리소스를 보호하지 못한다.

## 리소스를 원자적으로 할당

가용성을 확인한 뒤 나중에 점유하지 말고, 리소스 소유자의 할당기를 사용한다.

- 네트워크 fixture는 `listen(0)`으로 loopback에 바인딩하고, 서버가 listening을 보고한 뒤에만 할당된 주소를 읽는다. 빈 포트를 스캔한 뒤 나중에 바인딩하지 않는다.
- 비공개 테스트별 임시 루트는 `mkdtemp`로 만든다. 예측 가능한 공유 경로를 점유하지 않는다.
- 공유 데이터베이스, 소켓, 세션, 출력 위치에는 테스트별 고유 namespace를 준다.
- 경로가 이미 존재하면 안 되는 경우에는 exclusive creation을 사용한다.
- 안정적인 recorded identifier와 일시적인 transport 주소를 분리한다. 실제 리소스에 recorded 값을 강제로 쓰게 하지 말고, fixture 안에서 변환한다.

파서 입력이나 기대값으로만 쓰인 리터럴 경로와 URL은 획득한 리소스가 아니다. 고정처럼 보인다는 이유만으로 다시 쓰지 않는다.

## 프로세스 전역 상태 격리

`process.env`, `cwd`, fake timer, locale과 timezone, module mock, registry, console hook, `globalThis`, 전역 `fetch` 가로채기를 배타적 가변 리소스로 본다.

가능하면 주입된 의존성이나 인스턴스 로컬 어댑터를 쓴다. 변경이 필요하면 다음을 따른다.

- 원래 값이 없었는지 있었는지 기록한다.
- 그 정확한 상태를 복원한다.
- 복원을 즉시 등록한다.
- 가장 작은 변경 범위를 `try/finally`로 감싼다.
- 지역 `finally` 이전에 실패할 가능성이 있으면 `afterEach` 폴백을 둔다.
- fixture가 소유한 가장 좁은 정확한 요청이나 호출만 가로챈다.

## 플랫폼이 소유한 의미 존중

CI는 Windows와 POSIX 호스트에서 같은 스위트를 실행하며, 운영체제가 소유한 값은 테스트가 쓴 대로 돌아오지 않을 수 있다.

- 값을 되써 넣는 것은 assertion이 되쓰기 실패를 허용할 때만 안전하다. 지문이 어차피 무효화된다는 것을 증명하려고 파일 `mtime`을 복원하는 것은 모든 플랫폼에서 성립한다. 기록이 여전히 유효하다는 것을 증명하려고 복원하는 것은 무손실 왕복을 가정하는데, NTFS의 100나노초 tick은 소수 밀리초 값에 대해 그것을 보장하지 않는다. assertion이 복원에 의존한다면, 기억해 둔 값이 아니라 새로 읽은 값에서 기대값을 가져온다.
- Windows는 환경 변수 이름을 대소문자 구분 없이 매칭하므로, `http_proxy`와 `HTTP_PROXY`를 별도 키로 심는 fixture는 그곳에서 항목 하나만 남는다.
- Windows는 파일 핸들을 비동기적으로 해제하므로, POSIX에서는 즉시 완료되는 rename이나 제거에는 관측된 경합 크기에 맞춘 제한된 재시도가 필요하다.
- Windows에는 POSIX의 권한이나 signal 의미가 없다. 그에 의존하는 케이스는 모든 플랫폼에서 약화된 assertion을 쓰지 말고, 이유를 명시한 플랫폼 skip을 둔다.

플랫폼과 무관하게 성립하는 관찰을 선호한다. 정말 그럴 수 없는 경우에만 해당 플랫폼에서 명시적으로 제외한다.

## 타임아웃을 lane 예산에 맞춘다

`describe`나 케이스 timeout은 runner의 `--testTimeout`에 양보하지 않고 그것을 덮어쓴다. 따라서 lane 예산보다 낮은 값은 CI가 이미 허용한 시간을 줄이고, 같은 리터럴이 기본값이 더 작은 호스트에서는 오히려 늘리는 것처럼 보인다. 프로세스 생성에 묶인 스위트는 lane 예산을 따른다. 더 짧은 값에는 그 이유를 함께 적는다.

hook 예산은 테스트 예산과 함께 올린다. setup과 teardown도 같은 경합을 겪으므로, 케이스 예산만 올리면 경합으로 인한 실패가 `afterEach`로 옮겨 갈 뿐이다.

타임아웃 자체가 검증 대상이라면, 바깥 대기 시간을 테스트 중인 타임아웃보다 훨씬 길게 둔다. 20 ms 데드라인이 실제로 발동하는지 증명하는 케이스가 하네스 자체의 대기와 경쟁하면, 부하에 따라 어느 데드라인이 먼저 보고될지가 결정되어 버린다.

## 상태에 동기화

고정 sleep은 setup이 끝났다거나 cleanup이 정착했다는 증거가 아니다.

- 명시적인 readiness 이벤트, handshake, 상태 전이, 소유한 promise, 외부에서 관찰 가능한 조건을 기다린다.
- deferred promise나 barrier로 경합을 결정적인 지점에 두고, 관련 작업이 실제로 겹쳤음을 증명한다.
- timeout은 대기를 제한하는 데만 쓰고, assertion을 올바르게 만드는 조건으로 쓰지 않는다.
- 제품 동작이 아닌 한, 스케줄러에 의존하는 순서를 assert하지 않는다.
- 시간 자체가 대상이라면 시계를 주입하거나 가짜로 만들고, 실제 timer는 항상 복원한다.

## 정지 상태까지 dispose

리소스를 획득하자마자 정리를 등록해, assertion이 실패해도 리소스가 해제되게 한다. 정리는 새 callback이나 요청을 멈추고, listener를 분리하고, 전역 hook을 복원하고, 소유한 작업을 종료하고, 자식 프로세스 종료, 서버 close, worker 종료, 또는 그와 동등한 완료 신호를 기다린다.

소유한 완료 신호를 기다리지 않고 `abort()`, `close()`, `kill()`만 호출하는 것은 불완전한 teardown이다. 늦은 완료가 가능하다면, dispose가 그것이 다른 테스트를 변경하지 못하게 막는다는 것을 증명한다.

## 의도한 회귀를 증명

- 가능하면 수정 전에 일반적인 회귀가 실패하는 것을 관찰한다.
- 새 정적 검사나 corpus 가드라면, 거부 대상 사례를 일시적으로 넣고 의도한 실패가 나는지 관찰한다.
- 경합이라면 barrier로 겹침을 증명한다. 반복 실행만으로는 경합 테스트가 되지 않는다.
- 포트, 소켓, 공유 경로, 서브프로세스 같은 호스트 리소스라면, 교차 프로세스 격리가 수정의 일부일 때 독립 테스트 프로세스를 동시에 실행한다.
- fixture가 자체 데드라인으로 spawn한다면, 자식의 종료 상태를 assert하기 전에 signal이나 timeout이 자식을 끝내지 않았음을 먼저 assert한다. 그래야 강제 종료된 자식이 상태 불일치가 아니라 timeout으로 보고된다.
- 컴포넌트의 자기 보고 대신, 외부 상태, 이벤트, 파일, 로그, 종료, dispose를 관찰한다.

stress 실행은 결정적인 회귀 테스트를 보완할 뿐, 대체하지 않는다.

## flake를 가리는 수정 거부

결정적인 로컬 테스트의 근본 원인 수정으로 다음을 제시하지 않는다.

- 기다리는 상태를 밝히지 않은 채 timeout을 늘리는 것;
- retry를 추가하는 것;
- 모든 파일을 직렬화하는 것;
- 에러나 unhandled rejection을 삼키는 것;
- assertion을 약화하는 것;
- 불안정한 동작을 정규화해 없애는 것;
- cleanup이나 assertion 전에 sleep을 추가하는 것.

retry는 실제 API 정책에 따라 문서화된 일시적 외부 provider 테스트에서만 유효하다. 그 예외는 외부 경계에만 둔다.

예산을 복원하는 것은 가리기가 아니다. 스위트가 이미 받았던 lane 예산까지 올리는 것, 또는 측정된 runner 경합에 맞춰 제한된 retry를 정하는 것은, 기다리는 작업을 명시하고 lane이 허용한 값을 되돌려 줄 뿐이다. 검토하지 않은 대기 주위에 여유를 만들어 내지 않는다.

## 기존 flake 진단

기존의 확률적 CI 실패는 [CI flake 진단 워크플로](references/ci-flake-diagnosis.md)를 읽는다. 진단만 요청받은 경우에는 읽기 전용으로 유지한다. 사용자가 수정도 요청하지 않았다면 원인과 증거를 보고한다.

## 검증과 보고

영향을 받는 동작에 대한 가장 작은 집중 회귀를 실행한다. 변경이 그 위험을 실제로 소유할 때만 토폴로지별 증거를 추가한다.

- 전역 변경에는 복원 증거가 필요하다.
- lifecycle이나 subprocess 작업에는 정지 상태 teardown 증거가 필요하다.
- 포트, 소켓, 공유 경로에는 동시 독립 프로세스 증거가 필요하다.
- 새 가드에는 negative control이 필요하다.

푸시 전에는 [dsh-pre-push-checks](../dsh-pre-push-checks/SKILL.md)를 사용한다. 정확한 명령과 관찰된 결과를 보고한다. retry, 건너뛴 테스트, 대기 중인 CI를 통과한 것처럼 설명하지 않는다.
