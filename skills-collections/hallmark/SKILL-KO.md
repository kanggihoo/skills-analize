# Hallmark (홀마크)

AI 코딩 어시스턴트를 위한 프론트엔드 디자인 스킬입니다. 생성형 AI가 찍어낸 듯한 UI가 아닌, **사람 디자이너가 정성스럽게 빚어낸 듯한 완성도 높은 UI**를 만듭니다.

Hallmark는 의도적으로 뚜렷한 주관을 가지며, 간결하고 원칙을 엄격히 고수합니다. AI 특유의 천편일률적인 디자인(AI-slop)을 타파하기 위해 정립된 업계 합의(Anthropic의 프론트엔드 디자인 스킬, Claude 프론트엔드 미학 쿡북, 2026년 "촉각적 반란(tactile rebellion)" 운동 등)를 바탕으로 엄격한 규칙을 적용하며, LLM이 흔히 빠지는 기본값(템플릿스러운 결과물)으로 회귀하는 것을 단호히 거부합니다.

**차별화 요소:** Hallmark는 단순한 색상 변화뿐만 아니라 **구조적 다양성(structural variety)**을 핵심으로 강조합니다. 서로 다른 두 요구사항에 대해 동일한 리듬(예: 히어로 → 3열 카드 기능 소개 → CTA → 푸터)의 페이지를 절대 반복하지 않습니다. 색상만 바꾼 템플릿 사이트가 아니라, 완전히 다른 사이트처럼 느껴져야 합니다. ([`references/structure.md`](references/structure.md) 참조)

**Powered by Together AI.**

## 스킬 사용 방법

Hallmark는 1개의 기본 동작과 3개의 명시적 명령어를 제공합니다.

| 호출 방식 | 수행 작업 |
| --- | --- |
| *(기본값)* | 사용자가 새로운 것을 디자인하거나 만들도록 요청한 경우. 아래의 **디자인 흐름(Design flow)**을 따릅니다. |
| `hallmark audit <대상>` | 대상 코드를 읽고 안티 패턴 목록을 기준으로 점수를 매겨 우선순위가 지정된 체크리스트를 반환합니다. **코드를 직접 수정하지 않습니다.** |
| `hallmark redesign <대상> [--mood <이름>]` | 대상의 콘텐츠와 의도를 유지하면서 시각적 구조를 재설계합니다. **사용자가 명시적으로 전체 재구축을 승인하지 않는 한 기존 구현 범위 내에서 작업합니다.** 새로운 섹션 리듬, 헤딩 배치, 컴포넌트 어조를 적용하되, 기존 라우트, 컴포넌트 구조, 카피 의도, 브랜드, 정보 아키텍처(IA)를 보존하고 요청된 범위의 시각/인터랙션 계층만 교체합니다. |
| `hallmark study <스크린샷 \| URL>` | 사용자가 첨부한 디자인 레퍼런스 이미지 또는 웹페이지 URL에서 **DNA**(매크로 구조, 아키텍처, 폰트 페어링, 컬러 앵커)를 추출하여 진단 리포트를 생성합니다. 이후 추출된 DNA를 사용해 사용자 콘텐츠를 재구성하거나 독립형 `design.md`로 내보낼 수 있습니다. URL(`http://`, `https://`)은 자동으로 URL 모드로 처리되며 그 외는 이미지 모드로 처리됩니다. **URL 모드**는 HTML/CSS를 읽어 정확한 폰트명과 색상값을 추출하지만 시각적 리듬 판단에는 한계가 있습니다. 진단 후 사용자는 DNA 기반 빌드, `design.md`로 고정, 또는 진단만 확인하고 종료하는 3가지 후속 조치가 가능합니다. **절대 픽셀을 그대로 복제하지 않으며, 템플릿 마켓플레이스 URL은 거부합니다.** ([`references/study.md`](references/study.md) 참조) |

사용자가 `audit`, `redesign`, `study`에 명확히 매핑되지 않는 입력을 한 경우 기본 동작으로 처리합니다. 동사 없이 이미지나 URL만 전달된 경우 다음과 같이 질문합니다:
> *"이 레퍼런스에서 디자인 DNA를 추출(`study`)할까요, 아니면 새로운 빌드를 위한 참고 자료로 사용할까요?"*

**구현 안전 가드레일:** Hallmark는 디자인 스킬이며, 코드베이스를 임의로 파괴할 권한이 없습니다. 기존 프로젝트에서는 다음을 준수합니다:
- 사용자가 명시적으로 삭제를 요청하거나 삭제 파일 목록이 포함된 계획을 승인하지 않는 한, 프로덕션 파일, 라우트 트리, 컴포넌트 디렉토리, 기존 웹사이트를 절대 삭제하지 않습니다.
- 기존 파일의 인플레이스(in-place) 수정이나 기존 라우트에 연결되는 추가 컴포넌트/토큰 생성을 기본으로 합니다. 여러 컴포넌트를 제거해야 하는 경우 먼저 사용자에게 확인을 받습니다.
- PDF, README, `.md` 기획서, 문서, 회의록, 피치덱은 참조 자료로만 취급하며, 문자 그대로 페이지에 복사하지 않습니다.
- 편집 전 수정/생성/삭제할 파일 목록을 정확히 밝힙니다. 삭제는 명시적 승인이 필수입니다.

기본 디자인 흐름은 항상 테마를 선택합니다. 기본적으로 **21개 카탈로그 테마** 중 하나를 선택하며 다양화 규칙에 따라 순환합니다. 브리프에 명확한 창작 의도(브랜드 컬러 지정, 복합적인 무드 요구 등)가 있을 때는 원오프(one-off) OKLCH 팔레트와 무료 폰트 페어링을 구성하는 *커스텀(custom)* 브랜치로 자동 분기합니다. 일반적인 브리프에서는 사용자가 카탈로그/커스텀이라는 단어를 의식하지 않고 자연스럽게 진행됩니다.

## 모든 명령어에 공통 적용되는 6가지 원칙

다음 6가지 원칙은 특정 명령어에 국한되지 않고 기본 디자인, `audit`, `redesign`, `study`, 컴포넌트 단위 작업 모두에 적용됩니다.

1. **출력 전 자체 비평 (Pre-emit self-critique)**: 결과물을 출력하기 전 6가지 축(철학, 위계, 실행력, 구체성, 절제미, 다양성)에 대해 1~5점 척도로 평가합니다. **3점 미만**인 항목이 있으면 즉시 수정 패스를 거칩니다. 아티팩트 상단에 점수를 스탬프로 남깁니다 (`/* Hallmark · pre-emit critique: P5 H4 E5 S4 R5 V5 */`).
2. **정직한 카피 — 허위 콘텐츠 생성 금지 (Honest copy)**: 사용자가 구체적인 수치를 제공하지 않았다면 임의로 수치를 지어내지 마십시오. 통계형 레이아웃, 비교 테이블 등은 실제 데이터, 플레이스홀더(`—` 표시 및 '확인 필요' 라벨), 또는 다른 매크로 구조를 사용해야 합니다. *"+47% 전환율"*, *"50,000+ 팀이 신뢰"* 등의 임의 생성 문구는 금지됩니다. (추천사, 로고 목록도 동일)
3. **토큰 고정 — 렌더링 도중 임의 스타일 추가 금지 (Locked tokens)**: 테마가 결정되면 아티팩트의 모든 색상과 `font-family`는 반드시 정의된 네임드 토큰(`var(--color-accent)`, `font-family: var(--font-display)`)을 참조해야 합니다. 토큰 블록을 우회하는 인라인 OKLCH/HEX/RGB 값이나 임의 폰트 선언은 허용되지 않습니다.
4. **가짜 브라우저/디바이스 프레임 직접 그리기 금지 (Re-drawn chrome forbidden)**: 가짜 브라우저 상단바(신호등 점 + URL 알약 형태), 가짜 스마트폰 프레임, 가짜 터미널/코드 창 프레임을 직접 그리지 마십시오. 실제 환경에서 캡처한 스크린샷을 `<figure>`(헤어라인 테두리 정도)로 감싸거나, 프레임 없이 콘텐츠 자체로 승부하십시오.
5. **모바일 반응형 검증 — 320 / 375 / 414 / 768 px**: 모든 출력물은 4가지 해상도에서 완벽하게 렌더링되어야 합니다. 가로 스크롤 금지(`html`, `body`에 `overflow-x: clip`), 버튼/링크 텍스트 줄바꿈 방지, 이미지 그리드 트랙 `minmax(0, 1fr)` 적용, 모바일에서 섹션 헤더 단일 컬럼 축소 등이 포함됩니다.
6. **타이포그래피 순수성 — 이탤릭 헤딩 금지 (No italic headers)**: 제목 및 디스플레이 폰트는 항상 로만(`font-style: normal`) 스타일을 유지합니다. 제목 중간에 특정 단어만 이탤릭으로 강조하는 것(`Built to <em>think</em>`)은 전형적인 AI 티를 내는 패턴입니다. 굵기, 포인트 컬러, 언더라인으로 강조하십시오. 이탤릭은 본문 문단 내부에서만 허용됩니다.

## 요청이 페이지가 아닌 단일 컴포넌트인 경우

전체 디자인 흐름에 진입하기 전에 **범위를 확인**하십시오. 다음 신호가 감지되면 **컴포넌트 스코프 흐름(Component-scope flow)**을 실행합니다:

**컴포넌트 스코프 신호:**
- 단일 UI 요소 명시: *버튼, 인풋, 카드, 모달, 드롭다운, 툴팁, 셀렉트, 체크박스, 스위치, 탭, 칩, 배지, 배너, 스낵바, 팝오버, 슬라이더, 데이트피커, 아바타*.
- 요구사항이 짧고(30단어 이하) 하나의 요소를 가리킴.
- 대상 파일이 단일 컴포넌트임 (예: `./Button.tsx`, `./components/Input.css`).
- 사용자가 *"X 버튼만"*, *"이 요소 하나만"*과 같이 명시함.

### 컴포넌트 스코프에서 유지되는 항목
- **Step 0 프리플라이트 스캔**: 기존 프로젝트의 토큰, 폰트, 프레임워크를 읽어 계승.
- **Step 1 장르 감지**: 에디토리얼, 모던-미니멀, 애트모스페릭, 플레이풀 중 주변 UI 장르를 계승.
- **8가지 상태 규칙 (더욱 엄격)**: 모든 인터랙티브 컴포넌트는 **8가지 상태 전체**를 필수로 구현해야 함 (기본, 호버, `:focus-visible`, `:active`, 비활성화, 로딩, 에러, 성공).

### 컴포넌트 스코프에서 생략되는 항목
- 매크로 구조 선택, 네비게이션/푸터 아키텍처 선택, 히어로 폴리싱 패턴, 배경 일러스트 등의 장식 요소, 다중 섹션 프리뷰, 프로젝트 히스토리(`.hallmark/log.json`) 기록.

### 컴포넌트 스코프가 출력하는 2개 파일
1. **컴포넌트 아티팩트**: 프로젝트 컨벤션에 맞는 단일 독립 파일 (예: `Button.tsx` 또는 `button.css` + `button.html`). 토큰 변수를 사용함.
2. **8개 상태 데모 래퍼 (`<ComponentName>.preview.html` 또는 `.preview.tsx`)**: 8가지 상태(default, hover, focus, active, disabled, loading, error, success)를 수직으로 나열하여 한눈에 확인할 수 있는 독립형 데모 페이지.

## 기본 디자인 흐름 (Design Flow)

### Step 0. 사전 스캔 (Pre-flight scan)
기존 프로젝트 코드베이스(`package.json`, `tailwind.config.*`, CSS 파일 등)를 먼저 읽어 기존 폰트, 컬러 팔레트, 모션 라이브러리, 간격 스케일, 프레임워크를 파악하고 보존합니다. 만약 루트에 `design.md`가 존재하면 이를 잠정적인 단일 진실 공급원(SSOT)으로 삼습니다.

### Step 1. 디자인 맥락 게이트 (Design-context gate)
코드 작성 전 3가지를 확인합니다:
1. **타겟 사용자(Audience)**: 누가 사용하는가?
2. **사용 사례(Use case)**: 이 페이지가 유도해야 하는 단 하나의 핵심 액션은 무엇인가? (가입, 구독, 구매 등)
3. **톤(Tone)**: *에디토리얼, 브루탈리스트, 소프트, 유틸리테리안, 럭셔리, 플레이풀, 테크니컬, 오스티어(절제된)* 중 극단적인 톤 선택. ("깔끔하고 모던함"은 톤이 아님)

사용자에게 질문을 던지되, 사용자가 "알아서 해줘(go ahead)"라고 하거나 답변이 없으면 브리프에서 합리적으로 추론하여 명시하고 진행합니다. 또한 4대 장르(에디토리얼, 모던-미니멀, 애트모스페릭, 플레이풀) 중 적합한 장르를 확정합니다.

### Step 2. 매크로 구조(Macrostructure) 우선 선택
디자인 규칙을 로드하기 전, **21개 매크로 구조 인덱스**에서 하나를 선택합니다. 매크로 구조는 헤딩 배치, 본문 구성, 구분선 스타일, 버튼 어조 등을 하나로 묶은 페이지의 골격입니다.
* **다양화 규칙 (필수)**: 최근 작업했거나 프로젝트 로그에 있는 구조와 겹치지 않는 새로운 매크로 구조를 선택해야 합니다.
* **네비게이션(N1a~N13) 및 푸터(Ft1~Ft8) 아키텍처 선택**: 페이지의 구조적 지문에 맞는 네비게이션과 푸터를 함께 결정합니다.

### Step 2.5. 프로젝트 메모리 확인 (`.hallmark/log.json`)
이전 빌드 기록을 조회하여 최근 3~5회 동안 사용된 매크로 구조, 테마, 인리치먼트가 중복되지 않도록 순환(Rotation)시킵니다.

### Step 2.6. 테마 경로 결정
- **studied-DNA**: `study` 진단 후 해당 DNA로 빌드 요청 시 적용.
- **custom**: 사용자가 커스텀 테마를 요구하거나 특정 브랜드 컬러/복합적 무드를 제시한 경우 적용.
- **catalog**: 21개 기본 테마 중 다양화 규칙에 맞춰 선택.

### Step 3. 시각적 룰셋 로드
필요한 가이드 파일만 선택적으로 로드하여 컨텍스트 낭비를 방지합니다. 타이포그래피, 컬러(OKLCH), 레이아웃/공간(4pt 그리드), 모션, 카피, 안티패턴 규칙을 적용합니다.

### Step 4. 히어로 인리치먼트(Enrichment) 결정
대부분의 페이지는 타이포그래피 중심이 가장 강력합니다. 이미지가 필요한 경우 순수 CSS 아트(Tier A) $\rightarrow$ 수제작 SVG(Tier B) $\rightarrow$ 생성형 정적이미지(Tier C) $\rightarrow$ 라이브러리(Tier D) $\rightarrow$ Lottie 애니메이션(Tier E, 최후의 수단) 계층 구조에 따라 제작합니다.

### Step 5. 사전 프리뷰 출력 (Preview)
코드를 작성하기 전, 핵심 사양(매크로 구조, 테마, 인리치먼트, 섹션 구성, 모션, 슬롭 테스트 결과)을 요약한 마크다운 블록을 출력하여 사용자에게 작업 방향을 공유합니다.

### Step 6. 코드 빌드 (Build)
- 헤드라인 길이에 따른 적정 폰트 크기 계산
- 섹션 태그/아이브로우는 세로 스택(상단 태그, 하단 제목) 유지 (좌우 2컬럼 분할 금지)
- 모든 색상은 OKLCH 및 `:root` CSS 커스텀 프로퍼티 사용
- 4pt 기반 간격 스케일 (`--space-sm`, `--space-md` 등)
- 8가지 인터랙션 상태 완벽 구현
- 레이아웃 속성이 아닌 `transform`, `opacity`만 애니메이션 적용
- CSS 상단에 Hallmark 선택 스탬프 주석 추가 및 `.hallmark/log.json` 업데이트
- `tokens.css` 파일 독립 생성 및 내보내기

### Step 7. 슬롭 테스트 (The Slop Test - 58개 관문)
출력 전 58개 항목의 안티-AI-슬롭 체크리스트를 실행하여 모든 항목을 통과(No)해야 합니다. 실패 항목이 있을 경우 코드를 즉시 수정한 후 완성합니다.

## 특수 명령어

### `hallmark audit`
대상 페이지나 코드를 분석하여 AI 특유의 클리셰나 안티패턴이 있는지 감사하고, 수정 우선순위가 포함된 보고서를 출력합니다.

### `hallmark redesign`
기존의 기능과 정보 아키텍처는 보존하면서, 진부한 UI를 세련되고 차별화된 매크로 구조와 테마로 완전히 새롭게 탈바꿈시킵니다.

### `hallmark study`
인상 깊은 웹사이트 URL이나 스크린샷 이미지에서 디자인의 핵심 DNA(구조, 타이포그래피 조합, 컬러 앵커 등)를 역공학적으로 추출하여 분석 리포트를 제공하고, 이를 바탕으로 내 프로젝트를 구축할 수 있도록 지원합니다. (픽셀 단순 복제는 거부)
