# 의심 주도 개발 (Doubt-Driven Development)

## 개요 (Overview)

확신에 찬 답변이 반드시 올바른 답변은 아닙니다. 긴 대화 세션은 컨텍스트가 누적되면서 아무도 눈치채지 못하는 사이에 가정을 '사실'로 둔갑시킵니다. 의심 주도 개발은 사소하지 않은(non-trivial) 결과물이 확정되기 전에, 승인이 아닌 **반증(disprove)**을 목표로 편향된 새로운 컨텍스트(fresh-context)의 리뷰어를 투입하는 규율입니다.

이는 `/review`와 다릅니다. `/review`는 완성된 산출물에 대한 최종 판정입니다. 의심 주도 개발은 작업 진행 중(in-flight)의 자세입니다. 진로 수정 비용이 여전히 저렴할 때 중요한 결정을 교차 검증합니다.

## 사용 시점 (When to Use)

다음 중 하나 이상에 해당할 때 **사소하지 않은(non-trivial) 결정**으로 간주합니다:

- 분기 로직(branching logic)을 도입하거나 수정할 때
- 모듈 또는 서비스 경계를 넘나들 때
- 타입 시스템이나 컴파일러가 검증할 수 없는 속성(스레드 안전성, 멱등성, 순서 보장, 불변식)을 단언할 때
- 정확성이 미래의 코드를 읽는 사람이 볼 수 없는 숨겨진 컨텍스트에 의존할 때
- 영향 범위(blast radius)가 되돌릴 수 없을 때 (프로덕션 배포, 데이터 마이그레이션, 공개 API 변경)

다음 상황에서 이 스킬을 적용하세요:

- 불확실한 상황에서 아키텍처 결정을 내리려 할 때
- 중요 코드를 커밋하기 직전
- 직관적이지 않은 사실("이것은 안전하다", "확장 가능하다", "사양과 일치한다")을 주장하려 할 때
- 완전히 이해하지 못한 코드를 다룰 때

**사용하지 않는 경우:**

- 기계적인 작업 (이름 변경, 포맷팅, 파일 이동)
- 명확하고 모호함이 없는 사용자 지침을 따를 때
- 기존 코드를 읽거나 요약할 때
- 정확성이 자명한 한 줄짜리 변경
- 순수 도구 작업 (테스트 실행, 파일 목록 조회)
- 사용자가 검증보다 속도를 명시적으로 요구했을 때

모든 키 입력을 의심하면 아무것도 출시할 수 없습니다. 이 스킬은 위에서 정의한 중요 결정에만 적용됩니다.

## 로딩 제약 조건 (Loading Constraints)

이 스킬은 3단계(DOUBT)에서 새로운 컨텍스트의 리뷰어를 호출할 수 있는 **메인 세션 오케스트레이터**를 위해 설계되었습니다.

- **페르소나의 `skills:` frontmatter에 이 스킬을 추가하지 마세요.** 3단계를 수행하는 페르소나가 또 다른 페르소나를 호출하게 되며, 이는 오케스트레이션 안티패턴("페르소나는 다른 페르소나를 호출하지 않는다")에 위배됩니다.
- **서브에이전트 내부에서 이 스킬을 적용해야 하는 경우:** 중첩 서브에이전트 생성이 제한되므로, 의심 주도 검토를 중첩 실행할 수 없음을 사용자에게 알리고 메인 세션에서 처리하도록 하는 것이 권장됩니다. 최후의 수단으로만 자기 질문(self-questioning) 폴백을 사용하세요. 이 경우 이전 추론과 엄격히 단절된 새로운 프롬프트로 ARTIFACT와 CONTRACT를 재작성하여 1~5단계를 수행합니다. 이는 완전한 '새로운 컨텍스트'가 아니므로 결과가 불완전함을 표시하고 사용자와 대화 가능할 때 에스컬레이션하세요.

## 진행 절차 (The Process)

스킬 적용 시 다음 체크리스트를 따르세요:

```
의심 사이클 (Doubt cycle):
- [ ] 1단계: 주장 (CLAIM) — 주장과 그것이 중요한 이유 작성
- [ ] 2단계: 추출 (EXTRACT) — 산출물(Artifact)과 계약(Contract) 격리, 추론 과정 제거
- [ ] 3단계: 의심 (DOUBT) — 적대적 프롬프트로 새 컨텍스트 리뷰어 호출
- [ ] 4단계: 조정 (RECONCILE) — 산출물 텍스트와 비교하여 모든 지적 사항 분류
- [ ] 5단계: 종료 (STOP) — 종료 조건 충족 (사소한 지적만 남음, 3사이클 완료, 또는 사용자 승인)
```

### 1단계: 주장 (CLAIM) — 검증할 결정을 명시

결정을 2~3줄로 명확히 서술합니다:

```
주장 (CLAIM): "새로운 캐싱 레이어는 사양에 설명된 읽기 집약적 워크로드에서
              스레드 안전(thread-safe)하다."
중요한 이유 (WHY THIS MATTERS): 여기서 발생하는 레이스 컨디션은 사용자 데이터를 오염시키며
                               QA 단계에서 발견하기 매우 어렵다.
```

주장을 이렇게 간결하게 작성할 수 없다면 그것은 결정이 아니라 단순한 '느낌(vibe)'에 불과합니다. 면밀히 조사하기 전에 먼저 명확히 서술하세요.

### 2단계: 추출 (EXTRACT) — 검토 가능한 최소 단위 분리

새로운 컨텍스트의 리뷰어에게 필요한 것은 결론에 이른 긴 과정이 아니라 **산출물(Artifact)**과 **계약(Contract)**뿐입니다.

- 코드: 전체 파일이 아닌 diff 또는 해당 함수
- 결정: 3~5문장의 제안서 및 만족해야 할 제약 조건
- 단언(Assertion): 주장 및 이를 뒷받침하는 구체적 근거

본인의 추론 과정을 제거하세요. 결론을 전달하면 결론에 대한 동조만 돌아옵니다. 리뷰어가 한 번에 이해할 수 있을 만큼 작아야 합니다 — 500줄짜리 PR이라면 먼저 분해하세요.

### 3단계: 의심 (DOUBT) — 새 컨텍스트 리뷰어 호출

리뷰어의 프롬프트는 반드시 **적대적(adversarial)**이어야 합니다. 질문의 프레이밍이 답변을 결정합니다.

```
적대적 리뷰입니다. 이 산출물의 결함과 문제점을 찾아내세요.
작성자가 지나치게 확신하고 있다고 가정하세요. 다음 사항을 중점적으로 찾으세요:
- 언급되지 않은 숨겨진 가정
- 처리되지 않은 엣지 케이스
- 숨겨진 결합도 또는 공유 상태
- 계약(Contract)을 위반할 수 있는 시나리오
- 깨질 수 있는 기존 컨벤션
- 예상치 못한 입력에 대한 실패 모드

칭찬하거나 요약하지 마세요. 오직 문제점만 찾거나,
철저한 검토 후에도 문제를 찾을 수 없다면 명시적으로 없다고 밝히세요.

ARTIFACT (산출물): <산출물 붙여넣기>
CONTRACT (계약): <계약/요구사항 붙여넣기>
```

**ARTIFACT와 CONTRACT만 전달하세요. 1단계의 CLAIM(주장)은 전달하지 마세요.** 리뷰어에게 내 결론을 넘겨주면 동조 편향이 생깁니다. 리뷰어는 산출물이 계약을 만족하는지 독립적으로 판단해야 합니다.

#### 다중 모델 에스컬레이션 (Cross-model escalation)

단일 모델 리뷰어는 원작자와 동일한 맹점을 공유하기 쉽습니다. 아키텍처가 다른 모델이 이를 잡아낼 수 있습니다. 의심 주도 개발은 중요한 결정에 적용되므로, 다중 모델 검토를 제안하는 것은 불필요한 마찰이 아니라 스킬의 핵심 가치입니다.

**대화형 세션: 항상 제안하세요. 절대 조용히 건너뛰지 마세요.**

**1단계: 사용자에게 질문**

위 3단계의 단일 모델 검토 후, 4단계(조정)로 넘어가기 전에 잠시 멈추고 묻습니다:

> *"단일 모델 검토가 완료되었습니다. 다른 모델의 2차 의견을 받아보시겠습니까? 옵션: Gemini CLI, Codex CLI, 수동 외부 검토(직접 복사하여 외부 도구에 붙여넣기), 또는 건너뛰기."*

이 질문은 대화형 의심 사이클에서 필수입니다. 비용과 시간을 감수할 가치가 있는지 결정하는 것은 에이전트가 아니라 사용자입니다.

**2단계: 사용자가 CLI를 선택한 경우 — 검증 후 실행**

1. PATH에 도구가 있는지 확인 (`which gemini`, `which codex`)
2. 전체 프롬프트를 넘기기 전에 정상 동작하는지 테스트 (`gemini --version` 등)
3. 필수 플래그, 인증, 환경 변수를 포함한 정확한 실행 명령어를 사용자에게 확인
4. ARTIFACT + CONTRACT + 적대적 프롬프트**만** 전달 (세션 컨텍스트, CLAIM 제외)
5. 셸 이스케이프 주의 (따옴표, 백틱 문제 방지를 위해 stdin 파이프 또는 임시 파일 사용)
6. 출력을 받아 4단계(조정)로 전달

```bash
# 적대적 프롬프트 + ARTIFACT + CONTRACT를 임시 파일에 작성 후 stdin으로 파이프 실행
# Codex (읽기 전용 샌드박스로 작업 공간 쓰기 방지):
codex exec --sandbox read-only -C <repo-path> - < /tmp/doubt-prompt.md

# Gemini (플랜 승인 모드로 읽기 전용 실행):
gemini --approval-mode plan -p "" < /tmp/doubt-prompt.md
```

**3단계: CLI를 사용할 수 없거나 실패한 경우**

실패를 명시적으로 알리고 수동 실행, 다른 도구 시도, 건너뛰기 중 선택하게 하세요. 조용히 단일 모델로 후퇴하지 마세요.

**4단계: 사용자가 건너뛰기를 선택한 경우**

출력에 이를 명시하고(*"단일 모델 결과만으로 진행합니다"*) 4단계로 이동합니다. 건너뛰는 것은 괜찮지만 '조용한 건너뛰기'는 안 됩니다.

**비대화형 컨텍스트(CI, `/loop`, 자율 실행):**

- 다중 모델 검토는 **건너뛰며**, 출력에 이를 명시해야 합니다: *"다중 모델 검토 건너뜀: 비대화형 컨텍스트."*
- **사용자의 명시적 승인 없이 외부 CLI를 실행하지 마세요.**

### 4단계: 조정 (RECONCILE) — 발견 사항 반영

리뷰어의 출력은 판결이 아니라 데이터입니다. **오케스트레이터는 여전히 당신입니다.** 리뷰어의 의견을 무비판적으로 수용(rubber-stamp)하는 것은 무시하는 것만큼이나 나쁜 실패 모드입니다. 산출물 텍스트와 비교하여 다음 **우선순위 순서**대로 분류하세요:

1. **계약 오해 (Contract misread)** — 제공한 CONTRACT가 불명확하여 잘못 지적된 경우. 계약을 먼저 수정한 뒤 다음 사이클에서 재분류.
2. **유효하며 조치 필요 (Valid + actionable)** — 산출물 수정이 필요한 실제 결함. 수정하고 사이클 재실행.
3. **유효한 트레이드오프 (Valid trade-off)** — 문제는 실재하지만 수정 비용이 수용 비용보다 큰 경우. 사용자가 볼 수 있도록 명시적으로 문서화.
4. **노이즈 (Noise)** — 리뷰어가 갖지 못한 컨텍스트상 실제로는 올바른 내용인 경우. 기록하고 넘어가되, 계약에 그 맥락을 추가했어야 했는지 자문할 것.

새로운 리뷰어도 맥락이 부족해 틀릴 수 있습니다. 단순히 '새로운 시각'이라는 이유만으로 맹종하지 마세요.

### 5단계: 종료 (STOP) — 제한된 루프 유지

다음 조건에서 멈춥니다:

- 다음 반복에서 사소하거나 이미 검토된 지적 사항만 나올 때, **또는**
- 3사이클이 완료되었을 때 (혼자 4번째 사이클을 돌리지 말고 사용자에게 에스컬레이션), **또는**
- 사용자가 명시적으로 승인했을 때

3사이클 후에도 중요한 문제가 계속 제기된다면 산출물 자체가 준비되지 않은 것입니다. 이는 사용자에게 공유해야 할 정보이지 계속 루프를 돌 이유가 아닙니다. 산출물이 너무 커서 3사이클로 부족하다면, 2단계로 돌아가 분해(decompose)하세요.

## 흔한 합리화 및 반박 (Common Rationalizations)

| 합리화 (Rationalization) | 실제 현실 (Reality) |
|---|---|
| "내 코드에 확신이 있으니 의심 단계를 건너뛰겠다" | 새로운 문제에서 확신과 정확성은 상관관계가 낮습니다. 확실하다고 느끼는 순간에 맹점이 숨어 있습니다. |
| "리뷰어를 새로 띄우는 것은 비용이 많이 든다" | 프로덕션에 잘못된 커밋이 나가서 디버깅하는 비용이 훨씬 큽니다. 검사 비용은 한정되어 있지만 버그 비용은 무한합니다. |
| "리뷰어가 사소한 트집만 잡을 것이다" | 프롬프트를 제한하지 않았을 때만 그렇습니다. "계약상 실패를 유발할 문제"로 프롬프트를 한정하세요. |
| "나중에 `/review`로 한꺼번에 검토하겠다" | `/review`는 최종 게이트입니다. 의심 주도 개발은 방향 수정이 저렴한 초기에 잘못된 방향을 잡습니다. PR 시점에는 너무 늦습니다. |
| "모든 단계를 의심하면 아무것도 출시 못한다" | 이 스킬은 모든 키 입력이 아니라 중요(non-trivial) 결정에만 적용됩니다. |
| "리뷰어가 반대했으니 내가 틀렸다" | 리뷰어는 컨텍스트가 부족합니다 — 의견 불일치는 판결이 아니라 정보입니다. 산출물을 다시 읽고 분류한 후 결정하세요. |
| "다중 모델은 항상 더 우수하다" | 다중 모델은 맹점을 잡지만 비용과 도구 불안정성을 유발합니다. 사용자가 가치를 판단하도록 선택권을 제시하세요. |

## 위험 신호 (Red Flags)

- 단순 이름 변경이나 포맷팅에 새 컨텍스트 리뷰어를 호출하는 것
- 산출물 텍스트를 재확인하지 않고 리뷰어의 출력을 절대적 사실로 받아들이는 것
- 사용자에게 알리지 않고 3사이클을 초과하여 루프를 도는 것
- 리뷰어에게 "이게 좋은가요?"라고 긍정 유도형 프롬프트를 주는 것
- 리스크가 큰 결정에서 시간 압박을 이유로 의심을 건너뛰는 것
- 변경되지 않은 동일한 산출물에 대해 리뷰어를 반복 호출하는 것 (지연 행위)
- **의심 흉내내기 (Doubt theater):** 리뷰어가 중요한 문제를 지적했는데도 2사이클 이상 조치 필요(actionable)로 분류된 항목이 0개인 경우 (의심이 아니라 자기 정당화 중임)
- 커밋을 완료한 후에야 의심을 시작하는 것 (그것은 의심 주도가 아니라 사후 `/review`임)
- 대화형 세션에서 다중 모델 검토를 조용히 생략하는 것
- 계약(CONTRACT)을 누락하고 리뷰어에게 전달하는 것
- 리뷰어에게 작성자의 주장(CLAIM)을 함께 넘기는 것 (동조 편향 유발)

## 최종 검증 체크리스트 (Verification)

의심 주도 개발 적용 후:

- [ ] 모든 중요 결정이 확정되기 전에 CLAIM으로 명시적으로 정의됨
- [ ] 중요 산출물마다 최소 1회 이상의 새로운 컨텍스트 검토를 거침 (TDD의 RED 실패 테스트도 동작 단언에 대해 이를 만족함)
- [ ] 리뷰어에게 ARTIFACT + CONTRACT만 전달됨 (CLAIM 및 추론 과정 미포함)
- [ ] 리뷰어의 프롬프트가 검증형이 아닌 적대적("문제를 찾아라")으로 작성됨
- [ ] 지적 사항이 산출물 텍스트와 비교되어 계약 오해 / 조치 필요 / 트레이드오프 / 노이즈로 엄격히 분류됨
- [ ] 명확한 종료 조건을 만족함 (사소한 지적만 남음, 3사이클 도달, 또는 사용자 승인)
- [ ] 대화형 모드에서 다중 모델 검토 기회가 사용자에게 명시적으로 제안됨
- [ ] 비대화형 모드에서는 다중 모델 검토 건너뜀이 명시적으로 공지됨
- [ ] 외부 CLI 호출 시 사전에 PATH 확인, 버전 테스트, 문법 확인 및 사용자 승인을 거침
