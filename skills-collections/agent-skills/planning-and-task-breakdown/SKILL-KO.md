# 계획 및 작업 분해 (Planning and Task Breakdown)

## 개요 (Overview)

명확한 인수 기준(acceptance criteria)을 가진 검증 가능한 작은 단위의 작업들로 전체 업무를 분해합니다. 좋은 작업 분해는 신뢰성 있게 작업을 완료하는 에이전트와 엉망진창으로 코드를 꼬이게 만드는 에이전트를 가르는 핵심 차이입니다. 모든 작업은 단일 집중 세션에서 구현, 테스트, 검증할 수 있을 만큼 작아야 합니다.

## 사용 시점 (When to Use)

- 사양서가 있고 이를 구현 가능한 단위로 쪼개야 할 때
- 작업이 너무 크거나 모호해서 시작하기 어려울 때
- 여러 에이전트나 세션에 걸쳐 작업을 병렬화해야 할 때
- 사람에게 작업 범위를 소통해야 할 때
- 구현 순서가 직관적이지 않을 때

**사용하지 않는 경우:** 작업 범위가 자명한 단일 파일 변경, 또는 사양서에 이미 잘 정의된 작업 목록이 포함되어 있을 때.

## 계획 수립 프로세스 (The Planning Process)

### 1단계: 계획 모드 진입 (Enter Plan Mode)

코드를 작성하기 전에 읽기 전용(read-only) 모드로 동작합니다:

- 사양서 및 관련 코드베이스 섹션을 읽음
- 기존 패턴과 컨벤션 식별
- 컴포넌트 간 의존성 매핑
- 위험 요소 및 미지의 영역(unknowns) 기록

**계획 단계에서는 코드를 절대 작성하지 마세요.** 산출물은 `tasks/plan.md`에 저장되는 계획 문서와 대상 작업 목록(기본값 `tasks/todo.md`)이며, 구현 코드가 아닙니다.

### 2단계: 의존성 그래프 식별 (Identify the Dependency Graph)

무엇이 무엇에 의존하는지 매핑합니다:

```
데이터베이스 스키마
    │
    ├── API 모델/타입
    │       │
    │       ├── API 엔드포인트
    │       │       │
    │       │       └── 프론트엔드 API 클라이언트
    │       │               │
    │       │               └── UI 컴포넌트
    │       │
    │       └── 유효성 검사 로직
    │
    └── 시드 데이터 / 마이그레이션
```

구현 순서는 의존성 그래프를 아래에서 위로(bottom-up) 따릅니다: 기초 토대를 먼저 구축하세요.

### 3단계: 수직적 슬라이스 (Slice Vertically)

모든 DB를 만들고, 모든 API를 만들고, 모든 UI를 만드는 수평적 방식 대신, 한 번에 하나의 완전한 기능 경로를 수직으로 구축하세요:

**나쁨 (수평적 슬라이스):**
```
작업 1: 전체 DB 스키마 생성
작업 2: 모든 API 엔드포인트 구축
작업 3: 모든 UI 컴포넌트 제작
작업 4: 모든 요소 연결
```

**좋음 (수직적 슬라이스):**
```
작업 1: 계정 생성 기능 (회원가입을 위한 스키마 + API + UI)
작업 2: 로그인 기능 (인증 스키마 + API + UI)
작업 3: 할 일 생성 기능 (작업 스키마 + API + UI)
작업 4: 할 일 목록 조회 (조회 쿼리 + API + UI)
```

각 수직 슬라이스는 작동하고 테스트 가능한 기능을 제공합니다.

### 4단계: 작업 명세 작성 (Write Tasks)

각 작업은 다음 구조를 따릅니다:

```markdown
## 작업 [N]: [짧고 설명적인 제목]

**설명:** 이 작업이 달성하는 바를 설명하는 한 문단.

**인수 기준 (Acceptance criteria):**
- [ ] [구체적이고 테스트 가능한 조건]
- [ ] [구체적이고 테스트 가능한 조건]

**검증 방법 (Verification):**
- [ ] 테스트 통과: [리포지토리의 단위 테스트 실행 명령어]
- [ ] 빌드 성공: [리포지토리의 빌드 명령어]
- [ ] 수동 검사: [검증할 내용 설명]

**선행 의존성 (Dependencies):** [의존하는 작업 번호, 또는 "없음"]

**수정될 예상 파일:**
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**예상 규모:** [Small: 1-2개 파일 | Medium: 3-5개 파일 | Large: 5개 이상 파일]
```

### 5단계: 순서 지정 및 체크포인트 설정 (Order and Checkpoint)

다음 기준에 맞춰 작업을 배치합니다:

1. 의존성이 충족됨 (기초를 먼저 구축)
2. 각 작업이 완료된 후에도 시스템이 항상 작동 가능한 상태 유지
3. 2~3개 작업마다 명시적인 검증 체크포인트 배치
4. 고위험 작업을 앞쪽에 배치 (빠른 실패 유도)

작업 목록에 체크포인트를 명시하세요:

```markdown
## 체크포인트: 작업 1~3 완료 후
- [ ] 모든 테스트 통과
- [ ] 애플리케이션 빌드 에러 없음
- [ ] 핵심 사용자 흐름이 엔드투엔드로 작동함
- [ ] 다음 단계 진행 전 사람과 검토 완료
```

## 작업 크기 가이드라인 (Task Sizing Guidelines)

| 크기 | 파일 수 | 범위 | 예시 |
|---|---|---|---|
| **XS** | 1개 | 단일 함수 또는 설정 변경 | 유효성 검사 규칙 추가 |
| **S** | 1-2개 | 하나의 컴포넌트 또는 엔드포인트 | 새 API 엔드포인트 추가 |
| **M** | 3-5개 | 하나의 기능 슬라이스 | 사용자 회원가입 흐름 |
| **L** | 5-8개 | 다중 컴포넌트 기능 | 필터링 및 페이지네이션 검색 |
| **XL** | 8개 이상 | **너무 큼 — 반드시 더 쪼갤 것** | — |

작업이 L 이상이라면 더 작은 작업들로 분할해야 합니다. 에이전트는 S와 M 크기 작업에서 가장 높은 성능을 냅니다.

**작업을 더 분할해야 하는 신호:**
- 한 번의 집중 세션(에이전트 기준 2시간 이상)을 초과할 것 같을 때
- 인수 기준을 3개 이하의 항목으로 설명할 수 없을 때
- 둘 이상의 독립적인 하위 시스템(예: 인증과 결제)을 동시에 건드릴 때
- 작업 제목에 "그리고(and)"를 쓰고 있을 때 (두 개의 작업이라는 명백한 신호)

## 출력 파일 (Output Files)

- **계획 문서 (Plan document):** `tasks/plan.md`에 전체 구현 계획을 저장합니다.
- **작업 목록 (Task list):** 대상 작업 목록(기본값 `tasks/todo.md`)에 각 작업을 기록합니다.

`tasks/` 디렉터리가 없다면 생성하세요.

**미완료된 기존 계획을 절대 함부로 덮어쓰지 마세요.** `tasks/plan.md`나 `tasks/todo.md`를 작성하기 전에, 파일이 이미 존재하고 아직 체크되지 않은 미완료 작업이 남아 있는지 확인하세요:

- 동일한 작업의 재계획/확장인 경우 → 기존 파일을 제자리에서 업데이트.
- 서로 다른 별개의 작업인 경우 → **멈추고 사용자에게 확인.** 다른 세션에서 빌드 진행 중인 작업일 수 있습니다. 기존 파일을 임의로 삭제하거나 덮어쓰지 마세요.

### 작업 목록 대상 (Task List Target)

- **기본값:** `tasks/todo.md`의 체크리스트 마크다운 파일. `/build` 및 하류 도구들이 기대하는 기본 컨벤션입니다.
- **외부 트래커(GitHub Issues, Linear, Jira, bd 등):** 프로젝트 규칙이나 사용자가 외부 트래커를 지정한 경우, `tasks/todo.md` 대신 트래커에 이슈를 생성합니다. `tasks/plan.md`에는 트래커 이슈 ID나 링크를 명시하세요.

## 계획 문서 템플릿 (Plan Document Template)

```markdown
# 구현 계획: [기능/프로젝트 이름]

## 개요 (Overview)
[구축하려는 대상에 대한 한 문단 요약]

## 아키텍처 결정 사항 (Architecture Decisions)
- [핵심 결정 1 및 근거]
- [핵심 결정 2 및 근거]

## 작업 목록 (Task List)

### 1단계: 토대 구축 (Foundation)
- [ ] 작업 1: ...
- [ ] 작업 2: ...

### 체크포인트: 토대 구축 완료
- [ ] 테스트 통과, 빌드 성공

### 2단계: 핵심 기능 (Core Features)
- [ ] 작업 3: ...
- [ ] 작업 4: ...

### 체크포인트: 핵심 기능 완료
- [ ] 엔드투엔드 흐름 정상 동작

### 3단계: 다듬기 (Polish)
- [ ] 작업 5: ...
- [ ] 작업 6: ...

### 체크포인트: 최종 완료
- [ ] 모든 인수 기준 충족
- [ ] 리뷰 준비 완료

## 위험 요소 및 완화 방안 (Risks and Mitigations)
| 위험 | 영향도 | 완화 전략 |
|---|---|---|
| [위험 내용] | [High/Med/Low] | [전략] |

## 미결 질문 (Open Questions)
- [사람의 확인이 필요한 질문]
```

## 병렬화 기회 (Parallelization Opportunities)

- **병렬화 안전:** 독립적인 기능 슬라이스, 이미 구현된 기능에 대한 테스트 작성, 문서화
- **반드시 순차 진행:** 데이터베이스 마이그레이션, 공유 상태 변경, 선행 의존성 체인
- **조율 필요:** 동일한 API 계약을 공유하는 기능 (계약을 먼저 정의한 후 병렬화)

## 흔한 합리화 및 반박 (Common Rationalizations)

| 합리화 (Rationalization) | 실제 현실 (Reality) |
|---|---|
| "진행하면서 그때그때 해결하겠다" | 코드가 엉키고 재작업이 발생하는 지름길입니다. 10분의 계획이 몇 시간을 아낍니다. |
| "작업 내용이 뻔하다" | 그래도 명문화하세요. 명시적인 작업 분해는 숨겨진 의존성과 놓친 엣지 케이스를 드러냅니다. |
| "계획 수립은 오버헤드다" | 계획 수립이 곧 핵심 작업입니다. 계획 없는 구현은 단순한 타자에 불과합니다. |
| "머릿속에 다 들어있다" | 컨텍스트 윈도우는 유한합니다. 문서화된 계획은 세션 경계와 컨텍스트 압축을 넘어 살아남습니다. |
| "기존 tasks/plan.md는 오래되었으니 덮어쓰겠다" | 미완료 작업은 다른 세션에서 진행 중일 수 있습니다. 작업 상태를 파괴하지 말고 먼저 물어보세요. |

## 위험 신호 (Red Flags)

- 문서화된 작업 목록 없이 구현을 시작하는 것
- 확인 없이 미완료 작업이 남은 `tasks/plan.md`나 `tasks/todo.md`를 덮어쓰는 것
- 인수 기준 없이 "기능 구현"이라고만 적힌 작업
- 계획에 검증 단계가 누락된 경우
- 모든 작업이 XL 크기인 경우
- 작업 간 체크포인트가 없는 경우
- 의존성 순서가 고려되지 않은 경우

## 최종 검증 체크리스트 (Verification)

구현을 시작하기 전에 확인 사항:

- [ ] 모든 작업에 명확한 인수 기준이 있음
- [ ] 모든 작업에 구체적인 검증 단계가 명시됨
- [ ] 작업 의존성이 파악되고 올바른 순서로 배치됨
- [ ] 작업 목록 대상(기본 `tasks/todo.md`)에 작업들이 기록됨
- [ ] 사용자의 명시적 확인 없이 기존 미완료 계획을 덮어쓰지 않음
- [ ] 작업당 수정 파일 수가 5개 이내로 분할됨
- [ ] 주요 단계 사이에 검증 체크포인트가 존재함
- [ ] 사람이 계획을 검토하고 승인함
