# 관찰 가능성 및 계측 (Observability and Instrumentation)

## 개요 (Overview)

관찰할 수 없는 코드는 운영할 수 없는 코드입니다. 관찰 가능성(Observability)이란 코드가 방출하는 텔레메트리(telemetry)를 통해 외부에서 "시스템이 지금 무엇을, 왜 하고 있는가?"에 답할 수 있는 능력입니다. 계측(Instrumentation)은 출시 후 덧붙이는 부가물이 아닙니다 — 테스트와 마찬가지로 기능과 함께 작성되어야 합니다. 텔레메트리 없이 기능을 출시하면, 첫 사용자 장애 리포트는 쿼리 조회가 아니라 유적 발굴 작업(archaeology)이 됩니다.

## 사용 시점 (When to Use)

- 프로덕션에서 실행될 모든 기능을 구축할 때
- 새로운 서비스, 엔드포인트, 백그라운드 작업, 외부 연동을 추가할 때
- 프로덕션 인시던트 진단에 너무 오랜 시간이 걸렸을 때 ("무슨 일이 일어났는지 알 수 없었다")
- 알림(Alerting) 규칙을 설정하거나 검토할 때
- I/O, 재시도, 큐, 서비스 간 호출을 추가하는 PR을 검토할 때

**사용하지 않는 경우:**
- 지금 당장 발생한 장애를 디버깅할 때 — `debugging-and-error-recovery` 스킬 사용 (관찰 가능성은 다음번에 그 디버깅을 빠르게 만들어 줍니다)
- 측정된 병목 현상을 프로파일링하고 최적화할 때 — `performance-optimization` 스킬 사용
- 출시 당일 모니터링 체크리스트 및 롤백 트리거 — `shipping-and-launch` 스킬 참조 (이 스킬은 그에 필요한 텔레메트리를 계측함)

## 진행 절차 (Process)

### 1단계: 계측 전에 "정상 작동"의 정의를 명확히 하기

질문 없는 텔레메트리는 단순한 노이즈입니다. 계측을 추가하기 전에, 온콜(on-call) 엔지니어가 이 기능에 대해 물어볼 2~4가지 핵심 질문을 먼저 작성하세요:

```
기능: 체크아웃 결제 재시도 (checkout payment retry)
온콜 엔지니어가 던질 질문:
1. 첫 시도에서 성공하는 결제와 재시도 후 성공하는 결제의 비율은 얼마인가?
2. 결제가 영구적으로 실패했을 때 그 이유는 무엇인가? (PG사 오류? 타임아웃? 유효성 검사 실패?)
3. PG사의 응답 속도가 평소보다 느려졌는가?
→ 아래의 모든 신호는 이 질문들 중 하나에 답할 수 있어야 합니다.
```

이 질문들을 명시할 수 없다면 아직 계측할 준비가 되지 않은 것입니다 — 모든 것을 무의미하게 로깅하고 아무것도 배우지 못하게 됩니다.

### 2단계: 질문에 맞는 올바른 신호(Signal) 선택

| 신호 (Signal) | 답할 수 있는 질문 | 비용 특성 | 예시 |
|---|---|---|---|
| **구조화된 로그 (Structured Log)** | "이 특정 케이스에서 무슨 일이 일어났는가?" | 이벤트당 비용; 트래픽에 비례해 증가 | PG사 오류 코드가 포함된 `payment_failed` |
| **메트릭 (Metric)** | "전체적으로 얼마나 자주 / 얼마나 빠르게 일어나는가?" | 시계열당 고정 비용; 쿼리 비용 저렴 | PG사 호출의 p99 지연 시간(latency) |
| **트레이스 (Trace)** | "여러 서비스 간에 시간이 어디서 소모되었는가?" | 요청당 비용; 주로 샘플링 적용 | 홉(hop)별로 분해된 느린 체크아웃 1건 |

**핵심 경험칙:** 메트릭은 무언가 잘못되었다는 **사실(That)**을 알려주고, 트레이스는 **어디서(Where)** 발생했는지 알려주며, 로그는 **왜(Why)** 발생했는지 알려줍니다.

### 3단계: 구조화된 로깅 (Structured Logging)

단순 줄글이 아닌 '이벤트(event)'를 로깅하세요. 모든 로그 라인은 고정된 이벤트 이름과 기계가 읽을 수 있는 필드를 가진 JSON 객체여야 합니다:

```typescript
// 나쁨: 문자열 결합 — 쿼리 불가, 일관성 없음
logger.info(`Payment ${id} failed for user ${userId} after ${n} retries`);

// 좋음: 고정된 이벤트 이름 + 구조화된 필드
logger.warn({
  event: 'payment_failed',
  paymentId: id,
  provider: 'stripe',
  errorCode: err.code,
  attempt: n,
}, 'payment failed');
```

**로그 레벨의 일관된 사용:**

| 레벨 | 의미 | 온콜 엔지니어 조치 |
|---|---|---|
| `error` | 불변식이 깨짐; 사람의 조치가 필요할 수 있음 | 원인 조사 |
| `warn` | 성능 저하나 문제가 있지만 처리됨 (재시도 성공, 폴백 사용) | 트렌드 모니터링 |
| `info` | 중요한 비즈니스 이벤트 (주문 완료, 배치 작업 종료) | 조치 불필요 |
| `debug` | 상세한 진단 정보 | 프로덕션에서는 기본 비활성화 |

**상관관계 ID (Correlation ID / Request ID)는 필수입니다.** 시스템 경계에서 요청 ID를 생성(또는 수신)하여 모든 로그 라인, 스팬, 아웃바운드 호출에 첨부하세요. 이것이 없으면 섞여서 출력되는 수많은 로그 중에서 단일 요청의 흐름을 재구성할 수 없습니다:

```typescript
// Express: 요청당 자식 로거 생성, 하류로 ID 전파
app.use((req, res, next) => {
  req.id = req.headers['x-request-id'] ?? crypto.randomUUID();
  req.log = logger.child({ requestId: req.id });
  res.setHeader('x-request-id', req.id);
  next();
});
```

**시크릿, 토큰, 비밀번호, 전체 PII(개인식별정보)를 절대 로깅하지 마세요.** 텔레메트리 파이프라인은 고전적인 데이터 유출 경로입니다. 필드를 화이트리스트 방식으로 허용하고, 요청 본문(body) 전체를 그대로 로깅하지 마세요.

### 4단계: 메트릭 (Metrics)

요청 기반 서비스의 경우 모든 엔드포인트와 외부 의존성에 **RED** 메트릭을 계측하세요:
- **R (Rate):** 요청 처리율 (requests/sec)
- **E (Errors):** 오류 발생률 (failure rate)
- **D (Duration):** 지연 시간 (평균이 아닌 히스토그램)

리소스(큐, 커넥션 풀, 호스트)의 경우 **USE** 메트릭을 사용하세요: **U**tilization(사용률), **S**aturation(포화도), **E**rrors(오류).

```typescript
import { Histogram } from 'prom-client';

const httpDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP 요청 지연 시간',
  labelNames: ['method', 'route', 'status_class'],  // '200'이 아닌 '2xx' 사용
  buckets: [0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});
```

**카디널리티(Cardinality) 폭발을 주의하세요.** 고유한 라벨 조합마다 별도의 시계열이 생성됩니다. 라벨은 반드시 작고 고정된 집합(라우트 템플릿, 상태 클래스, 공급자 이름)이어야 합니다. 사용자 ID, 전체 URL, 에러 메시지 텍스트처럼 무제한으로 늘어나는 값을 메트릭 라벨로 사용하지 마세요 (이런 정보는 로그와 트레이스에 속합니다).

```
라벨로 적합:     route="/api/tasks/:id"   status_class="5xx"   provider="stripe"
절대 라벨 금지:  user_id, email, request_id, 전체 URL, 에러 메시지 텍스트
```

평균값(average)은 끔찍한 경험을 하고 있는 상위 1%의 사용자를 가려버립니다. 항상 히스토그램을 사용하고 p50/p95/p99 백분위수를 확인하세요.

### 5단계: 분산 트레이싱 (Distributed Tracing)

벤더 중립적 표준인 OpenTelemetry를 사용하세요. 자동 계측(auto-instrumentation)을 통해 코드 수정 거의 없이 HTTP, gRPC, 주요 DB 클라이언트를 커버할 수 있습니다:

```typescript
// tracing.ts — 다른 어떤 코드보다 먼저 임포트되어야 함
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';

const sdk = new NodeSDK({
  serviceName: 'checkout-service',
  instrumentations: [getNodeAutoInstrumentations()],
});
sdk.start();
```

유의미한 내부 작업 단위(예: `applyDiscounts`, `chargeProvider`)에만 수동 스팬을 추가하고, 온콜 엔지니어가 필터링할 속성을 첨부하세요. 비동기 경계(HTTP 헤더, 큐 메시지 메타데이터)를 넘나들 때 컨텍스트를 반드시 전파(propagate)하세요.

### 6단계: 알림 설정 (Alerting)

원인(cause)이 아닌 **사용자가 느끼는 증상(symptom)**에 대해 알림을 설정하세요:

```
증상 기반 (페이지 호출 대상):       원인 기반 (대시보드 모니터링 대상):
오류율 > 1% (5분 지속)             CPU 사용률 85%
p99 지연 시간 > 2초                파드(pod) 1개 재시작됨
큐 적체 시간 > 10분                디스크 사용량 70%
```

원인 기반 알림은 아무 문제가 없을 때도 울리고, 예측하지 못한 장애는 놓칩니다. 증상 기반 알림은 원인에 관계없이 사용자가 피해를 입는 정확한 순간에 울립니다.

**모든 알림의 필수 규칙:**
1. **조치 가능해야 함 (Actionable):** 대처 방법이 "무시해라, 알아서 회복된다"라면 그 알림은 삭제하세요.
2. **런북(Runbook) 링크 포함:** 의미, 첫 번째 실행할 쿼리, 에스컬레이션 경로를 포함한 3줄짜리 가이드라도 연결하세요.
3. **임계값과 기간의 근거:** 추측이 아니라 SLO나 과거 데이터에 기반해 설정하세요.
4. **2단계 심각도만 사용:** **Page**(사용자 영향, 즉시 조치)와 **Ticket**(성능 저하, 이번 주 내 조치). 3번째 등급은 모든 알림을 무시하게 만드는 소음이 됩니다.

### 7단계: 텔레메트리 자체를 검증 (Verify the telemetry itself)

계측도 코드이므로 틀릴 수 있습니다. 작업을 완료하기 전에 실제 경로를 트리거하고 출력을 확인하세요:

- 스테이징에서 강제로 에러 유발 → `requestId`로 로그를 찾고 필드가 `[object Object]`가 아닌 정상 구조화되어 있는지 확인
- 테스트 트래픽 전송 → 기대한 라벨과 정상적인 수치로 메트릭 시계열이 생성되는지 확인
- 트레이싱 UI에서 서비스 간 요청 1건을 추적 → 끊어진 스팬이 없는지 확인
- 새로운 알림을 임시로 트리거 → 올바른 채널로 수신되고 런북 링크가 열리는지 확인

## 흔한 합리화 및 반박 (Common Rationalizations)

| 합리화 (Rationalization) | 실제 현실 (Reality) |
|---|---|
| "기능이 동작한 후에 로깅을 추가하겠다" | '이후'는 보통 '첫 장애가 발생한 이후'가 되며, 이는 눈이 멀어 있었다는 것을 깨닫는 가장 비싼 순간입니다. 개발할 때 함께 계측하세요. |
| "로그가 많을수록 관찰 가능성이 높아진다" | 구조화되지 않은 소음은 인시던트 대응을 느리게 만듭니다. 쿼리 가능한 3개의 이벤트가 300줄의 줄글 로그보다 낫습니다. |
| "지금은 console.log로 충분하다" | 구조화되지 않은 출력은 필터링, 상관관계 파악, 알림 연동이 불가능합니다. 구조화된 로거를 쓰는 데 5분밖에 안 걸립니다. |
| "장애가 나면 대시보드를 보면 된다" | 정의된 질문 없이 만든 대시보드는 답을 빼고 모든 것을 보여줍니다. 온콜 엔지니어의 질문에서 시작하세요. |
| "사용자 ID를 메트릭 라벨로 쓰면 디버깅이 편하다" | 메트릭 백엔드를 마비시키는 지름길입니다. 고카디널리티 데이터는 로그와 트레이스에 넣어야 합니다. |

## 위험 신호 (Red Flags)

- 재시도, 큐, 외부 호출을 추가하면서 텔레메트리가 전혀 없는 기능 PR
- 구조화된 필드 대신 문자열 결합으로 작성된 로그
- 상관관계/요청 ID가 없어 고아가 된 로그 라인들
- 사용자 ID, 전체 URL, 에러 메시지 텍스트가 메트릭 라벨로 사용됨 (카디널리티 폭발)
- 백분위수 없이 평균값으로만 추적되는 지연 시간
- 매일 울리지만 아무도 조치하지 않고 묵인되는 알림
- 사용자 오류율은 모니터링하지 않으면서 CPU, 메모리 알림으로 사람을 호출하는 것
- 로그에 시크릿, 토큰, 요청 본문 전체가 노출되는 것

## 최종 검증 체크리스트 (Verification)

계측 적용 후:

- [ ] 온콜 엔지니어의 질문이 문서화되었고 각 신호가 이에 매핑됨
- [ ] 모든 로그 출력이 고정 이벤트 이름과 상관관계 ID를 가진 구조화된 JSON 형태임
- [ ] 로그 라인에 시크릿, 토큰, 가공되지 않은 PII가 없음
- [ ] 모든 신규 엔드포인트와 외부 의존성에 제한된 라벨을 가진 RED 메트릭이 존재함
- [ ] 지연 시간이 히스토그램으로 측정되어 p95/p99 조회가 가능함
- [ ] 트레이싱 UI에서 단일 요청을 엔드투엔드로 끊김 없이 추적할 수 있음
- [ ] 모든 신규 알림이 증상 기반이며 런북 링크를 포함하고 1회 이상 테스트 발송됨
- [ ] 스테이징에서 유발한 결함이 소스 코드를 보지 않고 텔레메트리만으로 원인 위치가 파악됨
