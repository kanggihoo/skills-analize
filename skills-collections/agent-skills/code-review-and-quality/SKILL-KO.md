# 코드 리뷰 및 품질 (Code Review and Quality)

## 개요 (Overview)

품질 게이트를 갖춘 다차원 코드 리뷰입니다. 모든 변경 사항은 병합되기 전에 예외 없이 검토를 거칩니다. 리뷰는 **정확성(Correctness), 가독성(Readability), 아키텍처(Architecture), 보안(Security), 성능(Performance)**이라는 5가지 축을 다룹니다.

**승인 기준 (The approval standard):** 완벽하지 않더라도 전체적인 코드 건강성을 확실히 향상시키는 변경 사항이라면 승인하세요. 완벽한 코드란 존재하지 않으며, 목표는 '지속적인 개선'입니다. 내가 작성했을 방식과 정확히 일치하지 않는다는 이유로 변경을 차단하지 마세요. 코드베이스를 개선하고 프로젝트 컨벤션을 따른다면 승인해야 합니다.

## 사용 시점 (When to Use)

- PR이나 변경 사항을 병합하기 전
- 기능 구현을 완료한 후
- 다른 에이전트나 모델이 생성한 코드를 평가해야 할 때
- 기존 코드를 리팩터링할 때
- 버그 수정 후 (수정 코드와 회귀 테스트 모두 검토)

## 5축 리뷰 기준 (The Five-Axis Review)

모든 리뷰는 다음 차원에서 코드를 평가합니다:

### 1. 정확성 (Correctness)

코드가 의도한 대로 정확히 동작하는가?

- 사양(Spec)이나 작업 요구사항과 일치하는가?
- 엣지 케이스(null, 빈 값, 경계값)가 적절히 처리되었는가?
- 오류 경로(error path)가 처리되었는가? (해피 패스뿐만 아니라)
- 모든 테스트를 통과하는가? 테스트가 실제로 올바른 대상을 테스트하고 있는가?
- 오프바이원(off-by-one) 오류, 경쟁 상태(race condition), 상태 불일치가 없는가?

### 2. 가독성 및 단순성 (Readability & Simplicity)

작성자의 설명 없이도 다른 엔지니어(또는 에이전트)가 코드를 이해할 수 있는가?

- 변수/함수명이 맥락을 명확히 전달하고 프로젝트 컨벤션을 따르는가? (맥락 없는 `temp`, `data`, `result` 지양)
- 제어 흐름이 직관적인가? (중첩 삼항 연산자, 깊은 콜백 피하기)
- 코드가 논리적으로 구성되었는가? (관련 코드 그룹화, 명확한 모듈 경계)
- 단순화할 수 있는 "지나치게 기교를 부린" 트릭이 있는가?
- **더 적은 라인 수로 작성할 수 있는가?** (100줄로 충분한 곳에 1,000줄을 쓰는 것은 실패입니다)
- **추상화가 복잡성을 감수할 만큼의 가치를 지니는가?** (세 번째 유스케이스가 나오기 전까지는 성급히 일반화하지 마세요)
- 직관적이지 않은 의도를 명확히 하는 주석이 필요한가? (단, 뻔한 코드에는 주석을 달지 마세요)
- 사용하지 않는 변수(`_unused`), 이전 버전 호환용 껍데기(shim), `// removed`와 같은 불필요한 레거시 코드가 남아있는가?
- **관련 없는 흐름에 새로운 조건문이 덕지덕지 붙어 있는가?** 이는 사소한 문제가 아니라 설계 결함입니다. 기존 경로를 엉키게 하지 말고 로직을 별도의 헬퍼, 상태, 또는 정책으로 분리하세요.
- **동일한 형태에 대한 반복적인 조건문이 나타나는가?** 이는 모델이나 디스패처가 누락되었음을 의미합니다. "임시" 분기는 대개 영구적인 기술 부채가 됩니다.

### 3. 아키텍처 (Architecture)

변경 사항이 시스템의 전체 설계에 잘 부합하는가?

- 기존 패턴을 따르고 있는가, 아니면 새로운 패턴을 도입했는가? 새로운 패턴이라면 타당한 근거가 있는가?
- 깔끔한 모듈 경계를 유지하고 있는가?
- 공통화해야 할 코드 중복이 있는가?
- 의존성이 올바른 방향으로 흐르고 있는가? (순환 의존성 없음)
- 추상화 수준이 적절한가? (과도한 엔지니어링 없음, 과도한 결합 없음)
- **이 리팩터링이 복잡성을 실제로 줄였는가, 아니면 단순히 위치만 옮겼는가?** 코드를 이해하기 위해 머릿속에 담아야 하는 개념의 수를 세어보세요. "더 깔끔해진" 버전에서도 그 수가 변하지 않았다면 개선된 것이 아닙니다. 동일한 로직을 재중앙화하는 것보다 분기, 모드, 레이어 전체를 제거하는 구조 조정을 선호하세요. 추상화를 다듬기보다 삭제하는 것이 낫습니다.
- **특정 기능 전용 로직이 공통/범용 모듈로 유출되고 있지 않은가?** 로직은 해당 개념을 소유한 레이어에 두고, 유사한 중복 함수 대신 기존 헬퍼를 재사용하며, 아키텍처 표류(drift)를 방치하지 마세요.
- **타입 경계가 명시적인가?** 불명확한 불변식을 덮기 위한 무분별한 `any`/`unknown`/optional/타입 캐스팅 및 조용한 폴백(fallback)을 경계하세요. 경계를 명시적으로 만들면 주변 제어 흐름이 훨씬 단순해집니다.

### 4. 보안 (Security)

상세한 보안 지침은 `security-and-hardening`을 참조하세요. 변경 사항이 취약점을 유발하는가?

- 사용자 입력이 검증(validate) 및 정제(sanitize)되었는가?
- 시크릿이 코드, 로그, 버전 관리 시스템에 노출되지 않았는가?
- 필요한 곳에서 인증/인가 검사가 수행되는가?
- SQL 쿼리가 파라미터화되었는가? (문자열 결합 금지)
- XSS 방지를 위해 출력이 인코딩되었는가?
- 의존성이 신뢰할 수 있는 소스이며 알려진 취약점이 없는가?
- 외부 소스(API, 로그, 사용자 콘텐츠, 설정 파일)의 데이터를 신뢰할 수 없는 것으로 취급하는가?
- 외부 데이터 흐름이 로직이나 렌더링에 사용되기 전에 시스템 경계에서 검증되는가?

### 5. 성능 (Performance)

상세한 프로파일링 및 최적화는 `performance-optimization`을 참조하세요. 변경 사항이 성능 문제를 유발하는가?

- N+1 쿼리 패턴이 존재하는가?
- 무제한 루프나 제약 없는 데이터 조회가 있는가?
- 비동기로 처리해야 할 동기식 작업이 있는가?
- UI 컴포넌트에 불필요한 리렌더링이 발생하는가?
- 목록 엔드포인트에 페이지네이션이 누락되었는가?
- 핫 패스(hot path)에서 큰 객체가 불필요하게 생성되는가?

## 구조적 개선 방안 제시 (Structural Remedies)

구조적 문제를 지적할 때는 문제점뿐만 아니라 **구체적인 개선 방안(move)**을 함께 제시하세요. 단순히 "코드가 복잡하다"고만 하면 작성자는 헤매게 됩니다. 명확한 리팩터링 패턴을 제안하세요:

- **조건문 체인을** 타입화된 모델이나 명시적인 디스패처로 대체
- **중복된 분기들을** 하나의 명확한 흐름으로 통합
- **오케스트레이션과 비즈니스 로직을 분리**하여 각각 독립적으로 읽히도록 개선
- **특정 기능 로직을** 공통 모듈에서 해당 개념을 소유한 패키지로 이동
- 맞춤형 유사 함수 대신 **기존의 정규(canonical) 헬퍼를 재사용**
- **타입 경계를 명시적으로 만들어** 하류의 복잡한 분기 로직을 제거
- API를 명확하게 하지 못하고 간접 계층만 늘리는 **패스스루 래퍼(pass-through wrapper) 제거**
- **헬퍼를 추출하거나 대형 파일을** 집중된 작은 모듈로 분할

동일한 복잡성을 여기저기 분산시키는 방식보다, 움직이는 부품(moving pieces) 자체를 제거하는 해결책을 우선시하세요.

## 변경 크기 관리 (Change Sizing)

작고 집중된 변경일수록 리뷰하기 쉽고, 더 빨리 병합되며, 안전하게 배포됩니다. 다음 크기를 목표로 하세요:

```
약 100줄 변경   → 좋음. 한 번에 집중해서 리뷰 가능.
약 300줄 변경   → 단일 논리적 변경이라면 수용 가능.
약 1000줄 변경  → 너무 큼. 쪼개야 함.
```

**diff 크기뿐만 아니라 전체 파일 크기도 주의 깊게 살피세요.** 작은 diff라도 파일 크기가 적정 수준을 넘게 만들 수 있습니다. 단일 파일에서 약 1,000줄의 *전체 라인 수*(위의 1,000줄 *변경*과 구분됨)는 리팩터링을 고려해야 할 검토 신호입니다. 변경 사항으로 인해 이미 큰 파일이 더 비대해진다면, 더 추가하기 전에 헬퍼, 하위 컴포넌트, 모듈을 *먼저* 추출할 수 있는지 검토하세요. 분해한 후 추가하세요.

**"하나의 변경(One change)"의 기준:** 한 가지 작업만 다루고, 관련 테스트를 포함하며, 제출 후에도 시스템이 정상 동작하도록 유지하는 독립적인 수정 단위입니다. 전체 기능이 아니라 기능의 한 부분이어야 합니다.

**변경 사항이 너무 클 때의 분할 전략:**

| 전략 | 방법 | 적용 시점 |
|---|---|---|
| **스택(Stack)** | 작은 변경을 먼저 제출하고, 이를 기반으로 다음 작업을 진행 | 순차적 의존성이 있을 때 |
| **파일 그룹별 분할** | 서로 다른 리뷰어가 필요한 그룹별로 변경을 분리 | 횡단 관심사(Cross-cutting) |
| **수평적 분할** | 공통 코드/스텁을 먼저 생성하고, 이후 사용하는 코드 작성 | 계층형 아키텍처 |
| **수직적 분할** | 기능의 더 작은 풀스택 슬라이스 단위로 나눔 | 기능 개발 작업 |

**대규모 변경이 허용되는 예외:** 완전한 파일 삭제, 또는 리뷰어가 모든 라인을 볼 필요 없이 의도만 검증하면 되는 자동화된 리팩터링.

**리팩터링과 기능 추가를 분리하세요.** 기존 코드를 리팩터링하면서 새 기능을 추가하는 작업은 두 개의 독립된 변경 사항입니다 — 별도로 제출하세요. 사소한 정리(변수 이름 변경 등)는 리뷰어의 재량에 따라 포함될 수 있습니다.

## 변경 설명 작성법 (Change Descriptions)

모든 변경 사항에는 버전 관리 기록에서 그 자체로 완결성을 갖는 설명이 필요합니다.

**첫 줄:** 짧고, 명령형으로, 독립적인 문장. "Deleting the FizzBuzz RPC" 대신 "Delete the FizzBuzz RPC". diff를 보지 않고도 히스토리 검색만으로 변경 내용을 이해할 수 있을 만큼 구체적이어야 합니다.

**본문:** 무엇이 왜 변경되었는지 설명합니다. 코드 자체에서 드러나지 않는 맥락, 결정 사항, 이유를 포함하세요. 버그 번호, 벤치마크 결과, 설계 문서 링크를 첨부하세요. 접근 방식에 한계점이 있다면 인정하고 명시하세요.

**안티패턴:** "Fix bug", "Fix build", "Add patch", "Moving code from A to B", "Phase 1", "Add convenience functions".

## 리뷰 프로세스 (Review Process)

### 1단계: 맥락 이해 (Understand the Context)

코드를 보기 전에 변경의 의도를 먼저 파악합니다:

```
- 이 변경이 달성하려는 목표는 무엇인가?
- 어떤 사양(spec)이나 작업을 구현한 것인가?
- 예상되는 동작 변화는 무엇인가?
```

### 2단계: 테스트 먼저 검토 (Review the Tests First)

테스트는 코드의 의도와 커버리지를 가장 명확하게 드러냅니다:

```
- 변경 사항에 대한 테스트가 존재하는가?
- 구현 세부사항이 아닌 '동작(behavior)'을 테스트하고 있는가?
- 엣지 케이스가 다루어졌는가?
- 테스트 이름이 명확하고 서술적인가?
- 코드가 잘못 수정되었을 때 테스트가 회귀(regression)를 잡아낼 수 있는가?
```

### 3단계: 구현 코드 검토 (Review the Implementation)

5가지 축을 염두에 두고 코드를 훑어봅니다:

```
변경된 각 파일에 대해:
1. 정확성: 테스트가 명시한 동작을 코드가 올바르게 수행하는가?
2. 가독성: 도움 없이도 이 코드를 이해할 수 있는가?
3. 아키텍처: 시스템의 전체 구조와 잘 어울리는가?
4. 보안: 잠재적인 취약점이 있는가?
5. 성능: 병목 지점이 있는가?
```

### 4단계: 발견 사항 분류 (Categorize Findings)

작성자가 필수 사항과 선택 사항을 구분할 수 있도록 모든 코멘트에 심각도 라벨을 붙이세요:

| 접두사 (Prefix) | 의미 | 작성자 조치 |
|---|---|---|
| *(접두사 없음)* | 필수 수정 사항 | 병합 전 반드시 해결해야 함 |
| **Critical:** | 병합 차단 이슈 | 보안 취약점, 데이터 손실, 기능 파손 |
| **Nit:** | 사소한 제안, 선택 사항 | 작성자가 무시해도 됨 — 포맷팅, 스타일 선호 |
| **Optional:** / **Consider:** | 제안 사항 | 고려할 가치가 있으나 필수는 아님 |
| **FYI** | 단순 정보 공유 | 조치 불필요 — 향후 참고용 컨텍스트 |

이렇게 하면 작성자가 모든 피드백을 필수로 오해하여 사소한 제안에 시간을 낭비하는 것을 방지할 수 있습니다.

**영향력이 큰 문제부터 제시하세요.** 정확성과 보안 문제를 가장 먼저 다루고, 그 다음 구조적 퇴행 및 누락된 단순화 기회, 그 외 사소한 사항 순으로 정렬하세요. 중요한 이슈를 자잘한 꼬투리(nit) 주석 속에 묻어두지 마세요 — 높은 확신의 코멘트 몇 개가 긴 목록보다 낫습니다. 구조적 문제 하나와 10개의 nit가 있다면, 그 구조적 문제 하나가 리뷰의 핵심입니다.

### 5단계: 검증 과정 확인 (Verify the Verification)

작성자가 어떻게 검증했는지 확인합니다:

```
- 어떤 테스트를 실행했는가?
- 빌드가 성공했는가?
- 수동 테스트를 수행했는가?
- UI 변경의 경우 스크린샷이 첨부되었는가?
- 전/후 비교 결과가 있는가?
```

## 다중 모델 리뷰 패턴 (Multi-Model Review Pattern)

서로 다른 모델을 활용하여 다양한 관점에서 리뷰를 수행합니다:

```
모델 A가 코드 작성
    │
    ▼
모델 B가 정확성과 아키텍처 관점에서 리뷰
    │
    ▼
모델 A가 피드백 반영 및 수정
    │
    ▼
사람이 최종 검토 및 결정
```

단일 모델이 놓칠 수 있는 맹점을 다른 모델이 보완해 줍니다.

**리뷰 에이전트용 프롬프트 예시:**
```
이 코드 변경 사항의 정확성, 보안, 프로젝트 컨벤션 준수 여부를 검토해주세요.
사양(Spec)은 [X]이며, 변경 사항은 [Y]를 수행해야 합니다.
모든 발견 사항에 Critical, Required, Optional, Nit 라벨을 붙여주세요.
```

## 데드 코드 관리 (Dead Code Hygiene)

리팩터링이나 기능 변경 후에는 방치된 코드가 없는지 확인하세요:

1. 더 이상 접근할 수 없거나 사용되지 않는 코드 식별
2. 해당 목록을 명시적으로 정리
3. **삭제 전 확인:** "더 이상 사용되지 않는 다음 항목들을 제거할까요: [목록]?"

죽은 코드를 방치하면 향후 코드를 읽는 사람과 에이전트 모두에게 혼란을 줍니다. 단, 확신이 서지 않는 코드를 임의로 삭제하지 말고 의문이 들 때는 물어보세요.

```
확인된 데드 코드:
- src/utils/date.ts 의 formatLegacyDate() — formatDate()로 대체됨
- src/components/ 의 OldTaskCard 컴포넌트 — TaskCard로 대체됨
- src/config.ts 의 LEGACY_API_URL 상수 — 참조 없음
→ 이 항목들을 삭제해도 될까요?
```

## 리뷰 속도 (Review Speed)

느린 리뷰는 팀 전체를 정체시킵니다. 리뷰를 위해 컨텍스트를 전환하는 비용은 다른 사람들에게 발생하는 대기 비용보다 훨씬 적습니다.

- **영업일 기준 1일 이내 응답** — 이는 목표치가 아닌 최장 한도선입니다.
- **이상적인 주기:** 집중 코딩 중이 아니라면 리뷰 요청이 도착한 직후 빠르게 응답합니다. 일반적인 변경은 하루 안에 여러 번의 리뷰 라운드를 끝낼 수 있어야 합니다.
- 빠른 최종 승인보다 **개별 피드백의 빠른 응답을 우선시**하세요. 피드백이 빠르면 여러 라운드가 필요하더라도 답답함이 줄어듭니다.
- **거대한 변경:** 거대한 코드 변경을 한꺼번에 보려 하지 말고, 작성자에게 분할을 요청하세요.

## 의견 불일치 해결 (Handling Disagreements)

리뷰 중 의견 충돌이 발생하면 다음 우선순위를 적용하세요:

1. **기술적 사실과 데이터**는 개인적 의견과 선호보다 우선합니다.
2. **스타일 가이드**는 스타일 문제에 대한 절대적인 기준입니다.
3. **소프트웨어 설계**는 개인적 취향이 아닌 엔지니어링 원칙에 따라 평가되어야 합니다.
4. **코드베이스 일관성**은 전체적인 코드 건강을 해치지 않는 한 존중됩니다.

**"나중에 정리하겠다"는 말을 수용하지 마세요.** 경험상 미뤄둔 정리는 거의 실행되지 않습니다. 긴급한 상황이 아니라면 병합 전에 정리를 요구하세요. 이번 변경에서 해결할 수 없는 주변 문제라면, 담당자가 스스로에게 할당된 이슈를 등록하도록 요구하세요.

## 솔직한 리뷰 (Honesty in Review)

본인, 다른 에이전트, 사람이 작성한 코드를 검토할 때:

- **맹목적인 도장 찍기(Rubber-stamp)를 하지 마세요.** 실제 리뷰 근거 없는 "LGTM"은 아무에게도 도움이 되지 않습니다.
- **진짜 문제를 축소하지 마세요.** 프로덕션에 영향을 줄 버그를 두고 "사소한 문제일 수 있습니다"라고 완곡하게 돌려 말하는 것은 정직하지 않습니다.
- **가능한 경우 문제를 수치화하세요.** "느릴 수 있습니다"보다 "이 N+1 쿼리는 목록의 항목당 약 50ms를 추가합니다"가 훨씬 유용합니다.
- **명백한 문제가 있는 접근 방식에는 단호히 이의를 제기하세요.** 무조건적인 칭찬과 동조는 리뷰에서 실패를 낳습니다. 문제가 있다면 직접적으로 지적하고 대안을 제시하세요.
- **결정권자의 오버라이드는 겸허히 수용하세요.** 작성자가 전체 맥락을 파악하고 있고 의견을 굽히지 않는다면 그 판단을 존중하세요. 사람이 아닌 코드를 평가하세요 — 개인적인 비판을 피하고 코드 자체에 집중하도록 표현을 다듬으세요.

## 의존성 관리 원칙 (Dependency Discipline)

의존성 검토도 코드 리뷰의 중요한 일부입니다:

**새로운 의존성을 추가하기 전:**
1. 기존 스택으로 해결할 수 있는가? (대부분 가능합니다)
2. 라이브러리의 크기는 얼마인가? (번들 크기에 미치는 영향 확인)
3. 활발히 유지보수되고 있는가? (마지막 커밋, 열린 이슈 확인)
4. 알려진 취약점이 있는가? (`npm audit`)
5. 라이선스는 무엇인가? (프로젝트 라이선스와 호환되어야 함)

**규칙:** 새로운 의존성보다 표준 라이브러리와 기존 유틸리티를 우선하세요. 모든 의존성은 잠재적인 부채입니다.

**기존 의존성 업그레이드**도 다른 코드 변경과 동일하며, "bump deps"와 같은 메시지로 일괄 병합되는 업그레이드가 가장 위험합니다. 동일한 원칙으로 검토하세요:

1. **버전 번호만 보지 말고 변경 로그(changelog)를 읽으세요.** Semver는 약속일 뿐이며 지켜지지 않을 수 있습니다 — 패치 버전에서도 동작 변화가 일어날 수 있습니다. 메이저 업데이트의 경우 마이그레이션 가이드를 확인하고 깨지는 부분을 찾으세요.
2. **변경당 하나의 의존성만 업그레이드하세요.** 개별적으로(또는 작게 연관된 그룹 단위로) 업그레이드하고 병합하세요. 일괄 업데이트 시 빌드가 깨지면 어떤 패키지가 원인인지 찾기 어렵지만, 단일 패키지 변경은 원인이 명확하고 롤백도 깔끔합니다.
3. **테스트 결과로 판단하세요.** 업그레이드의 검증은 "설치가 되었다"가 아니라 전/후 테스트 스위트의 성공 여부로 판단합니다. 의존성 동작에 대한 테스트 커버리지가 부족하다면, 테스트를 먼저 추가하는 것이 우선입니다.
4. **전이적 의존성(Transitive graph)을 주의하세요.** 설치된 대부분의 패키지는 직접 선택하지 않은 간접 의존성입니다. `package.json`뿐만 아니라 lockfile diff도 확인하세요. 단 하나의 패키지 업그레이드가 수십 개의 간접 변경을 유발할 수 있습니다.
5. **Lockfile의 무결성을 유지하세요.** 커밋하고, diff를 리뷰하며, 절대 수동으로 편집하지 마세요. Lockfile은 실제로 배포되는 항목을 고정하는 핵심 파일입니다.

## 리뷰 체크리스트 (The Review Checklist)

```markdown
## 리뷰: [PR/변경 제목]

### 맥락 (Context)
- [ ] 이 변경이 무엇을 왜 하는지 이해함

### 정확성 (Correctness)
- [ ] 사양/작업 요구사항과 일치함
- [ ] 엣지 케이스 처리됨
- [ ] 에러 경로 처리됨
- [ ] 테스트가 변경 사항을 적절히 커버함

### 가독성 (Readability)
- [ ] 네이밍이 명확하고 일관됨
- [ ] 로직이 직관적임
- [ ] 불필요한 복잡성이 없음

### 아키텍처 (Architecture)
- [ ] 기존 패턴을 따름
- [ ] 불필요한 결합이나 의존성이 없음
- [ ] 적절한 추상화 수준
- [ ] 리팩터링이 복잡성을 재배치하는 것이 아니라 실제로 감소시킴
- [ ] 공통 모듈에 기능 전용 로직이 없으며 파일 크기가 적정 수준을 유지함

### 보안 (Security)
- [ ] 코드에 시크릿이 없음
- [ ] 시스템 경계에서 입력이 검증됨
- [ ] 주입(Injection) 취약점이 없음
- [ ] 인증/인가 검사가 적용됨
- [ ] 외부 데이터 소스를 신뢰할 수 없는 것으로 취급함

### 성능 (Performance)
- [ ] N+1 패턴이 없음
- [ ] 무제한 실행 작업이 없음
- [ ] 목록 엔드포인트에 페이지네이션 적용됨

### 검증 (Verification)
- [ ] 테스트 통과
- [ ] 빌드 성공
- [ ] 수동 검증 완료 (해당되는 경우)

### 최종 판정 (Verdict)
- [ ] **승인 (Approve)** — 병합 준비 완료
- [ ] **수정 요청 (Request changes)** — 문제 해결 필요
```

## 흔한 합리화 및 반박 (Common Rationalizations)

| 합리화 (Rationalization) | 실제 현실 (Reality) |
|---|---|
| "동작하니까 이 정도면 충분하다" | 읽기 어렵고, 불안전하며, 아키텍처가 잘못된 작동 코드는 복리로 불어나는 부채를 만듭니다. |
| "내가 작성했으니 당연히 맞다" | 작성자는 자신의 가정에 대해 맹목적입니다. 모든 변경은 제3자의 시각을 통해 개선됩니다. |
| "나중에 정리하겠다" | 나중은 절대 오지 않습니다. 리뷰는 품질 게이트입니다 — 나중이 아닌 병합 전에 정리를 요구하세요. |
| "AI가 생성한 코드니 문제없을 것이다" | AI 코드는 덜 검토하는 것이 아니라 더 면밀히 살펴야 합니다. 틀렸을 때도 그럴듯하고 확신에 차 있습니다. |
| "테스트를 통과했으니 괜찮다" | 테스트는 필요조건이지 충분조건이 아닙니다. 아키텍처 결함, 보안 취약점, 가독성 문제는 잡아내지 못합니다. |
| "리팩터링을 통해 더 깔끔해졌다" | 복잡성의 위치를 옮기는 것은 복잡성을 줄이는 것이 아닙니다. 이해해야 하는 개념의 수가 같다면 개선된 것이 아닙니다. 분기 자체가 사라지는 버전을 찾으세요. |
| "이 파일에 아주 조금 추가했을 뿐이다" | 작은 diff라도 파일 크기를 한계치 이상으로 밀어넣고 관련 없는 흐름에 분기를 추가할 수 있습니다. diff 크기가 아닌 결과 구조로 판단하세요. |
| "단순한 버전 업그레이드일 뿐이다" | 버전 업그레이드는 내가 작성하지 않은 동작 변화입니다. 변경 로그를 확인하세요. Semver가 무결함을 보장하지 않습니다. |
| "시간 절약을 위해 한 PR에서 모든 의존성을 업그레이드하겠다" | 일괄 업그레이드로 빌드가 깨지면 원인 패키지를 찾기 어렵습니다. 변경당 하나의 의존성을 업그레이드해야 원인 파악과 롤백이 깔끔합니다. |

## 위험 신호 (Red Flags)

- 리뷰 없이 병합되는 PR
- 테스트 통과 여부만 확인하고 다른 축을 무시하는 리뷰
- 실제 검토 근거가 없는 "LGTM" 승인
- 보안 중심의 검토가 생략된 보안 민감 변경 사항
- "너무 커서 제대로 리뷰하기 힘든" 거대한 PR (분할해야 함)
- 회귀 테스트가 누락된 버그 수정 PR
- 심각도 라벨이 없는 리뷰 코멘트 (필수인지 선택인지 불분명)
- "나중에 고치겠다"는 약속을 수용하는 것 (절대 지켜지지 않음)
- 개념의 수를 줄이지 않고 코드 위치만 옮기는 리팩터링
- 분해하지 않고 이미 비대한 파일을 더 키우는 변경
- 관련 없는 코드 경로에 무분별하게 흩뿌려진 새로운 조건문 (추상화 누락)
- 기존 표준 헬퍼가 있음에도 중복 구현된 맞춤형 헬퍼, 또는 공통 모듈에 들어간 기능 전용 로직
- 변경 로그 확인 및 패키지 격리 없이 일괄 처리된 의존성 업데이트 PR
- 수동 편집되거나, 커밋되지 않거나, diff 검토 없이 병합된 lockfile 변경

## 최종 검증 체크리스트 (Verification)

리뷰 완료 후:

- [ ] 모든 Critical 이슈가 해결됨
- [ ] 모든 Required(접두사 없음) 변경 사항이 해결되었거나 타당한 근거와 함께 명시적으로 유예됨
