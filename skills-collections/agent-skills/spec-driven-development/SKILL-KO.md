# 스펙 주도 개발 (Spec-Driven Development)

## 개요 (Overview)

코드를 작성하기 전에 **구조화된 사양서(Specification)**를 먼저 작성하세요. 사양서는 엔지니어와 에이전트 간의 단일 진실 공급원(Single Source of Truth)입니다 — 무엇을, 왜 구축하는지, 그리고 작업이 완료되었음을 어떻게 알 수 있는지 정의합니다. 사양 없는 코드는 단순한 추측일 뿐입니다.

## 사용 시점 (When to Use)

- 새 프로젝트나 기능을 시작할 때
- 요구사항이 모호하거나 불완전할 때
- 변경 사항이 여러 파일이나 모듈에 걸쳐 있을 때
- 아키텍처 결정을 내리려 할 때
- 구현에 30분 이상 소요될 것으로 예상되는 작업일 때

**사용하지 않는 경우:** 한 줄짜리 버그 수정, 오타 수정, 또는 요구사항이 자명하고 단일 파일에 국한된 경우.

## 단계별 게이트 워크플로우 (The Gated Workflow)

스펙 주도 개발은 4개 단계로 구성되며, 단일 요청이 독립적으로 테스트 가능한 여러 역량을 포함할 때만 활성화되는 사전 단계(0단계)가 있습니다. 현재 단계가 검증되기 전에는 다음 단계로 진행하지 마세요.

```
사양 작성 (SPECIFY) ──→ 계획 (PLAN) ──→ 작업 분해 (TASKS) ──→ 구현 (IMPLEMENT)
        │                     │                 │                   │
        ▼                     ▼                 ▼                   ▼
    사람이 검토           사람이 검토       사람이 검토         사람이 검토
```

### 0단계: 범위 점검 및 역량 맵핑 (Scope Check & Capability Map)

대부분의 요청은 단일 역량을 다룹니다. 그렇다면 이 단계를 건너뛰고 바로 1단계(사양 작성)로 가세요.

**감지 기준:** 하나의 요구사항에 독립적으로 테스트 가능한 여러 역량이 묶여 있는 경우, 사양을 쓰기 전에 먼저 분해하세요:
- 요구사항이 각자의 데이터나 사용자를 가진 독립적 역량들을 포함함 (예: 인증, 결제, 알림, 리포팅)
- 인수 기준들이 개별적으로 배포되고 검증될 수 있는 그룹들로 나뉨
- 하나의 역량을 제거하거나 교체해도 다른 역량의 요구사항을 다시 작성할 필요가 없음

**사양 작성 전에 '역량 맵(Capability Map)'을 먼저 제안하세요:**

```markdown
# 역량 맵: [이니셔티브 이름]

| 모듈 ID | 책임 | 선행 의존성 |
|---|---|---|
| identity | 계정, 세션, SSO | — |
| billing | 요금제, 인보이스, 결제 | identity |
| notifications | 이메일 및 웹훅 발송 | identity |
| reporting | 사용량 대시보드 | billing, notifications |

구현 순서: identity → billing, notifications → reporting
```

- **불변의 모듈 ID:** 케밥 케이스(kebab-case)로 한 번 정의하면 변경하지 않음.
- **단방향 의존성:** 순환 의존성 금지 (서로 필요하다면 그것은 하나의 모듈임).
- **게이트 승인:** 사람이 모듈 경계, 의존성 방향, 빌드 순서를 먼저 검토하고 승인해야 합니다.

그 후 의존성 순서대로 각 모듈에 대해 **사양 작성 → 계획 → 작업 분해 → 구현**을 재귀적으로 수행합니다. 승인된 맵은 프로젝트 루트에 저장하고, 각 모듈의 사양서는 `SPEC-identity.md`, `SPEC-billing.md`와 같이 모듈 ID로 명명하여 저장합니다.

### 1단계: 사양 작성 (Specify)

고수준의 비전에서 시작하여 요구사항이 구체화될 때까지 사람에게 명확한 질문을 던집니다.

**자신의 가정을 즉시 드러내세요.** 사양 내용을 작성하기 전에 본인이 하고 있는 가정을 먼저 나열하세요:

```
제가 전제하고 있는 가정들:
1. 네이티브 앱이 아닌 웹 애플리케이션이다
2. 인증에 JWT가 아닌 세션 쿠키를 사용한다
3. 데이터베이스는 PostgreSQL이다 (기존 Prisma 스키마 기반)
4. 모던 브라우저만 타깃으로 한다 (IE 지원 안 함)
→ 틀린 부분이 있다면 지금 바로잡아 주세요.
```

모호한 요구사항을 자의적으로 채워넣지 마세요. 사양서의 목적은 코드가 작성되기 *전에* 오해를 표면화하는 것입니다.

**사양서에 포함되어야 할 6가지 핵심 영역:**

1. **목표 (Objective)** — 무엇을 왜 만드는가? 사용자는 누구인가? 성공의 모습은 어떠한가?
2. **명령어 (Commands)** — 도구 이름만이 아닌 플래그가 포함된 실행 가능한 전체 명령어 (빌드, 테스트, 린트, 개발 서버).
3. **프로젝트 구조 (Project Structure)** — 소스 코드, 테스트, 문서가 위치할 디렉터리 레이아웃.
4. **코드 스타일 (Code Style)** — 장황한 설명 대신 원하는 스타일을 보여주는 실제 코드 스니펫 1개.
5. **테스트 전략 (Testing Strategy)** — 테스트 프레임워크, 테스트 위치, 커버리지 기대치.
6. **경계 및 제약 (Boundaries)**:
   - **항상 준수:** 커밋 전 테스트 실행, 명명 규칙 준수, 입력 유효성 검사
   - **사전 확인:** DB 스키마 변경, 의존성 추가, CI 설정 변경
   - **절대 금지:** 시크릿 커밋, 승인 없는 실패 테스트 삭제

**사양서 템플릿:**

```markdown
# 사양서: [프로젝트/기능 이름]

## 목표 (Objective)
[무엇을 왜 구축하는지, 유저 스토리 또는 인수 기준]

## 기술 스택 (Tech Stack)
[프레임워크, 언어, 주요 의존성 및 버전]

## 실행 명령어 (Commands)
[빌드, 테스트, 린트, 개발 서버 전체 명령어]

## 프로젝트 구조 (Project Structure)
[디렉터리 레이아웃 설명]

## 코드 스타일 (Code Style)
[예시 코드 스니펫 + 핵심 컨벤션]

## 테스트 전략 (Testing Strategy)
[프레임워크, 테스트 위치, 커버리지 요구사항]

## 경계 및 제약 (Boundaries)
- 항상 준수: [...]
- 사전 확인: [...]
- 절대 금지: [...]

## 성공 기준 (Success Criteria)
[완료되었음을 어떻게 알 수 있는지 — 구체적이고 테스트 가능한 조건]

## 미결 질문 (Open Questions)
[사람의 피드백이 필요한 미해결 질문]
```

**모호한 지시를 구체적인 성공 기준으로 재구성:**
- 요구사항: "대시보드를 더 빠르게 만들어줘"
- 재구성된 성공 기준:
  - 4G 네트워크에서 대시보드 LCP < 2.5초
  - 초기 데이터 로딩 < 500ms 이내 완료
  - 로딩 중 레이아웃 이동 없음 (CLS < 0.1)

### 2단계: 계획 수립 (Plan)

검증된 사양서를 바탕으로 기술적 구현 계획을 생성합니다:

1. 주요 컴포넌트 및 의존성 식별
2. 구현 순서 결정 (무엇을 먼저 구축해야 하는가)
3. 위험 요소 및 완화 전략 수립
4. 병렬 가능한 작업과 순차 작업 분류
5. 단계별 검증 체크포인트 정의

계획은 `tasks/plan.md`에 저장하고 작업 목록은 `tasks/todo.md`에 기록합니다.

### 3단계: 작업 분해 (Tasks)

계획을 세부 작업으로 나눕니다:
- 각 작업은 단일 집중 세션에서 완료 가능해야 함
- 각 작업은 명시적인 인수 기준을 가짐
- 각 작업은 검증 단계(테스트, 빌드, 수동 확인)를 포함함
- 중요도가 아닌 의존성 순서대로 정렬됨
- 단일 작업이 5개 이상의 파일을 수정하지 않도록 함

### 4단계: 구현 (Implement)

`incremental-implementation` 및 `test-driven-development` 스킬에 따라 작업을 하나씩 차례대로 수행합니다. `context-engineering`을 활용하여 전체 사양이 아닌 해당 작업에 필요한 섹션만 에이전트에게 로드하세요.

## 사양서의 지속적 관리 (Keeping the Spec Alive)

사양서는 일회성 산출물이 아니라 살아있는 문서입니다:
- **결정이 바뀌면 사양서 먼저 업데이트** — 데이터 모델 수정이 필요하면 사양서를 먼저 고치고 구현하세요.
- **범위 변경 반영** — 기능 추가/삭제 시 사양서에 반영.
- **버전 관리에 커밋** — 코드와 함께 리포지토리에 보관.

## 흔한 합리화 및 반박 (Common Rationalizations)

| 합리화 (Rationalization) | 실제 현실 (Reality) |
|---|---|
| "간단한 작업이니 사양이 필요 없다" | 간단한 작업도 인수 기준은 필요합니다. 두 줄짜리 짧은 사양이라도 작성하세요. |
| "코드 작성 후에 사양서를 쓰겠다" | 그것은 사양이 아니라 사후 문서화일 뿐입니다. 사양의 가치는 코딩 *전에* 명확성을 강제하는 데 있습니다. |
| "사양서 작성이 속도를 늦춘다" | 15분의 사양 작성이 몇 시간의 재작업을 막아줍니다. |
| "어차피 요구사항은 바뀐다" | 그렇기 때문에 사양서가 살아있는 문서여야 합니다. 낡은 사양이라도 없는 것보단 낫습니다. |
| "하나의 큰 기능이니 쪼개는 게 오버헤드다" | 인수 기준이 독립적으로 테스트 가능한 그룹으로 나뉜다면, 모놀리식 사양은 하류 작업을 복잡하게 만듭니다. 역량 맵으로 먼저 나누세요. |

## 위험 신호 (Red Flags)

- 문서화된 요구사항 없이 바로 코드를 작성하기 시작하는 것
- "완료(done)"의 의미를 명확히 하지 않고 개발을 시작하는 것
- 사양서나 작업 목록에 없는 기능을 임의로 구현하는 것
- 기록 없이 중요한 아키텍처 결정을 내리는 것
- 하나의 사양서가 독립적으로 검증 가능한 여러 역량을 한꺼번에 담고 있는 것

## 최종 검증 체크리스트 (Verification)

구현 단계로 넘어가기 전에:

- [ ] 사양서가 6가지 핵심 영역을 모두 다룸
- [ ] 사람이 사양서를 검토하고 승인함
- [ ] 성공 기준이 구체적이고 테스트 가능함
- [ ] 경계(항상/사전확인/절대금지)가 정의됨
- [ ] 사양서가 리포지토리 파일로 저장됨
- [ ] 여러 역량이 묶인 경우, 사전 역량 맵이 승인되었음
