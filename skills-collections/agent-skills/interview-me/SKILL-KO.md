# 나를 인터뷰해줘 (Interview Me)

## 개요 (Overview)

사람들이 요청하는 것과 실제로 원하는 것은 다릅니다. 사람들은 대시보드가 문제를 해결해서가 아니라 흔히 그렇게 요청하니까 "대시보드를 만들어달라"고 말합니다. 구체적인 목표 수치도 없이 "더 빠르게 만들어달라"고 말합니다.

이 간극을 발견하는 가장 비용이 적게 드는 순간은 어떠한 계획, 사양, 코드가 만들어지기 전입니다. 일단 개발을 시작하면 전환 비용이 발생하며, 사용자는 잘못된 결과물을 "이 정도면 됐다"며 합리화하게 됩니다. 그렇게 부적합한 설계가 고착화됩니다.

이 스킬은 비용이 발생하기 전에 그 간극을 좁힙니다. 다른 정의(Define) 단계의 스킬들은 이미 대략 무엇을 원하는지 알고 있다고 가정합니다: `idea-refine`은 아이디어로부터 변형을 생성하고, `spec-driven-development`는 요구사항을 문서화하며, `doubt-driven-development`는 작성된 계획을 스트레스 테스트합니다. `interview-me`는 이 모든 것의 '이전 단계'로서, 사용자가 말을 꺼내기도 전에 무슨 말을 할지 예측할 수 있을 때까지 본인의 추측(guess)을 덧붙여 한 번에 한 가지씩 질문하는 과정입니다.

## 사용 시점 (When to Use)

다음 상황에서 이 스킬을 적용하세요:

- 요청에 **누가(Who)** 대상인지, **왜(Why)** 원하는지, **성공(Success)**의 기준이 무엇인지, 제약 조건(**Constraint**)이 무엇인지 중 하나라도 누락되었을 때
- 요청이 구체적이지 않고 관습적일 때 ("X 만들어줘", "더 빠르게 해줘")
- 드러나지 않은 가정(assumption)을 바탕으로 작업을 시작하려는 유혹을 느낄 때
- 두 가지 합리적인 가치가 충돌할 때(단순성 vs 유연성, 비용 vs 속도) 사용자가 어떤 가치를 우선할지 명시하지 않았을 때
- 사용자가 명시적으로 호출할 때: "인터뷰해줘", "빡세게 질문해줘", "시작하기 전에 확실한지 점검해줘", "내 생각을 스트레스 테스트해줘"

**사용하지 않는 경우:**

- 요청이 명확하고 자명할 때 ("이 변수 이름 바꿔줘", "오타 수정해줘")
- 사용자가 검증보다 속도를 명시적으로 요구했을 때
- 단순 정보 요청 ("X는 어떻게 작동해?", "이 코드가 뭐하는 거야?")
- 기계적인 작업 (이름 변경, 포맷팅, 파일 이동)
- 이미 95% 이상의 확신이 있을 때 (아래 종료 조건 참조)

## 로딩 제약 조건 (Loading Constraints)

이 스킬은 실시간으로 응답하는 사용자가 필요합니다. CI 파이프라인, 예약된 실행, `/loop`, 자율 루프 등 **비대화형 컨텍스트에서는 호출하지 마세요.** 그러한 환경에서 요구사항이 불명확하다면 추측하지 말고 사용자 차단 요소(blocker)로 플래그를 지정하세요.

## 진행 절차 (The Process)

### 1단계: 가설 수립 및 확신도 수치 제시 (Hypothesize, with a confidence number)

어떤 질문을 하기 전에, 사용자가 원하는 것에 대한 현재 최선의 해석을 **한 문장**으로 적고, 솔직한 확신도(0–100%)를 기재합니다:

```
가설 (HYPOTHESIS): 스탠드업 미팅에서 "우리가 지금 잘하고 있는가?"에 답할 방법이 필요하며,
                  "대시보드"는 흔히 떠오르는 관습적인 표현으로 사용하셨습니다.
확신도 (CONFIDENCE): ~30% — 누락된 점: 사용 대상자, 맥락상 "지표"의 의미, 성공의 기준
```

수치를 적는 것은 정직함을 강제합니다. 높은 수치를 적었지만 다음에 할 3가지 질문에 대한 사용자의 반응을 예측할 수 없다면 그 수치는 잘못된 것입니다. 방어할 수 있는 솔직한 확신도 수준에서 시작하세요.

확신도가 70% 미만인 경우, 같은 줄에 아직 해결되지 않았거나 누락된 이유를 간략히 덧붙이세요. 이를 통해 인터뷰에서 무엇을 밝혀내야 하는지 사용자에게 명확히 전달합니다.

### 2단계: 추측을 덧붙여 한 번에 한 질문씩 하기 (Ask one question at a time, each with a guess attached)

질문 포맷:

```
Q: <집중된 질문 1개>
GUESS (추측): <그 답변에 대한 당신의 가설 및 그 가설을 도출한 근거>
```

다음 질문을 하기 전에 사용자의 반응을 기다리세요.

**왜 한 번에 여러 개가 아니라 한 개씩 질문하는가:**

- 질문 목록 속에 가설을 묻어버리면 사용자가 가설에 반응할 수 없습니다.
- 질문 묶음은 대충 훑어보고 피상적으로 답변하게 만듭니다.
- 3번째 질문은 종종 1번째 질문의 답변에 따라 달라집니다. 한꺼번에 물어보면 잘못된 프레임에 갇히게 됩니다.
- 신중하게 생각할 수 있는 사용자의 에너지는 유한합니다. 한 번에 한 질문에 집중하게 하세요.

**왜 추측(GUESS)을 덧붙이는가:**

- 백지상태에서 답을 생성하는 것보다 틀린 추측에 반박하는 것이 훨씬 빠릅니다.
- 눈에 띄게 틀릴 수 있는 가설을 제시함으로써 정직함을 유지합니다.
- 인터뷰의 목적인 에이전트 *자신의* 가정을 표면화합니다.

공손한 사용자가 맞장구치기 위해 추측에 무조건 동의하는 위험을 방지하려면, 언제든 틀릴 준비가 되어 있음을 보여주고, 가끔은 사용자가 반박할 것으로 예상되는 방향으로 추측을 제시하세요.

### 3단계: "원하는 것 vs 원해야 한다고 생각하는 것" 구별하기

가장 위험한 답변은 사용자가 실제로 원하는 것이 아니라, 사려 깊은 대답처럼 *들리는* 내용을 말할 때입니다. 다음을 주의 깊게 관찰하세요:

- 구체성 없이 모범 사례 단어("확장 가능해야 함", "클린 아키텍처")를 나열하는 답변
- 관습에 의존하는 답변 ("대부분의 앱이 하는 방식대로", "표준적인 접근법")
- "~해야 할 것 같다", "~하는 게 맞다고 생각한다", "좋은 엔지니어링 관행에 따르면…" 같은 표현
- 버즈워드를 목표로 삼는 경우 — 구체적 결과 대신 "현대적인", "확장 가능한", "견고한"이 목표가 될 때

이런 답변을 들었을 때 해야 할 핵심 질문:

> *"누구에게도 이 결정을 정당화하거나 설명할 필요가 없다면, 실제로 진짜 원하는 것은 무엇인가요?"*

이 질문 하나가 이전 다섯 개의 질문보다 더 많은 진실을 밝혀냅니다.

### 4단계: 사용자의 언어로 의도 재진술 (Restate intent in the user's own words)

확신도가 높아지면, 사용자가 원하는 것을 요약하여 제시합니다. 간결하게(5~8줄) 작성하고, 가능한 사용자의 표현을 사용하며, 사용자가 한 줄씩 확인하거나 수정할 수 있도록 구조화합니다:

```
제가 이해한 의도는 다음과 같습니다:

- 결과 (Outcome):      <한 줄>
- 사용자 (User):        <한 줄 — 혜택을 받는 대상>
- 이유 (Why now):      <한 줄 — 무엇이 달라졌는가>
- 성공 기준 (Success):   <한 줄 — 작동함을 어떻게 알 수 있는가>
- 제약 조건 (Constraint):<한 줄 — 반드시 지켜야 할 한계>
- 범위 제외 (Out of scope): <한 줄 — 명시적으로 하지 않을 작업>

맞나요 / 아닌가요 / 수정할 부분이 있나요?
```

**범위 제외(Out of scope)**를 포함하는 것은 필수입니다. 불일치의 절반은 *무엇을 만들지 않을 것인가*에 대한 암묵적 의견 차이에서 비롯됩니다.

### 5단계: 확인 — 명시적인 "예" 받기 (Confirm)

게이트는 명시적인 "예(Yes)"입니다. 다음은 승인이 **아닙니다**:

- "알아서 최선으로 생각하는 대로 해주세요." → 위임한 것이며, 사용자 본인도 95% 확신이 없음을 의미합니다. 선택할 수 있는 2가지 구체적 옵션으로 다시 질문하세요.
- "좋아 보이네요." → 모호함. "수정하고 싶은 부분이 있나요?"라고 묻기.
- "네, 진행하죠." → 정중한 회피일 수 있음. 구체적인 재확인 필요.
- 침묵 후 "네 시작해주세요." → 합의된 것이 아니라 인터뷰에 지친 상태일 수 있음.

수정 사항이 있다면 반영하여 다시 재진술하세요. 명시적인 승인을 얻을 때까지 반복합니다.

### 95% 확신도 종료 기준 (The 95% Confidence Stop)

다음 질문에 "예"라고 답할 수 있을 때 인터뷰를 종료합니다:

> *내가 다음에 던질 3가지 질문에 대해 사용자가 어떻게 반응할지 예측할 수 있는가?*

그렇다면 상호 이해에 도달한 것입니다. 인터뷰를 멈추고 최종 의도 요약을 작성하세요. 아니라면 아직 끝나지 않은 것이니 다음 질문을 진행하세요.

여러 라운드를 거쳤는데도 여전히 반응을 예측할 수 없다면, 계속 진행하지 말고 사용자에게 솔직히 말하세요: "몇 가지 질문을 드렸지만 아직 사용자분의 반응을 예측하기 어렵습니다. 근본적인 무언가가 누락된 것 같습니다. 한 걸음 물러서서 다시 정리해볼까요?"

## 산출물 (Output)

이 스킬의 최종 결과물은 **확인된 의도 선언서(Confirmed statement of intent)**입니다 (4단계의 재진술 + 5단계의 명시적 승인). 사양(Spec), 계획, 작업 목록은 하류(downstream) 단계이며, 이 스킬이 생산한 명확한 의도를 바탕으로 작성됩니다.

의도를 영구적으로 보존하길 원한다면 `docs/intent/[topic].md` 파일로 저장하세요.

## 대화 예시 (Example)

**`interview-me`가 없을 때:**

```
사용자: 우리 지표를 볼 수 있는 대시보드 하나 만들어줘
에이전트: <차트 라이브러리와 레이아웃을 제안하기 시작함>
```

에이전트는 누구를 위한 것인지, 어떤 지표인지, 성공 기준이 무엇인지 전부 자의적으로 가정했습니다. 나중에 사용자가 "내가 원한 건 이게 아닌데"라고 말할 위험이 큽니다.

**`interview-me`를 적용했을 때:**

```
사용자: 우리 지표를 볼 수 있는 대시보드 하나 만들어줘

에이전트:
가설: 스탠드업 미팅에서 "우리가 지금 잘하고 있는가?"에 답할 방법이 필요하며, 관습적인 표현으로 "대시보드"를 언급하셨습니다.
확신도: ~30% — 누락된 점: 사용 대상, 지표의 종류, 성공의 기준

Q:     "우리가 잘하고 있는가?"를 확인할 때, 확인 주체는 누구인가요? — 본인 혼자, 스탠드업의 엔지니어링 팀, 아니면 경영진/이사회인가요?
추측:   스탠드업의 엔지니어링 팀일 것 같습니다. "우리"라는 표현과 일상적인 점검 용도이기 때문입니다. 경영진 대상이라면 지표와 프레이밍이 완전히 달라집니다.

사용자: 사실은 저 혼자 볼 거예요. 어떤 실험들이 돌아가고 있고 초기 시그널이 어떤지 자꾸 놓쳐서요.

에이전트:
업데이트된 해석: 팀 대시보드가 아니라 개인용 실험 트래커입니다. 확신도: ~60% — 여전히 누락된 점: "초기 시그널"의 구체적 의미와 완료 기준.

Q:     현재 겪고 계신 문제는 어떤 실험이 존재하는지 목록을 모르는 것인가요, 아니면 결과가 한곳에 모이지 않는 것인가요?
추측:   후자일 것 같습니다. 실험 목록은 어딘가에 있지만 결과가 5개 툴에 흩어져 있어 수동 취합에 지치셨을 것입니다.

사용자: 사실은 전자예요. 목록 자체가 없어요. 여러 문서에 흩어져 있어요.

에이전트: <계속 진행>
```

단 2개의 질문만으로 에이전트는 실제 필요한 것이 "대시보드"가 아니라 "목록"이라는 사실을 발견했습니다. 산출물도, 범위도, 작업도 완전히 달라집니다. 대시보드를 만들었다면 완전히 헛수고가 되었을 것입니다.

## 흔한 합리화 및 반박 (Common Rationalizations)

| 합리화 (Rationalization) | 실제 현실 (Reality) |
|---|---|
| "요청이 충분히 명확하다" | 사용자가 원하는 결과를 지금 한 문장으로 명확히 적을 수 없다면 명확한 것이 아닙니다. |
| "질문을 너무 많이 하면 사용자 시간을 뺏는다" | 4~6개의 집중된 질문으로 쓰는 시간은 매우 적습니다. 엉뚱한 것을 만들어 낭비하는 시간은 엄청나며, 그 비용은 사용자가 치르게 됩니다. |
| "개발하면서 알아가면 된다" | 코드가 작성된 후의 전환 비용은 지금의 10배입니다. 구현 중의 발견은 곧 재작업(rework)을 의미합니다. |
| "'알아서 해달라'고 했으니 내가 결정하면 된다" | "알아서 해달라"는 결정이 아니라 위임입니다. 2가지 구체적 옵션을 제시하여 선택하게 하세요. |
| "추측을 덧붙이면 사용자를 유도(leading)하게 된다" | 유도하는 것이 핵심입니다. 틀린 추측에 반응하는 것이 백지에서 생각하는 것보다 훨씬 빠릅니다. 정직하게 틀릴 준비를 하세요. |
| "충분히 이야기했으니 이해했다" | 테스트해보세요: 다음 3가지 질문에 대한 사용자의 반응을 예측할 수 있나요? 아니라면 아직 이해하지 못한 것입니다. |

## 위험 신호 (Red Flags)

- 한 번에 3개 이상의 질문을 던지는 것 (인터뷰가 아니라 일괄 설문지임)
- 자신의 가설/추측(GUESS) 없이 질문만 던지는 것
- "알아서 최선으로 해주세요"를 최종 답변으로 수용하는 것
- 사용자가 재진술을 명시적으로 승인하기 전에 사양, 계획, 작업 목록을 먼저 생성하는 것
- "무엇이 모범 사례인가"를 묻고 "실제로 무엇을 원하는가"를 묻지 않는 것
- 사용자가 버즈워드("확장성", "클린")로 답했을 때 진짜 의도를 파고들지 않고 수용하는 것
- 확신도가 올라가지 않는데도 3라운드 이상 의미 없는 질문을 반복하는 것
- 70% 미만의 확신도에 이유를 명시하지 않는 것
- 재진술에서 "범위 제외(Out of scope)" 항목을 생략하는 것

## 최종 검증 체크리스트 (Verification)

interview-me 스킬 적용 후:

- [ ] 첫 턴에서 명시적인 가설과 확신도 수치가 제시됨
- [ ] 70% 미만의 확신도 수치마다 무엇이 누락되었는지 이유가 명시됨
- [ ] 질문은 한 번에 하나씩 에이전트의 추측과 함께 던져짐
- [ ] 모범 사례나 관습을 흉내 내는 답변에 대해 "진짜 원하는 것이 무엇인가"를 묻는 검증이 최소 1회 수행됨
- [ ] 구체적인 재진술(결과/사용자/이유/성공기준/제약/범위제외)이 작성되어 전달됨
- [ ] 사용자가 명시적인 "예"로 재진술을 확인함
- [ ] 종료 시점에서 에이전트가 다음 3가지 질문에 대한 사용자의 반응을 예측할 수 있음
- [ ] 하류 스킬(`idea-refine`, `spec-driven-development`)로의 인계가 모호한 원본 요청이 아닌 확인된 의도를 기반으로 이루어짐
