# 제약 주도 개발 (Constraint-Driven Development)

## 개요 (Overview)

이 스킬 팩의 다른 스킬들은 '좋은 코드란 무엇인가'를 설명합니다. `code-review-and-quality`는 5가지 축을 제공하고, `test-driven-development`는 개발 사이클을 제공하며, `security-and-hardening`은 위협 목록을 제공합니다. 하지만 이 모든 내용은 에이전트가 읽고 따를 수도 있고 따르지 않을 수도 있는 줄글(prose)로 존재하며, 세션이 끝나면 휘발됩니다.

이 스킬은 다른 결과를 만들어냅니다: 대화 세션이 끝나도 지속되며 기계적으로 검사할 수 있는, 구체적인 수치를 포함한 **이 프로젝트만의 명문화된 기준 기록**을 생성합니다.

이유는 명확합니다. 사람이 직접 코드를 작성할 때는 읽어보는 것만으로 품질을 알 수 있었습니다. 하지만 에이전트는 사람이 일주일 동안 읽을 수 있는 양보다 더 많은 코드를 단 한 번의 오후에 작성합니다. 따라서 판단의 기준은 사람의 머릿속에서 벗어나 개발 루프 주변에서 실행되는 자동화된 검사로 이동해야 합니다. 이러한 검사가 실제로 존재해야 하고, 직접 선택한 구체적인 수치가 있어야 하며, 에이전트가 자신의 출력을 스스로 수정할 수 있도록 작업과 가까운 시점에 트리거되어야 합니다.

스펙 주도 개발(Spec-driven development)은 무엇을 만들지 정의합니다. 테스트 주도 개발(Test-driven development)은 그것이 작동함을 증명합니다. 제약 주도 개발(Constraint-driven development)은 PR에서 논쟁이 벌어지기 전에 "배포 가능한 충분한 품질"이 무엇인지 정의합니다.

## 사용 시점 (When to Use)

다음 상황에서 이 스킬을 적용하세요:

- 프로젝트나 대규모 기능을 시작할 때 명문화된 품질 기준이 없을 때
- 사용자가 "제약 조건 설정해줘", "품질 게이트 추가해줘", "표준 정의해줘", "에이전트가 엉터리 코드를 배포하지 못하게 해줘"라고 요청할 때
- 에이전트가 아무도 한 줄 한 줄 읽지 못할 만큼 많은 양의 코드를 생성하고 있을 때
- CI에 검사 항목은 있지만 어떤 것이 병합 차단(block) 대상이고 어떤 것이 단순 장식인지 명확하지 않을 때
- 커버리지, 성능, 접근성 수치가 한 번 결정되지 않고 PR마다 논쟁거리가 될 때
- `/build auto`나 자율 루프를 실행하려 하는데, 메인 브랜치와 그것 사이에 있는 유일한 방어선이 에이전트가 직접 작성한 테스트 스위트뿐일 때

**사용하지 않는 경우:**

- 프로젝트에 이미 `CONSTRAINTS.md`가 있고 사용자가 이를 변경하지 않을 때 — 대신 읽고 준수할 것
- 일회성 스크립트, 스파이크(Spike), 폐기할 프로토타입
- 사용자가 지금 당장 코드 리뷰(`code-review-and-quality`)나 CI 파이프라인 구축(`ci-cd-and-automation`)을 원할 때
- 2주 후 폐기될 PMF(Product-Market Fit) 검증 이전 단계의 코드 — 아래의 '최소 기준(Floor)'은 가치가 있지만 나머지는 과합니다.

## 제약 조건 로딩 (Loading Constraints)

인터뷰에는 실제 사용자의 참여가 필요합니다. **비대화형 컨텍스트(CI, `/loop`, 자율 실행)에서는 인터뷰를 실행하지 마세요.** 그러한 환경에서 제약 조건이 누락되어 있다면, 아래의 '최소 기준(Floor)'만 적용하고 이를 기록한 뒤 나머지는 사람이 확인하도록 플래그를 남기세요.

## 진행 절차 (The Process)

### 1단계: 묻기 전에 먼저 감지하기 (Detect before you ask)

코드를 읽어서 알 수 있는 것을 사용자에게 묻지 마세요. 첫 질문을 하기 전에 다음을 먼저 수집합니다:

| 파악할 항목 | 확인할 위치 |
|---|---|
| 언어 및 스택 | `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml` |
| 테스트 러너 | devDependencies, `test` 스크립트, 기존 테스트 파일 |
| 기존 린터 | `eslint.config.*`, `biome.json`, `.ruff.toml` |
| 현재 커버리지 | `coverage/` 출력 결과, 또는 테스트 스위트 1회 실행 |
| CI 환경 | `.github/workflows/`, `.gitlab-ci.yml` |
| 에이전트 설정 | `.claude/`, `.codex/`, `AGENTS.md` |

발견한 내용을 두 줄로 요약하여 보고하고, 남은 내용만 질문하세요.

### 2단계: 기본값이 포함된 4가지 질문 (Four questions, each with a default)

`interview-me`의 '한 번에 한 질문' 원칙을 따르되, 한 가지 차이점이 있습니다: 여기의 모든 질문에는 기본값(default)이 있으므로 "잘 모르겠다"고 답해도 정상 작동하는 설정이 생성됩니다.

```
Q1: 기본 최소 기준 외에 다음 중 강제하고자 하는 항목은 무엇인가요?
    (a) 새로운 코드에 대한 테스트 커버리지
    (b) 보안 스캐닝
    (c) 성능 예산 (Performance budget)
    (d) 접근성 (Accessibility)
    (e) 아키텍처 경계
추천(GUESS): (a) 및 (b) — 이미 테스트 러너가 있고 사용자 입력을 처리하고 있습니다.
불확실할 때 기본값: (a) 및 (b).
각 선택에 필요한 비용 안내: (c)와 (d)는 실행 중인 URL이 필요하며, (e)는 규칙 파일 작성이 필요합니다.
```

```
Q2: 에이전트가 작업 중 검사에 실패했을 때 작업을 차단(Block)해야 하나요, 아니면 경고(Warn)만 해야 하나요?
추천(GUESS): 차단(Block). 에이전트를 무인으로 실행하고 있다면 아무도 안 보는 경고는 의미가 없습니다.
불확실할 때 기본값: 최소 기준(Floor)은 차단, 나머지는 첫 2주 동안 경고.
```

```
Q3: 염두에 둔 목표 수치가 있나요, 아니면 현재 상태를 측정하여 그 선을 유지(ratchet)할까요?
추천(GUESS): 현재 측정 후 유지. 대부분의 팀은 명확한 수치가 없으며, 임의로 만든 수치는 무시됩니다.
불확실할 때 기본값: 현재 상태 측정 후 유지 (아래 래칫 섹션 참조).
```

```
Q4: 에이전트가 작업을 넘기기 전까지 허용할 수 있는 가장 긴 검사 시간은 얼마인가요?
추천(GUESS): 약 90초. 더 길어지면 검사를 실행하지 않게 됩니다.
불확실할 때 기본값: 작업 종료 시 90초, CI에서는 무제한.
```

질문은 최대 4개로 제한합니다. 12개의 질문은 아무도 이해하지 못하는 설정과 후회하는 사용자만 남깁니다.

### 3단계: CONSTRAINTS.md 작성 (Write CONSTRAINTS.md)

리포지토리 루트에 단 하나의 파일로 생성합니다. 어떤 하네스의 어떤 에이전트도 읽을 수 있으며, 이에 대한 변경 사항은 코드 리뷰에 드러납니다.

```markdown
# 제약 조건 (Constraints)

마지막 검토: 2026-08-08 by @addy

## 최소 기준 (Floor - 항상 강제됨, 추가 설정 불필요)

- 새로운 억제 주석 금지: `@ts-ignore`, `eslint-disable`, `# noqa`, `# type: ignore`
- 미구현 스텁 금지: `throw new Error("Not implemented")`, 빈 `catch {}`
- 커밋 메시지에 명확한 이유가 없는 테스트 스킵 또는 삭제 금지
- 소스 코드 내 시크릿 노출 금지
- 테스트를 억지로 통과시키기 위해 이 파일을 약화시키지 말 것

## 수치로 강제되는 항목 (Enforced with numbers)

| 차원 | 규칙 | 검사 도구/명령어 | 실행 시점 |
|---|---|---|---|
| 타입 | 타입 에러 0개 | `tsc --noEmit` | 매 수정 시 |
| 린트 | 설정 규칙 에러 0개 | `biome check` | 매 수정 시 |
| 시크릿 | 소스 내 시크릿 없음 | `gitleaks detect --redact` | 매 수정 시 |
| 커버리지 | 변경 라인 커버리지 ≥ 80% | `vitest run --coverage` + git diff | 작업 완료 시, CI |
| 보안: 코드 | High 등급 이상 취약점 없음 | `semgrep scan --config p/default` | CI |
| 보안: 의존성 | High 등급 이상 취약점 없음 | `osv-scanner scan source -r .` | CI |
| 접근성 | Critical 또는 Serious 0개 | `axe $PREVIEW_URL --tags wcag2a,wcag2aa,wcag21aa` | 프리뷰 배포 시 |
| 성능 | LCP ≤ 2500ms, CLS ≤ 0.1 | `lighthouse $PREVIEW_URL --output=json` | 프리뷰 배포 시 |

모든 행에는 결과를 도출하는 구체적인 명령어가 명시되어야 합니다.
수치만 있고 이 열에 실행 명령어가 없는 차원은 제약 조건이 아니라 희망 사항일 뿐입니다.

## 측정 중 (아직 강제되지 않음)

| 지표 | 현재 수치 | 방향 |
|---|---|---|
| 프로젝트 전체 커버리지 | 62.4% | 하락 금지 |
| 번들 크기 (main) | 184 kB | 증가 금지 |

## 예외 사항 (Exceptions)

| ID | 규칙 | 경로 | 사유 | 담당자 | 만료일 |
|---|---|---|---|---|---|
| W1 | `no-explicit-any` | `src/legacy/**` | ENG-441에서 재작성 추적 중 | @addy | 2026-11-01 |
```

그런 다음 `AGENTS.md`와 `CLAUDE.md`에 한 줄을 추가합니다: `코드를 작성하기 전에 CONSTRAINTS.md를 읽으세요. 검사를 통과시키기 위해 이를 약화시키지 마세요.`

### 4단계: 각 차원에 필요한 도구 설치 (Install what each dimension needs)

차원을 선택했다는 것은 도구를 설치해야 함을 의미합니다. 수치만 정해두고 실행 메커니즘을 방치하지 마세요. 사실상의 표준(de facto) 도구가 이미 존재할 때 자체 검사 도구를 새로 만들지 마세요 — 아래 도구들은 그 규칙 형식과 임계값이 생태계의 표준이므로 팀의 기존 설정과 잘 맞아떨어집니다.

| 차원 | 도구 | 설치 방법 | 실행 명령어 | 차단 기준 |
|---|---|---|---|---|
| 타입 (TS) | tsc | 이미 존재 | `tsc --noEmit` | 모든 에러 |
| 타입 (Python) | mypy | `pip install mypy` | `mypy .` | 모든 에러 |
| 린트 | 기존 린터 | 이미 존재 | `eslint .` / `biome check` / `ruff check` | 모든 에러 |
| 커버리지 (JS) | 기존 테스트 러너 | 이미 존재 | `vitest run --coverage` (또는 `jest --coverage`) | 변경된 라인의 커버리지 |
| 커버리지 (Python) | pytest-cov | `pip install pytest-cov` | `pytest --cov --cov-report=lcov` | 변경된 라인의 커버리지 |
| 보안: 코드 | Semgrep | `pipx install semgrep` | `semgrep scan --config p/default --config p/owasp-top-ten` | High 등급 발견 시 |
| 보안: 시크릿 | gitleaks | `brew install gitleaks` | `gitleaks detect --redact --no-banner` | 모든 발견 사항 |
| 보안: 의존성 | osv-scanner | `brew install osv-scanner` | `osv-scanner scan source -r .` | High 등급 이상 |
| 성능: 페이지 | Lighthouse | `npm i -D lighthouse` | `lighthouse $URL --output=json --quiet` | LCP, CLS, 성능 점수 |
| 성능: 번들 | size-limit | `npm i -D size-limit` | `size-limit --json` | 엔트리별 바이트 예산 |
| 접근성 | axe-core | `npm i -D @axe-core/cli` | `axe $URL --tags wcag2a,wcag2aa,wcag21aa` | Critical 또는 Serious 0개 |
| 아키텍처 | dependency-cruiser | `npm i -D dependency-cruiser` | `depcruise --validate src` | 모든 위반 사항 |
| Assertion 품질 | Stryker | `npm i -D @stryker-mutator/core` | `stryker run --mutate <changed files>` | 뮤테이션 점수 |

건너뛰면 문제를 일으키는 5가지 주의사항:

1. **gitleaks의 `--redact`는 필수입니다.** 이것이 없으면 발견된 시크릿이 에이전트 트랜스크립트에 그대로 남아 로그, 요약, 커밋 메시지로 유출될 수 있습니다. 규칙과 위치만 보고하고 값은 절대 노출하지 마세요.
2. **Lighthouse와 axe는 실행 중인 URL이 필요합니다.** 실제 실행 중인 앱을 대상으로만 작동하므로, 프리뷰 배포나 먼저 시작된 로컬 서버를 대상으로 런타임 단계에서 실행해야 합니다. CLI, 라이브러리 등 URL이 없는 프로젝트라면 실행할 수 없는 가짜 검사를 만들지 말고 해당 차원을 제외하세요.
3. **비용이 큰 검사는 diff 범위로 한정하세요.** 전체 리포지토리에 대한 `stryker run --mutate`는 몇 시간이 걸려 결국 꺼버리게 되지만, 변경된 파일에 대해서만 실행하면 1분 미만으로 끝납니다. 경로 목록을 받는 Semgrep도 마찬가지입니다.
4. **커버리지 측정을 위해 테스트를 두 번 돌리지 마세요.** 기존 테스트 스위트가 생성한 lcov 파일을 읽어 `git diff`와 교차 비교하세요. 수치를 얻겠다고 전체 테스트를 두 번 실행하는 것은 검사 시스템을 기피하게 만드는 지름길입니다.
5. **Semgrep의 레지스트리 규칙은 무료로 실행 가능하지만 재배포 라이선스를 확인하세요.** 법무팀 요구사항이 있다면 동일한 규칙 형식과 JSON 출력을 제공하는 오픈소스 포크인 `opengrep`을 드롭인 대체재로 사용할 수 있습니다.

에이전트 없이도 재현할 수 있도록 프로젝트의 `package.json` 스크립트에 추가하세요:

```json
{
  "scripts": {
    "check:fast": "tsc --noEmit && eslint . && gitleaks detect --redact --no-banner",
    "check:task": "npm run check:fast && vitest run --coverage",
    "check:full": "npm run check:task && semgrep scan --config p/default && osv-scanner scan source -r ."
  }
}
```

이 매핑은 도구 자체보다 중요합니다. `check:fast`는 코드 수정 직후 실행되고, `check:task`는 에이전트가 작업 완료를 선언할 때, `check:full`은 CI에서 실행됩니다.

명령어는 `CONSTRAINTS.md`의 `검사 도구/명령어` 열과 이 스크립트 두 곳에 존재합니다. `CONSTRAINTS.md`가 단일 진실 공급원(canonical source)입니다. 스크립트와 내용이 충돌할 경우 `CONSTRAINTS.md`가 우선합니다.

### 5단계: 라이프사이클에 연결 (Wire it to the lifecycle)

가장 큰 실수는 모든 곳에서 모든 검사를 실행하는 것입니다. 에이전트의 작업을 지체시키는 검사는 결국 비활성화되며, 비활성화된 게이트는 게이트가 없는 것보다 위험합니다(기준이 존재하는 것처럼 착각하게 만들기 때문).

| 단계 | 명령어 | 실행 내용 | 허용 시간 예산 |
|---|---|---|---|
| BUILD | `/build` | 타입, 린트, 시크릿, 최소 기준(Floor) | 5초 미만, 변경된 파일만 |
| VERIFY | `/test` | 관련 테스트, 변경 라인 커버리지 | 90초 미만 |
| REVIEW | `/review` | 모든 검사 + 아래의 기준 보호 가드 검사 | 수 분 |
| SHIP | `/ship` | 방향성 검사, 회귀 버그 없음 확인 | CI |

유지 가능한 수준을 지키기 위한 2가지 규칙:

1. **diff 범위로 한정할 것.** 전체 리포가 아닌 이번 변경이 건드린 라인을 검사하세요. 변경 라인의 커버리지는 에이전트가 직접 개선할 수 있는 수치이지만, 프로젝트 전체 커버리지는 상속받은 수치입니다.
2. **비용이 실행 위치를 결정함.** 몇 초 이상 걸리는 것은 편집 루프 밖으로 빼세요. 전체 리포의 뮤테이션 테스트는 몇 시간이 걸리지만 변경된 파일만 대상으로는 1분 미만입니다.

### 6단계: 기준 자체를 보호하기 (Guard the bar itself)

"에이전트가 코드와 검사를 모두 작성한다면 그 검사는 아무것도 증명하지 못한다"는 지적이 있을 수 있습니다. 반은 맞고, 대비가 필요한 부분입니다.

에이전트는 교묘한 허점을 파고들지 않습니다. 실패하는 검사를 만나면 통과하기 위한 '가장 비용이 적게 드는 길'을 택할 뿐입니다. 리뷰 시 diff에서 다음 5가지 시도를 감시하세요:

1. **임계값을 낮춤:** 예산을 낮추거나, 심각도를 낮추거나, 빠른 검사 단계에서 항목을 제거함. 브랜치 시작 지점의 `CONSTRAINTS.md`와 비교하세요.
2. **테스트를 쉽게 만듦:** `.skip` 추가, 테스트 파일 삭제, 테스트 내부의 assertion 제거.
3. **검사기를 침묵시킴:** 새로운 `@ts-ignore` 또는 `eslint-disable`. 특히 의존하는 검사를 꺼버리는 억제에 주의하세요: `istanbul ignore`(테스트 대신 커버리지에서 제외), `Stryker disable`(돌연변이 숨김), `nosemgrep` 및 `gitleaks:allow`(보안 발견 숨김).
4. **미완성 작업 방치:** 에러를 던지는 스텁, 실패를 조용히 덮는 빈 `catch`, 구현되어야 할 자리에 방치된 `TODO`.
5. **예외가 몰래 추가됨:** 논의되지 않은 새로운 행이 예외 테이블에 추가됨.

이 감시에는 `git diff` 외의 별도 도구가 필요하지 않습니다. 기준을 강화하는 것은 조용히 진행되어도 되지만, 기준을 약화시키는 것은 크게 드러나야 합니다.

**모든 검사가 똑같이 순환적인 것은 아닙니다.** 다음 질문으로 검사를 분류하세요: "에이전트가 작동하지 않는 코드를 작성해서 이 검사를 통과시킬 수 있는가?"

- **외부(External):** axe-core는 WCAG를 인코딩하고, `osv-scanner`는 취약점 DB를 읽으며, Lighthouse는 실제 브라우저를 측정합니다. 에이전트는 이를 속일 수 없습니다.
- **프로젝트(Project):** 린트 규칙, 레이어 경계. 사람이 규칙 파일을 소유합니다.
- **스위트(Suite):** 프로젝트 자체의 테스트. 가장 유용하지만 유일하게 완전히 순환적인 검사입니다.

세 번째 종류로만 구성된 기준선은 외부의 시각이 포함된 기준선보다 취약합니다. 최소한 하나 이상의 외부 제약 조건이 포함되어 있는지 확인하세요.

### 7단계: 수치가 없을 때의 래칫(Ratchet) 전략

현재 62% 커버리지인 코드베이스에 무작정 80%를 설정하면 빌드는 영원히 빨간색(실패)이 되고, 팀은 빨간 빌드를 무시하는 법을 배우게 됩니다.

대안은 결정을 강요하지 않는 것입니다: 현재 상태를 기록하고, '더 나빠지는 것'을 거부하세요. "측정 중 (아직 강제되지 않음)" 테이블에 오늘의 수치와 방향을 기록합니다. 모든 검사는 막연한 목표가 아닌 기록된 실제 값과 비교됩니다. 수치가 개선되면 업데이트하고, 떨어지면 그것이 바로 지적 사항이 됩니다.

이는 AI 모델 학습의 한계를 보완합니다. 모델은 초 단위로 평가할 수 있는 테스트 통과에는 보상을 받지만, 몇 달에 걸쳐 나타나는 아키텍처 부패에는 벌을 받지 않습니다. 래칫(Ratchet)은 빌드가 확인할 수 있는 형태로 기록된 '누락된 페널티'입니다.

## 합리적인 기본값 (Sane Defaults)

사용자의 명확한 의견이 없을 때는 다음 기본값을 사용하세요:

| 제약 조건 | 기본값 | 선택 이유 |
|---|---|---|
| 변경 라인 커버리지 | ≥ 80% | 테스트 작성을 강제하기에 충분히 높고 설정 파일 등을 허용할 만큼 합리적임 |
| 프로젝트 전체 커버리지 | 오늘의 수치, 하락 금지 | 논쟁 없이 즉시 도입 가능 |
| 뮤테이션 점수 (사용 시) | 시작 시 ≥ 60% | 이전에 뮤테이션 테스트를 안 해본 스위트의 일반적 수준 (80%는 성숙 단계) |
| 의존성 취약점 | High 등급 이상 없음 | 그 이하는 대부분 노이즈임 |
| LCP | ≤ 2500 ms | Core Web Vitals의 "좋음(Good)" 기준 |
| CLS | ≤ 0.1 | 동일 |
| 접근성 | Critical 또는 Serious 위반 0개 | Moderate 및 Minor는 논쟁의 여지가 많음 |
| 예외 만료 기간 | 90일 | 수정을 계획하기에 충분하고 잊혀지지 않을 만큼 짧음 |
| 래칫 허용 오차 | 0.5% | 무관한 파일 수정으로 인한 미세한 수치 변동 흡수 |

수치와 이유를 항상 함께 명시하세요. 근거 없는 임계값은 나중에 문제를 겪는 다음 사람에 의해 삭제됩니다.

## 단계적 적용 경로 (Escalation Path)

제약 조건은 3단계 강도로 적용할 수 있습니다. 1단계부터 시작하세요.

1. **문서 전용:** `CONSTRAINTS.md`가 존재하고 에이전트가 이를 읽음. 비용이 들지 않고 정직한 실수를 잡아내며 에이전트의 준수에 의존함.
2. **스크립트 기반:** 빠른 검사를 실행하는 `npm run check`(또는 `make check`)가 에이전트의 편집 후 훅(hook)과 CI에 연결됨. 결정론적이며 새로운 의존성 없음.
3. **도구 기반:** diff 범위 지정, 예산, 래칫, 가드 검사를 전담 러너가 처리. 설정이 셸 스크립트 범위를 넘어설 때 사용.

대부분의 프로젝트는 2단계로 충분합니다. 검사 셸 스크립트가 30줄 이상 늘어날 때 3단계로 이동하세요.

**첫날에는 최소 기준(Floor)만 적용해도 됩니다.** 최소 기준 가드는 diff만 검사하며 도구 설치가 필요 없으므로, 첫 커밋부터 보호할 수 있습니다. 수치화된 차원은 도구를 설치하면서 점진적으로 추가하세요.

## 흔한 합리화 및 반박 (Common Rationalizations)

| 변명 (Excuse) | 실제 현실 (Reality) |
|---|---|
| "코드가 안정화되면 제약 조건을 추가하겠다" | 코드는 작성되는 동안 허용되었던 기준에 맞춰 굳어집니다. |
| "테스트가 곧 제약 조건이다" | 직접 작성한 테스트는 본인의 생각과 일치함을 증명할 뿐, 신규 코드 커버리지, 의존성 위험, 번들 증가에 대해선 아무것도 말해주지 않습니다. |
| "80% 커버리지는 달성할 수 없다" | 그렇다면 80%로 설정하지 마세요. 오늘의 수치를 기록하고 그 선을 유지하세요. |
| "이것 때문에 에이전트 작업이 느려진다" | 빠른 루프에 느린 검사를 넣었을 때만 그렇습니다. 그것은 배치 위치의 오류이지 제약 조건 자체의 문제가 아닙니다. |
| "우리 표준이 뭔지 머릿속으로 기억하고 있다" | 에이전트는 기억하지 못하며, 대부분의 코드를 에이전트가 작성하고 있습니다. |
| "제약 조건 때문에 배포가 막힌다" | 담당자와 기한이 명시된 예외(Exception)를 등록하면 차단이 해제됩니다. 제약 조건을 삭제하는 것은 모두에게 영구적으로 문을 열어주는 것입니다. |

## 위험 신호 (Red Flags)

다음을 발견하면 즉시 멈추고 재검토하세요:

- 인터뷰 질문이 4개를 넘어가거나 사용자가 설명하지 못하는 설정이 만들어짐
- 현재 코드베이스가 실패하고 있는데 달성 계획도 없는 비현실적 예산 설정
- `CONSTRAINTS.md`에 수치는 적혀 있지만 뒷받침하는 도구가 없음
- 사실상의 표준 도구가 있는데도 자체 검사기를 급조하여 기존 설정을 무시함
- 모든 제약 조건이 외부 시각 없이 프로젝트 자체 테스트 스위트로만 검사됨
- 실패하던 기능 변경 커밋에 `CONSTRAINTS.md` 완화가 함께 포함됨
- 예외에 담당자가 없거나 만료일이 1년 이상 뒤로 잡혀 있음
- 에이전트가 코드를 고치는 대신 임계값 완화를 제안함
- 편집 루프에 느린 검사가 들어가 사용자가 `--no-verify`를 쓰기 시작함
- 작성된 이후 아무도 `CONSTRAINTS.md`를 열어보지 않음

## 최종 검증 체크리스트 (Verification)

이 스킬이 올바르게 적용되었을 때:

- [ ] `CONSTRAINTS.md`가 존재하며 모든 수치에 이유가 명시됨
- [ ] 최소 기준(Floor)이 강제되며 현재 코드베이스에서 변경 없이 통과함
- [ ] 사용자가 선택한 모든 차원에 도구가 설치되고 실행 명령어가 존재함
- [ ] 각 제약 조건의 실행 위치가 정의되어 있고, 빠른 단계는 수 초 내로 완료됨
- [ ] 최소 하나 이상의 외부 제약 조건(자체 테스트가 아닌 외부 기준)이 포함됨
- [ ] 측정 전용 지표에 오늘의 수치와 유지 방향이 기록됨
- [ ] 예외 사항에 담당자와 만료일이 지정됨
- [ ] `AGENTS.md` 또는 `CLAUDE.md`가 이 파일을 참조하도록 설정됨
- [ ] 현재 브랜치에서의 시험 실행 결과 사용자가 동의하지 않는 실패가 발생하지 않음
