# 문서화와 ADR

## 개요

코드뿐 아니라 결정도 문서화합니다. 가장 가치 있는 문서는 *왜*를 담습니다. 즉, 결정으로 이어진 맥락, 제약, 트레이드오프입니다. 코드는 *무엇을* 만들었는지 보여주고, 문서는 *왜 이렇게 만들었는지*와 *어떤 대안을 검토했는지*를 설명합니다. 이 맥락은 앞으로 코드베이스에서 작업할 사람과 에이전트에게 필수적입니다.

## 사용 시점

- 중요한 아키텍처 결정을 내릴 때
- 경쟁하는 접근법 중 하나를 고를 때
- 공개 API를 추가하거나 변경할 때
- 사용자에게 보이는 동작을 바꾸는 기능을 출시할 때
- 새 팀원(또는 에이전트)을 프로젝트에 온보딩할 때
- 같은 내용을 반복해서 설명하고 있는 자신을 발견할 때

**사용하지 않을 때:** 자명한 코드를 문서화하지 마세요. 코드가 이미 말하는 내용을 되풀이하는 주석을 달지 마세요. 버릴 프로토타입에 대한 문서를 쓰지 마세요.

## 아키텍처 결정 기록(ADR)

ADR은 중요한 기술 결정의 배경을 기록합니다. 여러분이 쓸 수 있는 문서 중 가장 가치가 높습니다.

### ADR을 작성할 때

- 프레임워크, 라이브러리, 주요 의존성을 고를 때
- 데이터 모델이나 데이터베이스 스키마를 설계할 때
- 인증 전략을 고를 때
- API 아키텍처를 결정할 때(REST vs. GraphQL vs. tRPC)
- 빌드 도구, 호스팅 플랫폼, 인프라를 고를 때
- 되돌리는 데 비용이 많이 드는 모든 결정

### 먼저 기존 관례를 따르세요

ADR을 만들기 전에 저장소에서 확립된 관례가 있는지 확인하세요. 기존 ADR, 프로젝트 지침, ADR 관련 설정이나 도구(예: `.adr-dir` 파일)를 살펴보면 됩니다. 확립된 관례는 아래의 기본값보다 우선합니다. 다음을 맞추세요.

- **위치와 형식** — 예: `docs/adr/*.md`, `Documentation/Decisions/*.rst`, MADR 레이아웃, 또는 `adr-tools` 설정. 기존 디렉터리, 파일 확장자, 마크업 방식(Markdown vs reStructuredText)을 따르세요.
- **번호와 이름** — 기존 순서와 파일명 패턴을 이어가세요(`ADR-004-Title.rst`, `0004-title.md` 등). 001부터 다시 시작하거나 두 번째 체계를 도입하지 마세요.
- **섹션 제목** — 이 템플릿의 제목을 강요하지 말고 프로젝트가 이미 쓰는 제목 체계를 재사용하세요.

근거가 서로 충돌하면 말없이 다른 체계를 들여오지 말고 충돌을 드러내세요. 관례를 전혀 확인할 수 없을 때에만 아래 기본값을 적용합니다.

### ADR 템플릿

ADR은 `docs/decisions/`에 순차 번호를 붙여 저장합니다(프로젝트가 이미 다른 위치를 쓰고 있다면 위 내용을 따르세요).

```markdown
# ADR-001: 기본 데이터베이스로 PostgreSQL 사용

## 상태
Proposed | Accepted | Superseded by ADR-XXX | Deprecated

## 날짜
2025-01-15

## 맥락
작업 관리 애플리케이션을 위한 기본 데이터베이스가 필요합니다. 주요 요구사항은 다음과 같습니다.
- 관계형 데이터 모델(사용자, 작업, 팀 간의 관계)
- 작업 상태 변경을 위한 ACID 트랜잭션
- 작업 내용에 대한 전문 검색(full-text search) 지원
- 관리형 호스팅 이용 가능(소규모 팀이라 운영 역량이 제한적)

## 결정
Prisma ORM과 함께 PostgreSQL을 사용합니다.

## 검토한 대안

### MongoDB
- 장점: 유연한 스키마, 시작이 쉬움
- 단점: 우리 데이터는 본질적으로 관계형이라 관계를 직접 관리해야 함
- 기각: 문서 저장소에 관계형 데이터를 담으면 복잡한 조인이나 데이터 중복이 생김

### SQLite
- 장점: 설정이 필요 없고, 임베디드 방식이며, 읽기가 빠름
- 단점: 동시 쓰기 지원이 제한적이고, 운영 환경을 위한 관리형 호스팅이 없음
- 기각: 운영 환경의 다중 사용자 웹 애플리케이션에는 적합하지 않음

### MySQL
- 장점: 성숙하고, 널리 지원됨
- 단점: PostgreSQL이 JSON 지원, 전문 검색, 생태계 도구 면에서 더 나음
- 기각: 우리의 기능 요구사항에는 PostgreSQL이 더 잘 맞음

## 결과
- Prisma가 타입 안전한 데이터베이스 접근과 마이그레이션 관리를 제공함
- Elasticsearch를 추가하는 대신 PostgreSQL의 전문 검색을 사용할 수 있음
- 팀에 PostgreSQL 지식이 필요함(일반적인 기술이며 위험은 낮음)
- 관리형 서비스(Supabase, Neon, 또는 RDS)에서 호스팅함
```

### ADR 수명 주기

```
PROPOSED → ACCEPTED → (SUPERSEDED or DEPRECATED)
```

- **오래된 ADR을 삭제하지 마세요.** 과거의 맥락을 담고 있습니다.
- 결정이 바뀌면 기존 ADR을 참조하고 대체하는 새 ADR을 작성하세요.

## 인라인 문서화

### 주석을 달 때

*무엇*이 아니라 *왜*를 주석으로 남기세요.

```typescript
// 나쁨: 코드를 그대로 다시 말함
// 카운터를 1 증가
counter += 1;

// 좋음: 명확하지 않은 의도를 설명함
// 레이트 리밋은 슬라이딩 윈도우를 사용함 — 카운터는 고정된 주기가 아니라
// 윈도우 경계에서 초기화해야 함. 그래야 윈도우 가장자리에서의 버스트 공격을 막을 수 있음
if (now - windowStart > WINDOW_SIZE_MS) {
  counter = 0;
  windowStart = now;
}
```

### 주석을 달지 말아야 할 때

```typescript
// 스스로 설명되는 코드에는 주석을 달지 마세요
function calculateTotal(items: CartItem[]): number {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

// 지금 바로 해야 할 일을 TODO로 남기지 마세요
// TODO: add error handling  ← 그냥 지금 추가하세요

// 주석 처리된 코드를 남기지 마세요
// const oldImplementation = () => { ... }  ← 삭제하세요. git에 이력이 있습니다
```

```yaml
paths:
```

## README 구조

모든 프로젝트에는 다음 내용을 다루는 README가 있어야 합니다.

```markdown
# 프로젝트 이름

이 프로젝트가 무엇을 하는지 설명하는 한 단락.

## 빠른 시작
1. 저장소를 클론합니다
2. 의존성을 설치합니다: `npm install`
3. 환경을 설정합니다: `cp .env.example .env`
4. 개발 서버를 실행합니다: `npm run dev`

## 명령어
| 명령어 | 설명 |
|---------|-------------|
| `npm run dev` | 개발 서버 시작 |
| `npm test` | 테스트 실행 |
| `npm run build` | 프로덕션 빌드 |
| `npm run lint` | 린터 실행 |

## 아키텍처
프로젝트 구조와 핵심 설계 결정에 대한 간략한 개요.
자세한 내용은 ADR로 링크합니다.

## 기여하기
기여 방법, 코딩 표준, PR 절차.
```

## 변경 로그 관리

출시된 기능에 대해서는 다음과 같이 씁니다.

```markdown
# 변경 로그

## [1.2.0] - 2025-01-20
### 추가됨
- 작업 공유: 사용자가 팀원과 작업을 공유할 수 있음 (#123)
- 작업 할당 시 이메일 알림 (#124)

### 수정됨
- 생성 버튼을 빠르게 연속 클릭할 때 작업이 중복으로 나타나는 문제 (#125)

### 변경됨
- 더 나은 UX를 위해 작업 목록이 페이지당 50개 항목을 불러옴(이전에는 20개) (#126)
```

## 에이전트를 위한 문서

AI 에이전트의 맥락에서 특히 고려할 사항입니다.

- **CLAUDE.md / 규칙 파일** — 에이전트가 따르도록 프로젝트 관례를 문서화하세요
- **명세 파일** — 에이전트가 올바른 것을 만들도록 명세를 최신 상태로 유지하세요
- **ADR** — 과거 결정이 왜 이루어졌는지 에이전트가 이해하도록 돕습니다(같은 결정을 다시 하는 것을 막음)
- **인라인 함정 주석** — 에이전트가 알려진 함정에 빠지지 않도록 막아줍니다

## 문장 검토

기술적 내용을 확인한 뒤에는 이 문서를 읽을 사람을 위해 문장을 검토하세요. 문장을 명확하게 고치더라도 결정이나 그 한계를 바꿔서는 안 됩니다.

1. 수정 과정에서 반드시 보존해야 할 세부 사항을 표시하세요. 이름, 숫자와 단위, 명령어, 경로, 링크, 조건, 트레이드오프, 불확실성이 여기에 해당합니다. 이를 사용 가능한 코드와 결정 맥락에 대조하고, 확인할 수 없는 내용은 표시하세요.
2. 상투적인 도입부, 홍보성 형용사, 반복되는 요약을 독자에게 필요한 구체적 정보로 바꾸세요. 근거 없는 주장을 지어낸 예시나 더 강한 보장으로 바꾸지 마세요. 필요한 기술적 반복과 프로젝트에서 확립된 용어는 유지하세요.
3. 수정본을 원본 및 출처와 비교하세요. 빠진 한정어나 주의 문구를 복원하고, 명령어와 코드 예시가 문서대로 여전히 동작하는지 확인하세요. 해결되지 않은 사실 관계 문제는 다듬어서 감추지 말고 설명하세요.

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "코드가 스스로 문서화되어 있다" | 코드는 *무엇*을 보여줄 뿐입니다. *왜*, 기각된 대안, 적용되는 제약은 보여주지 않습니다. |
| "API가 안정되면 문서를 쓸게요" | 문서화하면 API가 더 빨리 안정됩니다. 문서는 설계를 처음으로 검증하는 수단입니다. |
| "아무도 문서를 안 읽어요" | 에이전트는 읽습니다. 미래의 엔지니어도 읽습니다. 3개월 뒤의 여러분 자신도 읽습니다. |
| "ADR은 부담이에요" | 10분짜리 ADR이 6개월 뒤 같은 결정을 두고 벌어질 2시간짜리 논쟁을 막아 줍니다. |
| "주석은 금방 낡아요" | *왜*에 대한 주석은 오래 유효합니다. *무엇*에 대한 주석이 낡습니다. 그래서 *왜*만 씁니다. |

## 위험 신호

- 서면 근거 없이 내려진 아키텍처 결정
- 문서나 타입이 없는 공개 API
- 프로젝트 실행 방법을 설명하지 않는 README
- 삭제 대신 주석 처리된 코드
- 몇 주째 남아 있는 TODO 주석
- 중요한 아키텍처 선택이 많은 프로젝트에 ADR이 없음
- 의도를 설명하지 않고 코드를 그대로 되풀이하는 문서

## 검증

문서화한 뒤에는 다음을 확인하세요.

- [ ] 모든 중요한 아키텍처 결정에 대해 ADR이 존재함
- [ ] README가 빠른 시작, 명령어, 아키텍처 개요를 다룸
- [ ] API 함수에 매개변수와 반환 타입 문서가 있음
- [ ] 알려진 함정이 필요한 곳에 인라인으로 문서화되어 있음
- [ ] 주석 처리된 코드가 남아 있지 않음
- [ ] 규칙 파일(CLAUDE.md 등)이 최신이고 정확함
- [ ] 문장 수정으로 원본의 세부 사항, 결정의 트레이드오프, 한정어가 보존되었고 근거 없는 보장이 추가되지 않았음
