# 코드 리뷰와 품질

## 개요

품질 게이트를 갖춘 다차원 코드 리뷰입니다. 모든 변경은 병합 전에 리뷰를 거칩니다. 예외는 없습니다. 리뷰는 다섯 가지 축을 다룹니다: 정확성, 가독성, 아키텍처, 보안, 성능.

**승인 기준:** 완벽하지 않더라도 전체 코드 건강도를 확실히 개선하는 변경은 승인하십시오. 완벽한 코드는 존재하지 않습니다. 목표는 지속적인 개선입니다. 본인이라면 그렇게 작성하지 않았을 것이라는 이유로 변경을 막지 마십시오. 코드베이스를 개선하고 프로젝트의 관례를 따른다면 승인하십시오.

## 사용 시점

- PR이나 변경을 병합하기 전
- 기능 구현을 마친 후
- 다른 에이전트나 모델이 만든 코드를 평가해야 할 때
- 기존 코드를 리팩터링할 때
- 모든 버그 수정 후(수정 사항과 회귀 테스트를 모두 리뷰)

## 다섯 가지 축의 리뷰

모든 리뷰는 다음 차원에 걸쳐 코드를 평가합니다:

### 1. 정확성

코드는 자신이 하겠다고 주장하는 일을 하는가?

- 명세나 작업 요구사항과 일치하는가?
- 엣지 케이스(null, 빈 값, 경계값)가 처리되는가?
- 오류 경로가 처리되는가(정상 경로만이 아니라)?
- 모든 테스트를 통과하는가? 테스트가 실제로 올바른 것을 테스트하는가?
- off-by-one 오류, 레이스 컨디션, 상태 불일치가 있는가?

### 2. 가독성과 단순성

다른 엔지니어(또는 에이전트)가 작성자의 설명 없이 이 코드를 이해할 수 있는가?

- 이름이 설명적이며 프로젝트 관례와 일관적인가? (맥락 없이 `temp`, `data`, `result`를 쓰지 않음)
- 제어 흐름이 직관적인가(중첩된 삼항 연산자, 깊은 콜백을 피함)?
- 코드가 논리적으로 구성되어 있는가(관련 코드가 묶여 있고, 모듈 경계가 명확한가)?
- 단순화해야 할 "영리한" 기법이 있는가?
- **더 적은 줄로 할 수 있는가?** (100줄이면 충분한데 1000줄인 것은 실패입니다)
- **추상화가 복잡성만큼의 가치를 하는가?** (세 번째 사용 사례가 나오기 전까지는 일반화하지 마십시오)
- 주석이 명확하지 않은 의도를 설명하는 데 도움이 되는가? (하지만 자명한 코드에는 주석을 달지 마십시오)
- 죽은 코드 흔적이 있는가: 아무 일도 하지 않는 변수(`_unused`), 하위 호환성 shim, `// removed` 주석?
- **관련 없는 흐름에 새 조건문이 덧붙여졌는가?** 이는 사소한 지적이 아니라 설계 악취입니다. 기존 경로를 뒤엉키게 하는 대신 로직을 별도의 헬퍼, 상태, 또는 정책으로 분리하십시오.
- **같은 형태의 조건문이 반복되는가?** 이는 모델이나 디스패처가 빠져 있다는 신호입니다. "임시" 분기는 대개 영구적인 부채가 됩니다.

### 3. 아키텍처

변경이 시스템의 설계에 맞는가?

- 기존 패턴을 따르는가, 아니면 새 패턴을 도입하는가? 새 패턴이라면 정당화되는가?
- 깔끔한 모듈 경계를 유지하는가?
- 공유되어야 할 코드 중복이 있는가?
- 의존성이 올바른 방향으로 흐르는가(순환 의존성 없음)?
- 추상화 수준이 적절한가(과도한 설계도 아니고, 지나치게 결합되지도 않았는가)?
- **이 리팩터링이 복잡성을 줄이는가, 아니면 단지 위치만 옮기는가?** 변경을 따라가기 위해 독자가 머릿속에 유지해야 하는 개념의 수를 세어 보십시오. "더 깔끔한" 버전에서도 그 수가 그대로라면, 그것은 더 깔끔한 것이 아닙니다. 같은 로직을 다시 중앙에 모으기보다, 분기, 모드, 계층 전체를 사라지게 만드는 재구성을 선호하십시오. 추상화를 다듬기보다 삭제하는 것을 선호하십시오.
- **기능 특화 로직이 공유되거나 범용적인 모듈로 새고 있는가?** 로직은 소유하는 계층에 두고, 거의 중복된 코드 대신 기존의 표준 헬퍼를 재사용하십시오. 아키텍처 드리프트를 정상화하지 마십시오.
- **타입 경계가 명시적인가?** 불필요한 `any`/`unknown`/선택적 값/캐스트, 그리고 불명확한 불변식을 덮어 가리는 조용한 폴백에 의문을 제기하십시오. 경계를 명시적으로 만들면 주변 제어 흐름이 단순해지는 경우가 많습니다.

### 4. 보안

자세한 보안 지침은 `security-and-hardening`을 참조하십시오. 변경이 취약점을 도입하는가?

- 사용자 입력이 검증되고 정제되는가?
- 비밀 정보가 코드, 로그, 버전 관리에서 배제되는가?
- 필요한 곳에서 인증/인가가 확인되는가?
- SQL 쿼리가 파라미터화되어 있는가(문자열 연결 없음)?
- XSS를 방지하기 위해 출력이 인코딩되는가?
- 의존성이 신뢰할 수 있는 출처에서 왔고 알려진 취약점이 없는가?
- 외부 소스(API, 로그, 사용자 콘텐츠, 설정 파일)의 데이터가 신뢰할 수 없는 것으로 취급되는가?
- 외부 데이터 흐름이 로직이나 렌더링에 사용되기 전에 시스템 경계에서 검증되는가?

### 5. 성능

자세한 프로파일링과 최적화는 `performance-optimization`을 참조하십시오. 변경이 성능 문제를 일으키는가?

- N+1 쿼리 패턴이 있는가?
- 제한 없는 루프나 제약 없는 데이터 가져오기가 있는가?
- 비동기여야 할 동기 연산이 있는가?
- UI 컴포넌트에 불필요한 재렌더링이 있는가?
- 목록 엔드포인트에 페이지네이션이 빠져 있는가?
- 핫 패스에서 큰 객체를 생성하는가?

## 구조적 해결책

구조적 문제를 지적할 때는 문제만이 아니라 해결 방향을 제안하십시오. "이것은 복잡하다"라고만 말하는 리뷰는 작성자를 추측하게 만듭니다. 이름이 붙은 재구조화 기법을 제시하십시오:

- **조건문 연쇄를 교체**하여 타입이 지정된 모델이나 명시적인 디스패처를 사용하십시오.
- **중복된 분기를 통합**하여 하나의 더 명확한 흐름으로 만드십시오.
- **오케스트레이션과 비즈니스 로직을 분리**하여 각각을 독립적으로 읽을 수 있게 하십시오.
- **기능 특화 로직을 이동**하여 공유 모듈에서 개념을 소유하는 패키지로 옮기십시오.
- **표준 헬퍼를 재사용**하고, 맞춤형의 거의 중복된 코드를 만들지 마십시오.
- **타입 경계를 명시적으로 만들어** 하위의 분기가 사라지게 하십시오.
- **통과형 래퍼를 삭제**하십시오. API를 명확히 하지 않으면서 간접 참조만 추가합니다.
- **헬퍼를 추출**하거나 큰 파일을 집중된 모듈로 분할하십시오.

동일한 복잡성을 주변에 흩뿌리는 해결책보다, 움직이는 부품을 제거하는 해결책을 선호하십시오.

## 변경 크기 조절

작고 집중된 변경은 리뷰하기 쉽고, 더 빨리 병합되며, 배포하기에도 더 안전합니다. 다음 크기를 목표로 하십시오:

```
~100 lines changed   → Good. Reviewable in one sitting.
~300 lines changed   → Acceptable if it's a single logical change.
~1000 lines changed  → Too large. Split it.
```

**diff 크기만이 아니라 파일 크기도 확인하십시오.** 작은 diff도 파일을 건강한 경계 너머로 밀어낼 수 있습니다. 한 파일의 총 줄 수가 약 1000줄을 넘으면(위의 변경된 줄 1000줄 기준과는 별개로) 흔히 검토 신호로 간주되지만, 엄격한 상한은 아닙니다. 변경이 이미 큰 파일을 실질적으로 키운다면, 그 위에 더 쌓기 전에 먼저 헬퍼, 하위 컴포넌트, 또는 모듈로 추출할 수 있는지 물어보십시오. 분해한 다음, 추가하십시오.

**"하나의 변경"의 의미:** 하나의 사항을 다루고, 관련 테스트를 포함하며, 제출 후에도 시스템이 정상 동작을 유지하는, 자체적으로 완결된 단일 수정입니다. 기능 전체가 아니라 기능의 한 부분입니다.

**변경이 너무 클 때의 분할 전략:**

| 전략 | 방법 | 사용 시점 |
|----------|-----|------|
| **Stack** | 작은 변경을 제출하고, 그 위에 다음 변경을 시작 | 순차적 의존성이 있을 때 |
| **By file group** | 서로 다른 리뷰어가 필요한 그룹별로 변경을 분리 | 횡단 관심사 |
| **Horizontal** | 공유 코드/스텁을 먼저 만들고 그다음 소비자를 만듦 | 계층형 아키텍처 |
| **Vertical** | 기능을 더 작은 풀스택 조각으로 나눔 | 기능 작업 |

**큰 변경이 허용되는 경우:** 리뷰어가 모든 줄이 아니라 의도만 검증하면 되는 완전한 파일 삭제와 자동화된 리팩터링.

**리팩터링과 기능 작업을 분리하십시오.** 기존 코드를 리팩터링하면서 새 동작을 추가하는 변경은 두 개의 변경입니다. 따로 제출하십시오. 작은 정리 작업(변수 이름 변경)은 리뷰어의 재량에 따라 포함할 수 있습니다.

## 변경 설명

모든 변경에는 버전 관리 이력에서 단독으로 읽혀도 이해되는 설명이 필요합니다.

**첫 줄:** 짧고, 명령형이며, 독립적이어야 합니다. "Delete the FizzBuzz RPC"이지 "Deleting the FizzBuzz RPC"가 아닙니다. 이력을 검색하는 사람이 diff를 읽지 않고도 변경을 이해할 수 있을 만큼 정보가 충분해야 합니다.

**본문:** 무엇이 바뀌는지와 왜 바뀌는지. 코드 자체에서 보이지 않는 맥락, 결정, 근거를 포함하십시오. 관련이 있다면 버그 번호, 벤치마크 결과, 설계 문서에 링크하십시오. 접근 방식의 단점이 있다면 인정하십시오.

**안티패턴:** "Fix bug," "Fix build," "Add patch," "Moving code from A to B," "Phase 1," "Add convenience functions."

## 리뷰 과정

### 1단계: 맥락 이해

코드를 보기 전에 의도를 이해하십시오:

```
- What is this change trying to accomplish?
- What spec or task does it implement?
- What is the expected behavior change?
```

### 2단계: 테스트를 먼저 리뷰

테스트는 의도와 커버리지를 드러냅니다:

```
- Do tests exist for the change?
- Do they test behavior (not implementation details)?
- Are edge cases covered?
- Do tests have descriptive names?
- Would the tests catch a regression if the code changed?
```

마지막 질문은 읽는 것이 아니라 실험으로 답하십시오. 변경이 추가한 조건 하나를 반전시키고(부정을 제거하거나, `&&`를 `||`로 바꿈), 테스트 스위트를 실행한 뒤, 복사본에서 파일을 복원하십시오. 여전히 green인 변이(mutation)는 발견 사항입니다. 빠진 테스트 케이스를 명시하십시오. 프로젝트 전체의 변이 점수는 `constraint-driven-development`를 참조하십시오.

### 3단계: 구현 리뷰

다섯 가지 축을 염두에 두고 코드를 훑어보십시오:

```
For each file changed:
1. Correctness: Does this code do what the test says it should?
2. Readability: Can I understand this without help?
3. Architecture: Does this fit the system?
4. Security: Any vulnerabilities?
5. Performance: Any bottlenecks?
```

### 4단계: 발견 사항 분류

모든 코멘트에 심각도를 표시하여, 작성자가 무엇이 필수이고 무엇이 선택인지 알 수 있게 하십시오:

| 접두사 | 의미 | 작성자의 조치 |
|--------|---------|---------------|
| *(접두사 없음)* | 필수 변경 | 병합 전에 반드시 처리 |
| **Critical:** | 병합 차단 | 보안 취약점, 데이터 손실, 기능 고장 |
| **Nit:** | 사소함, 선택 사항 | 작성자가 무시해도 됨 — 포맷팅, 스타일 선호 |
| **Optional:** / **Consider:** | 제안 | 고려할 가치는 있지만 필수는 아님 |
| **FYI** | 정보 제공용 | 조치 불필요 — 향후 참고용 맥락 |

이는 작성자가 모든 피드백을 필수로 받아들여 선택적 제안에 시간을 낭비하는 것을 방지합니다.

**중요한 것부터 말하십시오.** 영향력이 큰 순서로 발견 사항을 정렬하십시오. 정확성과 보안이 먼저, 그다음 구조적 회귀와 놓친 단순화, 그 밖의 나머지 순입니다. 실제 문제를 사소한 nit 아래에 묻지 마십시오. 확신이 높은 몇 개의 코멘트가 긴 목록보다 낫습니다. 구조적 문제 하나와 nit 열 개가 있다면, 그 구조적 문제가 곧 리뷰입니다.

### 5단계: 검증의 검증

작성자의 검증 내용을 확인하십시오:

```
- What tests were run?
- Did the build pass?
- Was the change tested manually?
- Are there screenshots for UI changes?
- Is there a before/after comparison?
```

## 다중 모델 리뷰 패턴

서로 다른 리뷰 관점에 서로 다른 모델을 사용하십시오:

```
Model A writes the code
    │
    ▼
Model B reviews for correctness and architecture
    │
    ▼
Model A addresses the feedback
    │
    ▼
Human makes the final call
```

이는 단일 모델이 놓칠 수 있는 문제를 잡아냅니다. 서로 다른 모델은 서로 다른 맹점을 가지고 있기 때문입니다.

**리뷰 에이전트용 예시 프롬프트:**
```
Review this code change for correctness, security, and adherence to
our project conventions. The spec says [X]. The change should [Y].
Flag any issues as Critical, Required, Optional, or Nit.
```

## 죽은 코드 위생

리팩터링이나 구현 변경 후에는 고아가 된 코드를 확인하십시오:

1. 이제 도달할 수 없거나 사용되지 않는 코드를 식별하십시오
2. 명시적으로 목록을 작성하십시오
3. **삭제 전에 확인하십시오:** "이제 사용되지 않는 다음 요소들을 제거할까요: [list]?"

죽은 코드를 방치하지 마십시오. 미래의 독자와 에이전트를 혼란스럽게 합니다. 하지만 확실하지 않은 것을 조용히 삭제하지 마십시오. 의심스러우면 물어보십시오.

```
DEAD CODE IDENTIFIED:
- formatLegacyDate() in src/utils/date.ts — replaced by formatDate()
- OldTaskCard component in src/components/ — replaced by TaskCard
- LEGACY_API_URL constant in src/config.ts — no remaining references
→ Safe to remove these?
```

## 리뷰 속도

느린 리뷰는 팀 전체를 막습니다. 리뷰를 위해 문맥을 전환하는 비용은 다른 사람들에게 가해지는 대기 비용보다 작습니다.

- **영업일 기준 1일 이내에 응답하십시오** — 이것은 목표가 아니라 최대치입니다
- **이상적인 주기:** 깊이 집중한 코딩 중이 아니라면, 리뷰 요청이 도착한 직후에 응답하십시오. 일반적인 변경은 하루 안에 여러 차례의 리뷰 라운드를 마칠 수 있어야 합니다
- **최종 승인의 신속함보다 개별 응답의 신속함을 우선하십시오.** 여러 라운드가 필요하더라도 빠른 피드백은 좌절을 줄입니다
- **큰 변경:** 거대한 변경 세트를 리뷰하기보다 작성자에게 나누어 달라고 요청하십시오

## 의견 충돌 처리

리뷰 분쟁을 해결할 때는 다음 우선순위를 적용하십시오:

1. **기술적 사실과 데이터**가 의견과 선호를 이깁니다
2. **스타일 가이드**가 스타일 문제에 대한 절대적 권위입니다
3. **소프트웨어 설계**는 개인적 선호가 아니라 엔지니어링 원칙에 따라 평가해야 합니다
4. **코드베이스 일관성**은 전체 건강도를 떨어뜨리지 않는 한 허용됩니다

**"나중에 정리할게요"를 받아들이지 마십시오.** 경험상 미뤄진 정리는 거의 일어나지 않습니다. 진짜 긴급 상황이 아니라면 제출 전에 정리를 요구하십시오. 주변 문제를 이 변경에서 처리할 수 없다면, 본인에게 할당된 버그 리포트를 작성하도록 요구하십시오.

## 리뷰에서의 정직성

코드를 리뷰할 때 — 본인이 작성했든, 다른 에이전트가 작성했든, 사람이 작성했든:

- **대충 승인하지 마십시오.** 리뷰의 증거 없는 "LGTM"은 아무에게도 도움이 되지 않습니다.
- **실제 문제를 누그러뜨리지 마십시오.** 프로덕션에서 발생할 버그인데 "이것은 사소한 우려일 수 있습니다"라고 말하는 것은 부정직합니다.
- **가능하면 문제를 수치화하십시오.** "이 N+1 쿼리는 목록의 항목당 약 50ms를 추가합니다"가 "이것은 느릴 수 있습니다"보다 낫습니다.
- **명백한 문제가 있는 접근 방식에는 반론을 제기하십시오.** 아첨은 리뷰에서 실패 모드입니다. 구현에 문제가 있다면 직접 말하고 대안을 제안하십시오.
- **재정의를 우아하게 받아들이십시오.** 작성자가 전체 맥락을 알고 있고 동의하지 않는다면, 그의 판단을 따르십시오. 사람이 아니라 코드에 대해 코멘트하십시오. 개인에 대한 비판은 코드 자체에 초점을 맞추도록 바꾸어 표현하십시오.

## 의존성 규율

코드 리뷰의 일부는 의존성 리뷰입니다:

**어떤 의존성을 추가하기 전에:**
1. 기존 스택으로 이 문제를 해결할 수 있는가? (대개 가능합니다.)
2. 의존성이 얼마나 큰가? (번들 영향을 확인하십시오.)
3. 여전히 활발히 유지보수되는가? (마지막 커밋, 열린 이슈를 확인하십시오.)
4. 알려진 취약점이 있는가? (`npm audit`)
5. 라이선스는 무엇인가? (프로젝트와 호환되어야 합니다.)

**규칙:** 새 의존성보다 표준 라이브러리와 기존 유틸리티를 선호하십시오. 모든 의존성은 부담입니다.

**기존 의존성 업그레이드**도 다른 코드 변경과 마찬가지로 코드 변경이며, 가장 위험한 업그레이드는 "bump deps" 같은 메시지와 함께 일괄 병합된 것들입니다. 같은 원칙으로 리뷰하십시오:

1. **버전 번호가 아니라 changelog를 읽으십시오.** Semver는 메인테이너가 지키지 않았을 수도 있는 약속입니다. "패치"도 동작 변경을 담고 있을 수 있습니다. 메이저 버전 업은 마이그레이션 노트를 읽고 무엇이 깨지는지 찾으십시오.
2. **변경 하나당 의존성 하나.** 개별적으로(또는 작은 관련 그룹으로) 업그레이드하고 병합하십시오. 일괄 업데이트로 빌드가 깨지면 어떤 패키지가 원인인지 알 수 없게 됩니다. 단일 패키지 변경은 원인을 명확하게 하고 되돌리기를 깔끔하게 합니다.
3. **테스트가 판단하게 하십시오.** 업그레이드는 "설치가 되었다"가 아니라, 업그레이드 전과 후에 모두 스위트가 green인지로 검증합니다. 해당 의존성의 동작을 둘러싼 커버리지가 얇다면, 그 공백이 진짜 발견 사항입니다. 먼저 테스트를 추가하십시오.
4. **전이적 그래프를 고려하십시오.** 설치된 패키지 대부분은 아무도 직접 선택하지 않은 것들입니다. `package.json`만이 아니라 lockfile diff를 리뷰하십시오. 직접 의존성 하나를 올리면 간접 의존성 수십 개가 함께 바뀔 수 있습니다.
5. **lockfile을 정직하게 유지하십시오.** 커밋하고, 그 diff를 리뷰하고, 절대 손으로 편집하지 마십시오. lockfile이 실제로 배포되는 것을 고정합니다.

`npm audit` 결과와 공급망 위험(typosquatting, 침해된 메인테이너)의 분류는 `security-and-hardening` 스킬을 따르십시오. 이 섹션은 업그레이드 *워크플로*를 다루고, 그 스킬은 보안 판정을 다룹니다.

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "It works, that's good enough" | 작동하지만 읽기 어렵거나, 안전하지 않거나, 아키텍처상 잘못된 코드는 복리로 쌓이는 부채를 만듭니다. |
| "I wrote it, so I know it's correct" | 작성자는 자신의 가정에 눈이 멉니다. 모든 변경은 다른 사람의 눈을 거칠 가치가 있습니다. |
| "We'll clean it up later" | 나중은 오지 않습니다. 리뷰가 품질 게이트입니다. 사용하십시오. 병합 후가 아니라 병합 전에 정리를 요구하십시오. |
| "AI-generated code is probably fine" | AI 코드는 덜이 아니라 더 면밀한 검토가 필요합니다. 틀렸을 때도 자신만만하고 그럴듯합니다. |
| "The tests pass, so it's good" | 테스트는 필요하지만 충분하지 않습니다. 아키텍처 문제, 보안 문제, 가독성 문제는 잡아내지 못합니다. |
| "The refactor makes it cleaner" | 복잡성의 위치를 옮기는 것은 줄이는 것이 아닙니다. 독자가 여전히 같은 수의 개념을 붙들고 있다면 구조가 나아진 것이 아닙니다. 분기가 사라지는 버전을 찾으십시오. |
| "It's only a small addition to this file" | 작은 diff도 파일을 건강한 크기 너머로 밀어내고, 관련 없는 흐름에 분기를 덧붙입니다. diff 크기가 아니라 결과적인 구조를 판단하십시오. |
| "It's just a version bump" | 버전 업은 여러분이 작성하지 않은 동작 변경입니다. changelog를 읽으십시오. semver는 깨짐이 없음을 보장하지 않습니다. |
| "I'll upgrade everything in one PR to save time" | 일괄 업그레이드로 빌드가 깨지면 어떤 패키지가 원인인지 숨겨집니다. 변경 하나당 의존성 하나가 원인과 되돌리기를 명확하게 유지합니다. |

## 위험 신호

- 아무 리뷰 없이 PR이 병합됨
- 테스트 통과 여부만 확인하고 다른 축은 무시하는 리뷰
- 실제 리뷰의 증거 없는 "LGTM"
- 보안에 민감한 변경인데 보안 중심 리뷰가 없음
- "너무 커서 제대로 리뷰할 수 없는" 대형 PR(나누어야 함)
- 버그 수정 PR에 회귀 테스트가 없음
- 심각도 표시가 없는 리뷰 코멘트 — 무엇이 필수이고 무엇이 선택인지 불명확함
- "나중에 고치겠다"는 말을 받아들임 — 그런 일은 일어나지 않음
- 독자가 머릿속에 유지해야 하는 개념의 수를 줄이지 않고 코드를 옮기기만 하는 리팩터링
- 이미 큰 파일을 분해하지 않고 더 키우는 변경
- 관련 없는 코드 경로에 흩뿌려진 새 조건문(빠진 추상화)
- 기존의 표준 헬퍼와 중복되는 맞춤형 헬퍼, 또는 공유 모듈에 놓인 기능 로직
- changelog 리뷰도 패키지별 격리도 없는 일괄 "bump dependencies" PR
- 손으로 편집되었거나, 커밋되지 않았거나, diff를 리뷰하지 않고 병합된 lockfile 변경

## 검증

리뷰를 마친 후:

- [ ] 모든 Critical 문제가 해결됨
- [ ] 모든 Required(접두사 없음) 변경이 해결되었거나 정당한 사유와 함께 명시적으로 연기됨
- [ ] 테스트 통과
- [ ] 빌드 성공
- [ ] 검증 내용이 문서화됨(무엇이 바뀌었고 어떻게 검증했는지)
- [ ] 의존성 업그레이드가 changelog 기준으로 리뷰되었고, 패키지별로 격리되었으며, lockfile diff를 리뷰한 상태에서 green 스위트로 검증됨

**추정 차단 사항:** 각각에 대해 더 단순한 설계를 드러내고 제안하십시오. 변경이 실제로 구조를 더 나쁘게 만들 때만 Required로 격상하십시오: 복잡성을 줄이지 않고 옮기는 리팩터링, 분해 없이 파일을 크기 경계 너머로 밀어내는 변경, 공유 모듈에 추가된 기능 로직, 기존 표준 헬퍼와 거의 중복되는 코드, 불명확한 불변식을 숨기는 조용한 폴백.
