# 출시 및 런칭

## 개요

자신감을 갖고 출시하세요. 목표는 단순히 배포하는 것이 아니라, 안전하게 배포하고, 모니터링을 갖추고, 롤백 계획을 준비하고, 무엇을 성공으로 볼지 명확히 이해하는 것입니다. 모든 출시는 되돌릴 수 있고, 관찰할 수 있으며, 점진적이어야 합니다.

## 사용 시점

- 기능을 처음으로 프로덕션에 배포할 때
- 사용자에게 중요한 변경을 릴리스할 때
- 데이터 또는 인프라를 마이그레이션할 때
- 베타 또는 얼리 액세스 프로그램을 열 때
- 위험이 따르는 모든 배포 (사실상 모든 배포)

## 출시 전 체크리스트

### 코드 품질

- [ ] 모든 테스트 통과 (단위, 통합, e2e)
- [ ] 경고 없이 빌드 성공
- [ ] 린트 및 타입 검사 통과
- [ ] 코드 리뷰 완료 및 승인
- [ ] 출시 전에 해결해야 할 TODO 주석 없음
- [ ] 프로덕션 코드에 `console.log` 디버깅 구문 없음
- [ ] 예상되는 실패 모드에 대한 오류 처리 포함

### 보안

- [ ] 코드나 버전 관리에 시크릿 없음
- [ ] 생태계의 의존성 감사(`npm audit`, `pip-audit`, `cargo audit`, ...)에서 critical 또는 high 취약점 없음
- [ ] 사용자 대상 엔드포인트 전반에 입력 검증 적용
- [ ] 인증 및 인가 검사 적용
- [ ] 보안 헤더 설정 (CSP, HSTS 등)
- [ ] 인증 엔드포인트에 레이트 리미팅 적용
- [ ] CORS가 와일드카드가 아닌 특정 origin으로 설정됨

### 성능

- [ ] Core Web Vitals가 "Good" 기준치 이내
- [ ] 핵심 경로에 N+1 쿼리 없음
- [ ] 이미지 최적화 (압축, 반응형 크기, 지연 로딩)
- [ ] 번들 크기가 예산 이내
- [ ] 데이터베이스 쿼리에 적절한 인덱스 존재
- [ ] 정적 에셋과 반복 쿼리에 캐싱 설정

### 접근성

- [ ] 모든 인터랙티브 요소에서 키보드 탐색 동작
- [ ] 스크린 리더가 페이지 콘텐츠와 구조를 전달할 수 있음
- [ ] 색상 대비가 WCAG 2.1 AA 충족 (텍스트 4.5:1)
- [ ] 모달 및 동적 콘텐츠의 포커스 관리가 올바름
- [ ] 오류 메시지가 구체적이며 폼 필드와 연결됨
- [ ] axe-core 또는 Lighthouse에서 접근성 경고 없음

### 인프라

- [ ] 프로덕션에 환경 변수 설정됨
- [ ] 데이터베이스 마이그레이션 적용됨 (또는 적용 준비됨)
- [ ] DNS 및 SSL 설정됨
- [ ] 정적 에셋용 CDN 설정됨
- [ ] 로깅 및 오류 보고 설정됨
- [ ] 상태 확인(health check) 엔드포인트가 존재하고 응답함

### 문서

- [ ] 새로운 설정 요구사항이 있다면 README 업데이트됨
- [ ] API 문서가 최신 상태임
- [ ] 아키텍처 결정에 대한 ADR 작성됨
- [ ] 변경 로그(Changelog) 업데이트됨
- [ ] 사용자 대상 문서 업데이트됨 (해당되는 경우)

## 기능 플래그 전략

배포와 릴리스를 분리하기 위해 기능 플래그 뒤에서 출시하세요:

```typescript
// 기능 플래그 확인
const flags = await getFeatureFlags(userId);

if (flags.taskSharing) {
  // 신규 기능: 작업 공유
  return <TaskSharingPanel task={task} />;
}

// 기본값: 기존 동작
return null;
```

**기능 플래그 수명 주기:**

```
1. 플래그 OFF 상태로 배포     → 코드는 프로덕션에 있지만 비활성 상태
2. 팀/베타 대상 활성화        → 프로덕션 환경에서 내부 테스트
3. 점진적 롤아웃              → 사용자의 5% → 25% → 50% → 100%
4. 각 단계마다 모니터링       → 오류율, 성능, 사용자 피드백 관찰
5. 정리                       → 전체 롤아웃 후 플래그와 죽은 코드 경로 제거
```

**규칙:**
- 모든 기능 플래그에는 담당자와 만료일이 있어야 합니다
- 전체 롤아웃 후 2주 이내에 플래그를 정리하세요
- 기능 플래그를 중첩하지 마세요 (조합이 기하급수적으로 늘어납니다)
- CI에서 플래그 양쪽 상태 (on과 off) 모두 테스트하세요

## 단계적 롤아웃

### 롤아웃 순서

```
1. 스테이징에 배포
   └── 스테이징 환경에서 전체 테스트 스위트 실행
   └── 핵심 흐름 수동 스모크 테스트

2. 프로덕션에 배포 (기능 플래그 OFF)
   └── 배포 성공 확인 (상태 확인)
   └── 오류 모니터링 확인 (새로운 오류 없음)

3. 팀 대상 활성화 (내부 사용자에게 플래그 ON)
   └── 팀이 프로덕션에서 기능 사용
   └── 24시간 모니터링 기간

4. 카나리 롤아웃 (사용자의 5%에게 플래그 ON)
   └── 오류율, 지연 시간, 사용자 행동 모니터링
   └── 지표 비교: 카나리 vs. 기준선
   └── 24~48시간 모니터링 기간
   └── 모든 임계값을 통과한 경우에만 진행 (아래 표 참고)

5. 점진적 증가 (25% -> 50% -> 100%)
   └── 각 단계마다 동일한 모니터링
   └── 어느 시점에서든 이전 비율로 롤백할 수 있어야 함

6. 전체 롤아웃 (모든 사용자에게 플래그 ON)
   └── 1주일간 모니터링
   └── 기능 플래그 정리
```

### 롤아웃 결정 임계값

각 단계에서 진행, 보류, 또는 롤백을 결정할 때 다음 임계값을 사용하세요:

| 지표 | 진행 (녹색) | 보류 및 조사 (노란색) | 롤백 (빨간색) |
|--------|-----------------|-------------------------------|-----------------|
| 오류율 | 기준선 대비 10% 이내 | 기준선 대비 10-100% 높음 | 기준선의 2배 초과 |
| P95 지연 시간 | 기준선 대비 20% 이내 | 기준선 대비 20-50% 높음 | 기준선 대비 50% 초과 높음 |
| 클라이언트 JS 오류 | 새로운 오류 유형 없음 | 세션의 0.1% 미만에서 새로운 오류 | 세션의 0.1% 초과에서 새로운 오류 |
| 비즈니스 지표 | 중립 또는 긍정적 | 5% 미만 하락 (노이즈일 수 있음) | 5% 초과 하락 |

### 롤백해야 할 때

다음 중 하나라도 해당하면 즉시 롤백하세요:
- 오류율이 기준선의 2배 이상 증가
- P95 지연 시간이 50% 이상 증가
- 사용자 보고 이슈가 급증
- 데이터 무결성 문제 발견
- 보안 취약점 발견

## 모니터링 및 관찰 가능성

### 모니터링 대상

```
애플리케이션 지표:
├── 오류율 (전체 및 엔드포인트별)
├── 응답 시간 (p50, p95, p99)
├── 요청량
├── 활성 사용자
└── 핵심 비즈니스 지표 (전환, 참여)

인프라 지표:
├── CPU 및 메모리 사용률
├── 데이터베이스 커넥션 풀 사용량
├── 디스크 공간
├── 네트워크 지연 시간
└── 큐 깊이 (해당되는 경우)

클라이언트 지표:
├── Core Web Vitals (LCP, INP, CLS)
├── JavaScript 오류
├── 클라이언트 관점의 API 오류율
└── 페이지 로드 시간
```

### 오류 보고

```typescript
// 보고 기능이 포함된 에러 바운더리 설정
class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    // 오류 추적 서비스로 보고
    reportError(error, {
      componentStack: info.componentStack,
      userId: getCurrentUser()?.id,
      page: window.location.pathname,
    });
  }

  render() {
    if (this.state.hasError) {
      return <ErrorFallback onRetry={() => this.setState({ hasError: false })} />;
    }
    return this.props.children;
  }
}

// 서버 측 오류 보고
app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  reportError(err, {
    method: req.method,
    url: req.url,
    userId: req.user?.id,
  });

  // 내부 정보를 사용자에게 노출하지 않음
  res.status(500).json({
    error: { code: 'INTERNAL_ERROR', message: 'Something went wrong' },
  });
});
```

### 출시 후 검증

출시 후 첫 1시간 동안:

```
1. 상태 확인 엔드포인트가 200을 반환하는지 확인
2. 오류 모니터링 대시보드 확인 (새로운 오류 유형 없음)
3. 지연 시간 대시보드 확인 (회귀 없음)
4. 핵심 사용자 흐름을 수동으로 테스트
5. 로그가 정상적으로 흐르고 읽을 수 있는지 확인
6. 롤백 메커니즘이 동작하는지 확인 (가능하면 드라이 런)
```

## 오류 예산 릴리스 게이트

서비스의 오류 예산(SLO가 실패를 허용하는 요청 또는 시간의 비율)은 출시가 안전한지를 결정합니다. 이를 협상이 아닌 객관적인 게이트로 사용하세요:

```
남은 예산 > 20%  →  정상 출시; 면밀히 모니터링
남은 예산 0–20%  →  롤아웃 속도만 낮추기; 고위험 변경 금지
예산 소진        →  기능 작업 동결; 전적으로 안정성에 집중
예산 회복        →  정상 속도 재개; 예산을 회복시킨 수정을 반영
```

카나리 중 높은 소진율(기준선 속도보다 빠르게 예산을 소비하는 경우)은 위 롤아웃 임계값 표에서 **보류** 신호입니다. 개별 오류율이 상승한 경우와 동일하게 취급하세요.

## 롤백 전략

모든 배포에는 배포 전에 롤백 계획이 있어야 합니다:

```markdown
## [기능/릴리스] 롤백 계획

### 트리거 조건
- 오류율 > 기준선의 2배
- P95 지연 시간 > [X]ms
- [구체적인 이슈]에 대한 사용자 보고

### 롤백 단계
1. 기능 플래그 비활성화 (해당되는 경우)
   또는
1. 이전 버전 배포: `git revert <commit> && git push`
2. 롤백 검증: 상태 확인, 오류 모니터링
3. 공유: 팀에 롤백 사실 알림

### 데이터베이스 고려사항
- 마이그레이션 [X]에는 롤백이 있음: <검증된 명령어 또는 런북 링크>
- 신규 기능이 삽입한 데이터: [보존 / 정리]

### 롤백 소요 시간
- 기능 플래그: 1분 미만
- 이전 버전 재배포: 5분 미만
- 데이터베이스 롤백: 15분 미만
```

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "스테이징에서 동작하니 프로덕션에서도 동작할 거야" | 프로덕션에는 다른 데이터, 트래픽 패턴, 엣지 케이스가 있습니다. 배포 후 모니터링하세요. |
| "이 기능에는 기능 플래그가 필요 없어" | 모든 기능에는 킬 스위치가 도움이 됩니다. "단순한" 변경도 무언가를 망가뜨릴 수 있습니다. |
| "모니터링은 오버헤드야" | 모니터링이 없으면 대시보드가 아니라 사용자 불만으로 문제를 알게 됩니다. |
| "모니터링은 나중에 추가하자" | 출시 전에 추가하세요. 보이지 않는 것은 디버그할 수 없습니다. |
| "롤백은 실패를 인정하는 거야" | 롤백은 책임 있는 엔지니어링입니다. 망가진 기능을 출시하는 것이 실패입니다. |
| "오류율이 괜찮아 보이니 계속 출시하자" | 현재 오류율만이 아니라 소진율을 확인하세요. 개별 임계값이 녹색이어도 기준선보다 빠르게 예산을 소비하는 것은 보류 신호입니다. |

## 위험 신호

- 롤백 계획 없이 배포하는 경우
- 프로덕션에 모니터링이나 오류 보고가 없는 경우
- 빅뱅 릴리스 (스테이징 없이 모든 것을 한 번에)
- 만료일이나 담당자가 없는 기능 플래그
- 배포 후 첫 1시간 동안 아무도 모니터링하지 않는 경우
- 프로덕션 환경 설정을 코드가 아니라 기억에 의존해 수행하는 경우
- "금요일 오후인데 그냥 출시하자"
- 오류 예산이 소진되었는데도 기능 작업이 그대로 계속되는 경우
