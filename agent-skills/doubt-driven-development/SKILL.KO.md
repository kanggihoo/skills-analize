# 의심 기반 개발

## 개요

확신에 찬 답이 곧 올바른 답은 아닙니다. 긴 세션은 맥락을 쌓으면서, 누구도 눈치채지 못하는 사이에 가정을 "사실"로 둔갑시킵니다. 의심 기반 개발은 사소하지 않은 결과물이 확정되기 전에, 승인이 아니라 **반증**을 목표로 하는 새 컨텍스트의 리뷰어를 세우는 규율입니다.

이것은 `/review`가 아닙니다. `/review`는 완성된 산출물에 대한 판정입니다. 이것은 진행 중에 적용하는 태도입니다. 사소하지 않은 결정을, 방향을 바꾸는 비용이 아직 낮을 때 교차 검증합니다.

## 사용 시점

결정이 **사소하지 않은** 경우는 다음 중 하나 이상이 참일 때입니다.

- 분기 로직을 도입하거나 수정함
- 모듈이나 서비스 경계를 넘어감
- 타입 시스템이나 컴파일러가 검증할 수 없는 속성을 주장함(스레드 안전성, 멱등성, 순서, 불변식)
- 정확성이 나중에 읽는 사람에게 보이지 않는 컨텍스트에 달려 있음
- 영향 범위가 되돌릴 수 없음(프로덕션 배포, 데이터 마이그레이션, 공개 API 변경)

다음 경우에 이 스킬을 적용하세요.

- 불확실한 상황에서 아키텍처 결정을 내리려 할 때
- 사소하지 않은 코드를 커밋하려 할 때
- 자명하지 않은 사실을 주장하려 할 때("이건 안전하다", "이건 확장된다", "이건 명세와 일치한다")
- 완전히 이해하지 못한 코드에서 작업할 때

**사용하지 않을 때:**

- 기계적인 작업(이름 변경, 포매팅, 파일 이동)
- 명확하고 모호하지 않은 사용자 지시를 따를 때
- 기존 코드를 읽거나 요약할 때
- 정확성이 자명한 한 줄짜리 변경
- 순수 도구 작업(테스트 실행, 파일 목록 조회)
- 사용자가 검증보다 속도를 명시적으로 원할 때

모든 키 입력마다 의심하면 아무것도 출시하지 못합니다. 이 스킬은 위에서 정의한 사소하지 않은 결정에만 적용합니다.

## 로딩 제약

이 스킬은 **메인 세션 오케스트레이터**를 위해 설계되었습니다. 그곳에서 Step 3(DOUBT, 아래에서 자세히 설명)이 새 컨텍스트의 리뷰어를 띄울 수 있습니다.

- **이 스킬을 페르소나의 `skills:` frontmatter에 추가하지 마세요.** Step 3을 따르는 페르소나는 또 다른 페르소나를 띄우게 되는데, 이는 `../../references/orchestration-patterns.md`가 명시적으로 금지하는 오케스트레이션 안티패턴입니다("페르소나는 다른 페르소나를 호출하지 않는다").
- **서브에이전트 컨텍스트 안에서 이 스킬을 적용하고 있음을 발견하면**(Claude Code가 중첩된 서브에이전트 생성을 막는 곳): 의심 기반 리뷰는 중첩 실행이 불가능하다고 사용자에게 알리고, 메인 세션이 처리하도록 하는 것이 권장 경로입니다. 최후의 수단으로만 열등한 자가 질문 대체 방법이 있습니다. ARTIFACT와 CONTRACT를 이전 추론과 분명히 구분되는 새 자기 프롬프트로 다시 쓰고, Step 1~5를 거치는 방식입니다. 이것은 **새 컨텍스트 리뷰가 아닙니다**(여러분은 자신의 컨텍스트를 그대로 가지고 있음). 따라서 결과를 degraded로 표시하고, 사용자에게 연락이 가능하다면 항상 에스컬레이션을 우선하세요.

## 진행 과정

이 스킬을 적용할 때 다음 체크리스트를 복사해서 사용하세요.

```
Doubt cycle:
- [ ] Step 1: CLAIM — 주장과 중요한 이유를 작성함
- [ ] Step 2: EXTRACT — 산출물과 계약을 분리하고 추론을 제거함
- [ ] Step 3: DOUBT — 적대적 프롬프트로 새 컨텍스트 리뷰어를 호출함
- [ ] Step 4: RECONCILE — 모든 발견 사항을 산출물 텍스트와 대조해 분류함
- [ ] Step 5: STOP — 중단 조건을 충족함(사소한 발견 사항, 3사이클, 또는 사용자 재정의)
```

### Step 1: CLAIM — 무엇이 유지되는지 드러내기

결정을 두세 줄로 명명하세요.

```
CLAIM: "새 캐싱 레이어는 명세에 기술된 읽기 중심 워크로드에서
        스레드 안전하다."
WHY THIS MATTERS: 여기서 레이스 컨디션이 발생하면 사용자 데이터가 손상되고,
                  QA에서 찾아내기 어렵다.
```

이 주장을 이렇게 간결하게 쓸 수 없다면, 그것은 결정이 아니라 막연한 느낌입니다. 검토하기 전에 먼저 드러내세요.

### Step 2: EXTRACT — 가장 작은 검토 단위

새 컨텍스트의 리뷰어에게 필요한 것은 **산출물**과 **계약**이지, 작업 과정이 아닙니다.

- 코드: 파일 전체가 아니라 diff 또는 함수
- 결정: 제안을 3~5문장으로 정리한 것과 그 제안이 만족해야 하는 제약
- 주장: 주장과 그 주장을 뒷받침한다고 여겨지는 근거(Step 1의 CLAIM 블록과 구분해서 유지함. CLAIM 블록은 오케스트레이터의 가설로, 검토 대상입니다)

추론은 제거하세요. 결론을 넘기면 결론에 대한 확인만 돌아옵니다. 리뷰어가 한 번 읽고 머릿속에 담을 수 있을 만큼 단위를 작게 유지해야 합니다. 500줄짜리 PR이라면 먼저 분해하세요.

### Step 3: DOUBT — 새 컨텍스트의 리뷰어 호출

리뷰어 프롬프트는 **반드시 적대적**이어야 합니다. 프레이밍이 답을 결정합니다.

```
적대적 리뷰. 이 산출물에서 잘못된 점을 찾으세요.
작성자가 과신하고 있다고 가정하세요. 다음을 찾으세요.
- 명시되지 않은 가정
- 처리되지 않은 엣지 케이스
- 숨은 결합이나 공유 상태
- 계약이 위반될 수 있는 경우
- 이것이 깨뜨릴 수 있는 기존 관례
- 예상치 못한 입력에서의 실패 모드

검증하지 마세요. 요약하지 마세요. 문제를 찾거나,
철저히 검토한 뒤 아무것도 찾을 수 없다고 명시적으로 밝히세요.

ARTIFACT: <산출물 붙여넣기>
CONTRACT: <계약 붙여넣기>
```

**ARTIFACT와 CONTRACT만 전달하세요. CLAIM은 전달하지 마세요.** 리뷰어에게 결론을 건네면 동의하는 쪽으로 편향됩니다. 리뷰어는 산출물이 계약을 만족하는지 독립적으로 판단해야 합니다.

Claude Code에서는 `agents/`의 역할 기반 리뷰어가 설계상 격리된 컨텍스트로 시작하므로, 여기에서 사용할 수 있습니다. 목록과 도메인별 매칭은 `agents/`를 참조하세요.

**위의 적대적 프롬프트는 페르소나의 기본 응답 형식보다 우선합니다.** `code-reviewer` 같은 페르소나는 강점과 약점을 모두 담은 균형 잡힌 판정을 내도록 작성되어 있습니다. 하지만 의심 기반 리뷰는 문제만 담은 출력이 필요합니다. 적대적 프롬프트를 호출에 그대로 붙여넣어서 페르소나의 기본 형식을 덮어쓰세요. 페르소나의 응답 형식을 깔끔하게 덮어쓸 수 없다면, 적대적 프롬프트를 가진 일반 서브에이전트로 대체하세요.

#### 교차 모델 에스컬레이션

단일 모델 리뷰어는 원래 작성자와 맹점을 공유합니다. 다른 아키텍처를 가진 차분한 모델이 이런 맹점을 잡아냅니다. 의심 기반 리뷰는 이미 사소하지 않은 결정에 한해 선택적으로 사용하므로, 그 범위 안에서 교차 모델을 제안하는 것은 선택 사항이 아니라 이 스킬의 가치에 포함됩니다.

**대화형 세션에서는 항상 제안하세요. 말없이 건너뛰지 마세요.**

**Step 1: 사용자에게 묻기**

Step 3의 단일 모델 리뷰가 끝난 뒤, RECONCILE 전에 멈추고 다음과 같이 물어보세요.

> *"단일 모델 리뷰가 완료되었습니다. 교차 모델 2차 의견을 원하시나요? 옵션: Gemini CLI, Codex CLI, 수동 외부 리뷰(다른 곳에 붙여넣기), 또는 건너뛰기."*

이 질문은 모든 대화형 의심 사이클에서 필수입니다. 저비용 산출물처럼 보이더라도 마찬가지입니다. 비용이 값어치가 있는지는 에이전트가 아니라 사용자가 결정합니다. 에이전트의 역할은 그 선택지를 드러내는 것입니다.

**Step 2: 사용자가 CLI를 고른 경우 — 검증한 뒤 호출**

1. 도구가 PATH에 있는지 확인하세요(`which gemini`, `which codex`).
2. 전체 프롬프트를 넘기기 전에 실제로 동작하는지 테스트하세요(`gemini --version` 또는 이에 준하는 명령). 오래되었거나 깨진 바이너리는 `which`는 통과해도 실제 입력에서 실패할 수 있습니다.
3. 필수 플래그, 인증, 환경 변수(예: API 키)를 포함해 정확한 호출 방식을 사용자와 확인하세요. 구현은 제각각이므로 추측하지 마세요.
4. ARTIFACT + CONTRACT + 적대적 프롬프트**만** 전달하세요. 세션 컨텍스트나 CLAIM은 넣지 마세요.
5. 셸 이스케이프에 주의하세요. 산출물에 따옴표, `$(...)`, 백틱이 들어 있다면 인라인 `-p "…"` 대신 stdin(`echo … | gemini`)이나 heredoc을 사용하세요. 확신이 없다면 실행 전에 사용자에게 호출 방식을 확인받으세요.
6. 결과를 Step 4(RECONCILE)로 가져가세요.

**산출물을 셸 인용 인자에 보간하지 마세요.** 코드, 마크다운, 리뷰 프롬프트에는 백틱, `$(...)`, 따옴표 문자가 흔히 들어 있어서, 프롬프트가 잘리거나 내장된 셸이 실행될 수 있습니다. 전체 프롬프트를 파일에 쓰고 stdin으로 파이프하세요.

예시 형태입니다(플래그는 설치된 도구에 맞춰 확인하세요. 구현과 버전마다 문법이 다릅니다).

```bash
# 먼저 적대적 프롬프트 + ARTIFACT + CONTRACT를 임시 파일에 씁니다.
# 그다음 stdin으로 파이프해서 산출물 안의 셸 메타문자가 무해하게 남도록 합니다.

# Codex (읽기 전용 샌드박스는 CLI가 작업 공간에 쓰지 못하게 막음):
codex exec --sandbox read-only -C <repo-path> - < /tmp/doubt-prompt.md

# Gemini ('--approval-mode plan'은 읽기 전용임. '-p ""'는 비대화형 모드를 켜고
# 프롬프트를 stdin에서 읽게 함):
gemini --approval-mode plan -p "" < /tmp/doubt-prompt.md
```

읽기 전용 샌드박스는 핵심적인 세부 사항입니다. 의심 대상 산출물에는 (의도적이든 우연이든) 프롬프트 인젝션 지시가 들어 있을 수 있는데, 이것을 교차 모델 CLI가 그대로 실행하면 작업 공간에 영향을 줄 수 있습니다.

**Step 3: CLI를 사용할 수 없거나 실패한 경우**

실패를 명시적으로 드러내세요. 직접 실행하기, 다른 도구 시도하기, 또는 건너뛰기를 제안하세요. 교차 모델이 실행되지 않았다는 사실을 사용자가 알아야 하므로, 말없이 단일 모델로 되돌아가지 마세요.

**Step 4: 사용자가 건너뛴 경우**

출력에 건너뛰었다는 사실을 밝히고(*"단일 모델 발견 사항만으로 진행합니다"*), RECONCILE로 계속 진행하세요. 건너뛰는 것은 괜찮지만, 말없이 건너뛰는 것은 괜찮지 않습니다.

**비대화형 컨텍스트**(CI, `/loop`, 자율 루프, 예약 실행):

- 교차 모델은 **건너뛰며**, 그 건너뜀을 출력에 **반드시 알려야** 합니다. *"교차 모델 건너뜀: 비대화형 컨텍스트."*
- 사용자의 명시적 허가 없이 외부 CLI를 **절대** 호출하지 마세요. 이것은 핵심적인 안전 속성입니다.

교차 모델은 비용, 지연 시간, 도구의 취약성을 더합니다. 에이전트는 매 사이클마다 선택지를 드러내고, 이 산출물에 그만한 가치가 있는지는 사용자가 결정합니다.

### Step 4: RECONCILE — 발견 사항을 다시 반영하기

리뷰어의 출력은 판정이 아니라 데이터입니다. **여러분은 여전히 오케스트레이터입니다.** 분류하기 전에 산출물 텍스트를 각 발견 사항에 대조해 다시 읽으세요. 리뷰어의 결과를 무비판적으로 승인하는 것은, 그것을 무시하는 것과 같은 실패 모드입니다.

각 발견 사항을 다음 **우선순위 순서**로 분류하세요(처음 맞는 분류가 채택됩니다).

1. **계약 오독** — 리뷰어가 여러분이 제공한 CONTRACT가 불명확하거나 불완전해서 지적한 경우. 먼저 계약을 고치고, 다음 사이클에서 다시 분류하세요.
2. **타당함 + 실행 가능** — 산출물의 변경이 필요한 실제 문제. 변경하고 다시 루프를 도세요.
3. **타당한 트레이드오프** — 문제는 실제이지만 고치는 비용이 수용하는 비용보다 큰 경우. 사용자가 볼 수 있도록 트레이드오프를 명시적으로 문서화하세요.
4. **노이즈** — 리뷰어가 지적했지만, 리뷰어가 가지고 있지 않았던 맥락에서는 실제로 올바른 경우. 메모해 두고 넘어가되, 그 맥락을 계약에 추가했다면 잘못된 지적을 막을 수 있었을지 자문하세요.

새 리뷰어도 맥락이 부족해서 틀릴 수 있습니다. "새로운 리뷰어니까" 판단을 미루지 마세요.

### Step 5: STOP — 경계가 있는 루프, 재귀가 아님

다음 중 하나에 해당하면 멈추세요.

- 다음 반복에서 사소하거나 이미 검토된 발견 사항만 나옴, **또는**
- 3사이클을 완료함(사용자에게 에스컬레이션하고, 네 번째 사이클을 혼자 반복하지 마세요), **또는**
- 사용자가 명시적으로 "ship it"이라고 말함

3사이클 후에도 리뷰어가 실질적인 문제를 계속 지적한다면, 산출물이 아직 준비되지 않았을 수 있습니다. 이를 사용자에게 알리세요. 해결되지 않은 세 사이클은 산출물에 대한 정보이지, 계속 반복할 이유가 아닙니다.

산출물이 커서 3사이클로는 "명백히 부족"하다면, 산출물이 너무 큰 것입니다. Step 2로 돌아가 분해하세요. 경계를 늘리지 마세요.

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "확신하니까 의심 단계는 건너뛸게요" | 새로운 문제에서 확신과 정확성은 잘 맞지 않습니다. 확신이 드는 순간이야말로 맹점이 숨어 있는 때입니다. |
| "리뷰어를 띄우는 건 비용이 많이 들어요" | 잘못된 커밋을 프로덕션에서 디버깅하는 것이 더 비쌉니다. 검사는 경계가 있지만, 버그는 경계가 없습니다. |
| "리뷰어는 그냥 트집만 잡을 거예요" | 범위를 제한하지 않았을 때만 그렇습니다. 프롬프트를 "계약 아래에서 실패하게 만들 문제"로 한정하세요. |
| "마지막에 `/review`로 의심하면 돼요" | `/review`는 최종 관문입니다. 의심 기반 개발은 방향 전환 비용이 낮을 때 잘못된 방향을 일찍 잡아냅니다. PR 단계에서는 이미 늦습니다. |
| "모든 단계를 의심하면 아무것도 출시 못 해요" | 이 스킬은 모든 키 입력이 아니라 사소하지 않은 결정에 적용됩니다. "사용하지 않을 때" 항목을 다시 읽으세요. |
| "의견은 두 개가 항상 하나보다 낫다" | 두 번째 의견이 맥락이 더 적어서 노이즈만 만든다면 그렇지 않습니다. 조정하세요. 미루지 마세요. |
| "리뷰어가 동의하지 않았으니 내가 틀린 거예요" | 리뷰어는 여러분의 맥락이 없습니다. 불일치는 판정이 아니라 정보입니다. 산출물을 다시 읽고 분류한 뒤 결정하세요. |
| "교차 모델이 항상 더 낫다" | 교차 모델은 한 모델이 자기 자신과 공유하는 맹점을 잡아내지만, 비용과 도구의 취약성을 더합니다. 대화형 의심 사이클마다 제안하되, 산출물에 그만한 가치가 있는지는 사용자가 결정합니다. 에이전트의 역할은 선택지를 드러내는 것이지, 선택을 막는 것이 아닙니다. |
| "사용자가 한 번 허락했으니 CLI를 계속 호출해도 돼요" | 각 호출은 별도의 허가입니다. 산출물, 프롬프트, 플래그는 호출마다 바뀝니다. 실행할 때마다 사용자와 정확한 명령을 다시 확인하세요. |

## 위험 신호

- 한 줄짜리 이름 변경이나 포매팅 변경에 새 컨텍스트의 리뷰어를 띄우는 것
- 산출물 텍스트를 다시 읽지 않고 리뷰어 출력을 권위 있는 것으로 취급하는 것
- 사용자에게 에스컬레이션하지 않고 3사이클을 넘겨 반복하는 것
- "이거 괜찮아?"라고 묻고 "문제를 찾아라"라고 묻지 않는 것
- 중요한 결정에서 시간 압박 때문에 의심 단계를 건너뛰는 것
- 변경되지 않은 산출물에 새 컨텍스트 리뷰어를 다시 띄우는 것(같은 발견 사항만 나오니 제자리걸음입니다)
- **의심 연극(확인 가능한 신호):** 실질적인 발견 사항이 나온 사이클이 2회 이상인데, 실행 가능하다고 분류된 발견 사항이 하나도 없는 경우. 지금은 의심하는 것이 아니라 검증하고 있는 것입니다. 멈추고 에스컬레이션하세요.
- 커밋한 뒤에야 의심하는 것. 그건 `/review`이지 의심 기반 개발이 아닙니다.
- 외부 CLI 호출을 하드코딩하면서, 그 도구가 존재하고 설정되어 있으며 정확한 문법을 받아들이는지 사용자에게 확인하지 않는 것
- 대화형 의심 사이클에서 교차 모델을 **조용히 건너뛰는 것.** 권하지 않을 때도 제안은 눈에 보여야 합니다. 건너뛰는 것은 괜찮지만, 말없이 건너뛰는 것은 괜찮지 않습니다.
- 외부 CLI가 오류를 내거나 없을 때 말없이 대체 수단으로 넘어가는 것. 실패를 드러내고 사용자가 방향을 정하게 하세요.
- 리뷰어 입력에서 계약을 빼 버리는 것
- 리뷰어에게 CLAIM을 전달하는 것(동의하는 쪽으로 편향됩니다)

## 다른 스킬과의 상호작용

- **`code-review-and-quality` / `/review`**: 상호 보완적입니다. `/review`는 사후 PR 판정이고, 의심 기반 개발은 결정별로 진행 중에 이루어집니다. 둘 다 사용하세요.
- **`source-driven-development`**: SDD는 *프레임워크에 관한 사실*을 공식 문서로 검증합니다. 의심 기반 개발은 *산출물에 대한 여러분의 추론*을 검증합니다. SDD는 API가 존재하는지 확인하고, 의심 기반 개발은 계약 아래에서 그 API를 올바르게 사용했는지 확인합니다.
- **`test-driven-development`**: TDD의 RED 단계는 구체화된 의심입니다. 실패하는 테스트는 반증 시도입니다. TDD가 적용되는 경우, 그 실패 테스트가 행동에 관한 주장에 대한 의심 단계가 됩니다.
- **`debugging-and-error-recovery`**: 리뷰어가 실제 실패 모드를 지적하면, 디버깅 스킬로 넘어가 원인을 찾고 고치세요.
- **저장소 오케스트레이션 규칙**(`../../references/orchestration-patterns.md`): 이 스킬은 메인 세션에서 오케스트레이션합니다. 페르소나가 다른 페르소나를 호출하는 것은 안티패턴 B이며, 위의 로딩 제약을 보세요.

## 검증

의심 기반 개발을 적용한 뒤에는 다음을 확인하세요.

- [ ] 모든 사소하지 않은 결정(위 정의 기준)이 확정되기 전에 CLAIM으로 명시적으로 이름 붙여졌음
- [ ] 사소하지 않은 산출물마다 최소 한 번의 새 컨텍스트 리뷰가 있었음(TDD의 RED 단계에서 나온 실패 테스트는 행동에 관한 주장에 대해 이를 충족하며, 상호작용 항목을 따름)
- [ ] 리뷰어는 ARTIFACT + CONTRACT를 받았음. CLAIM도, 여러분의 추론도 받지 않았음
- [ ] 리뷰어 프롬프트는 검증하는 것("괜찮은가?")이 아니라 적대적인 것("문제를 찾아라")이었음
- [ ] 발견 사항은 산출물 텍스트와 대조해 분류되었음(무비판적 승인이 아님). 계약 오독 / 실행 가능 / 트레이드오프 / 노이즈의 우선순위를 사용함
- [ ] 중단 조건이 충족되었음(사소한 발견 사항, 3사이클, 또는 사용자 재정의)
- [ ] 대화형 모드에서 교차 모델을 사용자에게 **명시적으로 제안했고**(산출물의 중요도와 무관하게), 그 응답을 출력에서 확인했음
- [ ] 비대화형 모드에서 교차 모델은 건너뛰었고, 그 건너뜀을 알렸음
- [ ] 외부 CLI 호출 전에 PATH 확인, 작동 바이너리 테스트, 사용자와의 문법 확인, 실행에 대한 명시적 허가를 거쳤음
