project-coding-standards는 PR 전에 무엇을 지키게 하나?

Long image

A

Answer

project-coding-standards는 modern-web-guidance-src 저장소의 TypeScript·JavaScript·CLI·harness·server endpoint·dashboard 코드를 쓰거나 PR로 올리기 전에 쓰는 규칙집이다. 핵심은 PR 하나에 목적 하나, 기존 abstraction과 정본 데이터 재사용, 공유 설정 약화 금지, pnpm run preflight 통과다.123

  1. PR은 data layer, CLI, UI 순으로 작게 쪼갠다. 백엔드·CLI·frontend를 한 PR에 묶지 않는다.2
  2. agent 이름은 Agents enum으로, 속성은 evals.json 같은 정본에서 읽는다. 문자열 상수와 경로 추측은 금지다.4
  3. tsconfig.json, .oxlintignore, package.json을 고쳐 typecheck나 lint 실패를 피하지 않는다.5
  4. dashboard나 src/dashboard/ 변경은 pnpm run preflight에 더해 pnpm run test:e2e도 통과해야 한다.3

Applies to로컬 원본 분석코드 작성과 명령 실행 없음원본 저장소의 src 파일 미확인

1

언제 켜지고 어떤 코드에 적용되나?

description은 모델이 호출 여부를 판단할 때 참고하는 설명이다. 특정 단어와 정확히 일치해야 켜진다는 뜻은 아니다. disable-model-invocation 같은 호출 제한 필드는 원문에 명시되어 있지 않다.6

원문은 TypeScript, JavaScript, CLI 명령, harness 유틸리티, server endpoint, dashboard 코드를 쓸 때 이 지침을 따르라고 한다.1 호출 맥락으로는 새 코드 작성, feature refactoring, CLI 도구, server endpoint 추가, PR 준비를 든다.6 사람 승인이나 종료 조건은 원문에 명시되어 있지 않다. 끝나는 기준은 아래 통과 조건이다.

주제강제 규칙
실행 환경dashboard는 정적 호스팅(GitHub Pages)과 로컬 서버(gd dashboard) 양쪽에서 돈다. 로컬 Node 서버가 필요한 기능과 endpoint는 정적 모드를 감지해 숨기거나 끈다. 로컬 endpoint에는 ?source=local 같은 데이터 출처를 넘겨 로컬 파일 작업과 원격 streaming을 구분한다.12
다중 run하루나 task당 run이 하나라고 가정하지 않는다. run index와 timestamp로 구분해 데이터가 덮어쓰이거나 합쳐지지 않게 한다. URL query parameter는 안전하게 parsing하고 기본값을 둬서 이동 사이에 상태를 유지한다.13
URL 구성path 변수로 URL을 만들 때 슬래시를 정리해 맨 앞 //가 생기지 않게 한다. 브라우저가 //...를 protocol-relative host로 읽는다.14
정렬차트 marker, badge, indicator, tooltip을 대상 요소의 수평·수직 중앙에 둔다.15

판정 · 원문 규칙 대부분은 "무엇을 하지 마라"가 아니라 "대신 이것을 써라" 형태라서, 리뷰할 때 위반 여부를 파일 단위로 판단할 수 있다. 이 저장소에는 대상 코드가 없어 실제 위반 사례는 확인하지 못했다.16

PR 전에 어떤 통과 조건을 거치나?

Diagram structure
  • 코드 변경 change
  • typecheck와 lint fast
  • preflight pre
  • dashboard·endpoint 변경? ui
  • test:e2e e2e
  • PR 제출 done
  • change → fast
  • e2e → done
  • fast → pre
  • pre → ui
  • ui → done · no
  • ui → e2e · yes

모든 변경은 PR 제출 전에 lint, typecheck, 테스트를 통과해야 한다.3

  1. typecheck와 lint ↗

    빠른 개발 중 확인. pnpm typecheck && pnpm lint.3

  2. preflight ↗

    모든 PR에 필요하다. build, typecheck, lint, 모든 workspace의 병렬 unit test를 묶는다. pnpm run preflight.3

  3. dashboard·endpoint 변경? ↗

    Playwright browser 테스트는 preflight에 없다. frontend visualizer, dashboard 코드, src/dashboard/의 server endpoint를 건드릴 때 직접 돌린다.3

  4. test:e2e ↗

    pnpm run test:e2e. browser 바이너리가 없으면 먼저 pnpm run setup:playwright를 돌린다.3

판정 · 그림의 순서(typecheck와 lint, preflight, e2e)는 원문이 "Tiered"라고 부르는 목록 순서에서 읽은 것이다. 원문이 이 순서를 지키라고 명시한 문장은 없다.3

다른 스킬과 어디에서 이어지나?

이 스킬은 다른 스킬이 호출하거나 이 스킬이 다른 스킬을 호출하는 직접 연결이 없다. 아래 관계는 모두 같은 명령을 쓰거나 목록에서 지목하는 것이어서 순서 그림은 그리지 않았다.

관계내용
R26 · 같은 계열(grader-replay)둘 다 마지막 검증으로 pnpm run preflight를 요구하고 grader 검증에 gd dev <guide> --test-grader를 쓴다. 연결을 지시한 문장은 없다.1920317
R27 · 같은 계열(coherence-auditor)--preflight 옵션이 pnpm run preflight를 실행한다. 이 스킬은 모든 PR에 같은 통과 조건을 요구한다. 연결을 지시한 문장은 없다.21223
R28 · 같은 계열(project-evals)grader 보정에 gd dev --test-grader를 쓰는 점이 같다. 직접 링크는 없다.2317
R31 · 참고(coherence-auditor가 이 스킬을 읽음)glob .agents/skills/project-*/SKILL.md로 project-* 스킬을 지정하고, 그 단계·checkpoint·역할·기술 요구가 서로 모순되지 않는지 읽고 확인한다. 이 스킬도 그 대상이다.2425

전체 관계는 색인 기준 _group-repo-upkeep/repo-upkeep.html에 있다.

확인하지 못한 부분

src/harness/config.ts, evals.json, src/dashboard/, .gitignore 등 원문이 가리키는 저장소 파일은 이 저장소에 없어 읽지 못했다. 규칙이 실제 코드에서 지켜지는지는 확인하지 못했다. pnpm, gd, Playwright 명령은 실행하지 않았다. 통과 조건이 실제로 어떻게 동작하는지는 직접 확인하지 않았다. 호스트가 실제로 이 스킬을 활성화하는 조건은 실행으로 확인하지 않았다.

분석 중 원본은 수정하지 않았다. 원문의 명령과 설치·설정 변경은 실행하지 않았다.
