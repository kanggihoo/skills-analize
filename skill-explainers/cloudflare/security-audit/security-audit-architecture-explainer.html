Cloudflare Source-First Framework

Security-Audit 스킬 아키텍처 및 라우팅 메커니즘

Cloudflare의 security-audit 스킬 원본 소스를 바탕으로, 어떻게 메인 부모 에이전트(Parent)가 다단계 샌드박스 파이프라인을 구축하고 타겟 소프트웨어 특성에 맞춰 전문 지침 파일(.md)들을 정밀하게 동적 라우팅하는지 설명합니다.

1. 운영 모드 및 안전 원칙 (Operating Modes)

Default Mode

Guidance Mode (기본 안내 모드)

보안 관련 단순 질문, 단일 취약점 트리아지, 방법론 문의 시 적용됩니다.

  • 파일 및 산출물 디렉터리(run-N)를 생성하지 않음.
  • 전체 6단계를 수행하지 않고 필요한 분석만 즉각 반환.
  • 대상이 애매할 경우 사용자의 의도를 확인하는 단일 질문을 먼저 던짐.

Execution Mode

Full Audit Mode (전체 감사 모드)

사용자가 코드베이스 전체 침투 테스트, 종합 보안 검토를 명시적으로 요청했을 때만 가동됩니다.

  • 엄격한 사전 예산(Budget Gate) 평가 후 6단계 파이프라인 가동.
  • 독립적인 에이전트 격리 디렉터리 및 구조화된 산출물 생성.
  • 모든 주장은 독립적인 제3의 에이전트(Fresh Verifier)에 의해 기각 시도(Refutation)를 거침.
보편적 실행 안전 원칙 (Universal Execution Safety)
실제 운영/외부 네트워크(Deployed endpoints, APIs, Cloud Control Plane) 대상 프로빙은 엄격히 금지됩니다. 오직 소스 코드 정적 분석과 OS 샌드박스(네트워크 차단, 빈 환경변수 허용목록, 읽기 전용 타겟 마운트, 리소스 제한) 내에서 로컬 더미 픽스처(Dummy Fixture)로만 재현합니다. 외부 환경 사실에 의존해야만 하는 건은 취약점이 아니라 needs_validation으로 격리합니다.

2. 파일 구조와 계층별 라우팅 (Module Routing Architecture)

security-audit/ 내부의 파일들은 정적인 매뉴얼이 아니라, **부모 에이전트가 런타임에 필요한 파일만을 조합하여 각 서브 에이전트의 프롬프트에 동적으로 조립·주입하는 모듈**입니다.

[ Layer 1: 총사령관 (Orchestration Router) ]
  └── SKILL.md (동작 모드 결정, 예산 게이트, 부모-서브에이전트 권한 격리 및 promotion 제어)

[ Layer 2: 6단계 라이프사이클 워크플로우 ]
  ├── RECONNAISSANCE.md (Phase 1: 타겟 정찰, 신뢰경계 식별, 동적 라우팅 결정)
  ├── HUNTING.md (Phase 2: Hunter 에이전트 생성, 격리 scratch 운용, 헌팅 웨이브 제어)
  ├── ATTACK-CLASSES.md (6대 기본 공격 유형 & 도메인 컴패니언 매핑 라우터)
  └── VALIDATION-AND-REPORTING.md (Phase 3~6: Fresh Verifier 교차 검증, JSON 스키마 검증, 최종 리포트)

[ Layer 3: 도메인 전문 지침 (Domain Companions - 선택적 라우팅) ]
  ├── AI-AND-LLM.md               → RAG, 프롬프트 주입, 도구 호출, MCP 클라이언트/서버
  ├── WEB-PROTOCOL-AND-AUTH.md     → 세션, OAuth/JWT, CSRF, HTTP 파서 차이, API 인증
  ├── CLIENT-SIDE.md               → DOM XSS, postMessage, 브라우저 저장소, Webview 통신
  ├── MEMORY-SAFETY-AND-BINARY.md  → C/C++/Rust Unsafe, 버퍼 오버플로우, FFI, 동시성/레이스
  ├── CLOUD-AND-DEPLOYMENT.md      → K8s, IAM 정책, IaC, 서버리스/엣지 런타임
  ├── PROTOCOLS-RPC-AND-MESSAGING.md→ gRPC, GraphQL, WebSocket, 브로커/메시지 큐
  ├── DATA-ISOLATION-AND-LIFECYCLE.md→ 멀티테넌트 격리 파기, 캐시 혼선, 데이터 삭제/복구 생명주기
  ├── DESKTOP-MOBILE-AND-LOCAL-IPC.md→ 네이티브 앱, 딥링크, D-Bus/Unix 소켓, IPC 권한상승
  ├── RESOURCE-EXHAUSTION-AND-AVAILABILITY.md → DoS, 쿼터 소진, 비대칭 연산 부하
  └── SUPPLY-CHAIN-AND-RELEASE.md  → 종속성 혼선, CI 파이프라인 오염, 아티팩트 서명 검증
라우팅의 황금률 (Selection Rule)
ATTACK-CLASSES.md에 명시된 원칙에 따라, 단순히 코드에 특정 패키지 이름이나 단어가 나온다고 컴패니언 문서를 선택하지 않습니다. "Phase 1 정찰 결과 실제 신뢰 경계를 넘나드는 공격 표면이 존재하는가?"를 기준으로만 라우팅합니다.

3. 전체 감사(Full Audit)의 6단계 동작 흐름

1

Phase 1: Reconnaissance (정찰 및 커버리지 계획) RECONNAISSANCE.md

부모 에이전트가 예산 게이트(Budget Gate)를 통과한 후 4개의 읽기 전용 research 서브 에이전트를 병렬 기동합니다.

  • Agent 1a (스택/엔트리포인트): 언어, 프레임워크, 로컬 빌드/테스트 명령어, 오프라인 실행 가능 여부 파악.
  • Agent 1b (권한/경계): 낮은 권한의 주체(Principal)와 진입점별 인증·인가 통제선 매핑.
  • Agent 1c (표면/싱크): 외부 입력이 들어오는 모든 표면과 위험한 싱크(Sink) 추적.
  • Agent 1d (실행환경/가시성): 로컬 샌드박스에서 재현 가능한 픽스처 및 소스 외부 사실 식별.

분석 결과를 토대로 도메인 컴패니언을 라우팅하고, [진입점 × 경계 × 서브시스템 × 공격클래스]로 구성된 coverage-ledger.json을 작성합니다.

2

Phase 2: Coverage-Led Hunting Waves (헌팅 웨이브) HUNTING.md

원장에 등록된 단위별로 general 타입의 Hunter 서브 에이전트 군단을 투입합니다.

  • 프롬프트 조립: architecture.md 요약본 + 배정된 진입점 경로 + 라우팅된 컴패니언 지침 조각(Verbatim Copy)을 주입.
  • 쓰기 격리 (Write Isolation): 각 Hunter는 고유의 agents/<agent-id>/scratch/ 내부만 쓸 수 있으며, 공유 파일이나 타겟 소스 코드는 수정할 수 없습니다.
  • 불변식 실패(Invariant Failure) 추적: "주체 → 입력 → 보안통제 실패 → 싱크 도달 → 관측 가능한 최소 피해" 경로를 규명.
3

Phase 3: Candidate Validation (독립 후보 검증) VALIDATION-AND-REPORTING.md

Hunter가 보고한 취약점 후보(Candidate)들을 지문(Fingerprint)별로 그룹화한 뒤, 사냥에 참여하지 않은 새로운 "Fresh Verifier" 에이전트에게 전달합니다.

Verifier 프롬프트 핵심 규칙:
"You did not write this candidate. Try to refute it from repository source and bounded local evidence."
(당신은 이 후보를 작성하지 않았습니다. 소스 코드와 로컬 증거를 동원해 이 주장을 기각(반박)해 보십시오.)

Verifier는 타겟 코드를 재검토하고 로컬 샌드박스에서 최소 재현을 시도하여 confirmed, needs_validation, rejected 중 하나로 최종 판정합니다.

4

Phase 4: Structured Output & Schema Validation Schema Validation

부모 에이전트가 검증된 결과들을 findings.json에 병합하고 기계적 무결성 스크립트를 직접 실행합니다.

  • node validate-findings.cjs findings.json 실행: 누락된 필드, 심각도 오분류 확인.
  • node validate-coverage-ledger.cjs coverage-ledger.json 실행: 누락되거나 건너뛴 커버리지 영역이 없는지 엄격 확인.
5

Phase 5: Independent Record Verification (독립 2차 검증) Cross-Check

보고서 작성 전, 최종 레코드의 소스 코드 참조 라인과 상태가 정확한지 또 다른 새로운 독립 에이전트로 2차 교차 검증을 마칩니다.

6

Phase 6: Target-Neutral Reporting (보고서 발행) Final Artifacts

완벽히 증명된 팩트만을 기반으로 최종 감사 보고서를 생성합니다.

  • REPORT.md: 경영진 및 관리자용 전체 요약, 커버리지 상태, 통계.
  • FINDINGS-DETAIL.md: 개발자용 상세 분석, 공격 경로 소스 라인, 최소 유효 수정 코드(Smallest Effective Fix).
  • NEEDS-VALIDATION.md: 외부 인프라/배포 설정 확인이 필요한 항목과 안전한 검증 체크리스트.

4. 철저한 쓰기 격리와 아티팩트 승격 (Write Isolation & Promotion)

감사 과정에서 AI가 작성하는 테스트 스크립트나 대상 빌드 프로세스가 호스트 머신이나 보고서 파일을 오염시키는 것을 방지하기 위해 정교한 승격(Promotion) 절차를 강제합니다.

영역 소유권 접근 권한 설명
output/architecture.md, findings.json 등 Parent (부모 에이전트) 부모 에이전트만 쓰기 가능 서브 에이전트는 절대 수정할 수 없는 공유 상태 파일
agents/<agent-id>/scratch/ Sub-Agent (Hunter / Verifier) 해당 에이전트 전용 쓰기 허용 로컬 테스트, 빌드 결과물, 임시 파일이 격리되는 일회용 공간
agents/<agent-id>/artifacts/ Parent (부모 에이전트) 서브 에이전트 접근 불가 (읽기/쓰기 차단) 부모 코드만이 fstat 및 심볼릭 링크 검증 후 scratch에서 승격 복사
TOCTOU 방지 승격 프로토콜 (Promotion Protocol)
서브 에이전트가 종료된 후, 부모는 심볼릭 링크 추적 금지(O_NOFOLLOW), 단일 하드링크 검증(link count == 1), 사전 선언된 바이트 한도 검사 등 엄격한 파일 시스템 검증을 거쳐서만 scratch/의 재현 픽스처를 영구 보존용 artifacts/로 복사합니다.

5. 엄격한 심각도 및 결과 판정 기준

CONFIRMED

확정된 취약점

소스 코드와 로컬 샌드박스에서 시작점부터 피해 싱크까지 완전히 입증된 결함.

  • Critical: 인증 없는 RCE, DB 전체 유출, 계정 탈취.
  • High: 명시적 통제 완전 우회 (인증 우회, 테넌트 간 침범).
  • Medium: 제한된 영향 범위의 경계 침해.
  • Low/Info: 비공개 내부정보 노출 등.
NEEDS_VALIDATION

검증 필요

소스 코드상 의심 경로는 명확하나, 최종 성립 여부가 외부 클라우드/배포 환경에 종속된 경우.

※ 확신이 낮은 취약점을 대충 넣는 휴지통이 아니며, 심각도(Severity) 점수를 매기지 않고 안전한 수동 검증 가이드를 제공함.

REJECTED

기각

Fresh Verifier가 소스 코드를 재추적한 결과 상위 통제 로직에 의해 차단되거나 성립 불가능한 경우.

추측성 허위 경보(False Positive)를 원천 차단하여 보고서의 신뢰도를 유지합니다.
