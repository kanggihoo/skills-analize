dsh-session-projection 스킬은 에이전트를 어떻게 바꾸나

Long image

A

Answer

dsh-session-projection을 쓰면 에이전트는 세션에서 복구해야 할 사실을 모두 프로젝션(Projection)에 둔다. 그리고 읽기는 그 상태를 가진 서비스의 도메인 메서드로만 열어 준다. 프로젝션 정의나 핸들은 프로덕션 읽기 API로 내보내지 않는다.123 이 스킬의 열 가지 규칙은 프로젝션을 만들거나 늘리거나 옮기거나 리뷰할 때 쓴다.4

  1. init과 apply는 동기 함수이고 결정적이다. 이 함수들은 I/O를 하지 않고, Cordis 훅·모델·도구를 부르지 않는다.5
  2. 상태는 고정 크기나 선형보다 느리게 느는(sublinear) 쪽으로 둔다. 이벤트 기록 크기만큼 자라는 색인을 습관으로 들고 있지 않는다.6
  3. 에이전트는 필요한 등록이 끝난 뒤에만 동기 리더를 열고, 과거 복구가 끝난 뒤에만 세션을 동기 리더에 게시한다.78
  4. 읽기 경로를 바꾸기 전에, 에이전트는 공식 소비자(플러그인, CLI/GUI, SDK 두 개)를 모두 찾는다. 동기 호출자는 명시적으로 옮길 때까지 유지한다.9

1

언제 켜지나

description은 프로젝션을 만들거나, 늘리거나, 리뷰할 때, 그리고 세션에서 파생된 복구 상태를 프로젝션으로 옮길 때 쓰라고 한다.4 호출을 막는 필드(disable-model-invocation 등)는 원문에 명시 없음. description은 모델이 스킬을 쓸지 판단할 때 참고하는 설명이다.

프로젝션의 준비·등록·읽기·정리 계약은 packages/session/session-projection/README.md가 정한다고 원문이 가리킨다.1 이 파일은 이 저장소에 없어서 확인하지 못했다.

2

상태는 어디에 두고 어떻게 읽게 하나

규칙 1~6은 "무엇을 어디에 두고, 얼마나 키우고, 어떻게 읽게 하나"를 정한다.

규칙요구원문의 강도
1저장하거나 복원하는 세션 파생 상태는 호스트 전용이라도 모두 프로젝션에 둔다. 맞는 기존 소유자가 있으면 재사용한다. 외부 자원과 프로세스 범위 소유는 저장 상태 밖에 둔다. 등록 핸들, 프라미스, 런타임 자원이 아니라 사실을 저장한다2의무
2프로젝션 정의나 핸들을 프로덕션 읽기 API로 내보내지 않는다. 준비된 핸들은 비공개로 두고, 소비자는 소유 서비스의 도메인 메서드를 쓴다. 핸들은 활성화 때마다 다시 만드는 프로세스 지역 리더다. 서비스가 sessionProjections에 의존하면 그것을 필수로 요구하고, 선택 등록은 선택 기여에만 쓴다. 필수 의존이 없는 것을 다른 복구 경로로 감추지 않는다3금지·의무
2(이어서)런타임이 프로젝션 상태를 여러 개 읽어야 하면 handle.readerFor(session)로 만든 콜백 객체 하나를 받는다. 상태가 늘면 생성자 인자나 기능별 리더를 늘리지 않고 속성을 추가한다. 콜백 타입은 () => S이고, 목적이 하나인 협력자는 콜백을 직접 받는다. 이 호스트 상태 리더는 와이어 스냅샷이나 살아 있는 Cordis 컨텍스트와 별개이며, 등록, 해제, 캐시, I/O를 소유하지 않는다3의무
3init과 apply로 하는 복구는 동기이고 결정적이다. I/O를 하지 않고 훅·모델·도구를 부르지 않는다(그 효과는 런타임 훅이 소유하고 재생이 되풀이해서는 안 된다). 관련 없는 이벤트에는 같은 상태 참조를 돌려준다. 뷰는 동기이며 보이는 값이 같으면 참조를 보존한다5의무·금지
4스키마가 받는 JSON 상태를 저장한다. README의 상태 버전과 복원 지점(checkpoint) 워터마크 규칙을 따른다. 복원 지점에서 시작해 뒷부분을 재생한 결과는 전체 재생과 같아야 한다. 상태 필드나 복구 의미가 바뀌면 버전을 바꾼다10의무
5고정 크기나 선형보다 느리게 느는(sublinear) 상태를 선호한다. 증가는 무시할 만큼 느릴 때만 허용한다. 불가피한 선형 상태는 현재 용도와 메모리·재생·이벤트당 비용을 명시한다. 이벤트 시퀀스 컬렉션을 포함해 기록 크기만큼 자라는 색인을 습관으로 들고 있지 않는다. 크기를 줄이려고 필요한 데이터를 버리거나 동작을 바꾸지 않는다. 완전한 구현으로 시작하고 구체적 필요가 있을 때 최적화한다6권고·조건부 의무·금지
6캐시는 버려도 동작이 바뀌지 않게 다시 만들 수 있어야 한다. 동기 소비자가 페이로드를 필요로 하면 시퀀스 참조만으로는 부족하므로, 규칙 5 안에서 현재 값을 저장하거나 명시적 비동기 경로로 준비한다. 캐시 미스에 전체 로그 읽기를 숨기지 않는다. snapshotEvents, eventAt, ownEvents 또는 같은 역할의 래퍼를 추가하지 않는다. 비동기 래퍼는 동기 기록 읽기를 비동기로 만들지 못한다. 기존 호스트 재생은 이름 붙은 지원 호출자, 소유자, 제거 조건이 있을 때만 남길 수 있고, 클라이언트 캐시 미스의 전체 로그 읽기는 허용하지 않는다. 대체된 복구 헬퍼는 지우고, 캐시 재구성이 복구 규칙을 중복하지 않게 한다11금지·조건부 허용

활성화·이전·검증은 어떻게 하나

규칙 7~10은 "언제 열고, 누가 준비하고, 무엇을 옮기고, 어떻게 확인하나"를 정한다. 규칙 7과 8의 준비는 서로 다른 것이다.78

준비끝나기 전에 하지 않을 것누가 맡나
필수 등록(규칙 7)그 핸들을 쓰는 동기 리더를 열거나 콜백을 설치한다주로 [Service.init]. 등록이 거부되면 그 활성화가 실패한다7
세션 과거 복구(규칙 8)세션을 동기 리더에 게시한다비동기 세션 로딩·준비 소유자8
규칙요구원문의 강도
7필수 등록을 기다린 뒤에 동기 리더를 열거나 그 핸들을 쓰는 콜백을 설치한다. 대기 중에도 이벤트가 올 수 있으니, 이벤트를 놓치지 않으려는 경우에만 리스너를 더 일찍 설치한다. 기다릴 수 있는 콜백에서만 기다린다. 리스너 위치를 옮기거나 대기를 기계적으로 넣지 않는다. 파이버 정리 소유를 유지하고, 명시적 해제를 기다리며, 소유자가 해제된 뒤에는 이펙트를 만들지 않는다7의무·금지
8등록 준비와 세션 복구를 분리한다. 비동기 세션 로딩·준비 소유자가 과거 복구를 끝낸 뒤에 세션을 동기 리더에 게시한다. 레지스트리가 지원하는 수명주기를 쓰고, 도메인 getter에 복원이나 숨은 I/O를 넣지 않는다. 복구는 상태를 준비하고 getter는 읽는다. 단위와 세션별 레지스트리 오류 범위를 보존한다8의무·금지
9읽기 경로를 바꾸기 전에 플러그인, CLI/GUI, SDK 두 개를 포함한 모든 공식 소비자를 찾는다. 동기 호출자는 명시적으로 옮길 때까지 유지한다. 프라미스는 동기 API를 구현할 수 없다. 새 필수 서비스나 활성화 단계는 소비자 갱신과 업그레이드 가이드가 필요하다. 호환은 실제 지원하는 호출자에 맞추고 테스트 전용 조합에 맞추지 않는다9의무
10실제 진입점으로 값, 알림, 오류 범위와 시점, 복구를 검증한다. 기존 동작 단언을 유지한다. 소비자 전용 오류를 즉시 실행하는 프로젝션 처리로 옮기지 않는다. 수명주기를 바꾸면 늦은 등록, 거부, 교체, 대기 중 해제를 시험한다. 부분적인 세션 모의 객체나 마이크로태스크 횟수가 아니라 실제 세션·저장소 수명주기와 명시적 장벽을 쓴다. 해제된 상태뿐 아니라 오류 로그도 본다. 복구 테스트는 쓸 수 있는, 없는, 호환되지 않는 복원 지점과 뒷부분 재생을 런타임 효과 없이 덮는다12의무

판정: 규칙 5의 "무시할 만큼 느린"은 수치 기준이 없다. 원문은 허용 기준을 숫자로 주지 않으므로 에이전트의 판단에 달려 있다.6
