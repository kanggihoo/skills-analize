principle-model-the-domain 스킬은 에이전트를 어떻게 바꾸나

Long image

A

Answer

이 원칙을 적용하면 에이전트는 도메인을 여러 곳에 흩어진 조건문으로 쓰지 않는다. 도메인에 맞는 자료 구조를 먼저 고르고, 그 구조에 규칙을 담는다.1

  1. 흩어진 boolean 대신 상태 기계, 여러 파일에 퍼진 분기 대신 표나 등록부처럼 구조를 바꿔 끼운다.2
  2. 구조는 코드를 쓸 때 고른다. 쓸 때 고르면 비용이 작지만, 나중에 되찾으려 하면 리팩터링으로 보여 계속 미뤄지기 때문이다.3
  3. 추상화를 억지로 만들지는 않는다. 모양이 이미 명확하고 지역적이면 평범한 코드를 둔다.4
  4. poteto-mode는 에이전트가 코드를 쓸 때마다 데이터 모양을 먼저 정하고, 그 구조를 이 원칙으로 고르게 한다.5

disable-model-invocation: true라서 모델이 스스로 이 스킬을 켜지 않는다.6 사용자가 /principle-model-the-domain을 입력하거나, 다른 스킬이 이 원칙을 읽게 할 때 켜진다. 사용자가 원칙을 직접 부르는 일은 드물다. 보통은 사용자가 대화에서 원칙 이름을 말해 에이전트의 방향을 잡는다.7

poteto-mode에서 켜지면 의무가 따라온다. 에이전트는 적용하는 원칙의 SKILL.md를 끝까지 읽는다.11 답변에는 결정을 바꾼 원칙과 바뀐 선택을 밝히고, 이번 세션에 읽은 원칙만 인용한다.12

description은 이 원칙이 다루는 상황을 적은 설명이다. 요청이 그 문장과 같은 말이어야 켜지는 것은 아니다.

이 원칙을 건너뛰었다는 신호도 원문에 있다.13

  • 새 기능이 기존 if/else 사슬에 분기를 하나 더 붙인다.
  • 첫 boolean과 맞춰 둬야 하는 두 번째 boolean이 생긴다.
  • 단계 이름이 붙은 모듈들이 같은 도메인 규칙을 단계마다 되풀이한다(시간순 분해).

원문에는 적용 전후 코드 예시가 없다.

확인하지 못한 것

"분기가 많다"나 "커질 것 같지 않다"의 수치 기준은 원문에 명시 없음. poteto-mode는 모든 코드에 이 원칙을 요구하지만, 원칙 본문은 평범한 코드를 남기라고도 한다. 판정: 두 지시는 충돌하지 않는다. 구조를 따져 본 결과로 평범한 코드를 고를 수 있다.54
