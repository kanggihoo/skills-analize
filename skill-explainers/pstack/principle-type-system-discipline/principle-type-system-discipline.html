Long image

A

Answer

이 원칙을 적용하면 에이전트는 타입 검사기를 증명 도구로 쓴다. 불가능한 상태, 섞이면 안 되는 기본형, 처리하지 않은 변형을 컴파일 시점에 막는다. 타입이 무시하게 둔 경우는 런타임 실패가 된다고 본다.1

  1. 잘못된 상태는 표현할 수 없게 만든다. 모순된 조합이 컴파일되는 선택 필드 묶음 대신 합 타입(sum type)을 쓴다.2
  2. 외부 데이터는 파싱하기 전까지 타입이 없다고 본다. 경계마다 파싱 함수를 둔다.3
  3. 형 변환(cast)으로 컴파일러를 속이지 않는다. 증명할 수 없으면 검증하거나 모델을 다듬는다.4
  4. 타입은 부분성(partiality)이 드러난 곳에서만 강화하고 거기서 멈춘다.5

언제 켜지나

disable-model-invocation: true라서 모델이 스스로 이 스킬을 켜지 않는다.6 사용자가 /principle-type-system-discipline을 입력하거나, 다른 스킬이 이 원칙을 읽게 할 때 켜진다. 사용자가 원칙을 직접 부르는 일은 드물다. 보통은 원칙 이름을 말로 꺼내 방향을 잡는다.7

description은 이 원칙이 다루는 상황을 알려 주는 설명이다. 그 문장과 같은 말이 나와야 켜지는 장치는 아니다.

2

무엇을 강제하나

원문은 어느 타입 언어에나 적용된다고 한다. 언어별 문법은 typescript-best-practices 같은 스킬이 맡는다.12

패턴하는 일
잘못된 상태를 표현할 수 없게변형은 합 타입으로 모델링한다. 언어별 예: 판별 유니언(TypeScript), 값 있는 enum(Rust·Swift·Kotlin), sealed class(Scala), ADT(Haskell·OCaml)2
타입은 구성이다느슨한 타입을 검사로 깎지 말고 원하는 값으로 쌓는다. 비어 있지 않은 목록은 머리와 나머지, 유효한 시간 범위는 시작과 길이13
의미 있는 기본형에 브랜드UserId와 OrderId는 둘 다 문자열이지만 바꿔 쓰지 못하게 한다. 만들 때 한 번 검증하고 그 뒤로는 타입을 믿는다14
외부 데이터는 파싱 전까지 타입 없음RPC 내용, JSON, IPC 메시지, CLI 인자, 설정 파일, 환경 변수, DB 행. 경계마다 파싱 함수를 둔다3
타입 시스템을 속이지 않기형 변환, 안전하지 않은 강제 변환, 컴파일러를 우회하는 단언 함수는 잠복한 런타임 충돌이다4
빠짐없는 매칭은 컴파일러 몫새 변형을 처리하지 않으면 컴파일이 실패해야 한다. 언어별 관용구: never 바인딩(TypeScript), 주석 없는 match(Rust), -Wincomplete-patterns(Haskell)15
권위 있는 스키마에서 파생protobuf, OpenAPI, GraphQL 스키마, DB 마이그레이션, 디자인 토큰이 모양을 정하면 손으로 평행 타입을 만들지 않는다16
부분성이 보일 때만 강화런타임 단언, null 검사, "일어날 리 없다"는 throw가 타입이 약한 곳이다. 그 검사를 타입으로 올리고 멈춘다. 전체 함수를 고른다5

원문이 드는 적용 전후 예시는 이렇다.2

강화를 멈추는 기준도 예가 있다. 빈 목록의 sum은 0이므로 평범한 목록을 받는다. 빈 목록의 head는 답이 없으므로 비어 있지 않은 목록을 요구한다.5
