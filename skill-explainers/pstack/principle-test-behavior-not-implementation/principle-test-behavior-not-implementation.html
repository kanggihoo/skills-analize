Answer

이 원칙을 적용하면 에이전트는 테스트를 남기기 전에 한 가지를 묻는다. 가져온 함수가 모두 undefined를 돌려줘도 이 테스트가 통과하는가? 그렇다면 결함을 잡지 못하는 테스트이므로 단언을 다시 쓰거나 지운다.1

  1. 테스트는 사용자가 부르는 방식으로 코드를 부르고, 사용자가 보는 결과를 리터럴 기댓값과 비교한다.2
  2. 어떤 호출이 일어났는지 확인하거나, 코드 안의 상수를 다시 적는 테스트는 행동을 보지 않는다.2
  3. 원문은 undefined 검사에 걸리는 모양 다섯 가지와 고치는 법을 준다.34
  4. poteto-mode는 테스트를 쓰거나, 바꾸거나, 남길 때 이 원칙을 꺼낸다.5

무엇을 강제하나

결함 때문에 실패할 수 없는 테스트는 CI 시간과 리뷰 주의만 쓰고 아무것도 잡지 못한다. 상수를 고정하는 테스트는 더 나쁘다. 누가 그 상수나 프롬프트를 고치면 실패해서 정당한 수정을 막는다.10

원문이 드는 좋은 예는 expect(slugify("Hello, World!")).toBe("hello-world")다. 본문에서 대상을 구체적 입력 하나로 부르고, 리터럴 출력을 단언한다.4
