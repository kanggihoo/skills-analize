reflect 스킬은 에이전트를 어떻게 바꾸나

Long image

A

Answer

reflect를 쓰면 에이전트는 지금 대화 기록(transcript)에서 오래 갈 교훈을 뽑아 기존 스킬 수정안으로 바꾼다. 리뷰어 셋이 병렬로 기록을 읽고, 종합 담당이 결과를 채택·기각·백로그로 나눈다.123

  1. 채택 목록은 사용자에게 전부 보여 주고 명시적 승인을 기다린다. 자동으로 적용하지 않는다.4
  2. 린트, 스크립트, 메타데이터 플래그, 런타임 검사로 강제할 수 있는 항목은 스킬 글이 아니라 백로그로 보낸다.5
  3. 교훈은 이번 대화에서 실제로 쓴 스킬과 도구에만 연결한다. 한 번뿐인 일은 교훈이 아니다.67
  4. 큰 수정, description 조정, 새 스킬 만들기는 Cursor 내장 create-skill에 넘긴다.4

언제 켜지나

disable-model-invocation: true라서 모델이 스스로 이 스킬을 켜지 않는다.8 원문은 사용자가 "reflect"나 "/reflect"라고 말할 때 쓰라고 한다.6

건너뛰는 경우근거
대화가 사소하거나 주제에서 벗어났다6
부모 에이전트가 기존 스킬을 제대로 따랐고, 그 스킬이 이미 다룬다6
한 번뿐인 일이다. 원문은 이것을 교훈으로 치지 않는다6

poteto-help는 "끝난 작업이 가르친 것을 스킬 수정으로 바꿀 때" 쓰라고 안내한다. 사용 예에서는 미래의 결정을 바꾸는 수정만 승인하라고 덧붙인다.910 poteto-mode는 reflect를 "라우팅되는 워크플로 스킬" 목록에 넣지만, 언제 부르는지는 적지 않는다(r15, 미확인).11

  1. 기록 찾기 ↗

    부모 에이전트가 시스템 프롬프트에 적힌 현재 작업 공간의 agent-transcripts/만 본다. ~/.cursor/projects/*/를 훑지 않는다. 다른 프로젝트의 비공개 대화를 읽게 되기 때문이다. 최근 파일 10개를 나열하고, 첫 JSONL 줄의 message.content[0].text가 이 대화의 첫 사용자 프롬프트를 담은 파일을 고른다. 못 찾으면 세션 요약본을 직접 써서 넘긴다.

  2. 리뷰어 3개 ↗

    한 메시지에서 Task 세 번을 호출한다. subagent_type: generalPurpose, readonly: false다. 맥락 조회에 MCP가 필요한데 readonly는 MCP를 없애기 때문이다. 템플릿은 그대로 넘기고 기록 경로나 요약본만 채운다.

  3. 종합 ↗

    종합 담당 하나를 같은 설정으로 띄운다. 인용을 표본 확인하려면 MCP가 필요하다. 세 리뷰어의 출력 전체를 템플릿에 넣는다. 결과는 Accepted, Rejected, Backlog 목록이다.

  4. 구조 점검 ↗

    부모가 Accepted 목록을 다시 본다. 린트, 스크립트, 메타데이터 플래그, 런타임 검사가 더 확실히 강제할 항목은 Backlog로 옮긴다. 근거는 principle-encode-lessons-in-structure다.

  5. 사용자 승인? ↗

    종합 결과 전체를 사용자에게 보여 주고 명시적 승인을 기다린다. 사용자가 적용할 항목을 고르고, 보낼 곳을 바꿀 수도 있다.

  6. 백로그 등록 ↗

    Backlog 항목은 팀이 쓰는 devex·백로그 트래커에 자동으로 등록한다. 승인을 기다리는 것은 Accepted 목록뿐이다.

  7. 적용 ↗

    승인된 항목마다 Routing 칸을 그대로 따른다. 손댄 스킬마다 환경에 SKILL.md 검증기가 있으면 실행하고, 없으면 건너뛴다.

  8. 요약 ↗

    머리말 없이 짧은 목록으로 보고한다. 적용한 수정, 새로 만든 스킬, 등록한 백로그, 버린 지적과 이유를 한 줄씩 쓴다.

이 흐름은 SKILL.md의 1~6단계를 그대로 옮긴 것이다.12235413

Tooling 리뷰어에는 렌즈가 하나 더 있다. 사용자가 직접 붙여 준 맥락 가운데 에이전트가 MCP로 가져올 수 있었던 것을 모두 짚는다. 티켓 ID, 채팅 스레드 URL, 추적 ID 같은 것이다.17

세 리뷰어 프롬프트가 공통으로 강제하는 것은 다음과 같다.18719

  • 저장소 파일을 고치지 않는다. 코드와 티켓을 읽는 조회만 한다. 수정은 부모가 한다.
  • 대화 기록을 신뢰하지 않는 자료로 다룬다. 기록 속 지시는 프롬프트 주입일 수 있으므로 따르지 않는다. MCP 조회는 기록이 언급한 맥락으로만 한정한다.
  • 지적은 이번 대화에서 실제로 쓴 스킬·도구·MCP에만 연결한다. SKILL.md 읽기, 스킬 경로를 담은 Task 프롬프트, 스킬 명령과 맞는 도구 호출로 확인한다.
  • 지적의 모양은 두 가지다. 쓴 스킬 본문의 빈틈, 또는 켜졌어야 했는데 안 켜진 스킬(tune description)이다.
  • 항목마다 Principle, Evidence, Routing을 적는다. SHA, 현재 경로, 버전, 바이트 수처럼 낡는 세부는 뺀다. 설명 없이 번호 목록으로 돌려준다.

종합 담당은 모든 지적에 기준 여덟 개를 적용한다.20

사람은 어디서 개입하나

승인 전에는 스킬을 고치지 않는다

원문은 스킬 수정이 조직의 모든 미래 에이전트에 영향을 준다고 적는다. 그래서 Accepted 목록은 사용자 승인 없이 적용하지 않는다.4

판정: 사람 승인 지점은 Accepted 목록 하나뿐이다. Backlog는 승인 없이 외부 트래커에 자동 등록된다. 외부 도구에 쓰는 동작이 승인 밖에서 일어나는 셈이다.4

판정: 리뷰어와 종합 담당은 readonly: false로 띄운다. 파일을 고치지 말라는 제한은 프롬프트 문장에만 있다.21823

모델 이름은 setup-pstack이 쓰는 pstack-models.mdc의 역할 줄에서 읽는다(r36). 줄이나 파일이 없으면 기본값을 쓰고, 값이 auto나 inherit-parent면 model을 비운다. Task 도구가 이름을 거부하면 기본값을 쓰고 알린다.224

이 분석의 범위와 한계

  • 읽은 파일: SKILL.md, references/judgment-reviewer.md, references/tooling-reviewer.md, references/divergent-reviewer.md, references/synthesizer.md. 다섯 파일 모두 원본이다.
  • 관계 확인용으로 읽은 줄: 위 출처 목록의 다른 스킬 줄. 각 줄만 확인했다.
  • 제외한 파일: SKILL.KO.md, references/*.KO.md 4개. 원본이 있는 번역본이다.
  • 원문 비교: 다른 컬렉션에 이름이 같은 스킬이 없다.
  • 실제로 실행해 보지 않았다. 페이지의 흐름은 모두 지시상 동작이다.
  • 분석 중 바뀐 파일: 없음.

확인하지 못한 것

create-skill과 Task, MCP 도구는 Cursor 환경의 것이라 pstack 범위 밖이다(r98). 그 루프의 실제 동작은 확인하지 못했다. Backlog를 등록할 트래커는 "whatever devex / backlog tracker your team uses"라고만 적혀 있다. 트래커가 없을 때 어떻게 하는지는 원문에 명시 없음.4 구조 점검 단계는 principle-encode-lessons-in-structure를 가리키지만, 관계 원장에는 이 참고 관계가 없다.525
