benchmark-checklist 스킬은 에이전트를 어떻게 바꾸나

Long image

A

Answer

benchmark-checklist를 쓰면 에이전트는 직접 잰 성능 수치를 바로 보고하지 않는다. 질문 7개에 실행 근거로 답한 뒤에야 판정과 수치를 낸다.1

  1. 측정 전에 내보낼 주장을 문장으로 먼저 적는다. 질문 7개는 그 문장을 시험한다.2
  2. 답은 코드에 대한 짐작이 아니라 실행에서 얻은 근거여야 한다.1
  3. 각 쪽을 5회 이상 번갈아 돌리고 중앙값과 범위를 보고한다.3
  4. 병목(limiter)을 대지 못하거나, 한쪽이 튜닝되지 않았거나, 4번·7번을 확인하지 못하면 판정은 "결론 없음"이다.4

언제 켜지나

disable-model-invocation: true라서 모델이 스스로 이 스킬을 켜지 않는다.5 사용자가 /benchmark-checklist를 입력하거나 다른 스킬이 부를 때 켜진다. 본문은 성능 수치를 만들 때 쓰라고 한다. PR의 전후 비교, 성능 저하(regression) 주장, 수치 끌어올리기(hillclimb) 하네스, 라이브러리나 설정 선택이 예다.1

  1. 사전 준비 ↗

    내보낼 주장을 실제 문장으로 적는다(예: "60k행 데이터셋에서 p50 기준 export가 30% 빠르다"). 측정 스크립트를 읽고 무엇을 재고, 세고, 무시하는지 적는다. uptime으로 부하 평균을, nproc로 코어 수를 본다. 기계가 바쁘면 무엇이 도는지 찾는다. 멈출 수 없으면 두 쪽을 번갈아 돌려 같은 잡음을 받게 하고, 보고서에 그렇게 했다고 적는다.

  2. 대략치? ↗

    사용자가 빠른 대략치를 요청했는지 본다. 선택지 사이에서 고르는 일은 절대 대략치가 아니다.

  3. 1회 실행 ↗

    한 번 돌린다. 그래도 4번(오류)과 7번(일이 실제로 일어났나)은 확인한다. 한 번 돌린 결과라고 밝힌다. 결과가 이상해 보이지 않으면 나머지 질문은 건너뛴다.

  4. 질문 7개 ↗

    아래 표의 질문 7개에 모두 실행 근거로 답한다.

  5. 보고 ↗

    판정을 먼저 쓴다. 수치, 단위, 실행 횟수, 범위, 병목을 붙인다.

대략치 분기는 원문 11줄을, 나머지는 13~34줄을 따랐다.1024 판정: 대략치 분기와 사전 준비 중 무엇이 먼저인지는 원문에 명시 없음. 그림은 사전 준비를 공통으로 둔다.

질문 7개는 무엇을 확인하나

질문확인하는 것실패하면
1 왜 두 배가 아닌가병목을 댄다. 보고하지 않을 별도 실행에서 프로파일한다. 프로세스별 CPU(top, pidstat), 런타임 프로파일러(node --cpu-prof, py-spy, perf), I/O 대기, 시스템 콜 수(strace -c)를 본다. 부하 생성기도 본다11부하 생성기가 먼저 포화되면 부하 생성기를 잰 것이다. 수치가 안 움직였어도 병목을 찾기 전에는 변경이 쓸모없다고 하지 않는다
2 튜닝했나모든 쪽을 운영 환경처럼 돌린다. 릴리스 빌드, 운영 플래그와 환경 변수, 배치·트랜잭션 설정, 연결 풀, 운영과 같은 캐시 상태, 같은 버전과 데이터12승자 금지한쪽이 기본값이면 구현이 아니라 설정을 비교한 것이다. 튜닝 후 다시 잰다. 튜닝할 수 없으면 그 실행으로 승자를 고르지 않는다
3 한계를 넘었나산수로 확인한다. 초당 바이트를 디스크·네트워크 대역폭과, 초당 연산 × 연산당 비용을 코어 수와 비교한다13한계를 넘은 결과는 캐시, 아무 일도 안 하는 코드, 버그를 잰 것이다
4 오류가 났나실패와 비정상 응답을 센다. 출력이 있는지가 아니라 맞는지 본다. 스크립트가 오류를 안 세면 세게 고친다14거절은 빠르고 시간 초과·재시도는 느려서 수치가 왜곡된다
5 재현되나각 쪽을 5회 이상 A, B, A, B로 번갈아 돌린다. 중앙값과 범위를 보고한다. 아슬아슬하면 순위합 검정이나 하네스 자체 통계를 쓴다3실행 간 변동보다 작은 차이는 "측정 가능한 차이 없음"이다
6 중요한가미시 결과 옆에 사용자가 기다리는 전체 경로를 현실적인 데이터 크기와 동시성으로 잰다. 미시 결과는 전체 대비 비율로 보고한다15요청의 1%를 쓰는 헬퍼는 아무리 빨라져도 요청을 최대 1%만 빠르게 한다
7 실제로 일어났나측정 구간 안에서 일이 돌았는지 본다. 요청이 서버에 닿았고, 행이 쓰였고, 바이트를 읽었고, 코드가 결과를 썼는지16아무도 순회하지 않는 제너레이터, 기다리지 않는 프로미스, JIT 컴파일러가 버리는 결과, 시간 초과는 일어나지 않은 일의 수치를 만든다

무엇을 보고하나

규칙원문의 강도
판정을 먼저 쓴다. 빠름, 느림, 측정 가능한 차이 없음, 결론 없음 중 하나4의무
수치와 단위, 실행 횟수, 범위, 병목을 함께 쓴다4의무
차이를 주장하는데 병목을 못 대거나, 한쪽이 튜닝되지 않았거나, 4번·7번을 확인 못 했으면 "결론 없음". 빈 곳을 밝힌다4의무
PR 본문에는 대표 수치 하나만. 실행 기록, 범위, 병목 근거는 링크한 산출물이나 노트 파일로4의무
현재 출시 설정으로 주장을 좁혀도 튜닝 문제는 풀리지 않는다. 사용자는 오늘의 설정이 아니라 선택지를 도입하기 때문이다12금지(우회 불가)

원문의 보고 예시는 이렇다. "p50 41 ms → 33 ms, 각 쪽 7회 실행의 중앙값, 이후 범위 32~35 ms, 코어 하나에서 JSON 파싱에 묶임."4 PR 대표 수치 규칙은 opening-a-pr 플레이북을 따른다. 그 플레이북은 before → after 형태의 수치 하나를 단위와 함께 쓰라고 한다.17

perf-issue 플레이북이 느린 곳을 찾아 고치면, 이 스킬은 그 기준선과 이후 모든 수치를 검증한다. hillclimb 플레이북에서는 하네스를 고정하기 전에 검증한다. 고정된 하네스가 오류 수와 일한 양을 출력하므로, 유지·되돌리기 판단마다 4번과 7번을 따로 하지 않아도 확인된다.18

확인하지 못한 것

원장에는 이 스킬이 opening-a-pr, perf-issue, hillclimb 플레이북을 가리키는 관계 행이 없다. 원문은 34·38·39줄에서 세 플레이북을 이름으로 가리킨다. "아슬아슬한" 차이의 수치 기준과 순위합 검정의 유의 수준은 원문에 명시 없음. Linux 외 환경에서 strace -c 대신 쓸 도구도 원문에 명시 없음.
