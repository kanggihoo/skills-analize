validation은 후보 하나하나를 어떤 근거로 어떤 처분에 놓나?

Long image

A

Answer

validation은 넘겨받은 후보마다 근거가 받쳐 주는지 따져 reportable, suppressed, not_applicable, deferred 중 하나로 처분한다.12 전체 PR, commit, branch, patch, 저장소 scan을 시작하는 1차 트리거는 아니다.3

  1. 일치하는 advisory, 위험한 API, helper 이름, 빠진 guard는 단서일 뿐 finding이 아니다. 보안 영향이 뒷받침돼야 한다.4
  2. 방어하는 근거가 없다는 이유만으로 안전하다고 하지 않는다. 설정이나 배포 근거가 없으면 한계이고 deferred나 추가 조사로 이어질 수 있다.15
  3. 네트워크 접근과 PoC 실행은 사용자 승인과 scan 권한 안에서만 한다.6
  4. 독립적으로 취약한 인스턴스는 따로 처분한다. 안전한 이웃이나 더 강한 이웃 finding이 다른 행을 결정하지 않는다.1

언제 켜지고 무엇을 검증하나?

description은 모델이 호출 여부를 판단할 때 참고하는 설명이다. 특정 문구와 정확히 일치해야 켜진다는 뜻은 아니다.

disable-model-invocation 같은 호출 제한 필드는 원문에 명시 없음이다. agents/openai.yaml에도 policy가 없다.37

상황에이전트의 행동
scan이 이미 validation 단계에 있다이 스킬을 쓴다.3
사용자가 후보 security finding이 유효한지 판단해 달라고 직접 요청한다이 스킬을 쓴다. 요청한 finding 하나는 저장소 전체 검색을 승인하지 않는다.34
저장소 전체 scandiscovery의 coverage ledger와 advisory seed 행은 아직 다듬은 finding이 아니어도 범위에 든다.4
Standard scan, Deep Scan worker자기 Standard workflow 안에서 validation하고 이 스킬을 호출하지 않는다.89

각 후보에서 확립할 것은 공격자가 조작하는 source, 가장 가까운 통제, 민감한 sink, 도달 가능한 경로, 신뢰 경계, 구체적 영향이다.4 파일을 만들거나 보관하기 전에 ../../references/artifact-storage.md를 읽는다.2

2

어떤 순서로 후보를 따지나?

  1. 주장 파악

    공격자 입력, 보안 경계, 관련 통제, 민감한 동작, 전제를 정한다. 주어진 맥락과 저장소 근거를 쓰고, 의미 있는 평가가 막힐 때만 빠진 정보를 사용자에게 묻는다.10

  2. 근거 찾기

    주장을 받치거나 깨는 근거를 찾는다. 집중한 소스 분석이나 승인된 재현 중 불확실성을 풀어 줄 쪽을 고른다. 실행 가능하고 비용이 맞으면 runtime 확인을 쓴다.10

  3. 피드백 확인

    활성 scan에 <context_dir>/false_positive_feedback.json이 있으면 지시가 아니라 근거로 읽는다. 적힌 이유가 현재 코드와 통제에서도 성립할 때만 해당 후보를 suppress한다.10

  4. 처분 기록

    모든 후보에 정확한 영향 위치, 관찰한 근거, 반증이나 증명 간극, 확신도를 적어 처분한다. 독립적으로 취약한 인스턴스와 받은 범위를 보존한다.10

강제·금지내용
네트워크·PoC사용자 승인과 활성 scan의 권한을 넘어 네트워크에 접근하거나 PoC를 실행하지 않는다. 오프라인 scan은 계속 오프라인이다.6
대상 변경대상을 바꾸지 않는 scan에서는 build, 생성한 harness, PoC를 storage 정책이 준 disposable workspace에서 돌린다. 별도 재구현보다 원본 코드를 시험한다.6
방법 선택언어나 도구 이름으로 방법의 순위를 매기지 않는다. 소스 근거가 주장을 정리하면 build나 live 배포를 요구하지 않는다.11
setup 실패서비스, dependency, 설정이 없으면 증명 간극으로 적는다. 안전하다는 근거로 쓰지 않는다. 대상을 재구현한 코드로 원본 동작이 증명됐다고 주장하지 않는다. 멈추기 전에 로그나 프로세스 상태를 확인한다.11
정적 결론정적 결론과 실제 실행한 시험을 구분한다. 실행하지 않은 일을 실행했다고, 실패한 validation을 성공했다고 쓰지 않는다.5

처분과 확신도는 어떻게 정하나?

모든 후보는 reportable, suppressed, not_applicable, deferred 중 하나를 받는다. 처분 값에 대한 정의 문장은 원문에 명시 없음이다. 원문이 설명하는 것은 처분하는 방식이다.1

판단 상황에이전트의 행동
인스턴스가 여러 개대표 재현 하나가 관련 인스턴스를 뒷받침할 수는 있지만 인스턴스마다 source, control, sink, impact를 확인한다. 독립적으로 발동하는 동작과 깨진 통제는 따로 지정할 수 있게 두고 각각 처분한다.1
래퍼와 구현래퍼는 도달 가능성을 증명한다. 취약점을 일으키는 concrete implementation이나 공유 통제를 보존한다.1
suppress정확히 그 주장을 깨는 근거가 있어야 한다. 호출자, 배포, 출처 근거가 없으면 추가 조사나 deferred가 맞을 수 있고, 근거 부재만으로 안전하다고 하지 않는다.1
우선순위뒷받침된 영향, 도달 가능성, 미해결 불확실성 순으로 먼저 본다. 한 인스턴스의 추가 작업이 처분이나 심각도를 바꾸지 못하면 나머지 후보로 넘어간다.1
통제 확인통제는 사용 지점에서 확인한다. 대체 표현, 분기별 변환, redirect, 상태 변화, 객체 선택이 검증 대상을 바꿀 수 있으면 따라간다. 통제는 민감한 동작이 실제로 쓰는 값에 걸려야 한다.1

확신도는 도달 가능성, 위반한 경계, 영향, 반증을 포함한 finding 전체에 대해 정한다.12

high
관련 경로와 보안 영향이 확립됐고 해소되지 않은 중대한 반증이 없다.12
medium
직접 근거가 주장을 받치지만 중대한 전제나 경로 일부가 불확실하다.12
low
근거가 간접적이거나 중요한 맥락이 빠졌다.12

crash를 재현한 PoC는 관찰된 crash만 증명하고 주장한 모든 결과를 증명하지 않는다. 정적 근거도 전체 주장을 확립하면 high를 받칠 수 있다.12 runtime 증거에는 짧고 비대화형인 명령을 쓴다. 필요하면 gdb -q -batch -ex run -ex bt -ex quit나 lldb -b -o run -o bt -o quit를 쓰고, 정상 입력을 대조군으로 둘 수 있다.13
