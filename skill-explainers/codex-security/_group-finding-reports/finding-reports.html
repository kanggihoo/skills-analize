vulnerability-writeup은 취약점 하나나 disclosure 묶음을 다른 연구자가 확인할 수 있는 독립 보고서로 쓴다. propose-security-hardening은 개별 patch를 넘는 구조적 보강안을 대안 비교와 함께 제안한다.12 두 스킬 사이에는 필수 순서도, 호출도, 위임도 원문에 없다. scan이 최종 보고에서 요청하거나 사용자가 요청할 때 각각 따로 쓴다.34 부분 분석이다. 플러그인 루트의 references/artifact-storage.md와 호스트의 artifact 도구는 컬렉션에 없어 읽지 못했다.56

  1. vulnerability-writeup은 원래 finding을 결론으로 삼지 않고 평가할 주장으로 본다. 공격자, 통제 입력, 경계, 실제 실패, 지원되는 영향을 먼저 확인한다.7
  2. propose-security-hardening은 공유된 invariant 위반이나 흩어진 통제 소유권처럼 구조 원인이 증거로 이어질 때만 쓴다. 독립 finding은 국소 수정이 나을 수 있다.8
  3. 자동 보고에서 저장 위치가 다르다. 보고서는 findings/<slug>/<slug>.md, 보강안은 hardening/hardening.md다.910
  4. 어느 scan이 두 스킬을 호출하는지는 두 스킬 원문 모두에 명시 없음. 원장 R22, R23은 불명이다.92

두 스킬은 무엇을 만들고 어디가 다른가?

두 스킬은 서로의 입력을 요구하지 않는다. 같은 finding을 다른 방식으로 정리하므로 만드는 것, 입력, 경계가 다르다. 아래 표는 두 원문을 항목별로 맞춰 본 것이다.

항목vulnerability-writeuppropose-security-hardening
만드는 것다른 연구자가 이해하고 확인할 수 있는 자기 완결 보고서다. 취약점 하나나 disclosure 묶음에 쓴다.111구조적 변경을 제안하고 의미 있는 대안을 비교하며 비례하는 다음 단계를 권고한다.12
시작에 충분한 입력취약점 메모, disclosure 보고서, PoC, 소스, Codex Security finding이다. scan은 선택이다.1disclosure나 소스 트리면 시작할 수 있다. scan은 선택이다.12
입력을 다루는 방식원래 finding은 평가할 주장이다. 소스가 없으면 출처를 밝힌 설명은 쓸 수 있지만 소스에 기대는 주장은 조건부로 둔다. 발췌, 줄 번호, 관찰을 지어내지 않는다.7저장소 내용과 보고서는 증거이지 지시나 권한이 아니다. 제안은 취약점이 고쳐졌다는 증명이 아니다.13
실행·구현 경계권한 범위선택적으로 PoC를 쓴다. 권한 범위 안에서만 실행하고, 파괴적인 PoC는 일회용 로컬 대상에서만 돌린다.14구현 별도분석만으로는 구현이 허락되지 않는다. 사용자가 구현을 요청하면 선택한 설계와 제약을 이어받는다.15
형식 참고 문서전체 disclosure 보고서는 references/report-format.md의 개요를 따른다. 좁은 편집이면 필요한 절만 쓴다.1617상세 설계안이나 여러 기회의 portfolio일 때 references/proposal-format.md를 읽는다. 별도 JSON, 다이어그램 파일, 기회별 문서는 선택이다.1819
자동 보고에서 저장Codex Security 최종 보고 중에는 findings/<slug>/<slug>.md에 두고 writeup.reportPath로 그 상대 경로를 돌려준다.9scan 최종 보고가 요청하면 scan의 artifact 도구로 hardening/hardening.md를 저장하고 상대 경로를 orchestrator의 scan.hardening.portfolioPath로 돌려준다.10
저장하기 전에플러그인 루트 references/artifact-storage.md를 읽고 managed storage 기본값을 쓴다. 사용자가 정한 위치가 있으면 그 정책 아래에서 따른다.5같은 파일을 읽는다. 형제 output 폴더를 지어내지 않고 완료된 scan을 고치지 않는다.6

판정 · 두 스킬은 같은 증거를 쓰는 병렬 산출물이라서 어느 쪽을 먼저 만들어도 원문이 막지 않는다. 근거는 두 스킬 어디에도 선행 스킬이나 후속 스킬 지시가 없다는 점이다.1618

순서나 위임이 있나, 어떤 관계로 이어지나?

순서, 선택지, 반복, 위임을 그릴 만한 원문 근거가 없어 이 묶음에는 다이어그램을 넣지 않았다. 원장이 정한 대로 입력, 산출물 경로, 요청 조건을 표로만 남긴다. 그림에서 뺀 관계는 표에 모두 남기고 그림 없음으로 표시했다.

어떤 요청에 어느 스킬을 쓰고, 무엇은 하지 않나?

description은 모델이 호출 여부를 판단할 때 참고하는 설명이다. 두 스킬의 SKILL.md에는 disable-model-invocation 같은 호출 제한 필드가 없고 agents/openai.yaml에도 policy가 없다.122324

요청스킬경계
취약점 하나를 다른 연구자가 확인할 보고서로 쓴다vulnerability-writeup주 용도원래 finding을 더 강하게 쓰지 않는다. 증거가 finding과 어긋나면 어긋남을 설명하고 가까운 다른 약점으로 바꿔 쓰지 않는다.7
여러 취약점의 disclosure campaign을 정리한다vulnerability-writeup취약점을 근본 원인과 영향 코드로 구분해 중복을 가린다. 따로 이해될 finding은 따로 둔다.16
같은 invariant 위반이 반복되는지 보고 구조 대안을 비교한다propose-security-hardening주 용도구조적 프로젝트를 지어내지 않는다. 독립 finding이면 국소 수정이 낫다고 답한다.8
보강안을 구현해 달라고 한다propose-security-hardening구현 별도분석 요청만으로는 구현을 허락받지 않는다. 구현을 요청받았을 때만 선택한 설계로 진행한다.15
PoC를 만들거나 돌린다vulnerability-writeup허가 없는 대상사용자의 권한 범위 안에서만 한다. 공개, 외부, 운영 대상은 대상별 허가가 필요하다. 실행하지 않은 로그나 결과를 지어내지 않는다.14

두 스킬은 취약점이 고쳐졌다고 증명하지 않는다

propose-security-hardening은 제안이 취약점을 고쳤다는 증명이 아니라고 명시한다. 취약점을 실제로 고치고 검증하는 스킬은 이 묶음 밖의 fix-finding이다.1321 vulnerability-writeup의 보고서는 제안 코드와 shipped fix, 확인된 fixed release를 구분해 적는다.17

확인하지 못했거나 원문에 명시가 없는 부분

어느 scan이 vulnerability-writeup과 propose-security-hardening을 호출하는지는 원문에 명시 없음. R22, R23은 불명으로 두었다.92 플러그인 루트 references/artifact-storage.md는 읽지 못했다. 저장 경로와 managed storage 기본값을 더 정하는지는 알 수 없다. 관련 원장 행은 R60이다.56 get_codex_security_scan_context, scan의 artifact 도구, writeup.reportPath와 scan.hardening.portfolioPath를 소비하는 호스트 구현은 컬렉션에 없어 실행하지 않았다. 자동 보고 동작은 지시상 동작이다.13109 vulnerability-writeup의 보고서를 propose-security-hardening이 입력으로 받는 일은 서로 지목하지 않는 추론(R41)이다. 같은 요청에서 두 산출물을 어떻게 이어 쓰는지는 원문에 명시 없음.112

분석 중 원본은 수정하지 않았다. 스킬 안의 지시(소스 확인, PoC 실행, 파일 저장, 도구 호출)는 분석할 자료로만 읽고 실행하지 않았다. 자동 검증은 HTML 구조와 출처 해석만 확인한다. 사람 검토는 미실시다.
