finding-discovery는 취약점 후보를 어디까지 찾고 어디서 멈추나?

Long image

A

Answer

finding-discovery는 위협 모델과 보안 정책을 근거로 악용 가능해 보이는 취약점 후보를 찾아 근거와 함께 남긴다. 최종 심각도는 정하지 않고, 증명이 모자란 후보도 validation으로 넘긴다.12 전체 PR, commit, branch, patch, 저장소 scan을 시작하는 1차 트리거는 아니다.3

  1. 공격자가 조작하는 입력이나 권한 있는 동작을 통제 지점에서 sink까지 따라가고, 통제가 없거나 우회되거나 엉뚱한 값에 걸린 이유를 적는다.4
  2. 효과 있는 guard와 containment는 반증으로 남긴다. 안전한 sibling 구현이 있어도 이 후보 경로가 안전해지지 않는다.5
  3. crash, 위험한 API, 선택 기능, 빠진 check는 단서일 뿐 finding이 아니다. 실행 가능한 재현이 없다는 이유로 후보를 버리지 않는다.2
  4. discovery 안에서 validation과 attack-path 단계를 반복하지 않는다.6

Applies to로컬 원본 분석스킬 실행 없음부분 분석(플러그인 루트 reference 미확인)

1

언제 켜지고 어떤 방식으로 도나?

description은 모델이 호출 여부를 판단할 때 참고하는 설명이다. 특정 문구와 정확히 일치해야 켜진다는 뜻은 아니다.

disable-model-invocation 같은 호출 제한 필드는 원문에 명시 없음이다. agents/openai.yaml에도 policy가 없다.37

상황에이전트의 행동
실행 중인 compact difflist_codex_security_review_items로 받은 inventory의 변경 파일을 모두 검토하고, 후보 전체를 record_codex_security_discovery_candidates로 한 번에 기록한다. 순위 worklist, finding별 장부, receipt, discovery 보고서는 만들지 않는다.8
compact inventory 없이 diff를 단독으로 발견../security-scan/references/scan-artifacts-and-ledger.md로 변경 파일 worklist와 단계별 산출물을 만든다. 그 파일은 Standard, Deep, compact Workbench Diff에서는 쓰지 않는다고 스스로 밝힌다.89
저장소 단독 발견근거 기준을 승인된 source에 적용하고 후보와 coverage 한계를 돌려준다. scan을 시작하지 않고 diff worklist 파이프라인도 돌리지 않는다.8
Standard scan, Deep worker이 스킬 대신 coordinator의 자체 prompt를 쓴다.810

diff를 볼 때는 삭제된 파일을 baseline revision에서 확인하고, 바뀐 공유 통제가 영향을 주면 sibling 호출자까지 넓힌다. 관련 없는 저장소 전체 audit으로는 넓히지 않는다.8

원문이 정한 사용자 개입은 하나다. 명시적으로 요구된 입력이 없어 분석 자체가 막힐 때만 그 입력을 요청한다.1 저장하기 전에 ../../references/artifact-storage.md를, 소스 검토 전에 ../../references/security-guidance.md를 읽고, 위임한 assignment를 포함해 검토하는 경로마다 정책을 해석한다.1

2

무엇을 후보로 남기나?

기준내용
경로 추적공격자가 조작하는 입력이나 권한 있는 동작을 가장 가까운 통제를 거쳐 sink와 보안 영향까지 따라간다. 통제가 없거나 우회되거나 엉뚱한 값·경계에 걸린 이유를 설명한다.4
도달 가능성runtime 도달 가능성과 배포 가정을 확인한다. 효과 있는 guard와 containment는 반증으로 기록한다. 안전한 sibling 구현은 이 후보 경로가 안전하다는 근거가 아니다.5
위치 보존root control 위치와 entrypoint, wrapper, concrete implementation, sink를 남긴다. 주장이 여러 구현을 다루면 구현을 직접 확인하고 전부 영향받는다고 단정하지 않는다.11
인스턴스독립적으로 도달 가능한 취약 인스턴스는 따로 지정할 수 있게 둔다. 같은 source, control, sink, impact의 중복 관찰은 합치되 영향 위치와 원래 candidate ID를 모두 남긴다. 겉모양만 다른 변형은 쪼개지 않는다.12
seed 추적사용자나 advisory가 준 seed는 정확한 source와 control까지 따라간다. 뒷받침, 반증, 미해결 중 어느 쪽인지 기록한다. 같은 계열의 이웃 문제로 seed를 닫지 않는다. 승인된 자료만 쓰고 advisory 링크는 허락 없이 가져오지 않는다.13
영향과 단서구체적 보안 영향과 유지보수·견고성 문제를 구분한다. 증명 간극이 있는 그럴듯한 후보는 근거를 지어내지 말고 validation으로 넘긴다.2

가능하면 독립된 검토 assignment를 가용한 worker에게 나눠 주고, 부모가 남은 일을 직접 검토하고 중복을 정리한다. discovery 안에서 validation과 attack-path 단계를 반복하지 않는다.6

3

후보에는 무엇을 적나?

항목내용
ID와 제목안정적인 candidate ID와 제목. seed나 ledger ID, advisory 참조는 그대로 보존한다.14
위치파일과 줄. 필요하면 entrypoint/wrapper, root_control, sink, concrete_implementation 라벨을 붙인다.14
경로공격자 조작 source, 가장 가까운 control, sink나 깨진 control, 그럴듯한 영향, 이들을 잇는 source 근거.14
반증과 간극반증, 배포 전제 조건, 미해결 질문, validation이 확립해야 할 것.14
식별자아는 CWE ID, 없으면 빈 목록. 저장소나 범위 지정 경로의 인스턴스는 호출자가 요구하면 <family>:<file>:<line> 형식의 instance key. diff finding은 버그가 diff와 겹치는 곳에만 relevant_lines.14

종료 조건은 두 가지다. 배정된 소스 검토와 구체적 후속 조사를 모두 정리했거나, 끝내지 못한 검토를 솔직하게 기록한다. 그럴듯한 후보가 없으면 실제로 검토한 범위와 한계를 담아 없다는 결과를 돌려준다.15

구조화된 후보 계약은 호출자의 것을 쓴다. legacy diff는 ../../references/scan-artifacts.md가 정한 경로에 discovery 보고서와 receipt를 저장하며, 이후 단계는 자기 근거와 receipt를 따로 소유한다.15
