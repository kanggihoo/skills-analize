attack-path-analysis는 finding을 어떤 근거로 보고하고 어떤 근거로 버리나?

Long image

A

Answer

attack-path-analysis는 finding마다 공격자가 source에서 sink까지 가는 경로, 영향, 심각도, 보고 여부를 정한다. 사실 정리, 심각도 보정, 최종 정책 결정을 결과에서 따로 보이게 두고, 이미 정한 사실을 바꾸려고 discovery를 다시 열지 않는다.123 전체 PR, commit, branch, patch, 저장소 scan을 시작하는 1차 트리거는 아니다.4

  1. 공격자 위치, 진입점, 조작 입력, 보안 경계, 민감한 동작을 저장소 근거로 따라간다. 근거 없는 공격 사슬은 만들지 않는다.56
  2. 자기 영향만 있거나 달성하기 매우 어려운 전제는 hard suppression 대상이다. 특권, 운영자, 개발자, 물리 접근이 전제이면 ignore다. 권한 상승 차이가 문제일 때만 예외다.7
  3. 영향이나 가능성이 낮다는 이유만으로 진짜 reportable finding을 버리지 않고 낮은 심각도를 준다.7
  4. 심각도는 critical P0, high P1, medium P2, low P3으로 대응한다. 무시한 finding은 우선순위가 없다.8

Applies to로컬 원본 분석스킬 실행 없음부분 분석(플러그인 루트 reference 미확인)

언제 켜지고 무엇을 입력으로 받나?

description은 모델이 호출 여부를 판단할 때 참고하는 설명이다. 특정 문구와 정확히 일치해야 켜진다는 뜻은 아니다.

disable-model-invocation 같은 호출 제한 필드는 원문에 명시 없음이다. agents/openai.yaml에도 policy가 없다.49

상황에이전트의 행동
scan이 attack-path 단계에 있다scan별 위협 모델과 후보 집합을 쓴다. 입력 경로는 그대로 쓰고, 필요한 scan 산출물이 없으면 없다고 보고한다.10
사용자가 source에서 sink까지의 경로와 심각도 보정을 직접 요청한다(단독 분석)주어진 finding, 저장소, 위협 모델이나 보안 정책, 맥락을 쓴다. scan별 산출물은 필요 없다. 중요한 가정은 밝히고, 의미 있는 평가가 막힐 때만 빠진 맥락을 묻는다.10
Standard scan, Deep Scan worker자기 Standard workflow 안에서 경로를 평가하고 이 스킬을 호출하지 않는다.1112

2

경로는 어떻게 세우고 무엇을 보고하나?

  1. 공격자와 표면

    범위 안의 공격자, 영향받는 제품 표면, 진입점, 조작 입력, 보안 경계, 민감한 동작을 정한다. 저장소 근거와 공급된 관찰로 각 단계를 따라간다.5

  2. 통제와 반증

    관련 통제와 가장 강한 반증을 찾는다. 그것이 무엇을 확립하고 어떤 전제가 남는지, 주장한 경계를 정확히 넘는지 설명한다.13

  3. 영향과 정책

    사실에서 영향과 가능성을 평가하고 references/severity-policy.md로 최종 결정한다. scan이 심각도 rubric을 주면 reportable finding을 그것으로 채점하고 영향이 없는 후보는 ignore로 둔다. 사실, 심각도 보정, 최종 결정을 결과에서 구분한다.14

  4. 모든 후보 결정

    자격이 있는 후보마다 명시적 결정을 낸다. 무시하거나 deferred인 후보도 포함한다. 뒷받침된 인스턴스를 이웃 finding으로 바꾸거나 root-control 위치를 잃지 않는다.15

강제·금지내용
근거 없는 사슬뒷받침되지 않은 공격 사슬을 만들지 않는다. 배포나 공개 ingress 근거가 없는 것은 확신도를 낮추거나 사실을 미지로 둘 수 있을 뿐, 다른 근거가 받치는 finding을 깨지는 못한다.6
기준 보존심각도 정책은 확립된 사실에 적용한다. discovery를 다시 열거나 다른 공격 이야기로 바꾸지 않는다.163
설명 보존살아남은 finding과 suppress한 finding을 모두 설명할 만큼의 근거를 남긴다.16
출력 항목제목과 candidate, instance, ledger ID, 정확한 위치와 공격자에서 영향까지의 단계, references/attack-path-facts.md의 사실, 통제·반증·전제·증명 간극, 영향·가능성·보정된 심각도·최종 결정과 이유.16

공격 경로 사실 필드는 범위와 맥락, 공격 경로, 노출과 벡터, 신원과 전제, 영향, 통제와 반증, 불확실성, 결정이다. 알 수 없는 것은 중요하면 명시한다. 사실과 심각도·suppress 결정을 섞지 않는다.17

AWS Continuum에서 가져온 issue는 finding 증거의 source_data.evidence_artifacts를 읽는다. 시험 대상, 공격자 권한, 관찰된 효과를 주장한 경로와 맞춰 보고, 단계를 받치거나 반박하는 artifact ID와 관찰을 인용한다.18

보고 여부와 심각도는 어떤 정책으로 정하나?

심각도 정책은 경로, 범위, 반증을 세운 뒤 적용한다. 후보의 심각도 가설에서 출발해 저장소와 validation 근거가 뒷받침하는 영향, 가능성, 전제, 완화로 조정한다. 채점은 scan의 rubric을 쓰고 없으면 ../../../references/default-severity-rubric.md를 쓴다.3

상황결정
반증됐거나 의미 있는 보안 영향이 없는 버그ignore7
진짜 reportable finding인데 영향이나 가능성이 낮다버리지 않고 낮은 심각도로 보고한다.7
자기 자신에게만 영향이 있다, 달성 불가능하거나 매우 비현실적인 전제가 필요하다hard suppression7
특권, 운영자, 개발자, 물리 접근, 보호된 쓰기 경로가 전제다{caution:ignore} 단, 권한 상승 차이(delta)가 문제인 경우는 예외다.7

모드입력과 제출
Compact Workbench Diff(scanId 있음)list_codex_security_candidates({ scanId, cursor?, limit? })로 scan별 위협 모델과 검증된 후보 전체를 읽는다. reportable 또는 deferred인 validation 후보를 모두 분석하고 candidate 정체성과 기존 discovery, validation 필드를 보존한다. 모든 결정을 record_candidate_attack_paths({ scanId, attackPaths: [{ candidateId, attackPath }] }) 한 번으로 제출하고, 단계에 들어갈 후보가 없으면 attackPaths: []를 제출한다. 도구가 후보 순서를 보존한다. 이 결정이 단계 산출물 전부이며 중복 보고서, receipt, 수동 ledger는 만들지 않는다.21
다른 phase-based scan활성 workflow의 보고서와 receipt 경로를 쓴다. 단계에 들어온 후보마다 명시적 결정과 receipt(ID, 사실이나 정확한 증명 간극, 보고서 참조)가 있어야 한다. 무시한 후보도 살아남는 finding 집합에서 빼기 전에 기록한다.22
저장소 전체 또는 범위 지정 scandiscovery가 다듬은 finding 번호를 주지 않았더라도 reportable 또는 survives: yes인 validation closure 행을 포함한다. validation이 준 entrypoint, wrapper, root-control, sink, concrete-implementation 위치를 보존한다.22
