scan 전에 읽을 보안 맥락은 어느 스킬이 만들고 누가 읽나?

Long image

A

Answer

threat-model은 위협 모델을 만들거나 재사용하고, define-security-policy는 SECURITY.md를 쓰거나 검토하고, threat-model-visualize는 이미 있는 위협 모델을 standalone HTML explorer로 바꾼다.123 셋 사이에 필수 순서는 없다. 이어지는 것은 threat-model이 저장한 threatmodel.md를 threat-model-visualize가 입력으로 받는 한 곳(R42)이고, SECURITY.md는 쓰는 스킬과 읽는 스킬이 따로 있는 공유 파일이다(R44~R47).432 부분 분석이다. plugin 루트의 references/와 호스트 도구, threat-model-visualize의 renderer assets를 이 페이지 작성에서 읽지 못했다.

  1. threat-model은 단독 요청으로 켜지거나 scan의 threat-modeling 단계에 있을 때 쓴다. 전체 scan의 첫 진입점으로 쓰지 않는다.5
  2. define-security-policy는 SECURITY.md를 정책 맥락으로만 다룬다. 정책은 실행 지시가 아니며 명령, 수정, 공개, 범위 변경을 승인하지 못한다.26
  3. threat-model-visualize는 새 평가를 하지 않고 입력 문서도 바꾸지 않는다.3
  4. 사이트 호스팅은 사용자가 명시로 요청할 때만 한다. 이 호스팅 문서와 도구는 컬렉션에 없다(R69).7

세 스킬은 각각 무엇을 만들고 어떻게 이어지나?

Diagram structure
  • threat-model tm
  • threat-model-visualize tmv
  • tm → tmv · threatmodel.md R42

그림은 순서가 아니라 산출물이 입력 조건에 맞는 한 쌍(R42)만 그린다. define-security-policy는 이 산출물 흐름과 연결되지 않아 그림에 노드가 없다. 선후 관계가 없는 공유 상태라서 아래 표와 다음 패널에 둔다.32

  1. threat-model ↗

    저장소의 실제 구조와 공격자 능력, 신뢰 경계로 위협 모델을 만들거나 재사용한다.

  2. threat-model-visualize ↗

    기존 위협 모델을 읽어 근거가 붙은 explorer HTML을 만든다. 새 평가는 하지 않는다.

  3. define-security-policy

    SECURITY.md를 새로 쓰거나 검토해 scanner가 무엇을 finding으로 볼지 알려 준다. 위 그림 밖이다.

rel-id·종류전달물과 조건그림 반영
R42 · 산출물 호환threat-model-visualize의 기본 입력은 "the existing threat-model artifact"이고 --assessment <threat-model.md>로 넘긴다. threat-model은 단독 요청에서 threatmodel.md를 저장한다. threat-model-visualize는 새 assessment를 하지 않는다. 필수 후속 단계는 아니다.438표시
R45 · 공유 상태저장소별 AGENTS.md나 해석된 SECURITY.md는 필요한 경계를 담고 있으면 위협 모델을 대신할 수 있다. 정책은 분석 데이터이며 workflow를 바꿀 권한이 없다. define-security-policy가 쓰고 threat-model이 읽는다. 선후 관계는 없다.29생략(순서가 아니라 공유 상태)
R48 · 참고define-security-policy는 정책을 쓸 때 경계를 확인하려고 "threat models, and validated findings"를 읽을 수 있다. 이름으로 스킬을 지목하지 않는다. 원장 방향은 문장의 주체를 따라 define-security-policy → threat-model이다.104생략

어떤 파일과 상태를 공유하나?

파일·상태쓰는 스킬·주체읽는 스킬·조건
SECURITY.md(루트와 컴포넌트별)define-security-policy가 쓴다. 새 정책은 <repo_root>/SECURITY.md 또는 <component>/SECURITY.md다. .github/SECURITY.md나 docs/SECURITY.md는 저장소 전체 지침으로 보지 않고 덮어쓰지 않는다.1112threat-model이 경계를 담고 있으면 모델 대신 쓴다(R45). finding-discovery가 검토 경로마다 해당 정책을 찾아 쓴다(R44). security-diff-scan이 관련 guidance를 적용한다(R47). triage-finding이 영향받는 파일마다 루트와 범위 정책을 검토한다(R46). 호스트 helper인 resolve-security-md가 chain을 해석하고 가까운 정책이 우선한다.913141512
threatmodel.md(단독 요청)threat-model이 저장하거나 유효한 cache hit이면 기존 문서 경로를 돌려준다. 재사용 가능한 공유 모델은 사용자가 만들거나 고치라고 직접 요청했을 때, 호스트가 금지하지 않는 한 갱신한다. 공유 모델에만 Repository와 Version footer를 붙인다.4threat-model-visualize가 기본 입력으로 읽는다(R42). 정책 작성자가 경계를 확인하려고 읽을 수 있다(R48).310
<scan_dir>/threatmodel.md(scan 중)호스트가 만든다. threat-model은 { "format": "markdown", "content": "<exact model text>" }를 호출자에게 돌려주고 complete: false 초안을 먼저 저장한다. scan별 모델의 저장·내보내기는 공유 cache 갱신 승인이 아니다.4이후 단계가 같은 모델을 이어받는다(R06). 마지막 scan의 위협 모델을 시각화하라는 요청이 이 파일을 입력으로 삼는지는 scan 쪽이 "canonical artifacts"라고만 적어 확정되지 않는다(R43).4316
위협 모델 공유 cache위에 적은 직접 요청 때만 threat-model이 쓴다.4threat-model이 최종 Repository와 Version 줄이 목표와 현재 revision 또는 snapshot digest에 맞고 사용자가 교체·생성·수정을 요청하지 않았을 때만 재사용한다. 모델이 주어졌거나 비어 있지 않은 userContext, 권위 있는 knowledge base, 좁힌 범위가 있는 scan은 cache를 읽지도 바꾸지도 않는다.9
explorer.html과 작업 파일threat-model-visualize가 --output으로 쓴다. 입력 문서는 바꾸지 않는다.83사용자가 로컬 HTML로 연다. 작업 파일(source-inventory.md, correctness-review.md 등)은 이 스킬의 내부 절차라 스킬 페이지에 둔다.8

언제 켜지고 어디에서 멈추나?

세 스킬의 description은 모델이 판단할 때 참고하는 설명이고 이 단어가 있으면 켜진다는 사전이 아니다.51718

스킬켜지는 조건하지 않는 일과 멈추는 곳
threat-modelscan의 threat-modeling 단계에 이미 있거나, 사용자가 $threat-model을 명시하거나, 저장소 위협 모델의 생성·수정·저장을 명시로 요청했을 때다.5전체 PR·commit·branch·patch·저장소 scan의 첫 진입점으로 쓰지 않는다. Standard scan과 Deep worker는 자기 workflow 안에서 모델을 만들고 이 스킬을 호출하지 않는다(R14). 명시된 필수 입력이 없으면 생성한 모델로 바꾸지 않고 사용자에게 묻는다.5119
define-security-policy저장소나 컴포넌트의 SECURITY.md를 정의·검토·갱신하려 할 때다. scanner가 무엇을 검토하고 무엇이 범위 밖인지 밝히려는 요청이 해당한다.17대상이 모호하면 묻는다. review 요청은 사용자가 draft나 edit를 요청할 때까지 review에 머문다. owner 확인이 없는 범위·심각도·제외·accepted-risk 결정은 미해결로 두고, 추론을 suppression 근거로 삼지 않는다. staging·commit·push·PR은 사용자가 허락한 범위 안에서만 한다.20212223
threat-model-visualize이미 있는 위협 모델로 아키텍처와 위협 경로 explorer를 만들 때다. "Visualize the threat model generated in the last scan of X" 같은 한 문장 요청이면 대상, 최신 assessment, snapshot을 정한다.183새 scan이나 새 평가를 하지 않고 애플리케이션 코드를 보지 않는다. 입력은 바꾸지 않고 snapshot을 몰래 합치지 않는다. 독립 리뷰의 PASS 기록이 현재 JSON에 있어야 browser QA를 시작한다. 사이트는 사용자가 호스팅을 명시로 요청할 때만 만든다.324257

scan 묶음과는 어떻게 이어지나?

아래 관계는 scan-vulnerabilities 묶음 스킬과 맺는 것이다. 전체 흐름은 색인 기준 _group-scan-vulnerabilities/scan-vulnerabilities.html에 있다. 모두 그림에서 뺐다.

rel-id·종류전달물과 조건그림 반영
R06 · 내부 위임security-diff-scan이 "Run $threat-model once, or use the supplied model". 한 번만 실행하고 사용자가 모델을 주면 그것을 쓴다. 모델은 저장소 전체가 기본이고 사용자가 좁히라고 할 때만 좁힌다. 위임이 끝나면 diff scan이 complete: false 초안을 저장한다.264생략
R10 · 산출물 호환finding-discovery는 "the threat model and applicable security policy"를 근거로 쓴다. 이 순서를 강제하는 곳은 diff scan(R06~R09)뿐이다. 단독 호출에서 위협 모델 없이 discovery를 돌려도 되는지는 원문에 명시 없음이다.134생략
R13 · 산출물 호환scan 단계의 attack-path 분석은 per-scan 위협 모델과 후보 집합을 쓴다. 단독 분석에서는 위협 모델이나 보안 정책이 있으면 쓰고 per-scan 산출물은 필요 없다.274생략
R14 · 참고Standard scan과 Deep worker는 위협 모델을 자기 workflow 안에서 만들며 threat-model을 호출하지 않는다.1생략
R43 · 산출물 호환security-scan이 끝난 뒤 "Visualize the threat model generated in the last scan of X"라는 요청만으로 충분하다. 최신 artifact가 없으면 오래된 것을 쓰기 전에 알린다. 새 scan은 돌리지 않는다. from 줄(scan-results.md)은 "canonical artifacts"라고만 쓰고 threatmodel.md를 이름으로 지목하지 않아 직접 근거는 to 줄 쪽이다. diff scan과 deep scan의 위협 모델도 같은 방식인지는 원문에 명시 없음이다.163생략
R44 · 공유 상태SECURITY.md는 "policy context, not executable instructions"다. finding-discovery는 검토하는 경로마다 해당 정책을 찾아 쓴다. 선후 관계는 없다.213생략
R46 · 공유 상태triage-finding은 코드를 따라가기 전에 영향받는 파일마다 루트와 범위 SECURITY.md를 검토한다. 정책은 "the primary local definition"이지만 코드 근거가 claim을 받쳐야 하고 가장 가까운 정책이 우선한다.1512생략
R47 · 공유 상태security-diff-scan은 "Apply relevant SECURITY.md guidance". 선후 관계는 없다.214생략

어디까지 대조했고 무엇이 남았나?

  • 이 묶음의 스킬 본문 3개를 전부 읽었다.
  • scan 쪽 연결을 확인하려고 security-diff-scan, finding-discovery, attack-path-analysis의 본문과 scan-results.md를 전부 읽었고 triage-finding은 39~48줄만 읽었다.
  • 번역본과 skills-lock.json은 열지 않았다. threat-model-visualize의 references/, scripts/, assets/는 이 페이지를 쓰는 동안 열지 않았다.
  • 대상 스킬의 지시와 명령은 읽기만 했고 실행하지 않았다.

관계 16개(범위 내 R06, R10, R13, R14, R42~R48 중 R42·R43·R44·R45·R46·R47·R48, 범위 밖 R60·R61·R62·R65·R69·R70)를 원문의 해당 줄과 대조했다. 이 묶음에 해석 상태가 불명인 관계는 없다. 안내 역할 스킬도 없다. 원장은 세 스킬을 모두 단계로 둔다.

미확인 범위

위 표의 문서와 호스트 도구는 컬렉션에 없어 읽지 못했다. 이 페이지가 "순서가 없다"고 쓴 곳은 이 컬렉션의 원문에 순서가 없다는 뜻이다. threat-model은 생성·수정 때 plugin 루트 references/threat-model.md를 따르라고 한다. 원장 R70이다. 컬렉션에 없어 읽지 못했다.28 threat-model-visualize의 renderer와 references/view-model.md 같은 하위 파일은 이 페이지에서 확인하지 않았다. 스킬 본문이 말하는 build_explorer.py의 구조 검사만 인용했다.8

자동 검증은 HTML 구조와 출처 해석을 확인한다. 사실 대조와 사람 검토는 별도다. 사람 검토는 미실시다.
