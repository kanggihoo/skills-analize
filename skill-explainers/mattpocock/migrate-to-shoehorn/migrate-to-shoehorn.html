migrate-to-shoehorn 스킬은 에이전트를 어떻게 바꾸나

Long image

A

Answer

migrate-to-shoehorn을 쓰면 에이전트는 테스트 파일의 as 타입 단언을 @total-typescript/shoehorn 함수로 바꾼다. 테스트에 일부 데이터만 넘겨도 타입 검사를 통과하게 하는 것이 목적이다.1

  1. as Type은 fromPartial()로, as unknown as Type은 fromAny()로 바꾼다.2
  2. 테스트 코드에만 쓴다. 제품 코드에는 절대 쓰지 않는다.1
  3. 시작 전에 사용자에게 세 가지를 묻는다. 끝나면 타입 검사로 확인한다.2

1

언제 켜지나

frontmatter에 disable-model-invocation이 없다. 그래서 모델이 description을 보고 스스로 켤 수 있다.3 agents/openai.yaml에도 policy 블록이 없다.4

description이 그리는 상황은 사용자가 shoehorn을 언급할 때, 테스트의 as를 없애고 싶을 때, 테스트용 일부 데이터가 필요할 때다. 이 설명은 판단 참고용이다.

2

무엇을 무엇으로 바꾸나

위 diff는 원문의 두 예시를 한데 모은 것이다.5

함수쓰임
fromPartial()일부만 채운 데이터를 타입 검사를 통과시키며 넘긴다6
fromAny()일부러 틀린 데이터를 넘긴다. 자동 완성은 유지된다6
fromExact()객체 전체를 강제한다. 나중에 fromPartial로 바꿔 끼울 수 있다6

원문이 꼽는 as의 문제는 세 가지다. 쓰지 않도록 길들여져 있고, 대상 타입을 손으로 적어야 하고, 일부러 틀린 데이터에는 as unknown as를 겹쳐 써야 한다.1 속성이 20개 넘는 Request에서 body.id만 필요한 경우가 대표 예시다.7

3

어떤 순서로 진행하나

  1. 요구 질문 ↗

    사용자에게 묻는다. 문제를 일으키는 as가 어느 테스트 파일에 있나, 일부 속성만 중요한 큰 객체인가, 오류 시험용으로 일부러 틀린 데이터가 필요한가.

  2. 설치 ↗

    npm i @total-typescript/shoehorn을 실행한다.

  3. 대상 찾기 ↗

    grep -r " as [A-Z]" --include="*.test.ts" --include="*.spec.ts"로 찾는다.

  4. 치환 ↗

    as Type은 fromPartial(), as unknown as Type은 fromAny()로 바꾸고 import를 더한다.

  5. 타입 검사 ↗

    타입 검사를 돌려 확인한다. 이것이 완료 조건이다.

순서와 문구는 Workflow 절의 확인 목록을 따른다.2 타입 검사 명령은 원문에 명시 없음.

  • 판정: 설치 명령에 -D가 없어서 테스트 전용 라이브러리가 일반 의존성으로 들어간다. 패키지 관리자도 npm으로 고정돼 있다.8
  • 판정: 검색 패턴은 *.test.ts와 *.spec.ts만 본다. .test.tsx 파일이나 소문자로 시작하는 타입의 단언은 찾지 못한다.2
  • 판정: fromExact()는 표에만 있고 언제 바꿔 넣으라는 치환 패턴은 없다.6

이 분석의 범위와 한계

  • 읽은 파일: SKILL.md, agents/openai.yaml. 두 파일 모두 원본이다.
  • 제외한 파일: SKILL.KO.md. 원본이 있는 번역본이다.
  • 원문 비교: 다른 컬렉션에 이름이 같은 스킬이 없다(원장 기준). 원장에 이 스킬의 관계 행은 없다.
  • 실행하지 않았다. 질문·설치·치환은 모두 지시상 동작이다. shoehorn 라이브러리 자체의 동작은 확인하지 않았다.
  • 분석 중 바뀐 파일: 없음.

확인하지 못한 것

사용자 답에 따라 범위를 어떻게 좁히는지, 타입 검사가 실패하면 되돌리는지는 원문에 명시 없음. 커밋 지시도 없다.
