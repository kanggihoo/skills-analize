Answer

이 묶음의 다섯 스킬은 UI 조각 하나를 다룰 때 각자 다른 질문에 답한다. 실제로 다음 스킬을 부르라고 적힌 곳은 animate가 pick-ui-library를 부르는 한 곳뿐이다(r02). 나머지는 "그건 다른 스킬의 몫"이라고 경계만 긋는다.12

  1. animate는 작업에 애니메이션이 아니라 toast, drawer 같은 컴포넌트가 필요하면 멈추고 pick-ui-library를 호출하라고 한다. 그런데 pick-ui-library는 disable-model-invocation: true라서 모델이 스스로 켤 수 없다.13
  2. pick-ui-library가 toast에 Sonner를 추천하고, ask-sonner가 그 Sonner의 사용법을 답한다. 두 스킬은 서로 이름을 부르지 않으므로 이 연결은 판정이다(r22).45
  3. prototype(여러 버전 만들기)과 break-ui(최악 데이터로 깨 보기)는 다른 스킬로 넘기지 않는다. 서로를 역할 구분으로만 가리킨다(r16, r21).62

  1. 무엇이 필요한가? ↗

    판정: 이 갈림길은 각 스킬의 description을 모아 그린 것이다. 스킬들이 이런 분기 규칙을 함께 정해 두지는 않았다.

  2. animate ↗

    애니메이션을 직접 구현한다. 작업이 toast·drawer·command menu·dropdown 같은 컴포넌트면 멈추고 pick-ui-library를 호출하라고 한다(r02).

  3. pick-ui-library ↗

    사용자가 말한 라이브러리 이름이 아니라 작업을 보고, package.json부터 확인한 뒤 정해진 목록에서 고른다. 명시 호출만 된다.

  4. ask-sonner ↗

    Sonner의 설치, toast() 호출, 스타일, 흔한 고장을 답한다. pick-ui-library와의 연결은 추론이다(r22).

  5. prototype ↗

    서로 다른 방향의 버전 3개(최대 5개)를 화면 선택기 뒤에 두고, 사용자가 고르면 나머지를 지운다. 명시 호출만 된다.

  6. break-ui ↗

    값마다 최악의 데이터를 만들어 Demo data / Worst case toggle 뒤에 두고, 깨진 곳과 고칠 방법을 보고한 뒤 멈춘다.

근거: r02는 animate 81줄,1 pick-ui-library의 작업 방식은 21~22줄,7 Sonner 추천은 34·80줄,48 prototype의 버전 수와 정리는 52·31줄,910 break-ui의 toggle과 멈춤은 74·131줄이다.1112

유일한 넘김은 왜 막힐 수 있나

r02: 의무형 넘김과 명시 호출 제한이 부딪친다

animate는 컴포넌트가 필요하면 "멈추고 pick-ui-library를 호출하라"고 적는다.1 pick-ui-library의 frontmatter는 disable-model-invocation: true이고, description은 "명시적으로 부를 때만 실행된다"고 한다.3 두 원문 사이에 우선순위는 적혀 있지 않다. 판정: 에이전트가 이 지점에서 할 수 있는 일은 사용자에게 /pick-ui-library를 부르라고 알리거나, 목록 없이 판단하는 것이다. 어느 쪽인지는 원문으로 정해지지 않는다.
