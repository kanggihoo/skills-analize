## 제가 하는 일

밀도 높고 전문 용어가 많은 기술 문서를 누구나 이해할 수 있는 설명으로 바꿉니다. 어려운 기술 개념은 개발자, IT 관리자, 마케터, 학생, 취미 개발자 등 누구에게나 접근 가능해야 합니다.

**주요 기능:**

- **명확성 문제 분석** — 전문 용어, 가정, 불명확한 논리, 누락된 맥락을 식별합니다
- **before/after 비교 생성** — 원본과 단순화 버전을 문제 분석과 함께 나란히 보여 줍니다
- **기술 기반 비유 제작** — 설명을 흐리지 않으면서 명확하게 해 주는 친숙한 기술 비유를 사용합니다
- **"왜"를 설명** — 세부 사항을 다루기 전에 가치, 사용 사례, 맥락을 먼저 설명합니다
- **흔한 함정 짚기** — 독자들이 자주 겪는 오해를 직접 다룹니다
- **혼합 독자층에 맞춘 계층화** — 초보자와 전문가를 동시에 고려합니다
- **기술적 정확성 유지** — 단순화하는 것은 언어이지 사실이 아닙니다

## 철학

기술 문서는 흔히 명확성보다 정밀성을 우선합니다. 맥락 없는 전문 용어, 빠진 "왜", 명시되지 않은 가정, 그리고 "simply", "just", "obviously" 같은 생색내는 단순화가 그렇습니다. ELI5는 다음 방식으로 이 문제를 해결합니다.

1. **세부 사항보다 맥락 먼저** — "무엇"과 "어떻게"보다 "왜"와 "언제"로 시작합니다
2. **기술 기반 비유** — 지나치게 단순한 일상 사물이 아니라 친숙한 기술에 뿌리를 둔 비유를 사용합니다. 비유가 어디서 깨지는지도 밝힙니다.
3. **계층화된 설명** — 여러 진입점을 둡니다: 쉬운 언어 → 자세한 설명 → 기술적 깊이
4. **가치 우선 프레이밍** — 기능과 설정보다 이점과 해결하는 문제를 앞세웁니다
5. **명시적인 함정** — 흔한 오해를 직접 다룹니다
6. **친숙한 연결** — 새로운 아이디어를 독자가 이미 아는 개념과 이어 줍니다

**독자:** 독자는 똑똑하지만 특정 맥락이 부족합니다. 가장 낮은 공통분모에 맞춰 쓰지 마세요. 이 도메인에 익숙하지 않은 똑똑한 사람을 전제로 쓰세요.

**정확성은 타협할 수 없습니다:** 단순화는 더 명확한 언어를 뜻하지, 정밀도를 낮추는 것을 뜻하지 않습니다. 단순화된 설명이 기술적으로 틀리게 된다면 생략하지 말고 뉘앙스를 더하세요.

**이미 잘 작동하는 것은 보존합니다:** 원본 텍스트가 기술적으로 정확하고 대상 독자에게 명확하다면, 어조나 친근함 때문에 다시 쓰지 마세요. 사실 오류, 실제 모호함, 또는 실질적인 명확성 문제가 있을 때만 수정합니다. 올바른 문장을 다시 쓰면 부정확함이 끼어들 위험이 있습니다. 그럴듯하게 들리지만 잘못된 메커니즘을 설명하는 문장은 전문 용어보다 더 나쁩니다.

**새로운 정보는 모두 사실 확인합니다:** 원본 문서에 없던 설명, 비유, 맥락을 추가한다면 포함하기 전에 **정확성을 검증해야 합니다**. 기술적 정의, 동작 설명, 프로토콜 세부 사항, 그리고 무엇이 어떻게 동작하는지에 대한 모든 주장에 적용됩니다.

이는 **Cloudflare 고유 구현에 특히 중요합니다**. Cloudflare는 업계 표준 동작에서 벗어날 수 있습니다(예: Workers가 요청 수명 주기를 처리하는 방식은 전통적인 서버리스 플랫폼과 다르며, Cloudflare CDN의 캐시 로직은 다른 CDN과 다릅니다). Cloudflare 제품에 일반적인 업계 지식이 적용된다고 가정하지 마세요. Cloudflare 고유 동작에 대한 설명을 추가할 때는 다음을 따르세요.

1. **원본 문서와 대조해 검증** — Cloudflare 제품이나 기능의 동작을 설명하기 전에 이 저장소의 기존 문서와 교차 확인하세요.
2. **출처 인용** — 새로운 정보(설명, 비교, 구현 세부 사항)를 도입할 때는 그 주장을 뒷받침하는 특정 문서 페이지, API 레퍼런스, 또는 권위 있는 출처를 포함하세요. 인라인 링크나 각주를 사용합니다.
3. **불확실성 표시** — 기존 문서에서 주장을 검증할 수 없다면 사실로 제시하지 말고, 작성자가 확인하도록 명시적으로 표시하세요.
4. **제품 용어를 맥락에서 검증** — Cloudflare 제품 용어는 특정한 의미를 가집니다. "Full setup"은 Cloudflare를 유일한 DNS 제공자로 두는 것이 아니라 Cloudflare의 권한 있는 네임서버를 사용하는 것을 뜻합니다. 링크 텍스트의 "Global network"는 일반적인 인프라 설명이 아니라 관례적으로 네트워크 마케팅 페이지를 가리킵니다. 확립된 Cloudflare 용어(설정 유형, 제품명, 마케팅 문구)를 사용할 때는 그 용어가 존재하는지뿐 아니라, 기존 문서와 같은 맥락에서 같은 의미로 쓰이는지 검증하세요. 실제 용어를 잘못된 맥락에 적용하는 것은 지어낸 용어를 쓰는 것만큼 오해를 부릅니다.

**어조:** 명확하고, 직접적이며, 전문적으로. 생색내지 않고, 지나치게 가볍지 않으며, 과장하지 않습니다. "simply", "just", "obviously", "clearly", "as everyone knows", "it's easy to"는 쓰지 마세요.

## 사용 시점

넓거나 혼합된 독자층을 대상으로 하는 콘텐츠에 이 스킬을 사용하세요. 모든 검토에 필요한 것은 아닙니다.

**적합한 대상:**

- **보안 및 네트워킹 문서** (예: DDoS 보호, WAF, Magic Transit, Tunnel) — 독자에는 네트워킹 배경이 깊지 않은 IT 관리자, 마케터, 또는 의사결정권자가 자주 포함됩니다
- **시작하기 및 개요 페이지** — 독자가 아직 도메인 맥락을 쌓지 않은 첫 접점 콘텐츠입니다
- **비개발자를 대상으로 한 개념 페이지** — 소프트웨어 엔지니어를 넘어선 독자에게 "무엇"과 "왜"를 설명하는 페이지입니다
- **제품 간 문서** (Zero Trust, SASE) — 여러 도메인에 걸쳐 있고 다양한 독자를 끌어들입니다

**다음의 경우에는 사용하지 않거나 우선순위를 낮추세요:**

- **개발자 중심 API 및 SDK 레퍼런스** (예: Workers, D1, R2, Durable Objects, KV) — 독자는 프로그래밍 개념, 데이터베이스 용어, API 규칙을 알 것으로 기대되는 개발자입니다
- **개발자를 대상으로 한 코드 중심 튜토리얼** — 독자는 스스로 선택해 들어오며 필요한 선행 지식을 이미 갖추고 있습니다
- **순전히 기술적인 독자를 위한 설정 레퍼런스** — 매개변수 표, CLI 레퍼런스, 스키마 문서처럼 전문 용어 자체가 내용인 경우입니다

**그 밖의 경우에는 판단하세요.** 이렇게 물어보세요: "이 페이지를 읽는 합리적인 독자가 이 용어들을 이미 알고 있을까?" 그렇다면 이 스킬은 가치를 거의 더하지 못합니다. 반대로 다음 조건이 해당된다면 이 스킬이 상당한 가치를 줄 수 있습니다.

- 콘텐츠가 사전 지식을 너무 많이 전제하는 경우
- 전문 용어와 약어가 설명되지 않은 경우
- 문서가 "왜"를 설명하지 않고 "어떻게"로 넘어가는 경우
- 독자가 무엇을 언제, 어디에서 써야 하는지 이해하기 어려워하는 경우
- 어떤 부분이 콘텐츠를 헷갈리게 만드는지 피드백을 원하는 경우

## 작업 방식

### 워크플로

**1. 파일 경로 입력**

```bash
/eli5 path/to/documentation.md
```

지원 형식: `.md`, `.mdx`

**2. 콘텐츠 읽기 및 파싱**

파일을 읽고, 섹션을 감지하고, 구성 방식을 분석한 뒤 콘텐츠 유형을 판별합니다.

**콘텐츠 유형:** Overview(개요), Concept(개념), How To(방법), Reference(레퍼런스), Tutorial(튜토리얼)

**판별 신호:**

- **Overview:** 제목에 제품명, 기능 목록, 이점 문구, "Perfect for..." 섹션
- **Concept:** "What is...", "How it works", 개념 설명, "Why it matters"
- **How To:** 번호가 매겨진 단계, "Prerequisites", 제목의 동작 동사, 검증 섹션
- **Reference:** 표, 매개변수 목록, 기술 사양, 데이터 타입
- **Tutorial:** "What you'll build", 단계별로 진행되는 코드 예시, "Time required"

판별 후에는 콘텐츠 유형을 확인받습니다. 유형마다 다른 전략이 필요합니다.

| 유형 | 전략 |
|------|----------|
| Overview | 문제 → 해결책 → 이점 |
| Concept | 비유 → 쉬운 설명 → 기술적 세부 사항 |
| How To | 맥락 → 여러 경로의 단계(Dashboard + API) |
| Reference | 사용 사례 중심 구성 + 두 단계 설명(쉬운 설명과 기술 설명) |
| Tutorial | 코드 설명을 곁들인 점진적 복잡도 |

**3. 보강 제약 적용**

보강하기 전에 다음 한도를 지키세요. 1.5~2배 확장을 목표로 합니다(5~10배가 아닙니다). 기존 콘텐츠를 대체하지 말고 맥락으로 보강하세요.

**문서당 최대 추가량:**

- **문제/가치 진술:** 인라인으로 2~4문장(별도 섹션이 아님)
- **사용 사례 예시:** 주요 개념당 1~2개, 각 5~15줄
- **인라인 "왜":** 기능을 소개할 때 1~2문장
- **전문 용어 정의:** 처음 등장할 때 짧게 인라인으로
- **문제 해결:** 치명적인 문제 1~2개만
- **테스트:** 검증 명령어 최대 3~5개

**보존:** 기존 콘텐츠, 구조, 다이어그램, 코드 예시, 컴포넌트 사용, 흐름 전부.

**추가하지 않는 것:** 별도의 개념 설명 섹션(본문 앞에 오는 것), 다이어그램 주석, 개념당 여러 예시, 포괄적인 테스트/문제 해결 섹션, 모범 사례 섹션, 새로운 Dashboard 또는 API 경로.

**Dashboard 대 API 경로 감지:** 경로가 하나만 있다면 제안 사항에 기록하고 작성자에게 확인을 요청하세요. 없는 경로를 새로 만들지 마세요.

**4. 단순화할 섹션 선택 요청**

다음 옵션을 제시하고 응답을 기다립니다.

- **모든 섹션** — 문서 전체를 처리합니다
- **특정 섹션** — 줄 번호와 함께 감지된 섹션 중에서 고릅니다
- **가장 복잡한 섹션 자동 감지** — 전문 용어 밀도와 가정 빈도로 우선순위를 정합니다
- **사용자 지정 범위** — 줄 번호 또는 섹션 이름을 지정합니다

**5. 선택된 섹션 분석**

각 섹션에서 다음을 식별합니다.

- **전문 용어** — 설명되지 않은 용어, 정의되지 않은 약어, 이중 의미를 가진 용어
- **가정** — 명시되지 않은 선행 조건, 설명 없이 언급된 개념, 건너뛴 기초 단계
- **불명확한 논리** — 흐름 문제, 빠진 전환, 밀도 높은 단락, 불명확한 계층 구조
- **맥락 공백** — 빠진 "왜", 없는 사용 사례, "언제 이것을 쓰는가"의 부재

**6. 용어 추출**

용어집 정의나 상호 링크가 필요할 수 있는 모든 용어를 중복 없이 모읍니다.

- **정의되지 않은 기술 용어** — 설명 없이 쓰인 도메인 특화 단어
- **약어** — 처음 등장할 때 풀어 쓰지 않은 약어
- **제품/기능 이름** — 문서 링크가 없는 특정 제품, 서비스, 기능에 대한 언급
- **연결할 가치가 있는 개념** — 다른 곳에 전용 문서 페이지가 있지만 링크되지 않은 용어

각 용어에 대해 용어, 등장 위치(줄 번호), 문맥 내 정의 여부, 제안 조치(용어집 툴팁 추가, 상호 링크 추가, 인라인 정의 추가)를 보고합니다.

**GlossaryTooltip 품질 게이트:** 어떤 용어에 대해 GlossaryTooltip을 제안하기 전에, 실제 용어집 정의(`src/content/glossary/`)를 읽으세요. 다음 기준으로 평가합니다.

- **정의가 정확한가?** 용어집 항목이 모호하거나, 오래되었거나, 기술적으로 부정확하다면 링크하지 말고 개선이 필요하다고 표시하세요. 잘못된 툴팁은 툴팁이 없는 것보다 나쁩니다.
- **정의가 주변 문장과 중복되는가?** 툴팁이 붙는 문장과 거의 같은 단어를 반복한다면 건너뛰세요. 툴팁은 새로운 이해 없이 시각적 잡음만 더합니다.
- **정의가 단독으로 성립하는가?** 독자는 툴팁을 단독으로 봅니다. 용어집 항목이 다른 맥락에서만 이해되거나 자체 전문 용어를 쓴다면 링크하지 말고 표시하세요.

용어집 항목이 이 검사 중 하나라도 통과하지 못하면, "Add glossary tooltip" 대신 "Flag glossary entry for review — [reason]"이라는 조치와 함께 용어 색인에 보고하세요.

용어 색인은 항상 출력에 포함합니다. 조치가 필요한 용어가 없다면 그 사실을 명시하세요.

**7. 비교 생성**

다음 내용을 담은 비교 결과를 만듭니다.

- **원본 콘텐츠**를 정확히 보존

**적대적 검토 프롬프트 시작**

**원본 파일:** `[original file path]`
**제안된 변경 사항:** `[full ELI5 output — the simplified/enhanced content]`

두 파일을 주의 깊게 읽으세요. 당신의 임무는 **제안된 변경 사항만** 검토하는 것입니다. 원본 파일은 이미 진술된 내용과 새로 도입된 내용을 구분하기 위한 기준선입니다.

### 무엇이 주장으로 간주되는가

독자가 합리적으로 의문을 제기할 수 있는 제안된 변경 사항의 모든 진술은 주장입니다.

- 기술적 동작 ("Workers supports up to 128 MB of memory")
- 비교 ("faster than alternative X")
- 수치, 한도, 기본값, 할당량
- 제품, 프로토콜, 표준이 어떻게 동작하는지에 대한 진술
- 단순화된 메커니즘 설명 — 단순화 과정에서 추가된 "how it works" 설명
- 유추와 비유 — 1:1 대응 주장. "X works like Y"는 대응되는 동작이 실제 X의 동작과 일치해야 합니다
- 새로 추가된 맥락 — 원본에 없던 "왜", "언제 이것을 쓰는가", "어떤 문제를 해결하는가" 식의 프레이밍
- Cloudflare 제품 동작에 관한 모든 주장

의견, 문서 자체가 만든 정의, 절차 단계("Select **Save**")는 주장이 아닙니다.

### ELI5 특화 중점 영역

문서가 단순화되었을 때 가장 위험한 범주입니다. 이를 우선하세요.

1. **단순화된 메커니즘 설명** — 단순화 과정에서 원본에 없던 "how it works" 설명. 가장 높은 위험을 지닙니다. 그럴듯하게 들리지만 잘못된 메커니즘을 설명하는 것은 원래의 전문 용어보다 나쁩니다. 이 저장소의 원본 문서와 대조해 실제 메커니즘을 검증하세요.

2. **오해를 부르는 뉘앙스** — 완전히 틀리지는 않지만 중요한 뉘앙스를 평면화해 잘못된 멘탈 모델을 만드는 진술. 예: "Cloudflare generates a `robots.txt` file that instructs AI crawlers to stay away from your content"는 오해를 부릅니다. `robots.txt`는 전면 차단이 아니라 경로별 allow/disallow 메커니즘입니다. 이 문장은 크롤러가 *어디로* 가도 되고 가면 안 되는지를 명시한다는 사실을 생략합니다. 단순화가 의미 있는 구분을 잃는 모든 진술을 표시하세요.

3. **새로운 주장** — 단순화 과정에서 추가되었고 원본 문서에 없던 설명, 맥락, 프레이밍. 새로운 정보마다 인용이 필요합니다. 원본이 "zones pair with resolver policies"라고 했는데 단순화가 "based on source IP, user identity, or domain"을 추가했다면, 세 가지 선택자가 모두 실제로 지원되는지 검증하세요.

4. **Cloudflare 고유 동작** — Cloudflare 제품에 업계 표준 동작이 적용된다고 가정하지 마세요. Cloudflare 구현은 일반적인 방식과 자주 다릅니다(예: Workers 요청 수명 주기 대 전통적인 서버리스, Cloudflare CDN 캐시 로직 대 다른 CDN, Cloudflare Tunnel 상태 확인 방식 대 일반적인 상태 확인 패턴). 이 저장소의 `src/content/docs/`에 있는 실제 문서와 대조해 모든 Cloudflare 고유 주장을 검증하세요.

5. **범주를 넘는 과잉 일반화** — 단순화가 "all records", "the IP address"(단수), "every request"라고 말할 때 그 주장이 실제로 보편적으로 적용되는지 검증하세요. DNS 레코드 타입(A, AAAA, CNAME, MX, TXT, NS)은 프록시 규칙이 다릅니다. Cloudflare는 하나가 아니라 여러 anycast IP를 반환합니다. 프로토콜 동작, 플랜 수준 기능, 설정 기본값은 레코드 타입, 플랜, 제품 등급에 따라 자주 달라집니다. 수량사("all", "every", "any")와 관사("the"가 단수를 암시하는 경우)가 정확한지 확인하세요. A 레코드에 참인 진술이 MX 레코드에는 거짓일 수 있고, Enterprise에서 가능한 기능이 Free에는 없을 수 있습니다.

### 검토 절차

1. **추출** — 제안된 변경 사항의 모든 주장을 나열하세요. 원본에서 변경 없이 옮겨진 주장도 포함합니다. 원본이 틀렸다면 단순화는 그 오류를 물려받은 것입니다.
2. **출처 확인** — 각 주장에 대해 이 저장소의 문서(`src/content/docs/`)를 검색해 가장 강력한 인용을 찾으세요.
   - 이 저장소에 있는 기존 문서 페이지 — 우선 사용하며 파일 경로를 씁니다
   - 공개된 Cloudflare 블로그 글, 변경 로그, 공지
   - RFC 또는 프로토콜 명세 — Cloudflare가 아닌 주장에 사용
   - 주장이 원본 파일에 그대로 있었다면 "present in original — `[file path]`:[line number]"로 인용합니다
3. **뉘앙스 평가** — 출처가 있는 각 주장에 대해 제안된 변경 사항의 문장이 출처의 내용을 정확히 나타내는지 확인하세요. 주장에 출처가 있더라도 한정어를 생략하거나, 조건을 평면화하거나, 출처가 뒷받침하는 것보다 넓은 적용 가능성을 암시하면 여전히 오해를 부를 수 있습니다.
4. **표시** — 문제마다 심각도를 표시하세요.
   - **critical** — 주장이 페이지의 목적에 핵심적이며, 틀리거나 부정확하면 독자를 오도할 수 있습니다.
   - **high** — 주장이 눈에 띄지만 핵심 요지는 아닙니다. 부정확하면 신뢰를 떨어뜨립니다.
   - **medium** — 주장이 부차적이지만 여전히 검증 가능합니다.
   - **low** — 주장이 사소하거나 널리 받아들여지는 상식입니다.
5. **보고** — 다음 형식으로 결과를 제시하세요.

| # | 주장 (정확한 텍스트) | 출처 | 상태 |
|---|---|---|---|
| 1 | "Workers KV supports keys up to 512 bytes" | `src/content/docs/kv/api/write-key-value-pairs.mdx` | ✅ sourced |
| 2 | "Latency is under 50 ms globally" | — | ❌ unsourced (high) |
| 3 | "instructs crawlers to stay away from your content" | `src/content/docs/bots/robots-txt.mdx` — source says per-path allow/disallow, not blanket block | ⚠️ misleading (critical) |
| 4 | "zones pair with resolver policies" | present in original — `path/to/file.mdx:34` | ✅ sourced (original) |

## 결정 프레임워크

**용어를 단순화해야 할까?**

- **대체하거나 설명하기** — 도메인 특화 전문 용어이고, 대부분의 독자가 모르며, 더 단순한 용어도 똑같이 정확할 때
- **유지하되 정의하기** — 독자가 배워야 할 업계 표준이고, 더 단순한 정확한 용어가 없으며, 용어가 자주 등장할 때

**콘텐츠를 추가해야 할까?**

- **예** — "왜"가 빠져 있고, 사용 사례가 없으며, 흔한 오해를 다루지 않는 경우
- **아니요** — 원본이 이미 명확하거나, 추가해도 가치 없이 분량만 늘어나거나, 독자가 맥락에서 추론할 수 있는 경우

- **아니요** — 대상 독자가 원인에서 결과를 추론할 수 있을 때. 예를 들어 네트워킹 독자에게 "blocking health checks"는 "which means Cloudflare may consider your tunnels unhealthy"라고 덧붙일 필요가 없습니다. 도메인 전문성을 신뢰하세요.
- **예** — 결과가 눈에 띄지 않거나, 직관에 반하거나, 독자에게 점들을 연결할 도메인 지식이 실제로 없을 때에만

**GlossaryTooltip을 추가해야 할까?**

- **예** — 용어집 정의가 정확하고, 문장이 이미 말하는 것 이상의 정보를 더하며, 추가 맥락 없이 단독으로 성립할 때
- **아니요** — 용어집 정의가 모호하거나, 기술적으로 부정확하거나, 주변 문장과 거의 같을 때. 대신 용어집 항목을 검토 대상으로 표시하세요.
- **아니요** — 같은 단락에서 용어가 이미 인라인으로 명확히 정의되어 있을 때

**용어의 동의어나 별칭을 추가해야 할까?**

- **드물게.** 명백히 중복되거나 주제에서 벗어난 경우에만 합니다. 주의 문구, 정확성을 위한 한정어, 보안 경고는 절대 제거하지 마세요.

원래 문장이 사실적으로 정확하고 구조적으로 건전하다면, 더 따뜻하거나 단순하게 들리도록 다시 쓰지 마세요. 재작성은 기계적인 부정확함을 만들 위험이 있습니다. 구체적인 문제(잘못된 사실, 모호한 지시어, 정의되지 않은 용어, 깨진 논리)가 있는 문장만 손대세요.

**2. 독자가 추론할 수 있는 결과 연쇄 추가하기**

대상 독자가 이미 인과 관계를 이해하고 있다면 "If X happens, then Y, which causes Z"라고 풀어 쓰지 마세요. 예: 네트워크 엔지니어에게 차단된 상태 확인이 터널을 비정상 상태로 만든다고 말하는 것은 뻔한 이야기입니다. 물어보세요: "이 페이지를 읽는 합리적인 독자가 이 결과를 이미 알고 있을까?" 그렇다면 생략하세요.

**3. 동의어 주석("also called X") 추가하기**

개념이 같은 문장에서 이미 동작으로 정의되어 있다면 "also called 'default deny'"나 비슷한 별칭을 덧붙이지 마세요. 정의는 하나면 충분합니다. 동의어를 쌓는 것은 이해를 더하지 않고 잡음만 만듭니다.

**4. 문서에서 수사적 질문 쓰기**

예시 목록을 질문으로 바꾸지 마세요("VPN, NTP, 또는 데이터베이스 서비스를 운영하십니까?"). 예시는 예시로 진술하세요. 문서는 대화가 아닙니다.

**5. 상호 보완적인 기능이 서로 배타적인 것처럼 암시하기**

한 기능이 다른 기능을 대체하는 것처럼 암시하는 표현("rather than writing rules from scratch" 같은)을 추가하지 마세요. 두 기능이 함께 쓰일 때는 대비시키지 말고 서로를 참조하세요.

**6. 그럴듯한 단순화로 잘못된 메커니즘 설명하기**

시스템 동작을 단순화할 때는 그 단순화가 실제 메커니즘을 설명하는지 검증하세요. 예를 들어 "a Custom rule can change a Managed rule's action"은 평가 순서 때문에 Custom 규칙이 실제로는 우선하는 경우 틀린 설명입니다. 그럴듯하지만 기계적으로 부정확한 설명은 원래의 전문 용어보다 나쁩니다.

**7. 독자가 이미 가진 정밀도를 과하게 설명하기**

Wireshark 문법의 필터 식을 작성하는 독자에게 `==`가 "equals"를 뜻한다고 설명하지 마세요. 가상의 초보자가 아니라 페이지의 실제 독자에 맞춰 인라인 정의 수준을 조절하세요.

**8. 공식 문서에 캐주얼한 말투 쓰기**

"Let you"는 Cloudflare 문서에 비해 너무 캐주얼합니다. "allow you to"를 쓰거나 동작을 직접 진술하세요. 대화체 이상이 아니라 기존 문서의 어조에 맞추세요.

**9. 관련은 있지만 다른 개념을 한 문장에 섞기**

단순화할 때 두 개의 별개 개념을 한 문장으로 합쳐서 같은 것이거나 하나가 다른 하나를 요구하는 것처럼 보이게 하지 마세요. 예: "CNAME flattening resolves the chain and returns a Cloudflare anycast IP"는 CNAME flattening(DNS 해석 동작)과 proxying(트래픽 라우팅 결정)을 섞습니다. proxy가 꺼진 상태에서도 CNAME flattening은 가능하며, 이 경우 Cloudflare IP는 반환되지 않습니다. 마찬가지로 "Full setup means Cloudflare is your only DNS provider"는 설정 유형(Cloudflare 권한 있는 네임서버 사용)과 배타성(다른 DNS 제공자가 없음)을 섞습니다. 각 개념은, 자주 함께 나타나더라도 독자적인 의미로 도입해야 합니다. 두 기능이 상호작용한다면 각각을 따로 설명한 뒤 관계를 설명하세요.
