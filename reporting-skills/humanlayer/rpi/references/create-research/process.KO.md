# 현재 시스템 리서치

라이브 코드, 테스트, 사용 가능한 문서에서 얻은 사실로 리서치 질문에 답합니다. 무엇이 존재하는지, 어떻게 동작하는지, 각 부분이 어떻게 상호작용하는지 설명합니다. 미래의 설계 선택은 설계 단계로 남겨 둡니다.

다음 단계를 순서대로 따릅니다.

## 1. 리서치 범위 읽기

리서치 질문 문서를 쓰거나, `/rpi create research for how the electric collections connect to tanstack`처럼 직접 질문을 던질 수 있습니다. 직접 질문은 바로 리서치를 시작하고, 그 질문에 답하는 문서 하나를 만듭니다. 깊이는 질문에 맞춥니다.

리서치 질문 문서를 쓰는 경우에는 위임하기 전에 메인 컨텍스트에서 그 문서를 전체 읽고, 이를 작업 전체의 컨텍스트로 사용합니다. 직접 요청이라면 사용자의 질문과 지정된 소스를 사용합니다. 입력이 가리키는 현재 시스템의 소스 파일과 문서를 읽습니다. 원래 요청과 원하는 상태를 담은 설계 문서는 이후 설계 및 구현 세션에서 불러옵니다. 두 종류의 리서치 입력이 모두 없으면 리서치 질문을 요청합니다.

리서치 질문 문서나 호출에서 선택한 flow가 있다면 인계 시 함께 가져갑니다. 독립적인 리서치 답변은 저장된 문서와 후속 질문 초대로 마칩니다.

## 2. 질문을 리서치 영역으로 나누기

관련 질문을 초점이 맞는 영역으로 묶습니다. 보통 범위에 맞춰 서브에이전트를 두세 개에서 여섯 개 사이로 사용합니다.

각 조사가 다룰 컴포넌트, 디렉터리, 패턴, 의존성을 파악합니다. 모든 질문에 답이 달리도록 조사 항목을 추적합니다.

## 3. 서브에이전트로 조사하기

- `codebase-locator`는 관련 코드, 설정, 테스트를 찾습니다.
- `codebase-analyzer`는 동작, 데이터 흐름, 컴포넌트 상호작용을 추적합니다.
- `codebase-pattern-finder`는 기존 예시와 컨벤션을 찾습니다.
- `web-search-researcher`는 외부 자료를 확인하고 발견 사항과 함께 링크를 반환합니다.

필요하면 Explore 에이전트를 사용합니다. 필요한 곳에서는 먼저 코드를 찾고, 그다음 관련 구현을 분석합니다. 서로 독립적인 조사는 병렬로 실행합니다. 각 에이전트에는 범위가 정해진 읽기 전용 질문을 주고, 구체적인 경로, 라인 참조, 테스트 패턴, 근거를 요청합니다.

의존성 질문에는 사용 가능한 웹이나 라이브러리 문서 도구를 활용합니다. 웹에 접근할 수 없으면 그 한계를 적고, 코드와 로컬 문서만으로 계속합니다.

## 4. 결과를 기다리고 발견 사항 종합하기

종합하기 전에 모든 조사가 끝날 때까지 기다립니다. 근거를 검토하고, 상충하는 발견 사항은 라이브 코드와 대조해 해결하며, 컴포넌트 간 결과를 연결합니다. 각 리서치 질문에 구체적인 근거로 답하고, 인용한 경로가 실제로 맞는지 확인합니다.

## 5. 메타데이터 수집하고 문서 템플릿 읽기

현재 날짜와, 리서치한 저장소마다 식별자와 커밋 SHA를 수집합니다. 해당하는 저장소가 없으면 `repos: []`를 사용합니다. 작업 디렉터리에서 다음 `NN-` 번호와 짧은 설명을 골라 `NN-research-<description>.md`를 만듭니다.

리서치가 끝났으니 `$SKILLBASE/references/create-research/references/research_template.md`를 읽습니다.

문서의 시각 설명을 위해 `$SKILLBASE/references/show-me.md`에 있는 `/show-me` 지침을 읽습니다. 시스템이 오늘날 어떻게 존재하는지 보여 주려면 현재 상태 뷰를 사용합니다.

## 6. 리서치 문서 쓰기

템플릿을 사용해 시스템이 어떻게 동작하는지를 중심으로 구성한, 자체적으로 완결된 기술 설명을 씁니다. 발견 사항 섹션의 제목은 참인 사실을 주장하도록 씁니다. 독자가 제목만 읽어도 주요 발견 사항을 이해할 수 있어야 합니다.

예를 들어 "Worker startup"이나 "How do workers restore jobs?" 대신 "Workers restore pending jobs before accepting new work"처럼 씁니다. 결론을 먼저 말하고, 설명, 인용, 시각 자료로 뒷받침합니다. 섹션은 위치를 밝히기 전에 각 부분이 하는 일을 설명하도록 개념 단위로 구성합니다.

구조를 더 분명히 할 수 있다면 Mermaid 다이어그램, 표, 호출 트리, 컴포넌트 트리, 계약, 시그니처, 의사코드를 사용합니다. 각 뷰는 그것이 뒷받침하는 본문 옆에 둡니다. 모든 리서치 질문에 답할 만큼 충분한 기술적 깊이를 유지합니다.

각 컴포넌트에 대해 현재 테스트를 설명합니다. 테스트 파일 위치, 단위/통합/엔드투엔드 커버리지, 픽스처, 목(mock), 유틸리티를 포함합니다. 테스트를 찾지 못했다면 그렇게 명시합니다. 외부 소스 링크와, 리서치한 영역을 탐색할 수 있을 만큼 충분히 묶은 코드 참조 목록을 포함합니다.

읽은 테스트와 실행한 확인을 구분합니다. 확인이 통과했다고 주장한다면 그 명령과 관찰된 결과로 뒷받침합니다.

선택한 경로에 수집한 메타데이터와 함께 문서를 저장합니다. 워크플로를 골랐다면 frontmatter에 `flow`를 포함합니다.

## 7. 남은 열린 질문 조사하기

질문이 남아 있다면 목표가 분명한 후속 조사를 한 번 수행하고, 그 결과를 관련 섹션에 엮어 넣습니다. 남은 불확실성은 문서에 명시적으로 드러냅니다.

## 8. 최종 답변 템플릿 읽고 응답하기

`$SKILLBASE/references/workflow.md`를 읽어 다음 단계를 고르고, 그다음 `$SKILLBASE/references/create-research/references/research_final_answer.md`를 읽어 그 템플릿으로 응답합니다. 리서치 경로, 다음 단계, 작업 디렉터리, 선택한 flow를 채웁니다. 열린 질문이 남아 있으면 함께 언급합니다.

문서를 VS Code, Cursor, 또는 사용자가 선호하는 편집기나 브라우저에서 검토할 수 있게 열지 제안합니다.

독립 리서치라면 템플릿의 저장된 문서와 검토 부분만으로 응답을 완성합니다.

## 9. 후속 리서치 처리하기

후속 요청이 오면 필요에 따라 조사하고, 새 발견 사항을 검증한 뒤 기존 문서에 제자리에서 엮어 넣습니다.
