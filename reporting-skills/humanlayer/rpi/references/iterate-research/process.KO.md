# 리서치 반복 개선

사용자의 피드백을 사용해 기존 리서치 문서를 바로잡거나 확장하고, 일부만 끝난 조사를 이어갑니다. 코드, 테스트, 사용 가능한 문서에서 얻은 근거로 현재 존재하는 시스템을 설명하세요.

다음 단계를 순서대로 따르세요.

## 1. 리서치와 피드백 읽기

위임하기 전에 선택한 리서치 문서를 메인 맥락에서 전체적으로 읽으세요. 리서치 문서와 사용자의 피드백을 작업의 전체 맥락으로 사용하세요. 문서가 지정한 현재 시스템의 소스 파일이나 문서를 전체적으로 읽으세요. 설계 및 구현 세션이라면 원래 요청 문서와 목표 상태 설계 문서도 불러오세요. 문서를 찾을 때는 실제 리서치 보고서를 선택하세요. 리서치 질문은 별도의 문서 유형입니다.

문서가 완성되어 있고 피드백이 없다면 사용자에게 무엇을 조사하거나 바꾸고 싶은지 물어보세요. 미완료 리서치라면 기록된 범위와 열린 질문에서 이어서 진행하세요.

## 2. 다시 살펴볼 부분 파악하기

피드백이 어떤 결과에 영향을 주는지, 어떤 질문이 아직 답되지 않았는지, 어떤 근거가 필요한지 확인하세요. 관련된 조사를 집중된 영역으로 묶으세요. 질문은 현재 동작과 상호작용에 관한 것으로 유지하고, 향후 설계 선택은 설계 단계에 남겨 두세요.

## 3. 추가 리서치 수행하기

각 조사에 적절한 에이전트를 사용하세요:

- `codebase-locator`는 관련 소스 파일, 설정, 테스트를 찾습니다.
- `codebase-analyzer`는 동작, 데이터 흐름, 구성 요소 간 상호작용을 추적합니다.
- `codebase-pattern-finder`는 기존 예시와 관례를 찾습니다.
- `web-search-researcher`는 사용자가 웹 리서치를 요청했을 때 외부 자료를 확인하고, 발견한 내용과 함께 링크를 반환합니다.

유용하다면 Explore 에이전트를 사용하세요. 필요한 곳에서는 먼저 코드를 찾고, 그다음 관련 구현을 분석하세요. 서로 독립적인 조사는 병렬로 실행하세요. 각 에이전트에게는 집중된 읽기 전용 작업을 맡기고, 경로, 줄 번호, 테스트 패턴, 뒷받침 근거를 요청하세요.

외부 질문에는 사용 가능한 웹 또는 라이브러리 문서 도구를 사용하세요. 웹 접근이 불가능하면 그 한계를 기록하고, 코드와 로컬 문서를 기준으로 계속 진행하세요.

## 4. 결과를 기다리고 발견 사항 검증하기

모든 조사가 끝날 때까지 기다리세요. 근거를 실제 코드와 대조해 확인하고, 상충하는 결과를 해결하고, 구성 요소 전반에 걸친 발견 사항을 연결하세요. 외부 자료를 사용했다면 링크를 포함하세요. 남아 있는 불확실성은 명시적으로 드러내세요.

## 5. 문서 템플릿과 시각화 가이드 읽기

문서 구조는 `$SKILLBASE/references/iterate-research/references/research_template.md`를 읽고, 시각적 설명은 `$SKILLBASE/references/show-me.md`를 읽으세요. 시스템이 오늘날 어떻게 동작하는지 보여 주기 위해 현재 상태를 보여 주는 그림을 사용하세요.

## 6. 문서를 그 자리에서 갱신하기

검증된 발견 사항을 기존 경로의 관련 섹션에 자연스럽게 엮으세요. 문서가 하나의 일관된 기술 설명으로 읽히도록 해당 섹션을 다시 작성하세요. 프런트매터는 보존하고, 필요에 따라 저장소 항목이나 상태를 갱신하세요. 저장소는 `identifier`와 `sha`를 가진 `repos` 항목으로 0개 이상 기록하고, 해당하는 것이 없으면 `repos: []`를 사용하세요.

각 발견 섹션의 제목은 무엇이 사실인지 드러내야 합니다. 독자가 제목만 훑어봐도 주요 발견 사항을 이해할 수 있어야 합니다. 예를 들어 "Session storage"나 "How are sessions persisted?" 대신 "Sessions persist before the daemon acknowledges the write"처럼 쓰세요. 영향을 받은 제목도 같은 스타일로 새로 고치세요.

개념이 어디에 있는지 인용하기 전에 먼저 그 개념을 설명하세요. 주장은 파일과 줄 번호로 뒷받침하고, 리서치 범위에 답하는 데 필요한 기술적 깊이를 유지하세요. 다이어그램, 표, 시그니처, 계약, 트리, 의사 코드는 설명하는 산문 바로 옆에 배치하세요.

영향을 받은 각 구성 요소에 대해 테스트 패턴을 갱신하세요. 테스트 위치, 접근 방식, 픽스처, 목, 유틸리티를 포함하세요. 테스트를 찾지 못했다면 그렇다고 명시하세요. 요약, 코드 참조 목록, 아키텍처 문서, 열린 질문이 발견 사항과 일치하도록 유지하세요.

읽은 테스트와 실행한 검사를 구분하세요. 검사가 통과했다고 주장한다면 명령과 관찰된 결과로 뒷받침하세요.

## 7. 최종 답변 템플릿을 읽고 응답하기

`$SKILLBASE/references/iterate-research/references/research_final_answer.md`를 읽고 그 템플릿에 따라 응답하세요. 워크플로가 선택된 경우에는 `$SKILLBASE/references/workflow.md`를 사용해 작업 디렉터리와 flow와 함께 다음 단계를 제안하세요. 독립형 리서치라면 저장된 문서와 리뷰 부분만으로 응답을 완성하세요.

검토를 위해 VS Code, Cursor, 또는 사용자가 선호하는 편집기나 브라우저에서 문서를 열지 제안하세요.
