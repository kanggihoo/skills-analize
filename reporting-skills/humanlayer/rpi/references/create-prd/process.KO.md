# 제품 요구사항 문서(PRD) 작성

사용자와 함께 무엇을 왜 만들지 정의합니다. 문제, 성공 지표, 사용자 경험, 기능, 동작을 다룹니다. 구현 관련 질문은 TDD로 넘깁니다.

다음 단계를 순서대로 따르며, 인터뷰는 메인 대화에서 진행합니다.

## 1. 사용 가능한 컨텍스트 읽기

작업 디렉터리의 워크플로 문서와 지정된 소스를 전체 읽습니다. 리서치, 디자인 디스커션, 짧은 요청 등 현재 있는 입력을 기반으로 작업합니다. 상위 문서의 사실은 참조하고, 빠진 제품 맥락은 질문으로 드러냅니다.

대화가 현재 코드 동작에 의존하면 리서치 에이전트로 그 동작을 확인합니다. 결과를 기다린 뒤, 리서치 문서가 있으면 업데이트합니다.

UI 작업이라면 리서치의 디자인 시스템 발견 사항을 활용합니다. 목업에 더 많은 맥락이 필요하면 컴포넌트, 색상, 타이포그래피, 간격, 테마를 조사합니다.

## 2. 템플릿 읽기와 짧은 시작 문서 쓰기

`$SKILLBASE/references/create-prd/references/prd_template.md`와 `$SKILLBASE/references/show-me.md`를 읽습니다.

다음 번호를 붙여 `NN-prd-<description>.md`를 씁니다. frontmatter, 제목, 초안 **Problem to Solve**, 비어 있는 **Success**, **Proposed Solution**, **Solution Details** 섹션으로 시작합니다. `repos`에는 관련 식별자와 SHA를 채우거나, `repos: []`를 사용합니다.

초안으로 작성한 문제 정의를 인용하고, 그것을 확인하거나 고칠 수 있도록 질문 하나를 던집니다. 인터뷰가 바로 시작될 수 있도록 이 도입부는 짧게 유지합니다.

## 3. 문제와 성공 지표 확정하기

먼저 문제에 합의합니다. 사용자가 표현을 확정하면 해당 섹션을 한 번 다시 다듬습니다.

그다음 변경이 출시 후 사용자에게 도움이 되는지 어떻게 판단할지 논의합니다. 작업에 맞는 지표를 제안합니다. 예를 들어 도입률, 벤치마크, 오류, 지연 시간, 정성적 결과 등입니다. 유용한 지표가 없는 작은 작업이라면 사용자의 동의를 받아 그 선택을 기록합니다.

메시지마다 질문은 하나만 하고 답을 기다립니다. 문제와 성공 지표가 확정되면 솔루션 인터뷰를 시작합니다.

## 4. 솔루션에 대해 사용자와 인터뷰하기

제품 결정은 한 번에 하나씩, 옵션 두세 개와 트레이드오프, 추천안과 함께 제시합니다. 사용자가 답하고 선택을 명확히 할 시간을 줍니다. 선택이 확정되면 문서를 업데이트합니다.

영향을 받는 섹션을 일관된 명세로 다시 작성합니다. **Solution Details**를 업데이트하고, **Proposed Solution**을 다듬으며, 범위나 대안이 바뀌면 이를 기록합니다. 짧은 문단을 사용하고, "리뷰어는 로그인 없이 댓글을 남긴다"처럼 결과를 말하는 섹션 제목을 씁니다.

UI 선택에는 초점이 맞는 `mockup-<description>.html` 파일을 작업 디렉터리에 저장합니다. 사용자의 제품에 맞추고 실제에 가까운 라벨을 사용합니다. 각 목업은 문서와 대화에서 그 설명 옆에 링크합니다. 결정이 바뀌면 목업도 업데이트합니다.

스키마, 저장소, 코드 구조 같은 기술적 질문은 **Deferred to TDD**에 기록하고, 제품 동작 논의로 돌아갑니다.

## 5. 전체 솔루션 검토 요청하기

솔루션 작성이 끝나면 사용자에게 **Solution Details**를 처음부터 끝까지 읽고 전체를 승인해 달라고 요청합니다. 사용자의 수정 사항을 반영하고, 문서와 목업을 최신 상태로 유지합니다.

문서를 VS Code, Cursor, 또는 사용자가 선호하는 편집기나 브라우저에서 검토할 수 있게 열지 제안합니다.

## 6. 최종 답변 템플릿을 읽고 응답하기

승인을 받으면 `$SKILLBASE/references/create-prd/references/prd_final_answer_resolved.md`를 읽고 인계에 사용합니다. 보통 다음 단계는 TDD입니다. 사용자는 아웃라인이나 바로 구현을 선택할 수도 있습니다.
