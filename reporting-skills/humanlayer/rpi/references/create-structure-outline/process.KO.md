# 구조 아웃라인 작성

합의된 설계를 각각 테스트할 수 있는 순서 있는 구현 단계로 바꿉니다. 검토에 필요한 수준으로 의도와 코드 형태를 설명합니다.

다음 단계를 순서대로 따릅니다.

## 1. 워크플로 문서 읽기

완료된 리서치, 설계 문서, 원래 요청, 지정된 소스를 메인 컨텍스트에서 전체 읽습니다. 있는 문서를 사용합니다. 확정된 결정, 원하는 동작, 범위, 따를 패턴을 검토합니다.

## 2. 관련 코드 읽기와 공백 메우기

문서가 인용한 소스 파일을 읽고, 프로젝트의 테스트 및 검증 명령을 확인합니다. 남은 질문은 리서치 에이전트로 조사하고, 결과를 기다린 뒤 아웃라인을 작성합니다.

## 3. 시각 가이드와 문서 템플릿 읽기

`$SKILLBASE/references/show-me.md`와 `$SKILLBASE/references/create-structure-outline/references/structure_outline_template.md`를 읽습니다.

## 4. 작업을 테스트 가능한 단계로 나누기

관련 모듈이나 서비스 경계를 가로지르는 작은 엔드투엔드 결과를 우선합니다. 각 단계는 끝났을 때 동작하고 검증 가능해야 합니다. 예를 들어 먼저 간단한 결과를 엔드투엔드로 제공하고, 그다음 편집 기능을 추가하고, 그다음 오류 경로를 추가합니다. 각 단계에 테스트를 함께 둡니다.

실제 작업에 맞게 이 접근을 조정합니다. 하나의 단계로 충분한 변경도 있고, 안전한 사전 준비 단계가 필요한 변경도 있습니다. 각 단계의 검사가 지금까지 완료된 작업으로 실행될 수 있도록 단계 순서를 정합니다.

각 단계마다 다음을 설명합니다.

- 그 단계가 제공하는 결과와 왜 지금 오는지.
- 간결한 변경 아웃라인: 관련 파일, 소유권, 데이터 구조, 계약, 동작.
- 프로젝트의 기존 패턴을 따르는 테스트.
- 실행 가능한 자동 검사와 사람의 판단이 필요한 검사.

단계에 맞는 시각 뷰를 고르고 순서를 정합니다. 파일 트리로 시작하는 것보다 계약이나 데이터 형태가 작업을 더 잘 설명할 수도 있습니다. 뷰 사이에는 짧은 설명을 둡니다. 기존 형태는 초점이 맞는 diff로, 새 코드는 완전한 최종 형태로 보여 줍니다. 파일 소유권이 중요하면 `/show-me`의 트리 형식을 사용합니다.

## 5. 아웃라인 쓰기

선택한 작업 디렉터리에 다음 번호를 붙여 `NN-structure-outline-<description>.md`를 씁니다. 관련 `repos` 식별자와 SHA를 포함하거나, `repos: []`를 사용합니다.

각 단계 제목마다 체크되지 않은 항목이 있는 **Implementation Overview**를 추가합니다. 각 단계에는 결과, **Change Outline**, **Validation**을 적습니다. **Automated Verification**과 **Manual Verification**을 분리하고, 사람의 판단이 필요한 확인은 manual에 포함합니다. 저장소의 실제 명령을 사용합니다.

해결되지 않은 범위나 단계 질문은 **Open Questions**에 기록합니다. 사람이 제안된 변경을 검토할 수 있도록 단계 제목과 짧은 설명을 명확하게 씁니다.

## 6. 아웃라인 피드백 반영하기

사실 관계 정정은 검증한 뒤, 아웃라인을 제자리에서 수정합니다. 범위, 순서, 검증에 대한 피드백은 이 문서의 변경으로 취급합니다. 확정된 답변은 관련 섹션에 반영하고, 개요가 단계와 계속 맞도록 유지합니다.

## 7. 최종 답변 템플릿을 읽고 응답하기

`$SKILLBASE/references/create-structure-outline/references/structure_outline_final_answer.md`를 읽고, 사용자의 다음 세션을 위해 문서 경로와 제안하는 구현 명령을 제공합니다.

문서를 VS Code, Cursor, 또는 사용자가 선호하는 편집기나 브라우저에서 검토할 수 있게 열지 제안합니다.
