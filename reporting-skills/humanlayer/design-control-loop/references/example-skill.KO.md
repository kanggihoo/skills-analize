# Narrow React Prop Types

React 컴포넌트의 prop이 스토리, 목(mock), 테스트, 데모를 위해 넓어져서 라이브 애플리케이션이 진입하지 않는 상태를 표현하게 되었을 때 이 스킬을 사용합니다.

목표는 컴포넌트 타입이 실제 라이브 코드 경로의 계약을 설명하도록 만든 다음, 타입을 약화시키는 대신 스토리/테스트/목이 그 계약에 맞추도록 요구하는 것입니다.

## 핵심 요건

- 타입을 바꾸기 전에 실제 non-test, non-Storybook 호출 지점을 찾습니다.
- 라이브 코드 경로를 prop 계약의 원천(source of truth)으로 취급합니다.
- 스토리, 테스트, 목 데이터를 더 쉽게 만들기 위해서만 선택적 prop을 유지하지 마세요.
- non-Storybook, non-test 호출 지점 중 일부가 해당 prop을 제공하지 않고, 그렇게 하지 않을 타당한 이유가 있을 때만 prop을 선택적으로 유지합니다.
- 타입은 non-test, non-Storybook 호출 지점에서 관찰되지 않는 상태를 표현할 수 없어야 합니다.
- 코드를 최대한 단순하게 만들 수 있도록 타입은 가능한 한 엄격해야 합니다.
- 가능하면 기존 라이브 코드 경로의 값과 API로부터 타입을 파생하고 추출합니다.

## 워크플로

이 스킬을 CodeLayer를 통해 실행하는 예시 반복 GitHub Actions 워크플로는 `references/agent-narrow-component-props.yml`을 참고하세요. 예시 에이전트 메모리 파일은 `references/narrow-component-props-memory.md`입니다.

### 1. 의심 컴포넌트 식별

다음 신호가 있는 컴포넌트를 찾습니다.

- 선택적 필드가 많은 큰 props 인터페이스.
- `onSelect?.(...)` 또는 `onArchive?.(...)` 같은 선택적 콜백 호출.
- 라이브 코드가 항상 제공할 가능성이 높은 값 주변의 `items ?? []`, `count ?? 0`, `handler && ...` 같은 폴백 상태 처리.
- 콜백이 선택적인데도 항상 렌더링되는 UI affordance.
- `defaultFoo`, 대체 핸들러 형태, 라이브 코드가 사용하지 않는 표시 토글처럼 데모 지향적으로 보이는 props.

스토리나 테스트만 보고 대상을 고르지 마세요. 스토리/테스트는 타입이 넓어졌다는 보조 근거로만 사용하고, 어떤 상태가 실제라는 근거로 쓰지는 않습니다.

### 2. 모든 라이브 사용처 찾기

컴포넌트, 내보낸 prop 타입, 공유 자식 프리미티브의 모든 import/사용처를 검색합니다.

호출 지점을 라이브 코드 경로인지 지원 코드인지로 분류합니다.

- 라이브 코드 경로: 앱 라우트, 연결된(wired) 컴포넌트, 프로바이더, 훅, 프로덕션 패키지 export, 그런 경로에서 사용되는 공유 컴포넌트.
- 지원 코드: Storybook 스토리, 테스트 파일, 픽스처, 목, 데모 하네스, 시각 전용 예제.

컴포넌트 API가 무엇을 지원하는지는 라이브 코드 경로만 결정해야 합니다.

### 3. 라이브 코드 경로에서 실제 타입 도출

라이브 호출 지점을 읽고 각 prop을 분류합니다.

- 필수: 모든 non-test, non-Storybook 호출 지점이 제공함.
- 선택적: 최소 하나의 non-test, non-Storybook 호출 지점이 생략하며, 그 생략이 의미 있는 런타임 상태임.
- 제거: 어떤 non-test, non-Storybook 호출 지점도 사용하지 않음.

Nullable과 선택성은 다릅니다. 라이브 코드가 prop을 항상 전달하지만 값이 비어 있을 수 있다면, `focusedItem?: FocusedItem | null` 보다 `focusedItem: FocusedItem | null` 같은 필수 nullable prop을 선호합니다.

### 4. 공개 prop 타입 조이기

내보낸 prop 타입을 라이브 코드 경로에서 관찰된 상태에만 맞게 업데이트합니다.

타입이 느슨하고 선택적일수록 컴포넌트가 처리해야 할 가능한 상태가 많아집니다. 모든 선택적 prop은 컴포넌트가 처리하고, 테스트하고, 정확하게 유지해야 할 또 하나의 분기를 만듭니다. 방어적 렌더링 로직을 요구하는 넓은 타입보다, 불가능한 상태를 막는 엄격한 타입을 선호합니다.

컴포넌트가 항상 상호작용 가능한 affordance를 렌더링한다면, 그것을 동작하게 만드는 핸들러를 필수로 요구합니다. `onRename?.(...)`를 호출하는 보이는 메뉴 항목처럼 동작하지 않는 상태를 허용하지 마세요.

### 5. 가능한 곳에서 타입 파생 및 추출

타입을 수동으로 다시 적기보다, 라이브 API에서 파생하는 것을 선호합니다.

- 함수 인자 타입에는 `Parameters<typeof fn>[0]`.
- 반환 타입에는 `ReturnType<typeof fn>`.
- 유니언을 실제 variant로 좁히려면 `Extract<Union, Shape>`.
- React 상태 setter는 `(value: T) => void`로 근사하지 말고 `React.Dispatch<React.SetStateAction<T>>`.

추론이 의도한 상태 형태를 넓히거나 흐리게 만들 때는 명시적인 상태 타입 파라미터를 선호합니다.

```ts
const [dialogState, setDialogState] = useState<DialogState>({
  id: null,
  isOpen: false,
})
```

`useState(...)`의 암묵적 추론이 넓은 nullable 객체 형태, 문자열 리터럴 확장, 나중에 수작업 근사가 필요해지는 콜백 타입을 만들 때는 그것에 의존하지 마세요.

### 6. 내부 자식 props도 조이기

공개 컴포넌트에서 멈추지 마세요. 넓은 props를 자식 프리미티브에 넘기고 있다면 그것도 함께 조입니다.

행/메뉴/버튼 자식 컴포넌트가 부모 props가 넓었기 때문에만 선택적 핸들러를 받고 있다면, 그 내부 props도 함께 조입니다. 다음과 같은 선택적 호출을:

```ts
onRename?.(id, name)
```

필수 호출로 바꿉니다:

```ts
onRename(id, name)
```

### 7. 지원되지 않는 상태를 위한 폴백 로직 제거

prop이 필수가 되면, 넓어진 타입을 위해서만 존재했던 방어적 폴백을 제거합니다.

예:

```ts
new Set(expandedIds ?? defaultExpandedIds ?? [])
```

는 다음처럼 되어야 합니다:

```ts
new Set(expandedIds)
```

```ts
items && items.length > 0
```

는 다음처럼 되어야 합니다:

```ts
items.length > 0
```

### 8. 같은 prop 타입을 공유하는 모든 변형 업데이트

여러 컴포넌트가 넓은 prop 타입을 공유한다면, 모두 함께 업데이트해서 같은 라이브 코드 경로 계약을 강제하도록 합니다.

### 9. 테스트와 스토리가 라이브 코드에 맞게 조정되도록 하기

prop을 좁힌 뒤 스토리나 테스트가 깨지면, 현실적인 핸들러와 상태를 제공해서 고칩니다. 테스트 설정을 줄이려고 라이브 코드 경로 prop을 다시 선택적으로 만들지 마세요.

스토리/테스트 설정이 장황하게 느껴지면, 엄격한 라이브 코드 경로 계약을 만족하는 테스트 헬퍼나 픽스처를 만듭니다. 헬퍼는 지원 코드에 두고, 컴포넌트 API를 약화시키지 마세요.

### 10. 변경 검증

변경된 패키지와, 변경된 컴포넌트를 소비하는 각 라이브 앱/패키지에 대해 패키지 단위 typecheck를 실행합니다.

저장소 전용 검증 명령이 있으면 그것을 사용합니다. 이 모노레포에서는 다음을 우선합니다.

```bash
bun --bun run typecheck --filter <package>
```

## 리뷰 체크리스트

- 변경된 prop 타입은 non-test, non-Storybook 호출 지점에서 파생되었다.
- 항상 렌더링되는 상호작용에서 선택적 콜백을 제거했다.
- 핸들러가 없어서 렌더링된 메뉴 항목이나 버튼이 동작하지 않는 상태가 될 수 없다.
- 제거된 props는 라이브 코드 경로에서 사용되지 않는다.
- nullable은 현재 포커스가 없는 경우처럼 실제 상태에 대해서만 유지된다.
- 타입은 가능한 경우 수동으로 중복 작성하지 않고 파생 또는 추출되었다.
- 추론이 의도한 상태를 넓히거나 흐리게 만들 곳에는 `useState<T>(...)`를 사용했다.
- 공유 변형들이 같은 좁아진 계약에 대해 컴파일된다.
- 공유 패키지와 소비하는 라이브 앱/패키지의 typecheck가 통과한다.

## 피해야 할 안티패턴

- 스토리에서 콜백을 생략할 수 있도록 콜백을 선택적으로 만드는 것.
- `onAction?.(...)`를 호출하는 메뉴 항목을 렌더링하는 것.
- 라이브 코드가 제어되는 경우에도 Storybook을 위해 `default*` props를 추가하는 것.
- 누락된 필수 라이브 상태를 숨기기 위해 `?? []` 또는 `?? 0`을 사용하는 것.
- 라이브 코드가 한 가지 형태만 사용하는데 여러 API 형태를 받아들이는 것.
- 순수 컴포넌트를 느슨한 계약을 가진 목 컴포넌트처럼 취급하는 것.
