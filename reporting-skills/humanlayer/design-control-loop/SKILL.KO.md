# Design Control Loop

사용자가 작은 위험도의 리뷰 가능한 변경을 일정에 따라 반복적으로 적용하여 코드베이스의 어떤 속성을 목표값으로 이끌고 싶을 때 이 스킬을 사용합니다. 이것이 **에이전틱 제어 루프(agentic control loop)**입니다.

당신의 역할은 사용자를 **인터뷰하고, 사용자와 _함께_ 루프를 설계한 뒤, 사용자를 위해 구축하는 것**입니다. 설계는 *사용자의* 코드베이스와 이미 쓰고 있는 도구에 맞춰야 합니다. 고정된 도구 세트나 그대로 재현할 템플릿은 없습니다. 저장소에서 찾은 내용에 근거해 옵션을 제안하고, 트레이드오프를 논의하고, 설계에 합의한 뒤 구현하세요.

## 기본 모델

제어 이론에서 개념을 빌려옵니다. 코드베이스는 팀원, 의존성, 생성된 코드(**교란(disturbance)**)에 의해 지속적으로 변경되는 동적 시스템입니다. 제어 루프는 한 번에 모두 바꾸는 대신, 시스템을 원하는 상태로 점진적으로 몰아갑니다.

- **설정값(set point)**: 코드베이스의 어떤 속성에 대해 원하는 최종 상태.
- **센서(sensor)**: 현재 상태를 측정하여 설정값과의 차이를 산출.
- **컨트롤러(controller)**: 그 측정값으로부터 다음번의 작고 위험도가 낮은 변경을 결정.
- **액추에이터(actuator)**: 변경을 적용하고 PR을 여는 코딩 에이전트.
- 결과는 다음 실행으로 피드백됩니다. 사람은 루프에 _참여한 채로_ 방향을 조정합니다.

설계를 시작하기 전에 `references/control-loop-taxonomy.md`를 읽고 이 개념들을 사용자와 함께 살펴보세요. 완전히 작성된 예시 하나는 `references/example-control-loop.md`에 있습니다. 이는 설계도가 아니라 예시로만 다루세요.

## 이 스킬을 실행하는 방법

- **질문하기 전에 저장소를 읽으세요** (Phase A). 빈 양식이 아니라 제안을 가지고 인터뷰에 임하세요.
- **모든 컴포넌트를 맞춤 설계하세요.** 적절한 센서, 컨트롤러, 액추에이터는 사용자의 문제와 기술 스택에 전적으로 달려 있습니다. 참조 문서의 목록은 논의를 촉발하기 위한 예시이며, 밀어붙일 체크리스트가 아닙니다.
- **CI에 연결하기 전에 각 컴포넌트를 로컬에서 독립적으로 실행 가능하게 만드세요** (Phase D). 워크플로는 사용자가 이미 손으로 실행할 수 있는 조각들만 조율해야 합니다.
- **합의된 설계는 구축 전에 문서로 남기세요.** 그래야 사용자가 적은 비용으로 수정할 수 있습니다.

## 산출물

합의된 설계에 맞춰 대상 저장소에 다음을 생성하거나 업데이트합니다.

- **센서**와 **컨트롤러**: 사용자가 로컬에서 실행할 수 있는, 버전 관리되는 명령/스크립트.
- `.claude/skills/<skill-name>/SKILL.md`: 에이전트의 판단을 담는 **액추에이터** 스킬 (저장소 관례에 따라 경로는 `.agents/skills/...`일 수 있음).
- 루프를 실행하고 PR을 여는 반복 **워크플로** (기본은 GitHub Actions. 저장소가 쓰는 CI가 무엇이든 그것을 사용).
- 실행 간에 지속적인 피드백을 전달하는 **메모리/피드백 파일**.
- 선택 사항으로, 루프가 개선하는 동안 문제가 더 나빠지지 않도록 막는 **댐퍼(dampener, 회귀 게이트)**.

## 워크플로

### Phase A — 시스템 이해

**다음 참조 문서를 읽습니다:** `references/example-control-loop.md`.

설정 질문을 하기 전에 먼저 읽습니다.

- 기존 CI: `.github/workflows/*.yml`, `.github/actions/**`, 또는 저장소의 비-GitHub CI 설정. 러너, 체크아웃, 의존성 설치, 캐시, PR 관례를 확인합니다.
- 패키지 관리 파일 (`package.json`, `bun.lock`, `pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, …).
- 기존 검증 스크립트: typecheck, lint, test, quality, format, 그리고 패키지 단위 명령.
- 기존 `.claude/skills` / `.agents/skills`와 기존 에이전트 루프(워크플로, `agent-memory`, 보조 스크립트가 있는 위치)를 확인해서 새 관례를 만들어내지 않고 기존 관례를 따릅니다.
- 저장소에 이미 있는 정적 분석, 린팅, 코드 생성, 테스트 도구. 이것들이 센서의 가장 유력한 원재료입니다.
- 패키지, 서비스, 저장소의 목적을 상위 수준에서 파악합니다.

완료 기준: 저장소의 패키지 관리자, 설치 명령, 예상 검증 명령, CI 플랫폼, 기존 루프 관례를 말할 수 있어야 합니다. 저장소에 포함된 패키지/서비스/애플리케이션을 상위 수준에서 이해해야 합니다.

### Phase B — 사용자와 함께 루프 설계

**다음 참조 문서를 읽습니다:** `references/control-loop-taxonomy.md`, `references/example-control-loop.md`, `references/agent-runner-templates.md`.

이것은 인터뷰입니다. 아래 각 컴포넌트를 차례로 다룹니다. 먼저 설정값에 대해 사용자에게 질문합니다. Phase A에 근거한 옵션을 제안하고, 어떤 선택이든 강요하지 않으면서 트레이드오프를 드러냅니다. 진행하면서 결정 사항을 기록합니다.

1. **설정값(Set point).** 어떤 속성을 어떤 목표로 몰고 가나요? 예: 불변식("오래된 패턴을 사용하는 프로시저가 없을 것"), 임계값("이 패키지들에서 테스트 커버리지 ≥ X"), 또는 방향("매 실행마다 발생 횟수를 줄일 것"). 또한 **범위**를 명확히 하세요. 루프가 변경할 수 있는 디렉터리/패키지와 읽기만 할 수 있는 디렉터리/패키지.

2. **센서(Sensor).** 루프는 설정값과의 차이를 어떻게 측정하나요? 코드베이스와 사용자의 기존 도구를 살펴보고, *그들의* 스택에 맞는 옵션을 제안하세요. 정적 분석 또는 린트 도구, 구조적/AST 검색, 테스트 스위트, 타입 체커, 텔레메트리나 에러 쿼리, 커스텀 스크립트, 또는 에이전트 기반 검사까지 포함될 수 있습니다. 사용자에게 중요한 트레이드오프(안정성, 비용, 반복 가능성, 측정이 조용히 비활성화될 수 있는지)를 논의하세요. 어떤 속성도 강제하지 마세요. 컨트롤러가 반복적으로 활용할 수 있는 측정을 목표로 하세요.

3. **컨트롤러(Controller).** 루프는 측정값으로부터 다음 증분을 어떻게 선택하고, 그 크기를 어떻게 저위험·리뷰 가능한 수준으로 유지하나요? 이것은 사용자와 *함께* 설계하세요. 대상의 우선순위를 어떻게 정할지, 한 증분이 얼마나 클지, 여기서 "리뷰 가능한 작업 단위 하나"가 무엇인지. 컨트롤러는 완전히 결정론적인 것(다음 대상을 고르는 스크립트)부터 완전히 에이전트적인 것(자연어 기준으로 결정하는 에이전트)까지 가능하며, 센서나 액추에이터와 **융합(fused)**될 수도 있습니다. 컨트롤러는 루프의 출력으로부터 시간이 지나며 **튜닝하게 될** 부분입니다. 단순하게 시작하고 수정을 예상하세요.

4. **액추에이터(Actuator).** 코딩 에이전트와 저장소 로컬 스킬이 변경을 적용합니다.
   - **에이전트 + 자격 증명.** CLI 코딩 에이전트(Claude Code, Codex, OpenCode, CodeLayer 등), 그 시크릿, 그리고 헤드리스 명령을 `references/agent-runner-templates.md`에서 고릅니다.
   - **골든 패턴 먼저.** 자동화하기 전에 좋은 변경이 어떤 모습인지 확립합니다. 코드베이스의 기존 패턴을 따라야 하는지 사용자에게 묻고, 코드를 검사해 그 패턴을 찾습니다. 이것들을 액추에이터 스킬(Phase C)에 기록합니다.
   - **검증.** 에이전트가 커밋하기 전에 어떤 명령이 통과해야 하는지 결정합니다 (Phase A에서 제안하고 확인).

5. **교란 + 댐퍼(제안).** 루프 밖에서 시스템을 바꾸는 것이 무엇인지 명명합니다(동시에 배포하는 팀원, 의존성 업데이트, 생성된 코드). 그다음 댐퍼를 **제안**합니다. 예약된 루프가 문제를 조금씩 줄여 나가는 동안 측정된 문제가 더 나빠지지 않도록 막는 검사입니다. 예를 들어 센서 출력을 기준선과 비교해 새로 도입된 편차를 드러내거나(결국에는 차단하는) PR 검사가 있습니다. 이것은 선택 사항이며, 어떤 루프는 필요하지 않습니다.

완료 기준: 설정값, 센서, 컨트롤러, 액추에이터(에이전트 + 스킬 + 검증), 교란/댐퍼를 이름으로 명시한 짧은 설계 문서. 각 컴포넌트는 사용자가 로컬에서 실행할 수 있어야 합니다.

### Phase C — 액추에이터 스킬 구축

**다음 참조 문서를 읽습니다:** `references/skill-template.md`, `references/example-skill.md`, `references/response-template.md`.

이 작업에 대한 액추에이터의 판단을 담는 저장소 로컬 스킬을 작성합니다. 저장소 안에 있으므로 저장소별 경로, 패키지 이름, 관례를 사용할 수 있습니다.

- 순서가 있는 동작은 확인 가능한 완료 기준과 함께 단계로 `SKILL.md`에 작성합니다. 길이가 긴 템플릿과 예시는 형제 참조 파일로 옮깁니다.
- Phase B4의 골든 패턴을 인코딩해서 에이전트가 확립된 관례를 따르도록 합니다.
- 각 규칙은 하나의 출처만 갖도록 합니다. 스킬, 프롬프트, 메모리 파일에 같은 지침을 반복하지 않습니다.
- 에이전트가 최종 출력을 어떤 형식으로 작성해야 하는지 정의하는 응답 템플릿(예: `references/response-template.md`)을 포함하세요. 이 출력이 PR 본문이 됩니다. 스킬이 이 템플릿을 읽고 따르도록 지시하세요.
- 골격으로 `references/skill-template.md`를, 구체적인 예시로 `references/example-skill.md`를 사용합니다. 스킬 명세는 https://agentskills.io/specification 을 참고하세요.

**중요:** 스킬 frontmatter의 `name`은 디렉터리 슬러그와 일치해야 합니다. `migrate-foo`라는 이름의 스킬은 `.claude/skills/migrate-foo/SKILL.md`(또는 `.agents/skills/migrate-foo/SKILL.md`)에 있어야 합니다.

완료 기준: 스킬이 에이전트가 무인으로 작업을 수행할 수 있을 만큼 작업을 명확히 설명하고, 최종 응답의 형식도 포함해야 합니다.

### Phase D — 각 컴포넌트를 로컬에서 실행 가능하게 만들기

**다음 참조 문서를 읽습니다:** `references/agent-runner-templates.md`.

CI가 존재하기 전에, 센서와 컨트롤러를 버전 관리되는 명령이나 스크립트로 먼저 만들고(그런 스크립트를 두는 위치는 저장소의 관례를 따릅니다), 전체 루프가 손으로 실행했을 때 동작하는지 검증합니다.

- **센서**를 단독으로 실행해 안정적이고 쓸 만한 측정값이 나오는지 확인합니다.
- **컨트롤러**를 실제 센서 출력에 대해 실행해 합리적인 다음 증분을 선택하는지 확인합니다.
- **액추에이터**를 컨트롤러가 선택한 대상에 대해 헤드리스 CLI 명령으로 로컬에서 실행해, 변경을 만들고 검증을 통과하는지 확인합니다.

각 조각이 단독으로 로컬에서 실행된 뒤에만 CI로 진행하세요. 이렇게 하면 루프를 디버깅하기 쉬워지고, 워크플로는 사용자가 이미 실행할 수 있는 것들을 얇게 조율하는 역할만 하게 됩니다.

완료 기준: 사용자가 센서, 컨트롤러, 액추에이터를 로컬에서 각각 독립적으로 실행할 수 있어야 합니다.

### Phase E — 루프를 CI에 연결

**다음 참조 문서를 읽습니다:** `references/workflow-template.yml`, `references/prompt-template.md`, `references/agent-runner-templates.md`.

컴포넌트들을 반복 실행되는 작업으로 조립합니다. GitHub Actions가 기본값인 이유는 이미 코드, 시크릿, 버전 관리, 스케줄링/디스패치를 갖추고 있기 때문입니다. 다만 저장소가 쓰는 CI를 사용하세요.

- 루프를 **개별 단계: 센서 → 컨트롤러 → 액추에이터**로 실행한 뒤, 에이전트의 최종 메시지를 본문으로 사용해 커밋하고 PR을 엽니다. (센서가 이미 우선순위를 정하거나 한 에이전트가 선택과 변경을 모두 하는 등 컴포넌트가 융합된 경우에는 단일 단계로 합칩니다. 설계에 없는 분리를 만들어내지 마세요.)
- 재사용 가능한 로직은 커스텀 컴포지트 액션에 둘 수 있습니다.
- 작업 위험도와 리뷰 부담을 기준으로 **주기**(매일, 평일, 매주, 매월, 수동 전용, 또는 사용자 지정 cron)를 결정합니다.
- 메모리 파일(Phase F)을 액추에이터의 컨텍스트에 보간합니다.
- 기본 골격으로 `references/workflow-template.yml`을, 포함된 프롬프트로 `references/prompt-template.md`를 사용합니다. 에이전트 실행 및 응답 추출 단계는 `references/agent-runner-templates.md`에서 가져옵니다(에이전트마다 출력이 다르므로, 최종 응답을 `/tmp/pr-body.md`로 가져와야 합니다).

완료 기준: 워크플로는 존재하지 않는 파일에 의존하지 않고 `workflow_dispatch`로 실행할 수 있어야 합니다.

### Phase F — 사람을 루프에 참여시키기

**다음 참조 문서를 읽습니다:** `references/memory-template.md`, `references/agent-iteration.ts`.

예약된 루프는 조정 없이는 표류합니다. 사람에게 두 가지 채널을 주세요. 둘 다 현재 PR뿐 아니라 향후 동작을 바꿔야 합니다.

- **메모리/피드백 파일.** 버전 관리되는 마크다운 파일(예: `.github/agent-memory/<task-slug>.md`)로, 매 실행마다 **컨트롤러 이후** 액추에이터의 컨텍스트에 결정론적으로 로드됩니다. `references/memory-template.md`를 사용하세요. 좋은 항목: 영구적인 범위 제외, 알려진 오탐 영역, 향후 선택을 바꿔야 하는 리뷰어 피드백. 일회성 지시나 단일 실행 로그는 넣지 않습니다.
- **PR에서의 `/iterate`.** 각 루프의 PR에 라벨을 붙이고, 숨겨진 마커를 삽입해 각 워크플로가 자신이 만든 PR의 댓글만 처리하도록 합니다. 메인테이너가 `/iterate`를 댓글로 남기면, 해당 워크플로가 PR 컨텍스트(diff, 댓글)와 피드백을 로드하고, 에이전트가 메모리와 PR을 업데이트합니다. `references/agent-iteration.ts`(모드: `footer`와 `prompt`)를 저장소가 CI 스크립트를 두는 위치에 설치하세요.

사용자에게 이것을 **컨트롤러와 스킬을 시간이 지나며 튜닝하는 방법**으로 설명하세요. 루프가 좋아지는 이유는 사람이 계속 교정하기 때문입니다.

완료 기준: 지속적인 피드백이 실행 간에 유지되고, `/iterate`(활성화된 경우)가 기존 PR을 업데이트해야 합니다.

### Phase G — 흐름 제어

**다음 참조 문서를 읽습니다:** `references/workflow-template.yml`.

진행 중인 작업량을 제한해서 루프가 리뷰 속도보다 빠르게 PR을 만들지 않도록 합니다. **추천 기본값: 루프당 열린 PR 1개.**

- 워크플로는 이 루프의 라벨이 붙은 열린 PR이 있는지 확인하고, 제한이 찼다면 예약 실행을 건너뜁니다(no-op). 수동 `workflow_dispatch` 실행은 이 검사를 우회합니다.
- PR 메타데이터를 결정합니다: 라벨 이름, PR 제목 접두사, 브랜치 접두사.

이것이 없으면 일간 루프는 아무도 리뷰하지 않는 동안 중복되거나 충돌하는 PR을 쌓아 올릴 수 있습니다. 완료 기준: 이 루프의 열린 PR 제한이 이미 찼을 때 예약 실행이 건너뛰어져야 합니다.

### Phase H — 검증, 드라이 런, 더 빠른 반복

**다음 참조 문서를 읽습니다:** `references/workflow-template.yml`.

워크플로 YAML을 **검증**합니다(`bunx js-yaml file.yml`, `python -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" file.yml`, 또는 `yq`). 그리고 스킬, 워크플로, 메모리 파일이 언급하는 모든 경로가 존재하거나 이 작업에서 생성되는지 확인합니다.

**드라이 런.** 워크플로는 한 번 실행되기 전까지 `workflow_dispatch`로 실행할 수 없습니다. 현재 브랜치에 대해 `push` 트리거를 임시로 추가하고, 푸시한 뒤 실행을 지켜보고, 트리거를 제거합니다. 열린 PR을 검토해서 루프의 동작을 확인합니다.

**더 빠르게 반복할 준비가 되면** (루프가 튜닝되어 일관되고 고품질의 결과를 낼 때): 예약 빈도를 높이거나, 컨트롤러의 배치를 넓히거나(예: 실행당 N개 대상 선택), 워크플로 한 번 실행에서 센스→제어→액추에이트 사이클을 N번 돌리거나, 워크플로를 여러 번 실행해서 팀원 한 명당 PR 하나씩 할당할 수 있습니다.

완료 기준: 워크플로 YAML이 파싱되고, 참조된 모든 파일이 존재하며, 루프가 최소 한 개의 리뷰된 PR을 만들어야 합니다.
