# React Prop 타입 좁히기

React 컴포넌트의 prop이 스토리, 목(mock), 테스트, 데모를 위해 넓어져서 실제 애플리케이션이 진입하지 않는 상태까지 표현하게 되었을 때 이 스킬을 사용하세요.

목표는 컴포넌트 타입이 실제 라이브 코드 경로의 계약을 설명하도록 만드는 것입니다. 타입을 느슨하게 만드는 대신, 스토리/테스트/목이 그 계약에 맞춰지도록 하세요.

## 핵심 요구 사항

- 타입을 바꾸기 전에 실제 non-test, non-Storybook 호출 지점을 찾으세요.
- prop 계약의 기준은 라이브 코드 경로로 삼으세요.
- 스토리, 테스트, 목 데이터를 쉽게 만들기 위해서만 optional prop을 남기지 마세요.
- non-Storybook, non-test 호출 지점 중 해당 prop을 제공하지 않으면서 그럴 만한 타당한 이유가 있는 경우에만 prop을 optional로 유지하세요.
- 타입은 non-test, non-Storybook 호출 지점에서 관찰되지 않는 상태를 표현할 수 없어야 합니다.
- 코드를 최대한 단순하게 만들 수 있도록 타입은 가능한 한 엄격하게 두세요.
- 가능하면 기존 라이브 코드 경로의 값과 API에서 타입을 파생하거나 추출하세요.

## 워크플로

예시로, 이 스킬을 CodeLayer를 통해 주기적으로 실행하는 GitHub Actions 워크플로는 `references/agent-narrow-component-props.yml`에 있습니다. 해당 예시 에이전트 메모리 파일은 `references/narrow-component-props-memory.md`입니다. CI 에이전트 응답 형식은 `references/response-template.md`를 참고하세요.

### 1. 의심 컴포넌트 찾기

다음 신호가 있는 컴포넌트를 찾으세요.

- optional 필드가 많은 큰 props 인터페이스.
- `onSelect?.(...)`나 `onArchive?.(...)`처럼 optional 콜백을 호출하는 코드.
- 라이브 코드가 항상 값을 제공할 가능성이 높은데도 `items ?? []`, `count ?? 0`, `handler && ...` 같은 폴백 처리를 하는 코드.
- 콜백이 optional인데도 항상 렌더링되는 UI 요소.
- `defaultFoo`, 대체 핸들러 형태, 라이브 코드에서 사용하지 않는 표시 토글처럼 데모 지향으로 보이는 prop.

스토리나 테스트만 보고 대상을 고르지 마세요. 스토리와 테스트는 타입이 넓어졌다는 보조 근거로만 사용하고, 어떤 상태가 실제로 존재한다는 근거로 사용하지 마세요.

### 2. 모든 라이브 사용처 찾기

컴포넌트, 내보낸 prop 타입, 공유 자식 프리미티브의 모든 import와 사용처를 검색하세요.

호출 지점을 라이브 코드 경로인지 지원 코드인지로 분류하세요.

- 라이브 코드 경로: 앱 라우트, 연결된(wired) 컴포넌트, provider, 훅, 프로덕션 패키지 export, 그런 경로에서 쓰이는 공유 컴포넌트.
- 지원 코드: Storybook 스토리, 테스트 파일, fixture, 목, 데모 하네스, 시각 전용 예제.

컴포넌트 API가 무엇을 지원해야 하는지는 라이브 코드 경로만으로 결정하세요.

### 3. 라이브 코드 경로에서 실제 타입 도출하기

라이브 호출 지점을 읽고 각 prop을 다음과 같이 분류하세요.

- 필수: 모든 non-test, non-Storybook 호출 지점이 전달함.
- optional: 최소 한 개의 non-test, non-Storybook 호출 지점이 생략하며, 그 생략이 의미 있는 런타임 상태임.
- 제거: non-test, non-Storybook 호출 지점 어디서도 사용하지 않음.

nullable과 optional은 다릅니다. 라이브 코드가 항상 prop을 전달하지만 값이 비어 있을 수 있다면, `focusedItem?: FocusedItem | null` 대신 `focusedItem: FocusedItem | null`처럼 필수 nullable prop을 선호하세요.

### 4. 공개 prop 타입 좁히기

내보낸 prop 타입을 라이브 코드 경로에서 관찰된 상태에만 맞도록 갱신하세요.

타입이 느슨하고 optional이 많을수록 컴포넌트가 처리해야 할 상태가 많아집니다. optional prop 하나마다 컴포넌트가 처리하고, 테스트하고, 올바르게 유지해야 할 분기가 하나씩 생깁니다. 방어적인 렌더링 로직을 요구하는 넓은 타입 대신, 불가능한 상태를 막는 엄격한 타입을 선호하세요.

컴포넌트가 항상 상호작용 요소를 렌더링한다면, 그 요소를 동작하게 만드는 핸들러를 필수로 만드세요. `onRename?.(...)`를 호출하는 보이는 메뉴 항목처럼 동작하지 않는 상태를 허용하지 마세요.

### 5. 가능한 곳에서 타입 파생 및 추출하기

타입을 수동으로 다시 쓰기보다 라이브 API에서 파생하세요.

- 함수 인자 타입에는 `Parameters<typeof fn>[0]`.
- 반환 타입에는 `ReturnType<typeof fn>`.
- 유니온을 실제 variant로 좁히려면 `Extract<Union, Shape>`.
- React state setter에는 `(value: T) => void`로 근사하지 말고 `React.Dispatch<React.SetStateAction<T>>`.

추론이 의도한 상태 형태를 넓히거나 흐리게 만든다면 명시적인 state 타입 파라미터를 사용하세요.

```ts
const [dialogState, setDialogState] = useState<DialogState>({
  id: null,
  isOpen: false,
})
```

추론된 `useState(...)`가 넓은 nullable 객체 형태, 문자열 리터럴 확장, 나중에 손으로 근사해야 하는 콜백 타입을 만든다면 암묵적 추론에 의존하지 마세요.

### 6. 내부 자식 prop도 좁히기

공개 컴포넌트에서 멈추지 말고, 넓은 prop을 자식 프리미티브에 전달하는 부분도 확인하세요.

row/menu/button 자식 컴포넌트가 부모 prop이 넓었기 때문에 optional 핸들러를 받고 있다면, 그 내부 prop도 좁히세요. 다음과 같은 optional 호출을:

```ts
onRename?.(id, name)
```

필수 호출로 바꾸세요.

```ts
onRename(id, name)
```

### 7. 지원하지 않는 상태를 위한 폴백 로직 제거하기

prop이 필수가 되었다면, 넓은 타입을 위해서만 존재하던 방어적 폴백을 제거하세요.

예를 들면 다음과 같습니다.

```ts
new Set(expandedIds ?? defaultExpandedIds ?? [])
```

는 다음과 같이 바꿉니다.

```ts
new Set(expandedIds)
```

```ts
items && items.length > 0
```

은 다음과 같이 바꿉니다.

```ts
items.length > 0
```

### 8. 같은 prop 타입을 공유하는 모든 변형 업데이트하기

여러 컴포넌트가 넓은 prop 타입을 공유한다면, 모두 함께 업데이트해서 같은 라이브 코드 경로 계약을 강제하도록 하세요.

### 9. 테스트와 스토리가 라이브 코드에 맞춰지도록 하기

prop을 좁힌 뒤 스토리나 테스트가 깨지면, 현실적인 핸들러와 상태를 제공해서 고치세요. 테스트 설정을 줄이려고 라이브 코드 경로 prop을 다시 optional로 만들지 마세요.

스토리/테스트 설정이 지나치게 길어지면, 엄격한 라이브 코드 경로 계약을 만족하는 테스트 헬퍼나 fixture를 만드세요. 헬퍼는 지원 코드에 두고, 컴포넌트 API는 약화시키지 마세요.

### 10. 변경 검증하기

변경된 패키지와, 변경된 컴포넌트를 소비하는 각 라이브 앱/패키지에 대해 패키지 단위 타입 체크를 실행하세요.

저장소별 검증 명령이 있으면 그것을 사용하세요. 이 모노레포에서는 다음을 우선 사용하세요.

```bash
bun --bun run typecheck --filter <package>
```

### 11. 응답 형식 맞추기

CI 에이전트로 실행 중이라면, 최종 응답을 `references/response-template.md`에 따라 작성하세요. 이 응답이 PR 본문이 됩니다.

다음을 포함하세요.
- 몇 개의 컴포넌트를 좁혔는지 요약
- 근거와 함께 변경 사항을 정리한 표
- 각 축소를 정당화하는 라이브 호출 지점
- 업데이트가 필요했던 지원 코드(스토리/테스트)
- 검증 결과
- 위험 평가

## 리뷰 체크리스트

- 변경된 prop 타입이 non-test, non-Storybook 호출 지점에서 도출되었다.
- 항상 렌더링되는 상호작용에서 optional 콜백이 제거되었다.
- 렌더링된 메뉴 항목과 버튼이 핸들러 누락 때문에 동작하지 않는 상태가 될 수 없다.
- 제거된 prop은 라이브 코드 경로에서 사용되지 않는다.
- nullable은 현재 포커스가 없음처럼 실제 상태에서만 유지되었다.
- 가능한 곳에서 타입을 수동으로 중복 작성하지 않고 파생하거나 추출했다.
- 추론이 의도한 상태 형태를 넓히거나 흐리게 만드는 곳에서 `useState<T>(...)`를 사용했다.
- 공유 변형들이 같은 축소된 계약에 대해 컴파일된다.
- 공유 패키지와 소비하는 라이브 앱/패키지의 타입 체크가 통과한다.

## 피해야 할 안티 패턴

- 스토리에서 콜백을 생략할 수 있도록 콜백을 optional로 만드는 것.
- `onAction?.(...)`를 호출하는 메뉴 항목을 렌더링하는 것.
- 라이브 코드가 제어되는 경우에도 Storybook을 위해 `default*` prop을 추가하는 것.
- 누락된 필수 라이브 상태를 숨기기 위해 `?? []`나 `?? 0`을 사용하는 것.
- 라이브 코드가 한 가지 형태만 사용하는데 여러 API 형태를 받아들이는 것.
- 순수 컴포넌트를 느슨한 계약을 가진 목 컴포넌트처럼 취급하는 것.
