# DeepSeek Harness 프로즈 표준

계약을 보존하기에 충분한 만큼만 쓰고, 추론 기록, 반복, 장식은 제거하십시오. 계약이란 호출자, 피호출자, 구현자, 생산자, 소비자가 의존하는 의무, 불변식, 전제 조건, 사후 조건, 호환성 약속을 말합니다. 이 스킬은 편집상의 판단과 필수 프로즈 범위를 담당합니다. 배치, 분량 예산, 이중 언어 쌍, 문서화 게이트는 [dsh-doc](../dsh-doc/SKILL.md)을, 추론 기록 누출을 찾고 고치는 일은 [dsh-trim-cot-leakage](../dsh-trim-cot-leakage/SKILL.md)를 사용하십시오. 이것은 스크립트가 아니라 가이드입니다.

`contract`, `boundary`, `shape`, `surface`, `seam`, `gate`, `vocabulary`는 금지어가 아니라 사용 전에 확인할 용어입니다. 먼저 정확한 규칙, API, 필드 집합, 타입, 검증, 시점, 컴포넌트 분리, 실패 상태가 그 사실을 더 잘 표현하는지 물으십시오. 호출자/피호출자 계약이나 보안/프로세스 경계처럼 정확한 기술적 대상을 가리킨다면 용어를 유지하십시오.

주석은 코드가 표현할 수 없는 자명하지 않은 계약이나 근거를 설명합니다. 코드가 이미 암시하는 내용을 다시 말하지 마십시오.

## 입력과 제외 대상

명시적인 `scope`가 필요합니다. 없다면 필요한 입력을 보고하고 중단하십시오. 저장소 전체 범위를 임의로 추정하거나 인터뷰를 시작하지 마십시오.

`mode: automatic | interactive`를 받으며 기본값은 `automatic`입니다. 사용자가 질문이나 보정을 명시적으로 요청한 경우에만 interactive 모드에 들어가십시오.

`mode`는 질문을 제어할 뿐 쓰기 권한을 제어하지 않습니다. 검토 및 감사 작업은 편집하지 않고 결과만 보고하며, 명시적으로 요청된 쓰기, 수정, 축소 작업만 명확한 변경을 적용합니다.

요청 범위가 저장소 전체라도 `vendor/`는 항상 탐색, 검토, 편집에서 제외하십시오. 그 안으로 들어가는 심볼릭 링크도 따르지 마십시오. 제외 항목은 포함 glob 뒤에 두어, 나중의 include가 다시 포함하지 못하게 하십시오. 예를 들어 ripgrep 명령은 `--glob '!vendor/**'`로 끝내고, Git 명령은 명시적인 `:(exclude)vendor/**` pathspec을 지정하십시오. 요청 범위가 `vendor/`뿐이라면 검토할 수 있는 파일이 없다고 보고하십시오.

또한 프로즈 검토와 편집에서 `.agents/notes/archived/`를 제외하십시오. 보관된 Agent Note는 고정된 스냅샷입니다. 과거의 인바운드 인용을 이해하기 위해서만 정확한 대상을 확인하고, 그 프로즈나 아웃바운드 링크를 현대화하지 마십시오.

생성된 카탈로그, 스냅샷, 픽스처는 파생물로 취급하십시오. 편집 전에 모든 소비자를 추적하십시오. 소스 JSDoc이 생성된 모델 노출 카탈로그에도 들어갈 수 있습니다. 소유 소스나 시나리오를 먼저 편집한 뒤 모든 파생물을 다시 생성하십시오. 생성기가 소유자의 프로즈에서 요약을 추출한다면, 추출된 문장이 그 표면에서 완결되도록 만드십시오. 이중 언어 쌍에는 고정된 소유자가 없습니다. 어느 언어든 업데이트의 작성 기준이 될 수 있습니다. [가벼운 루틴 경로](../../../docs/AGENTS.md#writing-rules)를 따라 반대쪽 언어를 최소한으로 갱신하고 쌍을 다시 기록하십시오.

## 완전한 명제 보존하기

편집 전에 해당 문단의 모든 명제를 식별하십시오. 다음 각각을 보존하십시오.

- 행위자와 행위;
- 조건, 시점, 순서;
- must, may, never 같은 양태;
- 부정 보장과 예외;
- 소유권, 부작용, 실패 모드, 결과.

관련 사실 절이 모두 살아남고 결과가 더 명확할 때만 형용사, 반복, 서술을 제거하십시오. 단어 수가 줄었다는 것만으로는 개선이 아닙니다.

사용 지점에는 호출자나 유지보수자에게 필요한 동작, 실패, 소유권, 결과를 담은 완전한 지역 계약을 두십시오. 아키텍처, 근거, 알고리즘, 이력, 확장 예시는 소유 문서로 적극적으로 링크하십시오. 하나의 설명은 한 곳에만 두되, 핵심 계약 사실은 지역적으로 반복될 수 있습니다.

생략하면 misuse나 잘못된 단순화가 일어날 수 있는 자명하지 않은 근거는 유지하십시오. 그렇지 않다면 결과를 서술하고 근거의 본래 위치로 링크하십시오.

## 위치별 필수 범위

이것은 한 방향으로만 줄이라는 지침이 아닙니다. 아래 계약을 코드, 타입, 구조가 전달하지 못한다면 프로즈를 추가하거나 복원하십시오. 그 사실이 이미 지역적으로 자명하다면 주석을 추가하지 마십시오.

- **공개 JSDoc:** 호출자가 볼 수 있는 반환값의 구분, throw 또는 rejection, 부작용, 소유권, 시점, 취소, 내구성을 문서화하십시오.
- **내부 주석:** 비지역적 구조와 명백히 복잡한 지역 구조를 방향 잡아 주십시오. 불변식, 경쟁 순서, 소유권, 보안 경계, 놀라운 실패 동작을 포함합니다. 제어 흐름 서술과 코드 재진술은 삭제하십시오.
- **모듈 주석:** 모듈의 역할, 의존성, 책임, 자명하지 않은 아키텍처 선택을 서술하십시오. 아키텍처 선택은 그 소유 설명으로 링크하십시오.
- **테스트:** 픽스처, assertion, 플랫폼 조정, 실제 진입 경로, 간접 관찰이 왜 필요한지처럼 자명하지 않은 테스트 설계만 설명하십시오. 워크스루와 목록은 삭제하십시오.
- **쿡북:** 전제 조건, 필수 동작, 실제 진입 경로, 관찰 가능한 검증, 간결한 경고를 포함하십시오.
- **README:** 소비자 계약을 포함하십시오. 설정, 의미, 실패, 한계, 확장 지점, 모델에 보이는 효과를 다룹니다. 패키지가 소유한 안정적인 모델 노출 텍스트는 인용하고, 생성된 카탈로그와 패키지 간 소유자는 링크하십시오. 지속되는 공백과 유지보수 함정은 유지하되, 일반적인 정리 작업 목록은 두지 마십시오. [패키지 README 요구사항](../../../docs/cookbook/adding-a-package.md#4-write-the-package-readme)을 따르십시오.
- **Agent Note:** 고유한 근거, 메커니즘, 대안, 결과, 배포된 검증 증거, 명시된 커버리지 공백을 유지하십시오. 구현이 끝난 Agent Note는 배포된 현재 상태를 현재 시제로 서술하십시오. 계획 체크리스트는 제거하되, 결정을 고정하는 증거는 남기십시오.
- **사후 분석:** 사고 순서, 증거, 인과 사슬, 영향, 재발 방지를 유지하십시오. 반복되는 설득이나 인과관계를 입증하지 않는 구현 세부사항은 제거하십시오.
- **스킬과 에이전트 지침:** “guidance, not a script/checklist” 같은 행동 가드레일과 명시적인 범위 한계를 서술하십시오. 워크플로는 간결하게 유지하고 그 근거가 되는 원본으로 링크하십시오.
- **예시와 설정 주석:** 접근 제한, 자명하지 않은 연결이나 로드 순서, 보안 입장, 재생 동작, 예외, 가능한 misuse를 설명하십시오. 설정이 이미 보여 주는 항목은 서술하지 마십시오.
- **프롬프트와 화면에 보이는 문자열:** 문구를 동작으로 취급하십시오. 클라이언트 UI 문구는 타입이 지정된 locale 사전에 두고, Cordis 없는 프리미티브에는 명시적인 현지화 props로 전달됩니다. 텍스트, 접근성 이름, 툴팁, placeholder, 형식 템플릿을 함께 검사한 뒤 `verify-client-ui-i18n`을 실행하십시오. 모델에 보이는 텍스트는 소유하는 실행 가능한 스냅샷과, 저장소가 요구하는 GUI 증거를 함께 갱신하십시오. 허용된 범위에 소유 시나리오가 없다면 문구를 그대로 두고 보류를 보고하십시오. 프로즈 전용 편집에 조용히 포함시키지 마십시오.
- **진단:** 실패한 주체나 경로, 위반된 규칙, 자명하지 않은 경우의 수정 방법을 명시하십시오. 내부 실행 서술은 제거하십시오.

검색 가능한 메커니즘 이름과 의미 있는 양태, 시간, 부정 강조는 보존하십시오. 장식적 강조만 정규화하십시오.

## 워크플로

1. 범위, 모드, 현재 브랜치 또는 PR base, 적용 가능한 `AGENTS.md` 파일을 확인하십시오. 관련 없는 브랜치는 조사하지 마십시오.
2. 문단을 판단하기 전에 [문서 표준](../../../docs/AGENTS.md)과 소유 코드 또는 문서를 읽으십시오. 보정이 필요하거나 낯선 사례라면 [정제된 예시](references/examples.md)를 읽으십시오.
3. 가장 큰 파일만이 아니라 요청된 범위 전체를 검사하십시오. 검색과 단어 수로 후보를 찾은 뒤 의미를 기준으로 문단을 판단하십시오.
4. 각 후보를 유지, 추가, 축소, 복원, 재구성, 보류 중 하나로 분류하십시오. 작업이 편집을 허용할 때만 명확한 변경을 적용하고, 삭제 목표를 채우기 위해 변경을 만들어 내지 마십시오.
5. 파생 산출물보다 소유자를 먼저 갱신하십시오. 새 규칙을 배운 뒤에는 유사한 문단을 다시 확인하십시오.
6. 좁은 범위의 관련 검사, 문서화 게이트, `git diff --check`, 표시되는 문자열에 대한 동작 테스트를 실행하십시오. 최종 diff에 `vendor/` 경로가 없는지 확인하고, 우발적인 vendor 일치가 있다면 깨끗한 제외 이력을 주장하지 말고 보고하십시오.
7. 검사한 범위, 명확한 변경, 의도적인 유지, 보류된 사례, 실제로 실행한 검사를 보고하십시오.

## 경계 판단

사례가 경계선에 있다는 것은, 완전한 명제 규칙을 만족하는 버전이 최소 두 개 있으면서 서로 다른 원칙을 맞바꾸고, 이 스킬이 그 상충을 이미 해결하지 않은 경우뿐입니다. 명제를 보존하는 답이 하나뿐인 재작성은 경계선 사례가 아닙니다.

자동 모드에서는 권한이 있을 때 명확한 편집을 적용하고, 진짜 경계선 사례는 질문하지 않고 보고하십시오. 진전을 위해 명제를 약화시키지 마십시오.

interactive 모드에서는 유사한 문단을 지배적인 원칙 아래로 묶으십시오. 실행 가능한 버전 두세 개를 제시하고 하나를 추천하며, 사실이나 구조상의 차이를 밝히십시오. 열등한 오답 후보를 제시하지 마십시오. 사용자가 요청한 채널을 사용하고, inline 댓글로 PR을 보정하는 경우에는 추천하는 임시 버전을 diff에 두고 대안을 정확히 그 줄에 첨부하십시오.

사용자가 결정한 뒤에는 PR 이력이나 리뷰어의 서술 없이 원칙과 버전을 [예시](references/examples.md)로 정리하고, 범위 안의 모든 유사한 문단에 학습한 규칙을 적용하십시오.
