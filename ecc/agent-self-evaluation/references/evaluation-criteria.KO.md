# 평가 기준 — 상세 채점 가이드

이 참고 문서는 각 축에 대한 구체적인 채점 기준점을 제공합니다. 어떤 격차가 4점인지 3점인지, 또는 2점인지 1점인지 판단하기 애매할 때 사용하세요.

## 정확성 (Accuracy)

| 점수 | 기준 | 예시 |
|---|---|---|
| 5 | 모든 사실이 도구 출력, 문서 또는 신뢰할 수 있는 출처로 검증됨. 오류 없음. | httpx transport로 재시도를 설정함 — httpx 문서에서 확인. 모든 메서드 이름을 코드베이스에서 grep으로 검증. |
| 4 | 정확성에 영향을 주지 않는 사소한 부정확함 하나. | 올바른 라이브러리이지만 매개변수 하나의 기본값이 틀림 (0.5초라고 주장했으나 문서에는 1.0초). |
| 3 | 중요한 사실 오류 하나, 또는 사소한 부정확함 3개 이상. | httpx 기반 코드베이스에서 `urllib3.Retry`를 사용함. 이 경우에는 동작하지만 잘못된 라이브러리. |
| 2 | 중요한 오류가 여러 개. 그대로 따르면 실패함. | 프로젝트는 pyproject.toml을 쓰는데 "package.json에 이것을 추가하세요"라고 주장함. 다른 설정 주장 두 개도 틀림. |
| 1 | 근본적으로 잘못됨. 결과물이 스스로 모순되거나 알려진 사실과 충돌함. | 코드에 문법 오류가 있음. 존재하지 않는 API 엔드포인트. grep으로 반박되는 함수 시그니처를 주장함. |

## 완전성 (Completeness)

| 점수 | 기준 | 예시 |
|---|---|---|
| 5 | 명시적·암묵적 요구사항을 모두 다룸. 엣지 케이스를 처리함. 오류 경로를 다룸. | 사용자 요청: "모든 HTTP 요청에 재시도를 추가하세요." GET, POST, PUT, DELETE를 모두 다룸. 타임아웃, 429, 5xx를 모두 처리. |
| 4 | 명시적 요구사항은 모두 다뤘지만 암묵적 요구사항 하나를 놓침. | 모든 HTTP 메서드를 다룸. 언급되지 않았지만 기대되는 연결 타임아웃 처리를 빠뜨림. |
| 3 | 명시적 요구사항 하나를 놓쳤거나, 암묵적 누락이 2개 이상. | 사용자가 "로깅도 추가하세요"라고 함. 재시도 로직은 추가했지만 로깅이 없음. |
| 2 | 명시적 요구사항을 여러 개 놓침. 결과물이 부분적인 해결책임. | 재시도와 서킷 브레이커를 요청함. 재시도만 구현됨. |
| 1 | 핵심 요청을 놓침. 요청과 관계없는 것을 전달함. | 재시도 로직을 요청함. 대신 헬스 체크 엔드포인트를 작성함. |

## 명확성 (Clarity)

| 점수 | 기준 | 예시 |
|---|---|---|
| 5 | 구조가 완벽함. 전문 용어를 설명하거나 피함. 시각적 위계가 훑어보기에 도움이 됨. 모호함이 없음. | 명확한 섹션, 코드 블록, 맨 위의 10초 요약이 있는 README. |
| 4 | 전반적으로 명확함. 한 섹션의 구성이 더 나을 수 있거나 용어 하나가 정의되지 않음. | 구조는 좋지만 `지수 백오프(exponential backoff)`를 설명 없이 사용함 — 독자가 안다고 가정함. |
| 3 | 다시 읽어야 이해됨. 구성상의 문제가 여러 개이거나 정의되지 않은 용어가 있음. | 설명이 요점에 도달하기 전에 맴돎. 정의되기 전에 쓰인 용어가 여러 개. |
| 2 | 일부 부분이 혼란스러움. 독자가 후속 질문을 해야 함. | 코드는 동작하지만 PR 설명에 재시도가 왜 필요했는지, 무엇을 고치는지 설명되지 않음. |
| 1 | 이해할 수 없거나 모순됨. 독자가 무엇을 했고 왜 했는지 알 수 없음. | 구조 없이 긴 글이 이어짐. 결론이 앞선 진술과 모순됨. |

## 실행 가능성 (Actionability)

| 점수 | 기준 | 예시 |
|---|---|---|
| 5 | 필요한 조치가 하나뿐임. 검증 경로가 포함됨. 암묵적 단계가 없음. | "이 PR을 머지하세요. 테스트 통과: `42 passed`. `./deploy.sh`로 배포." |
| 4 | 조치는 하나지만 검증 경로가 명시되지 않고 암시만 됨. | "이 PR을 머지하세요." (테스트는 존재하지만 언급되지 않음. 사용자가 직접 확인해야 함.) |
| 3 | 여러 조치가 필요하거나, 하나의 조치에 다음 단계가 불분명함. | "검토 후 머지하세요. 그다음 설정을 업데이트하세요." (어떤 설정? 어디에? 링크나 경로가 없음.) |
| 2 | 사용자가 결과물을 어떻게 쓸지 스스로 알아내야 함. 핵심 지침이 빠짐. | 코드는 작성했지만 테스트 파일도, 실행 지침도, PR도 없음. 사용자가 모든 것을 직접 조립해야 함. |
| 1 | 상당한 재작업이나 설명 없이는 결과물을 실행할 수 없음. | "여기 설계 아이디어가 있습니다." (코드, 파일, PR 없음. 사용자가 처음부터 시작해야 함.) |

## 간결성 (Conciseness)

| 점수 | 기준 | 예시 |
|---|---|---|
| 5 | 모든 문장이 제 역할을 함. 중복이 없음. 정보 밀도가 높음. | 60줄이 할 일을 30줄로 함. 반복되는 요점이 없음. 군더더기가 없음. |
| 4 | 사소한 중복이 있음. 한 문단을 더 줄일 수 있음. | 전반적으로 좋지만 동기를 PR 설명과 코드 주석에서 둘 다 반복함. |
| 3 | 눈에 띄는 중복이 있음. 내용의 20% 이상을 손실 없이 제거할 수 있음. | 같은 개념을 요약, 본문, 결론에서 세 번 설명함. 장황한 예시. |
| 2 | 상당히 군더더기가 많음. 내용의 40% 이상이 군더더기이거나 반복임. | 60줄이면 될 작업에 200줄. 사용자의 질문을 그대로 되풀이함. 관련 없는 배경 설명 포함. |
| 1 | 잡음 대 신호 비율이 뒤집힘. 실질보다 군더더기가 많음. | 두 줄짜리 질문에 500줄 응답. 대부분이 상투적 문구, 반복, 또는 관련 없는 맥락. |

## 예외 상황 (Edge Cases)

### 사용자의 지시가 불명확했을 때

사용자의 요청이 모호했다면, 사용자의 의도를 짐작하지 못했다고 완전성 점수를 깎지 마세요. 대신 평가에 다음과 같이 적으세요: "사용자의 요청은 [범위]에 대해 모호했습니다. 저는 [선택한 해석]을 택했습니다. 만약 [대안 해석]을 의도했다면 이 점수는 [점수]로 내려갑니다."

### 작업이 본질적으로 단순할 때

3줄짜리 버그 수정은 정당하게 정확성·완전성·명확성·실행 가능성·간결성 모두 5점을 받을 수 있습니다. 루브릭은 복잡도에 맞춰 조정됩니다 — 단순한 작업을 완벽하게 했다면 그것이 5.0입니다. 낮은 점수를 정당화하려고 격차를 만들어내지 마세요.

### 작업 중 스스로 실수를 발견하고 고쳤을 때

실수를 했다가 전달 전에 발견해서 고쳤다면, 최종 결과물의 정확성은 5점입니다. 평가는 사용자가 받은 결과물에 관한 것이지, 내부 과정에 관한 것이 아닙니다. 자기 수정은 감점 요인이 아니라 꼼꼼함의 증거로 기록하세요.

### 도구 출력이 주장과 모순될 때

"테스트 통과"라고 주장했는데 터미널 출력에 실패가 나타나면, 자동으로 정확성 2점 이하입니다. 도구 출력이 기준 진실(ground truth)입니다. 검증 없는 주장은 낮은 정확성 점수의 가장 흔한 원인입니다.
