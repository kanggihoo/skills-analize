# 벤치마크 최적화 루프

"20배 빠르게 만들어줘" 또는 "재귀 최적화를 50번 시도해줘" 같은 요청을, 실제로 시스템을 개선할 수 있는 제한되고 측정 가능한 루프로 바꾸는 데 이 스킬을 사용합니다.

## 필수 기준선

다음이 준비되기 전에는 최적화하지 마세요.

- 최적화 대상 작업
- 계속 green이어야 하는 정확성 게이트
- 지표: 벽시계 시간(wall time), p95 지연 시간, rows/sec, 실행당 비용, 메모리, 에러율
- 현재 기준선
- 탐색 예산: 최대 변형 수, 최대 시간, 최대 비용, 최대 데이터 영향

사용자가 비현실적인 목표를 요청하면, 야심은 유지하되 루프를 제한되고 측정 가능하게 만드세요.

## 루프

1. 기준선을 측정한다.
2. 증거로부터 병목을 식별한다.
3. 가설 하나씩을 검증하는 변형을 생성한다.
4. 같은 입력 형태로 변형을 실행한다.
5. 정확성, 안전성, 또는 재현성에 실패한 변형을 기각한다.
6. 가장 빠르면서 안전한 변형을 승격한다.
7. 승리한 경로를 스크립트, 명령, 테스트, 설정, 또는 문서로 코드화한다.
8. 기준선과 승자를 다시 실행하여 차이를 확인한다.

## 변형 표

변형을 다음과 같이 추적하세요.

```text
Variant | Hypothesis | Command | Time | Correct? | Notes
baseline | current path | npm run job | 120s | yes | stable
batch-500 | fewer round trips | npm run job -- --batch 500 | 42s | yes | winner
parallel-8 | more workers | npm run job -- --workers 8 | 31s | no | rate limited
```

## 재귀 탐색

재귀적이거나 하이퍼파라미터 작업의 경우:

- 모든 실행을 원장(ledger)에 기록한다.
- 직전 실행만이 아니라, 이전에 수락된 승자와 비교한다.
- 보류(holdout) 또는 재생(replay) 검사를 유지한다.
- 개선이 잡음 범위 안에 들어가거나, 정확성이 실패하거나, 비용이 예산을 초과하거나, 탐색이 설명할 수 있는 것보다 많은 변수를 바꾸기 시작하면 멈춘다.

탐색 공간이 실제로 완전 탐색된 경우가 아니라면 "전역 최적(global optimum)" 대신 "측정된 가장 빠른 안전 변형(best measured safe variant)" 같은 표현을 사용하세요.

## 승격 게이트

다음 조건을 모두 충족하기 전까지 변형은 새로운 기본값이 될 수 없습니다.

- 정확성 테스트가 통과한다.
- 성능 차이가 반복 확인되었거나 설명되었다.
- 롤백이 명확하다.
- 변경 사항이 소스 컨트롤이나 지속 가능한 런북에 코드화되어 있다.
- 최종 요약에 정확한 명령과 측정값이 포함되어 있다.
