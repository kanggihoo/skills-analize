# Terminal Ops

사용자가 실제 저장소 실행을 원할 때 이 스킬을 사용합니다. 명령 실행, git 상태 확인, CI 또는 빌드 디버깅, 좁은 범위의 수정, 그리고 실제로 무엇이 바뀌었고 무엇이 검증되었는지 정확히 보고하는 작업이 여기에 해당합니다.

이 스킬은 일반적인 코딩 지침보다 의도적으로 범위가 좁습니다. 근거 우선의 터미널 실행을 위한 운영자 워크플로입니다.

## 스킬 스택

관련이 있을 때 다음 ECC 기본 스킬을 워크플로에 포함합니다.

- `verification-loop`: 변경 후 정확한 검증 단계를 수행할 때
- `tdd-workflow`: 올바른 수정에 회귀 테스트가 필요할 때
- `security-review`: 비밀 값, 인증, 외부 입력이 관련될 때
- `github-ops`: 작업이 CI 실행, PR 상태, 릴리스 상태에 의존할 때
- `knowledge-ops`: 검증된 결과를 지속적인 프로젝트 맥락으로 기록해야 할 때

## 사용 시점

- 사용자가 "fix", "debug", "run this", "check the repo", "push it"라고 말할 때
- 작업이 명령 출력, git 상태, 테스트 결과, 또는 검증된 로컬 수정에 의존할 때
- 답변이 로컬에서 변경됨, 로컬에서 검증됨, 커밋됨, 푸시됨을 구분해야 할 때

## 가드레일

- 편집하기 전에 먼저 점검합니다.
- 사용자가 감사나 리뷰만 요청했다면 읽기 전용을 유지합니다.
- 즉흥적인 임시 래퍼보다 저장소 로컬 스크립트와 도우미를 우선합니다.
- 증명 명령을 다시 실행하기 전에는 수정되었다고 주장하지 않습니다.
- 브랜치가 실제로 업스트림으로 이동하기 전에는 푸시되었다고 주장하지 않습니다.

## 워크플로

### 1. 작업 surface 확정

다음을 정합니다.

- 정확한 저장소 경로
- 브랜치
- 로컬 diff 상태
- 요청된 모드:
  - inspect (점검)
  - fix (수정)
  - verify (검증)
  - push (푸시)

### 2. 실패한 surface를 먼저 읽기

무엇인가를 바꾸기 전에:

- 오류를 점검합니다.
- 파일이나 테스트를 점검합니다.
- git 상태를 점검합니다.
- 맹목적으로 다시 읽기 전에 이미 제공된 로그나 맥락을 먼저 활용합니다.

### 3. 수정 범위를 좁게 유지

한 번에 지배적인 실패 하나만 해결합니다.

- 가장 작고 유용한 증명 명령부터 사용합니다.
- 로컬 실패가 해결된 뒤에만 더 큰 빌드/테스트 단계로 넘어갑니다.
- 같은 시그니처로 명령이 계속 실패하면 광범위한 재시도를 멈추고 범위를 좁힙니다.

### 4. 정확한 실행 상태 보고

정확한 상태 용어를 사용합니다.

- inspected (점검함)
- changed locally (로컬에서 변경함)
- verified locally (로컬에서 검증함)
- committed (커밋함)
- pushed (푸시함)
- blocked (차단됨)

## 출력 형식

```text
SURFACE
- repo
- branch
- requested mode

EVIDENCE
- failing command / diff / test

ACTION
- what changed

STATUS
- inspected / changed locally / verified locally / committed / pushed / blocked
```

## 주의점

- 실시간 저장소 상태를 읽을 수 있을 때는 오래된 기억을 바탕으로 작업하지 않습니다.
- 좁은 수정을 저장소 전체의 대규모 변경으로 키우지 않습니다.
- 파괴적인 git 명령을 사용하지 않습니다.
- 관련 없는 로컬 작업을 무시하지 않습니다.

## 검증

- 응답에 증명 명령이나 테스트의 이름을 적습니다.
- git 관련 작업에는 저장소 경로와 브랜치를 적습니다.
- 푸시 주장에는 대상 브랜치와 정확한 결과를 포함합니다.
