# 지연 시간에 민감한 시스템

사용자가 실시간 동작, 핫 패스, 스트리밍 데이터 신선도, 또는 실행 속도에 관심을 가질 때 이 스킬을 사용합니다. HFT와 유사한 인프라도 포함되지만, 이 스킬은 엔지니어링에 초점을 둡니다. 실거래나 금융 조언을 승인하지 않습니다.

## 지표를 나누어 보기

모든 것을 "빠르다"로 뭉뚱그리지 마세요. 다음을 추적합니다:

- p50, p95, p99 지연 시간;
- 처리량;
- 데이터 신선도(freshness age);
- 큐 깊이;
- 캐시 적중률;
- 제공자/API 응답 시간;
- 브라우저 렌더링 시간;
- 부하 상황에서의 정확성;
- 실패 및 재시도 동작.

## 핫 패스 매핑

사용자/이벤트에서 최종적으로 화면에 보이는 상태까지의 경로를 적습니다:

```text
source event -> provider API -> ingest worker -> queue -> cache -> edge route
-> client stream -> browser render -> user-visible state
```

그런 다음 각 구간을 개별적으로 측정합니다.

## 최적화 순서

1. 불필요한 왕복(round trip)을 제거합니다.
2. 안정적인 읽기는 신선도 메타데이터와 함께 캐시합니다.
3. 작은 호출과 쓰기를 묶어서(batch) 처리합니다.
4. 연산을 데이터나 사용자 가까이로 옮깁니다.
5. 핫 패스와 콜드 패스를 분리합니다.
6. 큐가 무한정 커지기 전에 백프레셔(backpressure)를 적용합니다.
7. 신선도나 사용자 경험을 실제로 개선할 때만 스트리밍을 사용합니다.
8. 오래된 데이터, 저하된 제공자, 잘못된 캐시 상태를 감지하는 카나리를 추가합니다.

## 검증

배포된 표면이 있을 때는 실시간 readback을 사용합니다:

- HTTP 타이밍과 응답 헤더;
- 제공자의 신선도 타임스탬프;
- 큐 또는 작업 상태;
- 엣지/캐시 상태;
- 실제 UI 신선도를 위한 브라우저 검증;
- 재시도 및 저하 모드 주변의 로그.

시장 데이터 또는 실행과 인접한 경로라면, 준비 완료라고 판단하기 전에 오더북 경과 시간, VWAP 가정, 제공자 상태, 킬 스위치 동작도 검증합니다.
