# 에이전트 자기 점검 디버깅

에이전트 실행이 반복적으로 실패하거나, 진전 없이 토큰을 소모하거나, 같은 도구에서 루프를 돌거나, 의도한 작업에서 벗어날 때 이 스킬을 사용합니다.

이것은 숨겨진 런타임이 아니라 워크플로 스킬입니다. 사람에게 에스컬레이션하기 전에 에이전트가 체계적으로 스스로 디버깅하도록 가르칩니다.

## 활성화 시점

- 최대 도구 호출 / 루프 한도 실패
- 전진 없이 반복되는 재시도
- 컨텍스트 증가나 프롬프트 드리프트로 출력 품질이 저하되기 시작할 때
- 기대와 현실 사이의 파일 시스템 또는 환경 상태 불일치
- 진단과 더 작은 교정 조치로 회복 가능할 가능성이 높은 도구 실패

## 범위 경계

다음 목적으로 이 스킬을 활성화합니다.
- 맹목적으로 재시도하기 전에 실패 상태를 캡처할 때
- 일반적인 에이전트 특유의 실패 패턴을 진단할 때
- 격리된 회복 조치를 적용할 때
- 구조화된 사람이 읽을 수 있는 디버그 보고서를 작성할 때

다음의 주요 출처로는 이 스킬을 사용하지 마세요.
- 코드 변경 후 기능 검증: `verification-loop` 사용
- 더 좁은 ECC 스킬이 이미 있는 프레임워크별 디버깅
- 현재 하네스가 자동으로 강제할 수 없는 런타임 약속

## 4단계 루프

### 1단계: 실패 캡처

회복을 시도하기 전에 실패를 정확히 기록합니다.

캡처 항목:
- 오류 유형, 메시지, 가능하다면 스택 트레이스
- 마지막으로 의미 있었던 도구 호출 순서
- 에이전트가 무엇을 하려고 했는지
- 현재 컨텍스트 압력: 반복된 프롬프트, 과도하게 붙여 넣은 로그, 중복된 계획, 통제되지 않는 메모
- 현재 환경 가정: cwd, 브랜치, 관련 서비스 상태, 예상 파일

최소 캡처 템플릿:

```markdown
## 실패 캡처
- 세션 / 작업:
- 진행 중인 목표:
- 오류:
- 마지막 성공 단계:
- 마지막 실패한 도구 / 명령:
- 관찰된 반복 패턴:
- 검증할 환경 가정:
```

### 2단계: 근본 원인 진단

무엇인가를 바꾸기 전에 실패를 알려진 패턴과 맞춰 봅니다.

| 패턴 | 가능한 원인 | 확인 방법 |
| --- | --- | --- |
| 최대 도구 호출 / 같은 명령 반복 | 루프 또는 종료 경로 없는 관찰자 경로 | 마지막 N번의 도구 호출에서 반복 확인 |
| 컨텍스트 overflow / 추론 저하 | 무제한 메모, 반복된 계획, 과도한 로그 | 최근 컨텍스트에서 중복과 저신호 대량 데이터 확인 |
| `ECONNREFUSED` / 타임아웃 | 서비스 사용 불가 또는 잘못된 포트 | 서비스 상태, URL, 포트 가정 확인 |
| `429` / 할당량 소진 | 재시도 폭주 또는 백오프 누락 | 반복 호출 횟수 세기 및 재시도 간격 확인 |
| 쓰기 후 파일 없음 / 오래된 diff | 경합, 잘못된 cwd, 또는 브랜치 드리프트 | 경로, cwd, git status, 실제 파일 존재 여부 재확인 |
| "수정" 후에도 테스트 실패 | 잘못된 가설 | 정확히 실패한 테스트를 격리하고 버그를 다시 도출 |

진단 질문:
- 이것은 논리 실패, 상태 실패, 환경 실패, 정책 실패 중 무엇인가?
- 에이전트가 실제 목표를 잃고 잘못된 하위 작업을 최적화하기 시작했는가?
- 실패가 결정적인가, 일시적인가?
- 진단을 검증할 수 있는 가장 작은 되돌릴 수 있는 조치는 무엇인가?

### 3단계: 격리된 회복

진단 표면을 바꾸는 가장 작은 조치로 회복합니다.

안전한 회복 조치:
- 반복된 재시도를 멈추고 가설을 다시 진술하기
- 저신호 컨텍스트를 정리하고 활성 목표, 차단 요소, 증거만 남기기
- 실제 파일 시스템 / 브랜치 / 프로세스 상태를 다시 확인하기
- 작업 범위를 실패한 명령 하나, 파일 하나, 테스트 하나로 좁히기
- 추측에 기반한 추론에서 직접 관찰로 전환하기
- 고위험이거나 외부에서 차단된 실패는 사람에게 에스컬레이션하기

"에이전트 상태 재설정" 또는 "하네스 설정 업데이트" 같은 근거 없는 자동 치유 조치는 현재 환경에서 실제 도구로 수행하지 않는 한 주장하지 마세요.

격리된 회복 체크리스트:

```markdown
## 회복 조치
- 선택한 진단:
- 취한 가장 작은 조치:
- 이것이 안전한 이유:
- 수정이 효과가 있었음을 증명할 증거:
```

### 4단계: 자기 점검 보고서

다음 에이전트나 사람이 회복 과정을 알아볼 수 있도록 보고서로 마무리합니다.

```markdown
## 에이전트 자기 디버그 보고서
- 세션 / 작업:
- 실패:
- 근본 원인:
- 회복 조치:
- 결과: success | partial | blocked
- 토큰 / 시간 소모 위험:
- 필요한 후속 조치:
- 나중에 반영할 예방 변경:
```

## 회복 휴리스틱

다음 개입을 순서대로 우선합니다.

1. 실제 목표를 한 문장으로 다시 진술합니다.
2. 기억을 믿지 말고 세계 상태를 검증합니다.
3. 실패한 범위를 줄입니다.
4. 결정적인 확인을 하나 실행합니다.
5. 그 후에만 재시도합니다.

나쁜 패턴:
- 표현만 조금씩 바꿔 같은 행동을 세 번 재시도하기

좋은 패턴:
- 실패 캡처
- 패턴 분류
- 직접 확인 하나 실행
- 확인이 뒷받침할 때만 계획 변경

## ECC와의 통합

- 회복 후 코드가 변경되었다면 `verification-loop`를 사용합니다.
- 실패 패턴이 본능(instinct)이나 나중의 스킬로 만들 가치가 있다면 `continuous-learning-v2`를 사용합니다.
- 문제가 기술적 실패가 아니라 결정의 모호함이라면 `council`을 사용합니다.
- 실패가 충돌하는 로컬 상태나 저장소 드리프트에서 왔다면 `workspace-surface-audit`를 사용합니다.

## 출력 기준

이 스킬이 활성화되어 있을 때는 "고쳤습니다"라는 말만으로 끝내지 마세요.

반드시 다음을 제공합니다.
- 실패 패턴
- 근본 원인 가설
- 회복 조치
- 상황이 나아졌는지 또는 여전히 차단되어 있는지에 대한 증거
