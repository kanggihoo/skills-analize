# 아키텍처 결정 기록 (ADR)

코딩 세션 중에 이루어지는 아키텍처 결정을 그때그때 기록합니다. 결정이 Slack 스레드, PR 코멘트, 또는 누군가의 기억 속에만 남아 있지 않도록, 이 스킬은 코드와 함께 보관되는 구조화된 ADR 문서를 만듭니다.

## 사용 시점

- 사용자가 명시적으로 "이 결정을 기록하자" 또는 "ADR로 남겨줘"라고 말할 때
- 사용자가 중요한 대안(프레임워크, 라이브러리, 패턴, 데이터베이스, API 설계) 사이에서 선택할 때
- 사용자가 "우리는 ~하기로 했다" 또는 "우리가 Y 대신 X를 하는 이유는 ~이다"라고 말할 때
- 사용자가 "왜 X를 선택했지?"라고 물을 때 (기존 ADR을 읽음)
- 계획 단계에서 아키텍처 트레이드오프가 논의될 때

## ADR 형식

Michael Nygard가 제안한 경량 ADR 형식을 AI 보조 개발에 맞게 조정하여 사용합니다.

```markdown
# ADR-NNNN: [결정 제목]

**Date**: YYYY-MM-DD
**Status**: proposed | accepted | deprecated | superseded by ADR-NNNN
**Deciders**: [참여자]

## Context

우리가 마주한 어떤 문제가 이 결정이나 변경을 촉발했는가?

[상황, 제약, 작용하는 힘을 2-5문장으로 설명]

## Decision

우리가 제안하거나 실행하는 변경은 무엇인가?

[결정을 명확하게 1-3문장으로 서술]

## Alternatives Considered

### Alternative 1: [이름]
- **Pros**: [장점]
- **Cons**: [단점]
- **Why not**: [이 대안을 기각한 구체적 이유]

### Alternative 2: [이름]
- **Pros**: [장점]
- **Cons**: [단점]
- **Why not**: [이 대안을 기각한 구체적 이유]

## Consequences

이 변경으로 인해 무엇이 더 쉬워지거나 더 어려워지는가?

### Positive
- [이점 1]
- [이점 2]

### Negative
- [트레이드오프 1]
- [트레이드오프 2]

### Risks
- [위험과 완화 방법]
```

## 워크플로

### 새 ADR 기록하기

결정 시점이 감지되면:

1. **초기화 (최초 1회만)** — `docs/adr/`가 없으면, 디렉터리, 인덱스 테이블 헤더로 시드된 `README.md`(아래 ADR 인덱스 형식 참조), 수동 사용을 위한 빈 `template.md`를 만들기 전에 사용자에게 확인을 받으세요. 명시적 동의 없이 파일을 만들지 마세요.
2. **결정 식별** — 핵심 아키텍처 선택이 무엇인지 추출
3. **맥락 수집** — 어떤 문제가 이것을 촉발했는가? 어떤 제약이 있는가?
4. **대안 문서화** — 검토된 다른 선택지는 무엇인가? 왜 기각되었는가?
5. **결과 명시** — 트레이드오프는 무엇인가? 무엇이 더 쉬워지고/어려워지는가?
6. **번호 부여** — `docs/adr/`의 기존 ADR을 스캔하여 번호를 1 증가
7. **확인 후 작성** — 초안 ADR을 사용자에게 검토용으로 제시. 명시적 승인을 받은 후에만 `docs/adr/NNNN-decision-title.md`에 씁니다. 사용자가 거절하면 파일을 쓰지 않고 초안을 버립니다.
8. **인덱스 갱신** — `docs/adr/README.md`에 추가

### 기존 ADR 읽기

사용자가 "왜 X를 선택했지?"라고 물을 때:

1. `docs/adr/`가 존재하는지 확인 — 없으면 다음과 같이 응답: "이 프로젝트에는 ADR이 없습니다. 아키텍처 결정을 기록하기 시작할까요?"
2. 존재하면 `docs/adr/README.md` 인덱스에서 관련 항목을 찾기
3. 일치하는 ADR 파일을 읽고 Context와 Decision 섹션을 제시
4. 일치하는 것이 없으면 다음과 같이 응답: "해당 결정에 대한 ADR을 찾지 못했습니다. 지금 기록해둘까요?"

### ADR 디렉터리 구조

```
docs/
└── adr/
    ├── README.md              ← 모든 ADR의 인덱스
    ├── 0001-use-nextjs.md
    ├── 0002-postgres-over-mongo.md
    ├── 0003-rest-over-graphql.md
    └── template.md            ← 수동 사용을 위한 빈 템플릿
```

### ADR 인덱스 형식

```markdown
# Architecture Decision Records

| ADR | Title | Status | Date |
|-----|-------|--------|------|
| [0001](0001-use-nextjs.md) | Use Next.js as frontend framework | accepted | 2026-01-15 |
| [0002](0002-postgres-over-mongo.md) | PostgreSQL over MongoDB for primary datastore | accepted | 2026-01-20 |
| [0003](0003-rest-over-graphql.md) | REST API over GraphQL | accepted | 2026-02-01 |
```

## 결정 감지 신호

대화에서 아키텍처 결정을 나타내는 다음 패턴을 주시하세요.

**명시적 신호**
- "X로 가자"
- "Y 대신 X를 쓰자"
- "그 트레이드오프는 ~때문에 가치가 있다"
- "이것을 ADR로 기록해줘"

**암묵적 신호** (ADR 기록을 제안할 것 — 사용자 확인 없이 자동 생성하지 말 것)
- 두 프레임워크나 라이브러리를 비교하고 결론에 도달할 때
- 근거를 밝히며 데이터베이스 스키마를 설계할 때
- 아키텍처 패턴을 선택할 때 (모놀리스 vs 마이크로서비스, REST vs GraphQL)
- 인증/인가 전략을 결정할 때
- 대안을 평가한 뒤 배포 인프라를 선택할 때

## 좋은 ADR의 조건

### 할 것
- **구체적으로 쓰기** — "ORM을 쓴다"가 아니라 "Prisma ORM을 쓴다"
- **이유를 기록하기** — 근거가 무엇인지보다 왜인지가 더 중요하다
- **기각된 대안을 포함하기** — 미래의 개발자는 무엇이 고려되었는지 알아야 한다
- **결과를 솔직하게 명시하기** — 모든 결정에는 트레이드오프가 있다
- **짧게 유지하기** — ADR은 2분 안에 읽을 수 있어야 한다
- **현재 시제 사용하기** — "We will use X"가 아니라 "We use X"

### 하지 말 것
- 사소한 결정을 기록하지 않기 — 변수 이름이나 포매팅 선택은 ADR이 필요 없다
- 에세이를 쓰지 않기 — Context 섹션이 10줄을 넘으면 너무 길다
- 대안을 생략하지 않기 — "그냥 골랐다"는 유효한 근거가 아니다
- 과거 결정을 소급 기록할 때 표시하지 않고 넣지 않기 — 원래 날짜를 명시하라
- ADR이 낡도록 방치하지 않기 — 대체된 결정은 그 대체물을 참조해야 한다

## ADR 수명 주기

```
proposed → accepted → [deprecated | superseded by ADR-NNNN]
```

- **proposed**: 결정이 논의 중이며, 아직 확정되지 않음
- **accepted**: 결정이 효력을 가지며 준수되고 있음
- **deprecated**: 결정이 더 이상 관련이 없음 (예: 기능이 제거됨)
- **superseded**: 더 새로운 ADR이 이를 대체함 (대체 ADR을 반드시 링크할 것)

## 기록할 가치가 있는 결정의 범주

| 범주 | 예시 |
|----------|---------|
| **기술 선택** | 프레임워크, 언어, 데이터베이스, 클라우드 제공자 |
| **아키텍처 패턴** | 모놀리스 vs 마이크로서비스, 이벤트 기반, CQRS |
| **API 설계** | REST vs GraphQL, 버전 관리 전략, 인증 방식 |
| **데이터 모델링** | 스키마 설계, 정규화 결정, 캐싱 전략 |
| **인프라** | 배포 모델, CI/CD 파이프라인, 모니터링 스택 |
| **보안** | 인증 전략, 암호화 방식, 시크릿 관리 |
| **테스트** | 테스트 프레임워크, 커버리지 목표, E2E와 통합 테스트의 균형 |
| **프로세스** | 브랜칭 전략, 리뷰 프로세스, 릴리스 주기 |

## 다른 스킬과의 연동

- **Planner 에이전트**: planner가 아키텍처 변경을 제안하면 ADR 작성을 제안
- **Code reviewer 에이전트**: 대응하는 ADR 없이 아키텍처 변경을 도입하는 PR을 표시
