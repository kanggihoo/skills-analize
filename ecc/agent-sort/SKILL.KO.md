# Agent Sort

저장소에 기본 전체 설치 대신 프로젝트 맞춤형 ECC 구성이 필요할 때 이 스킬을 사용하세요.

목표는 "유용해 보이는 것"을 짐작하는 것이 아닙니다. 실제 코드베이스에서 얻은 근거로 ECC 구성 요소를 분류하는 것입니다.

## 사용 시점

- 프로젝트에 ECC의 일부만 필요하고, 전체 설치는 너무 시끄러울 때
- 저장소의 스택은 분명하지만 스킬을 하나씩 직접 고르고 싶지 않을 때
- 팀이 의견이 아니라 grep 근거에 기반한 반복 가능한 설치 결정을 원할 때
- 매번 로드되는 일상 워크플로 요소와, 검색 가능한 라이브러리/참고 요소를 분리해야 할 때
- 저장소에 잘못된 언어, 규칙, 훅 세트가 들어가 정리가 필요할 때

## 협상 불가 규칙

- 일반적인 선호가 아니라 현재 저장소를 진실의 원천으로 삼으세요
- 모든 DAILY 결정에는 구체적인 저장소 근거가 있어야 합니다
- LIBRARY는 "삭제"를 뜻하지 않습니다. 기본으로 로드하지 않되 접근은 가능하게 둔다는 뜻입니다
- 현재 저장소에서 사용할 수 없는 훅, 규칙, 스크립트는 설치하지 마세요
- ECC 기본 요소를 우선하고, 두 번째 설치 시스템을 도입하지 마세요

## 분류 모델

두 범주만 사용합니다:

- `DAILY`
  - 이 저장소의 모든 세션에서 매번 로드되어야 함
  - 저장소의 언어, 프레임워크, 워크플로, 또는 운영 표면과 강하게 맞음
- `LIBRARY`
  - 보관할 가치는 있지만 기본으로 로드할 가치는 없음
  - 검색, 라우터 스킬, 또는 선택적 수동 사용을 통해 계속 접근 가능해야 함

## 근거 출처

분류하기 전에 저장소 내부의 근거를 사용하세요:

- 파일 확장자
- 패키지 관리자와 lockfile
- 프레임워크 설정
- CI 및 훅 설정
- 빌드/테스트 스크립트
- import와 의존성 매니페스트
- 스택을 명시적으로 설명하는 저장소 문서

유용한 명령은 다음과 같습니다:

```bash
rg --files
rg -n "typescript|react|next|supabase|django|spring|flutter|swift"
cat package.json
cat pyproject.toml
cat Cargo.toml
cat pubspec.yaml
cat go.mod
```

## 병렬 검토 단계

병렬 서브에이전트를 사용할 수 있다면, 검토를 다음 단계로 나누세요:

1. Agents
   - `agents/*` 분류
2. Skills
   - `skills/*` 분류
3. Commands
   - `commands/*` 분류
4. Rules
   - `rules/*` 분류
5. Hooks and scripts
   - 훅 표면, MCP 상태 점검, 헬퍼 스크립트, OS 호환성 분류
6. Extras
   - 컨텍스트, 예시, MCP 설정, 템플릿, 가이드 문서 분류

서브에이전트를 쓸 수 없다면 같은 단계를 순차적으로 실행하세요.

## 핵심 작업 흐름

### 1. 저장소 읽기

무엇이든 분류하기 전에 실제 스택을 파악하세요:

- 사용 중인 언어
- 사용 중인 프레임워크
- 주 패키지 관리자
- 테스트 스택
- 린트/포맷 스택
- 배포/런타임 표면
- 이미 존재하는 운영 연동

### 2. 근거 표 만들기

후보 표면마다 다음을 기록하세요:

- 구성 요소 경로
- 구성 요소 유형
- 제안된 범주
- 저장소 근거
- 짧은 이유

다음 형식을 사용하세요:

```text
skills/frontend-patterns | skill | DAILY | .tsx 파일 84개, next.config.ts 존재 | 핵심 프론트엔드 스택
skills/django-patterns   | skill | LIBRARY | .py 파일 없음, pyproject.toml 없음    | 이 저장소에서 활성 아님
rules/typescript/*       | rules | DAILY | package.json + tsconfig.json            | 활성 TS 저장소
rules/python/*           | rules | LIBRARY | Python 소스 파일 0개                    | 접근만 가능하게 유지
```

### 3. DAILY 또는 LIBRARY 결정

다음의 경우 `DAILY`로 올리세요:

- 저장소가 해당 스택을 분명히 사용할 때
- 구성 요소가 모든 세션에 도움이 될 만큼 범용적일 때
- 저장소가 이미 해당 런타임이나 워크플로에 의존할 때

다음의 경우 `LIBRARY`로 내리세요:

- 구성 요소가 스택과 맞지 않을 때
- 나중에는 필요할 수 있지만 매일 필요하지는 않을 때
- 즉각적인 관련성 없이 컨텍스트 부담만 늘릴 때

### 4. 설치 계획 만들기

분류를 실행 가능한 조치로 바꾸세요:

- DAILY 스킬 -> `.claude/skills/`에 설치하거나 유지
- DAILY 명령 -> 여전히 유용한 경우에만 명시적 shim으로 유지
- DAILY 규칙 -> 일치하는 언어 세트만 설치
- DAILY 훅/스크립트 -> 호환되는 것만 유지
- LIBRARY 표면 -> 검색 또는 `skill-library`를 통해 접근 가능하게 유지

저장소가 이미 선택적 설치를 사용한다면, 다른 시스템을 만들지 말고 그 계획을 갱신하세요.

### 5. 선택적 라이브러리 라우터 만들기

프로젝트가 검색 가능한 라이브러리 표면을 원한다면 다음을 만드세요:

- `.claude/skills/skill-library/SKILL.md`

이 라우터에는 다음이 들어 있어야 합니다:

- DAILY와 LIBRARY의 차이에 대한 짧은 설명
- 그룹으로 묶은 트리거 키워드
- 라이브러리 참고 문서가 위치한 곳

라우터 안에 모든 스킬 본문을 복제하지 마세요.

### 6. 결과 검증

계획을 적용한 후 다음을 확인하세요:

- 모든 DAILY 파일이 예상한 위치에 있는지
- 오래된 언어 규칙이 활성 상태로 남아 있지 않은지
- 호환되지 않는 훅이 설치되지 않았는지
- 최종 설치가 저장소 스택과 실제로 맞는지

다음을 담은 간결한 보고서를 반환하세요:

- DAILY 개수
- LIBRARY 개수
- 제거된 오래된 표면
- 미해결 질문

## 핸드오프

다음 단계가 대화형 설치나 복구라면 다음으로 넘기세요:

- `configure-ecc`

다음 단계가 중복 정리나 카탈로그 검토라면 다음으로 넘기세요:

- `skill-stocktake`

다음 단계가 더 넓은 컨텍스트 정리라면 다음으로 넘기세요:

- `strategic-compact`

## 출력 형식

결과를 다음 순서로 반환하세요:

```text
STACK
- 언어/프레임워크/런타임 요약

DAILY
- 근거와 함께 항상 로드되는 항목

LIBRARY
- 근거와 함께 검색/참고용 항목

INSTALL PLAN
- 설치, 제거, 또는 라우팅할 항목

VERIFICATION
- 실행한 검사와 남은 공백
```
