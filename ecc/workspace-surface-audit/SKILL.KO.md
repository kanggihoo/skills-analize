# Workspace Surface Audit

"이 워크스페이스와 이 머신이 지금 실제로 무엇을 할 수 있으며, 다음에 무엇을 추가하거나 활성화해야 하는가?"라는 질문에 답하는 읽기 전용 감사 스킬입니다.

이것은 설정 감사 플러그인에 대한 ECC 네이티브 답변입니다. 사용자가 후속 구현을 명시적으로 요청하지 않는 한 파일을 수정하지 않습니다.

## 사용 시점

- 사용자가 "set up Claude Code", "recommend automations", "what plugins or MCPs should I use?", "what am I missing?"라고 말할 때
- 스킬, hooks, 커넥터를 더 설치하기 전에 머신이나 저장소를 감사할 때
- 공식 마켓플레이스 플러그인과 ECC 네이티브 커버리지를 비교할 때
- `.env`, `.mcp.json`, 플러그인 설정, 연결된 앱 surface를 검토해 빠진 워크플로 계층을 찾을 때
- 어떤 기능을 스킬, hook, 에이전트, MCP, 외부 커넥터 중 무엇으로 만들지 결정할 때

## 타협할 수 없는 규칙

- 비밀 값을 절대 출력하지 마세요. 제공자 이름, 기능 이름, 파일 경로, 키나 설정이 존재하는지 여부만 드러냅니다.
- ECC가 합리적으로 소유할 수 있는 surface라면, 일반적인 "다른 플러그인을 설치하세요" 조언보다 ECC 네이티브 워크플로를 우선합니다.
- 외부 플러그인은 권위 있는 제품 경계가 아니라 벤치마크와 영감의 원천으로 취급합니다.
- 다음 세 가지를 명확히 구분합니다.
  - 지금 이미 사용할 수 있는 것
  - 사용할 수 있지만 ECC에서 잘 감싸여 있지 않은 것
  - 사용할 수 없으며 새로운 통합이 필요한 것

## 감사 입력

질문에 잘 답하는 데 필요한 파일과 설정만 점검합니다.

1. 저장소 surface
   - `package.json`, 잠금 파일, 언어 마커, 프레임워크 설정, `README.md`
   - `.mcp.json`, `.lsp.json`, `.claude/settings*.json`, `.codex/*`
   - `AGENTS.md`, `CLAUDE.md`, 설치 매니페스트, hook 설정
2. 환경 surface
   - 활성 저장소와 명백히 인접한 ECC 워크스페이스의 `.env*` 파일
   - `STRIPE_API_KEY`, `TWILIO_AUTH_TOKEN`, `FAL_KEY`처럼 키 이름만 surface합니다.
3. 연결된 도구 surface
   - 설치된 플러그인, 활성화된 커넥터, MCP 서버, LSP, 앱 통합
4. ECC surface
   - 필요를 이미 다루고 있는 기존 스킬, 명령, hooks, 에이전트, 설치 모듈

## 감사 과정

### 1단계: 존재하는 것 목록화

간결한 목록을 만듭니다.

- 활성 하네스 대상
- 설치된 플러그인과 연결된 앱
- 설정된 MCP 서버
- 설정된 LSP 서버
- 키 이름으로 암시되는 환경 변수 기반 서비스
- 워크스페이스와 관련된 기존 ECC 스킬

surface가 원시 기능으로만 존재한다면 이를 명시합니다. 예를 들면 다음과 같습니다.

- "Stripe is available via connected app, but ECC lacks a billing-operator skill"
- "Google Drive is connected, but there is no ECC-native Google Workspace operator workflow"

### 2단계: 공식 및 설치된 surface와 비교

워크스페이스를 다음과 비교합니다.

- 설정, 리뷰, 문서, 디자인, 워크플로 품질과 겹치는 공식 Claude 플러그인
- Claude 또는 Codex에 로컬로 설치된 플러그인
- 사용자가 현재 연결한 앱 surface

이름만 나열하지 마세요. 각 비교에 대해 다음에 답합니다.

1. 실제로 무엇을 하는가
2. ECC가 이미 동등한 기능을 갖추고 있는가
3. ECC에는 원시 기능만 있는가
4. ECC에 워크플로 자체가 빠져 있는가

### 3단계: 격차를 ECC 결정으로 바꾸기

실제 격차마다 올바른 ECC 네이티브 형태를 추천합니다.

| 격차 유형 | 권장 ECC 형태 |
|----------|---------------------|
| 반복 가능한 운영자 워크플로 | Skill |
| 자동 강제 또는 부수 효과 | Hook |
| 특화된 위임 역할 | Agent |
| 외부 도구 브리지 | MCP server 또는 connector |
| 설치/부트스트랩 안내 | 설정 또는 감사 스킬 |

필요가 인프라가 아니라 운영적인 것이라면, 기본값으로 기존 도구를 조율하는 사용자 대면 스킬을 제안합니다.

## 출력 형식

다섯 개 섹션을 이 순서대로 반환합니다.

1. **현재 surface**
   - 지금 바로 사용 가능한 것
2. **동등성(Parity)**
   - ECC가 벤치마크와 일치하거나 능가하는 부분
3. **원시 기능만 있는 격차**
   - 도구는 있지만 ECC에 깔끔한 운영자 스킬이 없는 것
4. **누락된 통합**
   - 아직 사용할 수 없는 기능
5. **상위 3-5개 다음 조치**
   - 영향도 순으로 정렬한, 구체적인 ECC 네이티브 추가 사항

## 추천 규칙

- 카테고리마다 가장 가치가 높은 아이디어를 최대 1-2개만 추천합니다.
- 사용자 의도와 비즈니스 가치가 분명한 스킬을 선호합니다.
  - 설정 감사
  - 결제/고객 운영
  - 이슈/프로그램 운영
  - Google Workspace 운영
  - 배포/운영 제어
- 커넥터가 회사 특화라면, 실제로 사용할 수 있거나 사용자의 워크플로에 분명히 유용할 때만 추천합니다.
- ECC에 강력한 원시 기능이 이미 있다면, 완전히 새로운 하위 시스템을 만들기보다 래퍼 스킬을 제안합니다.

## 좋은 결과

- 사용자가 무엇이 연결되어 있고, 무엇이 빠져 있으며, ECC가 다음에 무엇을 소유해야 하는지 즉시 알 수 있습니다.
- 추천이 충분히 구체적이어서, 추가 탐색 없이 저장소에서 바로 구현할 수 있습니다.
- 최종 답변은 API 브랜드가 아니라 워크플로를 중심으로 구성됩니다.
