# 에이전트 아키텍처 감사

래퍼 계층, 오래된 메모리, 재시도 루프, 전송/렌더링 변형 뒤에 실패를 숨기는 에이전트 시스템을 위한 진단 워크플로입니다.

## 활성화 시점

**필수 상황:**
- 에이전트 또는 LLM 기반 애플리케이션을 프로덕션에 릴리스할 때
- 도구 호출, 메모리, 다단계 워크플로를 포함한 기능을 출시할 때
- 래퍼 계층을 추가한 뒤 에이전트 동작이 나빠질 때
- 사용자가 "에이전트가 점점 나빠지고 있다" 또는 "도구가 불안정하다"고 보고할 때
- 같은 모델이 플레이그라운드에서는 잘 동작하지만 래퍼 안에서는 깨질 때
- 근본 원인을 찾지 못한 채 15분 넘게 에이전트 동작을 디버깅하고 있을 때

**특히 중요한 경우:**
- 새로운 프롬프트 계층, 도구 정의, 메모리 시스템을 추가했을 때
- 시스템 내 서로 다른 에이전트들이 일관되지 않게 동작할 때
- 어제까지 모델이 괜찮았는데 오늘 환각을 일으킬 때
- 숨겨진 수리/재시도 루프가 응답을 조용히 변형하고 있다고 의심될 때

**사용하지 않는 경우:**
- 일반적인 코드 디버깅 — `agent-introspection-debugging` 사용
- 코드 리뷰 — 언어별 리뷰어 에이전트 사용
- 보안 스캔 — `security-review` 또는 `security-review/scan` 사용
- 에이전트 성능 벤치마킹 — `agent-eval` 사용
- 새 기능 작성 — 적절한 워크플로 스킬 사용

## 12계층 스택

모든 에이전트 시스템에는 다음 계층이 있습니다. 어느 계층이든 답변을 손상시킬 수 있습니다.

| # | 계층 | 무엇이 잘못되는가 |
|---|------|------------------|
| 1 | 시스템 프롬프트 | 상충하는 지시, 지시문 비대화 |
| 2 | 세션 히스토리 | 이전 턴에서 온 오래된 컨텍스트 주입 |
| 3 | 장기 메모리 | 세션 간 오염, 새 대화에 등장하는 오래된 주제 |
| 4 | 증류(Distillation) | 압축된 산출물이 가짜 사실로 재유입 |
| 5 | 능동 회상(Active recall) | 중복된 재요약 계층이 컨텍스트를 낭비 |
| 6 | 도구 선택 | 잘못된 도구 라우팅, 모델이 필수 도구를 건너뜀 |
| 7 | 도구 실행 | 환각 실행 — 호출한다고 주장하지만 실제로는 호출하지 않음 |
| 8 | 도구 해석 | 도구 출력을 잘못 읽거나 무시함 |
| 9 | 답변 형성 | 최종 응답의 형식 손상 |
| 10 | 플랫폼 렌더링 | 전송 계층 변형 (UI, API, CLI가 올바른 답변을 변형) |
| 11 | 숨겨진 복구 루프 | 두 번째 LLM 패스를 실행하는 조용한 폴백/재시도 에이전트 |
| 12 | 영속성 | 만료된 상태 또는 캐시된 산출물이 실시간 증거로 재사용됨 |

## 흔한 실패 패턴

### 1. 래퍼 회귀

기본 모델은 올바른 답변을 내지만, 래퍼 계층이 상황을 더 나쁘게 만듭니다.

**증상:**
- 플레이그라운드나 직접 API 호출에서는 잘 동작하지만 에이전트 안에서는 깨짐
- 새 프롬프트 계층을 추가한 뒤 기존 동작이 저하됨
- 에이전트가 확신에 차 있지만 확신을 갖고 틀림
- "지난 업데이트 전까지는 잘 동작했다"

### 2. 메모리 오염

오래된 주제가 히스토리, 메모리 검색, 또는 증류를 통해 새 대화로 새어 나옵니다.

**증상:**
- 에이전트가 관련 없는 과거 주제를 꺼냄
- 사용자의 정정이 유지되지 않음 (오래된 메모리가 새 내용을 덮어씀)
- 같은 세션의 산출물이 가짜 사실로 재유입됨
- 메모리가 무한정 커지며 시간이 지날수록 응답 품질이 저하됨

### 3. 도구 사용 규율 실패

도구가 프롬프트에 선언되어 있지만 코드에서 강제되지 않습니다. 모델이 도구를 건너뛰거나 실행을 환각합니다.

**증상:**
- 프롬프트에 "도구 X를 반드시 사용하라"고 되어 있지만 모델이 호출하지 않고 답변함
- 도구 결과가 맞아 보이지만 실제로는 실행되지 않았음
- 서로 다른 도구들이 같은 책임을 두고 충돌함
- 사용하면 안 될 때 도구를 쓰거나, 반드시 써야 할 때 건너뜀

### 4. 렌더링/전송 손상

에이전트의 내부 답변은 올바르지만, 전달 과정에서 플랫폼 계층이 이를 변형합니다.

**증상:**
- 로그에는 올바른 답변이 보이지만 사용자는 깨진 출력을 봄
- 마크다운 렌더링, JSON 파싱, 스트리밍 조각화가 올바른 응답을 손상시킴
- 숨겨진 폴백 에이전트가 전달 전에 답변을 조용히 교체함
- 터미널과 UI에서 출력이 다름

### 5. 숨겨진 에이전트 계층

명시적 계약 없이 조용한 수리, 재시도, 요약, 회상 에이전트가 실행됩니다.

**증상:**
- 내부 생성과 사용자 전달 사이에 출력이 바뀜
- 사용자가 모르는 두 번째 LLM 패스를 돌리는 "자동 수정" 루프
- 여러 에이전트가 조정 없이 같은 출력을 수정함
- 보이지 않는 계층에 의해 답변이 "다듬어지거나" "교정됨"

## 감사 워크플로

### 1단계: 범위 정의

감사 대상을 정의합니다.

- **대상 시스템** — 어떤 에이전트 애플리케이션인가?
- **진입점** — 사용자는 어떻게 상호작용하는가?
- **모델 스택** — 어떤 LLM과 제공자를 쓰는가?
- **증상** — 사용자가 무엇을 보고했는가?
- **시간 범위** — 언제 시작되었는가?
- **감사할 계층** — 12개 계층 중 어느 것이 해당하는가?

### 2단계: 증거 수집

코드베이스에서 증거를 모읍니다.

- **소스 코드** — 에이전트 루프, 도구 라우터, 메모리 승인, 프롬프트 조립
- **로그** — 과거 세션 트레이스, 도구 호출 기록
- **설정** — 프롬프트 템플릿, 도구 스키마, 제공자 설정
- **메모리 파일** — SOP, 지식 베이스, 세션 아카이브

`rg`로 안티 패턴을 검색합니다.

```bash
# 코드가 아니라 프롬프트 텍스트에만 표현된 도구 요구사항
rg "must.*tool|必须.*工具|required.*call" --type md

# 검증 없이 실행되는 도구 호출
rg "tool_call|toolCall|tool_use" --type py --type ts

# 메인 에이전트 루프 밖의 숨겨진 LLM 호출
rg "completion|chat\.create|messages\.create|llm\.invoke"

# 사용자 정정 우선순위 없이 이루어지는 메모리 승인
rg "memory.*admit|long.*term.*update|persist.*memory" --type py --type ts

# 추가 LLM 호출을 실행하는 폴백 루프
rg "fallback|retry.*llm|repair.*prompt|re-?prompt" --type py --type ts

# 조용한 출력 변형
rg "mutate|rewrite.*response|transform.*output|shap" --type py --type ts
```

### 3단계: 실패 매핑

각 발견 사항에 대해 다음을 기록합니다.

- **증상** — 사용자가 보는 것
- **메커니즘** — 래퍼가 그것을 어떻게 일으키는지
- **원인 계층** — 12개 계층 중 어느 것인지
- **근본 원인** — 가장 깊은 원인
- **증거** — file:line 또는 log:row 참조
- **신뢰도** — 0.0에서 1.0 사이

### 4단계: 수정 전략

기본 수정 순서(프롬프트 우선이 아니라 코드 우선)입니다.

1. **도구 요구사항을 코드로 게이트** — 프롬프트 텍스트만이 아니라 코드에서 강제
2. **숨겨진 수리 에이전트를 제거하거나 축소** — 폴백을 계약이 있는 명시적 형태로 만들기
3. **컨텍스트 중복 줄이기** — 같은 정보가 프롬프트 + 히스토리 + 메모리 + 증류로 중복 전달되는 경우
4. **메모리 승인 강화** — 사용자 정정 > 에이전트의 주장
5. **증류 트리거 강화** — 압축하면 안 되는 것은 압축하지 않기
6. **렌더링 변형 줄이기** — 변형하지 말고 그대로 통과시키기
7. **타입이 있는 JSON 엔벨로프로 전환** — 자유형 산문이 아니라 구조화된 내부 흐름

## 심각도 모델

| 수준 | 의미 | 조치 |
|------|------|------|
| `critical` | 에이전트가 확신을 갖고 잘못된 운영 동작을 만들어 낼 수 있음 | 다음 릴리스 전에 수정 |
| `high` | 에이전트가 자주 정확성이나 안정성을 떨어뜨림 | 이번 스프린트에 수정 |
| `medium` | 정확성은 보통 유지되지만 출력이 취약하거나 낭비적임 | 다음 사이클에 계획 |
| `low` | 대부분 외형적이거나 유지보수성 문제 | 백로그 |

## 출력 형식

사용자에게 발견 사항을 다음 순서로 제시합니다.

1. **심각도 순으로 정렬된 발견 사항** (가장 심각한 것부터)
2. **아키텍처 진단** (어느 계층이 무엇을 왜 손상시켰는지)
3. **순서가 정해진 수정 계획** (프롬프트 우선이 아니라 코드 우선)

칭찬이나 요약으로 시작하지 마세요. 시스템이 고장 났다면 그렇다고 직접 말하세요.

에이전트 시스템을 감사할 때 다음 질문에 답하세요.

|---|------|------------|
| 1 | 모델이 필수 도구를 건너뛰고도 답변할 수 있는가? | 도구가 코드로 게이트되지 않음 |
| 2 | 오래된 대화 내용이 새 턴에 나타나는가? | 메모리 오염 |
| 3 | 같은 정보가 시스템 프롬프트, 메모리, 히스토리에 모두 있는가? | 컨텍스트 중복 |
| 4 | 플랫폼이 전달 전에 두 번째 LLM 패스를 실행하는가? | 숨겨진 복구 루프 |
| 5 | 내부 생성과 사용자 전달 사이에 출력이 달라지는가? | 렌더링 손상 |
| 6 | "도구 X를 반드시 사용하라" 규칙이 프롬프트 텍스트에만 있는가? | 도구 사용 규율 실패 |
| 7 | 에이전트의 자체 독백이 영속 메모리가 될 수 있는가? | 메모리 오염(포이즈닝) |

## 피해야 할 안티 패턴

- 래퍼 계층 회귀를 반증하기 전에 모델을 탓하지 않기.
- 오염 경로를 보여주지 않고 메모리를 탓하지 않기.
- 현재 상태가 깨끗하다고 과거의 오염된 사건을 지우지 않기.
- 마크다운 산문을 신뢰할 수 있는 내부 프로토콜로 취급하지 않기.
- 코드가 강제하지 않는 "도구를 반드시 사용하라"는 프롬프트 텍스트를 받아들이지 않기.
- 발견 사항은 직접적이고, 증거에 기반하며, 심각도 순으로 유지하기.

## 관련 스킬

- `agent-introspection-debugging` — 에이전트 런타임 실패(루프, 타임아웃, 상태 오류) 디버깅
- `agent-eval` — 에이전트 성능을 head-to-head로 벤치마킹
- `security-review` — 코드와 설정에 대한 보안 감사
- `autonomous-agent-harness` — 자율 에이전트 운영 설정
- `agent-harness-construction` — 처음부터 에이전트 하네스 구축
