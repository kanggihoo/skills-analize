# 팀 에이전트 오케스트레이션

에이전트가 단일 어시스턴트가 아니라 팀처럼 관리될 때 이 스킬을 사용합니다. 목적은 팀 기반 오케스트레이션을 신뢰할 수 있게 만드는 것입니다. 이를 위해 명확한 작업 항목, 분명한 담당자 지정, 에이전트 칸반 상태, 브랜치 격리, 컨트롤 패널 가시성, 병합 게이트를 갖춥니다.

## 활성화 시점

- 작업이 여러 에이전트, 도구, 하네스, 브랜치, 워크트리에 걸쳐 있을 때
- 사용자가 팀 오케스트레이션, 에이전트 칸반, 스쿼드, 컨덕터, 컨트롤 패널, 매니저, 데스크톱 앱, Zellij, tmux, Hermes, Devin, Codex, Claude Code, 멀티 에이전트 작업을 언급할 때
- 프로젝트에 사람과 에이전트가 함께 쓰는 공유 워크플로 상태가 필요할 때
- 기존 에이전트 팬아웃이 결과물은 만들어 내지만 병합 가능한 제품으로 이어지지 않을 때

## 운영 모델

모든 에이전트를 좁은 계약을 가진 팀원으로 다룹니다.

- **담당자(Owner)**: 작업 항목에 대해 책임을 지는 사람 또는 에이전트
- **범위(Scope)**: 파일, 브랜치, 도구 범위, 금지 영역
- **상태(State)**: backlog, ready, running, review, blocked, merged, archived 중 하나
- **근거(Evidence)**: 테스트, 스크린샷, 로그, 리뷰 노트, 평가 리포트
- **병합 게이트(Merge gate)**: 통합을 허용하는 정확한 조건

## 에이전트 칸반

작업이 여러 세션에 걸쳐 보여야 할 때 에이전트 칸반을 사용합니다.

| 컬럼 | 의미 | 완료 기준 |
| --- | --- | --- |
| Backlog | 후보 작업 항목, 아직 구체화되지 않음 | 수락 기준이 작성됨 |
| Ready | 구체화되었고 할당 가능함 | 담당자와 브랜치/워크트리가 할당됨 |
| Running | 에이전트가 활발히 작업 중 | 핸드오프 산출물과 변경된 파일이 존재함 |
| Review | 작업은 끝났지만 아직 병합되지 않음 | 테스트, diff 리뷰, 위험 점검 통과 |
| Blocked | 외부 입력이 필요하거나 게이트에 실패함 | 블로커에 담당자와 다음 조치가 있음 |
| Merged | 메인라인에 통합됨 | PR이 병합되었거나 로컬 main이 업데이트됨 |
| Archived | 더 이상 관련 없음 | 사유가 기록됨 |

각 카드는 다음 스키마를 따라야 합니다.

```json
{
  "id": "agent-card-001",
  "title": "Build dynamic workflow skill",
  "owner": "codex",
  "state": "running",
  "branch": "product/dynamic-workflow-team-orchestration",
  "worktree": ".",
  "acceptance": [
    "Skill exists",
    "Tests cover required concepts",
    "Content artifact contains video and article angles"
  ],
  "merge_gate": "lint, focused tests, and catalog check pass",
  "handoff": "path/to/handoff.md"
}
```

## 팀 기반 오케스트레이션 흐름

1. **보드 구성**: 모호한 목표를 담당자와 병합 게이트가 있는 작업 항목으로 바꿉니다.
2. **실행 모드 선택**: 단일 에이전트, 동적 워크플로 모드, dmux/tmux, 워크트리 팬아웃, 외부 데스크톱 오케스트레이터 중에서 고릅니다.
3. **경계 지정**: 카드마다 담당자를 한 명만 두고, 파일 범위를 명확히 하며, 통합 담당자 없이 쓰기가 겹치지 않게 합니다.
4. **에이전트 실행**: 각 에이전트는 코드만이 아니라 근거와 핸드오프 노트를 남깁니다.
5. **순차 리뷰**: 테스트를 먼저 하고, 그다음 diff 리뷰, 보안/위험 점검, 마지막으로 콘텐츠/제품 다듬기를 합니다.
6. **신중하게 병합**: 한 명의 통합 담당자가 충돌을 해결하고 컨트롤 패널이나 상태 산출물을 업데이트합니다.
7. **재사용 가능한 스킬 추출**: 카드 패턴이 반복되면 `skills/`로 승격합니다.

## 컨트롤 패널 요구 사항

팀 오케스트레이션에 유용한 컨트롤 패널은 다음을 보여줘야 합니다.

- 활성 작업 항목과 각 항목의 에이전트 칸반 상태
- 담당자, 하네스, 브랜치, 워크트리, 마지막 하트비트
- 핸드오프 산출물, 테스트, 스크린샷, PR 링크
- 담당자별로 묶고 해제 조치를 함께 보여주는 블로커
- 분위기가 아니라 게이트별로 보여주는 병합 준비 상태
- 공유 스킬로 만들어야 할 재사용 가능한 워크플로 후보

운영자가 다음 질문에 답할 수 있기 전까지는 자동화를 더 추가하지 않습니다. 누가 이것을 담당하는가, 무엇이 바뀌었는가, 어떤 게이트가 실패했는가, 무엇을 안전하게 병합할 수 있는가.

## 동적 워크플로 호환성

카드에 동적 워크플로 모드가 필요할 때:

- 작업 로컬 하네스를 카드 담당자 아래에 둡니다.
- 입력과 출력을 카드에 저장합니다.
- Running에서 Review로 넘어가기 전에 평가를 반드시 거치게 합니다.
- 하네스는 반복 사용된 뒤에만 공유 스킬로 승격합니다.

## 주의해야 할 실패 모드

- **에이전트 수프(Agent soup)**: 에이전트는 많이 돌아가지만 담당자나 병합 게이트가 없음
- **보이지 않는 작업(Invisible work)**: 유용한 결과물이 채팅 기록에만 존재함
- **보드 연극(Board theater)**: 칸반 보드는 있지만 카드에 수락 기준이 없음
- **쓰기 충돌(Overlapping writes)**: 병렬 에이전트가 워크트리 없이 같은 파일을 편집함
- **제품 산출물 부재(No product artifact)**: 프로세스는 문서를 만들지만 실행 가능하거나 배포 가능한 결과물이 없음

## 출력 기준

각 오케스트레이션 주기는 다음을 포함하여 마칩니다.

- 보드/카드 변경 사항
- 병합된 브랜치 또는 대기 중인 브랜치
- 테스트 및 평가 근거
- 담당자와 다음 조치가 포함된 블로커
- 새로운 공유 스킬 후보
