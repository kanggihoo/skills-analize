# Security Bounty Hunter

목표가 일반적인 모범 사례 검토가 아니라, 책임 있는 공개나 바운티 제출을 위한 실용적인 취약점 발견일 때 사용합니다.

## 사용 시점

- 저장소에서 익스플로잇 가능한 취약점을 스캔할 때
- Huntr, HackerOne 또는 유사한 바운티 제출을 준비할 때
- "이론적으로 안전하지 않은가?"가 아니라 "이것이 실제로 보상을 받는가?"를 판단할 때

## 동작 방식

원격에서 도달 가능하고 사용자가 제어할 수 있는 공격 경로에 초점을 맞추고, 플랫폼이 일상적으로 정보성이거나 범위 밖이라며 거부하는 패턴은 버립니다.

## 범위 내 패턴

다음은 꾸준히 중요하게 다뤄지는 유형의 문제입니다.

| 패턴 | CWE | 일반적인 영향 |
| --- | --- | --- |
| 사용자 제어 URL을 통한 SSRF | CWE-918 | 내부 네트워크 접근, 클라우드 메타데이터 탈취 |
| 미들웨어 또는 API 가드의 인증 우회 | CWE-287 | 권한 없는 계정 또는 데이터 접근 |
| 원격 역직렬화 또는 업로드에서 RCE로 이어지는 경로 | CWE-502 | 코드 실행 |
| 도달 가능한 엔드포인트의 SQL 인젝션 | CWE-89 | 데이터 유출, 인증 우회, 데이터 파괴 |
| 요청 핸들러의 명령 인젝션 | CWE-78 | 코드 실행 |
| 파일 제공 경로의 경로 순회 | CWE-22 | 임의 파일 읽기 또는 쓰기 |
| 자동 실행되는 XSS | CWE-79 | 세션 탈취, 관리자 권한 탈취 |

## 제외 대상

프로그램에서 별도로 명시하지 않는 한, 다음은 보통 신호 대비 가치가 낮거나 바운티 범위 밖입니다.

- 원격 경로가 없는 로컬 전용 `pickle.loads`, `torch.load` 또는 동등한 코드
- CLI 전용 도구의 `eval()` 또는 `exec()`
- 완전히 하드코딩된 명령에 대한 `shell=True`
- 그 자체만으로는 보안 헤더 누락
- 익스플로잇 영향 없는 일반적인 레이트 리미팅 불만
- 피해자가 직접 코드를 붙여넣어야 하는 Self-XSS
- 대상 프로그램 범위에 포함되지 않은 CI/CD 인젝션
- 데모, 예제 또는 테스트 전용 코드

## 워크플로우

1. 먼저 범위를 확인합니다: 프로그램 규칙, SECURITY.md, 공개 채널, 제외 항목.
2. 실제 진입점을 찾습니다: HTTP 핸들러, 업로드, 백그라운드 작업, 웹훅, 파서, 연동 엔드포인트.
3. 도움이 되는 경우 정적 분석 도구를 실행하되, 이를 어디까지나 분류(triage) 입력으로만 취급합니다.
4. 실제 코드 경로를 처음부터 끝까지 읽습니다.
5. 사용자 제어 입력이 의미 있는 싱크(sink)에 도달함을 증명합니다.
6. 가장 작고 안전한 PoC로 익스플로잇 가능성과 영향을 확인합니다.
7. 보고서를 작성하기 전에 중복 여부를 확인합니다.

## 분류 루프 예시

```bash
semgrep --config=auto --severity=ERROR --severity=WARNING --json
```

그다음 수동으로 필터링합니다.

- 테스트, 데모, 픽스처, 벤더링된 코드 제외
- 로컬 전용이거나 도달할 수 없는 경로 제외
- 명확한 네트워크 또는 사용자 제어 경로가 있는 발견만 유지

## 보고서 구조

```markdown
## Description
[What the vulnerability is and why it matters]

## Vulnerable Code
[File path, line range, and a small snippet]

## Proof of Concept
[Minimal working request or script]

## Impact
[What the attacker can achieve]

## Affected Version
[Version, commit, or deployment target tested]
```

## 품질 게이트

제출 전 확인 사항:

- 코드 경로가 실제 사용자 또는 네트워크 경계에서 도달 가능한가
- 입력이 실제로 사용자 제어 하에 있는가
- 싱크가 의미 있고 익스플로잇 가능한가
- PoC가 동작하는가
- 이미 어드바이저리, CVE 또는 열린 티켓으로 다뤄진 문제가 아닌가
- 대상이 실제로 바운티 프로그램의 범위 안에 있는가
