# 프롬프트 작성하기

프롬프트에는 의도와 완료 확인 기준을 담습니다. 플레이북이 단계를 제공하므로, 몇 문장의 평이한 글이 사양서보다 낫습니다.

## 넣을 것

- 목표. 무엇이 잘못되었는지, 또는 사용자가 무엇을 원하는지 말하세요.
- 완료 확인 기준. 통과 또는 실패를 판정할 수 있어야 합니다. "더 낫게 만들어 줘"나 기간은 확인 기준이 아닙니다.
- 보여 달라고 요청할 증거. 실제 명령 출력, 흐름의 영상, 저장된 값, 또는 변경 전후 수치를 요청하세요.
- 사용자가 이미 아는 것. 증상, 재현 단계, 로그, 링크가 있으면 에이전트가 검색할 일이 줄어듭니다.
- 실제 제약. "repro first", "don't change any code yet", "zero behavior change", "let me review before proceeding"는 각각 에이전트의 행동을 바꿉니다.

## 빼둘 것

- 방법. 무엇을 이룰지 말하고, 에이전트가 더 나은 방법을 찾을 여지를 남기세요.
- 스킬이나 단계 목록. 손으로 쓴 순서는 플레이북이 유지하는 단계를 빠뜨리거나 순서를 바꿉니다. 한 가지 선택을 덮어쓸 때만 스킬을 지정하세요.
- 에이전트가 문제를 다시 설명하기 전의 사용자 원인 추측. 미리 말한 추측은 탐색 범위를 좁혀 버립니다.

## 먼저 컨텍스트 불러오기

- 잡음이 많은 보고라면, 다른 일을 하기 전에 에이전트에게 근본 문제를 자신의 말로, 쉬운 영어로 다시 설명하게 하세요. 잘못 이해한 부분은 코드가 생기기 전에 드러납니다.
- 새 채팅에서는 `/recall`로 그 주제의 이전 작업을 불러오세요. 오래된 채팅에는 새 에이전트에게 없는 컨텍스트가 있습니다.
- 익숙하지 않은 코드를 바꾸기 전에는 `/how`로 동작 방식을, `/why`로 이유를 확인하세요. 추적된 모델이 없는 에이전트는 가장 먼저 그럴듯한 자리에서 증상을 고칩니다.
- `/teach`에 선택의 근거를 설명하게 하세요. 예를 들어 "convince me it fixes the cause and not the symptom"처럼 말합니다. 근거는 요약보다 검증하기 쉽습니다.

## 설계를 계획보다 먼저

- 첫 설계를 그대로 채택하지 마세요. 여러 옵션의 프로토타입을 요청하고, UI라면 스크린샷이나 영상과 함께 증거를 보고 고르세요.
- 열린 질문은 프로토타입으로 답하게 하세요. 추상적인 계획을 적대적으로 검토하지 마세요. 리뷰어는 실제로 일어나지 않을 위험을 만들어 냅니다.
- 공유 패키지나 API라면 코드보다 README나 튜토리얼을 먼저 요청하세요. 그 문서가 에이전트가 스스로 확인할 목표가 됩니다.
- 설계가 정해진 뒤에만 계획을 요청하세요. 계획의 각 단계는 확인으로 끝나야 합니다.

## 짧게 이어 말하기

- "do it", "continue", "keep going until done"은 채팅에 작업이 이미 있다면 완전한 프롬프트입니다.
- 주제가 바뀌면 "new task"로 시작하세요. 그렇지 않으면 모드가 메시지를 다음 단계로 취급합니다.

## 자리를 비우기 전에

- "im going to bed" 또는 "im stepping away"라고 말해서 에이전트가 질문을 멈추게 하세요.
- 완료 조건을 모든 반복에서 실행할 수 있는 확인으로 적고, `/loop`에 그 판정식을 주세요.
- 이름을 지정한 기준에서 새 worktree를 만들게 하세요.
- 에이전트가 멈추고 물어볼 상황을 미리 답해 두세요. 예를 들어 "don't ask me before committing"처럼 말합니다.
- 나중에 검토할 수 있도록 결정 기록을 요청하세요.
- 출구를 주세요. 예를 들어 "if you're truly stuck after a few hours, stop and write up why"처럼 말합니다.

## 한 줄로 조정하기

- 목표를 다시 말하세요. 예를 들어 "i said the goal is to repro. i did not ask for a fix yet."
- 원칙을 이름으로 말하세요. 예를 들어 "apply prove it works. show me the real output, not the build log."
- 원칙 이름이 효과를 내는 이유는 에이전트가 이미 그 규칙을 읽었기 때문입니다. 에이전트의 답변은 규칙이 바꾼 결정을 명시합니다.
