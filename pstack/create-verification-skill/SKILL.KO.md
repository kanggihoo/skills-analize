# 검증 스킬 만들기

모든 본격적인 프로젝트에는 실제 앱을 스크립트로 구동하고 동작을 증명할 방법이 필요합니다. 앱을 실행하고, 사용자처럼 기능을 사용해 보고, 증거를 수집하는 것이죠. 이 스킬은 그런 기능을 저장소에 맞춰 프로젝트 로컬 스킬(`.cursor/skills/verify-<app>/`)로 생성합니다. 생성기의 출력은 사람이 아니라 다음 에이전트를 위한 것입니다. 앱을 본 적 없는 에이전트가 작업 도중 아무 사전 지식 없이 읽게 되기 때문입니다.

## 1. 사용자가 아니라 저장소를 조사하기

다음 항목은 사용자에게 묻기 전에 코드베이스에서 먼저 확인하세요. 관찰할 수 없는 것만 사용자에게 물어봅니다.

- **표면(Surface):** 사용자가 실제로 접하는 것은 무엇인가? 웹 UI, CLI/TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리? 저장소에 여러 개가 있을 수 있으니 주된 것 하나를 고르고 나머지는 메모해 두세요.
- **실행(Run):** 앱은 로컬에서 어떻게 시작되는가? 저장소가 문서화한 개발 명령(패키지 스크립트, Makefile, README 빠른 시작)을 우선하세요. 포트, 환경 변수, 시드 데이터, 인증을 기록하세요.
- **구동(Drive):** 에이전트가 프로그램으로 어떻게 상호작용할 수 있는가? 기존 하네스를 먼저 찾으세요. Playwright/Cypress 스펙, expect 스크립트, PTY 헬퍼, curl로 호출 가능한 엔드포인트, 디버그 포트 등이 있습니다. 그 다음에만 범용 방식을 고르세요. 웹과 Electron은 browser/CDP, CLI/TUI는 tmux/PTY 하네스, 서비스는 일반 HTTP입니다.
- **관찰(Observe):** 어떤 증거를 수집할 수 있는가? 스크린샷, 터미널 기록, 응답 본문, 로그, 종료 코드, DB 상태 등이 있습니다.
- **격리(Isolate):** 두 인스턴스를 나란히 실행할 수 있는가? (포트, 데이터 디렉터리, 프로필) 불가능하다면 생성된 스킬에 그렇다고 명시하세요. 공유 인스턴스를 중복으로 구동하기를 거부하는 편이, 사용자의 세션을 망가뜨리는 것보다 낫습니다.

체크아웃이 그대로는 빌드되거나 시작되지 않는다면, 생성 전에 먼저 고치거나(또는 정확히 보고하세요). 깨진 기반 위에 쓰인 스킬은 잘못된 단계를 가르치게 됩니다. 시작을 막는 관련 없는 누락 자산(API가 전혀 제공하지 않는 정적 디렉터리, 샘플 설정 등)이 있다면, 생성된 스킬이 이를 검증용 임시 구성물이라고 명확히 표시한 뒤 생성하고, 정리 단계에서 제거하도록 할 수 있습니다.

## 2. 스킬 생성하기

`.cursor/skills/verify-<app>/SKILL.md`를 작성하세요. YAML 프론트매터(`name: verify-<app>`와, 앱 이름, 표면, 그리고 언제 이 스킬을 찾아야 하는지를 담은 `description`)를 포함해야 합니다. 프론트매터가 없으면 스킬이 등록되지 않습니다. 본문에는 다음 섹션을 두고, 각 섹션은 인터뷰에서 실제로 확인한 내용에 근거해야 합니다(자리표시자를 남기지 마세요).

- **Launch(실행):** 검증용으로 앱을 시작하는 정확한 명령과, 준비 완료를 알 수 있는 방법(로그 한 줄, 응답하는 포트, 프롬프트 등)을 적으세요. 종료(teardown) 방법도 포함하세요. 수명이 짧은 CLI나 TUI에는 계속 유지할 서버가 없습니다. 이 경우 "실행"은 바이너리를 한 번 빌드(또는 의존성 설치)하고, 구동할 때마다 격리된 PTY 또는 tmux 세션을 새로 시작하는 것을 뜻합니다.
- **Doctor(점검):** "이 인스턴스를 구동할 가치가 있는가?"에 답하는 읽기 전용 점검 하나를 두세요. 프로세스가 살아 있는지, 올바른 버전/빌드인지, 포트를 우리가 점유하고 있는지, 인증이 유효한지를 확인합니다. 무엇인가 이상해 보일 때마다 에이전트가 가장 먼저 실행하는 명령입니다.
- **Drive(구동):** 실제 셀렉터와 명령을 담은 하네스 절차를 적으세요. 예시가 아니라 이 저장소의 것이어야 합니다. 좌표나 탭 순서보다 안정적인 핸들(ARIA 레이블, data 속성, 프롬프트 문자열, 라우트 경로)을 우선하세요.
- **Evidence(증거):** 증명을 위해 무엇을 캡처하고 어디에 저장하는지 적으세요. 증명 기준도 명시하세요. 실제 사용자 경로를 거쳐야 하며, 내부 setter나 테스트 전용 엔드포인트를 쓰면 안 됩니다. 최종 화면만이 아니라 동작과 그 결과 상태를 함께 캡처하세요. 눈에 보이는 결과와 함께 부수 효과(작성된 파일, 삽입된 행, 전송된 메시지)도 검증하세요. 목(mock)은 운영 환경의 경계가 이미 외부 시스템을 격리하고 있는 곳에서만 쓰세요. 안전한 경로가 드라이런이나 테스트 모드라면, 그 모드가 실제로 무엇을 건너뛰는지 이름만 믿지 말고 관찰(파일, 네트워크, git ref)로 확인하세요. 일부 드라이런은 여전히 네트워크에 접근하거나 브라우저를 엽니다.
- **Cleanup(정리):** 실행이 만든 인스턴스를 어떻게 종료하는지 적으세요. 프로세스 이름으로 죽이지 말고, 직접 시작한 것만 종료하세요. 정리는 인스턴스와 임시 상태를 제거하되, 증거는 절대 지우지 않습니다. 증명 산출물은 스킬이 지정한 위치에 정리 이후에도 남아 있어야 합니다.
- **Helpers(헬퍼):** 스킬이 제공하는 스크립트는 모두 실행 가능해야 하며, 호출 방법을 스킬 본문에 보여 주어야 합니다. 독자가 역공학으로 알아내야 하는 헬퍼는 헬퍼가 아닙니다.

## 3. 기능 맵 채우기

`.cursor/skills/verify-<app>/features/README.md`와, 식별 가능한 사용자 대상 기능마다 파일 하나를 만드세요. 처음에는 상위 3~5개를 목표로 하세요. 라우트, 명령, 메뉴, 문서에서 찾을 수 있습니다. 형식은 [`references/feature-map-example/`](references/feature-map-example/)를 따르세요. README 색인 하나와 기능별 파일 하나로 구성합니다. 각 파일은 사용자 관점에서 다음 네 가지에 답해야 합니다. 기능이 무엇인지, 어떻게 도달하는지, 하네스로 어떻게 구동하는지, 그리고 기능이 동작함을 증명하는 관찰 가능한 최종 상태가 무엇인지. 네 개의 H2 제목은 `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, `Gotchas`입니다. 이 맵은 저장소가 유지 관리하는 검증의 원천입니다. 맵에 다른 진입점이 적혀 있는데도 편리한 진입점 하나만 구동하는 증명은 불완전합니다.

## 4. 넘기기 전에 생성된 스킬을 증명하기

스킬 자체의 지침을 처음부터 끝까지 한 번 실행하세요. 실행, doctor, 매핑된 기능 하나 구동(하나면 충분합니다. 맵은 이후 실행에서 나머지를 다루기 위해 존재합니다), 증거 캡처, 정리 순서입니다. 정리 후에는 증거가 명시된 위치에 여전히 있는지 확인하세요. 정리 과정에서 증명이 사라졌다면 이 단계는 실패입니다. 실패한 항목은 고치고, 실패한 반복마다 생성된 정리 절차도 실행하세요. 그래야 실패한 시도가 프로세스와 포트를 남기지 않습니다. 한 번도 실행되지 않은 생성 스킬은 초안일 뿐, 결과물이 아닙니다.

## 5. 유지 관리 루프 안내하기

앱이 바뀔 때 맵을 정확하게 유지하려면 `/maintain-verification-skill`을 안내하세요. 주기는 사용자가 물어볼 때만 제안하세요.
