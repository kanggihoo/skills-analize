# Notes 검증 맵

이 디렉터리는 Notes의 사용자 대상 동작을 검증하기 위한 유지 관리 원본입니다. 앱을 구동하기 전에 색인을 읽고, 해당하는 기능 파일을 절차로 사용하세요.

## 기본 전제 조건

- 일회용 데이터 디렉터리로 `http://127.0.0.1:4173`에서 Notes를 실행하세요.
- 동시 실행이 상태를 공유하지 않도록 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`를 설정하세요.
- `Quarterly plan`과 `Grocery list` 제목의 노트를 시드하세요.
- `control-notes`와 `notes` CLI를 `PATH`에 두세요.
- `control-notes doctor`를 실행하고, 예상되는 URL, 데이터 디렉터리, 빌드 리비전을 요구하세요.
- 이 검증 실행이 시작하지 않은 인스턴스는 절대 구동하지 마세요.

## 구동 규칙

- 전제 조건에서 달리 명시하지 않는 한, 모든 절차는 기준 상태에서 시작하세요.
- CSS 셀렉터나 DOM 위치보다 ARIA role과 접근 가능한 이름을 우선하세요.
- 모든 명령은 글자 그대로 취급하세요. 따옴표로 묶인 이름과 플래그는 바꾸지 마세요.
- 브라우저 동작은 `control-notes browser`로 실행하세요.
- 터미널 동작은 `control-notes cli -- <command>`로 실행하세요.
- 변경 후에는 시드 데이터를 복원하세요. 정리 과정에서 증명 산출물을 제거하지 마세요.

## 증명과 건너뜀 보고

- 최종 화면만이 아니라 사용자 동작과 그 결과 상태를 캡처하세요.
- UI 증명에는 ARIA 스냅샷과, 앱 식별 정보가 보이는 스크린샷이 포함되어야 합니다.
- CLI 증명에는 명령, stdout, stderr, 종료 코드가 포함되어야 합니다.
- 변경 증명에는 저장된 값을 읽기 전용으로 두 번째로 확인한 결과가 포함되어야 합니다.
- 모든 산출물과 함께 사용한 기능 ID와 진입점을 기록하세요.
- 도달할 수 없는 경로는 시도한 명령과 충족되지 않은 전제 조건을 함께 보고하세요.
- 건너뛴 진입점을 다른 경로로 검증했다고 보고하지 마세요.

## 기능 진입 규약

각 기능 파일은 H1 제목과, 사용자에게 보이는 동작을 설명하는 단락 하나로 시작합니다. 그 다음에는 아래 순서대로 정확히 네 개의 H2 섹션을 사용합니다.

1. `Sub-features`는 짧은 ID와, 동작마다 한 줄 설명을 나열합니다.
2. `How to get to it (user POV)`는 사용자의 모든 진입점을 나열합니다.
3. `Driving it with <harness>`는 `Preconditions:`로 시작하며, 사용자 동작 각각을 정확한 명령과 관찰 가능한 결과에 짝지어 주는 레이블 달린 글머리 기호를 사용합니다.
4. `Gotchas`는 검증 실행을 낭비하거나 무효화할 수 있는 함정을 나열합니다.

구현 세부 사항은 맵에서 빼세요. 사용자 경로, 안정적인 핸들, 필요한 상태, 명령, 관찰 가능한 증명만 적으세요.

## 기능

- [Create a note](./create-note.md)는 브라우저와 CLI에서의 생성, 취소, 영속성, 정리를 다룹니다.
- [Search notes](./search.md)는 툴바, 키보드, CLI 검색과 일치, 빈 상태, 지우기 상태를 다룹니다.
