# Linear 티켓

## 이 소스에 담긴 것

- 기능, 버그, 그리고 그 동기를 설명하는 이슈
- 이슈에 첨부된 프로젝트 문서(보통 PRD 또는 스펙)
- 상위/하위 이슈 관계(넓은 이니셔티브 → 구체적인 티켓)
- 이슈 댓글(명확화, 범위 변경, "왜 이것을 하는가" 근거)
- 동기 유형을 드러내는 레이블(예: `compliance`, `customer-request`, `perf`)
- 범위 변경을 설명하는 상태 업데이트
- 첨부 파일과 연결된 GitHub PR

Linear는 제품과 사업 맥락이 종종 사는 곳입니다. "고객 X가 요청해서 한다" 또는 "이것은 Q3 컴플라이언스 이니셔티브를 위한 것이다"라는 층위입니다.

## 검색 방법

Linear MCP를 사용하십시오.

1. **연결된 티켓부터 시작하십시오.** 시드 커밋이나 PR이 티켓 ID(예: `ENG-1234`, `[BUG-567]`)를 참조하면, 먼저 `get_issue`로 가져오십시오. 댓글을 포함해 이슈 전체를 읽으십시오.
2. **키워드로 관련 이슈를 나열하십시오.** 기능 이름, 핵심 심볼, 또는 사업 용어로 `list_issues`를 텍스트 검색과 함께 사용하십시오. 여러 표현을 시도하십시오.
3. **이슈 트리를 따라가십시오.** 하위 이슈에 도달하면 상위 이슈를 가져오십시오. 하위 이슈는 전술적입니다. 상위 이슈에 종종 "왜"가 담겨 있습니다.
4. **프로젝트 문서를 읽으십시오.** 이슈가 프로젝트에 속하면 `get_project`를 사용하고 첨부된 문서를 확인하십시오. 스펙과 근거가 가장 자주 기록되는 곳은 프로젝트 수준의 문서입니다.
5. **레이블과 마일스톤을 확인하십시오.** 레이블은 동기의 범주(customer-request, incident-followup, compliance)를 암시합니다. 마일스톤은 작업을 마감일에 묶어, 종종 동기를 드러냅니다.

## 좋은 증거의 모습

- 사업상의 문제를 말하는 이슈 설명: "고객 Acme는 SOC2 감사 때문에 X가 필요하다"
- 결정을 기록한 댓글: "접근법 A는 billing 서비스를 건드려야 하므로 접근법 B로 가기로 결정했다"
- 이니셔티브처럼 제목이 붙은 상위 이슈: "Q3 Enterprise Readiness" 또는 "Reduce Payment Failures"
- 첨부된 PRD 또는 스펙
- `customer:acme`, `incident-followup`, `compliance`, `perf-regression` 같은 레이블

## 흔한 함정

- **범위 드리프트.** PR이 참조하는 티켓은 닫혔다가 다른 범위로 다시 열렸을 수 있습니다. 전체 이력을 읽으십시오.
- **기계적인 템플릿.** 일부 팀은 "Why" 섹션을 요구하지만 상투적인 말로 채웁니다. "사용자 경험 개선" 같은 일반적인 텍스트는 실제 답이 아닐 가능성이 큽니다.
- **오래된 티켓.** 오래된 티켓은 종종 바뀐 계획의 버전을 반영합니다. 날짜를 확인하고 코드의 출시 날짜와 교차 참조하십시오.
- **중복으로 닫힌 연쇄.** duplicate-of 관계를 따라 정식 티켓까지 거슬러 올라가십시오.
- **비공개 워크스페이스 내용.** 이슈에 접근할 수 없다면 추측하지 말고 공백으로 기록하십시오.

## 반환할 내용

관련 있는 티켓마다:
- 티켓 ID와 제목
- 설명이나 댓글에서 인용한 문제/동기(바꿔 쓰지 않고 정확한 텍스트. synthesizer가 인용하려면 정확한 텍스트가 필요합니다)
- 레이블, 상위 이슈, 프로젝트
- 작성자, 생성일, 닫힌 날짜
- 가능하면 티켓 링크
