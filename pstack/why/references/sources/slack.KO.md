# Slack 대화

## 이 소스에 담긴 것

- 문제와 결정에 대한 실시간 논의
- 긴급 대응 결정이 내려진 인시던트 채널
- 트레이드오프가 논쟁된 설계 논의 스레드
- 문서에 들어가지 않은, 시니어 엔지니어가 답한 질문
- 무언가가 왜 다시 검토되었는지 설명하는 머지 후 논의
- DM(보통 검색할 수 없으므로 범위를 그에 맞게 잡으십시오)

Slack은 *실제* 결정이 내려지는 곳인 경우가 많습니다. 특히 문서를 쓸 만큼 크지 않은 작은 변경에서 그렇습니다. 또한 가장 휘발성이 강한 소스입니다. 스레드는 삭제되고, 채널은 보관되며, 검색 품질은 시간이 지나며 떨어집니다.

## 검색 방법

Slack MCP 도구는 저마다 다릅니다. 사용 가능한 Slack MCP가 무엇인지 확인하고 먼저 도구 스키마를 살펴보십시오. `mcp_auth`가 필요할 수 있습니다. 인증이 실패하면 중단하고 공백을 보고하십시오.

1. **작성자 범위 검색.** PR 머지 날짜 무렵의 PR 작성자 메시지. 범위를 크게 좁히며, 종종 핵심 정보를 찾습니다.
2. **기능 이름과 핵심 심볼로 키워드 검색.** 오타와 구어체 표현도 포함하십시오.
3. **PR URL 검색.** Slack은 PR이 리뷰되거나 논의될 때 종종 PR을 링크합니다. PR URL(또는 `/pull/<number>`)로 검색하십시오.
4. **에러 문자열 검색.** 코드가 특정 에러를 처리한다면 그 에러 문자열을 검색하십시오. 인시던트 스레드가 종종 드러납니다.
5. **채널 범위 검색.** 가능성 높은 채널로 좁히십시오.
   - `#eng-*`. 엔지니어링 논의
   - `#proj-*`. 프로젝트 채널
   - `#incident-*` / `#sev-*`. 인시던트 채널
   - 담당 팀의 팀 전용 채널
   - 설계 리뷰 채널
6. **스레드 순회.** 관련 메시지를 찾으면 스레드 전체를 가져오십시오. 결정은 종종 답글에 있습니다.

## 좋은 증거의 모습

- 트레이드오프가 명시적으로 논쟁된 스레드("A를 쓰려고 했는데 B가 더 나은 이유는...")
- 코드가 막는 버그를 설명하는 인시던트 채널 메시지
- 리뷰어의 질문과 작성자 또는 리드의 권위 있는 답변
- 결정이 내려진 회의에 대한 참조
- 고객 요청을 설명하는 제품 매니저나 고객 대면 엔지니어의 메시지

## 흔한 함정

- **채널 고고학의 한계.** 아주 오래된 메시지는 보존 정책 때문에 사라졌을 수 있습니다. 특정 날짜 이전의 것을 찾을 수 없다면 보존 절벽을 기록하십시오.
- **검색되지 않는 DM.** 많은 결정이 검색할 수 없는 DM에서 내려집니다. 놓치게 됩니다. 이것은 알려진 한계입니다.
- **농담을 "결정"으로 착각하기.** Slack은 캐주얼합니다. "ㅋㅋ 그냥 해"는 커밋에 앞섰더라도 결정이 아닙니다. 숙고된 논의를 찾으십시오.
- **단일 메시지의 맥락 붕괴.** 스레드 없이는 단일 메시지가 맥락 속에서와 다르게 읽히는 경우가 많습니다. 항상 스레드를 가져오십시오.
- **인증 실패.** MCP가 인증되지 않았다면 중단하십시오. 결과를 지어내지 마십시오. Slack을 검색할 수 없었다고 보고하십시오.

## 반환할 내용

관련 있는 스레드마다:
- 채널 이름
- 퍼머링크 또는 스레드 ID
- 참여자
- 논의의 날짜 범위
- 작성자 귀속과 함께 핵심 인용(원문 그대로)
- 맥락: 이 스레드/인시던트/논의가 무엇의 일부였는지
