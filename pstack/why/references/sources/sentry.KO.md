# Sentry 에러 이력

## 이 소스에 담긴 것

Sentry는 잘못되었던 일들의 기록보관소입니다. 방어적, 교정적, 또는 에러 처리 코드의 경우, 누군가가 검사, catch, 재시도, 또는 폴백을 추가하도록 밀어붙인 직접적인 동기를 종종 담고 있습니다. 구체적인 예외, 스택 트레이스, 빈도입니다.

- **이슈.** 개수, 첫 관측/최종 관측 타임스탬프, 영향을 받은 릴리스, 댓글이 있는 그룹화된 에러
- **이벤트.** 이슈 안의 개별 에러 발생(스택 트레이스, 태그, 사용자 맥락)
- **릴리스.** 연결된 이슈가 있는 배포 기록("어떤 버전이 이것을 고쳤는가?"에 유용)
- **리플레이.** 사용자에게 보이는 에러의 세션 녹화(활성화된 경우)
- **프로파일.** 성능 프로파일링 데이터("왜"보다 "얼마나 느린가"에 덜 유용)
- **이슈 댓글과 담당자 지정.** 근본 원인에 대한 엔지니어의 노트가 담겨 있기도 합니다

Sentry가 제공하는 가장 가치 있는 것은 **시간적 상관관계**입니다. 예: "이슈 X는 2024-01-02에 생성되어 하루 500건으로 정점을 찍었고, 2024-01-15 방어 검사를 출시한 v2.14.0 릴리스 이후 더 이상 나타나지 않았다."

## 검색 방법

Sentry MCP를 사용하십시오.

1. **방향을 잡으십시오.** 프로젝트 slug와 조직을 모른다면:

   ```
   find_organizations
   find_projects
   ```

2. **대상과 관련된 이슈를 검색하십시오.**

   ```
   search_issues (natural language, e.g., "errors in PaymentService timeout", "unhandled exceptions in uploadFile")
   ```

   좋은 쿼리 구성 요소: 대상이 처리하는 예외 클래스 이름, 대상의 함수나 클래스 이름, 대상이 확인하는 에러 메시지 문자열, 대상의 파일 경로.

3. **릴리스와 시간 창으로 좁히십시오.**

   ```
   search_issue_events (filter by release, time, environment, trace ID, tags)
   get_issue_tag_values (for an issue, see distribution across versions, users, environments)
   ```

   의심되는 이슈에 대해 다음을 확인하십시오.
   - **First seen.** 에러가 언제 나타나기 시작했는가?
   - **Last seen.** 언제 멈췄는가? 대상의 출시일과 맞는가?
   - **Affected releases.** 어떤 버전에서 발생했는가? 어떤 것이 수정이었는가?
   - **Frequency trajectory.** 급증한 뒤 해결되었는가?

4. **맥락을 위해 전체 이벤트를 가져오십시오.**

   ```
   get_sentry_resource (pass a Sentry URL or type+ID)
   ```

   스택 트레이스가 대상 코드를 지나가는가? 태그와 breadcrumb가 대상이 방어하는 조건과 맞는가?

5. **대상 근처에 나간 릴리스를 확인하십시오.**

   ```
   find_releases (around the commit date of the target)
   ```

   릴리스 버전을 PR의 머지 날짜와 교차 참조하십시오.

6. **Seer는 아껴서 쓰십시오.**

   ```
   analyze_issue_with_seer
   ```

   Seer는 AI 근본 원인 분석을 만듭니다. 가설 생성기로는 유용하지만, 권위 있는 것이 아니라 추론으로 취급하십시오. 실제 이벤트와 스택 트레이스가 1차 증거입니다. Seer의 서술은 부차적입니다.

## 좋은 증거의 모습

- **first seen**이 대상 PR 직전이고 **last seen**이 직후여서, 대상이 이 에러를 해결했음을 시사하는 이슈
- 대상 함수를 지나거나 그곳에 도달하는 스택 트레이스로, 방어하려는 정확한 실패 모드를 보여 줌
- PR 작성자가 수정을 설명하는 이슈 댓글
- 대상의 PR 설명이나 커밋 메시지가 Sentry 이슈 URL 또는 ID를 참조함
- 대상을 포함하는 릴리스 이후 멈춘, 이벤트 개수가 많은 이슈

## 흔한 함정

- **그룹화 드리프트.** Sentry는 지문(fingerprint)으로 에러를 그룹화합니다. 리팩터링이나 이름 변경은 "같은" 에러를 새 이슈 ID로 추적할 수 있습니다. 이슈가 갑자기 끝나면 에러가 단지 다시 그룹화되었을 수 있습니다. 바로 직후에 새 이슈가 생겼는지 확인하십시오.
- **릴리스 상관관계는 노이즈가 많습니다.** 릴리스에는 많은 커밋이 있습니다. v2.14.0에서 이슈가 멈췄다고 해서 대상이 그것을 고쳤다는 증거는 아닙니다. 같은 릴리스의 다른 변경이 고쳤을 수 있습니다. 대상의 정확한 커밋과 교차 참조하십시오.
- **조용한 수정.** 때로는 upstream이 바뀌어서 에러가 멈춘 것이지, 방어 코드 때문이 아닐 수 있습니다. 상관관계는 수정을 시사하지만, 수정의 주체를 증명하지는 않습니다.
- **Resolved != fixed.** 이슈는 코드 변경 없이 수동으로 "resolved"로 표시될 수 있습니다. `resolved`는 사람이 남긴 표식으로 취급하고, 코드가 고쳤다는 증거로 취급하지 마십시오.
- **Seer 환각.** Seer는 확신에 찬 설명을 만들어 내지만 틀릴 수 있습니다. 주장을 할 때는 실제 이벤트, 스택 트레이스, 타임스탬프로 돌아가십시오.
- **샘플링.** 일부 프로젝트는 이벤트를 공격적으로 샘플링합니다. 이벤트 개수가 적다는 것은 드문 에러가 아니라 샘플링이 높다는 뜻일 수 있습니다. 확신이 없다면 공백으로 적으십시오.

## 반환할 내용

관련 있는 이슈마다:
- 이슈 ID와 제목
- 프로젝트와 조직
- 첫 관측 / 최종 관측 타임스탬프
- 이벤트 개수(알려진 경우 샘플링 비율 포함)
- 영향을 받은 릴리스
- 대상과의 관련성을 보여 주는 대표 스택 트레이스 발췌(요약이 아니라 원문 발췌)
- 대상 출시일과의 first/last-seen 상관관계
- 이슈 링크
- 작성자 댓글이나 해결 노트
