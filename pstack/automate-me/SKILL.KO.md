# Automate me

사용자의 작업 관례를 에이전트가 따를 스킬로 바꾸는 안내된 절차다. 결과물은 사용자에게 맞춘 `-mode` 스킬 하나다(예: `jay-mode`, `priya-mode`).

이 스킬은 다른 세 가지를 조율한다. 단계 1의 인라인 마이닝 과정, Cursor의 내장 `create-skill`(작성), 그리고 **unslop** 스킬(산문 규율)이다. 이들의 순서를 정할 뿐 대체하지는 않는다.

## 절차

### 0. 기존 스킬 확인

사용자의 핸들과 맞는 `.cursor/skills/**/*-mode/SKILL.md`와 `~/.cursor/skills/*-mode/SKILL.md`를 재귀적으로 찾는다. mode 스킬은 최상위가 아니라 개인 카테고리 디렉터리(`.cursor/skills/<handle>/`)에 있을 수도 있다. 있다면 `AskQuestion`으로 의도를 확인한다(사용자가 이미 "내 스킬 업데이트해" 같은 말을 했다면 생략):

- 기존 스킬 업데이트 (반복 실행 시 기본값)
- 처음부터 다시 시작 (드묾, 이유를 먼저 묻고 진행)

업데이트 모드는 나머지 절차를 바꾼다.
- 단계 1은 스킬이 마지막으로 편집된 이후의 기록만 마이닝한다(`git log -1 --format=%cI <path>`).
- 단계 2는 0에서 무엇을 담을지가 아니라, 무엇이 바뀌었거나 빠졌는지를 묻는다.
- 단계 4는 기존 파일을 제자리에서 편집한다. 사용자가 반박하지 않은 절은 보존한다. 새 증거가 있는 절은 수정한다. 정말 새로운 규칙에만 새 절을 추가한다.

### 1. 기록 마이닝

팬아웃 전에 활성 워크스페이스의 트랜스크립트를 찾는다. 시스템 프롬프트가 워크스페이스의 `agent-transcripts/` 디렉터리를 알려준다. 그 경로만 사용한다. `~/.cursor/projects/*/`를 전역으로 훑지 마라. 그러면 워크스페이스 경계를 넘어 관련 없는 프로젝트의 비공개 대화를 읽게 된다.

그 범위 안에서 최근 에이전트 대화를 훑어 반복되는 패턴을 찾는다. 기록의 여러 구간(예: 최근 2~4주를 3구간으로 나눠, 각 구간에 충분한 자료가 있도록)에 걸쳐 병렬 하위 에이전트를 실행한다. 각 구간의 마이닝 하위 에이전트는 부모가 넘긴 워크스페이스 범위 경로의 트랜스크립트를 읽고, 아래 신호를 찾아서 근거 위치와 함께 본 패턴의 짧은 구조화된 목록을 반환한다. 기본으로 찾을 신호는 다음과 같다.

- 응답 선호 (길이, 어조, 형식, "더 쉽게 설명해" 같은 교정)
- 위임 습관 (하위 에이전트, 모델, 특화된 워크플로우, 병렬화)
- 검증 자세 ("완료"의 의미, 단위 테스트 대 실시간 재현, 리뷰어)
- 코드와 산문 규율 (스타일, 인용된 원칙, 린트/포맷 도구)
- 프로세스 관례 (worktree, 커밋, PR, 리뷰/머지 도구)
- 메타 선호 (작업 중 스킬 고치기, 새 스킬 제안)

신호를 격상하기 전에 구간 간에 교차 확인한다. 2개 이상의 구간에서 보이는 패턴은 신뢰도가 높다. 단독 신호는 약하며 보통 버린다.

### 2. 사용자에게 직접 묻기

마이닝은 아직 나오지 않은 의도를 놓친다. 사용자에게 처음부터 타이핑하게 하지 말고, `AskQuestion` 도구(구조화된 객관식)를 쓴다.

형태: 질문 한두 개, 각 4~6개 선택지, 카테고리 질문에는 `allow_multiple: true`. 넓게 시작하고("어느 영역이 가장 중요한가?"), 선택된 영역에 대해 구체적인 선택지로 후속 질문을 한다. 구조화된 라운드 이후에는 자유 입력 채팅 질문 하나로, 선택지가 놓친 것을 잡는다.

질문을 20개씩 쏟아내지 마라.

### 3. 발견 사항 묶기

결합된 신호를 절로 묶는다. 흔한 절은 다음과 같다(해당하는 것만 쓴다).

- **응답 스타일**: 길이, 어조, 형식.
- **자율성**: 묻지 않고 할 수 있는 범위, MCP 도구 사용.
- **먼저 이해하기**: 변경의 범위를 정하거나 조사할 때 어떤 스킬을 쓸지.
- **하위 에이전트**: 기본값, 병렬성, 모델과 과제의 매칭, 특화된 워크플로우.
- **산문 / 코드 규율**: 원칙, 린트 도구, 스타일 가이드.
- **리뷰와 검증**: 재현 자세, 검증 스킬, 실시간 테스트 도구.
- **프로세스**: git worktree, 커밋, PR, 리뷰/머지 도구.
- **스킬**: 스킬 작성 습관, 작업 중 스킬부터 고치기, 새 스킬 제안.

**poteto-mode** 스킬이 형태를 보여 준다. 세분성을 보려고 읽되, 내용을 베끼지 마라. 사용자의 규칙은 poteto-mode의 규칙과 같지 않다.

### 4. 스킬 초안 쓰기

Cursor의 내장 `create-skill` 스킬로 스킬을 작성한다. 배치는 다음과 같다.

- 경로: 기존 mode 스킬이 있다면 그 카테고리를 보존한다. 새 mode라면, 저장소에 그 핸들을 위한 확립된 개인 카테고리가 있으면 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`를 쓴다. 아니면 프로젝트의 `.cursor/skills/<handle>-mode/SKILL.md`를 기본으로 쓴다(사용자가 개인 스킬을 원하면 `~/.cursor/skills/<handle>-mode/`).
- 핸들: 사용자의 이름이나 사용자가 고른 식별자.
- 프론트매터 `description`: 사용자의 이름 + `/<handle>-mode` + "그들의 스타일로 작업" 에 반응하도록 한다. "코드 작성"이나 "PR 리뷰" 같은 일반 키워드에 반응하면 안 된다.
- 프론트매터 형식: `create-skill`의 YAML 규칙을 따른다. `description`은 하나의 YAML 스칼라로 유지한다. 구두점이나 줄바꿈이 필요하면 따옴표로 감싸거나 들여쓴 이어지는 줄과 함께 `description: >-`를 쓴다.
- 프론트매터 `disable-model-invocation: true`가 기본값이다. 사용자가 모든 턴에 자신의 mode가 적용되기를 명시적으로 원할 때만 끈다.

### 5. 산문 다듬기

모든 줄에 **unslop** 스킬과 `create-skill`의 작성 지침을 적용한다.

초안을 사용자에게 보여 주고 피드백을 받는다. 여러 번 반복할 것으로 예상하라. 가차 없이 잘라내라. mode 스킬은 매뉴얼이 아니다.

### 6. 반영하기

main에서 분기한 worktree에서 작업한다. 커밋하고 PR을 연다. main에 직접 push하지 마라.

## 가드레일

- **한 대화에 과적합하지 마라.** 한 번 말했다가 다른 때 모순된 선호는 노이즈다. 명문화하기 전에 여러 번의 사례를 요구하라.
- **영리하게 굴지 마라.** 다른 스킬의 내용을 다시 서술하거나, 은유를 지어내거나, 에이전트 독자를 위해 "시적인" 산문을 쓰는 것은 비용만 있고 이득이 없다. 실행 가능하게 유지하라.
- **인라인하지 말고 참조하라.** 사용자가 의존하는 다른 스킬은 발췌문을 붙이지 말고 경로 참조로 써라. 사용자가 다른 곳에서 관리하는 원칙 문서도 마찬가지다.
- **절은 최소로 유지하라.** 사용자가 그 절에 구체적이고 기본값이 아닌 규칙을 가진 경우에만 절을 추가한다. "명확하게 소통하기"는 절이 아니다. "짧은 문단. 옵션을 비교할 때는 표. 항목이 정말 병렬일 때만 불릿."은 절이다.
- **이름 규칙은 일반적으로 쓴다.** 명령문에서는 "사용자" 또는 "사람"을 쓰고, 작성자의 이름을 쓰지 마라.
- **대칭을 억지로 맞추지 마라.** 사용자가 적어 둘 만한 프로세스 규칙이 없다면 Process 절은 통째로 건너뛴다.

## 평가

`-mode` 스킬은 주관적인 산출물이다. `create-skill` 스타일의 테스트/반복 벤치마크 루프는 여기서 쓸모가 없다. 사용자와 직관적으로 점검하라. 그 사람답게 읽히는가? 빠진 것은 없는가? 그다음 배포한다.

스킬의 트리거 정확도가 실제로 문제가 될 때만 설명 최적화 루프를 실행하라.

## 쓰지 말아야 할 때

- 사용자가 작업별 스킬(작업 관례가 아님)을 원할 때: 마이닝 없이 `create-skill`만 쓴다.
- 사용자가 좁은 워크플로우 하나를 기록하려 할 때(예: "커밋 메시지 쓰는 법"). 그것은 mode 스킬이 아니라 일반 스킬이다.
