### 출하

**무엇이 착지하는지에 책임을 진다. 각 PR을 독립적으로 검증하고, 루트에서부터 검증된 연속 구간만 착지시킨 뒤, 큐에서는 손을 뗀다.**

이것은 `playbooks/babysit.md` 다음에 오는 절반이다.

1. **forge를 확인한 뒤 모든 PR을 독립적으로 검증한다.** GitHub CLI(`gh`)가 기본이다. `command -v origin`이 성공하고 Origin이 저장소를 해석할 수 있다면, PR 보기, 감시, 편집, merge 작업에 `origin pr ...`을 쓴다. 그렇지 않다면 `gh`를 쓰고 대체 경로를 기록한다. Graphite(`gt`)는 절대 요구하지 않는다. PR마다 subagent 하나를 두되, 묶지 않는다. 각 subagent는 Cursor cloud agent이며, 맞는 control skill(예: `cursor-team-kit`의 `control-ui` 또는 `control-cli`)로 실제 표면을 부모 버전과 head 버전에서 실행한다. 각각 `PASS`, `PASS+NOTES`, `FAIL` 중 하나를 반환하고, 그 verdict를 자기 PR에 게시한다. 안전하다는 것은 코드를 쓰지 않은 agent가 낸 verdict라는 뜻이다. CI green은 verdict가 아니며, 봇이 승인한 리뷰도 verdict가 아니다.
2. **맨 아래에서 시작하는 검증된 연속 구간만 착지시킨다.** 가장 낮은 미merge PR부터 위로 올라가며, 통과 verdict(`PASS`와 `PASS+NOTES` 모두 통과)가 없는 첫 PR에서 멈춘다. 검증된 PR이라도 검증되지 않은 PR 위에 있다면 착지할 수 없다. 상한선을 PR 번호로 보고하고, 무엇이 사슬을 끊었는지 말한다.
3. **각 verdict가 여전히 패치를 설명하는지 다시 확인한다.** verdict의 head SHA, base SHA, 그리고 해당 PR의 base-to-head diff의 안정된 `git patch-id`를 기록한다. rebase나 base 재지정은 SHA를 다시 쓰므로, 검사에 아무 변화가 없어도 verdict를 조용히 무효화할 수 있다. PR을 착지시키기 전에 기록된 patch-id와 현재 base-to-head patch-id를 비교한다. 두 패치가 테스트, 문서, 린트 설정에서만 다르다면, 각 레인이 실행한 것을 확인한다. verdict SHA에서 두 번, 현재 head에서 한 번 빌드한다. verdict SHA에서 두 빌드도 같은 차이를 보인다면, 또는 그것이 내장된 커밋 SHA라면 그 차이는 노이즈다. 파일별이 아니라 차이별로 판단하고, 노이즈의 종류마다 해당 파일과 함께 보고한다. 노이즈만 달랐다면 그 레인의 결과는 여전히 유효하며, 검사와 변경에 대한 리뷰는 새로 돈다. 빌드 산출물이 없는 dev server나 다른 무엇이든 그 결과를 재사용하지 않는다. 그 레인을 다시 돌린다. 패치가 바뀌었다면 다른 모든 것을 다시 검증한다. 바뀌지 않았다면 코드 verdict는 유지하되, 현재 head에서 mergeability와 CI를 다시 돌린다. 커밋 메시지가 같거나 오래된 SHA의 green 체크를 대체물로 쓰지 않는다.
4. **맨 아래 PR만 준비한다.** 현재 trunk를 가져온다. 필요하면 가장 낮은 검증된 branch를 정확한 trunk 끝에 rebase하고 push한 뒤, `origin pr edit <pr> --base <trunk>` 또는 `gh pr edit <pr> --base <trunk>`로 그 PR 하나만 trunk로 재지정한다. push 뒤에 3단계를 다시 한다. 아직 자손을 재지정하거나, 예약하거나, merge하지 않는다.
5. **한 번에 PR 하나씩 착지시킨다.** 맨 아래 PR이 지금 mergeable하다면 `origin pr merge <pr> --squash` 또는 `gh pr merge <pr> --squash`로 squash한다. 요구 사항이 아직 실행 중이고 사용자가 merge-when-ready를 요청했다면, 그 PR 하나만 `origin pr merge <pr> --squash --auto` 또는 `gh pr merge <pr> --squash --auto`로 예약한다. Origin의 `--auto`는 Origin의 merge-when-ready다. GitHub의 `--auto`는 GitHub auto-merge다. 다음 PR을 준비하기 전에 그 PR이 merge될 때까지 기다린다.
6. **GitHub의 `autoMergeRequest`를 stack 준비 상태로 읽지 않는다.** 이 값은 많아야 GitHub PR 하나에 GitHub auto-merge가 요청되었다는 뜻일 뿐이다. Origin merge-when-ready가 예약되었다는 증거가 아니며, 자손이 대기열에 있다는 증거도 아니고, patch verdict가 최신이라는 증거도 아니며, 연속 stack이 안전하다는 증거도 아니다. 현재 맨 아래 PR에 대해 활성 forge의 상태를 확인하고, 활성 forge가 그 상태를 보고할 수 없다면 상태를 알 수 없다고 말한다.
7. **merge할 때마다 다시 계산한다.** trunk를 가져오고, merge된 SHA가 있는지 확인하고, 얼려 둔 맨 아래에서 위로의 목록에서 merge된 PR을 뺀다. 새 맨 아래 PR의 base, head, 검사, patch-id를 확인한다. 호스트가 자식을 자동으로 재지정했을 수 있지만, 그랬다고 가정하지 않는다. 그 PR 하나에 대해 3단계부터 6단계까지를 반복한다. 독립적인 작업은 이 사슬 밖에 두고 따로 출하한다.
8. **현재 프론티어가 merge되거나 실패할 때까지 지켜본다. 그 주변의 큐를 바꾸지 않는다.** Origin을 쓴다면 `origin pr view <pr> --checks --comments`와 `origin pr checks <pr> --watch`를 쓰고, PR을 다시 읽어 merged 또는 blocked가 될 때까지 확인한다. GitHub를 쓴다면 `scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom>`은 이벤트 깨우기로만 쓰고, 깨어날 때마다 `gh pr view <pr> --json state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest`로 폴링한다. `mergedAt`이 null이 아니거나 `state`가 `MERGED`가 되기 전까지 `READY`는 무시한다. 그 다음에만 7단계를 실행한다. 실패 판정은 다음 경우에만 한다. `state`가 `mergedAt` 없이 `CLOSED`인 경우, auto-merge가 더 이상 대기 중이 아닌데 필수 검사가 `FAILURE` 또는 `CANCELLED`로 끝나 merge를 막는 경우, 또는 auto-merge가 대기 중이 아닌데 `mergeStateStatus`가 `UNSTABLE` 또는 `DIRTY`인 경우. 검사가 진행 중이거나 auto-merge가 예약되어 있는 동안의 `BLOCKED`는 실패가 아니다. 여기서는 Babysit의 대기열용 `WAITING`/`merge-queue` 중단 조건을 쓰지 않는다. 감시는 dynamic mode의 `/loop` 아래에서 유지한다. merge마다 보고하고 새 상한선을 알린다. 대기열이 멈추면 변경하기 전에 원인을 진단한다.
9. **상한선에서 멈춘다.** 검증된 연속 구간이 merge되면, 무엇이 착지했는지, 다음 검증되지 않은 PR이 무엇인지, 그것을 검증하려면 무엇이 필요한지 보고한다. 실행을 연장하는 것은 1단계부터 다시 하는 새 패스다.

**응답:** 검증된 구간과 그 상한선, 각 PR의 verdict와 그것을 낸 주체, 무엇을 예약했고 그것을 어떻게 확인했는지, 무엇이 착지했는지, 다음 공백에 무엇이 필요한지.
