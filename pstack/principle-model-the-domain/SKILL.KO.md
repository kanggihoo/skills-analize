# 도메인 모델링

실제 도메인을 흩어진 조건문에 나누어 담는 대신, 데이터 구조로 표현한다.

**이유:** 흩어진 불리언, 반복되는 형태 가정, 여러 파일에 퍼진 분기는 우발적 복잡성이다. 도메인과 맞는 구조는 잘못된 상태를 표현 불가능하게 만들고 분기를 없앤다. 작성 시점에 선택하는 것은 저렴하지만, 나중에 복구하면 리팩터링으로 취급되어 미뤄지기 쉽다.

**다음과 같은 구조를 고려한다:**

- 흩어진 불리언, 단계(phase), 생명주기 검사 대신 **상태 머신**.
- 느슨한 매개변수나 반복되는 형태 가정 대신 **타입이 지정된 객체/모델**.
- 여러 파일에 퍼진 분기 대신 **맵, 레지스트리, 룩업 테이블, 또는 판별된 유니온(discriminated union)**.
- 임의의 상태 변경 대신 **리듀서 또는 커맨드/이벤트 모델**.
- 로드, 검증, 변환, 저장 같은 순서 대신 하나의 도메인 지식 묶음을 중심으로 구성한 **모듈**. 실행 순서는 소유권이 아니다.
- 반복되는 동작, 소유권, 불변식을 모으는 **작은 모듈 경계**.
- 데이터 접근 패턴이 요구할 때의 **큐, 캐시, 인덱스, 그래프/트리, 또는 정규화된 컬렉션**.
- 그 밖에 맞는 모든 구조. 맞는 것이 없다면, 코드가 절대 허용하지 말아야 할 것과 데이터가 어떻게 읽히는지 파악한 뒤, 정확히 그것을 표현하는 구조를 찾는다.

추상화를 억지로 만들지 않는다. 현재 형태가 명확하고 지역적이며 커질 가능성이 낮다면 단순한 코드를 선호한다. 분기, 중복 규칙, 잘못된 상태, 생명주기 위험을 줄이지 않으면서 간접 참조만 추가하는 추상화는 의심한다.

이 원칙을 건너뛰었다는 신호는, 기존 if/else 체인에 분기 하나를 더 얹는 새 기능, 또는 첫 번째 불리언과 항상 동기화되어야 하는 두 번째 불리언이다. 시간 기준 분해(temporal decomposition)도 신호다. 단계 이름을 딴 모듈은 여러 단계에 걸쳐 같은 도메인 규칙을 반복한다.
