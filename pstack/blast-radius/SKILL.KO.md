# 영향 범위 (Blast radius)

배포 전에 변경이 다른 곳에서 무엇을 깨뜨릴 수 있는지 찾는다. "X의 영향 범위", "이게 무엇을 깨뜨릴 수 있나", 또는 아직 신뢰하지 않는 작은 diff를 검토할 때 쓴다.

`how`와 `why`의 짝이다. `how`는 코드가 무엇을 하는지 알려 준다. `why`는 코드가 왜 그렇게 생겼는지 알려 준다. 영향 범위는 그 코드가 다른 곳에서 무엇을 깨뜨리는지 알려 준다.

호출자 목록을 뽑는 것은 이 작업의 목적이 아니다. 에이전트는 그것을 1초면 grep으로 찾는다. 작업의 목적은 grep으로는 보이지 않는 파손을 찾는 것이다.

## 자기 보고서를 믿지 마라

옳게 들리는 영향 범위 보고서는 쓸모가 없다. 그것은 사실이든 아니든 똑같이 설득력 있게 읽힌다. 그러니 보고서를 그대로 돌려주지 마라. 전체 주장이 기대고 있는 한두 가지 사실을 찾아서, 실행되는 코드로 증명하라.

### 얼마나 확신하는가

변경의 안전성이 기대는 각 사실에 대해, 비용이 적당한 만큼 아래 목록에서 최대한 아래 단계까지 끌어올리고, 어디서 멈췄는지 밝혀라.

1. 당신이 그렇다고 말했다. 그것만으로는 쓸모없다.
2. 줄을 가리켰다. 실제 `file:line`이거나 라이브러리 자체의 소스.
3. 나쁜 경우가 일어날 수 없음을 보였다. 실패를 단계별로 따라가서 도달하지 않는다는 것을 확인했다.
4. 실행했다. 실제 코드를 호출하고 틀리면 크게 실패하는 스크립트나 테스트.
5. 실행 중인 앱에서 재현했다.

4단계는 보통 앱이 배포하는 것과 같은 라이브러리를 임포트하고, 우려되는 정확한 함수를 호출하는 작은 스크립트 하나다.

## 절차

1. 변경을 읽어라. diff, 추가·변경·삭제된 심볼, 그리고 diff에 명시되지 않은 부분을 포함해 지금 무엇이 다르게 동작하는지. PR과 커밋을 가져오려면 `why`의 2단계를 쓴다.
2. 안전성이 기대는 한 가지 사실을 찾아라. 위험해 보이는 대부분의 변경은 "이 호출은 이미 죽은 캐시 항목만 지우고 다른 일은 하지 않는다" 같은 단일한 사실 덕분에 안전하다. 그 사실을 찾아라. 그것이 성립하면 위험해 보이는 경우 대부분이 한꺼번에 해소된다. 시간은 여기에 써라. 긴 "혹시나" 목록에 시간을 쓰지 마라.
3. grep이 멈추는 곳을 보라. 당신이 호출하는 라이브러리의 소스를 읽고, 고정된 버전과 로컬 패치가 있는지 확인하라. 실행 시점을 파악하라. 마이크로태스크, 언마운트와 teardown, Solid 대 React. 심볼 검색이 놓치는 것을 따라가라. API가 반환하는 JSON, DB 컬럼, 와이어 포맷, 같은 바이트를 읽는 다른 언어, 기능 플래그, 세 홉 떨어진 하위 코드.
4. 각 위험에 솔직해져라. 발생할 실제 가능성과 발생했을 때의 실제 비용을 매겨라. 확인된 위험은 남기고, 점검해서 해소된 것은 따로 나열하라. `why`와 같은 규칙이다. 실제 `file:line`을 인용하라. 아무것도 찾지 못한 검색도 답이다. 호출자나 API를 지어내지 마라.
5. 그 한 가지 사실을 증명하라. 실제 코드를 실행하는 스크립트나 테스트를 작성하고, 실행하고, 일어난 일을 그대로 붙여라.
6. 크거나 범위가 넓은 변경이라면 `arena`로 실행하라. 여러 모델에게 같은 질문을 던지고 답을 합쳐라. 서로 다른 모델은 서로 다른 실제 버그를 잡아낸다.

## 돌려줄 내용

- **무엇을 하는가.** 무엇이 바뀌었는지, 명확하지 않은 부분까지 포함해서.
- **안전한 이유가 되는 한 가지 사실.** 그것을 명시하고, 몇 단계까지 확인했는지 말하고, 증거를 보여라. 증명하지 못했다면 미증명(unproven)이라고 쓴다.
- **위험.** 각 위험은 어떻게 깨지는지, `file:line`, 발생 가능성과 피해 정도, 확인 방법을 적는다. 중요한 위험에는 증거를 붙여라.
- **해소됨.** 무엇을 점검했고 왜 괜찮은지.
- **머지 전에.** 실제 버그를 잡아낼 가장 저렴한 테스트나 재현 방법, 당신이 작성한 스크립트를 포함해서.

`unslop`을 거쳐 쓰고, 실제 코드를 인용하고, 공개되는 곳으로 가기 전에 비공개 정보를 제거하라.

**응답:** 위의 보고서. 한 가지 안전성 사실은 증명되었거나 미증명으로 표시되어 있어야 한다.
