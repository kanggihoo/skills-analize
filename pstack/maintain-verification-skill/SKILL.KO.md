# Maintain a verification skill

기능 맵은 앱이 바뀌는 순간부터 낡기 시작합니다. 이 스킬은 `/create-verification-skill`로 생성된 스킬(또는 기능 맵을 가진 모든 프로젝트 로컬 검증 스킬)을 위한 유지 관리 루프입니다. 엄격함의 단위는 문장이 아니라 기능입니다. 모든 기능 파일을 소스에서 확인하고, 모든 기능을 실제로 구동하되, 모든 글머리 기호를 하나하나 끝까지 검증하지는 않습니다.

## Outcomes

하나를 고르고, 무엇을 골랐는지 말하세요.

- **clean** — 모든 기능이 소스와 실시간 검증 모두에서 다뤄졌고, 배포할 만한 것이 없습니다. 브랜치도 PR도 만들지 않습니다.
- **changed** — 하나의 PR에 증명된 문서, 하네스, 맵 수정 사항을 담아 배포합니다.
- **blocked** — 검증을 끝내지 못했거나, 증명된 수정을 안전하게 배포하지 못했습니다. 무엇이 막았는지 정확히 말하세요.

## Edit scope

검증 스킬 자체의 디렉터리(SKILL.md, features/, 그리고 스킬이 소유한 하네스 스크립트)만 편집하세요. 실행 중에는 제품 코드를 절대 편집하지 마세요. 맵이 설명하지만 앱이 더 이상 하지 않는 동작은 문서 표류(맵을 고치세요)이거나 제품 회귀(보고하세요, 문서로 덮지 마세요) 중 하나입니다.

## Pass

0. **대상 찾기.** 유지 관리할 검증 스킬을 찾으세요. 본문에 launch/drive 섹션과 기능 맵이 있는 프로젝트 로컬 스킬이며, 보통 `.cursor/skills/verify-*/`입니다. 후보가 여럿이면 어느 것인지 물어보세요. 없다면 중단하고 `/create-verification-skill`을 안내하세요. 대상을 임의로 만들어 내지 마세요.

1. **색인 정리.** 기능 맵 README를 읽고, 형제 파일들을 glob으로 찾으세요. 누락, 초과, 중복, 죽은 항목을 고치세요. 가볍게 진행하며, 생성된 인벤토리는 만들지 않습니다.

2. **소스 웨이브.** 기능 파일마다 읽기 전용 서브에이전트 하나를 동시에 실행하세요. 각 서브에이전트는 "이 사용자 대상 기능은 소스에서 어떻게 동작하는가?"를 설명하고, 인용과 함께 문서 표류 가능성을 표시하며, 실시간 검증 절차 하나를 간결하게 반환합니다. 자식 에이전트는 앱을 구동하지 않으며 파일을 편집하지 않습니다. 반환 형식: 기능 요약 / 소스 진입점 / 가능한 표류 또는 없음 / 절차 하나.

3. **조정.** 모든 기능 파일에 반환된 요약이 있어야 합니다. 겹치는 절차는 가능한 한 적은 앱 상태로 합치세요. 인용된 표류는 샘플로 확인하고, 깨끗하다고 주장한 것은 다시 증명하지 마세요. 최근 변경을 훑어서, 맵에 빠진 사용자 대상 표면을 찾으세요. 누락되었다고 판단하려면 구체적인 소스 경로가 있어야 합니다.

4. **실시간 패스.** 소스가 깨끗해 보여도 반드시 수행해야 합니다. 코디네이터가 모든 구동을 담당하며, 검증 스킬 자체의 launch 모델을 따르세요. 서버와 UI에는 장기 실행 인스턴스 하나를 직렬로 구동하고, 수명이 짧은 CLI에는 구동마다 새로운 격리 세션을 쓰는 방식입니다. 이를 결정하는 것은 이 스킬이 아니라 검증 스킬의 Launch 섹션입니다. 모든 기능을 최소 한 번은 실행하고, 실패가 무엇이든 실행 전체에서 세 가지 불변식을 지키세요. (1) 마지막으로 무언가 이상한 일을 한 뒤에는 health-check를 하지 않은 인스턴스를 절대 구동하지 마세요. 첫 구동 전에 doctor를 실행하고, 세션이 단위인 경우에는 새 세션마다 doctor를 실행하며, 실패한 구동 후에는 doctor를 다시 실행하세요. doctor가 실패를 볼 수 없는 경우(정상 프로세스 위의 멈춘 UI 상태)에는 바라기만 하지 말고 알려진 상태로 되돌리거나 다시 실행하세요. (2) 지금까지 캡처한 증거는 모든 정리 이후에도 살아남아야 하며, 이는 가정하지 말고 명명된 위치에서 확인하세요. (3) 구동이 시작한 것은 그 구동이 쓸모없어진 뒤까지 살아남으면 안 됩니다. 실패한 반복의 잔여물은 세션이 멈췄든, 종료됐든, 공유되고 있든 정리하세요(공유 인스턴스의 경우 인스턴스가 아니라 잔여물만 정리합니다). doctor 실패가 스킬의 표류로 생긴 것이라면, 편집 범위 안에서 고치고 한 번 재시도하세요. 수정으로 무효화된 것만 다시 시작하고, 그 이상은 하지 마세요. 그 뒤에야 패스를 `blocked`로 판단합니다. 도달할 수 없는 기능은 구체적인 전제 조건(인증, 권한, OS, 외부 상태)과 시도한 경로가 있을 때만 `verified-unreachable`로 표시하세요. 맵이 그 전제 조건을 빠뜨렸다면, 그것 자체가 표류입니다. triage에서 나온 하네스 수정은 배포 전에 실시간으로 다시 구동해 확인하세요. 최종 종료(teardown)는 재증명을 포함해 실행의 마지막 구동 뒤에 수행하여, 실행 후에 아무것도 남지 않도록 하세요(증거는 스킬의 규칙에 따라 남깁니다).

5. **Triage.** 사용자 관점에서 틀리거나 빠진 설명은 문서 표류이므로 고치세요. 하네스가 구동할 수 없는 정상 동작은 하네스 공백이므로 고치세요. 하네스 수정은 생성 시와 같은 헬퍼 규칙을 따릅니다(스크립트는 실행 가능해야 하고, 호출 방법은 스킬 본문에 문서화되어야 합니다). 실제로 앱이 고장 난 동작은 제품 공백이므로 사용자를 위해 기록하고, 이번 PR에서는 제외하세요.

6. **배포 또는 중단.** changed라면, 증명된 수정 사항을 담은 PR 하나를 만드세요. 먼저 바뀐 모든 파일을 다시 읽으세요. clean이나 blocked라면 PR을 만들지 말고, 결과와 다룬 범위를 정직하게 보고하세요.

실행 메모(다룬 기능, 도달할 수 없었던 전제 조건, 확인된 표류, 결과)는 간결하게 임시 위치에 남기세요. 커밋하지 마세요.
