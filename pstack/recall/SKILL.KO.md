# Recall

**작업을 시작하거나 재개하기 전에, 사용자의 최근 작업 맥락을 다시 구성하고 지금 상태와 다음에 할 일을 담은 간결한 요약을 돌려준다.**

간결하고 주제에 맞게 유지한다. 해당 스레드에 필요한 내용만 읽고 멈춘다.

맥락은 두 기록에 있다. 자신의 채팅 기록에는 무엇을 했고 무엇을 결정했는지가 남아 있다. 공유 기록에는 같은 코드 주변에서 다른 이름으로 일어난 모든 일이 있다. 사용자들이 계속 보고하는 증상, 출시되었다가 되돌려진 수정, 운영 환경에서 여전히 발생하는 오류 등이다. **why** 스킬은 바로 이 두 번째 기록을 소스 컨트롤, 이슈 트래커, 채팅과 이슈 채널, 장문 문서, 오류 추적 도구에서 검색한다. 긴 버그 꼬리를 가진 기능은 그 이야기의 대부분을 여기에 담고 있으므로, 트랜스크립트만으로 재구성하지 않는다.

트랜스크립트는 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`에 있다. 여기서 `<slug>`는 워크스페이스 경로에서 맨 앞의 슬래시를 떼고 각 "/"를 "-"로 바꾼 값이다(예: `/Users/you/proj`는 `Users-you-proj`가 된다). 각 줄은 채팅 메시지 하나다.

1. 분류한 뒤 경로를 정한다. 이전 채팅 하나를 골라 재개하는 일은 `session-pickup` 플레이북이며 이 스킬이 아니다. 반복하는 습관을 지속 가능한 스킬로 바꾸는 일은 `automate-me`다. 작업을 사람이 읽을 수 있게 요약하는 일도 별개의 작업이다. recall은 행동하기 전에 최근 채팅 전반의 작업 맥락을 불러온다. 사용자가 이미 전체 상태 요약(경로, 브랜치, 변경 내용)을 줬다면 그것을 사용하고 마이닝은 건너뛴다.
2. 검색 전에 범위를 고정한다. 기간("recent"는 실제 범위이며 기본값은 최근 7일), 이름이 주어졌다면 주제, 워크스페이스(기본값은 현재 활성 워크스페이스다. 요청받지 않는 한 다른 프로젝트의 트랜스크립트는 절대 읽지 않는다)를 정한다. 범위를 사용자에게 다시 말해 준다. "all"을 조용히 "최근 N개"로 바꾸지 않는다.
3. 채팅 기록 전체에 걸쳐 병렬로 찾는다. 빠르고 저렴한 모델의 하위 에이전트를 여러 개 띄워 말뭉치의 각 부분을 맡긴다. 각 하위 에이전트에게 후보를 파일 이름의 UUID 순이 아니라 실제 수정 시각(`ls -t`) 순으로 정렬하라고 지시한다. 먼저 주제를 grep하고, 일치하는 채팅과 관련 구간만 읽는다. 현재 채팅과 명백한 잡음(하위 에이전트, 평가, 테스트 채팅)은 건너뛴다. 각 하위 에이전트는 같은 스키마로, 채팅당 블록 하나를 반환한다. 블록에는 주제, 사용자의 목표, 결정, 열린 스레드, 어려움과 정정, 산출물(PR, 티켓, 브랜치)이 들어가며, 각각 채팅 UUID를 인용한다. 채팅이 한두 개뿐이면 병렬 분산은 건너뛰고 직접 검색한다. 원본 트랜스크립트는 하위 에이전트에 머물고, 메인 스레드는 그들의 결과만 받는다.
4. 주제가 기능, 파일, 서브시스템, 영역, 버그를 지목할 때마다 공유 기록을 살핀다. 이는 기본 동작이며 판단에 따라 정하는 것이 아니다. "내 X 작업"이라고 해서 이 단계가 면제되지는 않는다. **why** 스킬의 소스 조사자에게 맡기되, 질문을 "왜 이렇게 만들었는가"에서 "현재 상태는 무엇이고, 무엇을 시도했다가 효과가 없었으며, 사용자들이 여전히 무엇을 보고하는가"로 바꾼다. 그 스킬의 소스별 플레이북을 재사용하고, 조사자는 소스마다 하나씩 두고 채팅 기록 마이닝과 병렬로 실행하며, 그 자세를 그대로 따른다. 즉 null 결과도 결과로 취급하고, 사용할 수 없는 MCP는 건너뛰고 그 사실을 말한다. 돌아온 내용을 요약에 반영한다. 이 단계를 건너뛰어도 되는 경우는 이름 붙은 대상이 없는 순수한 활동 회상뿐이다("이번 주에 뭘 했지"처럼). 이때는 자신의 기록과 현재 상태가 답의 전부다.
5. 실제 상태와 대조한다. 마이닝과 공유 기록 조사에서 드러난 PR, 브랜치, 티켓을 `git`과 `gh`로 확인한다. 답이 에이전트가 실제로 한 일(실행한 도구, 읽은 파일, 만난 오류)에 달려 있다면, 잘린 로컬 사본이 아니라 전체 트랜스크립트를 읽는다.
6. 아래 계약에 맞춰 요약을 작성한다. 스레드별로 묶고, 지정된 주제에 머문다.

## 출력 계약

캡슐을 먼저 쓰고, 그다음 스레드 상태, 문제, 다음 행동 순으로 쓴다. 더 자세한 내용은 아래에 두거나 잘라낸다.

- **캡슐.** 최대 5개 글머리 기호. 이 작업이 무엇이며 전체적으로 어디까지 왔는지.
- **스레드.** 스레드마다 한 줄씩, 상태 태그 정확히 하나를 앞에 붙인다. `[merged #N]`, `[open PR #N]`, `[in flight <branch>]`, `[verified, uncommitted]`, `[reverted #N]`, `[planned, not started]` 중 하나다. 태그가 없는 스레드는 아직 끝나지 않은 것이므로 태그를 붙인다.
- **문제.** 최대 5개, 반복되는 것만. 사용자들이 계속 보고하는 증상과 출시되었다가 되돌려진 수정도 포함해, 다음 시도가 이전 시도가 실패한 지점에서 시작하게 한다.
- **다음 행동.** 가장 유용한 다음 행동 하나를 구체적으로.

이 작업을 막지 않는 한 인접한 기능이나 티켓은 포함하지 않는다. 캡슐과 스레드 줄이 한 화면을 넘으면, 스레드를 자르기 전에 세부 내용부터 줄인다. 요약은 **unslop** 스킬을 거쳐 작성하고, 채팅 결과는 UUID로, 공유 기록 결과는 출처(PR 번호, 티켓 ID, 채팅 퍼머링크, 오류 추적 이슈)로 인용하며, 공개 출력 전에는 비공개 맥락을 정제한다.

**응답:** 위 계약에 맞춘 요약.
