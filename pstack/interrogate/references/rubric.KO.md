# Review Rubric

적용 가능한 관점으로 검토하세요. 모든 관점이 모든 변경에 해당하지는 않습니다. 판단을 사용하세요.

## Correctness

코드가 의도가 말하는 대로 실제로 동작하는가?

- 엣지 케이스: 빈 입력, nil/undefined, 경계값, 동시 접근
- 오류 처리: 오류가 잡히는가, 전파되는가, 아니면 조용히 삼켜지는가?
- Off-by-one, 타입 강제 변환, 정수 오버플로, 문자열 인코딩
- 상태 관리: 경쟁 조건, 오래된 클로저, 매달린 참조
- 정상 경로가 동작하는가? 실패 경로가 동작하는가?
- 멱등성: 이 작업을 두 번 실행하면 무슨 일이 생기는가? 이전 실행이 중간에 크래시했다면 어떻게 되는가? 답이 "남겨진 상태에 따라 다르다"라면, 조정(reconciliation) 단계가 빠져 있는 것입니다.
- 동시성: 여러 행위자가 같은 가변 상태(파일, 브랜치, 공유 데이터)에 접근할 수 있다면, 접근이 구조적으로 직렬화되어 있는가(락, 순차 단계, 배타적 소유권)? 아니면 지켜지지 않을 규약에 의존하는가?

잠재적 버그를 발견하면 실행 경로를 추적하세요. "이것은 nil일 수 있다"라고만 표시하지 마세요. 그것을 nil로 만드는 호출 체인을 보여 주세요.

## Root Causes vs. Symptoms

코드가 실제 문제를 고치고 있는가, 아니면 증상을 덮고 있는가?

이를 판단하려면 종종 변경된 파일 너머를 봐야 합니다. 주변 코드(호출자, 피호출자, 타입 정의, 형제 모듈)를 읽고, 변경이 속한 아키텍처를 이해하세요. 사용 가능한 도구(Read, Grep, Glob)로 탐색하세요. 호출 체인을 따라가세요. 타입을 읽으세요. 변경이 올바른 계층을 다루는지 판단하기 전에 코드가 왜 존재하는지 이해하세요.

- 더 깊은 불변식 위반을 가리는 가드 절
- 깨진 계약을 숨기는 재시도 로직
- 모델링 오류를 침묵시키는 타입 캐스트
- 우회 방법을 보면 물어보세요. 왜 그 우회가 필요한가? 제대로 된 수정은 어떤 모습인가?
- 모듈 A의 수정이 실제로는 모듈 B 계약의 수정이어야 하는 경우
- 구조가 더 나은 지침: 수정이 "X를 하지 마라"는 주석이나 누군가가 기억해야 하는 규약이라면, 대신 타입 제약, 린트 규칙, 또는 잘못된 것을 불가능하게 만드는 런타임 검사가 될 수 있는지 물어보세요.

## Structural Integrity

코드가 자신이 속한 시스템에 잘 맞는가?

- 경계 규율: 검증이 시스템 경계에 있는가, 아니면 비즈니스 로직 곳곳에 흩어져 있는가? 데이터는 시스템에 들어오는 지점에서 한 번 검증하고, 내부에서는 신뢰하세요.
- 추상화 수준: 코드가 고수준 오케스트레이션과 저수준 세부 사항을 섞고 있는가?
- 결합도: 이 변경이 앞으로의 변경을 더 어렵게 만드는 의존성을 도입하는가?
- 데이터 모델 적합성: 데이터 구조가 실제 접근 패턴과 맞는가? 올바른 구조는 하류 코드를 명확하게 만듭니다. 잘못된 구조는 매번 당신과 싸우게 합니다.
- 덧붙인 것 vs. 통합된 것: 변경이 기존 설계 위에 덧붙여졌는가, 아니면 설계가 처음부터 그것을 고려했던 것처럼 읽히는가? 새 요구 사항을 처음부터 알고 있었다면 코드가 이런 모습이었을까?
- 레거시 이중 경로: 변경이 새 API를 도입하면서 기존 API를 살려 두고 있는가? 외부 소비자가 없다면 같은 작업 단위에서 호출자를 마이그레이션하고 옛 경로를 삭제하세요. 영구적으로 남을 호환성 계층을 두지 마세요.

단순한 코드가 추상화가 부족하다고 감점하지 마세요. 시기상조의 추상화는 중복보다 나쁩니다.

## Verification

코드를 읽는 것만으로 이 코드가 동작한다는 것을 알 수 있는가?

- 테스트가 있는가? 테스트가 동작을 검증하는가, 아니면 구현 세부 사항을 검증하는가?
- 회귀를 잡아낼 단언이나 불변식이 있는가?
- 버그 수정이라면, 그 버그에 대한 테스트가 있는가?
- 통합 경계를 건드린다면, 전체 경로가 테스트되는가?
- 대리물이 아니라 실제 대상을 확인하세요. 코드가 실제 값을 읽지 않고 파일 mtime이나 캐시된 상태로 활성 여부를 확인한다면, 그것은 검증의 공백입니다.
- 위임되었거나 비동기적인 작업이라면, 코드가 실제 산출물을 검증하는가, 아니면 자기 보고와 요약을 신뢰하는가?

## Complexity Budget

복잡성이 코드가 달성하는 것으로 정당화되는가?

- 정확성이나 명확성을 잃지 않고 더 단순해질 수 있는 코드
- 호출 지점이 하나뿐인 추상화
- 아직 존재하지 않는 경우를 위한 설정이나 매개변수화
- 죽은 코드, 사용되지 않는 import, 흔적만 남은 매개변수
- 과설계: 현재 호출자가 없는 "혹시 몰라서" 만든 경로
- 과도기적 안정성을 위해 살아 있지만 더 이상 필요 없는 구식 호환성 경로. 마이그레이션이 끝났다면 비계(scaffolding)를 삭제하세요
- 사용자 경험이 복잡성을 정당화하는가? 모든 기능, 컨트롤, 옵션은 존재할 이유를 증명해야 합니다. 반쯤 완성된 기능은 없는 것보다 나쁩니다.

정확성이나 명확성을 잃지 않는 한 단순한 것이 낫습니다. 세 줄의 중복이 시기상조의 추상화보다 낫습니다.

## Security

각 보안 발견 사항에 대해, 입력 경로를 코드 전체에서 추적해 보여 주세요.

- 살균(sanitization) 없이 위험한 싱크(SQL, shell, eval, innerHTML)로 흘러 들어가는 사용자 입력
- 새 엔드포인트의 인증/인가 공백
- 코드, 로그, 오류 메시지에 노출된 비밀 값
- 보안에 중요한 경로에서의 TOCTOU(time-of-check-time-of-use)
