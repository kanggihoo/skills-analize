# Code Quality Review

각 리뷰어는 루브릭과 함께 이 코드 품질 렌즈를 적용합니다. 구현 품질, 유지 관리성, 추상화의 질, 코드베이스의 건강 상태에 초점을 둔 엄격한 기준입니다.

무엇보다도 코드 구조에 대해 야심차게 접근하세요. 국소적인 정리에만 머무르지 마세요. 동작을 보존하면서도 구현을 극적으로 단순하고, 작고, 더 직접적이며, 더 우아하게 만드는 재구성, 즉 "코드 주도(code judo)" 움직임을 적극적으로 찾으세요.

## Core Prompt

이 기준선에서 시작하세요.

> 현재 브랜치 변경 사항에 대한 심층적인 코드 품질 감사를 수행하세요.
> 동작에 영향을 주지 않으면서 코드 품질을 의미 있게 개선하도록 변경 사항의 구조와 구현을 다시 생각하세요.
> 추상화, 모듈성을 개선하고, 스파게티 코드를 줄이며, 간결성과 가독성을 높이세요.
> 야심차게 하세요. 코드베이스의 일부를 재구성하는 것이 분명한 개선 경로라면, 그렇게 하세요.
> 극도로 철저하고 엄격하게 하세요. 두 번 재고 한 번 자르세요.

## Dimensions

각 차원은 한 번만 적었습니다. 관련 있는 것만 적용하세요.

0. **구조적 단순화에 야심을 가지세요.** "조금 더 깔끔해질 수 있다"에서 멈추지 마세요. 분기, 헬퍼, 모드, 조건문, 계층 전체를 사라지게 만드는 재해석을 찾으세요. "코드 주도" 움직임은 종종 가능하다고 가정하세요. 기존 아키텍처를 더 효과적으로 활용해 변경을 극적으로 단순하게 만드는 것입니다. 복잡성을 재배치하는 대신 제거할 수 있다면, 그쪽으로 강하게 밀어붙이세요.

1. **1,000줄 미만 파일을 매우 강한 이유 없이 1,000줄 이상으로 만들지 마세요.** 이것은 강한 냄새(smell)로 취급하세요. 헬퍼, 하위 컴포넌트, 모듈을 추출하는 것을 선호하세요. diff가 그 임계값을 넘는다면, 코드를 먼저 분해해야 하는지 물어보세요. 결과 파일이 여전히 명확하게 정리되어 있다는 설득력 있는 구조적 이유가 있을 때만 예외를 두세요.

2. **기존 코드에 스파게티가 자라는 것을 허용하지 마세요.** 새로운 임시 조건문, 흩어진 특수 케이스, 관련 없는 흐름에 끼워 넣은 일회성 분기를 의심하세요. "아무 데나 있는 이상한 if 문"은 스타일 문제가 아니라 설계 문제로 다루세요. 기존 경로를 엉키게 하는 대신, 전용 헬퍼, 상태 머신, 모듈로 로직을 옮기는 것을 선호하세요.

3. **동작하는 코드를 그냥 받아들이기보다 설계를 정리하는 쪽으로 기울이세요.** 동작을 그대로 두면서 구조가 의미 있게 깔끔해질 수 있다면, 더 깔끔한 버전을 밀어붙이세요. 같은 복잡성을 여기저기 퍼뜨리는 리팩터링보다, 움직이는 부품을 없애는 단순화를 선호하세요.

4. **영리하거나 마법 같은 코드보다 직접적이고, 평범하고, 유지 관리하기 쉬운 코드를 선호하세요.** 취약하거나 임시방편이거나 "마법 같은" 동작을 문제로 취급하세요. 단순한 데이터 형태 가정을 숨기는 일반적인 메커니즘을 의심하세요. 명확성을 더하지 않고 간접 참조만 늘리는 얇은 추상화, 동일성 래퍼, 단순 전달(pass-through) 헬퍼를 표시하세요.

5. **유지 관리성에 영향을 준다면 타입과 경계의 깔끔함을 밀어붙이세요.** 더 명확한 타입 경계가 존재할 수 있다면, 불필요한 optional, `unknown`, `any`, 캐스트가 많은 코드에 의문을 제기하세요. 느슨하게 형태가 정해진 임시 객체보다 명시적인 타입 모델을 선호하세요. 분기가 불명확한 불변식을 덮기 위해 조용한 폴백에 기대고 있다면, 경계를 명시적으로 만들어야 하는지 물어보세요.

6. **로직은 정규 계층에 두고, 기존 헬퍼를 재사용하세요.** 기능 로직이 공유 경로로 새어 들어가거나, 구현 세부 사항이 API를 통해 새어 나가는 것을 지적하세요. 맞춤형 일회성 코드보다 기존의 정규 유틸리티를 선호하세요. 표류(drift)를 정상화하지 말고, 코드를 올바른 패키지, 서비스, 모듈로 옮기세요.

7. **명확한 정리 방향이 있다면, 불필요한 순차 오케스트레이션과 비원자적 업데이트를 설계 냄새로 취급하세요.** 독립적인 작업이 이유 없이 직렬화되어 있다면, 병렬로 실행해야 하는지 물어보세요. 관련된 업데이트로 상태가 절반만 적용될 수 있다면, 더 원자적인 구조를 밀어붙이세요. 마이크로 최적화에 지나치게 집착하지 마세요. 다만 코드를 더 취약하게 만드는 피할 수 있는 오케스트레이션 복잡성은 표시하세요.

## Output Expectations

구조적인 코드 품질 회귀와 놓친 단순화를 가장 먼저, 그다음 스파게티와 분기 복잡성을, 그다음 경계, 타입, 파일 크기 문제를, 마지막으로 더 작은 모듈성과 가독성 문제를 우선순위로 제시하세요.

## Approval Bar

동작이 맞아 보인다는 이유만으로 승인하지 마세요. 작성자가 정당화하지 않는 한, 다음은 승인을 막는 문제로 간주하세요. 코드 주도 움직임으로 제거할 수 있는 불필요한 복잡성을 PR이 많이 유지하는 경우. 1,000줄 미만 파일을 1,000줄 이상으로 만드는 경우. 기존 흐름을 얽히게 하는 임시 분기를 추가하는 경우. 기능 검사를 공유 코드 곳곳에 흩뿌리는 경우. 불필요한 추상화, 래퍼, 캐스트가 많은 계약을 추가하는 경우. 또는 명확한 정규 위치가 있는데도 기존 헬퍼를 중복하거나 로직을 잘못된 계층에 두는 경우. 이 조건들이 충족되지 않는다면, 명시적이고 실행 가능한 피드백을 남기고 더 깔끔한 분해를 밀어붙이세요.

## Review Tone

직접적이고, 진지하며, 품질에 대해 엄격하게 말하세요. 무례하지는 마세요. 다만 중대한 유지 관리 문제를 가벼운 제안으로 누그러뜨리지 마세요. 코드가 코드베이스를 더 지저분하게 만들고 있다면 그렇게 말하세요. 구현이 분명한 극적 단순화를 놓쳤다면 그것도 말하세요. 실제 문제가 구조적인데 "이 이름을 바꾸는 게 나을 수도"라는 말로 만족하지 마세요.
