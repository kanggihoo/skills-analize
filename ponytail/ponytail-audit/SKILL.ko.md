> 원본: `SKILL.md`. 프런트매터 키와 트리거 문구, 명령어는 원문 그대로 둡니다.

전체 저장소를, 방금 물려받았고 깨지면 자기가 호출될 시니어 개발자처럼 감사합니다. 중요도 순서는 다음과 같습니다: 올바른지, 안전한지, 부하를 견디는지, 테스트되어 있는지, 빠른지, 군더더기가 없는지. 군더더기 없음도 여전히 중요합니다. 추가되는 모든 줄은 누군가 읽고, 테스트하고, 나중에 고쳐야 하기 때문입니다. 이것은 사용자가 요청한 보고서이므로 빠짐없이 씁니다.

## 1. 먼저 지도 그리기

- 사용자가 지정한 대상(폴더, 패키지, 또는 저장소 전체)을 감사합니다. 지정이 없으면 저장소 전체입니다.
- README, 배포와 빌드 설정, 의존성 목록, 진입점(main, 라우트, 핸들러, 잡, CLI 명령), 테스트를 읽습니다.
- 예상 부하를 찾습니다. 스크립트를 한 명이 돌리는 수준인지, 사용자와 프로세스가 동시에 많은 수준인지 확인합니다. 규모는 이 부하에 비추어 판단하고, 어떤 부하를 가정했는지 말합니다.
- 주요 흐름을 처음부터 끝까지 추적합니다. 데이터가 어디서 들어오고, 무엇이 저장되고, 무엇이 나가는지 봅니다. 사용자 입력, 돈, 인증, 데이터 쓰기, 백그라운드 잡, 프로세스 사이에서 공유되는 것이 있는 경로는 끝까지 읽습니다.
- 저장소가 크면 파일 하나하나가 아니라, 실수하면 비용이 가장 큰 곳을 깊이 봅니다. 읽지 않은 부분을 밝힙니다.

## 2. 찾을 것

1. **버그:** 잘못된 결과, 크래시, 놓친 경계 조건(빈 값, 0, 마지막 항목, 반올림, 시간대), 함수가 반환하는 값과 호출자의 기대가 어긋나는 경우, 같은 규칙이 두 곳에서 다르게 적용되는 경우.
2. **위험:** 보안 구멍(인젝션, 약한 난수, 코드에 든 비밀 값, 사용자 입력 검사 누락), 데이터 손실(삼켜진 에러, 잘못된 순서의 쓰기, 트랜잭션 없음).
3. **규모:** 한 명에게는 괜찮지만 여럿에게는 틀린 것. 확인 후 쓰기 사이의 경쟁 상태(race), 모든 프로세스가 반복하는 같은 작업, 계속 커지기만 하는 메모리나 리스트, 항목마다 하나씩 나가는 쿼리, 큰 입력에서의 O(n^2), 공유되어야 하는데 프로세스마다 따로 있는 상태.
4. **테스트 누락:** 위험한 로직(분기, 파서, 돈, 보안, 데이터 쓰기)에 망가지면 실패하는 테스트가 없는 경우. 커버리지가 아니라 좋은 테스트 하나면 충분합니다.
5. **속도:** 큰 저하는 문제입니다. 작은 개선(뜨거운 루프 안에서 반복되는 작업)은 제안입니다. 밀리초를 세는 소프트웨어도 있습니다.
6. **군더더기:** 있으면 안 되거나 더 작아야 할 코드.
   - delete: 죽은 코드, 쓰이지 않는 옵션, 플래그와 config, 추측에 의한 기능
   - reuse: 같은 일을 하는 helper가 둘인 경우(하나만 남기고 경로를 적습니다)
   - stdlib / native: 표준 라이브러리나 플랫폼이 이미 하는 일. 몇 줄이나 플랫폼으로 되는 일을 의존성이 하는 경우
   - yagni: 구현이 하나뿐인 인터페이스, 제품이 하나뿐인 factory, 호출을 그대로 넘기기만 하는 wrapper
   - merge: 함께 바뀌어야 하는 거의 같은 복사본들
   - split: 서로 무관한 여러 일을 하는 함수나 클래스라서 읽거나 테스트하기 어려운 경우. 일의 종류로 나누고, 줄 수로 나누지 않습니다. 함수를 짧게 만들려고만 존재하는 helper로 쪼개지 않습니다.

## 3. 보고하기 전에 확인하기

- 모든 발견 사항에는 구체적인 사례가 있어야 합니다: "이 입력이나 상황이 이런 잘못된 결과로 이어진다". 사례가 없으면 발견 사항이 아닙니다.
- 코드를 쓰이지 않는다고 판단하기 전에, 테스트, fixture, 설정, 문자열이나 동적 참조를 포함해 저장소 전체를 grep합니다.
- `shortcut:`(또는 예전의 `ponytail:`) 주석으로 한계를 적어 둔 임시 방편은, 예상 부하가 그 한계를 이미 넘지 않는 한 발견 사항이 아니라 결정입니다.
- 동작하는 가장 작은 수정안을 제안합니다. 코드를 삭제하는 수정을 우선합니다. 문제에 필요 없는 계층, 프레임워크, config는 추가하지 않습니다.
- 취향에 따른 스타일 지적, "고려해 보세요", 막연한 걱정은 쓰지 않습니다.

## 4. 출력

아주 쉬운 영어를 씁니다: 짧은 문장과 일상 단어. 기술 용어는 처음 나올 때 설명합니다. 독자는 이 코드를 한 번도 본 적이 없을 수 있습니다.

`What this repo does:`로 시작하고, 2~3문장으로 이 저장소가 하는 일과 가정한 부하를 씁니다.

그다음 발견 사항을 세 그룹으로 중요도 순서대로 씁니다. 비어 있는 그룹은 생략합니다.
- **Must fix:** 버그, 보안, 데이터 손실, 예상 부하에서 깨지는 것.
- **Should fix:** 테스트 없는 위험한 코드, 실제 느린 부분, 중복, 여러 일을 섞은 함수, 있으면 안 되는 코드.
- **Nice to have:** 작은 속도 개선, 더 짧은 형태.

모든 그룹을 통틀어 발견 사항에 번호를 붙여서, 사용자가 "2번과 5번을 고쳐"라고 말할 수 있게 합니다. 발견 사항은 최대 20개입니다. 더 작은 것을 뺐다면 그 개수를 밝힙니다.
모든 발견 사항은 아래 네 부분을 모두 갖추고, 각 부분은 한두 문장으로 씁니다.

2. **주문이 엉뚱한 날에 잡힙니다** (`billing/close_day.py:L40-52`)
   - **What this is:** 자정에 이 작업이 하루를 마감하고, 그날의 모든 주문을 청구합니다.
   - **Problem:** "오늘"을 서버 시계에서 가져오는데, 서버 시계는 UTC로 돌아갑니다. 베를린 시간으로 00:30에 들어온 주문은 하루 전 날짜로 청구됩니다.
   - **Fix:** 가게의 시간대에서 날짜를 한 번만 계산합니다: `datetime.now(ZoneInfo("Europe/Berlin")).date()`. 한 줄이며 다른 것은 바뀌지 않습니다.
   - **If we skip it:** 늦은 주문의 날짜가 틀리게 보이고, 회계팀이 이를 손으로 고칩니다.

끝에는 다음을 씁니다.
- `Verdict:` 한 줄. 건강한 상태인지, 무엇을 먼저 고쳐야 하는지.
- 군더더기 발견 사항이 있을 때 `Lean: -<N> lines, -<M> dependencies possible.`
- `Not checked:` 읽지 않았거나 실행해 볼 수 없었던 부분.

발견 사항이 없으면 `What this repo does:`를 쓰고, 이어서 `Healthy. Nothing to fix.`와 확인한 내용을 한 줄로 씁니다.

한 번 실행하는 보고서이며 코드는 바꾸지 않습니다.
